---
name: 로그인 복구 증거 경계
description: 계정 내부 ID, 자동 생성 identifier, 사용자가 전달받은 일반 로그인 ID를 구분하는 복구 완료 기준
---

계정 복구 시 canonical user_id와 사용자가 실제 입력할 일반 로그인 ID를 반드시 구분한다. DB에서 조회한 identifier와 비밀번호로 API가 성공했다는 사실만으로 사용자 실사용 복구를 PASS로 보고하지 않는다.

**Why:** 소셜 가입의 자동 생성 identifier를 직접 사용한 API 성공을 사용자가 알고 있는 일반 ID의 존재로 잘못 보고한 사례가 있었다. 비밀번호 복구와 사용자용 ID 마련은 별개의 완료 조건이다.

**How to apply:** identifier의 저장 필드·종류·생성 경로와 운영자가 안전하게 확인하거나 지정할 수 있는 사용자용 ID인지 확인한다. 자동 생성 내부값만 존재하면 그 사실을 분리 보고하고, 승인된 최소 ID 설정 및 동일 계정 로그인 검증까지 완료해야 실사용 복구 PASS로 보고한다. 안전 입력이 취소되면 임의 등록하지 않고 HOLD로 보고한다. 실제 ID와 개인정보는 메모리에 저장하지 않는다.

배포 후 로그인 smoke는 설치된 앱의 실제 인증·역할 전환 경로를 따라야 한다. 구형 서버 endpoint의 401만으로 기존 비밀번호 오류나 배포 후 로그인 회귀를 확정하지 않는다.

**Why:** 유효한 자격증명과 변경되지 않은 계정도 구형 로그인 경로의 역할/identifier 제한으로 거부될 수 있었다. 실제 앱 흐름은 같은 자격증명으로 정상 인증했고 기존 허용 역할 token 전환도 성공했다.

**How to apply:** 먼저 실제 클라이언트의 호출 경로를 확인한다. 필요한 경우 읽기 전용으로 백업 전후 계정 상태와 제공된 자격증명 일치 여부만 대조하며 값/hash/token을 출력·보존하지 않는다. 잘못된 검증 경로를 맞추려고 비밀번호·계정 역할·인증 정책을 변경하거나 token을 직접 만들지 않는다.
