## 1. 적용 범위와 우선순위

이 문서는 원래 계획의 변경이 아닌 상세화·추가 요구다. Stage 1~10, 제품 목표, 기존 원문과 수용 이력을 보존한다.
아카2000 참고 자료에서는 사용자가 지정한 정보 분류·업무 연결만 취하고, 디자인·버튼명·복잡한 창 구조를 복제하지 않는다.
이번 전달의 요구 텍스트를 근거로 삼으며 외부 제품 화면의 시각적 동일성을 검증했다고 주장하지 않는다.

**사용자 확정:** 빠른 Drawer + 넓은 전체 회원정보, 같은 회원/수강/청구/결제 기준, 상위 탭·세부 접기, 복수 반 보존, 장부 중복 금지, 읽기/수정/내보내기 권한 분리.
**이번 구현상 선택:** 조회 가능한 기본정보·연락처·수강반·메모·성장리포트 5탭, 조회 전용, 같은 회원 OPEN의 view/tab 입력 확장, 회원/탭별 세션 내 스크롤. 탭 개수·CSS 치수는 제품 영구 규칙이 아니다.
**미확정 정책:** 최초 일할 계산·청구주기 종류·할인 우선순위·연락처 관계·안전정보 열람자·영수증 제공자·환불/이월·지출 범위.

현재 공통 Action 구현을 보존한다. 직전 첫 AI Vertical Slice 통합 지시는 이 보완 완료 후에도 자동 재개하지 않는다.
시작 기준 HEAD에는 조회/OPEN 공통 기반이 있으며 이번 작업 시작 시 제공 첨부 외 미커밋 변경은 없었다. 회원 수정·반이동·모델 실행을 새로 시작하거나 기존 소스를 삭제/되돌리지 않는다.

## 3. PC·모바일 공통 데이터와 메뉴 지도

PC는 직원의 회원·수강·청구/수납·매출 등 운영 중심, 모바일은 보호자·강사·관리자 역할 중심이다.
메뉴가 같을 필요는 없고 PC 전용 정보를 모바일에 무조건 노출하지 않는다.
동일 entity ID·Pool·권한과 원천 기록을 공유하되 읽기/수정/내보내기를 구분한다.
새로운 보호자·수강·금융 계약은 기존 모바일 소비자와 필드의 null/배열/상태 의미를 유지하는 호환 확장을 전제로 한다. 이번 모바일·Backend·DB schema 변경은 없다.
앱 구독/RevenueCat/IAP는 서비스 이용료다. 수영장 회원 수강료 장부·실제 결제 거래의 대용으로 쓰지 않는다.

메뉴 검색·즐겨찾기는 확장 후보다. 빈 업무 화면·성공하지 않는 실행 버튼을 대량 생성하지 않는다.

## 5. 넓은 전체 회원정보의 이번 구현

- 빠른 Drawer 유지, “전체 회원정보”로 중앙 업무 영역을 사용하는 페이지 진입.
- 기존 하단 AI와 정상 flex 공간 분할. 새 Windows 창·겹치는 대형 modal 없음.
- 상단 이름/상태·복수 반·주당 횟수·등록일, 미연결 수강기간·청구/납입을 구분. 중요 표시 원천이 없으므로 기존 메모를 “중요”로 승격하지 않음.
- 기본정보 / 연락처·보호자 / 수강반 / 메모 / 성장리포트만 노출. 탭 내부 섹션은 접고 펼칠 수 있음.
- 회원 메모와 상담·청구별 수납 메모는 별도 의미. 현재 메모만 독립 읽기 섹션에 표시.
- 없는 동의·가족·건강·금액·수강 종료일을 정상/0/없음으로 추정하지 않음.
- 현재 화면 요청은 기존 office.member.open에 {memberId,view:'full',tab}를 추가. 임의 URL·API·SQL은 계속 거부.
- 기존 QueryClient의 students를 공유하고 추가 광범위 개인정보 GET을 만들지 않음. 성장 이력은 기존 키/endpoint만 사용.
- 목록 검색/필터/페이지/좌우 스크롤과 상세 회원/탭의 본문 스크롤은 세션에서 별도 보존. 뒤로/앞으로·결과 OPEN은 같은 목적지 의미.
- 사용자·Pool/권한 교체 시 기존 세션 subtree 폐기. 조회 실패 시 stale 회원정보로 성공을 표시하지 않음.
- 수강 정보는 모두 조회 전용. 편집·AI 실행·결제·업로드 연결 없음.

## 6. 청구·납입 공통 설계 — 구현하지 않음

회원 상세의 청구/납입 탭과 전체 청구·미납·매출 메뉴는 같은 원천을 조회해야 한다. 별도 회원별 장부나 localStorage 저장 금지.

구분할 entity/의미:
1. 상품/수강료 조건: 기준 금액, 회원 적용 금액, 할인 방식/값/사유, 적용 시작/종료, 주기·청구일·납부기한.
2. 청구와 항목: 회원, 수강기간, 항목별 금액, 납부기한, 메모. 초기 청구·일할 계산·월별/횟수제 지원은 정책 미확정.
3. 납부와 배분: 납부 일자·금액·수단·처리자, 연결 청구·배분 금액. 부분납부/여러 청구 배분 및 중복 요청 방지.
4. 실제 승인 거래: 제공자 거래 ID·승인 상태/시각/금액. 수기 납부 등록과 카드 승인 버튼을 분리.
5. 할인/조정/취소/환불/이월: 원 기록·금액·사유·처리자·상태 연결. 장부 정정과 실제 승인 취소를 분리.
6. 증빙·이력: 과거 납부를 현재 조건 변경으로 덮지 않으며 사유 없는 이력 삭제 금지.

“이번 청구만 변경”과 “다음 청구부터 수강료 조건 변경”을 구분한다. 반복 청구는 대상·기간·원천 조건에 대한 멱등 키/경쟁 방지 계약이 필요하나 이번 schema를 선개발하지 않는다.
조회는 회원별 납입 이력 및 전체/반별/회원별 미납을 연결한다. 기간·기준일·현재/지난회원·상품/반·수단·처리자 필터를 명시한다.
인원/청구 건수/거래 건수/금액을 구분하고 납입률/미납률의 분모·기준 시점을 표시한다. 순수납·청구·미납을 모두 같은 매출로 취급하지 않는다.
영수증·현금영수증·가상계좌·실제 결제/취소/환불은 제공자와 기존 Stage 9 승인에 따른 후속 범위다.

## 7. 공통 목록·내보내기 — 기존 구현 매핑만

공통 목록은 검색·필터·정렬·건수·로딩·빈 결과·실패·재시도와 복귀 상태를 명시한다. 이번 기존 회원목록의 정렬/출력 범위를 임의 확장하지 않는다.
엑셀의 기본 출력은 현재 검색/필터 결과 전체이며 현재 페이지·선택 행과 구분한다.
실제 연결 전 조회/내보내기 권한, 열 정의·건수·조회조건·기준시각, 전화번호 선행 0·식별자·날짜·금액 형식, 수식 주입 방어를 확인해야 한다.
메뉴와 AI는 동일 조회/출력 계약을 사용한다. 기존 export는 후보이지 이번에 허용한 Desktop 기능이나 완성된 공통 출력이 아니다. 가짜 파일/성공 버튼을 만들지 않는다.

## 8. 검증·전달·정지

합성 회원으로 목록→Drawer→전체정보, 직접 OPEN/탭/반복 OPEN/Back/Forward, 독립 스크롤, 초안/첨부, 실패/없는 대상/권한, 이전 회원·세션의 늦은 이력, 문자열/배열 일정·복수 반·연락처·긴 메모를 제한 검증한다.
실제 CSS 브라우저에서 일반/접기/크게 보기와 좁고 낮은 창을 확인하고, 기존 Web 영향 범위·Desktop 타입·필요 build·diff만 확인한다.
기존 Action/Stage 2 PASS 증거를 재사용하며 전체 suite·설치/로그인 수용 검사는 반복하지 않는다.
기존 제작 도구로 HEAD+diff/신규 소스를 고정한 unsigned Windows 내부 설치본을 한 번 생성한다. payload/민감 파일 제외/해시/분할 재결합 및 기존 설치본 보존을 확인한다.
Windows 사용자 수용은 별도다. 로컬 fixture/Chromium PASS를 실기기 PASS로 바꾸지 않는다. 완료 보고 후 정지하고 AI 수정·반이동 작업을 자동 재개하지 않는다.
