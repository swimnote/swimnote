[SWIMNOTE 긴급 수정 — 보강반 배정 회차 선택 기능 구현 지시]

조사 보고서와 확정 정책을 기준으로 구현한다.

핵심 목적:

보강반 배정 시 단순히 반만 선택하는 구조를 다음 구조로 변경한다.

보강할 반 선택
→ 해당 반의 실제 수업 회차 선택
→ 보강 배정 또는 사후 완료 처리

현재 존재하는 미래 보강 예약 기능은 제거하지 않는다.

다음 세 가지를 모두 지원해야 한다.

1. 미래 수업 사전 예약
2. 오늘 수업 당일 배정
3. 이미 진행된 수업 사후 처리

코드 수정 후에는 Commit·Push·서버 배포·OTA를 바로 하지 말고,
먼저 구현 완료 보고서와 실제 diff를 제출하고 멈춘다.

━━━━━━━━━━━━━━━━━━━━━━
1. 확정 정책
━━━━━━━━━━━━━━━━━━━━━━

보강 배정 가능 회차:

- 결석일 이후의 실제 수업일
- 과거 수업일
- 오늘 수업일
- 미래 수업일
- 보강 유효기간을 초과한 날짜는 제외
- 결석일보다 이전 날짜는 제외

오늘 수업은 현재 시각과 관계없이 선택 가능해야 한다.

따라서 다음을 모두 허용한다.

- 오늘 시작 전 수업
- 오늘 진행 중 수업
- 오늘 이미 끝난 수업
- 실제 수업 후 앱에서 뒤늦게 처리하는 경우

미래 수업은 기존 사전 예약 기능이므로 유지한다.

임의의 달력 날짜를 선택하게 하지 않는다.

반의 수업 요일과 실제 운영 데이터를 기준으로 생성된
유효한 수업 회차만 선택하게 한다.

시작:
- 결석일 다음 수업 회차부터
- 현재 서비스에서 결석 당일 보강을 허용한다면 결석일 포함 여부를 기존 정책에서 확인하고 유지

종료:
- makeup_sessions.expire_at까지
- expire_at이 없으면 기존 보강 유효기간 계산 규칙 사용

3. 실제 수업 회차 생성 원칙
━━━━━━━━━━━━━━━━━━━━━━

먼저 Repository를 확인한다.

우선순위:

1. 기존 날짜별 수업 occurrence 또는 스케줄 테이블이 있으면 그것을 사용
2. 휴강·취소·공휴일 예외 데이터가 있으면 반드시 반영
3. 별도 occurrence 데이터가 없다면 class_groups의
   schedule_days + schedule_time을 이용해 회차 생성
4. 임의 날짜 전체를 노출하지 않음

회차 데이터 구조:

interface MakeupClassOccurrence {
  class_group_id: string;
  class_name: string;
  occurrence_date: string;    // YYYY-MM-DD
  schedule_time: string;      // HH:mm
  teacher_id?: string | null;
  teacher_name?: string | null;
  available_slots: number;
  is_full: boolean;
  is_past: boolean;
  is_today: boolean;
  is_future: boolean;
}

날짜 계산은 Asia/Seoul 기준으로 통일한다.

금지:

- new Date().toISOString().slice(0, 10)로 오늘 계산
- 기기 로컬 시간에만 의존
- UTC 날짜와 KST 날짜 혼용

기존 kstTodayStr 또는 동일하게 검증된 공통 KST 함수를 재사용한다.

4. 서버 API 설계
━━━━━━━━━━━━━━━━━━━━━━

기존 API를 억지로 전역 변경하지 말고,
보강 기능 전용 회차 조회 API를 추가하거나 기존 보강 API에 안전하게 확장한다.

권장 API:

GET /teacher/makeups/:makeupId/eligible-occurrences

Query 선택값:
- class_group_id
- include_full=true

응답 예시:

{
  "makeup_id": "mk_xxx",
  "absence_date": "2026-08-03",
  "expire_at": "2026-08-31",
  "occurrences": [
    {
      "class_group_id": "cg_xxx",
      "class_name": "금 19:00반",
      "occurrence_date": "2026-08-07",
      "schedule_time": "19:00",
      "available_slots": 1,
      "is_full": false,
      "is_past": true,
      "is_today": false,
      "is_future": false
    }
  ]
}

기존 eligible-classes API의
HAVING available_slots > 0 조건을 전역에서 단순 제거하지 않는다.

일반 반배정·반이동에 영향이 생기면 안 된다.

보강 전용 조회에서는 정원이 찬 반도 반환한다.

반환 정책:

- available_slots > 0: 정상 선택 가능
- available_slots <= 0: 목록에는 표시하고 정원 초과 경고 대상으로 구분
- inactive/삭제/폐강 반: 제외
- 권한 없는 수영장 반: 제외
- 다른 선생님 반: 기존 인계 정책에 따라 포함

━━━━━━━━━━━━━━━━━━━━━━
5. 정원 초과 정책
━━━━━━━━━━━━━━━━━━━━━━

사전 예약:

- 미래 수업
- 정원이 없으면 원칙적으로 저장 차단
- 기존 서비스가 관리자 예외 배정을 지원하면 기존 권한 정책 유지

당일·사후 처리:

- 학생이 실제 수업에 참여한 사실을 기록해야 하므로
  정원 초과만으로 반 자체를 숨기면 안 됨
- 경고 후 저장 가능

경고 문구 예시:

정원을 초과한 반입니다.
실제로 보강 수업에 참여한 경우에만 처리해 주세요.

[취소] [그래도 처리]

권한 정책:

- 기존 교사가 보강 사후 처리를 할 수 있었다면 동일 권한 유지
- 새로운 관리자 전용 권한을 임의로 만들지 않음
- 현재 권한 구조를 먼저 확인하여 최소 변경

서버는 클라이언트 경고만 믿지 말고 날짜 기준으로 구분한다.

- occurrence_date > KST today: 미래 예약
- occurrence_date = KST today: 당일 처리
- occurrence_date < KST today: 사후 처리

6. 저장 API
━━━━━━━━━━━━━━━━━━━━━━

기존 makeup_sessions 구조를 재사용한다.

반드시 저장할 값:

- assigned_class_group_id
- assigned_class_group_name
- assigned_teacher_id/name
- assigned_date = 선택한 occurrence_date
- handed_to_teacher_id/name
- status
- completed_at 또는 기존 완료 상태 필드

신규 DB 컬럼은 추가하지 않는다.

assignment_type은 아래 기준으로 서버에서 계산 가능하다.

- scheduled: assigned_date > KST today
- same_day: assigned_date = KST today
- retroactive: assigned_date < KST today

현재 응답이나 UI에서 구분이 필요하면 DB 컬럼 추가 대신
API 응답 계산 필드로 제공한다.

예:

{
  "assignment_type": "retroactive"
}

실제 수업 시간은
assigned_class_group_id → class_groups.schedule_time으로 조회한다.

7. 기존 API 날짜 검증 보강
━━━━━━━━━━━━━━━━━━━━━━

현재 assign / complete-direct API가 날짜를 아무 값이나 받아 저장한다면
서버 검증을 추가한다.

검증 조건:

1. YYYY-MM-DD 유효 날짜
2. assigned_date >= absence_date
3. assigned_date <= expire_at
4. 선택한 날짜가 대상 반의 실제 schedule_days에 해당
5. 대상 반이 해당 수영장 소속
6. 대상 반이 active 상태
7. 동일 보강 건이 이미 완료·취소 상태인지 확인
8. 동일 결석 건에 중복 배정되지 않았는지 확인

클라이언트가 임의 날짜를 보내도 서버가 거부해야 한다.

에러 코드 예시:

- INVALID_ASSIGNED_DATE
- DATE_BEFORE_ABSENCE
- MAKEUP_EXPIRED
- CLASS_NOT_SCHEDULED_ON_DATE
- MAKEUP_ALREADY_COMPLETED
- DUPLICATE_MAKEUP_ASSIGNMENT

기존 API 응답 Contract는 가능한 한 유지한다.

11. 중복·멱등성
━━━━━━━━━━━━━━━━━━━━━━

동일 makeup_session에 대해 동일 회차가 중복 저장되지 않도록 한다.

최소 검증:

- status가 completed이면 재완료 차단
- 동일 makeup_session의 동시 요청 직렬화
- 동일 학생·assigned_date의 attendance는 기존 ON CONFLICT 정책 유지
- API 재시도 시 출결 횟수가 두 번 증가하지 않음
- 보강 현황이 두 건 생성되지 않음
- 잔여 보강 횟수가 두 번 차감되지 않음

필요하면 makeup_sessions 행을 transaction에서 SELECT FOR UPDATE 한다.

DB Migration 없이 기존 PK와 상태 검증으로 구현 가능한지 우선 확인한다.

13. 구현 전 추가 확인
━━━━━━━━━━━━━━━━━━━━━━

코드 수정 전에 아래만 확인하고,
확인 결과를 구현 보고서에 포함한다.

1. 휴강·취소·공휴일 데이터 저장 위치
2. 실제 occurrence 테이블 존재 여부
3. class_groups.schedule_days 형식
4. expire_at 계산 방식
5. 동일 결석일 당일 보강 허용 여부의 기존 정책
6. complete-direct가 attendance에 기록하는 정확한 날짜
7. 정원 계산에 기존 보강생이 포함되는지
8. 다른 선생님 반 인계 저장 필드
9. 미래 배정과 완료 상태 전이

확인 후 설계 범위를 벗어나지 않는 선에서 구현한다.
새로운 구조가 필요하면 임의 구현하지 말고 보고 후 멈춘다.

A. 회차 생성

1. 월요일 반 → 월요일 날짜만 표시

4. expire_at 이후 회차 제외
5. 오늘 회차 포함
6. 미래 회차 기존대로 포함

1. 어제 수업 선택

4. 미래 배정 후 배정된 보강 목록 표시

E. 정원 초과

1. 과거·오늘 정원 초과 반도 목록 표시
2. 경고 표시
3. 확인 후 저장
4. 취소 시 미저장
5. 일반 반배정의 정원 정책은 변하지 않음

F. 중복

1. 동일 보강 세션 두 번 완료 차단
2. 버튼 연속 탭 중복 저장 방지
3. API 재시도 멱등성
4. attendance 중복 없음

1. iOS 회차 선택 서브모달 표시
2. 스크롤 가능
3. 마지막 회차 접근 가능
4. 닫기 가능
5. Android 동일 확인
6. 기존 반이동·보충수업·미배정 모달 회귀 없음
