[ 받은 알림 ] [ 내 요청 ]

두 개의 탭을 가진다.

(parent)/notifications.tsx

알림
├─ 받은 알림
└─ 내 요청

5. 요청 작성 Modal — 완성형으로 구현
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이번에는 Modal을 한 줄씩 패치하지 않는다.

처음부터 정상적인 Bottom Sheet 입력 Modal 구조로 완성한다.

목표 구조:

Modal
└─ View modalRoot
   ├─ Pressable backdrop
   │   └─ absoluteFill
   │
   └─ KeyboardAvoidingView / keyboard 대응 container
       └─ View modalSheet
           ├─ Header
           │   ├─ "새 요청 보내기"
           │   └─ "취소"
           │
           └─ ScrollView
               ├─ 학생 선택
               ├─ 요청 유형
               ├─ 내용 TextInput
               ├─ 안내 문구
               ├─ 오류 메시지
               └─ 요청 보내기 버튼

중요:

Backdrop과 sheet를
부모/자식 Pressable 전파 방식으로 억지 차단하지 않는다.

Backdrop은 별도 absolute layer.

Sheet는 그 위 별도 layer.

Modal 내부 터치가 backdrop dismiss와 충돌하지 않게
구조적으로 분리한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. Modal 크기
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

작은 반쪽 Modal 금지.

기본 목표:

화면 약 85~90%까지 사용 가능한 큰 Bottom Sheet.

내용에 따라 충분한 작업 공간 제공.

고정 flex:0 금지.

Scroll 영역 높이가 0이 되는 구조 금지.

modalSheet 내부:

Header
+
Scroll Area

가 실제 레이아웃 공간을 확보해야 한다.

필요한 부모에:

flex: 1
minHeight: 0

적용.

그러나 임의 absolute/height patch를
여러 개 쌓지 않는다.

중요:

requests.tsx를 지금 당장 삭제하지 않는다.

기존 설정 메뉴나 deep link가
/(parent)/requests를 호출할 수 있기 때문이다.

따라서 requests.tsx는
통합 notifications의 내 요청 탭으로
안전하게 redirect하는 compatibility route로 변경 가능.

예:

router.replace({
  pathname: "/(parent)/notifications",
  params: {
    tab: "requests",
    requestId
  }
})

단 redirect loop 절대 금지.

notifications.tsx는 requests.tsx로 다시 보내면 안 된다.

방향은 단방향:

requests
→ notifications requests tab

만 허용.
