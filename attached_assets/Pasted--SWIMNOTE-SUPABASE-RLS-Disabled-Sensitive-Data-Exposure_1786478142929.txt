[SWIMNOTE SUPABASE 긴급 보안 감사 — RLS Disabled / Sensitive Data Exposure]

Supabase에서 다음 보안 경고가 발생했습니다.

대상 프로젝트:

1. swimnote의 프로젝트
2. 수영노트-풀-db

경고:

- rls_disabled_in_public
- 공개적으로 접근 가능한 테이블
- 민감한 데이터가 공개적으로 접근 가능할 가능성

중요:

지금 바로 RLS를 일괄 활성화하거나
Supabase의 자동 “문제 해결” 버튼을 누르지 마십시오.

기존 SWIMNOTE / AI Engine의 DB 접근이 깨질 수 있으므로
먼저 전체 접근구조를 감사합니다.

STEP 2. 실제 접근 경로 확인
━━━━━━━━━━━━━━━━━━━━━━

각 테이블마다 실제 Repository에서 누가 접근하는지 찾으십시오.

분류:

A. Mobile App에서 Supabase Client 직접 접근
B. SWIMNOTE API Server에서 접근
C. AI Engine Server에서 접근
D. Worker/Batch에서 접근
E. 관리자 Tool에서 접근
F. 현재 미사용

각 접근에서 사용하는 credential/role도 확인:

- anon
- authenticated
- service_role
- direct postgres connection
- server secret

secret 값 자체는 보고하지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
STEP 3. 공개 Data API 필요 여부
━━━━━━━━━━━━━━━━━━━━━━

각 테이블을 다음으로 분류하십시오.

CLASS 1
클라이언트 Data API 접근 필요
→ RLS + 정확한 Policy 필요

CLASS 2
서버에서만 사용
→ 클라이언트 접근 차단
→ 필요하면 exposed schema에서 제거 또는 권한 제한 검토

CLASS 3
민감 데이터
→ anon/authenticated 공개 접근 금지

CLASS 4
미사용
→ 제거 여부 별도 검토

STEP 4. 정책 설계
━━━━━━━━━━━━━━━━━━━━━━

각 테이블별로 필요한 작업을 설계:

- ENABLE ROW LEVEL SECURITY
- SELECT policy
- INSERT policy
- UPDATE policy
- DELETE policy

필요한 경우 사용자/수영장 tenant 범위:

user_id
guardian_id
pool_id
organization_id

등 실제 schema 기준으로 제한하십시오.

예상으로 만들지 말고
현재 DB FK / Auth 구조에 맞춰 설계하십시오.
