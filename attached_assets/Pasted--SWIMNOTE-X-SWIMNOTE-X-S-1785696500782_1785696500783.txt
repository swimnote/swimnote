[SWIMNOTE X — 최종 실행순서 및 개발 통제 헌법]

이 문서는 SWIMNOTE X 개발의 최종 실행순서와 작업 통제 원칙을 확정하기 위한 문서입니다.

기존에 제출된 SWIMNOTE X 최종 설계서 v3.3.4는 기술 구현 기준 최종본입니다.

이번에 변경된 것은 기술 설계가 아닙니다.

변경된 것은 오직 다음 두 가지입니다.

1. 전체 기능을 PART 1·PART 2·PART 3으로 분리
2. 중간에 반드시 선행되어야 하는 설계를 넣기 위해 WP 실행순서 재배치

따라서 기존 v3.3.4에서 확정된 다음 설계를 임의로 변경하면 안 됩니다.

* DB 구조
* 컬럼
* ENUM
* Constraint
* Index
* Global Template 구조
* Advisory Lock
* Audit 구조
* AI Contract V1.3
* candidate_id
* MatchTokenV2
* HMAC 검증
* Growth Event
* Confidence Config
* Evidence 검증
* 학생 비식별화 정책
* Parent AI Reservation
* Growth Report 버전 추적
* Migration 실패 정책
* Rollback 설계

실행순서가 바뀌었다는 이유로 기술 구조를 새로 설계하거나 단순화하거나 대체하지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━

1. 실행순서를 변경한 이유
    ━━━━━━━━━━━━━━━━━━━━━━

v3.3.4 기존 순서에는 다음 기능이 하나의 Migration과 WP 흐름에 함께 포함되어 있었습니다.

* X모드 기반
* Global Template
* Growth Event
* Parent AI
* Growth Report
* PPT 관련 기반

그러나 실제 개발에서는 다음 문제가 있습니다.

1. X모드 자체가 완성되기 전에 Parent AI와 성장리포트를 함께 넣으면 검증 범위가 너무 넓어집니다.
2. 일반 SWIMNOTE와 X모드의 격리가 확인되기 전에 학부모 AI·결제·리포트를 연결하면 장애 원인 추적이 어려워집니다.
3. 성장리포트는 실제 평가항목·계산 규칙·설문·인터뷰 구조를 별도로 확정해야 하므로 임의 구현할 수 없습니다.
4. 일반모드 기능 축소는 X모드와 학부모 기능이 모두 검증된 이후에만 안전하게 진행할 수 있습니다.
5. WP별로 설계·코드·테스트를 확인하지 않고 대규모 구현을 한 번에 진행하면 실제 Repository와 다른 내용을 완료했다고 보고할 위험이 커집니다.

따라서 기술 설계는 유지하면서 실행순서만 다음과 같이 나눕니다.

PART 1
SWIMNOTE X모드 핵심 구현
PART 2
학부모 AI 커리큘럼 검색
+ 성장리포트
+ 학부모 결제
PART 3
일반모드 기능 제거·축소·정리

이 변경은 v3.3.4를 폐기하는 것이 아닙니다.

v3.3.4의 각 설계를 실제 필요한 PART와 WP에 배치하여 순차적으로 구현하는 것입니다.

헌법 1조 — 설계 고정

승인된 전체 설계와 실행순서를 중간에 임의 변경하지 마십시오.

금지:

* 새 기능 임의 추가
* 기존 기능 임의 삭제
* 테이블 임의 추가
* 컬럼 임의 추가
* API 임의 추가
* 상태값 임의 추가
* 설계에 없는 자동화 추가
* 설계에 없는 fallback 추가
* 설계에 없는 Background Job 추가
* 다음 PART 기능 선행 구현
* 다음 WP 기능 미리 구현
* “향후 필요할 것 같다”는 이유로 범위 확장
* Repository 구조를 이유로 승인된 핵심 설계를 다른 구조로 대체

더 단순한 구조가 있다고 판단되면 구현하지 말고 설계 단계에서 대안으로만 보고하십시오.

사용자가 승인하지 않으면 기존 확정 설계를 유지합니다.

헌법 2조 — Repository 확인 우선

Repository에서 직접 확인하지 않은 내용을 사실처럼 보고하지 마십시오.

모든 보고는 다음 세 가지 중 하나로 구분하십시오.

* REPOSITORY_VERIFIED
* NOT_FOUND
* NEEDS_VERIFICATION

추정한 내용을 REPOSITORY_VERIFIED로 표시하면 안 됩니다.

파일명·함수명·테이블명·API·호출 경로·현재 동작은 실제 코드를 열어 확인한 뒤 보고하십시오.

헌법 3조 — WP별 사전 설계 승인

모든 WP는 아래 순서를 지킵니다.

Repository 조사
→ 현재 구조 보고
→ 해당 WP 설계 계획 제출
→ 수정 파일·함수·Contract·테스트 제출
→ 사용자 검수
→ 사용자 승인
→ 해당 WP만 구현
→ 구현 결과 제출
→ 실제 코드 재확인
→ 타입체크·테스트
→ 일반모드 회귀검증
→ 사용자 승인
→ 다음 WP

설계 계획을 제출한 뒤 사용자 승인 전에는 코드를 수정하지 마십시오.
