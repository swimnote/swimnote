4. 삭제 방식
━━━━━━━━━━━━━━━━━━━━━━

현재 실제 Production schema/FK를 기준으로
referential integrity를 깨뜨리지 않는 안전한 순서로 삭제한다.

단순히 swimming_pools row부터 강제 삭제하지 않는다.

NO ACTION FK가 있으면 필요한 child record를 먼저 처리한다.

삭제 대상에 속한 테스트 데이터만 정리한다.

다른 pool의 데이터는 절대 수정하지 않는다.

users를 처리할 때도
해당 user가 다른 보존 pool 또는 다른 정상 관계에서 사용되는지
먼저 확인한다.

공유 user라면 임의 삭제하지 않는다.

R2 파일이 실제 존재하는 경우:
삭제 대상 pool 소유임이 확실한 object만 cleanup한다.
다른 pool의 object는 절대 건드리지 않는다.

결제/구독 기록이 존재한다면
실제 결제 이력인지 테스트 레코드인지 확인한다.
예상하지 못한 실제 결제 이력이면 STOP/HOLD한다.

가능한 DB 작업은 transaction으로 처리한다.

삭제 중 오류가 발생하면
부분 삭제 상태로 방치하지 말고 rollback 가능한 범위는 rollback한다.
