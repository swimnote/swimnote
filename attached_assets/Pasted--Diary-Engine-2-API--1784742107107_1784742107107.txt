# Diary Engine 2차 심층 조사 요청 — 실제 버그 근본 원인 특정

제출한 보고서는 전체 파일, 테이블, API 현황을 확인하는 데는 도움이 됐습니다.

하지만 이번 요청의 핵심이었던 아래 실제 버그의 근본 원인은 아직 특정되지 않았습니다.

이번에도 바로 수정하지 마세요.

정상 구조 설명이 아니라 실제 문제 데이터와 실행 경로를 추적하여
각 버그의 원인을 코드·DB·API 응답 수준에서 확정해 주세요.

==================================================
현재 확인된 실제 버그
==================================================

1. 일지에 실제 선택한 사진은 공통 2장 + 개인 2장, 총 4장인데 7장이 표시됨
2. 삭제한 이전 일지 사진이 새 일지에 섞여 나옴
3. 선생님 화면에서는 사진이 보이지만 학부모 화면에서는 보이지 않음
4. 개인앨범에 저장 직후 목록에 보이지 않고 재진입해야 나타남
5. 개인앨범 썸네일이 회색 placeholder 상태로 남음
6. 일지 저장 후 일지 이력이 아니라 홈 화면으로 이동함
7. 학부모 일지에서 동일한 문장이 반복 표시됨

==================================================
1. 사진 저장 구조를 실제 코드 기준으로 확정
==================================================

아래 네 종류의 미디어가 각각 어디에 어떻게 저장되는지
실제 함수명, API Body, DB 컬럼과 함께 추적하세요.

A. 공통 일지 — 기기에서 직접 업로드한 사진
B. 학생 개인 일지 — 기기에서 직접 업로드한 사진
C. 공통 일지 — 앨범에서 선택한 사진
D. 학생 개인 일지 — 앨범에서 선택한 사진

각 유형마다 다음을 표로 제출하세요.

- 앱 상태 변수
- 업로드 API
- R2 object key
- DB 테이블
- DB PK
- diary_id 또는 journal_id 저장 위치
- student_id 저장 위치
- 공통/개인 구분 필드
- 조회 API
- 삭제 시 연결 해제 방식

특히 현재 보고서에서는 photo_assets_meta.journal_id만 확인됐고,
학생 개인사진의 student_id 및 공통/개인 구분 구조가 확인되지 않았습니다.

정확히 조사하세요.

==================================================
2. /diary/upload 레거시 경로와 v2 일지의 관계
==================================================

POST /diary/upload가 아직 사용되고 있습니다.

다음을 확인하세요.

- 업로드 결과 URL 또는 media ID가 어디에 저장되는지
- class_diaries와 어떻게 연결되는지
- class_diary_student_notes와 어떻게 연결되는지
- photo_assets_meta에도 레코드가 생성되는지
- 본문에 URL을 삽입한다는 설명이 실제 코드상 무엇을 뜻하는지
- 동일 사진이 URL 방식과 photo_assets_meta 방식으로 이중 등록될 가능성이 있는지
- GET /diaries/:id에서 두 경로를 합쳐 반환하는지

기기 직접 업로드와 앨범 선택 사진이 서로 다른 저장 방식을 사용한다면
현재 중복·누락 문제의 핵심 후보로 표시하세요.

==================================================
3. 문제 일지의 실제 DB 데이터 추적
==================================================

문제가 발생한 일지를 실제 DB에서 찾아 다음 데이터를 제출하세요.

조건:
- 목요일 19:00 반
- 해당 문제 발생 날짜
- 사용자가 공통사진 2장, 개인사진 2장을 선택
- 앱에서는 총 7장 표시

반드시 다음 표를 만드세요.

- diary_id
- lesson_date
- class_group_id
- diary is_deleted
- media/photo ID
- R2 URL 또는 object key
- photo_assets_meta.journal_id
- student_id
- 공통/개인 분류
- 원본 album/photo record ID
- created_at
- deleted 여부
- 조회 결과에 포함된 이유

표시된 7장 각각이 어디에서 왔는지 반드시 특정하세요.

“가능성이 있다”가 아니라 실제 7개 media record를 추적하세요.

==================================================
4. 삭제 일지와 사진 연결 조사
==================================================

일지를 DELETE /diaries/:id로 소프트 삭제할 때 다음을 확인하세요.

- photo_assets_meta.journal_id가 유지되는지
- 학생별 개인사진 연결이 유지되는지
- R2 파일이 유지되는지
- 앨범 원본 사진과 일지 연결이 분리되는지
- 조회 API가 삭제된 diary의 사진을 제외하는지
- 새 일지를 작성할 때 기존 journal_id가 재사용되거나 잘못 매칭될 수 있는지

관리자 photo_only bulk-delete가 no-op인 것도
현재 버그와 관련이 있는지 확인하세요.

삭제된 일지 사진이 다시 조회되는 정확한 JOIN 또는 WHERE 조건을 제시하세요.

==================================================
5. 선생님 사진 API와 학부모 사진 API 비교
==================================================

같은 diary_id와 같은 student_id로 아래 응답을 실제 비교하세요.

- GET /diaries/:id
- GET /parent/diary/:diaryId/photos

각 응답에서 다음을 비교하세요.

- 총 사진 수
- photo/media ID
- student_id
- 공통사진 여부
- deleted 필터
- diary/journal 연결 조건
- URL 필드명
- thumbnail URL 필드명
- parent_visible 또는 공개 조건
- HTTP 상태와 실제 응답 JSON

선생님 응답에는 있는데 학부모 응답에서 빠지는 사진을
각 media ID별로 나열하고 빠지는 조건을 정확히 특정하세요.

==================================================
6. 학부모 앱 렌더링 경로 조사
==================================================

학부모 앱의 두 화면을 모두 확인하세요.

- (parent)/diary.tsx
- (parent)/swim-diary.tsx

각 화면에서:

- 사진 API를 실제 호출하는지
- DiaryPhotoStrip에 어떤 props를 넘기는지
- diaryId와 studentId가 올바른지
- API 응답 필드명과 컴포넌트 타입이 일치하는지
- thumbnail URL 또는 원본 URL을 사용하는지
- Image onError 로그가 있는지
- 403/404가 발생하는지
- R2 signed URL 만료 문제가 있는지

==================================================
7. 개인앨범 즉시 갱신 및 썸네일 조사
==================================================

개인앨범 저장 후 다음 흐름을 실제 추적하세요.

저장 버튼
→ 업로드 API
→ DB insert/update
→ 성공 응답
→ 로컬 state 변경
→ picker modal 데이터
→ 재조회 여부
→ 화면 렌더링

저장 직후에는 안 보이고 재진입 후 나타나는 정확한 원인을
다음 중 어디인지 확정하세요.

- refetch 미호출
- cache invalidation 누락
- state append 누락
- modal 내부 stale state
- navigation focus에서만 fetch
- 서버 응답 누락

회색 썸네일도 실제 URL과 HTTP 응답을 기록하세요.

- URI
- 상태 코드
- content-type
- thumbnail 존재 여부
- R2 object 존재 여부
- 앱 Image onError 내용

8. 저장 후 홈 화면 이동 원인 특정
==================================================

보고서에는 정상 흐름이 subView="history"라고 되어 있지만
실제 앱에서는 홈 화면으로 이동합니다.

실제 onSave 성공 이후 실행되는 모든 코드를 순서대로 추적하세요.

다음을 전체 검색하세요.

- router.push
- router.replace
- router.back
- navigation.navigate
- setSubView
- 성공 Alert의 onPress
- useEffect redirect
- layout redirect
- 세션 또는 역할 기반 redirect

정확히 어느 코드 줄이 홈으로 이동시키는지 확정하세요.

==================================================
9. 학부모 일지 문장 중복 원인 특정
==================================================

문장이 중복된 일지 하나를 골라 다음 세 단계를 비교하세요.

A. DB 원본
- class_diaries.common_content
- class_diary_student_notes.note_content
- 동일 diary/student 중복 row 존재 여부

B. API 응답
- /parent/students/:id/diary
- /parent/diary
- 해당 일지의 실제 JSON

C. 앱 렌더링
- common_content
- student_note
- 합치는 함수
- map 반복 여부
- 같은 문자열 중복 제거 여부

중복이 DB, API, 앱 중 어느 단계에서 최초 발생하는지 확정하세요.
