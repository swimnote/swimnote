[보낼 곳: APP REPLIT]

[SWIMNOTE — 운영형 공지사항 V2 완성]

현재 슈퍼관리자의 공지 관리/공지 등록 기능을
실제 Production에서 사용할 수 있는 운영형 공지 시스템으로 완성한다.

사용자 요구사항:

1. 공지를 등록하면 대상 사용자가 앱을 실행했을 때 팝업으로 노출
2. 해당 공지는 사용자에게 1회만 자동 노출
3. "다시 보지 않기" 버튼 사용 금지
4. 사용자는 그냥 닫기(X/닫기)만 하면 됨
5. 한 번 노출된 공지는 다음 앱 실행부터 자동 팝업으로 다시 나오지 않음
6. 이미지 첨부 가능
7. 외부 링크/버튼 첨부 가능
8. 발송 대상은 다음 두 그룹으로 분리
   - 학부모
   - 관리자 + 선생님
9. 공지 팝업은 쇼핑앱/커머스앱의 프로모션 공지처럼
   이미지와 내용이 깔끔하게 보이는 카드형 UI
10. 기능 안정성을 최우선으로 구현

중요:
기존 공지 시스템을 버리고 무조건 새로 만드는 것이 아니다.
먼저 현재 APP/API/DB의 공지 구현을 전부 조사하고,
재사용 가능한 구조는 유지하면서 최소 변경으로 완성한다.

AI ENGINE 작업 아님.

━━━━━━━━━━━━━━━━━━━━━━

- 공지 등록 화면
- 공지 API
- DB announcement/notice 관련 schema
- 앱 시작 시 공지 조회 로직
- 팝업 렌더링 로직
- 역할별 대상 지정 방식
- 공지 노출 시작일시
- 강제 확인/선택 확인 기능

2. 공지 대상 구조
━━━━━━━━━━━━━━━━━━━━━━

사용자에게 보이는 공지 대상 선택은 정확히 두 그룹으로 정리한다.

[학부모]
→ parent 역할만 대상

[관리자 + 선생님]
→ 해당 SWIMNOTE의 실제 canonical 관리자 역할과 teacher 역할을 포함

슈퍼관리자/시스템 관리자 계정을
일반 운영처 관리자 대상에 임의 포함하지 않는다.
현재 role 구조를 확인한 뒤 정확히 매핑한다.

공지 등록 화면에서는 두 그룹을 각각 선택할 수 있게 한다.

요구되는 조합:

- 학부모만
- 관리자 + 선생님만
- 둘 다

현재의
전체 / 관리자 / 선생님 / 학부모
처럼 혼란스러운 선택 구조는
위 요구에 맞게 단순화한다.

━━━━━━━━━━━━━━━━━━━━━━
3. 공지 작성 기능
━━━━━━━━━━━━━━━━━━━━━━

공지 등록 시 최소 다음을 지원한다.

필수:
- 제목
- 내용
- 대상

선택:
- 대표 이미지 1장
- 링크 URL
- 링크 버튼 문구
- 노출 시작일시

예:

제목:
SWIMNOTE 업데이트 안내

내용:
새로운 기능이 업데이트되었습니다...

이미지:
업데이트 소개 이미지

링크:
https://...

버튼 문구:
자세히 보기

이미지가 없거나 링크가 없어도
공지 등록/노출이 정상 작동해야 한다.

이미지는 현재 SWIMNOTE의 기존
R2/media 업로드 구조를 우선 재사용한다.

공지 이미지를 base64로 DB에 직접 저장하지 않는다.

새 업로드 infrastructure를 중복 구축하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
4. 링크 안전 처리
━━━━━━━━━━━━━━━━━━━━━━

링크가 존재할 경우 공지 하단에 CTA 버튼을 표시한다.

예:
[자세히 보기]

버튼을 누르면 정상적인 HTTPS URL을 연다.

반드시:
- URL validation
- http/https 허용 범위 확인
- malformed URL 방어
- 링크가 없으면 CTA 자체 미표시

를 구현한다.

링크 클릭 때문에 앱이 crash하지 않아야 한다.

━━━━━━━━━━━━━━━━━━━━━━
5. 앱 실행 시 자동 팝업
━━━━━━━━━━━━━━━━━━━━━━

대상 사용자가 앱을 실행하고
로그인/세션 복구가 완료된 뒤,

현재 사용자에게 적용되는
"아직 자동 노출되지 않은 최신 공지"가 존재하면
공지 팝업을 보여준다.

로그인 화면 위에 띄우지 않는다.

role과 사용자 식별이 완료된 이후에 판단한다.

공지 조회 실패가 앱 홈 진입 자체를 막으면 안 된다.

공지 API 오류/네트워크 오류가 발생해도
앱의 정상 사용은 계속 가능해야 한다.

━━━━━━━━━━━━━━━━━━━━━━
6. 핵심 — 사용자당 공지 1회 자동 노출
━━━━━━━━━━━━━━━━━━━━━━

"다시 보지 않기" 기능을 만들지 않는다.

사용자에게는 별도 선택을 요구하지 않는다.

각 공지는 해당 사용자에게
자동 팝업으로 정확히 1회만 노출되는 것을 기본 정책으로 한다.

중요:
AsyncStorage 같은 기기 로컬 값만으로
1회 노출을 판단하지 않는다.

서버 기준으로:

user_id + announcement_id

조합의 사용자별 노출 기록을 유지한다.

현재 DB에 announcement receipt/read/view 구조가 있다면
반드시 그것을 우선 재사용한다.

없다면 현재 schema/architecture에 가장 작은 방식으로 추가한다.

목표:

동일 사용자가
- 앱 종료 후 재실행
- 로그아웃 후 재로그인
- 다른 휴대폰 로그인
- 앱 재설치

를 해도 이미 자동 노출된 공지가 계속 반복 팝업되지 않아야 한다.

━━━━━━━━━━━━━━━━━━━━━━
7. '노출됨' 처리 시점
━━━━━━━━━━━━━━━━━━━━━━

공지 조회만 성공했다고 바로 읽음 처리하지 않는다.

실제로 해당 공지 modal/card가 사용자 화면에
정상적으로 표시된 것이 확인된 시점에
서버에 viewed/seen 기록을 남긴다.

단:

seen 기록 API가 순간적으로 실패했다고
현재 표시된 공지를 강제로 닫거나 앱을 막지 않는다.

중복 기록 요청에도 안전하도록
user_id + announcement_id 기준 idempotent하게 처리한다.

가능하면 DB unique constraint 또는
기존 equivalent 구조를 사용한다.

━━━━━━━━━━━━━━━━━━━━━━
8. 여러 개의 새 공지가 있을 경우
━━━━━━━━━━━━━━━━━━━━━━

앱 실행 때 팝업 여러 개를 연속으로 폭탄처럼 띄우지 않는다.

현재 사용자에게 미노출 공지가 여러 개라면
활성 공지 중 정책에 맞는 최신 공지 1개만 자동 팝업한다.

나머지 공지를 어떻게 처리할지는
현재 공지 목록/기존 정책을 조사하여
데이터를 잃지 않는 방향으로 유지한다.

중요:
새 공지를 등록했다고 과거 공지 DB를 삭제할 필요는 없다.

기존 화면에
"새 공지 등록 시 이전 공지는 대체됩니다"
라는 정책이 실제 backend 동작과 연결돼 있다면
그 로직도 조사하고 보고한다.

임의로 유지하거나 삭제하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
9. 공지 팝업 UI
━━━━━━━━━━━━━━━━━━━━━━

팝업은 모바일에서 깔끔한 카드형으로 구성한다.

대략적인 정보 계층:

[ X ]

[대표 이미지 — 있을 때만]

공지 제목

공지 내용

[자세히 보기] — 링크 있을 때만

[닫기]

요구사항:

- X 버튼은 우측 상단에서 충분히 크게 터치 가능
- 하단 닫기 버튼도 제공
- "다시 보지 않기" 없음
- "오늘 하루 보지 않기" 없음
- 불필요한 체크박스 없음
- 이미지 비율 유지
- 긴 내용은 스크롤 가능
- 작은 화면에서도 버튼이 가려지지 않음
- Safe Area 대응
- 이미지가 없어도 레이아웃 정상
- 링크가 없어도 레이아웃 정상
- 내용이 길어도 정상
- 한글 줄바꿈 정상

사용자가 공지를 읽고
X 또는 닫기를 누르면 즉시 쉽게 닫혀야 한다.

━━━━━━━━━━━━━━━━━━━━━━
10. 기존 '강제 확인 / 선택 확인' 정리
━━━━━━━━━━━━━━━━━━━━━━

현재 등록 화면에 있는

- 강제 확인
- 선택 확인

기능이 실제 어떤 동작을 하는지 먼저 조사한다.

이번 정책에서는
사용자의 확인 동의를 강제로 받아야 하는 공지가 목적이 아니다.

기본 공지는:
"앱 실행 시 1회 보여주고 쉽게 닫기"

이다.

기존 강제확인 기능이 다른 Production 기능에서
실제로 사용되고 있다면 함부로 삭제하지 말고
호환성을 유지하면서 신규 기본 정책과 분리한다.

사용되지 않는 dead UI라면
근거 확인 후 정리한다.

━━━━━━━━━━━━━━━━━━━━━━
11. 기존 공지 데이터 호환
━━━━━━━━━━━━━━━━━━━━━━

이미 Production DB에 존재하는 기존 공지가 있다면
schema 변경 때문에 crash하거나 조회 실패하지 않게 한다.

신규 필드:
- image
- link
- link label
- receipt/view state

등이 추가되더라도 기존 row와 backward compatible해야 한다.

기존 공지의 null 값도 안전하게 처리한다.

━━━━━━━━━━━━━━━━━━━━━━
12. 권한/보안
━━━━━━━━━━━━━━━━━━━━━━

공지 등록/수정/삭제 권한은
현재 슈퍼관리자 권한 체계를 그대로 따른다.

일반 관리자/선생님/학부모가
슈퍼관리자 공지 작성 API를 호출할 수 있게 만들지 않는다.

공지 조회 시에는 서버에서 대상 role을 검증한다.

클라이언트에서 버튼만 숨기는 것을
권한 통제로 취급하지 않는다.

다른 대상 그룹의 공지가 API 응답으로
불필요하게 노출되지 않도록 한다.

━━━━━━━━━━━━━━━━━━━━━━
13. 실패 안전성
━━━━━━━━━━━━━━━━━━━━━━

반드시 확인:

- 공지 없음 → 정상 홈 진입
- 공지 API timeout → 정상 홈 진입
- 이미지 로딩 실패 → 텍스트 공지는 정상 표시
- 잘못된/없는 이미지 → crash 금지
- 링크 없음 → 정상
- malformed link → crash 금지
- seen 기록 실패 → 앱 사용 가능
- 중복 seen 요청 → 데이터 오류 없음
- 오래된 기존 공지 → crash 없음
- role 없는 비정상 데이터 → fail-safe
- 로그아웃/계정 전환 → 다른 사용자의 seen 상태와 혼합 금지

━━━━━━━━━━━━━━━━━━━━━━
14. 테스트
━━━━━━━━━━━━━━━━━━━━━━

최소 아래 시나리오를 검증한다.

A. 학부모 전용
- 학부모 → 표시
- 관리자 → 미표시
- 선생님 → 미표시

B. 관리자+선생님 전용
- 관리자 → 표시
- 선생님 → 표시
- 학부모 → 미표시

C. 둘 다
- 학부모 → 표시
- 관리자 → 표시
- 선생님 → 표시

D. 1회 노출
- 첫 앱 실행 → 표시
- 닫기
- 앱 재실행 → 같은 공지 자동 미표시

E. 계정 독립
- 사용자 A가 확인
- 사용자 B 로그인
- B에게는 해당 공지가 대상이면 정상 표시

F. 콘텐츠
- 텍스트만
- 이미지 포함
- 링크 포함
- 이미지+링크
- 긴 본문

G. 오류
- 이미지 실패
- 링크 오류
- 공지 API 오류
- seen API 오류

가능하면 API/integration test를 추가하되
프로젝트 전체를 대규모 테스트 프레임워크로
재구축하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
15. 배포 금지
━━━━━━━━━━━━━━━━━━━━━━

이번 단계에서는 구현 및 검증까지만 한다.

Production API deploy 금지
Production web deploy 금지
Production OTA 금지
iOS/Android binary build 금지

DB migration이 필요하다면
