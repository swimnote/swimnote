1. diary_templates.scope 허용값 완전 제한
━━━━━━━━━━━━━━━━━━━━━━

현재 정합성 CHECK는 정상 조합을 검증하지만,
허용되지 않은 임의 scope 값이 들어올 가능성을 명시적으로 차단한다.

허용값:

- global
- teacher
- x_global

기존 CHECK를 아래 기준으로 확정한다.

DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1
    FROM pg_constraint
    WHERE conname = 'chk_diary_templates_scope_integrity'
      AND conrelid = 'diary_templates'::regclass
  ) THEN
    ALTER TABLE diary_templates
    ADD CONSTRAINT chk_diary_templates_scope_integrity
    CHECK (
      (
        scope = 'x_global'
        AND swimming_pool_id IS NULL
        AND global_template_set_id IS NOT NULL
      )
      OR
      (
        scope IN ('global', 'teacher')
        AND swimming_pool_id IS NOT NULL
        AND global_template_set_id IS NULL
      )
    );
  END IF;
END $$;

이 CHECK에 의해 다음 값은 모두 거부되어야 한다.

- 임의 scope 문자열
- x_global + swimming_pool_id 존재
- x_global + global_template_set_id 없음
- global/teacher + swimming_pool_id 없음
- global/teacher + global_template_set_id 존재

Migration 전에 아래 사전 검증 쿼리를 실행한다.

SELECT id, scope, swimming_pool_id, global_template_set_id
FROM diary_templates
WHERE
  scope NOT IN ('global', 'teacher')
  OR swimming_pool_id IS NULL;

기존 데이터에서 결과가 발생하면 Migration 실행 전에 원인을 보고하고 멈춘다.

━━━━━━━━━━━━━━━━━━━━━━
2. 동일 일지·동일 커리큘럼 중복 정책 확정
━━━━━━━━━━━━━━━━━━━━━━

성장판에서 동일 커리큘럼 항목은
하나의 학생별 일지 안에서 최대 1회만 인정한다.

일지 문장 안에서 같은 기술이 여러 번 언급되어도
성장판 완료 횟수는 1회만 증가한다.

따라서 아래 Partial Unique Index를 유지한다.

CREATE UNIQUE INDEX IF NOT EXISTS uq_growth_events_per_note
ON growth_events (
  diary_note_id,
  student_id,
  curriculum_item_id,
  source
)
WHERE
  diary_note_id IS NOT NULL
  AND is_invalidated = FALSE;

정책:

- 같은 diary_note에서 동일 curriculum_item 반복 언급
  → 첫 이벤트만 인정
  → 나머지는 중복 제거

- 같은 날짜라도 서로 다른 diary_note
  → 각각 별도 1회 인정 가능

- 기존 이벤트가 is_invalidated=true인 경우
  → 같은 diary_note에 새로운 유효 이벤트 생성 가능

- 동일 토큰 재시도
  → match_token_id 기준 멱등 처리

- 다른 토큰이 같은 note/item을 다시 생성하려는 경우
  → uq_growth_events_per_note에 의해 중복 차단
  → 기존 유효 이벤트를 반환하거나 DUPLICATE_PROGRESS_EVENT 응답

occurrence_index는 사용하지 않는다.

성장판은 언급 횟수가 아니라
수업 일지 단위의 반복 관찰 횟수를 측정한다.

3. MATCH_TOKEN_SECRET 회전 정책 확정
━━━━━━━━━━━━━━━━━━━━━━

현재 Match Token TTL은 24시간이므로
초기 버전에서는 복수 Key 관리까지 구현하지 않는다.

다만 향후 Secret 교체를 위한 구조적 호환성을 확보한다.

MatchTokenV2Payload에 다음 필드를 추가한다.

key_id: string

초기값:

key_id = 'match_key_v1'

환경변수:

MATCH_TOKEN_SECRET
MATCH_TOKEN_KEY_ID=match_key_v1

토큰 생성:

- 현재 MATCH_TOKEN_KEY_ID를 payload.key_id에 포함
- 해당 Secret으로 HMAC 생성

토큰 검증:

- payload.key_id 확인
- 현재 지원되는 key_id인지 확인
- 지원하지 않는 key_id이면 MATCH_TOKEN_KEY_NOT_SUPPORTED
- 서명 검증 실패 시 INVALID_MATCH_TOKEN

현재 V1 구현:

- 단일 Secret만 사용
- Secret 교체가 필요하면 기존 토큰 TTL 24시간 경과 후 교체
- 긴급 교체 시 기존 미저장 토큰은 무효화될 수 있음
- JWT_SECRET fallback 금지
- MATCH_TOKEN_SECRET 미설정 시 Match 기능 시작 금지

향후 확장:

MATCH_TOKEN_SECRETS_JSON 또는 동등 구조를 사용해
이전 key와 현재 key를 동시에 검증할 수 있도록 설계 가능하다.

예:

{
  "match_key_v1": "old-secret",
  "match_key_v2": "new-secret"
}

하지만 현재 WP1~WP6 범위에서는 단일 key만 구현한다.

4. Parent AI 만료 Reservation 이중 복구
━━━━━━━━━━━━━━━━━━━━━━

RESERVED 상태 복구를 Worker에만 의존하지 않는다.

다음 두 경로에서 만료 Reservation을 정리한다.

A. Background Worker
- 5분 주기
- expires_at < NOW()
- RESERVED → EXPIRED
- parent_ai_daily_usage.reserved_count 복구

B. Parent AI 요청 진입 시 방어적 정리
- 해당 parent_account_id의 만료 RESERVED만 먼저 정리
- 그다음 일일 한도 계산 및 신규 Reservation 생성

API 요청 진입 시 처리 순서:

1. 기본 인증 및 parent 권한 검증
2. 해당 parent의 만료 RESERVED 정리
3. 일일 한도 Reservation 확보
4. Intent Guard
5. 본 AI 처리
6. COMPLETED / FAILED / BLOCKED 전환

권장 함수:

async function expireStaleReservationsForParent(
  tx,
  parentAccountId: string,
  usageDate: string
): Promise<number>

동일 Transaction 안에서:

1. 만료 RESERVED를 FOR UPDATE SKIP LOCKED로 조회
2. RESERVED → EXPIRED 전환
3. 실제 전환된 행 수만큼 reserved_count 감소
4. 음수 방지를 위해 GREATEST(0, reserved_count - expiredCount)
5. 신규 Reservation 한도 계산

예시 구조:

await db.transaction(async (tx) => {
  const expired = await tx.execute(sql`
    UPDATE parent_ai_usage_reservations
    SET
      status = 'EXPIRED',
      completed_at = NOW()
    WHERE parent_account_id = ${parentAccountId}
      AND usage_date = ${usageDate}::date
      AND status = 'RESERVED'
      AND expires_at < NOW()
    RETURNING request_id
  `);

  const expiredCount = expired.rowCount ?? 0;

  if (expiredCount > 0) {
    await tx.execute(sql`
      UPDATE parent_ai_daily_usage
      SET
        reserved_count = GREATEST(
          0,
          reserved_count - ${expiredCount}
        ),
        updated_at = NOW()
      WHERE parent_account_id = ${parentAccountId}
        AND usage_date = ${usageDate}::date
    `);
  }

  // 이후 같은 tx에서 일일 한도 확인 및 신규 reservation 생성
});

Worker와 API가 동시에 같은 Reservation을 정리해도
status='RESERVED' 조건 때문에 한쪽만 실제 전환해야 한다.

필수 테스트:

- Worker가 중단된 상태에서도 신규 요청 시 만료 예약 복구
- Worker와 API 동시 정리 시 reserved_count 중복 감소 없음
- 만료되지 않은 RESERVED는 유지
- COMPLETED/FAILED/BLOCKED는 정리 대상 제외
- reserved_count가 절대 음수가 되지 않음
- 동일 request_id 재시도 시 예약 중복 증가 없음
