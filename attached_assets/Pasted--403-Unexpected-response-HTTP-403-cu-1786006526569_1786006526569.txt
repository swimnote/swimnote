[긴급 — 실제 기기 로그인 403 요청 단계 확정]

현재 실제 기기에서는 로그인이 계속 실패한다.

화면 오류:

Unexpected response (HTTP 403)

curl이나 서버 측 대체 계정 테스트에서는 재현되지 않았지만,
실제 앱 로그인은 현재도 실패 중이다.

따라서 “현재 정상”, “일시적 오류”, “Cloudflare 문제” 판정을 모두 폐기한다.

이번 작업은 실제 기기 로그인 흐름에서
어느 요청이 403을 반환했는지 화면에 직접 표시한다.

━━━━━━━━━━━━━━━━━━━━━━
STEP 1. safeJson이 요청 정보를 받도록 수정
━━━━━━━━━━━━━━━━━━━━━━

현재:

safeJson(res)

형태만으로는 어느 URL의 응답인지 알 수 없다.

다음 정보를 함께 전달하도록 최소 수정한다.

- stage
- method
- url
- status
- Content-Type
- raw body 앞 300자

예시 구조:

async function safeJson(
  res: Response,
  context: {
    stage: string;
    method: string;
    url: string;
  }
) {
  const rawText = await res.text();

  try {
    return JSON.parse(rawText);
  } catch {
    throw Object.assign(
      new Error(`HTTP ${res.status} 비정상 응답`),
      {
        diagnostic: {
          stage: context.stage,
          method: context.method,
          url: context.url,
          status: res.status,
          contentType: res.headers.get("content-type"),
          server: res.headers.get("server"),
          cfRay: res.headers.get("cf-ray"),
          renderOrigin: res.headers.get("x-render-origin-server"),
          rawText: rawText.slice(0, 300),
        },
      }
    );
  }
}

토큰과 비밀번호는 diagnostic에 절대 포함하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
STEP 2. 로그인 흐름 각 요청에 stage 지정
━━━━━━━━━━━━━━━━━━━━━━

최소 다음 요청에 stage를 붙인다.

1.
POST /auth/unified-login

stage:
UNIFIED_LOGIN

2.
GET /pools/my

stage:
FETCH_POOL

3.
GET /admin/refund-policy

stage:
REFUND_POLICY

4.
실제로 로그인 완료 전후 실행되는 다른 요청이 있으면 모두 추가한다.

각 요청은 최종 URL을 정확히 기록한다.

━━━━━━━━━━━━━━━━━━━━━━
STEP 3. 실제 오류 화면에 진단값 표시
━━━━━━━━━━━━━━━━━━━━━━

로그인 실패 시 일반 오류 문구만 보여주지 말고,
diagnostic이 있으면 임시 Alert 또는 진단 모달로 다음을 표시한다.

- stage
- method
- url
- status
- Content-Type
- server
- cf-ray
- x-render-origin-server
- rawText 앞 300자

예시:

로그인 진단

stage: FETCH_POOL
method: GET
url: https://...
status: 403
contentType: text/html
server: cloudflare
cfRay: ...
rawText: ...

비밀번호, 토큰, 사용자 개인정보는 표시 금지.

━━━━━━━━━━━━━━━━━━━━━━
STEP 4. JSON 403도 단계 표시
━━━━━━━━━━━━━━━━━━━━━━

JSON 파싱에 성공해도 status가 403이면
stage와 응답 error/error_code를 함께 표시한다.

즉 다음 두 경우를 모두 잡아야 한다.

A.
403 + 비JSON body

B.
403 + 정상 JSON body

현재 safeJson의 JSON 파싱 성공 여부만 조사해서는 부족하다.

━━━━━━━━━━━━━━━━━━━━━━
STEP 5. OTA
━━━━━━━━━━━━━━━━━━━━━━

변경 허용 파일은 로그인 진단에 꼭 필요한 앱 파일만이다.

예상:

artifacts/swim-app/context/auth/SessionContext.tsx
필요하면 로그인 화면 파일 1개 추가

서버 변경 없음.
Render 배포 없음.

iOS와 Android production OTA를 배포한다.

export 시 반드시:

EXPO_PUBLIC_API_URL=https://swimnote-api.onrender.com/api

runtimeVersion:

1.6.1

번들에서 swimnote.kr/api가 API_BASE로 포함되면 중단한다.

━━━━━━━━━━━━━━━━━━━━━━
STEP 6. 실제 기기 재현
━━━━━━━━━━━━━━━━━━━━━━

사용자가 실제 앱에서 기존 계정과 비밀번호로 로그인한다.

실패 화면의 진단 내용을 캡처한다.

그 결과로 다음 중 하나를 확정한다.

A. UNIFIED_LOGIN 403
B. FETCH_POOL 403
C. REFUND_POLICY 403
D. 다른 후속 요청 403
E. HTTP 응답 전 네트워크 예외
F. 로그인 성공 후 화면 전환 오류
