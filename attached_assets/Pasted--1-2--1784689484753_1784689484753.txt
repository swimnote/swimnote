# 선생님 일지쓰기 최종 수정 지시문
## 1. 삭제한 날짜에 일지 재작성 시 잘못된 경고 제거
## 2. 문장 불러오기 모달 확대 및 아래로 스와이프 닫기

이번 작업은 위 두 가지 문제만 수정합니다.

다른 일지 기능, 학부모 화면, 템플릿 데이터, API 구조, DB 구조를 임의로 변경하지 마세요.

작업 후 OTA 또는 Publish하지 말고 완료 보고 후 대기하세요.

==================================================
A. 삭제한 날짜에 일지 재작성 시 잘못된 경고 제거
==================================================

## A-1. 현재 문제

재현 순서:

1. 선생님이 특정 날짜의 지난 일지를 삭제
2. 학부모 화면에서도 해당 일지가 정상 삭제됨
3. 같은 날짜의 일지를 선생님이 새로 작성
4. 실제 일지는 정상 저장·전송됨
5. 그런데 화면에는 기존 일지가 남아 있는 것처럼
   `지난 일지 때문에 작성할 수 없습니다`
   또는 이와 유사한 실패·중복 경고가 표시됨

즉, 저장은 성공했는데 잘못된 실패 메시지가 노출되는 상태입니다.

이 잘못된 메시지를 제거해야 합니다.

## A-2. 수정 원칙

단순히 모든 오류 메시지를 숨기지 마세요.

먼저 실제 원인을 확인하세요.

가능성이 높은 원인:

- 삭제 후 로컬 지난 일지 목록이 갱신되지 않음
- 삭제된 diary ID 또는 날짜가 캐시에 남아 있음
- 저장 전에 사용하는 중복 검사 상태가 오래된 데이터임
- 저장 API는 성공했는데 후속 중복 검사 또는 상태 갱신이 실패함
- 성공 응답 이후에도 이전 error state가 남아 있음
- 삭제된 일지를 포함한 stale query/cache를 기준으로 경고를 띄움
- 동일 날짜가 아니라 삭제된 기존 diary record를 계속 참조함

정확한 경고 발생 코드와 조건을 먼저 찾은 후 수정하세요.

## A-3. 올바른 동작

### 기존 일지가 실제로 존재하는 경우

현재 시스템 정책상 동일 수업의 중복 작성이 금지되어 있다면
실제 존재하는 일지에 대해서만 기존 중복 방지 동작을 유지하세요.

### 기존 일지가 삭제된 경우

삭제된 일지는 존재하지 않는 것으로 처리해야 합니다.

같은 날짜와 수업에 새 일지를 작성할 수 있어야 하며:

- 잘못된 중복 경고 없음
- 잘못된 실패 Alert 없음
- 저장 성공 메시지만 표시
- 새로 작성한 일지가 지난 일지 목록에 정상 표시
- 학부모 화면에도 새 일지가 정상 표시

되어야 합니다.

## A-4. 저장 성공 여부를 최우선으로 판단

저장 API 응답이 성공했다면
후속 로컬 상태 문제 때문에 사용자에게 실패 메시지를 띄우지 마세요.

권장 흐름:

1. 저장 요청
2. 서버 응답 확인
3. 저장 성공이면 성공 상태 확정
4. 기존 error state 초기화
5. 지난 일지 목록 재조회 또는 캐시 갱신
6. 작성 화면 상태 초기화
7. 성공 안내 및 정상 이동

저장 성공 후 별도의 로컬 갱신이 실패했다면:

- `일지는 저장되었습니다`
- 필요하다면 목록 새로고침

으로 처리하고,
`작성할 수 없습니다`라고 표시하지 마세요.

## A-5. 삭제 후 상태 정리

일지 삭제가 성공하면 다음을 확인하세요.

- 삭제된 diary ID를 로컬 목록에서 제거
- 해당 날짜·수업의 기존 일지 상태 초기화
- duplicate/existing diary 상태 초기화
- 삭제된 데이터의 AsyncStorage 또는 query cache 제거·무효화
- 지난 일지 목록 재조회
- 현재 작성 화면이 삭제된 diary 객체를 계속 참조하지 않음

삭제와 저장이 서로 다른 화면에 있어도
삭제 후 다시 작성할 때 최신 서버 상태를 기준으로 판단해야 합니다.

## A-6. 중복 검사 기준

날짜 문자열만 보고 무조건 차단하지 마세요.

현재 시스템에서 실제 일지를 구분하는 정확한 기준을 확인하세요.

예상 기준:

- classGroupId
- lessonDate
- lessonTime 또는 schedule identifier
- swimmingPoolId
- 실제 활성 diary record

삭제 상태의 데이터나 존재하지 않는 diary ID는
중복으로 판단하면 안 됩니다.

DB에 soft delete가 있다면:

- deleted_at이 존재하는 데이터
- is_deleted=true 데이터
- 비활성 상태 데이터

는 중복 검사에서 제외되어야 합니다.

단, 서버·DB 변경이 필요하다고 판단되면
임의 수정하지 말고 먼저 정확한 원인과 필요한 변경을 보고하세요.

## A-7. 실제 검증

다음 순서로 반드시 확인하세요.

### 테스트 1

1. 특정 날짜 일지 작성
2. 저장 성공
3. 지난 일지에서 삭제
4. 학부모 화면에서 삭제 확인
5. 같은 날짜·같은 수업 일지 재작성
6. 저장
7. 잘못된 실패 경고가 나오지 않는지 확인
8. 새 일지가 지난 일지에 표시되는지 확인
9. 학부모 화면에 새 일지가 표시되는지 확인

### 테스트 2

실제로 삭제하지 않은 일지가 존재하는 상태에서
동일 일지 중복 작성 방지 정책이 유지되는지 확인하세요.

### 테스트 3

삭제 후 앱을 종료하고 재실행한 뒤
같은 날짜 일지를 다시 작성해도 잘못된 경고가 없는지 확인하세요.

==================================================
B. 문장 불러오기 모달 확대
==================================================

## B-1. 목표

문장 불러오기 모달은
뒤쪽 일지쓰기 화면이 거의 보이지 않을 정도로 크게 표시하세요.

키보드가 닫혀 있을 때:

- 화면 높이 약 94~96%
- 상단 Safe Area 아래에 작은 여백만 유지
- Bottom Sheet 형태는 유지
- 둥근 상단 모서리 유지

키보드가 열려 있을 때:

- Safe Area 아래부터 키보드 바로 위까지 사용
- 검색창이 항상 보임
- 검색 결과 목록 영역을 최대한 크게 확보
- 결과를 빠르게 길게 스크롤 가능
- 하단 완료 기능 사용 가능

기존처럼 화면 중간부터 시작하는 작은 모달로 만들지 마세요.

## B-2. 권장 높이 계산

실제 Safe Area와 키보드 높이를 사용하세요.

예시:

const topGap = insets.top + 6;
const closedHeight = SCREEN_H - topGap;
const keyboardAvailableHeight =
  SCREEN_H - kbHeight - topGap;

const sheetHeight =
  kbHeight > 0
    ? keyboardAvailableHeight
    : closedHeight;

필요하다면 기기별 하단 inset을 반영하세요.

중요:

- 고정된 `SCREEN_H * 0.88 - kbHeight` 방식 사용 금지
- 키보드가 열렸다고 시트가 작은 카드로 줄어들면 안 됨
- 모달 상단이 화면 밖으로 밀려나면 안 됨
- 시트 하단은 키보드 바로 위에 위치
- 높이가 음수 또는 비정상 값이 되지 않도록 clamp 적용
