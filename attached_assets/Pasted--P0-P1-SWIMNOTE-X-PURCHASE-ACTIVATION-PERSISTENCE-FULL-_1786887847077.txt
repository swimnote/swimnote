[P0+P1 — SWIMNOTE X PURCHASE ACTIVATION PERSISTENCE + FULL X UI/UX CONVERSION]

현재 실기기 TestFlight에서 확인된 문제를 한 번에 수정한다.

현재 상황:

1. X 정기결제 승인까지 진행됨

5. X모드로 진입해도 UI/UX가 일반 SWIMNOTE와 사실상 동일함

==================================================
3. APP RESTART / RELOAD POLICY
==================================================

목표는 "X 전환을 확실히 보장"하는 것.

우선순위:

A.
서버 mode=x 확인
→ state/cache/navigation을 정상 갱신하여
앱 재실행 없이 즉시 X 전환

이 방법이 완전하게 가능하면
강제 app reload는 하지 않아도 된다.

하지만 기존 architecture상
Normal/X app shell이 root 단계에서 고정되어
runtime state 변경만으로 완전 전환이 보장되지 않는 경우:

B.
서버 mode=x 확인 후
안전한 APP SHELL reload를 1회 수행한다.

Expo 환경에서 현재 프로젝트에 이미 사용하는
안전한 reload mechanism이 있으면 재사용한다.

예:
expo-updates reloadAsync 계열

단:

서버에서 mode=x 확인 BEFORE reload.

결제 성공 여부가 불명확한 상태에서
reload 금지.

무한 reload 금지.

reload loop 금지.

==================================================
4. RELOAD LOOP PROTECTION
==================================================

강제 reload를 사용할 경우 반드시 보호장치.

예:

purchase activation transition에 대해서만
session-scoped one-shot flag 사용.

SERVER mode=x
+
CURRENT rendered mode != x
+
reload not already attempted

일 때만 1회 reload.

재실행 후 mode=x이면 flag 제거.

절대:

앱 실행할 때마다 reload
mode=x일 때마다 reload
theme 변경마다 reload

하지 않는다.

5. COLD START — 가장 중요
==================================================

앱을 완전히 종료한 뒤 다시 실행했을 때:

서버 pool이 paid X이면
무조건 X모드로 시작해야 한다.

현재 cached/local mode를 먼저 확정값처럼 사용해서
Normal shell을 고정하는 구조가 있는지 전수 확인.

Cold start 흐름:

JWT/session restore

→ current user 확인

→ current pool 확인

→ SERVER mode/entitlement fetch

→ mode resolve

→ mode=x이면 X App Shell

→ 그 후 dashboard render

가능하면 server mode가 확정되기 전에는
잘못된 Normal dashboard를 먼저 보여주지 않는다.

필요하면 짧은 bootstrap/loading 상태 사용.
