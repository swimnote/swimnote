SWIMNOTE AI 성장리포트
APP/API SERVER 최종 마무리 작업

이번 작업의 목표는
AI 성장리포트 APP/API SERVER 측 전체 발급 파이프라인을
Production 운용 가능한 상태로 완성하는 것입니다.

이번 작업 완료 후에는
AI ENGINE 별도 품질/안정성 검증으로 넘어갑니다.

ENGINE 검증까지 모두 완료되기 전에는
밀려 있는 8월 수업기록 기반 성장리포트를
실제 재발급하지 마십시오.

최종 재발급 대상은
토이키즈스윔클럽 pool만입니다.

0. 최종 확정 정책
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

AI 성장리포트 무료 발급 최소조건:

1.
report_month 시작 시점 재원 상태

AND

2.
analysis month 실제 출석 인정 횟수 >= 3

AND

3.
analysis month 유효 학생별 일지 source >= 1

입니다.

즉 최종 정책:

재원 O
+
출석 3회 이상
+
이번 달 유효 학생일지 1개 이상
=
발급 대상

출석률 percentage는 사용하지 않습니다.

주1 / 주2 / 주3 모두 동일하게
절대 출석 3회를 사용합니다.

중간입회 학생도
조건을 충족하면 발급 가능합니다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. Eligibility Version 최종 갱신
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

기존:

version 1 = attendance3 / diary3
version 2 = attendance3 / diary2

였다면

신규 최종 정책:

attendance3 / diary1

은 반드시 새 version으로 구분하십시오.

예:

GROWTH_REPORT_MIN_ATTENDANCE_COUNT = 3
GROWTH_REPORT_MIN_SOURCE_RECORDS = 1
GROWTH_REPORT_ELIGIBILITY_VERSION = 3

실제 column type은 변경하지 말고
현재 schema 형식을 유지하십시오.

기존 version을 덮어쓰지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. Source Event 최종 정의
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

source_event_count는
"해당 학생에게 귀속된 유효 학생별 수업기록 event 수"
입니다.

최소 1개 필요.

유효 조건:

- 해당 student_id
- 해당 swimming_pool_id
- analysis_period_start 이상
- analysis_period_end_exclusive 미만
- diary not deleted
- student note not deleted
- 실제 내용 존재
- 동일 diary 중복은 1 event

단순 punctuation-only 값은
유효 source로 인정하지 마십시오.

예:

"."
","
"..."
"-"

같은 내용은 source 1개로 인정하면 안 됩니다.

반대로 다음처럼
측정 가능한 사실 또는 실제 수업 관찰이 있으면
짧더라도 유효할 수 있습니다.

예:

IM 80m 2분21초
평영 발차기 연습
자유형 호흡 성공

임의의 글자 수 threshold만으로
유효/무효를 결정하지 마십시오.

최소한 실제 문자/숫자 기반 정보가 존재하는지
안전하게 판정하십시오.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. COMMON Diary 처리 원칙
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Teacher Diary 구조의 common 내용과
학생별 note를 혼동하지 마십시오.

Eligibility의 최소 source 1개는
학생에게 실제 귀속 가능한 학생별 source가
존재해야 합니다.

COMMON 내용만 존재한다는 이유만으로
모든 학생을 자동으로 source=1 처리하지 마십시오.

단,
해당 학생의 유효 source event가 존재할 경우
같은 수업의 COMMON 내용은
향후 ENGINE snapshot의 보조 context로 전달할 수 있습니다.

Eligibility와 분석 context를 구분하십시오.

4. 지난달 리포트 연속성 구조
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이번 달 source >=1인 학생에게
직전 월 usable Growth Report가 존재하면

이번 달 분석 시
지난달의 검증된 구조화 데이터를
continuity context로 전달할 수 있도록
APP/API 계약을 준비하십시오.

우선순위:

1.
직전 report_fact_package
2.
기타 structured/verified fact data
3.
필요한 경우 report_content

완성된 자연어 문장을
사실 source보다 우선하지 마십시오.

중요:

지난달 AI 문장을
그 자체로 새로운 사실로 승격시키면 안 됩니다.

이번 달 실제 source가 반드시 최소 1개 있어야 합니다.

이번 달 source = 0이면
지난달 리포트가 아무리 풍부해도
이번 달 Growth Report 발급 금지입니다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이번 달 유효 source >=1

6. 직전 리포트 usable 판정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

직전 리포트가 존재한다고 해서
무조건 재사용하지 마십시오.

다음 정보를 조사하여
재사용 가능 여부를 판단하는 helper를 분리하십시오.

최소 확인:

- 동일 student
- 동일 pool
- 바로 직전 report month
- analysis_status = COMPLETE
- report_fact_package 실제 존재
- deleted_at IS NULL

product_status = DISCARDED인 과거 데이터는
무조건 usable로 처리하지 마십시오.

discard_reason / discard 의미를 확인하십시오.

단순:

발행 취소
테스트 취소
관리자 미발송

등으로 DISCARD된 것이고
분석 fact 자체는 유효한 경우만 재사용 가능.

내용 오류
근거 오류
분석 실패
잘못된 학생
잘못된 기간

등의 이유로 discard된 경우
절대 다음 달 근거로 사용하지 마십시오.

usable 판단 규칙을 코드로 명시하십시오.

7. Attendance 최종 의미
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

운영 정책:

정상 수업 대상
+
명시적 결석 아님
=
출석 인정

그리고 실제 완료한 보강수업도
출석으로 인정합니다.

단,
현재 개발된 attendance v2가
class_diary 존재를 수업 진행의 유일한 근거로 사용하는 경우
그 구조를 그대로 최종 확정하지 마십시오.

Diary는 출석 Source가 아닙니다.

APP에서 실제 정규수업 예정/진행을 계산하는
기존 schedule helper / class schedule logic을 먼저 확인하고
가능하면 재사용하십시오.

정규수업 출석 event는 최소:

- student_class_history
- class_group schedule
- analysis period
- enrolled_at / left_at
- pool_holidays
- 실제 취소/휴강 정보가 있다면 반영

으로 계산되어야 합니다.

수업 대상이었고
explicit absent가 없으면 출석.

present / late row가 있으면 명시적 출석.

absent row가 있으면 불출석.

8. 보강 출석
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

makeup_sessions.status='completed'가
실제 참여 완료임은 코드 경로에서 확인된 상태입니다.

실제 completed makeup은
출석 1회로 포함하십시오.

예약 / 대기 / 취소 상태는 포함 금지.

completed_attendance_id가 NULL이라는 이유만으로
실제 완료 보강을 누락하지 마십시오.

정규수업과 보강을
DISTINCT date 하나로 합치면 안 됩니다.

같은 날:

정규수업 1회
+
보강 1회

실제 두 번 참여했다면
attendance_count = 2입니다.

따라서 attendance event는
단순 DISTINCT date가 아니라
실제 수업 event identity 기준으로 계산하십시오.

15. 현재 Worker 미작동 문제 완전 해결
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- Worker가 어디서 시작되는가

- DB connection

- retry

"코드는 있는데 실행되지 않음"은 FAIL입니다.

16. Worker 운영 요구사항
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Worker는 최소 다음을 만족해야 합니다.

- 서버/worker process 시작 시 자동 시작
- queue 지속 소비
- idempotent
- FOR UPDATE SKIP LOCKED 또는 기존 안전 locking 유지
- 동일 report 중복 ENGINE 호출 방지
- request_id 사전 저장
- retryable failure 재시도
- permanent failure FAILED
- 최대 retry 횟수 명확
- crash 후 재기동 가능
- stuck job recovery 가능
- process restart 후 pending job 이어서 처리
- 여러 worker가 떠도 동일 report 중복 처리 안 됨

기존 검증된 locking/CAS 구조를
불필요하게 갈아엎지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
17. Scheduler 운영 요구사항
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

매월 5일 scheduler는:

- 동일 pool
- 동일 report_month

cycle을 중복 생성하면 안 됩니다.

기존 unique / ON CONFLICT / distributed lock을 유지하십시오.

서버가 5일 실행 시점에 다운되어 있었더라도
6일에 복구되면
해당 월 미실행 cycle을 catch-up할 수 있어야 합니다.

즉:

"5일 00:00에 정확히 서버가 살아있을 때만 실행"

구조는 금지합니다.

last completed cycle 또는
missing monthly cycle을 확인해
catch-up 가능해야 합니다.
