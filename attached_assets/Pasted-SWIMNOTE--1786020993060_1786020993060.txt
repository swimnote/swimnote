SWIMNOTE 보강 날짜 범위 수정 — 최종 보완 후 구현 승인 지시

관리자 경로에도 동일한 날짜 범위를 적용한다.

최종 운영 규칙:

- 선생님과 관리자 동일 적용
- KST 오늘 -14일 ~ 오늘 +28일
- 양 끝 포함 총 43일
- 결석일 이전·당일·이후 모두 허용
- 미래 날짜는 assign
- 오늘·과거 날짜는 complete-direct
- completed / cancelled / extinguished 보강권은 계속 차단
- 로그인·인증·JWT 관련 코드는 수정 금지

다만 현재 설계에서 다음 2개를 먼저 정정한 뒤 구현한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. expire_at과 화면 표시 불일치 해소
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 설계는 eligible-occurrences에서 expire_at을 무시하고 43일 전체를 표시하지만,
validateMakeupOccurrence에서는 expire_at을 계속 검사한다.

이 구조라면 화면에 날짜가 표시되어도 선택 시 MAKEUP_EXPIRED 오류가 발생할 수 있다.

다음 상태별 정책을 코드 기준으로 확정하라.

1. status=waiting
   - 오늘 -14일~+28일 안에서는 원래 expire_at보다 뒤여도 선택 가능하도록 할 것
   - 이번 통합 범위가 실제 사용 가능 범위의 최종 기준

2. status=expired
   - 기존 확인창과 allow_expired=true 흐름 유지
   - allow_expired=false면 기존 오류 유지
   - allow_expired=true여도 오늘 -14일~+28일 범위는 반드시 강제

3. status=completed / cancelled / extinguished
   - 계속 차단

4. carryover
   - 별도 날짜 규칙 없음
   - 동일한 43일 범위 사용

즉 날짜 선택 가능 여부는 다음 두 축으로 판단한다.

- 보강권 상태가 사용 가능한가
- 선택 날짜가 오늘 -14일~+28일 범위인가

원래 absence_date와 expire_at이 새 통합 범위를 다시 제한해서는 안 된다.
단, expired 상태의 사용자 확인 절차는 유지한다.

구현 전 현재 validateMakeupOccurrence의 expire_at 조건을 어떤 방식으로 변경할지 정확한 diff 계획을 먼저 짧게 제출하라.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. 날짜 helper를 서버 타임존 독립 방식으로 수정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Date.UTC로 만든 값을 다시 toKstDateStr로 변환하는 방식 대신,
YYYY-MM-DD 순수 날짜 연산 helper를 사용한다.

권장 구조:

function addDateDays(dateStr: string, days: number): string {
  const [y, m, d] = dateStr.split("-").map(Number);
  const date = new Date(Date.UTC(y, m - 1, d + days));

  return [
    date.getUTCFullYear(),
    String(date.getUTCMonth() + 1).padStart(2, "0"),
    String(date.getUTCDate()).padStart(2, "0"),
  ].join("-");
}

function dayOfWeekFromDateStr(dateStr: string): number {
  const [y, m, d] = dateStr.split("-").map(Number);
  return new Date(Date.UTC(y, m - 1, d)).getUTCDay();
}

원칙:

- kstTodayStr()만 현재 시각에서 KST 오늘을 구하는 역할
- 그 이후 날짜 가감과 요일 계산은 순수 YYYY-MM-DD UTC 연산
- 서버 로컬 timezone에 의존하는 getFullYear/getMonth/getDate/getDay 금지
- 월말·연말·윤년 테스트 필수

3. 관리자 경로 최종 결정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PATCH /admin/makeups/:id/assign에도 동일한 43일 범위 검증을 적용한다.

범위 밖이면:

HTTP 400
error: MAKEUP_DATE_OUT_OF_RANGE
message: 보강일은 오늘 기준 2주 전부터 4주 후까지 선택할 수 있습니다.

관리자라고 범위 우회 허용하지 않는다.

현재 관리자 앱이 서버 400 응답 메시지를 사용자에게 표시할 수 있는지 확인한다.

- 기존 오류 표시 구조로 메시지가 노출되면 앱 수정 없음
- 메시지가 사라지거나 일반 오류만 표시된다면 해당 증거를 제출하고 중단
- 승인 없이 관리자 앱 파일 수정 금지

앱 파일, 로그인, 인증, JWT 파일은 수정 금지.

5. 일지 문제는 별도 Task로 고정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이번 작업에서는 일지를 수정하지 않는다.

별도 미해결 Task로 고정:

- 기존 일지가 없는 과거 수업:
  보강 학생만 포함한 새 일지 작성과 해당 학부모 푸시 가능

- 기존 일지가 있는 과거 수업:
  POST /diaries/:id/student-notes로 보강 학생 note 추가 가능
  기존 common_content와 기존 학생 notes는 불변
  그러나 추가된 보강 학생에게만 발행·푸시하는 API/UI는 현재 없음

따라서 날짜 범위 수정 완료 후 별도 Task에서
“기존 일지에 추가된 보강 학생만 개별 발행” 기능을 설계한다.

이번 구현에 diary.ts나 앱 일지 화면을 포함하지 않는다.

- 오늘 -15일 → 400
- 오늘 -14일 → 허용
- 오늘 → 허용
- 오늘 +28일 → 허용
- 오늘 +29일 → 400

결석일 관계:

- 결석일 이전 → 허용
- 결석일 당일 → 허용
- 결석일 이후 → 허용

상태:

- waiting + 범위 내 + 기존 expire_at 이후 → 허용
- expired + allow_expired=false → 기존 확인 오류
- expired + allow_expired=true + 범위 내 → 허용
- expired + allow_expired=true + 범위 밖 → 400
- completed / cancelled / extinguished → 차단

7. 진행 방식

먼저 아래 2개만 답한다.

1. 새 43일 규칙에서 expire_at 검증을 정확히 어떻게 변경할지
2. 관리자 앱이 MAKEUP_DATE_OUT_OF_RANGE 서버 메시지를 기존 구조로 표시하는지

두 항목이 확인되면 구현을 진행한다.
