# 관리자 권한 부여·회수 실시간 반영 수정 지시

현재 서버 DB의 users.roles 변경은 정상 처리됩니다.

하지만 권한을 부여하거나 회수한 뒤
대상 선생님 앱에서는 앱을 완전히 종료하고 재시작해야만
관리자 전환 메뉴와 roles 상태가 변경됩니다.

이 상태는 승인할 수 없습니다.

관리자 권한 변경은 대상 선생님 앱에
실시간 또는 준실시간으로 반영되어야 합니다.

==================================================
1. 현재 원인
==================================================

대상 선생님 앱은 로그인 당시 저장된

session.adminUser.roles
AsyncStorage의 auth_admin
현재 JWT

를 계속 사용하고 있습니다.

원장이 users.roles를 변경해도
대상 앱은 /auth/me를 다시 호출하지 않으므로
로컬 roles가 갱신되지 않습니다.

앱 재시작 후에만 변경되는 것은
재시작 과정에서 /auth/me가 실행되기 때문입니다.

==================================================
2. 필수 적용 방식
==================================================

이번 수정에서는 별도 WebSocket을 새로 구축하지 말고,
다음 3단계 갱신 방식을 적용하세요.

A. 앱 포어그라운드 복귀 시 권한 갱신

AppState가 background/inactive에서 active로 바뀔 때마다
/auth/me 또는 기존 refreshSession을 호출하세요.

서버에서 받은 최신 roles와 현재 로컬 roles를 비교하고
변경된 경우 즉시 세션과 AsyncStorage를 갱신하세요.

B. 역할 전환 메뉴 또는 설정 화면 진입 시 권한 갱신

사용자가 역할 전환 화면이나 설정 화면을 열 때
항상 서버의 최신 roles를 다시 조회하세요.

오래된 AsyncStorage 값만으로
전환 가능한 역할을 표시하면 안 됩니다.

C. 앱이 활성 상태인 동안 주기적 권한 확인

대상 앱이 계속 켜져 있으면
AppState 복귀 이벤트가 발생하지 않을 수 있습니다.

따라서 로그인 상태에서 앱이 active인 동안
짧은 주기로 권한 상태를 확인하세요.

권장 주기:
15초

확인 API:
기존 /auth/me 사용 가능

단, 전체 사용자 데이터를 무겁게 조회한다면
경량 엔드포인트를 추가하세요.

예:

GET /auth/role-status

응답:

{
  "success": true,
  "role": "teacher",
  "roles": ["teacher"],
  "rolesVersion": 12
}

==================================================
3. 권한 버전 방식 추가 검토
==================================================

가능하면 users 테이블 또는 기존 tokenVersion 구조를 활용하여
rolesVersion 또는 permissionVersion을 관리하세요.

권한 부여·회수 시마다 version을 1 증가시키고,
클라이언트는 이전 version과 비교합니다.

예:

권한 변경 전:
rolesVersion = 11

권한 회수 후:
rolesVersion = 12

클라이언트가 15초마다 경량 API를 호출했을 때
version이 바뀐 경우에만 전체 /auth/me를 호출하고
세션을 갱신하도록 구성할 수 있습니다.

DB 컬럼 추가가 부담되면
이번에는 /auth/me 직접 비교 방식으로 구현해도 됩니다.

다만 향후 SWIMNOTE X와 AI Bundle까지 연결할 예정이므로
permissionVersion 구조가 더 적합한지 먼저 조사하세요.

==================================================
4. 최신 roles 수신 후 처리
==================================================

서버에서 최신 roles를 받은 즉시 다음을 처리하세요.

1. session.adminUser.roles 갱신
2. AsyncStorage auth_admin 갱신
3. 역할 전환 메뉴 다시 렌더링
4. last_used_role 유효성 확인
5. 현재 activeRole이 최신 roles에 존재하는지 확인

예:

현재 activeRole = pool_admin
최신 roles = ["teacher"]

이면 즉시:

- 관리자 캐시 삭제
- teacher JWT 발급
- session.applyRoleSwitch 실행
- last_used_role = teacher 저장
- teacher 홈으로 이동
- 안내 메시지 1회 표시

예:

현재 activeRole = teacher
최신 roles = ["teacher", "pool_admin"]

이면:

- 세션 roles 즉시 갱신
- 관리자 전환 버튼 즉시 표시
- 사용자를 강제로 관리자 모드로 이동시키지는 않음

==================================================
5. 원장 화면과 대상 선생님 화면을 구분
==================================================

원장 계정에서 다른 선생님의 권한을 변경한 경우:

원장 화면:
- 서버 응답 roles로 목록 즉시 갱신
- 성공 모달 정상 표시 및 닫힘

대상 선생님 화면:
- 포어그라운드 복귀, 역할 화면 진입 또는 15초 주기 확인으로 변경 감지
- 권한 부여 시 관리자 전환 버튼 즉시 표시
- 권한 회수 시 관리자 모드라면 teacher 모드 즉시 복귀
- teacher 모드라면 관리자 전환 버튼 즉시 제거

원장 계정 자체를 ROLE_REVOKED 처리하면 안 됩니다.

==================================================
6. 중복 처리 방지
==================================================

기존 _isHandlingRoleRevoked single-flight를 유지하세요.

주기적 refreshSession과 ROLE_REVOKED 응답이 동시에 발생해도

- switch-role 중복 호출
- Alert 중복
- router.replace 중복
- AsyncStorage 동시 갱신 충돌

이 발생하지 않도록 하나의 공통 함수로 처리하세요.

예:

applyServerRoleState(serverUser)

이 함수가

- roles 비교
- 세션 저장
- 현재 role 유효성 검사
- 필요 시 teacher 복귀

를 담당하도록 구조화하세요.

==================================================
7. 주기적 확인 생명주기
==================================================

폴링은 다음 조건에서만 실행하세요.

- 로그인 상태
- 앱 AppState = active
- teacher 또는 pool_admin 계정

다음 경우 반드시 중지하세요.

- 로그아웃
- 앱 background/inactive
- 컴포넌트 unmount
- 세션 토큰 없음

setInterval 누적 등록이 발생하지 않도록
cleanup에서 clearInterval을 반드시 호출하세요.

동시에 여러 /auth/me 요청이 겹치지 않도록
refresh in-flight 잠금도 추가하세요.

==================================================
8. 오류 처리
==================================================

주기적 권한 확인 중 일시적인 네트워크 오류가 발생했다고
사용자를 로그아웃시키면 안 됩니다.

네트워크 오류:
- 현재 세션 유지
- 다음 주기에 재시도
- 반복 Alert 표시 금지

401:
- 기존 로그아웃 정책 적용

403 ROLE_REVOKED:
- 기존 teacher 자동복귀 처리

503 ROLE_CHECK_FAILED:
- 현재 화면 유지
- 다음 주기에 재시도

==================================================
9. 테스트 항목
==================================================

반드시 실제 기기 2대로 테스트하세요.

테스트 1 — 권한 부여 실시간 반영

기기 A:
원장 계정

기기 B:
teacher 계정 로그인 및 앱 활성 상태 유지

기기 A에서 pool_admin 권한 부여

기대 결과:
15초 이내 기기 B의 관리자 전환 버튼 표시
앱 종료 및 재로그인 불필요

테스트 2 — teacher 모드에서 권한 회수

기기 B는 teacher 모드 유지
기기 A에서 권한 회수

기대 결과:
15초 이내 관리자 전환 버튼 제거
teacher 기능은 계속 정상 작동

테스트 3 — 관리자 모드에서 권한 회수

기기 B를 pool_admin 모드로 유지
기기 A에서 권한 회수

기대 결과:
15초 이내 또는 다음 관리자 API 호출 즉시
teacher 모드로 자동 복귀
Alert 1회
관리자 메뉴 제거

테스트 4 — 앱 백그라운드 복귀

기기 B를 background로 보냄
기기 A에서 권한 변경
기기 B를 다시 active로 전환

기대 결과:
복귀 즉시 최신 roles 반영

테스트 5 — 네트워크 단절

기기 B 네트워크 차단
기기 A에서 권한 변경
기기 B 네트워크 복구

기대 결과:
다음 폴링 또는 AppState active 시 갱신
강제 로그아웃 없음

==================================================
10. 완료 보고
==================================================

수정 전에 먼저 현재 refreshSession,
/auth/me,
AppState 처리 구조를 조사해 보고하세요.

조사 후 다음을 명확히 제시하세요.

1. 앱 재시작 전 roles가 갱신되지 않는 정확한 코드 경로
2. 기존 refreshSession 재사용 가능 여부
3. /auth/me 폴링과 경량 role-status 중 선택
4. 폴링 주기
5. 변경 파일 목록
6. DB 변경 여부

조사 승인 후 구현하고,
서버 배포 → OTA → 실제 기기 2대 테스트 결과를 보고하세요.
