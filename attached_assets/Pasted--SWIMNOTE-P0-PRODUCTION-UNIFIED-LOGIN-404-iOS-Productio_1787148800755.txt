[SWIMNOTE P0 — PRODUCTION UNIFIED LOGIN 404 복구]

현재 실제 iOS 기기에서 로그인 불가.

실제 Production 오류:

POST
https://swimnote-api.onrender.com/api/auth/unified-login

response:
HTTP 404
Content-Type: text/html
Cannot POST /api/auth/unified-login

현재 Render:
repo = swimnote/swimnote
branch = deploy-photo-clone
deployed SHA = d015149b...

중요:
서버 전체 장애로 추측하지 말고
/api/auth/unified-login route가 현재 배포 코드에 실제 존재하는지부터 확인한다.

목표:
현재 iOS 앱이 사용하는 unified-login API를 Production에서 정상 복구한다.

1. 현재 deploy-photo-clone HEAD에서 전수 확인

아래 문자열/route를 검색한다.

- /api/auth/unified-login
- unified-login
- UNIFIED_LOGIN
- unifiedLogin

확인:
- route 정의 파일
- router mount 경로
- POST handler
- 서버 index/app에서 router가 실제 등록되는지
- build output에 해당 router가 포함되는지

2. main / 이전 정상 Production 코드와 비교

이전 Render Live였던 commit:
acd36ff...

현재:
d015149b...

두 revision에서
/api/auth/unified-login 관련 코드 차이를 확인한다.

특히:
- 이전에는 route가 있었는데 현재 branch에서 빠졌는지
- route file은 있는데 app.use/router registration이 빠졌는지
- path prefix가 변경됐는지
- /auth/unified-login과 /api/auth/unified-login 경로 차이인지
- build artifact에 route가 누락되는지

3. 현재 iOS 앱의 실제 API client 확인

현재 앱이 실제로 호출하는 endpoint가:

POST /api/auth/unified-login

인지 확인한다.

앱이 잘못된 endpoint를 호출하는 것인지,
서버가 필요한 route를 누락한 것인지
양쪽을 비교해서 원인을 확정한다.

4. Production 로그 확인

Render runtime log에서 해당 요청 시각의 로그 확인.

확인:
- request 자체가 API server에 도착하는지
- Express/Fastify router가 404를 반환하는지
- 다른 서비스로 routing되는지

5. 수정 원칙

현재 iOS 앱이 이미 배포/빌드 중이므로
가능하면 서버를 현재 앱 API contract에 맞춘다.

즉 기존 정상 contract가
POST /api/auth/unified-login
이었다면 이 endpoint를 Production에서 복구한다.

불필요하게 모바일 앱 endpoint를 변경하지 않는다.
