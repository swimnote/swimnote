[SWIMNOTE — AI 일지 3개 이슈 집중 조사 + 최소 수정]

중요:

이번 작업은 AI 일지 작성 화면의 아래 3개 이슈만 다룹니다.

1.
AI 학생별 일지 확인 모달이 반복해서 나타나는 문제

2.
학생별 일지에 선택한 사진의 미리보기가 표시되지 않는 문제

3.
“다시 생성” 버튼 사용 시 실제 AI/API 호출 횟수와 비용 발생 구조 확인

범위 밖 기능 수정 금지.

광범위 리팩터링 금지.
DB 구조 변경 금지.
RevenueCat/결제 변경 금지.
Growth Report 변경 금지.
일지 권한 정책 변경 금지.
AI 문장 품질/프롬프트 개편 금지.

먼저 실제 원인을 조사하고,
1번과 2번은 원인이 확인되면 최소 수정하십시오.

3번은 호출 구조를 먼저 확인하고,
의도치 않은 중복 호출이 있을 때만 수정합니다.

1. 이슈 1 — 저장 확인 모달 반복
━━━━━━━━━━━━━━━━━━━━━━

실기기에서 확인된 재현:

1.
AI 일지 작성

2.
AI가 학생별 일지를 생성

3.
하단 “저장” 버튼 탭

4.
다음 모달 표시:

“AI 학생별 일지 확인
AI가 학생별 일지 1건을 작성했습니다.
내용을 확인하셨나요?”

버튼:
취소
확인하고 저장

5.
“확인하고 저장” 탭

6.
정상이라면 이 시점에
일지가 저장 완료되어야 함.

현재 문제:

“확인하고 저장”을 눌러도
동일 확인 모달이 다시 나타남.

그 후:

모달에서 “취소”를 한 번 누름
→ 다시 일지 작성 화면의 “저장” 탭
→ 그제서야 저장 완료됨.

즉:

확인 모달 confirm
→ 실제 save로 진행하지 못하고
→ 다시 confirmation gate로 재진입하는
상태/handler loop 가능성이 있음.

2. 이슈 1 조사 항목
━━━━━━━━━━━━━━━━━━━━━━

다음의 실제 handler/state 흐름을 추적:

- 하단 저장 버튼 onPress
- AI 학생별 일지 존재 여부 판정
- 확인 모달 open state
- “확인하고 저장” handler
- 실제 diary save function
- save 함수가 다시 confirmation 조건을 검사하는지
- confirmed flag/state/ref 존재 여부

- saving/loading flag

B.
confirmed state를 set한 직후
React state 비동기성 때문에
같은 함수 안에서 이전 false 값을 읽는지

C.
modal close와 save 호출 순서 문제인지

D.
실제 저장 API가 두 번 호출되는지

E.
모달은 두 번 뜨지만 저장 API는 한 번인지,
아예 첫 confirm에서는 API 호출이 없는지

추측하지 말고 실제 코드로 확인.

정상 UX:

저장

→ 화면 종료/기존 정상 완료 UX

confirmation과 실제 persistence를

단 현재 코드 구조에 맞는 최소 수정 사용.

새로운 복잡한 state machine 만들지 마십시오.

10. 비용 판정 기준
━━━━━━━━━━━━━━━━━━━━━━

결과를 다음 중 하나로 명확히 판정:

CASE A.

“다시 생성” 1회
=
새 AI model request 1회

→ 정상적인 추가 호출비용 발생.

버그 아님.

이 경우 코드 변경하지 말고
정확한 호출 구조만 보고.

CASE B.

“다시 생성” 1회인데
동일 generation이 2회 이상 호출

→ 버그.

중복 호출 원인 찾아 최소 수정.

CASE C.

“다시 생성”이
전체 일지 + 모든 학생별 일지를
필요 이상으로 전부 재생성

→ 현재 설계가 의도된 것인지
코드 근거와 함께 보고.

정책 결정 없이 임의 변경 금지.

CASE D.

모델 호출이 없고
기존 결과만 다시 사용

→ 그렇게 보고.
