[SWIMNOTE — 학부모 연결 승인 오류 조사 / 수정 전 STOP]

현재 X 초기설정은 완료된 상태입니다.
기존 X 구조를 재설계하지 마십시오.

현재 실기기에서 다음 문제가 확인됩니다.

1. 관리자 → 승인 관리 → 학부모 연결
2. 여러 가입신청이
   "자동승인 실패: 학생 이름 불일치"
   로 대기 상태에 남아 있음
3. 이 경우 관리자가 직접 [승인] 버튼을 눌러 연결하려 해도
   승인 버튼이 정상 작동하지 않음

목표는 두 가지입니다.

A. 자동승인 조건을 안전한 범위에서 최대한 유연하게 만든다.
B. 자동승인 실패 여부와 관계없이 관리자가 확인 후 수동 승인할 수 있게 한다.

단, 지금 바로 수정하지 마십시오.
먼저 현재 Production 기준 버전과 실제 코드를 조사해서 보고 후 STOP 하십시오.

━━━━━━━━━━━━━━━━━━

- X setup 관련 마지막 commit

추측 금지.

학부모 회원가입

3. "학생 이름 불일치" 정확한 원인 조사
━━━━━━━━━━━━━━━━━━

현재 화면의

"자동승인 실패: 학생 이름 불일치"

가 어떤 조건에서 발생하는지 실제 코드를 찾으십시오.

특히 확인:

- 학생 이름 exact match인지
- trim 처리 여부
- 공백 제거 여부
- 대소문자/Unicode normalization 여부
- 학부모가 입력한 자녀 이름과 students.name 비교 방식
- 전화번호 normalization 방식
- 학생 전화번호인지 보호자 전화번호인지
- guardian phone / parent phone 비교 여부
- 이름과 전화번호 중 어느 조건이 필수인지
- 학생 이름이 "박세연/박세아"처럼 복수 또는 특수 형식일 때 처리
- 동일 전화번호로 형제자매가 있을 때 처리
- 학생 이름 오타 시 처리
- 기존 학생 DB의 보호자 번호가 일치하지만 이름만 다를 때 왜 pending이 되는지

실제 실패 중 가능한 샘플 2~3건을 개인정보 마스킹하여
DB 값과 가입신청 값을 비교하십시오.

━━━━━━━━━━━━━━━━━━
4. 자동승인 정책 개선안
━━━━━━━━━━━━━━━━━━

목표는 "무조건 승인"이 아닙니다.

큰 위험이 없는 경우에는 최대한 자동으로 받아주되,
다른 학생에게 잘못 연결되는 오승인은 막아야 합니다.

다음 우선순위를 기준으로 현재 DB 구조에서 가능한지 검토하십시오.

강한 식별정보가 일치하는 경우
→ 이름 표기 차이 때문에 불필요하게 실패시키지 않는 방향

예:

- 앞뒤 공백
- 이름 내부 불필요 공백
- 전화번호 하이픈
- 전화번호 공백
- 010-1234-5678 / 01012345678 형식 차이

등은 normalization 후 비교.

하지만 다음은 자동승인하지 않습니다.

- 다른 학생으로 연결될 가능성이 있는 경우
- 동일 조건 학생이 여러 명 검색되는 경우
- 전화번호 등 핵심 식별정보가 불일치하는 경우
- tenant/swimming_pool이 다른 경우
- 신청만으로 학생을 유일하게 특정할 수 없는 경우

이런 경우에는 pending으로 보내 관리자가 결정합니다.

현재 DB 구조를 본 뒤
"자동승인 가능 / 관리자 확인 필요 / 승인 금지"
3단계 기준을 제안하십시오.

━━━━━━━━━━━━━━━━━━
5. 관리자 수동 승인 버튼 오류
━━━━━━━━━━━━━━━━━━

이것은 별도로 정확히 원인을 찾으십시오.

자동승인 실패는
"자동으로 연결하지 못했다"는 뜻이지
"관리자도 승인할 수 없다"는 뜻이 아닙니다.

관리자가 실제 학생/학부모 정보를 보고
올바른 연결이라고 판단했다면
[승인] 버튼으로 최종 승인할 수 있어야 합니다.

현재 [승인] 버튼을 눌렀을 때:

- onPress 실행 여부
- handler
- request id
- API URL
- HTTP method
- request body
- 서버 route
- auth/role 검사
- DB query
- response status
- client error handling

을 끝까지 추적하십시오.

특히 자동승인 실패 reason이 존재한다는 이유로
수동승인 API까지 차단하고 있는지 확인하십시오.

━━━━━━━━━━━━━━━━━━
6. 수동 승인 시 지켜야 할 것
━━━━━━━━━━━━━━━━━━

관리자 수동승인은 자동매칭 조건을 다시 통과시키는 기능이 아닙니다.

관리자가 확인하고 승인하는 별도 권한입니다.

따라서 올바른 대상이 특정된 상태라면:

pending
→ 관리자 승인
→ parent_students 연결/갱신
→ status = approved
→ 해당 학부모가 해당 학생 접근 가능

이 되어야 합니다.

단:

- 다른 swimming_pool 학생 연결 금지
- 존재하지 않는 student 연결 금지
- 존재하지 않는 parent 연결 금지
- 중복 연결 안전 처리
- 이미 approved이면 idempotent 처리 검토
- 관리자 권한 검증 유지

자동승인 실패 사유는
관리자에게 참고정보로 보여주되
수동승인을 원천 차단하는 조건으로 사용하지 마십시오.

━━━━━━━━━━━━━━━━━━
7. 거절 후에도 다시 승인 가능해야 함
━━━━━━━━━━━━━━━━━━

사용자 요구사항:

관리자가 실수로 거절했거나
추후 정보를 확인하여 정상 연결이라고 판단한 경우
거절된 신청도 다시 승인할 수 있어야 합니다.

따라서:

pending → approved
pending → rejected

뿐 아니라

rejected → approved

전환이 가능한지 현재 구조를 조사하십시오.

거절됨 탭에서도 해당 신청을 열어
관리자가 [승인]할 수 있어야 합니다.

단순히 UI 버튼만 추가하지 말고
서버 state transition과 DB까지 실제로 허용되는지 확인하십시오.
