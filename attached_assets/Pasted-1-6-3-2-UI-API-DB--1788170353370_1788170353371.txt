1.6.3 운영 버전에서 인증 관련 문제 2건을 반드시 실제 원인까지 추적해서 수정한다.

중요:
- 추측으로 수정하지 말 것.
- UI만 고치지 말고 실제 API/DB/인증 흐름까지 확인할 것.
- 1.6.3은 현재 운영 버전이므로 기존 사용자 로그인/회원가입을 깨뜨리지 않는 최소 수정으로 진행할 것.
- 조사 → 재현 → 원인 확정 → 수정 → 회귀테스트 → commit까지 한 번에 진행한다.
- 실제 Production 개인정보/비밀번호 원문을 로그에 출력하지 말 것.
- Production 데이터는 임의 삭제/변경하지 말 것.
- 배포가 필요한 경우 완료보고에서 정확히 구분한다.

==================================================
문제 1. 선생님 "비밀번호 찾기 → 비밀번호 변경" 후
비밀번호가 실제로 변경되지 않거나 이후 로그인도 되지 않는 문제
==================================================

현재 1.6.3에서 선생님이 비밀번호를 잊었을 때
"비밀번호 찾기" 경로로 들어가 새 비밀번호를 설정했는데,
변경이 정상 반영되지 않거나 변경 후 로그인할 수 없는 사례가 있다.

이 기능을 처음부터 끝까지 다시 검증한다.

A. 앱 흐름 조사
- 1.6.3의 선생님 로그인 화면
- 비밀번호 찾기 진입 경로
- 본인 확인 방식
- 새 비밀번호 입력 화면
- 비밀번호 변경 API 호출
- 성공/실패 응답 처리
- 변경 후 로그인 요청

각 화면/함수/API endpoint를 정확히 찾는다.

B. 서버 인증 로직 조사
다음을 확인한다.

- 비밀번호 찾기 API가 실제 어떤 user/teacher 계정을 조회하는지
- 전화번호/아이디/email 등 어떤 identifier를 사용하는지
- teacher 계정과 parent/admin 계정 테이블 또는 role 분기가 올바른지
- 새로운 비밀번호가 DB에 실제 UPDATE 되는지
- bcrypt/hash 방식이 회원가입 및 일반 비밀번호 변경과 동일한지
- plaintext가 저장되거나 이중 hash 되는 버그가 없는지
- reset 단계에서 hash된 값을 다시 hash하는지
- login의 bcrypt.compare 입력과 저장 hash가 일치하는지
- reset 대상 user id와 login 대상 user id가 동일한지
- center/pool tenant 조건 때문에 다른 계정을 찾는 문제가 없는지
- inactive/deleted 상태가 잘못 적용되는지
- reset token/verification token 만료나 consume 로직 문제인지
- transaction이 commit되지 않는 경우가 있는지
- UPDATE query의 WHERE 조건 때문에 affected rows=0이 되는지
- API가 UPDATE 실패인데도 success를 반환하는지

C. 반드시 테스트 계정으로 재현
Production 사용자 비밀번호를 임의 변경하지 말고,
테스트 DB 또는 안전한 테스트 계정으로 아래를 재현한다.

1. 기존 비밀번호 로그인 성공
2. 비밀번호 찾기 진입
3. 새 비밀번호 설정
4. DB hash가 실제 변경됐는지 확인
5. 이전 비밀번호 로그인 실패
6. 새 비밀번호 로그인 성공
7. 앱 재시작 후 새 비밀번호 로그인 성공

선생님 role 계정으로 반드시 테스트한다.

D. 정상 정책
비밀번호 찾기로 새 비밀번호 설정 성공 시:

- 서버에서 대상 계정이 정확히 1명 식별되어야 한다.
- 새 비밀번호는 현재 로그인과 동일한 hash 정책으로 저장되어야 한다.
- UPDATE가 실제 1 row 이상 반영된 경우에만 success 반환.
- 이후 새 비밀번호로 즉시 로그인 가능.
- 이전 비밀번호는 로그인 불가.
- 에러 발생 시 앱에서 "변경 완료"라고 잘못 표시하면 안 된다.

필요하면 API 응답에 명확한 error code를 추가하되
기존 1.6.3 클라이언트와 backward-compatible하게 처리한다.

==================================================
문제 2. 토이키즈스윔클럽
황이준 / 황승혜 회원가입 불가 원인 조사 및 수정
==================================================

토이키즈스윔클럽에서
- 황이준
- 황승혜

두 사용자가 회원가입이 안 된다고 한다.

이름만 보고 원인을 추측하지 말고 실제 Production 데이터/로그/가입 흐름을 확인한다.

A. 개인정보 보호
- 이름으로 DB를 조회할 수는 있지만 완료보고에 전화번호/생년월일/보호자 정보/비밀번호/hash 등 민감정보를 출력하지 말 것.
- 결과는 계정 상태와 오류 유형만 보고한다.

B. 두 사람의 현재 상태 조사
토이키즈스윔클럽 tenant/pool 기준으로 각각 확인:

- 회원/student 레코드 존재 여부
- parent/user 계정 존재 여부
- 보호자 연결 레코드 존재 여부
- 가입 대기 상태 여부
- 전화번호 중복 여부
- 다른 pool 계정과 identifier 중복 여부
- 탈퇴/삭제/비활성 계정 여부
- 기존 가입 흔적 여부
- 초대/연결 token 상태
- parent-child 관계가 이미 생성됐는지
- 두 명이 형제/동일 보호자 구조인 경우 가입 로직이 이를 잘못 막는지
- 첫째 가입 후 둘째 등록 시 unique constraint가 충돌하는지
- 보호자 1명이 자녀 2명을 연결하는 정상 흐름이 지원되는지
- 학생 이름 중복 검사 때문에 막히는지
- 휴대전화 정규화(010..., 하이픈 유무, +82 등) 문제인지
- DOB/이름/전화번호 매칭 조건이 너무 엄격하거나 잘못됐는지

C. 가입 API/DB 오류 확인
최근 해당 사용자 가입 시도와 연관된 서버 로그에서:

- HTTP status
- endpoint
- error code
- DB constraint
- unique violation
- foreign key violation
- validation error
- tenant mismatch
- "already exists"
- student not found
- guardian mismatch
등을 확인한다.

민감 입력값은 마스킹해서 확인한다.

D. 정확한 재현
두 사용자의 실제 계정에 임의 변경을 가하기 전에
현재 데이터 상태를 기반으로 테스트 fixture를 만들어 동일 조건을 재현한다.

특히 아래 케이스를 반드시 테스트:

1. 신규 보호자 + 자녀 1명
2. 기존 보호자 + 두 번째 자녀
3. 동일 전화번호로 형제 2명 연결
4. 이미 student가 존재하지만 parent user가 없는 경우
5. 기존 parent 계정은 있지만 해당 student 연결이 없는 경우
6. 이미 연결된 student를 재가입하려는 경우
7. 전화번호 하이픈/국가번호 표기 차이
8. 탈퇴 후 재가입 케이스

E. 원인별 수정
실제 원인이 확인되면 그 원인만 최소 수정한다.

예:
- 보호자 전화번호 unique 때문에 형제 가입이 막혔다면
  parent account를 새로 만들지 말고 기존 parent에 두 번째 child relation을 추가하도록 수정.
- 전화번호 normalize 문제면 가입/로그인/비밀번호찾기에서 동일 normalize 함수를 사용.
- stale pending account 문제면 안전한 재가입/재연결 정책 추가.
- 이미 가입된 계정인데 앱이 신규가입만 시도한다면 적절한 안내 또는 기존계정 연결 흐름으로 변경.
- DB constraint 설계가 잘못된 경우 backward-compatible migration을 만든다.

두 사람만 강제로 DB 수정해서 끝내지 말 것.
같은 상태의 다른 회원도 정상 가입할 수 있도록 근본 원인을 수정한다.

공통 회귀 테스트
==================================================

수정 후 아래 인증 흐름 전체 확인:

- 선생님 기존 계정 로그인
- 선생님 비밀번호 찾기
- 새 비밀번호 설정
- 새 비밀번호 로그인
- 잘못된 비밀번호 로그인 실패
- 관리자 로그인
- 학부모 기존 로그인
- 신규 학부모 가입
- 기존 학부모 + 추가 자녀 연결
- 형제 2명 동일 보호자 가입/연결
- 탈퇴/비활성 계정 처리
- 전화번호 normalize
- 기존 1.6.3 API contract 유지

가능한 관련 자동 테스트를 추가하고 전체 PASS 확인한다.

- shared API 수정이면 1.6.3 backward compatibility를 반드시 확인한다.

deploy-photo-clone

잘못된 branch(main 등)에만 수정하지 말 것.
