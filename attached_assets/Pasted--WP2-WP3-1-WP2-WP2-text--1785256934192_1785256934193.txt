# WP2 검토 결과 및 WP3 작업 승인

## 1. WP2 검토 결과

WP2는 수정 조건부로 통과합니다.

정상적으로 구현된 핵심 항목:

```text
표준 응답 student_ref + content 우선
구형 응답 student_id + feedback 임시 호환
request_id 일치 검증
오래된 응답 차단
알 수 없는 student_ref 전체 차단
중복 student_ref 전체 차단
일부 학생 누락 허용
응답 전체 검증 후 Draft 반영
잘못된 응답에서 기존 Draft 보존
Contract 오류 자동 재시도 차단
```

학생 결과를 임의로 합치지 않고 전체 응답을 차단하도록 바꾼 판단이 정확합니다.

---

# 2. WP2 필수 보완

## JSON 파싱 실패 분류 수정

현재 보고서상 JSON 파싱 실패는 다음 경로로 처리됩니다.

```text
JSON.parse 실패
→ PARSE_ERROR throw
→ 일반 catch
→ 네트워크 오류로 분류
→ 자동 재시도 1회
```

이 처리는 수정해야 합니다.

JSON 파싱 실패는 네트워크 오류가 아닙니다.

```text
HTTP 응답은 도착했지만
Response Contract를 해석할 수 없는 상태
```

이므로 다음과 같이 처리합니다.

```text
CONTRACT_RESPONSE_PARSE_ERROR
자동 재시도 없음
Draft 미적용
기존 입력 유지
사용자용 일반 오류 표시
```

권장 방향:

```ts
let body: unknown;

try {
  body = JSON.parse(responseText);
} catch {
  throw new DiaryContractError(
    'CONTRACT_RESPONSE_PARSE_ERROR'
  );
}
```

또는 현재 오류 처리 구조에 맞춰:

```ts
return {
  ok: false,
  contractError: 'CONTRACT_RESPONSE_PARSE_ERROR',
};
```

로 처리합니다.

JSON 파싱 실패를 Timeout, fetch 실패, DNS 실패와 같은 네트워크 오류 catch로 보내면 안 됩니다.

이 수정은 WP3 시작 시 가장 먼저 수행합니다.

# 3. WP3 작업 목적

WP3에서는 다음만 처리합니다.

```text
개인정보 로그 제거
민감정보 로그 차단
오류 코드 로그 정리
중복 요청 안전성 재확인
오래된 응답 차단 재검증
사용자 오류 메시지 정리
JSON 파싱 오류 분류 수정
```

기존 AbortController와 State Machine이 이미 정상적으로 구현되어 있으므로 구조를 다시 만들지 않습니다.

# 8. 학생 ref 로그 정책

현재 Contract 오류 문자열에 다음처럼 ref 값이 포함된 것으로 보고되었습니다.

```text
CONTRACT_UNKNOWN_STUDENT_REF: ref=student_xxx
CONTRACT_DUPLICATE_STUDENT_REF: ref=student_xxx
```

오류 로그에는 실제 ref 전체를 넣지 않습니다.

변경:

```text
CONTRACT_UNKNOWN_STUDENT_REF
CONTRACT_DUPLICATE_STUDENT_REF
```

필요하다면 별도 안전 메타데이터로 다음만 허용합니다.

```text
student_index
response_student_count
```

학생 ref도 개인 식별 연결 가능성이 있으므로 전체 값을 로그에 남기지 않습니다.

사용자 화면에는 Contract 오류 코드 자체도 노출하지 않습니다.

---

# 9. request_id 로그 정책

request_id는 로그 추적용으로 남길 수 있습니다.

허용:

```text
[DIARY-AI] request_started request_id=...
[DIARY-AI] request_completed request_id=...
[DIARY-AI] contract_error request_id=... code=...
```

다만 로그마다 같은 정보를 과도하게 반복하지 않습니다.

권장 최소 로그:

```text
REQUEST_STARTED
REQUEST_RETRY
REQUEST_SUCCEEDED
REQUEST_FAILED
REQUEST_ABORTED
```

# 10. 전체 응답 로그 제거 확인

다음 형태는 완전히 제거합니다.

```ts
console.log(JSON.stringify(data));
console.log(responseBody);
console.log(result);
```

대체 로그:

```ts
console.log('[DIARY-AI] response_received', {
  request_id: expectedRequestId,
  status: response.status,
  student_count: normalized.students.length,
  has_common: normalized.common.length > 0,
});
```

`has_common`은 boolean으로만 남깁니다.

본문 길이조차 필요하지 않으면 남기지 않습니다.

---

# 11. Request 로그 정리

Request Body 전체를 출력하지 않습니다.

권장:

```ts
console.log('[DIARY-AI] request_started', {
  request_id: requestBody.request_id,
  class_id_present: Boolean(requestBody.context.class_id),
  pool_id_present: Boolean(requestBody.context.pool_id),
  student_count: requestBody.context.students.length,
  input_length: requestBody.input.text.length,
});
```

`class_id`와 `pool_id` 실제 값은 로그에 넣지 않는 것을 권장합니다.

운영 추적상 꼭 필요하다면 별도 보안 로그 정책이 확정된 뒤 추가합니다.

# 12. JSON 파싱 실패 수정

WP3에서 다음 테스트를 추가합니다.

```text
HTTP 200
Content-Type application/json
Body가 잘못된 JSON
```

기대 결과:

```text
CONTRACT_RESPONSE_PARSE_ERROR
자동 재시도 0회
Draft 미적용
기존 입력 유지
사용자 일반 오류 메시지
```

HTTP 502 등으로 HTML 오류 페이지가 반환된 경우도 JSON 파싱 실패가 발생할 수 있습니다.

이때 HTTP Status를 먼저 검사하는 현재 구조라면:

```text
retryable HTTP status
→ 기존 서버 오류 재시도 정책 적용
```

하고, 성공 HTTP Status인데 JSON이 깨진 경우만 Contract Parse Error로 분류합니다.

처리 순서:

```text
HTTP status 판정
↓
성공 응답일 때 JSON 파싱
↓
파싱 실패면 Contract 오류
```

# 13. 오류 메시지 분리

사용자에게 내부 오류를 그대로 보여주지 않습니다.

## 사용자 메시지

Contract 오류:

```text
AI 일지 결과를 불러오지 못했습니다. 다시 시도해주세요.
```

네트워크 오류:

```text
네트워크 연결을 확인한 후 다시 시도해주세요.
```

인증 오류:

```text
로그인 정보가 만료되었습니다. 다시 로그인해주세요.
```

Timeout:

```text
AI 응답이 지연되고 있습니다. 다시 시도해주세요.
```

현재 앱의 기존 문구 체계가 있다면 그 표현을 유지합니다.

# 14. 중복 요청 처리 재확인

현재 구현:

```text
isInFlightRef
State Machine PROCESSING
AbortController
```

가 이미 있으므로 새 구조를 추가하지 않습니다.

다음만 테스트합니다.

```text
AI 생성 버튼 연속 2회
처리 중 버튼 비활성화 또는 무시
실제 HTTP 요청 1회
자동 재시도는 같은 request_id
사용자 다시 생성은 새 request_id
```

# 15. 오래된 응답 처리 재확인

다음 시나리오를 테스트합니다.

```text
요청 A 시작
A 취소 또는 새 요청 B 시작
B 응답 정상 도착
A 응답이 늦게 도착
```

기대:

```text
B만 Draft 반영
A는 State 변경 없음
A 오류가 현재 B 화면을 ERROR로 바꾸지 않음
```

마지막 항목이 중요합니다.

오래된 A 응답이 폐기되는 과정에서 현재 요청 B의 정상 결과 화면을 오류 상태로 바꾸면 안 됩니다.

따라서 stale response는 일반 Contract 오류와 구분할 수 있습니다.

권장:

```text
CONTRACT_REQUEST_ID_MISMATCH
→ 현재 활성 요청의 응답 자체가 잘못된 경우 ERROR

STALE_RESPONSE_IGNORED
→ 이미 다른 요청이 활성화된 경우 조용히 폐기
```

오래된 응답은 로그만 남기고 현재 State Machine을 변경하지 않는 것이 안전합니다.

---

# 16. Abort 처리 정책

다음 Abort 사유를 구분합니다.

```text
new-request
unmount
timeout
manual-cancel
```

권장 처리:

```text
new-request
→ 오류 화면 표시 안 함

unmount
→ State 변경 없음

timeout
→ 기존 Timeout 오류 처리

manual-cancel
→ 현재 UX 정책 유지
```

Abort error 전체 객체를 출력하지 않습니다.

---

# 17. 로그 환경 정책

가능하면 개발 로그는 다음 조건으로 제한합니다.

```ts
if (__DEV__) {
  console.log(...);
}
```

다만 운영 오류 추적 시스템이 이미 있다면 무조건 제거하지 말고 현재 Repository의 공통 Logger 사용 여부를 확인합니다.

이번 WP에서 새로운 외부 로그 서비스나 패키지를 추가하지 않습니다.

# 19. WP3 필수 테스트

## 로그 검사

```text
학생 이름 입력 후 Console에 이름 없음
STT 원문이 Console에 없음
AI 응답 본문이 Console에 없음
feedback/content가 Console에 없음
Authorization이 Console에 없음
학생 ref 전체가 Console에 없음
```

## 정상 요청

```text
request_started
request_succeeded
request_id
학생 수
처리 상태
```

만 출력되는지 확인합니다.

## Contract 오류

```text
request_id mismatch
unknown student
duplicate student
invalid type
empty result
JSON parse failure
```

확인:

```text
본문 미출력
학생 ref 미출력
자동 재시도 없음
기존 Draft 유지
```

## 네트워크 및 서버

```text
fetch 실패
Timeout
429
500
502
401
```

각 기존 재시도 정책이 유지되는지 확인합니다.

## Stale 응답

```text
오래된 응답이 최신 정상 Draft를 변경하지 않음
오래된 응답이 최신 화면을 ERROR로 바꾸지 않음
```

## Unmount

```text
화면 종료 후 응답 도착
State 변경 경고 없음
오류 화면 없음
```
