============================================================
3. GET /attendance
============================================================

Teacher가 class_group_id를 지정한 요청:

1.
authenticated teacher

2.
same pool

3.
teacher가 해당 class에 접근 권한 있음

검증 후 조회.

권한 없는 same-pool class:
403

Admin:
기존 same-pool 조회 정책 유지.

class_group_id가 없는 aggregate endpoint가
별도 의미를 갖는다면
기존 contract를 조사하여
teacher에게 허용되는 자신의 class 범위만 집계.

다른 반 데이터가 aggregate에 섞이면 FAIL.

============================================================
4. POST /attendance
============================================================

Teacher mutation은
반드시 server-side class ownership 검증.

검증 순서:

auth
→ role
→ pool
→ class ownership
→ student/class consistency if applicable
→ mutation

같은 pool 다른 teacher class:
403

UI에서 route를 못 찾는다는 이유로
허용하지 마십시오.

============================================================
5. Student / class consistency
============================================================

attendance payload에 studentId가 있다면:

student가 해당 class/context에 속하는지
기존 attendance business rule로 확인.

Teacher A의 classId
+
Teacher A 권한 밖 studentId

조합으로 mutation 가능하면 FAIL.

기존 보강/temporary enrollment 등
합법적인 예외가 있다면
현재 canonical attendance rule을 유지하고
임의로 막지 마십시오.
