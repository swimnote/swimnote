1. students 본체 처리 확인

canonical withdraw 완료 후
students 테이블에서 해당 회원이
정확히 어떤 상태로 남는지 확인하십시오.

보고:

- students row 존재 여부
- status
- name
- phone

최종 제품 정책:

퇴원은 단순 연기와 다르며
회원 교육/서비스 데이터가 제거되는 종료 처리입니다.

다만 재등록 시에는
과거 student를 복구하지 않고
신규 student_id로 시작해야 합니다.

현재 구조상 students row를 완전 DELETE하면
audit/attendance/history FK가 깨진다면
무리하게 DELETE하지 마십시오.

그 경우 최소 안전 구조:

- status = withdrawn 또는 deleted
- 활성 반/스케줄 제거
- 재등록 대상에서 제외
- 학부모 연결 제거
- 서비스용 개인정보 중 더 이상 필요 없는 값 제거/익명화

등으로 처리할 수 있는지 확인하십시오.

핵심은:

퇴원한 회원의 이름/연락처 등
서비스용 회원정보가 불필요하게 그대로 노출되는 상태를
“데이터 삭제 완료”라고 보고하지 않는 것입니다.

현재 FK 구조에 맞는 최소 방식을 적용하십시오.

2. R2 best-effort 제거 또는 실패 추적
━━━━━━━━━━━━━━━━━━━━━━

현재 보고:

student_photos / videos / assets
→ DB DELETE + R2 best-effort

라고 되어 있습니다.

퇴원 성공 응답이 났는데
R2 object 삭제가 실패하고 아무 추적도 남지 않는 구조는
최종 정책과 맞지 않습니다.

기존 storage helper 구조를 사용하여
다음 중 최소 하나를 보장하십시오.

A.
R2 삭제 실패 시 withdraw 전체를 실패 처리하고
사용자에게 성공으로 응답하지 않음

또는

B.
DB 삭제 전 R2 삭제 대상 목록을 확정하고,
실패 object를 재시도 가능한 cleanup queue/log에 남김

또는

C.
현재 프로젝트에 이미 존재하는 검증된
orphan cleanup/retry 구조를 재사용

대규모 storage framework 신규 개발 금지.

필수:

R2 삭제 실패를 조용히 무시하고
“퇴원 완료”라고 응답하는 경로는 없어야 합니다.

3. diary_push_queue 잔존 student_id 정리
━━━━━━━━━━━━━━━━━━━━━━

현재:

diary_push_queue.student_ids JSONB

안에 퇴원 회원 student_id가 남을 수 있으나

parent_students 삭제 때문에
실제 push 발송 대상에서는 제외된다고 보고했습니다.

하지만 퇴원 시 서비스 데이터 제거 정책상
이미 대기 중인 queue에서도
해당 student_id를 제거하십시오.

단:

같은 queue에 다른 학생 ID가 존재하면
그 학생들의 queue는 유지.

예:

student_ids = [A, B, C]

A 퇴원

→ [B, C]

A 하나뿐이면
현재 queue schema/worker 의미에 맞춰
row 삭제 또는 empty-safe 처리.

다른 학생의 push에 영향 금지.
