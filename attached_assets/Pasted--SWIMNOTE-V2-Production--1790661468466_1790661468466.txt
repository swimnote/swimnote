[SWIMNOTE 공지사항 V2 — 실기기 이미지 첨부 실패 긴급 수정]

Production 실기기 검증에서 신규 버그가 확인됐다.

증상:
- 공지 작성/미리보기/날짜시간 등 다른 기능은 정상
- 이미지를 첨부해도 최종 공지에 이미지가 정상 반영되지 않음

이번 작업은 이미지 파이프라인만 정확히 추적하여 Root Cause를 찾고
최소 수정한다.

추측 수정 금지.
관련 없는 공지 기능 수정 금지.
Production 배포 금지.

5) pickedImage / previewImageUri state 저장
6) 미리보기에서 이미지 표시
7) 최종 [공지 등록]

3. 크롭 전/후 비교
━━━━━━━━━━━━━━━━━━━━━━

이번에 이미지 크롭 기능을 추가한 뒤 발생한 문제일 가능성이 있으므로
반드시 다음 두 경로를 비교한다.

[기존 원본 이미지]
image-picker URI
→ 기존 upload pipeline

[현재 크롭 이미지]
image-picker
→ ImageManipulator crop
→ cropped URI
→ upload pipeline

두 입력의:

- URI
- metadata
- MIME type
- filename
- extension
- file existence
- file size

차이를 확인한다.

Root Cause가 crop 이후 metadata 유실이라면
이미지 업로드 전체를 재작성하지 말고
crop 결과를 기존 uploader가 요구하는 canonical asset 형태로
정규화하는 최소 수정으로 해결한다.

━━━━━━━━━━━━━━━━━━━━━━
4. 업로드 실패를 숨기지 말 것
━━━━━━━━━━━━━━━━━━━━━━

현재 이미지 업로드가 실패했는데
텍스트 공지만 등록되고 있다면 수정한다.

사용자가 이미지를 선택한 상태에서
이미지 upload가 실패하면:

- 공지 POST를 이미지 없이 조용히 진행하지 않는다.
- "이미지 업로드에 실패했습니다. 다시 시도해주세요." 등
  명확한 오류를 표시한다.
- 작성한 제목/내용/대상/날짜/링크/이미지 state를 유지한다.
- 재시도할 수 있게 한다.

반대로 이미지가 선택되지 않은 공지는
기존처럼 정상 등록 가능해야 한다.

━━━━━━━━━━━━━━━━━━━━━━
5. 로그/보안
━━━━━━━━━━━━━━━━━━━━━━

진단에 필요한 최소 로그는 허용한다.

확인할 것:

- pipeline stage
- URI scheme
- mime type
- file extension
- file size
- presigned request 성공/실패
- PUT HTTP status
- object_key 존재 여부
- POST /notices image_urls 개수

절대 로그에 남기지 말 것:

- JWT
- Authorization header
- presigned URL 전체
- secret
- 개인정보

디버깅용 과도한 Production 로그를 남기지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
6. 표시 경로까지 반드시 확인
━━━━━━━━━━━━━━━━━━━━━━

업로드 성공만 보고 완료하지 않는다.

최종적으로:

R2 object 존재
→ notices.image_urls 저장
→ /notices/pending 반환
→ NoticePopup URL 변환
→ 실제 이미지 표시

까지 확인한다.

현재 완료보고에는:

API_BASE.replace(/\/api$/, "") + "/uploads/" + key

방식으로 표시한다고 했으므로,
실제 Production API_BASE와 object_key를 넣었을 때
유효한 이미지 endpoint가 되는지도 확인한다.

R2 object는 존재하는데 이 URL이 404/403이면
upload 문제가 아니라 delivery/display 문제다.

정확히 구분한다.

8. 검증

→ 미리보기 정상

D. cropped file
→ uploader 정상 입력

E. presigned 발급 성공

F. R2 PUT 성공 status 확인

G. image_urls에 정확한 object_key 포함

H. POST /notices 성공

I. DB image_urls 저장 확인

J. pending API에서 image_urls 반환 확인

K. 최종 display URL 정상 접근 확인

L. NoticePopup 이미지 렌더 정상

M. 이미지 upload 실패 강제 상황
→ 이미지 없는 공지로 조용히 등록되지 않음
→ 작성 데이터 유지
→ 재시도 가능

N. JPEG/PNG 각각 가능한 범위에서 확인

O. 기존 공지 regression 없음
