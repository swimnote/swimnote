선생님 모드에서 신규회원 등록을 2곳에 제공하고,

학부모 가입/연결까지 자연스럽게 이어지는
최종 구현계획을 제출한다.

━━━━━━━━━━━━━━━━━━━━━━
0. 최종 제품 요구사항
━━━━━━━━━━━━━━━━━━━━━━

신규회원 등록 진입점은 2개.

A.
선생님 모드
→ 반 배정 / 회원 배정 화면
→ "배정 가능 회원 검색" 옆
→ [신규등록]

이 경우:
신규회원 생성
→ 현재 보고 있는 반/스케줄에 즉시 자동 배정.

B.
선생님 모드
→ 회원관리
→ [신규등록]

이 경우:
관리자 신규회원 등록과 동일한 기능으로 회원 생성.

두 경우 모두 동일한 canonical 회원 생성 backend를 사용.

Teacher 전용 별도 회원 시스템 만들지 말 것.

━━━━━━━━━━━━━━━━━━━━━━
1. 기존 관리자 신규회원 등록 전수 조사
━━━━━━━━━━━━━━━━━━━━━━

현재 관리자 회원등록 구조를 실제 코드 기준으로 조사.

제출:

- 관리자 신규등록 화면 route
- component 파일
- 입력 필드
- 필수/선택 필드
- validation
- 중복회원 판단 규칙
- 전화번호 처리
- 보호자 정보 처리
- 학생 생성 API
- members/students/guardians 관련 DB tables
- 생성 후 후속 처리
- class assignment 연결 방식
- parent linkage 연결 방식

추측 금지.
실제 코드 기준.

━━━━━━━━━━━━━━━━━━━━━━
2. Teacher 회원관리 현재 구조 조사
━━━━━━━━━━━━━━━━━━━━━━

선생님 모드 회원관리에서:

- 현재 route
- 회원 목록 component
- 회원 상세 route
- 현재 teacher 권한
- 회원 생성 API 접근 가능 여부
- 관리자와 공유 가능한 component/service
- UI 상 신규등록 버튼을 넣을 정확한 위치

제출.

━━━━━━━━━━━━━━━━━━━━━━
3. 반 배정 화면 현재 구조 조사
━━━━━━━━━━━━━━━━━━━━━━

현재:

배정 가능 회원 검색

이 존재하는 정확한 화면/파일 확인.

확인:

- class_group_id
- schedule_id
- selected_date
- teacher_id
- pool_id

중 어떤 context를 이미 가지고 있는지.

신규회원 등록 후
현재 반에 자동 배정할 때
재사용할 canonical assignment API/function도 특정.

━━━━━━━━━━━━━━━━━━━━━━
4. 회원 생성 Source of Truth 통일
━━━━━━━━━━━━━━━━━━━━━━

최종 구조는:

관리자 신규등록
Teacher 회원관리 신규등록
Teacher 반 배정 신규등록

세 진입점 모두

같은 회원 생성 service/API
같은 validation
같은 duplicate rules
같은 pool tenant rules

을 사용해야 한다.

Teacher 전용 INSERT 경로 추가 금지.

필요하면 기존 endpoint에
role authorization만 최소 확장.

━━━━━━━━━━━━━━━━━━━━━━
5. 보호자 연결은 선행조건 아님
━━━━━━━━━━━━━━━━━━━━━━

중요.

Teacher/Admin가 신규 학생을 먼저 등록할 수 있어야 한다.

등록 시 보호자 계정이 없어도:

- student 생성
- 회원관리 노출
- 반 배정
- 출석
- 일지
- AI 일지
- 사진/기록
- curriculum progress

사용 가능.

보호자 회원가입을 기다리기 때문에
학생 생성이 막히는 구조 금지.

━━━━━━━━━━━━━━━━━━━━━━
6. 학부모 회원가입/연결 구조 조사
━━━━━━━━━━━━━━━━━━━━━━

여기가 중요.

현재 Parent가 회원가입 후
자녀 연결을 요청하는 실제 flow를 조사.

제출:

- Parent signup
- 전화번호/보호자 식별
- student 검색/매칭
- parent_student_request 또는 현재 canonical request table
- 관리자 승인 API
- 자동/수동 승인 조건
- 연결 완료 후 guardian/student relation
- 과거 diary/attendance/progress가 어떤 student_id 기준으로 노출되는지

목표:

Teacher가 먼저 만든 student
→ Parent가 나중에 가입
→ 연결 요청
→ 즉시 승인 가능
→ 동일 student_id에 보호자 연결
→ 과거 기록 그대로 보임

새 student를 다시 생성하는 흐름 금지.

━━━━━━━━━━━━━━━━━━━━━━
7. "즉시 승인 가능"의 최종 설계
━━━━━━━━━━━━━━━━━━━━━━

사용자 요구:

Teacher가 회원관리에서 신규등록한 학생은
학부모가 이후 회원가입/연결 요청하면
승인이 원활하고 즉시 가능해야 함.

현재 코드 기준으로 가장 단순한 최종 UX 설계 제출.

검토 후보:

A.
Parent 전화번호가 학생 등록 시 이미 입력되어 있고
가입 전화번호와 정확히 일치
→ 연결 요청을 관리자/Teacher가 1탭 승인

또는

B.
현재 정책상 안전하면
명확한 phone/student match 시 자동승인

단:
현재 보안/권한 정책을 보고 결정.

임의로 자동승인 만들지 말고
현재 구조에 가장 안전하고 빠른 방식 제안.

중복 동명이인/전화번호 불일치 위험도 함께 보고.

━━━━━━━━━━━━━━━━━━━━━━
8. Teacher 권한 최소 확장 설계
━━━━━━━━━━━━━━━━━━━━━━

Teacher에게 필요한 권한:

- 자기 pool 신규 student 생성
- 자기 pool 회원 조회
- 현재 반 신규회원 자동 배정

학부모 연결 승인까지 Teacher에게 줄지,
관리자만 유지할지
현재 권한/정책 기준으로 추천안 제출.

금지:

- 타 pool 접근
- 회원 삭제 권한 자동 확대
- 전체 관리자 권한 부여

━━━━━━━━━━━━━━━━━━━━━━
9. 두 진입점 UX 설계
━━━━━━━━━━━━━━━━━━━━━━

A. 반 배정에서 신규등록

최종 UX 후보:

배정 가능 회원 검색 [신규등록]
→ 기존 관리자 회원등록 form 재사용
→ 저장
→ student 생성
→ 현재 class 자동 assignment
→ modal 닫힘
→ 현재 반 목록 refresh
→ 방금 등록한 학생 표시

Home 이동 금지.
관리자 화면으로 이동 금지.

B. Teacher 회원관리 신규등록

회원관리 상단 [신규등록]
→ 같은 form
→ 저장
→ student 생성
→ Teacher 회원 목록 refresh
→ 신규회원 상세/목록 유지

반 자동배정은 하지 않음
(반 배정 진입점에서만 자동배정).

━━━━━━━━━━━━━━━━━━━━━━
10. Component 재사용 설계
━━━━━━━━━━━━━━━━━━━━━━

현재 관리자 회원등록 화면을 그대로 route 이동시키는 방식보다

가능하면:

MemberCreateForm / StudentCreateForm
또는 기존 equivalent component/service

를 공유해서:

Admin
Teacher Member Management
Teacher Class Assignment

세 곳에서 재사용하는 구조 제안.

대규모 refactor 금지.
현재 코드에 가장 적은 변경으로 설계.

━━━━━━━━━━━━━━━━━━━━━━
11. 중복회원 방어
━━━━━━━━━━━━━━━━━━━━━━

기존 duplicate 정책 실제 확인.

최종 구현에서 반드시 유지.

예:

- 같은 phone
- 같은 student name
- guardian phone
- 기존 student
- 기존 parent linkage

실제 rule 기준.

신규등록 중 기존 회원으로 판단되면:

새 student 무조건 생성 금지.

가능하면:
"기존 회원을 현재 반에 배정"
flow로 연결.

━━━━━━━━━━━━━━━━━━━━━━
12. 최종 E2E 설계
━━━━━━━━━━━━━━━━━━━━━━

구현 후 반드시 검증할 시나리오 설계 제출.

CASE A:
Teacher 반 배정
→ 신규등록
→ student 생성
→ 현재 반 자동배정
→ 출석 대상 등장
→ Diary 학생 목록 등장

CASE B:
Teacher 회원관리
→ 신규등록
→ student 생성
→ 회원 목록 표시
→ 보호자 없음
→ 출석/일지 사용 가능

CASE C:
CASE B에서 만든 student
→ Parent 신규가입
→ 자녀 연결 요청
→ 승인
→ 동일 student_id 연결
→ 이전 diary/attendance/progress 노출

CASE D:
중복회원
→ 새 student 중복생성 0

CASE E:
Teacher 타 pool 접근
→ 차단
