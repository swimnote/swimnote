2. 먼저 실제 Route 조사
==================================================

현재 Repository에서 기존 화면을 직접 찾아라.

다음 request_type 각각에 대응하는 실제 기존 route:

1. 결석 신청
2. 연기 신청
3. 보강 요청
4. 퇴원 신청

추측해서 pathname을 만들지 마라.

반드시 현재 Expo Router 파일 구조와
실제 기존 navigation 호출을 검색해서 확정한다.

각 대상 화면이 받는 실제 params도 확인:

- studentId
- requestId
- date
- 기타 기존 param

대상 화면이 받지 않는 param을 새로 만들지 않는다.

상담 요청 / 문의는 전용 업무 화면이 없으면 이동시키지 않는다.

==================================================
3. 연결 위치
==================================================

두 진입점 모두 동일하게 작동시킨다.

A.
선생님 홈
→ 봉투
→ 쪽지 · 학부모 요청 Bottom Sheet
→ 요청 선택

B.
쪽지보관함
→ 학부모 요청
→ 요청 선택

단, 현재 messages-inbox 카드 탭은
content 펼치기 기능으로 사용 중이다.

따라서 카드 전체 탭 navigation으로 덮어쓰지 마라.

가장 안전한 방식:

요청 카드에

[업무 처리]

또는 기존 디자인에 맞는 작은 action button/chevron을 추가하고
그 action에서만 해당 업무 화면으로 이동한다.

content expand 동작은 그대로 유지한다.

Bottom Sheet에서도 요청 row 선택 시
동일한 navigation helper를 사용할 수 있으면 재사용한다.

==================================================
4. 요청 유형 Mapping
==================================================

실제 서버의 request_type 값을 먼저 확인한다.

그 실제 값 기준으로 mapping한다.

개념상:

absence → 기존 결석 업무 화면
pause/postpone → 기존 연기 업무 화면
makeup → 기존 보강 업무 화면
withdrawal → 기존 퇴원 업무 화면

위 문자열은 예시일 뿐이다.

실제 enum/value를 코드에서 확인해서 사용한다.

상담/문의 등 업무 전용 화면이 없는 type:
→ navigation 하지 않는다.
→ 현재 요청 내용 확인/처리 UI 유지.

==================================================
5. 중요한 UX 원칙
==================================================

학부모 요청은 "업무 발생 알림"이다.

예:

학부모:
보강 요청
"8월 18일 보강 가능한 시간 알려주세요"

선생님:
학부모 요청 확인
→ [업무 처리]
→ 기존 보강 화면

결석 신청
→ [업무 처리]
→ 기존 결석 처리 화면

연기 신청
→ [업무 처리]
→ 기존 연기 처리 화면

퇴원 신청
→ [업무 처리]
→ 기존 퇴원 처리 화면

새 업무 처리 기능을 만들지 않는다.
기존 기능으로 진입만 연결한다.

6. 요청 상태를 자동 변경하지 말 것
==================================================

업무 화면으로 이동했다는 이유만으로:

pending → done

자동 변경 금지.

읽음 처리와 처리 완료는 별개다.

기존 read API는 유지 가능하지만
done/rejected는 기존 명시적 처리 흐름에서만 변경한다.
