# 보호자 2 전화번호 저장 및 연결 실패 긴급 수정

현재 보호자 2 전화번호를 추가하면 다음 문제가 발생합니다.

1. 입력값:
01062102386

2. 저장 시:
"네트워크 오류가 발생했습니다."

3. 학생 상세 화면에는:
62102386
으로 표시됩니다.

즉 다음 문제가 동시에 존재합니다.

- 보호자 2 저장 API 실패
- 전화번호 앞자리 010 손실
- 잘못 저장된 번호가 가입 대기 상태로 표시
- 보호자 2 학부모 계정 연결 불가

이번 작업은 UI 문구 수정이 아니라
전화번호 저장부터 학부모 2 연결까지 실제 원인을 찾아 수정하는 작업입니다.

==================================================
1. 가장 먼저 확인할 것
==================================================

전화번호가 코드 어디에서 숫자형으로 변환되는지 전부 찾으세요.

다음 사용 여부를 검색하세요.

- Number(phone)
- parseInt(phone)
- parseFloat(phone)
- unary plus: +phone
- database integer/bigint 타입
- JSON schema의 number 타입
- z.number()
- SQL CAST(... AS INTEGER)
- 숫자 input value 처리
- replace 후 앞자리 제거
- slice(3)
- substring(3)
- 국가번호 변환 로직

전화번호는 절대 숫자로 처리하면 안 됩니다.

반드시 문자열로 처리하세요.

정상 저장 형태:

01062102386

표시 형태:

010-6210-2386

API 전송과 DB 저장 형태는 기존 정책에 맞게
하이픈 없는 문자열로 통일해도 됩니다.

==================================================
2. 네트워크 오류의 실제 원인 확인
==================================================

현재 앱은 모든 실패를
"네트워크 오류가 발생했습니다."
라고 표시하는 것으로 보입니다.

실제 원인이 네트워크인지
서버 4xx/5xx인지 구분하세요.

PATCH /students/:id/parent-phones 요청에 대해 다음을 확인하세요.

- 실제 요청 URL
- HTTP method
- request body
- Authorization header
- teacher 권한
- tenant_id
- student id
- 응답 status code
- 응답 body
- 서버 로그
- DB 오류
- validation 오류
- route 등록 여부
- production 서버에 엔드포인트가 실제 배포됐는지

앱에서 catch 하나로 모든 오류를
네트워크 오류라고 표시하지 마세요.

다음처럼 구분하세요.

- 실제 fetch 실패: 네트워크 오류
- 400: 입력값 오류
- 401/403: 권한 오류
- 404: API 또는 학생 없음
- 409: 중복 전화번호
- 500: 서버 처리 오류

서버 응답 메시지가 있으면 사용자에게 해당 메시지를 표시하세요.

==================================================
3. 요청 body와 서버 validation 일치 확인
==================================================

앱에서 보내는 body와
서버가 기대하는 schema가 정확히 일치하는지 확인하세요.

예시 확인 대상:

앱:
{
  parentPhone1,
  parentPhone2
}

서버:
{
  parent_phone_1,
  parent_phone_2
}

또는

앱:
{
  slot: 2,
  phone: "01062102386"
}

서버:
{
  index: 2,
  phoneNumber: "01062102386"
}

필드명이 다르면 수정하세요.

undefined, null, 빈 문자열의 처리도 통일하세요.

==================================================
4. 보호자 2 저장 로직 수정
==================================================

보호자 2를 추가할 때 다음 흐름이 되어야 합니다.

1. 입력값 문자열 유지
2. 숫자 이외 문자만 제거
3. 010으로 시작하는 11자리인지 검증
4. API에 문자열로 전송
5. 서버에서 문자열로 저장
6. DB 저장 성공 후 최신 학생 상세 재조회
7. 보호자 2에 010-6210-2386 표시
8. 해당 번호 계정이 없으면 가입 대기
9. 해당 번호 계정이 이미 있으면 학생 연결 생성
10. 보호자 1 연결은 그대로 유지

==================================================
5. 이미 잘못 저장된 번호 처리
==================================================

현재 화면에 62102386으로 저장된 데이터가 있습니다.

이 값을 그대로 정상 번호로 간주하지 마세요.

다음 중 실제 DB 상태를 확인하세요.

- DB에 62102386 저장
- DB에는 정상인데 UI 포맷만 잘못 표시
- 저장 요청 실패 후 로컬 state만 잘못 반영
- optimistic update가 실패 후 rollback되지 않음

원인에 따라 수정하세요.

만약 API 실패 후 UI만 62102386으로 바뀐 것이라면
rollback이 누락된 것입니다.

저장 실패 시:

- 기존 보호자 2 상태 복구
- 잘못 입력된 번호를 목록에 남기지 않음
- 연결 상태 변경하지 않음
- 재조회로 서버 상태와 동기화

==================================================
6. 학부모 계정 자동 연결 확인
==================================================

정상 번호 저장 후 아래를 확인하세요.

보호자 2 번호와 동일한 학부모 계정이 이미 존재하면:

- 기존 보호자 1 연결 유지
- 보호자 2 계정과 동일 학생 연결 추가
- 기존 연결 덮어쓰기 금지
- student-parent 연결 row 2개 유지

학부모 계정이 아직 없으면:

- 전화번호만 가입 대기 상태로 저장
- 해당 번호로 학부모 가입 시 자동 연결
- 보호자 1 연결 유지

==================================================
7. DB 타입 확인
==================================================

다음 컬럼 타입을 확인하세요.

- parent_phone_1
- parent_phone_2
- guardian phone
- user phone
- 연결 대기 전화번호

전화번호 컬럼은 다음이어야 합니다.

- varchar
- text

다음이면 잘못된 구조입니다.

- integer
- bigint
- numeric

DB 타입이 숫자형이라면
왜 기존 번호는 정상 보였는지까지 확인하고
안전한 마이그레이션 계획을 먼저 보고하세요.

DB 변경이 필요하면 바로 적용하지 말고
현재 타입과 변경안을 먼저 보고하세요.

==================================================
8. production API 배포 확인
==================================================

이번 기능은 OTA만으로 해결되지 않을 수 있습니다.

앱 OTA는 배포됐지만
서버 API 변경이 production 서버에 반영되지 않았을 가능성을 확인하세요.

확인할 것:

- PATCH /students/:id/parent-phones production 등록 여부
- production 서버 재배포 여부
- preview에서만 존재하는지
- production base URL이 구버전 서버를 보는지
- route import 누락 여부
- 서버 restart 여부

클라이언트 OTA만 배포하고
서버 엔드포인트가 미배포 상태라면
정확히 보고하세요.

==================================================
9. 실패 시 rollback
==================================================

보호자 번호 저장은 낙관적 업데이트하지 않거나,
사용한다면 반드시 rollback하세요.

API 실패 시:

- 기존 전화번호 복구
- 연결 상태 복구
- 가입 대기 뱃지 복구
- 잘린 전화번호 남기지 않음
- 서버 재조회
- 정확한 오류 메시지 표시

10. 필수 테스트
==================================================

API 또는 통합 테스트로 확인하세요.

테스트 A:
01062102386 저장
→ DB에 01062102386 저장
→ UI에 010-6210-2386 표시

테스트 B:
앞자리 0 보존 확인
→ 010이 절대 제거되지 않음

테스트 C:
보호자 1 연결 상태 유지
→ 보호자 2 추가 후 보호자 1 연결 유지

테스트 D:
보호자 2 기존 계정 자동 연결
→ 동일 학생에 보호자 2 연결 추가

테스트 E:
보호자 2 미가입
→ 가입 대기 표시

테스트 F:
API 실패
→ 기존 상태 rollback
→ 잘린 번호 미표시

테스트 G:
같은 번호 중복
→ 409 또는 명확한 오류

테스트 H:
형제자매 동일 번호
→ 허용
