# [RT2 SUPPORT — FINAL RETRIEVAL + KNOWLEDGE GAP CLOSURE]

현재 SHA:
258485b2

RT2 Retriever 구조는 거의 완료.

그러나 Production read-only 결과에서
두 종류의 문제가 남아 있음.

A. RETRIEVAL RANKING 문제
B. CANONICAL KNOWLEDGE 자체의 데이터 부족

둘을 구분하여 마지막으로 정리한다.

아직 Render deploy 금지.

==================================================
1. Q1 / Q2 — RETRIEVAL BUG
==================================================

현재:

Q1 "학부모리포트는 어떤기능이야?"
Q2 "성장리포트가 뭐야"

top-1:
"리포트 결과의 근거는 무엇인가요"

이것은 정확한 답변 KI가 아님.

이전 Production 검사에서 존재 확인된:

"학부모용 성장리포트가 뭔가요"

또는 동일한 정의/기능 설명 KI가
정의 질문에는 더 적합함.

따라서 DB 데이터 추가로 해결하지 말고
ranking/tie-break 원인을 확인.

확인:

- 두 KI 최종 score breakdown
- score cap=100 때문에 정보가 소실되는지
- 동일 100점 tie 정렬 기준
- title/question lexical relevance
- FEATURE_DESCRIPTION goal 내부에서
  definition/overview와 evidence/basis를 구분 가능한지

특정 KI ID boost 금지.

==================================================
2. SCORE SATURATION 확인
==================================================

현재 여러 서로 다른 후보가
100점으로 saturation될 가능성 확인.

score를 단순 cap 100으로 잘라
ranking 정보가 사라진다면 수정.

가능한 방식:

raw_score는 cap 없이 ranking에 사용
display_score만 0~100 normalize

또는 동등한 deterministic 방법.

목표:

더 직접적인 title/question match가
관련 있지만 다른 KI보다 항상 위.

==================================================
3. Q3 / Q4 — KNOWLEDGE GAP
==================================================

Production 확인 결과:

NOTIFICATION + PREFERENCE facet에
정확한 active KI가 없음.

따라서 이것은 Retriever 실패가 아니라
CANONICAL KNOWLEDGE GAP이다.

질문:

Q3 "알림끄는거 어디서해?"
Q4 "푸시 알림 설정"

에 답할 실제 SWIMNOTE 기능/화면 경로가
기존 Knowledge DB에 존재하는지 전체 active KI에서 재확인.

있다면 Retriever가 못 찾는 문제로 처리.

정말 없다면:
missing canonical knowledge = YES

라고 판정.

==================================================
4. DB에 없는 설정을 GPT가 창작 금지
==================================================

정확한 PREFERENCE KI가 없는데:

EVENT_TRIGGER
PERMISSION
TROUBLESHOOT

Knowledge만 전달하여
GPT가 "알림 설정은 어디에서 끕니다"
같은 제품 사용법을 임의 생성하면 안 됨.

따라서:

exact/relevant canonical evidence 없음
→ INSUFFICIENT_EVIDENCE

가 기본.

GROUNDED_AI는
실제로 질문에 답할 수 있는 verified evidence가
존재할 때만 허용.

==================================================
5. CANONICAL KNOWLEDGE 보강 원칙
==================================================

DB gap이 확정되면
utterance 문장을 추가하지 않는다.

canonical Knowledge Item 자체를 추가한다.

예시 개념:

NOTIFICATION_SETTINGS_PREFERENCE

질문/제목은
특정 테스트 문장 복사가 아니라
제품 기능의 canonical 형태.

예:

- 알림 수신 설정은 어디에서 변경하나요?
- 푸시 알림을 켜거나 끄는 방법
- 알림 설정 변경 방법

단 실제 앱에서 지원되는 경로/동작을
코드로 먼저 확인하고
사실인 내용만 Knowledge에 작성.

임의 기능 경로 창작 금지.

==================================================
6. 실제 앱 기능 TRACE
==================================================

알림 설정 관련 canonical KI가 없다면
앱 코드에서 실제 기능부터 확인.

확인:

- 알림 설정 UI 존재 여부
- 화면/component
- route/navigation
- OS 설정으로 보내는지
- 앱 내부 toggle인지
- role별 차이
- iOS/Android 차이

실제 구현된 동작만 Knowledge에 넣는다.

==================================================
7. DATA GAP과 RETRIEVAL GAP 분리
==================================================

최종 diagnostics에도 구분 가능해야 함.

예:

NO_MATCH
= 관련 Knowledge 없음

KNOWLEDGE_GAP
= 질문 intent/facet는 명확하지만
  해당 canonical Knowledge가 없음

RANKING_MISS
= 적합한 Knowledge가 DB에 있는데
  낮은 순위로 밀림

STATUS_EXCLUDED
= 관련 KI 존재하지만 inactive/pending

이 구분을 Runtime missing_reason에
최소 변경으로 추가 가능하면 반영.

10. CANONICAL KI 추가가 필요하면
==================================================

- answer_mode
- scope

까지 작성.

승인 후 DB에 넣는다.
