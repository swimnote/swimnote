[최신 실기기 증거]
━━━━━━━━━━━━━━━━━━━━━━

관리자 계정에서 앱을 실행했을 때
슈퍼관리자가 발송한 공지 팝업이 실제로 표시됐다.

따라서 기존의:

"앱 시작 시 공지 팝업 자체가 뜨지 않는다"

문제는 최신 실기기 기준 해결 확인이다.

다시 popup mount/pending lifecycle을 수정하지 마라.

하지만 실제 기기에서 새로운 문제 2건이 확인됐다.

문제 A.
슈퍼관리자가 대표 이미지를 첨부해서 공지를 발송했지만
실제 공지 팝업에는 이미지가 표시되지 않았다.

실제 팝업에는:

제목: 테스트
본문: 테스트
닫기

만 표시됐고 대표 이미지는 없었다.

문제 B.
팝업의 "닫기"를 누르면 팝업은 화면에서 사라지지만
그 직후 앱 전체의 터치가 먹지 않았다.

사용자는 앱을 완전히 재실행해야 다시 조작할 수 있었다.

이 두 문제는 실제 Production iPhone 증상이므로
코드상 추정보다 우선하는 최신 증거다.

PHASE 1-A

━━━━━━━━━━━━━━━━━━━━━━

실제 이미지 데이터가 어느 단계에서 사라지는지
end-to-end로 추적한다.

슈퍼관리자 이미지 선택
→ crop 결과
→ 최종 등록
→ R2 upload
→ POST /notices
→ notices.image_urls
→ GET /notices/pending
→ NoticePopup
→ NoticePopupCard
→ 이미지 URL resolution
→ React Native Image

각 단계를 실제 코드와 데이터 계약으로 확인한다.

반드시 확인:

1. 실제 테스트 공지 DB row의 image_urls 값
2. image_urls가 빈 배열인지 실제 key가 있는지
3. R2 object가 실제 존재하는지
4. 저장 형식이 object key인지 full URL인지
5. /notices/pending 응답에 image_urls가 포함되는지
6. pending API serializer에서 누락되는지
7. NoticePopup의 Notice type에 image_urls가 있는지
8. NoticePopup이 NoticePopupCard에 imageUri를 전달하는지
9. image_urls[0]을 실제 표시 URL로 변환하는 로직이 있는지
10. NoticePopupCard의 imageUri가 실제 Image source까지 전달되는지
11. URL encoding 문제 여부
12. 인증이 필요한 /uploads 경로인지
13. 관리자 공지함에서 사용하는 이미지 URL resolution과
    teacher/parent 공지함의 이미지 resolution이 일치하는지

현재 teacher/parent 공지함 수정에서는:

API_BASE/uploads/${encodeURIComponent(key)}

형태를 사용하도록 수정돼 있다고 보고됐다.

팝업도 동일한 서버 저장 계약을 사용하는 공지라면
가능하면 동일한 canonical image URL resolution을 사용한다.

단,
현재 구조 확인 없이 무조건 복사하지 마라.

실기기 증상:

popup 표시
→ 닫기 터치
→ popup 화면에서는 사라짐
→ underlying app 전체 touch 불가
→ 앱 재실행 필요

이 흐름을 정확히 추적한다.

확인:

닫기 button
→ handleClose
→ setVisible(false)
→ React render
→ RN Modal dismiss
→ onDismiss
→ backdrop 제거
→ responder 해제
→ underlying RootNav touch 복구

NoticePopup 관련 다음을 전부 확인:

- Modal
- transparent
- animationType
- presentationStyle
- statusBarTranslucent
- navigationBarTranslucent
- onRequestClose
- onDismiss
- backdrop View/Pressable
- absoluteFill
- pointerEvents
- zIndex
- elevation
- Gesture/PanResponder

특히 확인:

현재 코드가

if (!notice) return null;

구조이고

handleClose가
setVisible(false)

만 실행한다면,

visible=false 이후에도 notice state가 남아 있으면서
어떤 wrapper/native host가 render tree에 남는지 확인한다.

이것이 원인이라고 미리 단정하지 말고
실제 render 구조를 확인한다.

대표 이미지는 등록 UI에서 이미 16:9 crop을 사용한다.

16:9 결과가 자연스럽게 보이도록 한다.

원칙:

- 이미지가 있으면 카드 폭에 맞는 16:9 영역

충분히 시각적으로 사용할 수 있어야 한다.
