원인 조사 방향을 다시 정확히 잡아주십시오.

토이키즈스윔클럽 계정은 RevenueCat으로 결제하지 않는 계정입니다.

제가 앱의 실제 운영자이기 때문에 초기 개발 단계부터 슈퍼관리자가 결제 없이 강제로 플랜과 이용 권한을 부여하여 계속 사용할 수 있도록 만들어 놓은 계정입니다.

이것은 이번에 새로 요청하는 기능이 아니라, 초기부터 계속 정상 작동하던 기존 핵심 기능입니다.

정상 권한 판정은 반드시 다음 구조여야 합니다.

RevenueCat 또는 일반 결제 구독 활성
OR
슈퍼관리자 강제 이용 권한 활성
→ 앱 이용 허용

따라서 이번 문제를 단순한 RevenueCat 구독 취소나 일시적인 DB 불일치로 처리하지 마십시오.

현재 가장 유력한 문제는 OTA 재시작 후 로그인 및 /auth/me 재검증 과정에서 기존 슈퍼관리자 강제 이용 권한이 무시된 것입니다.

중요:
아직 코드를 수정하거나 DB 값을 임의로 변경하지 마십시오.
먼저 기존 강제 권한 기능의 실제 구현을 찾아 작업계획서를 제출하십시오.

반드시 조사할 내용:

1. 슈퍼관리자 화면의 '구독 직접 조정' 기능이 호출하는 정확한 API
2. 해당 API가 수정하는 테이블과 컬럼 전체
3. 초기부터 사용하던 강제 이용 권한 컬럼 또는 플래그
4. manual_override, admin_grant, force_active, subscription_override, complimentary, lifetime_access 등 유사 필드 존재 여부
5. Premier 1000 및 만료일 2035.12.31이 실제로 어디에 저장되는지
6. 결제 플랫폼이 없는 상태에서도 이용 가능하도록 만든 기존 조건식
7. /billing/status가 슈퍼관리자 강제 권한을 어떻게 인식하는지
8. /auth/me가 슈퍼관리자 강제 권한을 어떻게 인식하는지
9. 로그인 unifiedLogin()이 강제 권한을 어떻게 인식하는지
10. 모든 API에 적용되는 구독 미들웨어가 강제 권한을 어떻게 인식하는지
11. 기존에는 정상 작동했는데 현재 재로그인 시 무시되는 이유
12. 최근 코드 변경 또는 서버 배포에서 강제 권한 예외 조건이 제거되었는지
13. 앱이 메모리 세션에서는 작동하지만 재로그인 및 세션 복원에서만 차단되는 이유
14. 슈퍼관리자 직접 조정 화면과 실제 로그인 권한 판정이 같은 단일 소스를 사용하는지
15. 강제 권한 계정에 RevenueCat 상태를 덮어씌우거나 동기화하는 코드가 있는지
16. payment_platform이 null인 것을 취소 또는 비활성으로 오판하는 코드가 있는지
17. 403 응답의 실제 error_code와 서버 로그
18. 일반 403을 클라이언트가 pool_deactivated로 잘못 바꾸는 fallback 문제
19. '오늘 자정 이후 데이터가 영구 삭제됩니다' 문구가 실제 삭제 시스템과 연결되어 있는지
20. 슈퍼관리자 강제 권한 계정은 삭제 대상에서 반드시 제외되는지

필수 증거:

- 슈퍼관리자 '구독 직접 조정' API 코드
- 해당 API가 실행하는 DB update 코드
- 관련 DB 스키마
- 토이키즈스윔클럽 pool의 실제 관련 컬럼 값
- /billing/status 코드
- /auth/me 코드
- unifiedLogin 관련 서버 코드
- 구독 차단 미들웨어 코드
- pool_deactivated 반환 코드 전체
- 데이터 삭제 예약 또는 cron 코드
- 해당 계정의 최근 상태 변경 로그
- 기존 강제 권한 기능이 정상 작동했던 조건식의 git history

판정 기준:

A. 슈퍼관리자 강제 권한은 billing에 저장되지만 인증 미들웨어가 pools.subscription_status만 확인한다면
→ 권한 판정 소스 불일치가 원인입니다.

B. 강제 권한 플래그가 존재하지만 /auth/me 또는 미들웨어가 확인하지 않는다면
→ 기존 예외 조건 누락이 원인입니다.

C. 강제 권한은 정상인데 다른 403 응답을 클라이언트가 pool_deactivated로 바꿨다면
→ 403 fallback 오판이 직접 원인입니다.

D. RevenueCat 초기화 또는 Webhook이 강제 권한 상태를 덮어쓴다면
→ 수동 관리자 권한이 결제 시스템보다 우선하도록 분리해야 합니다.

수정 원칙:

- 기존 슈퍼관리자 강제 권한 기능을 복구할 것
- 단순히 토이키즈 계정 DB 값만 일회성으로 active 처리하지 말 것
- RevenueCat 미결제여도 슈퍼관리자 강제 허용 계정은 계속 이용 가능해야 함
- /auth/me, 로그인, 세션 복원, 전체 API 미들웨어가 동일한 권한 판정 함수를 사용해야 함
- 강제 허용 계정은 구독 중단 및 데이터 삭제 대상으로 판정하지 말 것
- 일반 403을 pool_deactivated로 변환하지 말 것
- 실제 데이터 삭제 기능은 원인이 해결될 때까지 실행되지 않도록 확인할 것
- 메인 수영장 데이터의 현재 상태를 먼저 백업하거나 기록할 것

작업계획서 승인 전에는 코드 수정, DB 변경, 서버 배포, OTA 배포를 진행하지 마십시오.
