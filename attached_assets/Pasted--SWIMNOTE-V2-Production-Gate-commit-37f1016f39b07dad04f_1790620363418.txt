[SWIMNOTE 공지사항 V2 — 발행 전 미리보기 추가 + Production 배포 전 최종 Gate]

현재 기준 commit:
37f1016f39b07dad04f91db8a8c47eb11e7a8fe3

현재 공지사항 V2 구현은 전체적으로 승인 방향과 일치한다.

다만 Production 배포 전에 아래 3개 작업을 완료한다.

1. 공지 작성 → 미리보기 → 수정 → 최종 발행 workflow 추가
2. 실제 Modal 표시 이후 seen 기록 보장
3. seen endpoint 대상/권한 검증 보강

Production DB migration / API deploy / OTA는 아직 실행하지 마라.

━━━━━━━━━━━━━━━━━━━━━━
GATE 1. 공지 발행 전 미리보기
━━━━━━━━━━━━━━━━━━━━━━

슈퍼관리자가 공지를 작성한 뒤
즉시 Production 공지로 등록되는 구조로 만들지 않는다.

최종 workflow는:

공지 작성
↓
[미리보기]
↓
실제 앱 공지와 동일한 형태로 확인
↓
[수정하기] 또는 [공지 등록]
↓
수정하기 선택
→ 작성 화면으로 돌아가 기존 입력값 수정
→ 다시 미리보기 가능

공지 등록 선택
→ 그때 최종 POST /notices 실행

즉 사용자가 실제 발행 전에
내용과 디자인을 직접 확인하고 수정할 수 있어야 한다.

━━━━━━━━━━━━━━━━━━━━━━
1-1. 작성 화면
━━━━━━━━━━━━━━━━━━━━━━

작성 화면에서 입력:

- 제목
- 내용
- 대상
  · 학부모
  · 관리자 + 선생님
  · 전체
- 이미지 optional
- 링크 URL optional
- 링크 버튼 문구 optional
- 노출 시작일시

하단 primary action은
즉시 "등록"하지 말고

[미리보기]

로 한다.

필수 입력값 validation을 통과해야
미리보기로 이동할 수 있다.

미리보기를 누르는 것만으로
DB에 공지가 생성되면 안 된다.

━━━━━━━━━━━━━━━━━━━━━━
1-2. 실제 사용자 화면 기반 미리보기
━━━━━━━━━━━━━━━━━━━━━━

미리보기는 단순 텍스트 alert가 아니다.

실제 사용자가 앱 실행 시 보게 되는
공지 Popup/Card의 최종 UI와 최대한 동일해야 한다.

가능하면 실제 NoticePopup의
presentation component를 재사용한다.

공지 표시 UI를:

- 실제 공지용
- 슈퍼관리자 미리보기용

두 벌로 복제하지 않는다.

공통 presentation component를 분리/재사용할 수 있다면
최소 변경으로 그렇게 구성한다.

목표:

미리보기에서 본 모습
≈
실제 학부모/관리자/선생님이 보는 모습

이어야 한다.

━━━━━━━━━━━━━━━━━━━━━━
1-3. 미리보기에서 확인할 내용
━━━━━━━━━━━━━━━━━━━━━━

실제 공지 카드 형태로 다음을 보여준다.

[대표 이미지 — 있을 경우]

공지 제목

공지 내용

[CTA 버튼 — 링크 있을 경우]

[닫기]

그리고 실제 공지 콘텐츠 외 별도 영역에서
슈퍼관리자에게만 다음 발행 정보를 명확히 표시한다.

- 발송 대상
- 노출 시작일시

예:

발송 대상: 학부모
노출 시작: 2026-09-29 09:00

이 정보는 실제 사용자 공지 Popup에는
불필요하게 노출하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
1-4. 미리보기 이미지
━━━━━━━━━━━━━━━━━━━━━━

이미지를 선택한 경우
발행 전에 미리보기에서 실제 이미지가 보여야 한다.

현재 upload 구조를 조사해서
불필요한 orphan R2 파일이 생기지 않는 방식으로 처리한다.

가능하다면 최종 등록 전 미리보기는
선택한 local image URI로 표시하고,

실제 R2 upload는 최종 "공지 등록" 시점에 수행한다.

현재 architecture상 먼저 upload해야 한다면
취소/수정 시 orphan file이 남지 않는지 반드시 확인하고
안전한 방식을 선택한다.

━━━━━━━━━━━━━━━━━━━━━━
1-5. 수정하기
━━━━━━━━━━━━━━━━━━━━━━

미리보기 화면에:

[수정하기]
[공지 등록]

두 동작을 제공한다.

"수정하기"를 누르면:

- 제목 유지
- 내용 유지
- 대상 유지
- 이미지 유지
- 링크 유지
- 버튼 문구 유지
- 노출 시작일시 유지

상태로 작성 화면에 돌아가야 한다.

사용자가 일부만 수정한 뒤
다시 미리보기를 할 수 있어야 한다.

수정 횟수 제한 없음.

━━━━━━━━━━━━━━━━━━━━━━
1-6. 최종 등록
━━━━━━━━━━━━━━━━━━━━━━

미리보기에서 사용자가
[공지 등록]을 명시적으로 눌렀을 때만
실제 공지를 생성한다.

등록 직전에 다시 validation한다.

성공:
→ 성공 안내
→ 공지 관리 목록으로 이동/갱신

실패:
→ 작성 내용 유지
→ 오류 안내
→ 재시도 가능

등록 API 실패 때문에
사용자가 작성한 긴 공지 내용을 전부 잃게 만들지 않는다.

중복 탭으로 동일 공지가 여러 개 생성되지 않도록
등록 진행 중 버튼 disable/loading 처리한다.

━━━━━━━━━━━━━━━━━━━━━━
GATE 2. seen 기록 시점
━━━━━━━━━━━━━━━━━━━━━━

요구사항:

공지 seen은 fetch 시점이나
setVisible(true) 호출 시점이 아니라

공지 Modal이 실제 사용자 화면에 표시된 이후
기록되어야 한다.

현재 NoticePopup.tsx를 확인한다.

현재:

setNotice(...)
setVisible(true)
POST /notices/:id/seen

형태라면 수정한다.

React Native Modal의 onShow 또는
실제 표시 완료를 확인할 수 있는 lifecycle을 사용하여

"실제 표시됨"
→ POST /notices/:id/seen

순서로 만든다.

조건:

- 한 표시 세션에서 seen 요청 1회
- re-render 중복 요청 금지
- seen 실패가 공지/앱을 막지 않음
- UNIQUE(notice_id,user_id) 유지
- X/닫기를 눌러야 seen 처리하는 방식 아님
- 실제 표시되면 seen 처리

중요:

슈퍼관리자의 "미리보기"는 실제 공지 노출이 아니다.

미리보기 과정에서는
POST /notices/:id/seen을 절대 호출하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
GATE 3. POST /notices/:id/seen 권한 검증
━━━━━━━━━━━━━━━━━━━━━━

현재 endpoint가 단순히

- requireAuth
- notice 존재 확인

만 하고 있는지 실제 코드를 확인한다.

seen endpoint 자체에서도
현재 사용자가 해당 공지의 실제 대상인지
서버에서 검증해야 한다.

최소 조건:

- status = published
- starts_at 조건
- ends_at 존재 시 유효기간 조건
- target_roles가 현재 사용자 role과 일치
- pool-scoped 공지라면 해당 pool 대상인지
- global 공지라면 기존 global 정책 준수

GET /notices/pending의 eligibility와
논리적으로 동일해야 한다.

대상이 아닌 공지 ID를 직접 POST해도
notice_dismissals row가 생성되면 안 된다.

회귀/기능 테스트
━━━━━━━━━━━━━━━━━━━━━━

기존 wp4-notices 테스트를 다시 실행한다.

추가로 최소 다음을 검증한다.

[미리보기]

1. 제목+내용만
→ 실제 공지 형태로 미리보기

2. 이미지 포함
→ 이미지 정상 표시

3. 링크+버튼 문구 포함
→ CTA 정상 표시

4. 이미지+긴 본문+링크
→ 스크롤/레이아웃 정상

5. 수정하기
→ 모든 입력값 유지

6. 수정 후 다시 미리보기
→ 변경된 값 반영

7. 미리보기만 하고 취소
→ 실제 notices row 생성 안 됨

8. 미리보기
→ notice_dismissals/seen 생성 안 됨

9. 최종 공지 등록
→ 정확히 1개 생성

10. 등록 버튼 연속 탭
→ 중복 공지 생성 안 됨

11. 등록 실패
→ 작성 데이터 유지

[공지 노출]

12. 대상 사용자 정상 공지
→ 표시

13. 대상 아닌 role
→ 미표시

14. 다른 pool 공지
→ 미표시

15. 실제 Modal 표시
→ seen 1회

16. 단순 fetch만 되고 실제 표시 안 됨
→ seen 없음

17. 같은 사용자/공지 중복 seen
→ 중복 row 없음

18. unpublished/deleted
→ seen 생성 안 됨

19. starts_at 이전
→ seen 생성 안 됨

20. ends_at 지난 공지
→ seen 생성 안 됨
