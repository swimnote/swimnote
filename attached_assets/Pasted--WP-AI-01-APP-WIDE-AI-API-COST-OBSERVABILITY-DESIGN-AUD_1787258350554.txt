# [WP-AI-01 — APP-WIDE AI/API COST OBSERVABILITY DESIGN AUDIT]

목적:

SWIMNOTE에서 발생하는 GPT/OpenAI 및 기타 유료 외부 API 비용을
Super Admin이 실시간에 가깝게 확인할 수 있도록
현재 코드/DB를 최대한 재사용한 최소 비용계측 구조를 설계한다.

이번 단계는 DESIGN AUDIT ONLY.

코드 수정 금지.
DB write 금지.
Migration 금지.
외부 API 호출 금지.
Render deploy 금지.
전체 regression 금지.

==================================================
0. 제품 원칙
==================================================

자동으로 AI 기능을 제한하거나 끄는 시스템은
현재 구현 목표가 아니다.

목표는:

"비용이 어디서 얼마나 발생하는지
운영자가 즉시 확인할 수 있게 한다."

운영자가 비용을 보고:

- 기능 제한
- 호출 횟수 변경
- 가격 변경

등을 직접 판단한다.

==================================================
4. COMMON USAGE EVENT CONTRACT 설계
==================================================

모든 유료 API 호출에서 공통으로 남길 최소 contract 제안.

필수:

provider
service
model_or_api
feature
trigger_type

trigger_type:
- USER_ACTION
- SYSTEM_MAINTENANCE
- ADMIN_MANUAL
- BATCH_JOB

추가:

pool_id
request_id
timestamp

usage:
- input_tokens
- cached_input_tokens
- output_tokens
- audio_seconds
- request_count
- units

cost:
- estimated_cost_usd
- cost_source

cost_source 예:
- TOKEN_PRICING
- CONFIGURED_UNIT_PRICE
- PROVIDER_REPORTED
- UNKNOWN

runtime:
- latency_ms
- retry_count
- success
- error_type

PII 저장 금지.

==================================================
5. 비용을 모르면 거짓 계산 금지
==================================================

특히:

Growth Report Engine
Curriculum Engine
기타 external engine

이 provider가:

- token usage
- model
- actual cost

를 반환하지 않는다면
추정값을 임의 생성하지 않는다.

그 경우:

request_count
latency
success
feature
trigger_type

는 기록하고

estimated_cost_usd = null
cost_source = UNKNOWN

으로 설계.

단,
환경설정으로 "건당 계약단가"를
운영자가 입력할 수 있는 구조가 합리적인지 제안 가능.

예:

TODAY TOTAL
MONTH TOTAL

SYSTEM_MAINTENANCE
ADMIN_MANUAL
BATCH_JOB

를 각각 확인 가능하게 설계.

11. AiGateway 관계
==================================================

현재 5개 direct OpenAI call을
AiGateway로 옮기면
usage/cost logging을 한 군데에서 처리할 수 있는지 확인.

확인할 것:

A.
AiGateway 자체에 usage logging을 넣는 것이 좋은지

또는

B.
AiGateway 아래 별도 UsageRecorder가 좋은지

책임분리와 최소 변경 기준으로
하나를 추천.

중요:

향후 Support
Curriculum
AI Diary
Growth Report

모두 재사용할 수 있어야 함.

==================================================
12. 외부 API도 공통 계측
==================================================

OpenAI 전용 구조로 만들지 않는다.

예:

recordExternalUsage({
  provider,
  service,
  feature,
  triggerType,
  units,
  estimatedCostUsd,
  ...
})

같은 provider-neutral 구조가 적합한지 검토.

AI뿐 아니라:

SMS
R2
future video API
future document API

까지 사용 가능해야 함.

==================================================
13. 비용 Dashboard 자체가 비용을 발생시키면 안 됨
==================================================

Dashboard 조회를 위해
OpenAI Usage API 또는 외부 API를
매번 호출하는 구조는 금지.

우리 DB에 누적된 usage event를
SQL aggregate해서 보여주는 구조 우선.

OpenAI provider invoice/usage API를
향후 reconciliation에 사용하는 것은 별도.

실시간 dashboard는 local usage logs 기준.

==================================================
14. 성능
==================================================

매 API 호출마다 usage log를 남겨도
production latency가 크게 증가하지 않아야 함.

확인:

event_logs insert 방식
transaction coupling 여부
failure handling

usage logging 실패 때문에
사용자 AI 요청이 실패하면 안 됨.

best-effort telemetry인지
transactional인지 추천.
