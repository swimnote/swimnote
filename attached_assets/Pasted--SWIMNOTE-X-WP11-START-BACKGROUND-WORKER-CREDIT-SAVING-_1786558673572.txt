5. CONCURRENCY / LOCK
━━━━━━━━━━━━━━━━━━━━

동시에 worker 2개가 실행돼도
같은 job을 두 번 처리하면 안 된다.

가능하면 PostgreSQL의 기존 방식:

FOR UPDATE SKIP LOCKED

또는 실제 프로젝트의 locking 패턴 재사용.

application 메모리 lock만으로 처리 금지.

Worker crash 후 영구 lock 상태가 남지 않도록
stale lock 처리도 실제 schema 범위에서 확인.

━━━━━━━━━━━━━━━━━━━━
6. IDEMPOTENCY
━━━━━━━━━━━━━━━━━━━━

Worker retry 시
동일 결과가 중복 생성되면 안 된다.

각 job handler는 가능한 한 idempotent하게.

기존 unique/source id/request id가 있으면 재사용.

새 결과 table 구조 만들지 말 것.

동일 job 재실행:

→ 이미 처리됨 확인
→ 안전하게 완료/skip

형태 우선.

━━━━━━━━━━━━━━━━━━━━
7. RETRY POLICY
━━━━━━━━━━━━━━━━━━━━

기존 attempts/max_attempts/backoff 구조가 있으면 재사용.

없다면 현재 schema/설계 범위 내에서
최소 retry 정책만 적용.

원칙:

일시적 오류
→ retry

영구 validation 오류
→ 무한 retry 금지

max attempts 초과
→ FAILED 또는 실제 기존 최종 상태

정확한 status는 schema 기준.

새 queue framework 도입 금지.
