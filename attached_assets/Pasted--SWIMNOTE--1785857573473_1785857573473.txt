[SWIMNOTE 긴급 오류 — 보강 수업 회차 조회 실패 원인 확정 및 최소 수정]

현재 운영 앱 현상:

보강 대기
→ 보강반 배정
→ 반 선택
→ “수업 회차를 불러오지 못했습니다”

실패 API:

GET /teacher/makeups/:makeupId/eligible-occurrences
  ?class_group_id=:classGroupId

현재까지 확인:

- 라우트 존재
- class_group_id 전달 정상
- validateMakeupOccurrence는 이 조회 라우트와 무관
- 클라이언트에서 r.ok=false
- 정확한 HTTP status와 response body는 아직 미확인
- 개발 로그에 EMAXCONNSESSION 발생 이력은 있으나 운영 오류 원인으로 확정되지 않음

이번에는 추측 보고를 반복하지 않는다.
운영 오류의 status/body/서버 예외를 확보하고 원인별 최소 수정까지 진행한다.

Push·Render 배포·OTA·운영 DB 수정은 최종 보고와 승인 전 금지한다.

STEP 1. 클라이언트 오류 응답 원문 확보
━━━━━━━━━━━━━━━━━━━━━━

대상:

artifacts/swim-app/app/(teacher)/makeups.tsx
artifacts/swim-app/components/teacher/my-schedule/ClassDetailSheet.tsx

eligible-occurrences 호출에서 r.ok=false일 때 응답을 버리지 않는다.

다음을 안전하게 파싱한다.

const status = r.status;
const rawText = await r.text();

let body: any = null;
try {
  body = rawText ? JSON.parse(rawText) : null;
} catch {
  body = { raw: rawText };
}

개발 로그:

if (__DEV__) {
  console.error("[MAKEUP-OCCURRENCES-ERROR]", {
    status,
    error: body?.error ?? null,
    message: body?.message ?? null,
    makeupId,
    classGroupId,
  });
}

운영 사용자 Alert에는 개인정보 없이 다음을 표시한다.

“수업 회차를 불러오지 못했습니다.
오류 코드: {status} / {errorCode}”

예:

403 / POOL_MISMATCH
404 / CLASS_NOT_FOUND
500 / DB_CONNECTION_LIMIT
500 / SERVER_ERROR

서버 stack trace나 SQL은 사용자 화면에 표시하지 않는다.

두 호출부 모두 동일하게 적용한다.

STEP 2. 서버 라우트 단계별 로그 추가

대상:

artifacts/api-server/src/routes/teachers.ts

eligible-occurrences 핸들러에 request_id와 단계별 시간을 기록한다.

개인정보 로그 금지:

- 학생 이름
- 전화번호

const requestId =

STEP 3. 오류 코드 명확화
━━━━━━━━━━━━━━━━━━━━━━

현재 모든 예외를 막연한 500으로 반환하지 않는다.

다음 매핑을 적용한다.

소속 수영장 없음:

HTTP 403
{
  error: "POOL_NOT_FOUND"
}

보강 세션이 다른 수영장 소속:

HTTP 403
{
  error: "MAKEUP_POOL_MISMATCH"
}

반을 찾지 못함:

HTTP 404
{
  error: "CLASS_NOT_FOUND"
}

DB 연결 한도 오류:

e.code === "EMAXCONNSESSION"
또는 실제 DB 드라이버의 연결 제한 코드와 일치할 때만

HTTP 503
{
  error: "DB_CONNECTION_LIMIT",
  message: "잠시 후 다시 시도해 주세요."
}

그 외:

{
  error: "ELIGIBLE_OCCURRENCES_FAILED"
}

━━━━━━━━━━━━━━━━━━━━━━
STEP 4. DB 연결 풀 문제 확인
━━━━━━━━━━━━━━━━━━━━━━

EMAXCONNSESSION이 실제 운영 요청에서 발생한 경우에만 아래를 조사한다.

1. DB 클라이언트 생성 위치 전체 검색
2. 요청마다 new Pool / new Client를 생성하는지
3. db 인스턴스가 singleton인지
4. connect() 후 release() 누락 여부
5. transaction 미종료 여부
6. streaming query 미종료 여부
7. 개발 서버 hot reload로 Pool이 중복 생성되는지
8. Render 인스턴스 수 × pool max 계산
9. DB session mode pool_size=15와 앱 pool max의 관계
10. 동일 화면에서 API가 중복 호출되는지

중요:

단순히 이 라우트가 쿼리 네 번을 실행한다는 이유만으로
DB 풀 초과 원인으로 확정하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
STEP 5. 중복 요청 방지 확인
━━━━━━━━━━━━━━━━━━━━━━

클라이언트 양쪽에서 반 선택 시 동일 API가 중복 호출되는지 확인한다.

확인:

- onPress 중복
- useEffect 재호출
- 빠른 연속 탭
- retry와 기존 요청 동시 실행
- StrictMode 개발 중복
- 모달 재렌더로 selectClass 재실행

기존 sequence ref를 유지한다.

추가로 동일 반 요청 진행 중에는 같은 요청만 차단한다.

예:

const occurrenceRequestKey =
  `${makeupId}:${classGroupId}`;

동일 key가 pending이면 재호출 금지.
다른 반 선택은 허용하며 오래된 응답은 무시한다.

━━━━━━━━━━━━━━━━━━━━━━
STEP 6. 라우트 쿼리 구조 최소 최적화
━━━━━━━━━━━━━━━━━━━━━━

실제 DB 병목이 확인된 경우에만 적용한다.

현재 네 번의 쿼리를 무조건 합치는 대규모 리팩터링은 금지한다.

먼저 다음을 확인한다.

- 각 쿼리가 순차인지
- 동일 데이터를 중복 조회하는지
- makeup과 class 조회를 단일 JOIN으로 합칠 수 있는지
- member count가 기존 eligible-classes 결과와 중복되는지
- pool_holidays 조회 범위가 과도한지

안전한 최소 최적화 예:

1. makeup_sessions + class_groups를 단일 JOIN으로 조회
2. member count와 holidays는 Promise.all로 병렬 실행
3. 동일 poolId 조회를 라우트 내 1회만 수행

단, Drizzle/DB 클라이언트가 같은 연결에서 병렬 쿼리를 지원하는지 확인 없이
무조건 Promise.all을 적용하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
STEP 7. 오류별 수정 정책
━━━━━━━━━━━━━━━━━━━━━━

CASE A — 403 POOL_NOT_FOUND

- users.swimming_pool_id 실제 상태 확인
- teacher 계정의 pool 연결 경로 확인
- DB를 임의 수정하지 말고 누락 원인 보고

CASE B — 403 MAKEUP_POOL_MISMATCH

- handover된 보강의 swimming_pool_id가 왜 다른지 확인
- 다른 수영장 항목을 허용하지 않음
- 데이터 정합성 문제로 분리

CASE C — 404 CLASS_NOT_FOUND

- 선택한 class_group_id
- is_deleted
- swimming_pool_id
- eligible-classes 응답과의 불일치 확인

CASE D — 503 DB_CONNECTION_LIMIT

- DB pool singleton·release·중복 요청을 수정
- 재시도는 최대 1회, 짧은 지연 후 수행 가능
- 무한 재시도 금지
- 사용자에게 재시도 버튼 유지

CASE E — 500 ELIGIBLE_OCCURRENCES_FAILED

- stage와 stack 기준으로 직접 원인 수정
- 오류를 빈 회차 목록으로 처리하지 않음
