지금 앱에서 다시 확인했지만 증상이 그대로입니다.

- 배정 취소를 누르면 화면에서는 사라짐
- 모달을 닫았다 다시 열면 다시 나타남
- 보강 대기에도 즉시 나타나지 않음
- 앱 재실행 후에도 assigned 상태로 복구됨

따라서 “수정 완료” 보고는 실제 운영 환경에 반영되지 않았거나,
현재 앱이 다른 서버/다른 라우트/다른 빌드를 사용하고 있는 상태입니다.

이번에는 코드 설명을 하지 말고
실제 운영 환경에서 아래 내용을 증명하세요.

==================================================
1. 현재 앱이 호출하는 실제 URL 확인
==================================================

ClassDetailSheet.tsx와
(teacher)/makeups.tsx에서

배정 취소 버튼 클릭 시 실제 호출되는 전체 URL을 확인하세요.

예:
https://실제도메인/teacher/makeups/:id/revert

다음 내용을 제출하세요.

- baseURL
- endpoint
- HTTP method
- request headers의 role 관련 정보
- response status
- response body

로컬 서버나 preview 서버가 아니라
현재 production 앱이 호출하는 실제 서버 기준으로 확인하세요.

==================================================
2. 운영 서버에 새 라우트가 실제 존재하는지 확인
==================================================

현재 production 서버에서

PATCH /teacher/makeups/:id/revert

가 실제 등록되어 있는지 확인하세요.

다음을 제출하세요.

- 배포된 서버 commit hash
- 현재 서버 시작 로그
- 라우트 등록 파일
- 배포 완료 시각
- production 서버가 해당 commit을 실행 중이라는 증거

코드 저장소에만 존재하는 것은 배포 완료가 아닙니다.

==================================================
3. 실제 앱 요청 1건을 서버 로그에서 추적
==================================================

제가 앱에서 버튼을 누른 실제 요청 1건을 기준으로
서버 로그를 추적하세요.

반드시 아래 로그가 실제 production 서버에 찍혀야 합니다.

[teacher/makeups/revert]
userId=...
role=...
poolId=...
mkId=...
mk.status=...
mk.swimming_pool_id=...
mk.assigned_teacher_id=...
updated rows=...
returned status=...

로그가 없다면 앱이 해당 서버 또는 해당 라우트를 호출하지 않는 것입니다.

==================================================
4. DB 변경을 운영 DB에서 직접 확인
==================================================

버튼 클릭 직전과 직후 동일 makeup id를
production DB에서 직접 조회하세요.

제출:

클릭 전:
- id
- status
- assigned_class_group_id
- assigned_teacher_id
- assigned_date

클릭 후:
- id
- status
- assigned_class_group_id
- assigned_teacher_id
- assigned_date

반드시 실제 값으로 제출하세요.

“UPDATE 쿼리가 있습니다”가 아니라
운영 DB에서 status가 waiting으로 바뀐 결과가 필요합니다.

==================================================
5. 성공 응답 위조 여부 확인
==================================================

현재 증상은 클라이언트가 성공으로 처리하지만
DB는 그대로인 패턴입니다.

다음을 확인하세요.

- catch 블록에서 에러를 무시하는지
- response.ok 확인 없이 성공 처리하는지
- 200이 아닌 응답도 카드 제거하는지
- mock 응답 또는 fallback success가 있는지
- optimistic update 후 실패 rollback이 없는지
- API 함수가 실제 response body를 확인하는지

서버가 실패했는데 UI만 제거되는 코드가 있으면 제거하세요.

==================================================
6. 다른 라우트 또는 중복 라우트 확인
==================================================

프로젝트 전체에서 다음 문자열을 검색하세요.

- /teacher/makeups/:id/revert
- /admin/makeups/:id/revert
- handleRevert
- revertMakeup
- 배정 취소
- 보강대기자로 되돌리기

중복된 함수나 오래된 API 호출이 남아 있는지 확인하세요.

특히:

- ClassDetailSheet
- AdminClassDetailSheet
- teacher makeups
- admin makeups
- schedule detail
- my-schedule

각 화면이 어느 함수를 호출하는지 표로 제출하세요.

==================================================
7. production 앱 버전 확인
==================================================

현재 앱이 실제로 새 OTA를 받은 상태인지 확인하세요.

제출:

- 현재 앱 runtimeVersion
- 현재 update ID
- production channel
- embedded update인지 OTA인지
- 버튼 화면에 적용된 update ID
- API endpoint 변경이 포함된 update ID

“앱을 두 번 재시작하세요”라는 안내만 하지 말고
현재 실행 중인 update ID를 앱에서 표시하거나 로그로 확인하세요.

==================================================
8. 수정 후 실제 재현 영상 또는 연속 스크린샷
==================================================

같은 makeup id로 아래 순서를 실제 실행하세요.

1. 배정된 보강 표시
2. 배정 취소 클릭
3. DB status=waiting 확인
4. 모달 닫기
5. 모달 다시 열기
6. 학생이 다시 나타나지 않음
7. 보강 대기 탭 이동
8. 해당 학생 표시
9. 앱 완전 종료
10. 재실행 후에도 waiting 유지

이 전체 결과를 실제 화면 증거로 제출하세요.

==================================================
완료 조건
==================================================

다음 중 하나라도 없으면 완료가 아닙니다.

- production 앱 실제 요청
- production 서버 실제 로그
- production DB 실제 변경
- 모달 재진입 정상
- 보강 대기 즉시 표시
- 앱 재실행 후 상태 유지

이번에는 코드 수정 보고를 하지 말고,
실제 운영 환경에서 같은 makeup id가
assigned → waiting으로 영구 변경되는 증거를 제출하세요.
