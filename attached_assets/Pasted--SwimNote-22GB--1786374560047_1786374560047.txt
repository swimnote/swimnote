[추가 긴급 지시 — 사용자별 대용량 발생 + 학부모 앱까지 전수조사]

추가로 확인된 실제 현상:

- 김수연 사용자 기기: SwimNote 문서 및 데이터 약 22GB
- 김동호 사용자 기기: SwimNote 문서 및 데이터 약 6GB

두 사용자는 사진/영상 업로드 사용량 차이에 따라
앱 로컬 사용량이 다르게 증가했을 가능성이 있다.

단, 아직 이것이 직접 원인이라고 확정하지 않는다.
반드시 코드와 실제 저장경로를 통해 검증한다.

━━━━━━━━━━━━━━━━━━━━━━
P. 사용자별 용량 차이와 업로드량 상관관계 조사
━━━━━━━━━━━━━━━━━━━━━━

다음을 확인한다.

1. 사진을 많이 업로드한 계정일수록
   앱 Documents/Data 사용량이 증가할 수 있는 구조인지

2. 사진 1장 업로드 시:
   - 원본
   - 압축본
   - resize본
   - thumbnail
   - upload용 copy
   - 표시용 cache

   중 몇 개가 로컬에 생성되는지

3. 업로드 후 이 파일들이 삭제되는지

4. 같은 사진이 여러 로컬 경로에 중복 저장될 가능성이 있는지

5. 영상의 경우 동일 현상이 더 크게 발생하는지

6. 김수연 22GB / 김동호 6GB 차이가
   실제 업로드 횟수·사진·영상 사용량 차이로 설명 가능한 구조인지

코드 근거를 제시한다.

━━━━━━━━━━━━━━━━━━━━━━
Q. 학부모 앱도 동일하게 전수조사
━━━━━━━━━━━━━━━━━━━━━━

선생님 기능만 조사하면 안 된다.

학부모 계정에서 실행되는 모든 media 관련 경로를 조사한다.

특히:

- 학부모 홈 피드
- 일지 조회
- 앨범 조회
- 사진 확대
- 영상 재생
- 프로필/자녀 사진
- AI 성장 리포트 관련 이미지
- Instagram Story 생성/공유
- 서버 사진 다운로드
- expo-image 캐시
- prefetch
- thumbnail
- 임시 파일
- 다운로드 파일

확인해야 할 핵심:

학부모는 사진을 "업로드하지 않고 보기만 해도"
서버 사진을 로컬 persistent storage에 계속 축적하는 구조인지 확인한다.

즉 문제를 두 가지로 분리한다.

A. 업로드 사용자:
사진/영상을 올릴 때 로컬 복사본이 누적되는 문제

B. 조회 사용자:
서버의 사진/영상을 볼 때 로컬 캐시가 무제한 누적되는 문제

둘 다 별도로 검증한다.

━━━━━━━━━━━━━━━━━━━━━━
R. SWIMNOTE 저장 원칙 확정
━━━━━━━━━━━━━━━━━━━━━━

SWIMNOTE의 영구 데이터 원본은 서버/R2이다.

서버/R2:
사진/영상 영구 저장

DB:
URL + metadata + 관계정보 저장

앱:
영구 media 저장소로 사용하지 않는다.

따라서 정상 상태에서는
사용자가 사진/영상을 수천 장 업로드하거나 조회했더라도
앱 로컬 용량이 그 사진/영상 전체 용량에 비례하여
수 GB~수십 GB까지 계속 증가하는 구조여서는 안 된다.

단, 성능을 위한 제한적 캐시는 허용한다.

캐시는 반드시:

- 임시적이어야 함
- 삭제 가능해야 함
- 상한이 있어야 함
- 오래된 데이터가 정리되어야 함
- 서버/R2 원본과 독립적인 영구 원본으로 취급하면 안 됨

━━━━━━━━━━━━━━━━━━━━━━
S. 서버 업로드 성공 이후 검증
━━━━━━━━━━━━━━━━━━━━━━

사진/영상 upload 성공 시점에서:

SERVER/R2 upload 성공
        ↓
DB URL 저장 성공
        ↓
local temporary media 필요 여부 확인
        ↓
불필요하면 DELETE

이 lifecycle이 실제 코드에 존재하는지 확인한다.

중요:

서버/R2에 정상 업로드된 파일을
앱에서도 계속 영구 보존할 이유가 없다.

━━━━━━━━━━━━━━━━━━━━━━
T. 학부모 조회 캐시 정책 검증
━━━━━━━━━━━━━━━━━━━━━━

remote URL:

R2/server URL
    ↓
학부모 앱 표시

과정에서 OS/expo-image가 만드는 일반적인 캐시와

SWIMNOTE 코드가 직접 만드는 local copy를
반드시 구분해서 보고한다.

특히:

remote image
→ downloadAsync/copyAsync
→ documentDirectory
→ permanent file

구조가 있다면 집중 보고한다.

━━━━━━━━━━━━━━━━━━━━━━
U. 목표 상태
━━━━━━━━━━━━━━━━━━━━━━

최종 목표는 다음과 같다.

[영구 데이터]

R2 / Server / DB
        ↑
        │
        │ source of truth
        │
SWIMNOTE APP

앱에는:

- 로그인/설정
- 작은 metadata
- draft
- 제한된 임시 cache
- 현재 작업에 필요한 temporary media

정도만 존재해야 한다.

서버에 이미 올라간
사진/영상 전체 라이브러리를
각 사용자의 휴대폰에 다시 보관하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
V. 기존 사용자 22GB / 6GB 복구 정책
━━━━━━━━━━━━━━━━━━━━━━

신규 누적 차단과
기존 누적 데이터 정리는 별개 작업으로 설계한다.

예:

김수연 22GB
김동호 6GB

사용자가 앱을 삭제하고 다시 설치하지 않아도
업데이트 후 안전하게 불필요한 local media를
정리할 수 있는 방법을 조사한다.

단:

전체 Documents 삭제 금지
전체 AsyncStorage 삭제 금지
로그인 정보 삭제 금지
미업로드 사진 삭제 금지
작성 중 draft 삭제 금지
사용자 설정 삭제 금지

반드시 SWIMNOTE가 생성했고
서버 업로드가 끝났거나 다시 서버에서 받을 수 있는
불필요한 media/cache만 식별해서 제거해야 한다.
