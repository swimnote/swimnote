2. ModeContext 공개 타입
━━━━━━━━━━━━━━━━━━━━━━

다음 타입을 사용하십시오.

```typescript
export type XModeStatus =
  | "NOT_CONFIGURED"
  | "CURRICULUM_PENDING"
  | "READY";

export type PoolMode =
  | "normal"
  | "x_pending"
  | "x";

export interface PoolModeResult {
  pool_id: string;
  mode: PoolMode;
  xmode_entitlement: boolean;
  xmode_config_status: XModeStatus;
}

export type ModeLoadState =
  | "idle"
  | "loading"
  | "ready"
  | "error";

export interface ModeContextValue {
  mode: PoolMode | null;
  xmode_entitlement: boolean;
  xmode_config_status: XModeStatus | null;
  status: ModeLoadState;
  error: string | null;
  refreshMode: () => Promise<void>;
}
```

기본값:

```text
mode = null
xmode_entitlement = false
xmode_config_status = null
status = idle
error = null
```

오류가 발생해도 `mode="normal"`을 실제 서버 결과처럼 저장하지 마십시오.

5. API 캐시 처리 정정
━━━━━━━━━━━━━━━━━━━━━━

설계서에는 `_bustRelated("/pools/x-mode")` 호출이 포함돼 있지만 `_bustRelated`는 AuthContext 공개 API가 아닙니다.

이번 WP에서 `_bustRelated`를 외부로 노출하거나 AuthContext를 수정하지 마십시오.

다음 방식으로 확정합니다.

```typescript
apiRequest(token, "/pools/x-mode", {
  method: "GET",
  cache: "no-store",
});
```

실제 `apiRequest` 인자 형태가 다르면 기존 `fetchPool()`의 `cache: "no-store"` 사용 방식을 그대로 재사용하십시오.

목표:

* `_apiCache`에 기존 Mode 응답이 있어도 사용하지 않음
* foreground 복귀 시 서버에 실제 재조회
* AuthContext 공개 인터페이스 변경 없음
* 전체 `clearApiCache()` 호출 금지

`cache: "no-store"`가 현재 `apiRequest`에서 지원되지 않는다면 임의 우회하지 말고 중단하여 실제 함수 시그니처를 보고하십시오.

━━━━━━━━━━━━━━━━━━━━━━
6. refreshMode 동시 호출 방지
━━━━━━━━━━━━━━━━━━━━━━

React state의 `status === "loading"`만으로 중복 호출을 막으면 비동기 closure에서 동시에 두 요청이 시작될 수 있습니다.

`useRef<boolean>` 기반 요청 잠금을 사용하십시오.

예시 의미:

```typescript
const isRefreshingRef = useRef(false);

const refreshMode = useCallback(async () => {
  if (isRefreshingRef.current) return;
  if (!token || !poolId || !isSupportedRole) return;

  isRefreshingRef.current = true;
  setState({
    status: "loading",
    result: null,
    error: null,
  });

  try {
    // no-store 서버 조회
  } finally {
    isRefreshingRef.current = false;
  }
}, [token, poolId, isSupportedRole, apiRequest]);
```

새로운 전역 Lock이나 별도 파일은 만들지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
7. 이전 수영장 Mode 즉시 폐기
━━━━━━━━━━━━━━━━━━━━━━

`token`, `poolId`, `role` 중 Mode 식별에 필요한 값이 변경되면 이전 결과를 즉시 폐기하십시오.

처리 순서:

```text
token 또는 poolId 또는 지원 역할 변경
→ 기존 result=null
→ status=idle
→ error=null
→ 조건 충족 시 새 Mode 조회
```

이전 수영장의 `mode="x"`가 새 수영장에서 잠시라도 유지되지 않아야 합니다.

비동기 요청 응답 순서가 뒤바뀌는 경우도 막으십시오.

권장 방식:

* 요청 시작 시 현재 token과 poolId 캡처
* 응답 시 현재 token·poolId와 일치할 때만 상태 적용
* 또는 request sequence ref 사용

이 처리는 ModeContext 내부에서만 구현하십시오.

━━━━━━━━━━━━━━━━━━━━━━
8. 로그아웃 처리
━━━━━━━━━━━━━━━━━━━━━━

기존 로그아웃 코드는 수정하지 않습니다.

```text

또는

또는

```

초기화 결과:

```text

result = null
error = null
mode = null
```

기존 `AuthContext.logout()`의 `clearApiCache()` 동작은 그대로 유지합니다.

9. foreground 리스너 구조
━━━━━━━━━━━━━━━━━━━━━━

`_layout.tsx`에서 `<ModeProvider>`를 렌더링하는 같은 컴포넌트는 `useMode()`로 그 Provider 값을 읽을 수 없습니다.

따라서 다음 구조를 사용하십시오.

```tsx
<AuthProvider>
  <ModeProvider>
    <ModeForegroundRefresh />
    <기존 앱 트리 />
  </ModeProvider>
</AuthProvider>
```

`ModeForegroundRefresh`는 `_layout.tsx` 내부의 작은 컴포넌트로 작성할 수 있습니다.

역할:

* 기존 공통 AppState listener 구조 재사용
* background/inactive → active 전환 시 `refreshMode()` 호출
* UI 렌더링 없음 (`return null`)
* 별도 파일 생성 없음

기존 foreground listener 안에 직접 합치는 것이 구조상 가능하면 합치되, 반드시 Provider 아래에서 `useMode()`가 호출돼야 합니다.

기존 OTA 및 문의 조회 동작을 변경하지 마십시오.

11. 오류 분류
━━━━━━━━━━━━━━━━━━━━━━

가능한 범위에서 응답 상태를 다음처럼 저장하십시오.

```text
401 → unauthorized
403 → forbidden
404 → pool_not_found
500 이상 → server_error
timeout → timeout
JSON 파싱 실패 → parse_error
기타 네트워크 예외 → network_error
```

기존 `apiRequest`가 401을 전역 처리하고 throw하거나 응답을 반환하는 실제 방식에 맞추십시오.

중요:

* 이전 result는 유지하지 않음
* error 시 result=null
* error 시 mode=null
* 오류를 숨기고 ready/normal로 처리 금지
