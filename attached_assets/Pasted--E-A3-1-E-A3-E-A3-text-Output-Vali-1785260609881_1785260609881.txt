```text

```

# 3. 배포 전 추가 단위 테스트 1건

다음 테스트를 추가합니다.

## STUDENT_ITEM_NOT_OBJECT

입력:

```json
{
  "common": "공통 내용",
  "students": [
    null,
    123,
    "invalid",
    []
  ]
}
```

각 항목을 개별 테스트하거나 하나씩 실행합니다.

기대:

```text
OUTPUT_VALIDATION_FAILED
reason = STUDENT_ITEM_NOT_OBJECT
HTTP 500
retryable false
request_id echo
```

Primitive 학생 항목을 조용히 제거하면 안 됩니다.

이 테스트가 통과하면 추가 Validator 수정은 필요 없습니다.

---

# 4. students 결과 개수 상한

현재 별도 고정 숫자 상한은 추가하지 않습니다.

대신 다음 방어가 이미 존재하는지 확인합니다.

```text
요청 allowedStudentRefs 범위 밖 ref 차단
중복 ref 차단
```

이 두 조건이 있으면 유효한 최종 결과 수는 요청 학생 수보다 많아질 수 없습니다.

즉:

```text
최종 students.length <= allowedStudentRefs.size
```

가 자연스럽게 보장됩니다.

별도의 `MAX_STUDENTS = 100` 같은 상수는 이번 단계에서 추가하지 않습니다.

# 5. 앱 보완 상태 확인

Production 배포 전에 앱 `useDiaryAI.ts`에서 다음 두 항목이 반드시 완료되어야 합니다.

## A. Stale 판정

실제 Stale:

```text
expectedRequestId !== currentRequestIdRef.current
```

처리:

```text
조용히 폐기
State 변경 없음
```

현재 활성 요청의 응답 ID 불일치:

```text
expectedRequestId === currentRequestIdRef.current
response.request_id !== expectedRequestId
```

처리:

```text
CONTRACT_REQUEST_ID_MISMATCH
machine.setError()
자동 재시도 없음
PROCESSING 종료
```

서버 응답 ID가 현재 ID와 다르다는 이유만으로 stale 처리하면 안 됩니다.

---

## B. 빈 student content 앱 방어

정규화 시:

```ts
const normalizedContent = content.trim();

if (!normalizedContent) {
  continue;
}
```

빈 학생 content를 Draft 적용 목록에 포함하지 않습니다.

최종적으로:

```text
common 비어 있음
학생 결과도 0명
```

이면:

```text
CONTRACT_EMPTY_RESULT
```

로 처리합니다.

AI Engine에서도 제거하지만 앱에서도 이중 방어를 유지합니다.

# 11. Production 블로커 판정

다음 중 하나라도 발생하면 배포 완료로 판단하지 않습니다.

```text
request_id 불일치
앱 PROCESSING 상태 고착
알 수 없는 학생에게 결과 적용
학생 결과 중복 적용

401에서 앱 crash

학생 이름 또는 일지 내용 로그 노출
```

# 12. Legacy Flag 최종 판단

실제 Production API에서 정상 요청을 최소 5회 실행합니다.

5회 모두:

```text
response.request_id 존재
request_id echo 일치
```

하면 앱의 다음 Flag를 변경합니다.

```ts
ALLOW_LEGACY_RESPONSE_WITHOUT_REQUEST_ID = false;
```

그 후 request_id가 없는 성공 응답은 Contract 오류로 처리합니다.

단, 개발·스테이징 등 다른 서버가 구형 응답을 사용한다면 환경별 상태를 먼저 확인합니다.

---

# 13. student_id fallback 최종 판단

Production 또는 실제 배포 서버 테스트에서 최소 10회 이상 다음을 확인합니다.

```text
legacy_student_id_used = 0
```

이면 추후 fallback 제거가 가능합니다.

이번 최종 통합 단계에서는 fallback을 유지해도 됩니다.

즉:

```text
Legacy request_id 허용 Flag
→ 서버 echo 안정 확인 후 false 전환 권장

student_id fallback
→ 당분간 유지 가능
```

---

# 14. Rollback 기준

다음 문제가 발생하면 즉시 이전 AI Engine 버전으로 rollback합니다.

```text
Teacher Diary Endpoint 500 급증
정상 Request가 400 처리됨
JWT 인증 실패 증가
request_id echo 누락
GPT 응답 파싱 실패 급증
다른 AI Endpoint 영향
서버 시작 실패
```

Rollback 후 앱 코드는 현재 Contract 상태를 유지합니다.

구형 flat Contract를 앱에 다시 추가하지 않습니다.
