3. sender UI 수정 원칙
============================================================

실제 current message data에서
sender display name을 확인.

가능하면:

full teacher name
+
"선생님"

형식으로 표시.

예:
김수연 → 김수연 선생님

단 관리자/원장/다른 role이면
현재 role semantics에 맞게 표시.

무조건 teacher라고 하드코딩하지 말고
실제 sender role/displayName 기준으로 처리.

예:
관리자 메시지라면
관리자/원장 표시 정책이 따로 있으면 유지.

중요:
이름을 새로 추측하거나 가공하지 말 것.

7. 삭제 SERVER/API 확인
============================================================

기존 messenger API/schema에서
delete 지원 여부 먼저 확인.

IF 기존 delete endpoint 존재:
→ 재사용.

IF soft delete field 존재:
→ 기존 정책 재사용.

IF 전혀 없다면:
→ 최소 범위로 구현.

보안 필수:

DELETE 요청 시
server가 반드시 확인:

message.sender_id == authenticated user id

즉,
client에서 버튼 숨기는 것만으로 끝내지 말 것.

타인 메시지 삭제 요청:
403 또는 기존 auth error.

============================================================
8. 삭제 방식
============================================================

가능하면 기존 DB/history 정책에 맞춰
soft delete 우선 검토.

예:
deleted_at
is_deleted

현재 schema가 hard delete만 전제로 되어 있다면
무리하게 새 migration 만들지 말고
현재 구조 기준 최소 수정.

이번 WP에서 DB migration이 필요한 경우:
STOP 하고 완료보고에 BLOCKED 이유 작성.

임의 production migration 금지.
