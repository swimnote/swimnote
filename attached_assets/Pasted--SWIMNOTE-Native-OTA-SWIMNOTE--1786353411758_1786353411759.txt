[SWIMNOTE 업데이트 정책 영구 고정 — Native 강제 업데이트 + OTA 재시작 자동 적용]

이번 작업은 앞으로 SWIMNOTE의 모든 배포에서 유지할
업데이트 정책을 코드 수준에서 영구 고정하는 작업입니다.

특히 학부모 화면에서는
수동 "업데이트 확인" 버튼을 제거했기 때문에
사용자가 직접 업데이트를 확인하는 방식에 의존하면 안 됩니다.

모든 역할:

- parent_account
- teacher
- pool_admin
- 기타 앱 사용자

에서 자동 업데이트 확인이 동작해야 합니다.

━━━━━━━━━━━━━━━━━━━━━━
0. 최종 정책
━━━━━━━━━━━━━━━━━━━━━━

SWIMNOTE 업데이트는 두 종류를 완전히 분리합니다.

A. Native / Store Build 업데이트

예:
1.6.1 → 1.6.2
1.6.2 → 1.6.3
1.6.x → 1.7.0

처리:

앱 자동 실행 검사
→ 서버 /api/app-version
→ 현재 Native version < min_version
→ 강제 업데이트 Modal
→ 취소 불가
→ App Store / Play Store 이동
→ 업데이트 전까지 기존 앱 사용 불가


B. Expo OTA 업데이트

예:
같은 runtimeVersion 1.6.2에서
production channel에 새 OTA 배포

처리:

앱 자동 OTA 검사
→ 새 Update 존재
→ Update 다운로드
→ "업데이트 적용을 위해 앱을 다시 시작합니다" Modal
→ 재시작
→ 새 OTA 적용

Native Store update와 OTA update를
절대 같은 로직으로 처리하지 않습니다.

━━━━━━━━━━━━━━━━━━━━━━
1. 먼저 현재 구현 감리
━━━━━━━━━━━━━━━━━━━━━━

코드를 수정하기 전에 현재 실제 구현을 모두 조사합니다.

다음 두 경로를 독립적으로 추적:

[NATIVE]

앱 시작
→ version check
→ /api/app-version
→ version compare
→ min_version
→ force modal
→ store URL
→ blocking

[OTA]

앱 시작
→ Updates.checkForUpdateAsync()
또는 현재 사용 중인 Expo Updates API
→ fetchUpdateAsync()
→ Modal
→ reloadAsync()

각각:

- 파일
- 함수
- line
- 호출 시점
- 역할 제한 여부
- 로그인 전/후 여부
- 오류 처리

보고 후 필요한 수정까지 진행합니다.

━━━━━━━━━━━━━━━━━━━━━━
2. Native 강제 업데이트 자동 검사
━━━━━━━━━━━━━━━━━━━━━━

현재 `_layout.tsx` Version Gate를 기준으로
모든 사용자에게 자동 실행되어야 합니다.

중요:

학부모 홈 화면이나
설정 화면 진입에 의존하면 안 됩니다.

Root App 진입 단계에서 검사합니다.

사용자 역할과 관계없이:

parent_account
teacher
pool_admin

모두 동일하게 적용.

수동 버튼 존재 여부와 무관해야 합니다.

━━━━━━━━━━━━━━━━━━━━━━
3. Native version source
━━━━━━━━━━━━━━━━━━━━━━

가능하면 실제 Native 설치 버전 값을 사용합니다.

우선 검토:

Application.nativeApplicationVersion

또는

Constants.nativeAppVersion

현재 Constants.expoConfig.version을 사용하고 있다면
실제 Production Native Build에서 안전한지 검증합니다.

OTA bundle의 app config 값 때문에
Native Store version 판정이 달라지는 구조가 없어야 합니다.

가장 신뢰 가능한 Native version source 하나로 통일하는 것을 검토합니다.

임의 변경하지 말고 현재 Expo SDK 55 환경에서
정확한 동작을 확인 후 결정합니다.

━━━━━━━━━━━━━━━━━━━━━━
4. Native 강제 차단
━━━━━━━━━━━━━━━━━━━━━━

조건:

currentNativeVersion < min_version

이면:

Modal/Alert는:

- 취소 불가
- backdrop로 닫기 불가
- Android back button으로 닫기 불가
- 앱 메인 UI 접근 불가
- 다른 route 이동 불가

버튼:

"업데이트"

하나만 제공.

탭:

iOS → App Store
Android → Google Play

Store 이동 후 앱으로 다시 돌아왔는데
아직 구버전이면
다시 강제 Modal 상태여야 합니다.

즉 사용자가 우회할 수 없어야 합니다.

━━━━━━━━━━━━━━━━━━━━━━
5. latest_version과 min_version 역할
━━━━━━━━━━━━━━━━━━━━━━

정책 명확히 분리:

latest_version:

선택 업데이트 안내에 사용할 수 있음.

min_version:

강제 사용 차단 기준.

SWIMNOTE의 새 Store Build를
강제 업데이트로 전환할 때는:

해당 버전이 실제 Store에서 다운로드 가능함을 확인
→ min_version을 신규 버전으로 올림.

Store 공개 전에 min_version을 올리면 안 됩니다.

이 원칙을 코드 주석 또는 운영 문서에 명확히 기록합니다.

━━━━━━━━━━━━━━━━━━━━━━
6. OTA 자동 검사 — 필수
━━━━━━━━━━━━━━━━━━━━━━

같은 Native runtimeVersion에서
새 Production OTA가 있으면
사용자가 업데이트 확인 버튼을 누르지 않아도
앱이 자동 감지해야 합니다.

특히 parent_account는
수동 업데이트 확인 버튼이 없으므로
자동 검사 필수.

Expo Updates 현재 SDK에 맞는 공식 경로를 사용:

checkForUpdateAsync()
→ isAvailable 확인
→ fetchUpdateAsync()
→ 적용 준비 완료
→ 재시작 안내
→ reloadAsync()

현재 구현이 있다면 재사용하고
중복 시스템을 새로 만들지 않습니다.

━━━━━━━━━━━━━━━━━━━━━━
7. OTA 검사 시점
━━━━━━━━━━━━━━━━━━━━━━

최소:

앱 cold start 시 자동 검사.

그리고 앱이 장시간 background에 있었다가
foreground로 돌아오는 경우도 검토합니다.

단:

매 화면 이동
매 렌더
짧은 주기 polling

금지.

불필요한 EAS Update 호출을 만들지 않습니다.

권장:

- cold start 1회
- 필요하면 foreground 복귀 시 적절한 throttle

정확한 기존 구조를 보고 최소 변경합니다.

━━━━━━━━━━━━━━━━━━━━━━
8. OTA 재시작 Modal
━━━━━━━━━━━━━━━━━━━━━━

OTA가 다운로드 완료되면
사용자가 새 코드를 실제 적용하도록 안내합니다.

문구 예:

"새로운 업데이트가 준비되었습니다.
업데이트 적용을 위해 앱을 다시 시작합니다."

버튼:

"다시 시작"

사용자가 누르면:

Updates.reloadAsync()

OTA가 다운로드만 되고
구버전 JS를 계속 사용하는 상태가 오래 지속되지 않도록 합니다.

━━━━━━━━━━━━━━━━━━━━━━
9. OTA Modal 강제 수준
━━━━━━━━━━━━━━━━━━━━━━

SWIMNOTE 운영 정책상 OTA도
최신 코드 적용을 확실하게 해야 합니다.

따라서 OTA 다운로드 완료 후에는
재시작 Modal을 쉽게 무시하고 계속 사용하는 구조를 피합니다.

가능하면:

- 취소 버튼 없음
- 다시 시작 버튼만 제공

으로 설계합니다.

단 reload 실패 시
앱이 무한 차단되는 구조는 금지.

reload 실패:
→ 오류 안내
→ 다시 시도 가능

정도로 안전장치를 둡니다.

━━━━━━━━━━━━━━━━━━━━━━
10. Native Gate가 OTA보다 우선
━━━━━━━━━━━━━━━━━━━━━━

앱 시작 시 우선순위:

1. Native Store version 강제 업데이트 여부 확인
2. Native version 정상
3. OTA update 확인
4. 앱 정상 진입

구버전 Native binary가 이미 강제 업데이트 대상이면
OTA를 다운로드해서 살리려고 하지 않습니다.

Store 업데이트가 먼저입니다.

━━━━━━━━━━━━━━━━━━━━━━
11. Development 환경 보호
━━━━━━━━━━━━━━━━━━━━━━

Expo Go / __DEV__에서는
Production 강제 업데이트 로직 때문에
개발이 막히지 않아야 합니다.

현재 DEV guard 유지 여부 확인.

단 Production Build에서는
반드시 활성화.

TestFlight/Preview 환경에서
어떤 정책을 사용할지도 현재 channel/runtime 구조 기준으로 명확히 보고합니다.

━━━━━━━━━━━━━━━━━━━━━━
12. 네트워크 오류
━━━━━━━━━━━━━━━━━━━━━━

Version API 또는 OTA check가
일시적으로 실패했다고 앱 전체를 차단하면 안 됩니다.

구분:

"서버가 명시적으로 current < min_version이라고 판정"
→ 강제 차단

"네트워크 자체 실패"
→ 기존 앱 사용 가능
→ 다음 실행/foreground에서 재시도

Fail-open을 기본으로 하되,
확정된 min_version 위반은 fail-closed.

━━━━━━━━━━━━━━━━━━━━━━
13. 중복 Modal 방지
━━━━━━━━━━━━━━━━━━━━━━

다음 Modal이 동시에 뜨면 안 됩니다.

- Native 강제 업데이트
- Native 선택 업데이트
- OTA 재시작
- 기타 시작 Modal

우선순위 관리 필요:

Native force update
>
OTA restart
>
soft update

동일 Modal 중복 표시도 금지.

useRef/state lock 등을 사용해
앱 start effect 중복에도 한 번만 표시.

━━━━━━━━━━━━━━━━━━━━━━
14. 학부모 특별 검증
━━━━━━━━━━━━━━━━━━━━━━

parent_account에서 반드시 검증:

- 업데이트 확인 버튼 없어도 작동
- 로그인 상태에서도 자동 작동
- 로그아웃 상태/앱 최초 실행에서도 가능한 범위에서 작동
- parent home까지 진입해야만 검사되는 구조 금지
- 새로운 OTA를 수동 버튼 없이 자동 감지
- Native 구버전은 앱 사용 불가

━━━━━━━━━━━━━━━━━━━━━━
15. Teacher / Admin 검증
━━━━━━━━━━━━━━━━━━━━━━

teacher / pool_admin도
동일한 root 정책 적용.

설정 화면의 수동 업데이트 버튼이 남아 있더라도
그것은 보조 기능일 뿐.

자동 검사가 본체입니다.

━━━━━━━━━━━━━━━━━━━━━━
16. 배포 운영 원칙 문서화
━━━━━━━━━━━━━━━━━━━━━━

향후 배포자가 헷갈리지 않도록
repository에 짧은 UPDATE_POLICY.md 또는
기존 배포 운영문서가 있다면 그곳에 기록합니다.

핵심:

[NATIVE BUILD RELEASE]

1. Store Build 생성
2. Store 업로드
3. Store 실제 공개/다운로드 확인
4. app-version latest/min 업데이트
5. 강제 update 활성화

[OTA RELEASE]

1. 같은 runtimeVersion 확인
2. production OTA 배포
3. 앱 자동 check
4. OTA download
5. restart modal
6. reload 적용

중요:

Native update에 OTA restart를 사용하지 않는다.
OTA update에 Store update modal을 사용하지 않는다.

18. 테스트 CASE
━━━━━━━━━━━━━━━━━━━━━━

Native 1.6.1

→ 강제 업데이트

Native 1.6.2

→ 앱 정상 사용

CASE 6
OTA check network fail
→ 앱 정상 사용

→ OTA 처리하지 않음

학부모 계정
→ 수동 버튼 없이 Native/OTA 자동 처리

teacher
→ 동일

CASE 10
pool_admin
→ 동일

CASE 11
App foreground 복귀
→ throttle 정책대로 OTA check
→ 중복 Modal 없음

CASE 12
reloadAsync 실패
