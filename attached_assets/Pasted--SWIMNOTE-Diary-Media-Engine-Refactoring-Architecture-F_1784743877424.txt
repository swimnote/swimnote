# SWIMNOTE Diary Media Engine Refactoring (Architecture First)

이번 작업은 버그 수정이 목적이 아닙니다.

현재 조사 결과를 기준으로 Diary Engine의 Media 구조를 재설계하여
앞으로 사진 업로드, 일지 작성, 학부모 조회, 개인앨범, 관리자 기능까지
하나의 구조로 통합합니다.

목표는

"안정성"
"응답속도"
"확장성"

입니다.

==========================================
최우선 목표
==========================================

1.
사진은 절대로 중복 조회되지 않는다.

2.
삭제된 일지 사진은 절대로 다시 나타나지 않는다.

3.
Teacher와 Parent가 같은 Media Engine을 사용한다.

4.
업로드 후 거의 즉시 화면에 반영된다.

5.
일지 작성 중에도 UI는 절대 멈추지 않는다.

6.
사진 수가 수천~수만 장이 되어도 응답속도를 유지한다.

==========================================
Media Engine 설계 원칙
==========================================

photo_assets_meta를

사진의 단일 Source of Truth

로 만든다.

모든 사진은

photo_assets_meta

기준으로만 관리한다.

다른 테이블에서
사진 URL
journal_id
student_id
등을 따로 관리하지 않는다.

==========================================
Media Service
==========================================

사진 조회는

MediaService

하나에서 처리한다.

예)

getDiaryPhotos()

getStudentPhotos()

attachDiaryPhotos()

attachStudentPhotos()

deleteDiaryPhotos()

restorePhotos()

모든 API는

MediaService

만 호출한다.

직접 SQL을 작성하지 않는다.
