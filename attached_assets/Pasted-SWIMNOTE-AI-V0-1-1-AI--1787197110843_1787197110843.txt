SWIMNOTE 학부모 AI 커리큘럼 검색
초기 모델 설계도 V0.1
1. 기능 정의

AI 커리큘럼 검색은 단순한 수영 질문 챗봇이 아니다.

학부모가 자연어로 자기 아이의 수영 진행상황을 질문하면,

실제 학생 수업기록 + SWIMNOTE 커리큘럼 + SWIMNOTE 수영 전문 DB

를 검색·판정한 뒤 GPT가 학부모가 이해하기 쉬운 자연어로 설명하는 학생별 근거 기반 대화형 커리큘럼 검색 시스템이다.

핵심 질문은 다음과 같은 것들이다.

우리 아이 지금 어디까지 배웠어요?
자유형 어디까지 했어요?
평영 시작했어요?
요즘 뭘 배우고 있어요?
다음에는 뭘 배우나요?
자유형 호흡은 아직인가요?
접영은 어느 정도예요?
최근에 어떤 부분이 좋아졌어요?
지금 단계에서 중요한 게 뭐예요?
왜 이걸 계속 연습하는 거예요?
빨간모자까지 뭐가 남았어요?
2. 앱 진입 구조 — 새 버튼 만들지 않음

새로운 홈 버튼을 추가하지 않는다.

현재 학부모 화면에 이미 존재하는:

커리큘럼 검색 버튼

을 그대로 사용한다.

흐름:

학부모 홈
   ↓
기존 "커리큘럼 검색" 버튼 탭
   ↓
AI 커리큘럼 검색 화면

기존 버튼의 위치·디자인은 유지한다.

버튼의 onPress/navigation만 새 커리큘럼 검색 화면으로 연결한다.

즉 이번 개발에서 학부모 홈 UI를 다시 설계하거나 버튼을 하나 더 만들지 않는다.

3. 커리큘럼 검색 UI 기본 철학

UI/UX는 사용자가 이미 익숙한 ChatGPT형 대화 인터페이스와 최대한 비슷한 사용감으로 만든다.

단, OpenAI 로고나 ChatGPT 고유 그래픽을 복제하는 것이 아니라:

대화가 아래로 계속 이어지는 구조
사용자 질문 버블
AI 답변
하단 고정 입력창
전송 버튼
답변 복사
대화 히스토리
자동 스크롤
긴 답변 자연스러운 스크롤

같은 익숙한 챗 인터페이스 패턴을 적용한다.

SWIMNOTE 브랜드 컬러와 기존 앱 디자인은 유지한다.

7. 사용자 질문 표시

사용자가 질문하면 오른쪽 또는 기존 SWIMNOTE 디자인에 맞는 질문 영역으로 표시.

예:

우리 아이 자유형 어디까지 했어요?

그 아래 AI가 답변.

대화는 계속 아래로 누적한다.

8. AI 답변 구조

답변은 지나치게 보고서처럼 만들지 않는다.

ChatGPT처럼 자연스러운 설명형 답변이 기본이다.

예:

현재 자유형에서는 팔동작과 호흡 연결을 중심으로 연습하고 있습니다. 최근 수업 기록에서는 자유형 킥과 팔동작이 반복적으로 확인됐고, 호흡 타이밍을 연결하는 과정도 시작된 것으로 확인됩니다.

자유형에서 호흡은 단순히 고개를 돌리는 동작보다 몸통 회전과 팔동작의 타이밍을 맞추는 것이 중요합니다. 현재 과정이 안정되면 SWIMNOTE 커리큘럼상 전체 자유형 동작을 자연스럽게 연결하는 단계로 이어집니다.

즉 답변 안에:

현재 상황 + 실제 기록 + 수영 전문 설명 + 다음 과정

이 자연스럽게 섞여야 한다.

10. 대화 연속성

이 기능은 매 질문을 독립 검색으로 만들면 안 된다.

예:

학부모:

자유형 어디까지 했어요?

AI 답변 후:

학부모:

그럼 다음에는 뭐 배워?

라고 해도 시스템이 그럼이 무엇을 뜻하는지 알아야 한다.

따라서 conversation context를 유지한다.

conversation
student
previous question
previous answer
current curriculum context
current evidence

를 연결한다.

다만 GPT에게 과거 대화를 무제한으로 계속 보내는 것은 피한다.

대화가 길어지면:

최근 N turn
conversation summary
현재 학생 progress context

정도만 사용한다.

11. 대화 히스토리

GPT와 비슷한 느낌을 만들려면 검색 기록이 유지돼야 한다.

학부모가 다시 들어와도 이전 질문을 볼 수 있게 한다.

예:

AI 커리큘럼 검색
────────────────


오늘
우리 아이 자유형 어디까지 했어요?
왜 호흡을 계속 연습하나요?


어제
평영은 시작했나요?

다만 초기 버전에서는 별도 사이드바까지 만들 필요는 없다.

현재 대화방을 계속 유지하거나 상단 메뉴에서 이전 대화를 볼 수 있는 정도로 시작 가능하다.

12. 새 대화

상단에 작은:

새 대화

기능을 둔다.

새 대화를 누르면 기존 기록을 삭제하는 것이 아니라 새 conversation_id를 생성한다.

기존 대화는 히스토리에 남는다.

13. 학생 컨텍스트 보안

학부모가 질문을 보냈다고 해서 client가 보낸 student_id를 그대로 신뢰하면 안 된다.

서버에서 매번:

parent_account
      ↓
parent_students relation
      ↓
student
      ↓
pool

권한 확인.

학부모는 자기 자녀 데이터만 검색할 수 있다.

다른 학생 기록이나 같은 반 다른 아이 데이터는 검색 대상에서 완전히 제외한다.

16. 학생 Evidence 검색

진도를 판단하는 가장 중요한 레이어.

사용 가능한 실제 학생 기록에서 찾는다.

예:

영법/기술 기록

여기서 교사 내부 메모와 학부모 공개 데이터는 반드시 구분한다.

17. 시간 가중치

최근 기록을 더 중요하게 본다.

예:

최근 30일      → 강한 근거
31~90일       → 보조 근거
90일 이상     → 과거 이력

단순히 최신 기록 하나만 보고 완료 여부를 뒤집으면 안 된다.

학생 기록과 별도로 SWIMNOTE 공식 커리큘럼에서 해당 기술 위치를 가져온다.

예:

↓

↓

↓

GPT가 자기 일반 지식으로 순서를 결정하면 안 된다.

19. Progress Resolver

학생의 실제 evidence와 curriculum을 합쳐 내부 상태를 만든다.

기본 상태:

COMPLETED
IN_PROGRESS
REVIEW
NOT_CONFIRMED
NEXT

예:

자유형 킥        COMPLETED
자유형 팔동작    COMPLETED
자유형 호흡      IN_PROGRESS
자유형 연결      NEXT

이 판정은 GPT가 하지 않는다.

서버/검색 엔진이 계산한다.

20. Evidence 등급

SWIMNOTE AI 전체 원칙과 맞춰 내부적으로 구분한다.

DIRECT
실제 수업 기록에서 직접 확인


TRACKED
반복된 기록/진행상태로 확인


INFERRED
SWIMNOTE 커리큘럼 순서에 따른 다음 단계


UNKNOWN
근거 부족

GPT에는 이 상태를 함께 넘긴다.

21. 수영 전문 DB의 역할

커리큘럼 검색 답변이 뻔하지 않게 만드는 핵심.

단, 전문 DB는 진도 판정에 쓰지 않는다.

진도 판정:

학생 기록 + 커리큘럼

전문 설명:

SWIMNOTE 수영 전문 DB

예를 들어 학생이 자유형 호흡 중이라면 전문 DB에서:

호흡의 기술적 의미
몸통 롤링
머리 위치
흔한 오류
왜 이 단계를 연습하는지
다음 단계와 어떤 관계인지

등 필요한 자료 몇 개만 검색한다.

그 결과를 GPT가 자연스럽게 답변에 섞는다.

현재 progress

출력 규칙

GPT가 별도로 학생 진도를 창작하면 안 된다.

23. GPT 답변 규칙

반드시 지켜야 한다.

실제 확인된 내용
→ 확정 표현 가능

커리큘럼상 예상되는 내용
→ “커리큘럼상 다음 단계는…”

기록이 부족한 내용
→ “현재 확인 가능한 기록에서는…”

→ 단정 금지

예:

금지:

허용:

24. DIRECT_DB / GROUNDED_GPT / HUMAN_ONLY

모든 질문에 GPT를 쓸 필요 없다.

DIRECT_DB

예:

현재 레벨이 뭐예요?

최근 수업일이 언제예요?

DB에서 명확하면 바로 답한다.

GROUNDED_GPT

예:

우리 아이 지금 어디까지 왔어요?

왜 이걸 계속 배우는 거예요?

근거를 모아서 GPT가 설명한다.

HUMAN_ONLY

예:

왜 우리 아이 진급을 안 시켜줘요?

다음주 레벨업 가능해요?

교사 판단이 필요한 질문은 AI가 확정하지 않는다.

25. 생성 중 UI

질문을 보내면 ChatGPT처럼 답변 위치에:

답변을 확인하고 있습니다...

또는 자연스러운 typing indicator를 표시한다.

너무 긴 로딩 모달로 화면 전체를 막지 않는다.

커리큘럼 검색은 비교적 가벼운 AI 요청이므로 우선 동기 응답을 목표로 한다.

나중에 서버 사용량이 많아져 처리시간이 길어지면 AI Job Queue 시스템과 연결 가능하다.

29. Evidence Snapshot이 중요한 이유

예를 들어 8월 20일에:

자유형 호흡 진행 중입니다.

라고 답했는데 한 달 뒤 학생 진도가 달라질 수 있다.

따라서 당시 AI가 어떤 기록을 보고 답했는지 snapshot을 남기면:

답변 재현
오류 조사
성장리포트
AI 검증
고객 문의

에 사용할 수 있다.

30. Student Progress Summary

성능 때문에 질문할 때마다 일지 수백 개를 전부 읽으면 안 된다.

장기적으로:

student_progress_summary

같은 계산 결과를 유지한다.

예:

{
  "backstroke": {
    "kick": "completed",
    "arms": "completed"
  },
  "freestyle": {
    "kick": "completed",
    "arms": "completed",
    "breathing": "in_progress"
  }
}

수업 기록이 변경될 때만 summary를 갱신.

검색할 때는 summary를 우선 읽고 필요한 evidence만 추가 조회한다.

31. 캐시

변경이 적은 데이터는 캐시한다.

curriculum tree
level structure
skill relation
next-step map
전문 DB 공통 노드

학생 개인 데이터는 짧은 TTL 또는 변경 이벤트 기반 캐시.

32. 목표 응답 속도

커리큘럼 검색은 학부모가 ChatGPT처럼 쓰는 기능이기 때문에 체감 속도가 중요하다.

구조 목표:

학생 summary 조회
+
curriculum cache
+
필요 evidence 조회
+
전문 DB 검색
+
GPT 1회

불필요하게 API가 5~10개 순차 호출되는 구조를 만들면 안 된다.

가능하면 앱에서는:

POST /parent/curriculum-ai/respond

같은 단일 진입 API 하나만 호출하고, 내부 서버가 필요한 데이터를 조합한다.

33. UI에서 보여주지 않을 것

사용자에게 다음은 숨긴다.

confidence 숫자
DB node ID
evidence JSON
intent 이름
검색 score
prompt
token
모델명
내부 엔진 정보

학부모는 깔끔한 자연어 답변만 보면 된다.

필요하면 답변 하단에 작게:

최근 수업 기록 및 SWIMNOTE 커리큘럼 기준

정도만 표시한다.

34. 향후 성장리포트와 연결

이 시스템은 나중에 성장리포트와 별개로 또 만들면 안 된다.

커리큘럼 검색에서 생성되는:

student progress
evidence
최근 변화
현재 단계
다음 단계

를 성장리포트도 재사용해야 한다.

즉 학생 Progress Engine은 하나이고,

커리큘럼 검색은 그것을 대화형으로 보여주는 기능,

성장리포트는 일정 기간 데이터를 분석해서 리포트로 보여주는 기능이 되는 게 이상적이다.

35. V1 초기 범위

처음부터 모든 질문을 해결하려고 하지 않는다.

V1에서는 우선:

현재 진도
특정 영법 진도
특정 기술 여부
최근 수업
다음 단계
현재 레벨
레벨까지 남은 과정
현재 배우는 기술 설명

을 안정적으로 처리한다.

교사 평가/진급 시점/개인적인 판단 질문은 HUMAN_ONLY.

36. 구현 전에 리플릿에게 확인받아야 할 사항

이 설계도 그대로 코딩시키기 전에 기존 앱에서 이미 가지고 있는 구조를 최대한 재사용할 수 있는지 확인해야 한다.

특히 확인 대상은:

기존 학부모 커리큘럼 검색 버튼의 screen/navigation 위치
현재 student progress 관련 테이블
기존 curriculum 테이블/템플릿 구조
diary와 curriculum의 연결 정보
parent_students 권한 구조
기존 parent AI 관련 API/화면 흔적
대화 history용 기존 테이블 존재 여부
현재 AI 엔진에 curriculum 검색 endpoint가 이미 있는지
전문 수영 DB 검색 API를 어떻게 호출하는지
앱 DB와 AI DB 사이 데이터 전달 방식
성장리포트용 progress 계산 코드 중 재사용 가능한 부분
신규 DB schema가 실제로 필요한지
최종 사용자 경험

학부모 입장에서는 아주 단순해야 해.

학부모 홈


[커리큘럼 검색]
       ↓


┌──────────────────────────┐
│ AI 커리큘럼 검색          │
│ 태웅 ▼                    │
│                          │
│          우리 아이       │
│   자유형 어디까지 했어요? │
│                          │
│ 현재 자유형에서는...      │
│ 최근 수업 기록에서는...   │
│ 다음 단계는...            │
│                          │
│  [복사]                  │
│                          │
│ ─────────────────────── │
│ 우리 아이 진도를 물어보세요 │
│                    [↑]   │
└──────────────────────────┘

사용자는 ChatGPT 쓰듯 질문만 하면 되고, 뒤에서는 SWIMNOTE가 자기 아이의 실제 데이터를 찾아서 답하는 구조야.

이 초기 모델의 핵심 정의

겉은 ChatGPT처럼 간단하게.
속은 SWIMNOTE 데이터와 커리큘럼으로 엄격하게.

그리고 이번 구현에서 절대 놓치면 안 되는 세 가지는:

① 기존 학부모 커리큘럼 검색 버튼을 그대로 진입점으로 사용
② ChatGPT형 대화 UI + 답변 복사 기능
③ GPT가 진도를 추측하지 않고 학생 실제 기록과 SWIMNOTE 커리큘럼으로 먼저 판정

이 V0.1을 먼저 리플릿에 보내서 “현재 코드/DB 기준 구현 가능 여부 + 재사용 가능한 기존 구성 + 추가 필요한 구성”만 확인받은 뒤, 그 결과를 내가 보고 V0.2 최종 구현 설계로 정리하면 돼.
