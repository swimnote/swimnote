==================================================
3. TRANSACTION / COMPENSATION
==================================================

가능하면 APP DB의:

- assistant message persistence
- quota RESERVED → COMPLETED
- reserved_count -1
- completed_count +1

을 하나의 DB transaction으로 묶는다.

가장 안전한 canonical 결과:

BEGIN

1. assistant message INSERT/UPSERT
2. reservation RESERVED → COMPLETED
3. usage reserved_count -1
4. usage completed_count +1

COMMIT

하나라도 실패:
ROLLBACK

ENGINE 외부 HTTP 호출 자체는
DB transaction 안에서 오래 잡지 않는다.

즉:

quota RESERVED
→ ENGINE call
→ validation
→ short DB success-finalization transaction

형태가 되어야 함.

==================================================
6. FAILURE BEHAVIOR
==================================================

ENGINE 성공 후
assistant persistence 또는 quota-finalization DB 작업이 실패하면:

HTTP 성공 반환 금지.

reservation/usage는
transaction rollback 결과와 일치해야 함.

필요 시 reservation은 RESERVED 상태로 남아서
동일 request_id 재시도가 가능해야 한다.

또는 기존 canonical recovery policy가 있으면
그 방식 사용.

절대:

COMPLETED + no persisted result

상태를 만들지 않는다.

==================================================
7. COMPLETED REPLAY INVARIANT
==================================================

COMPLETED reservation이라면 반드시:

동일 request_id의 persisted ASSISTANT result가
존재해야 한다.

코드상 이 invariant가 보장되는지 확인.

COMPLETED인데 assistant result가 없을 경우
정상 replay 성공으로 위장하지 않는다.

typed integrity error 또는 recovery path 사용.
