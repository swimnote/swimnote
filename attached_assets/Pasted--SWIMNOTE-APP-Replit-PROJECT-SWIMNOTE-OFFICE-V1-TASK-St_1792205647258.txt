2. 원래 계획 유지

필수 지침·고정계획서·Stage 2 보완 문서를 참조한다.
원래 Stage 3의 명칭·범위·완료 조건을 확인하여 이번 작업에 연결한다.

아래 실행 항목은 이번 후속 지시의 구체화이며,
원래 계획서의 인용문이나 기존 Task 번호로 꾸미지 않는다.

이번 목표:
기존 메뉴와 향후 AI가 같은 업무 호출 경로를 사용하도록,
기존 조회·화면 열기 기능의 공통 Action 기반을 구현한다.

현재 가능한 승인 범위는 문서 조사만으로 끝내지 말고 구현한다.
원래 계획과 실제 충돌하는 부분만 분리해 근거를 보고한다.
새로운 제품 로드맵이나 별도 대형 프레임워크는 만들지 않는다.

3. 공통 Action의 첫 연결 범위

기존 구현을 우선 재사용:
- 홈 열기.
- 회원목록 열기.
- 회원 ID로 상세 열기.
- 기존 허용 범위의 회원 검색·필터 조회.

메뉴·홈 바로가기·결과 이동이 같은 Action 경로를 사용한다.
기존 N01 Navigation·API client·QueryClient·인증·Pool 검증 재사용.
데이터 저장소·인증 상태·업무 조회를 중복 구현하지 않는다.

화면 열기와 데이터 조회를 구분한다.
화면 OPEN 성공을 업무 변경 완료로 표현하지 않는다.

Action마다 필요한 최소 계약:
- 안정적인 식별자와 용도.
- 입력 형식·검증.
- 현재 사용자/Pool 및 필요한 권한.
- 조회/화면 이동/변경 등 실행 종류.
- 확인 필요 여부.
- 성공·실패·취소·결과 불명 구분.
- 결과 화면 목적지와 관련 query 갱신 기준.

현재 실행 가능한 Action만 등록한다.
결제·발송·회원 수정 등을 가짜 실행기로 등록하지 않는다.
임의 URL/API/SQL 실행을 받는 범용 Action 금지.
사용자·Pool은 모델이나 입력 payload가 임의 지정하지 못하게 한다.
서버 권한 검증을 클라이언트 Action 검사로 대체하지 않는다.

4. AI 매니저와 연결할 경계

실제 AI가 연결되기 전에도 공통 Action을 시험할 수 있도록
격리 fixture에서 다음 흐름을 검증한다.

검증된 구조화 요청
→ 입력·scope·권한 조건 검사
→ 기존 조회/OPEN 호출
→ 작업 카드 결과
→ 결과 보기
→ 정상 조회 증거에 따른 결과 열람

자연어를 단순 키워드로 흉내 내 AI가 연결된 것처럼 만들지 않는다.
실제 제품의 전송 차단·미연결 표시는 유지한다.
테스트용 실행 버튼이나 가짜 작업을 운영 UI에 남기지 않는다.

기존 완료 상태와 결과 열람 계약을 재사용한다.
조회 성공·화면 이동·변경 성공의 의미를 혼합하지 않는다.
현재 없는 revision이나 변경 성공 증거를 만들어내지 않는다.
