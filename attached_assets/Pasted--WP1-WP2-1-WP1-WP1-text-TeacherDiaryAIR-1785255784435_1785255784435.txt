# WP1 검토 결과 및 WP2 작업 승인

## 1. WP1 검토 결과

WP1은 조건부 통과합니다.

확인된 사항:

```text
TeacherDiaryAIRequest 타입 추가 완료
request_id 생성 완료
crypto.randomUUID 우선 사용 완료
fallback 구현 완료
자동 재시도 시 동일 request_id 유지
사용자 재생성 시 새 request_id 생성
context.students[{ref,name}] 추가
기존 student_refs 병행 유지
기존 Diary Save 미변경
Whisper·Voice Recorder 미변경
```

WP1 범위는 적절하게 지켜졌습니다.

---

# 2. WP1에서 확인된 보완 사항

## 2.1 pool_id

현재 Session에서 `swimming_pool_id`가 optional이며, 없는 경우 빈 문자열이 전송됩니다.

이번 WP2에서는 pool_id 정책을 변경하지 않습니다.

다만 다음 원칙을 유지합니다.

```text
임의의 pool_id 생성 금지
class_id를 pool_id로 대체 금지
사용자 ID를 pool_id로 대체 금지
```

AI Engine의 빈 `pool_id` 허용 여부는 WP4 통합 테스트에서 확인합니다.

---

## 2.2 기존 TypeScript 오류

보고된 기존 TypeScript 오류 6건은 이번 작업과 무관한 것으로 인정합니다.

단, WP2 작업 후:

```text
useDiaryAI.ts에서 새로 발생한 오류가 0건인지
기존 오류 개수가 증가하지 않았는지
```

반드시 다시 확인합니다.

---

# 3. WP2 작업 승인 범위

이번에는 아래 작업만 수행합니다.

```text
1. Response Contract 타입 정의
2. 표준·구형 응답 필드 처리 수정
3. request_id 검증
4. 반환 학생 ref 검증
5. 중복 학생 ref 차단
6. 일부 학생 누락 허용
7. 전체 검증 후 Draft 원자적 반영
8. 잘못된 응답 시 기존 Draft 보존
```

WP3 범위인 로그 정리는 아직 수행하지 않습니다.

---

# 4. 중요: 현재 응답 필드 조합 수정

WP0·WP1 보고서에 따르면 현재 코드는 다음 조합을 처리하는 것으로 보입니다.

```text
student_ref + feedback
student_id + content
```

이 조합은 최종 Contract와 다릅니다.

최종 표준은 다음입니다.

## 표준 응답

```json
{
  "student_ref": "student_001",
  "content": "학생별 일지 내용"
}
```

## 임시 구형 응답

```json
{
  "student_id": "student_001",
  "feedback": "학생별 일지 내용"
}
```

처리 우선순위는 반드시 다음과 같아야 합니다.

```ts
const studentRef =
  item.student_ref ??
  item.student_id;

const content =
  item.content ??
  item.feedback;
```

금지:

```text
student_ref가 있으면 feedback만 사용
student_id가 있으면 content만 사용
필드 존재 여부에 따라 교차 조합 강제
```

표준 필드가 있으면 표준 필드를 우선합니다.

# 5. Response 타입

현재 파일 구조에 맞게 중복 없이 정의합니다.

권장 형태:

```ts
interface TeacherDiaryAIStudentResult {
  student_ref?: string;
  student_id?: string;
  content?: string;
  feedback?: string;
}

interface TeacherDiaryAIResponse {
  request_id?: string;
  schema_version?: string;
  result?: {
    common?: string;
    students?: TeacherDiaryAIStudentResult[];
  };
  usage?: {
    input_tokens?: number;
    output_tokens?: number;
    total_tokens?: number;
  };
}
```

외부 응답은 신뢰할 수 없으므로 처음부터 모든 필드를 required로 단언하지 않습니다.

실제 Runtime Validation을 거쳐 내부의 정상화된 타입으로 변환합니다.

권장 내부 타입:

```ts
interface NormalizedDiaryStudentResult {
  studentRef: string;
  content: string;
}

interface NormalizedDiaryResult {
  common: string;
  students: NormalizedDiaryStudentResult[];
}
```

---

# 6. 응답 처리 순서

반드시 아래 순서로 처리합니다.

```text
HTTP 응답 수신
↓
JSON 파싱
↓
Response 기본 구조 검증
↓
request_id 검증
↓
common 타입 검증
↓
students 배열 검증
↓
각 학생 필드 정상화
↓
학생 ref 유효성 검증
↓
중복 student_ref 검사
↓
전체 검증 성공
↓
한 번에 Draft 반영
```

응답 검증 도중 `setResultText()` 또는 `generatedStudentsRef.current`를 먼저 변경하면 안 됩니다.

---

# 7. 원자적 Draft 반영

응답 전체를 임시 지역 변수에 먼저 구성합니다.

예시 방향:

```ts
const normalizedResult = normalizeDiaryResponse({
  response: data,
  expectedRequestId,
  validStudentRefs,
});

// 여기까지 성공한 경우에만 실제 State 변경
generatedStudentsRef.current = normalizedResult.students;
setResultText(normalizedResult.common);
machine.receiveResult();
```

검증 도중 오류가 발생하면:

```text
공통 Draft 변경 금지
학생별 Draft 변경 금지
기존 수동 입력 변경 금지
기존 generatedStudentsRef 덮어쓰기 금지
```

즉, 일부 학생 결과만 적용되는 상태가 생기면 안 됩니다.

---

# 8. request_id 검증

## 8.1 일치

```text
response.request_id === currentRequestIdRef.current
```

이면 정상 처리합니다.

## 8.2 불일치

다르면:

```text
응답 전체 폐기
Draft 미적용
ERROR 상태 처리
request_id mismatch 오류 코드 기록
```

## 8.3 request_id 누락

현재 AI Engine 전환 기간을 고려해 임시 호환 정책을 구현합니다.

권장:

```ts
const ALLOW_LEGACY_RESPONSE_WITHOUT_REQUEST_ID = true;
```

정책:

```text
response.request_id 존재
→ 반드시 현재 요청 ID와 일치해야 함

response.request_id 없음
+ 임시 호환 Flag true
→ 구형 응답으로 처리 가능

response.request_id 없음
+ 임시 호환 Flag false
→ Contract 오류
```

이 Flag는 한 위치에서만 정의하고 쉽게 제거할 수 있어야 합니다.

AI Engine이 request_id 반환을 확정하면 false로 변경하거나 제거합니다.

누락된 request_id를 앱이 임의로 현재 request_id로 채워 넣으면 안 됩니다.

---

# 9. 학생 ref 검증

유효 학생 목록은 요청에 사용한 학생 목록을 기준으로 합니다.

```ts
const validStudentRefs = new Set(
  options.students.map((student) => student.id)
);
```

응답의 학생 ref가 이 목록에 없으면:

```text
해당 결과만 무시하고 계속 진행하지 않음
응답 전체를 Contract 오류로 처리
Draft 전체 미적용
```

이유:

잘못된 학생에게 일지가 연결되는 사고는 부분 무시보다 전체 차단이 안전합니다.

---

# 10. 중복 student_ref 처리

같은 학생이 응답에 두 번 이상 등장하면 오류로 처리합니다.

예:

```json
[
  {
    "student_ref": "student_001",
    "content": "내용 1"
  },
  {
    "student_ref": "student_001",
    "content": "내용 2"
  }
]
```

현재 코드처럼 문장을 자동 결합하지 않습니다.

```text
중복 발견
→ 응답 전체 폐기
→ Draft 미적용
→ Contract 오류
```

학생별 문장 결합은 AI Engine Output Validator 책임입니다.

앱이 임의로 문장을 합치면 안 됩니다.

---

# 11. 필드 정상화 규칙

각 학생 결과는 다음 순서로 정상화합니다.

```ts
const studentRef =
  typeof item.student_ref === 'string' && item.student_ref
    ? item.student_ref
    : typeof item.student_id === 'string' && item.student_id
      ? item.student_id
      : null;

const content =
  typeof item.content === 'string'
    ? item.content
    : typeof item.feedback === 'string'
      ? item.feedback
      : null;
```

유의사항:

```text
student_ref와 student_id가 둘 다 있으면 student_ref 우선
content와 feedback이 둘 다 있으면 content 우선
student ref가 없으면 오류
content가 문자열이 아니면 오류
```

내용의 앞뒤 공백 제거는 허용합니다.

내용을 재작성하거나 문장 의미를 변경하면 안 됩니다.

---

# 12. 일부 학생 누락 정책

응답에 모든 학생이 포함될 필요는 없습니다.

예:

```text
요청 학생 5명
AI 응답 학생 2명
```

이 경우 정상 응답으로 처리할 수 있습니다.

적용 정책:

```text
응답에 있는 2명만 AI Draft 후보로 보관
응답에 없는 3명의 기존 수동 입력은 유지
누락 학생을 빈 문자열로 생성하지 않음
누락 학생에게 공통 내용을 복사하지 않음
```

다만 응답 학생이 0명이고 공통 내용도 비어 있으면 Contract 오류로 처리합니다.

---

# 13. common 처리

`result.common`은 문자열이어야 합니다.

허용:

```text
문자열
빈 문자열
```

학생별 내용이 존재한다면 common이 빈 문자열인 응답은 허용합니다.

다음 조건이면 오류입니다.

```text
common이 빈 문자열
그리고
students도 비어 있음
```

`null`, 객체, 배열 등의 값은 오류로 처리합니다.

---

# 14. 기존 Draft 보존

AI 응답 검증 실패 시:

```text
현재 화면의 공통 입력 유지
현재 화면의 학생별 입력 유지
이전에 적용된 AI 결과 유지
사용자가 작성한 수동 내용 유지
```

잘못된 응답 때문에 빈 값으로 초기화하면 안 됩니다.

---

# 15. 오래된 응답 차단

AbortController가 이미 있지만 request_id 검증을 추가합니다.

검증 기준:

```text
요청에 사용한 expectedRequestId
현재 currentRequestIdRef.current
응답 response.request_id
```

다음 중 하나라도 명확하게 불일치하면 응답을 적용하지 않습니다.

```text
응답 ID와 요청 ID 불일치
응답 도착 시 현재 활성 ID가 다른 요청 ID
이미 새 요청이 시작된 상태
```

임시 Legacy 응답처럼 response.request_id가 없는 경우에도:

```text
expectedRequestId === currentRequestIdRef.current
```

인지 확인한 뒤에만 적용합니다.

---

# 16. 오류 상태 처리

Contract 오류는 네트워크 재시도 대상이 아닙니다.

예:

```text
request_id mismatch
알 수 없는 student_ref
중복 student_ref
잘못된 result 구조
학생 content 타입 오류
```

이 경우 자동 재시도를 하지 않습니다.

자동 재시도는 기존 정책대로 네트워크·Timeout·일시적 서버 오류에만 사용합니다.

# 17. WP2 수정 금지

이번 WP에서는 다음을 수정하지 않습니다.

```text
[GENERATE-REQ] 학생 이름 로그
[GENERATE-RESP] 전체 응답 로그
[GENERATE-STUDENT-RAW] 로그
Authorization Header
Whisper
Voice Recorder
State Machine 구조
Diary Save
DiaryWriteView
Curriculum
Template
Knowledge
AI Engine
Production 배포
```

로그 개인정보 제거는 WP3에서 수행합니다.

단, WP2에서 새 로그를 추가해야 한다면 다음 정보만 허용합니다.

```text
request_id
오류 코드
학생 결과 개수
HTTP Status
```

학생 이름과 응답 내용은 출력하지 않습니다.
