WP3-1B DESIGN RECONCILIATION 승인.

이번 WP3의 범위는:

1. pool_admin이 X 커리큘럼 설정을 요청
2. NOT_CONFIGURED → CURRICULUM_PENDING
3. 요청 상태 확인
4. 앱에서 "준비 중" 표시

까지다.

커리큘럼 실제 구축/편집 기능은 구현하지 않는다.
pool_admin READY 강제 전환 금지.

1. 서버 POST /pools/x-request
━━━━━━━━━━━━━━━━━━━━

artifacts/api-server/src/routes/pools.ts

2. POST 사전조건
━━━━━━━━━━━━━━━━━━━━

Transaction 시작 전/내에서 확인:

A.
pool 존재

B.
xmode_entitlement = true

false이면:
403
X entitlement 없음

C.
xmode_config_status 확인

READY:
새 요청 생성 금지.
이미 X 설정 완료 상태.

CURRICULUM_PENDING:
중복 요청 생성 금지.
현재 진행 중 요청 반환 또는 conflict 처리.

NOT_CONFIGURED:
요청 생성 가능.

━━━━━━━━━━━━━━━━━━━━
3. 중복 요청 방지
━━━━━━━━━━━━━━━━━━━━

같은 pool에서 다음 상태의 요청이 이미 있으면
새 curriculum_requests row 생성 금지:

pending
reviewing

현재 DB에 unique constraint가 없다면
이번 WP에서 임의 migration 만들지 말 것.

Transaction + SELECT FOR UPDATE 등
기존 DB 구조 안에서 가능한 안전한 방식 사용.

동시 요청에도 중복이 생기지 않는지 검토.

DB migration이 정말 필요하다고 판단되면
구현 중단하고 보고.

━━━━━━━━━━━━━━━━━━━━
4. curriculum_requests INSERT
━━━━━━━━━━━━━━━━━━━━

시스템 기본값으로 생성할지는
기존 UI 최소화 원칙을 따른다.

이번 WP에서는 별도 복잡한 요청폼 금지.

권장 최소:

title = "SWIMNOTE X 커리큘럼 설정 요청"

description = null 또는 선택 입력

단 현재 schema/API 스타일에 맞춰 구현.

5. config_status 전환
━━━━━━━━━━━━━━━━━━━━

같은 Transaction 안에서:

INSERT curriculum_requests

성공 후

UPDATE swimming_pools
SET xmode_config_status = 'CURRICULUM_PENDING'

WHERE id = authenticated poolId
AND xmode_entitlement = true
AND xmode_config_status = 'NOT_CONFIGURED'

둘 중 하나만 성공하는 상태 금지.

요청 생성 + status 변경 원자성 보장.

표시:
"커리큘럼 설정 요청이 접수되었습니다."

request_status에 따라:

pending
→ 요청 접수

reviewing
→ 커리큘럼 준비 중

rejected
→ 반려 안내 + review_note 표시

주의:
xmode_config_status가 CURRICULUM_PENDING인데
request가 rejected/cancelled 상태라면
현재 설계상 config_status 복귀 경로가 없을 수 있다.

이 불일치가 발견되면 임의 처리하지 말고 보고.
