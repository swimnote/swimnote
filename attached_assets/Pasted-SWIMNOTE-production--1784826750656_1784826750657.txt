SWIMNOTE 긴급 복구 작업 — 댓글·반응·추가 보호자 기능 실제 동작 완료 전 완료 보고 금지

현재 실제 production 앱에서 핵심 기능들이 계속 죽어 있습니다.

첨부한 실제 기기 화면 기준으로 확인된 문제:

1. 학부모 댓글 전송 실패
   - “전송에 실패했습니다” 오류가 계속 발생
   - 선생님 화면에 댓글이 넘어오지 않음

2. 좋아요·감사합니다 미연동
   - 학부모 화면에서 눌린 것처럼 보여도 선생님 화면은 0명
   - DB 저장 여부 확인되지 않음
   - 감사합니다는 한동안 클릭 자체도 동작하지 않았음

3. 추가 보호자 관리 화면 미완성
   - 현재 화면에는 안내 문구만 있음
   - 추가 보호자 이름 입력칸 없음
   - 전화번호 입력칸 없음
   - 저장 버튼 없음
   - 등록된 보호자 목록 없음
   - 수정·삭제 기능 없음
   - 따라서 실제 기능은 구현되지 않은 상태

이 문제들 때문에 다른 작업을 전혀 진행하지 못하고 있습니다.

이번 작업에서는 계획, 파일 생성, 라우트 존재, 401 응답만으로 절대 완료 보고하지 마세요.

실제 production 앱에서 모든 기능이 정상 동작하고,
production DB에 데이터가 저장되고,
반대편 사용자 화면에 반영되는 것까지 확인하기 전에는
“완료”, “정상 작동”, “검증 완료”라는 표현을 사용하지 마세요.

==================================================
A. 작업 원칙
==================================================

1. 한 번에 여러 기능을 완료했다고 주장하지 마세요.

2. 다음 순서로 하나씩 실제 production에서 통과시키세요.

   1) 댓글
   2) 좋아요
   3) 감사합니다
   4) 선생님 반응·댓글 조회
   5) 추가 보호자 입력 UI
   6) 추가 보호자 저장
   7) 관리자 전산 반영
   8) 추가 보호자 자동 연결

3. 각 기능은 다음 네 단계가 모두 확인돼야 통과입니다.

   앱 요청
   → Production API 200/201
   → Production DB row 생성
   → 상대방 앱 화면 반영

4. 라우트가 401을 반환하는 것은 기능 정상 증거가 아닙니다.

5. 로컬 서버나 preview에서만 성공한 것도 완료가 아닙니다.

6. 실제 production 앱과 Render production 서버 및 production DB를 기준으로만 검증하세요.

==================================================
B. 댓글 전송 실패부터 먼저 해결
==================================================

현재 학부모 댓글 전송은 계속 실패합니다.

실제 학부모 계정으로 댓글을 전송하고
오류 원문을 수집하세요.

클라이언트 필수 로그:

[PARENT COMMENT SUBMIT]
apiHost=
endpoint=
diaryId=
studentId=
tokenExists=
bodyLength=

[PARENT COMMENT RESPONSE]
httpStatus=
responseBody=

[PARENT COMMENT ERROR]
errorMessage=
stack=

서버 필수 로그:

[COMMENT CREATE START]
deploymentVersion=
userId=
role=
diaryId=
studentId=

[COMMENT CREATE ERROR]
httpStatus=
dbCode=
constraint=
column=
query=
error=
stack=

다음 전체 경로를 확인하세요.

- production 앱의 실제 API host
- Authorization 헤더
- diaryId
- studentId
- parent_students 연결
- diary 공개 권한
- diary_messages 실제 스키마
- student_id 컬럼
- parent_comment_id 컬럼
- message_type 컬럼
- 기존 NOT NULL 컬럼
- 댓글 INSERT
- INSERT 이후 알림 및 후처리

댓글 INSERT 성공 후 알림 실패 때문에 500이 되는 경우:

1. 댓글 저장 및 commit
2. 201 응답
3. 알림은 별도 try/catch

구조로 분리하세요.

부가 알림 실패를 댓글 전송 실패로 반환하지 마세요.

댓글 완료 기준:

- 학부모 댓글 POST 201
- Production DB comment row 생성
- 학부모 화면에 작성 댓글 표시
- 선생님 반응·댓글 화면에 같은 댓글 표시
- 앱 재실행 후 유지

이 다섯 가지 전에는 댓글 완료 보고 금지.

C. 좋아요·감사합니다 실제 저장
==================================================

좋아요와 감사합니다 반응 타입을 전 코드에서 통일하세요.

허용값:

like
thanks

다음 혼용을 전수 검색:

thank
thanks
gratitude
appreciation

프론트 요청, API 검증, DB 값, 집계 SQL 모두 일치해야 합니다.

학부모가 버튼을 누를 때:

[PARENT REACTION REQUEST]
apiHost=
diaryId=
studentId=
reactionType=
tokenExists=

서버 응답:

[REACTION RESPONSE]
httpStatus=
active=
reactionId=
likeCount=
thankCount=

실패 시 optimistic UI를 즉시 원래 상태로 롤백하세요.

버튼만 선택된 것처럼 보이고 DB 저장이 안 되는 상태는 금지합니다.

Production DB에서 실제 확인:

SELECT *
FROM diary_reactions
WHERE diary_id = :testedDiaryId
ORDER BY created_at DESC;

좋아요 완료 기준:

- POST 200
- reaction_type='like' DB row
- 학부모 선택 상태 유지
- 선생님 화면 좋아요 1명

감사합니다 완료 기준:

- POST 200
- reaction_type='thanks' DB row
- 학부모 선택 상태 유지
- 선생님 화면 감사합니다 1명

==================================================
D. 선생님 반응·댓글 조회
==================================================

학부모가 반응이나 댓글을 남긴 동일 diaryId를
선생님 화면이 조회하는지 확인하세요.

필수 비교:

학부모 diaryId=
좋아요 DB diary_id=
감사합니다 DB diary_id=
댓글 DB diary_id=
선생님 화면 diaryId=

모두 정확히 동일해야 합니다.

선생님 화면 API의 실제 production 응답:

{
  "likeCount": 1,
  "thankCount": 1,
  "commentCount": 1,
  "likes": [...],
  "thanks": [...],
  "comments": [...]
}

를 제출하세요.

DB에는 row가 있는데 선생님 화면이 0이면
조회 SQL이나 필드 매핑 문제입니다.

DB에도 row가 없다면
학부모 POST 문제입니다.

두 문제를 혼동하지 마세요.

선생님 화면 완료 기준:

- 좋아요 작성자 표시
- 감사합니다 작성자 표시
- 댓글 작성자 및 학생명 표시
- 선생님 답글 작성 가능
- 학부모에게 답글 표시

F. 추가 보호자 저장 로직
==================================================

새 학생을 생성하지 마세요.

기존 student_id의 빈 슬롯에 순서대로 저장하세요.

- parent_phone2
- parent_phone3
- parent_phone4

이름도 함께 저장하세요.

필요한 컬럼:

- parent_name2
- parent_name3
- parent_name4

관계를 저장한다면:

- parent_relation2
- parent_relation3
- parent_relation4

전화번호는 동일한 정규화 함수를 사용하세요.

010-1234-5678
01012345678
+82 10-1234-5678

이 모두 같은 번호로 비교돼야 합니다.

저장 완료 기준:

- 앱 POST/PATCH 200
- students row에 실제 전화번호 저장
- 화면 재진입 후 값 유지
- 관리자 전산에 동일 값 표시

==================================================
G. 추가 보호자 자동 연결
==================================================

추가 보호자 번호를 저장할 때:

1. 해당 번호의 기존 가입 계정이 있으면 즉시 연결
2. 가입 계정이 없으면 번호만 대기 저장
3. 나중에 해당 번호로 가입·인증하면 자동 연결

자동 연결 시:

- 새 student row 생성 금지
- 기존 student_id에 parent_students row만 추가
- 동일 학생·사용자 중복 연결 금지

응답 예:

이미 가입한 번호:

{
  "saved": true,
  "autoLinked": true,
  "linkedParentId": "..."
}

미가입 번호:

{
  "saved": true,
  "autoLinked": false,
  "status": "pending"
}

관리자 화면에는:

- 이름
- 전화번호
- 가입 대기 / 연결 완료
- 연결된 parent account

가 보여야 합니다.

I. 절대 금지 사항
==================================================

다음 상태에서 완료 보고 금지:

- 파일만 생성함
- 라우터만 등록함
- migration 코드만 작성함
- 401 응답만 확인함
- 로컬 서버에서만 성공함
- DB row를 확인하지 않음
- 상대방 화면 반영을 확인하지 않음
- 입력 화면에 안내문만 있음
- 버튼만 눌린 것처럼 보임
- 실제 production 앱 테스트를 하지 않음

“정상 작동할 것입니다”
“배포됐으니 확인해 보세요”
“엔드포인트가 등록됐습니다”

라는 표현으로 완료 처리하지 마세요.
