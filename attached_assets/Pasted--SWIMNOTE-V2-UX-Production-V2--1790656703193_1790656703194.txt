[SWIMNOTE 공지사항 V2 — 실기기 발견 문제 수정 + 게시일시 UX + 이미지 크롭]

Production 실기기 확인에서 공지사항 V2의 추가 문제가 발견됐다.

현재 Production 기준:
- DB/API/iOS/Android 배포 완료
- 실제 미리보기 화면 확인 완료
- 공지 등록 버튼이 활성화되지 않아 최종 등록 불가
- 노출 시작일시 입력 UX 개선 필요
- 이미지 표시 영역에 맞춰 사용자가 잘리는 부분을 조절할 수 있어야 함

이번 작업은 아래 3개를 해결한다.

1. 공지 등록 버튼 비활성화 버그
2. 노출 시작일시를 날짜/시간 선택 방식으로 개선
3. 공지 이미지 크롭/위치 조절 기능

AI ENGINE 작업 아님.

1. 공지 등록 버튼 버그 — 최우선
━━━━━━━━━━━━━━━━━━━━━━

첨부된 실제 Production 화면에서:

- 미리보기 정상 진입
- 제목/내용 존재
- 발송 대상 존재
- 노출 시작일시 존재
- 하단 "공지 등록" 버튼이 disabled 상태

이다.

추측해서 고치지 말고 실제 disabled 조건부터 추적한다.

확인 대상:

- canSave
- saving
- uploading
- submittingRef
- OTP 관련 상태
- step === "preview"
- 이미지 upload 상태
- title/content validation
- target_roles
- starts_at validation
- deep_link/link_label validation
- 기타 disabled 조건

특히 미리보기 단계에서
최종 등록 버튼이 어떤 조건으로 disabled 되는지 정확히 찾는다.

정상적인 공지라면:

미리보기
→ 공지 등록 버튼 활성
→ 탭
→ 기존 보안/OTP 절차
→ 필요 시 이미지 R2 upload
→ POST /notices
→ 성공

이 되어야 한다.

버튼을 억지로 항상 enabled 처리하지 말고
잘못된 validation/state dependency를 수정한다.

등록 진행 중에만 중복 제출 방지를 위해 disabled 처리한다.

2. 노출 시작일시 UX 개선
━━━━━━━━━━━━━━━━━━━━━━

현재처럼

2026-09-29T18:03

같은 ISO 문자열을 사용자가 직접 입력하게 하지 않는다.

공지 작성 화면에서는 사람이 이해하기 쉬운
날짜 + 시간 선택 UI를 제공한다.

예:

노출 시작

[ 2026년 9월 29일 ]  [ 오후 1:40 ]

또는 모바일에 적합한 동일 수준의 picker UI.

요구사항:

- 날짜 선택
- 시간 선택
- 오전/오후 또는 24시간 표기를 사용자에게 명확히 표시
- 현재 시각을 기본값으로 사용할 수 있음
- 사용자가 원하는 미래 날짜/시간 선택 가능
- 선택 결과를 작성 화면에서 읽기 쉬운 한국식 형식으로 표시
- 미리보기에서도 동일하게 읽기 쉬운 형식으로 표시

예:
2026. 09. 29. 오후 1:40

내부 API 전송 시에는
현재 backend가 요구하는 starts_at 형식으로 정확히 변환한다.

중요:
한국 사용자가 선택한 시간을 UTC/서버시간으로 잘못 해석하여
9시간 차이가 발생하면 안 된다.

현재 starts_at DB type/API parsing/timezone 정책을 먼저 조사하고,
대한민국 로컬 시간 선택 → 서버 저장 → 다시 조회 → 실제 노출 시간이
동일한 시점을 의미하도록 구현한다.

임의로 +9/-9 보정하지 말고
현재 Date/DB/API contract를 확인해서 처리한다.

━━━━━━━━━━━━━━━━━━━━━━
3. 즉시 노출도 명확하게 지원
━━━━━━━━━━━━━━━━━━━━━━

공지 작성자가 예약 발행이 필요하지 않을 수도 있다.

노출 시작 영역을 이해하기 쉽게 구성한다.

예:

노출 시작

● 지금부터
○ 날짜/시간 지정

"지금부터":
→ backend의 기존 즉시 노출 contract에 맞게 처리

"날짜/시간 지정":
→ 날짜 picker + 시간 picker 표시

사용자가 ISO 문자열을 직접 작성할 필요가 없어야 한다.

미리보기 발행 정보도:

노출 시작: 즉시

또는

노출 시작: 2026. 09. 30. 오전 9:00

처럼 표시한다.

4. 이미지 크롭/위치 조절
━━━━━━━━━━━━━━━━━━━━━━

공지 대표 이미지를 선택했을 때
앱이 임의로 중요한 부분을 잘라버리는 방식으로 끝내지 않는다.

사용자가 최종 공지 카드에 표시될 영역을
직접 확인하고 조절할 수 있게 한다.

목표 workflow:

[이미지 선택]
↓
[크롭/위치 조절]
↓
실제 공지 이미지 비율의 crop frame 표시
↓
사용자가 이미지 이동/확대·축소
↓
[적용]
↓
공지 작성 화면
↓
[미리보기]
↓
실제 사용자 화면과 동일한 결과 확인

최소 지원:

- 이미지 이동
- 확대/축소
- 실제 최종 표시 영역 확인
- 적용
- 다시 이미지 조정 가능

사용자가 크롭을 취소하면
기존 작성 데이터가 사라지면 안 된다.

━━━━━━━━━━━━━━━━━━━━━━
5. 이미지 비율 먼저 확정
━━━━━━━━━━━━━━━━━━━━━━

NoticePopupCard의 실제 이미지 container를 확인하고
공지 대표 이미지의 canonical aspect ratio를 하나로 정한다.

크롭 화면의 frame과
실제 NoticePopupCard의 이미지 영역이
동일한 aspect ratio를 사용해야 한다.

예를 들어 실제 카드가 16:9라면:

크롭 frame = 16:9
실제 공지 image container = 16:9
미리보기 = 16:9

로 일치시킨다.

임의로 16:9라고 가정하지 말고
현재 NoticePopupCard의 실제 layout을 확인해서 결정한다.

미리보기에서 확인한 crop 결과와
실제 사용자 공지에서 보이는 crop 결과가 달라지면 안 된다.

━━━━━━━━━━━━━━━━━━━━━━
6. Native dependency Gate
━━━━━━━━━━━━━━━━━━━━━━

이미지 크롭 구현 전에 현재 프로젝트 dependency를 조사한다.

우선 확인:

- expo-image-picker의 현재 editing 기능
- 현재 설치된 image manipulation 관련 package
- 기존 앱에서 crop/edit 기능을 사용하는 화면 존재 여부
- OTA만으로 구현 가능한 기존 component/library 존재 여부

원칙:

A. 현재 설치된 dependency/기존 코드만으로
안정적인 crop/zoom/position UI 구현 가능
→ 구현

B. 새로운 native dependency가 반드시 필요
→ 임의 설치 금지
→ 크롭 부분은 HOLD
→ 필요한 package와 binary rebuild 필요 여부를 보고

공지 등록 버튼 및 날짜/시간 UX는
크롭 dependency 문제 때문에 같이 멈추지 않는다.

새 native dependency를 몰래 추가해서
기존 binary와 OTA 호환성을 깨뜨리지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
7. 이미지 저장
━━━━━━━━━━━━━━━━━━━━━━

가능하면 최종 적용된 crop 결과를
local temporary file로 생성하고,

최종 "공지 등록" 시점에만
기존 R2 upload pipeline으로 업로드한다.

미리보기만 했다고 R2 upload하지 않는다.

크롭을 여러 번 수정했다고
R2 orphan 파일이 여러 개 생기지 않아야 한다.

최종 등록:
crop 결과 1개
→ 기존 압축 정책
→ presigned upload
→ R2
→ image_urls 저장

순서를 유지한다.

━━━━━━━━━━━━━━━━━━━━━━
8. 회귀 보호
━━━━━━━━━━━━━━━━━━━━━━

기존 완료된 기능을 깨뜨리지 않는다.

반드시 유지:

- 작성 → 미리보기 → 수정 → 등록
- 미리보기에서는 DB write 없음
- 미리보기에서는 seen 없음
- 실제 Modal onShow 이후 seen
- 사용자별 1회 자동 노출
- 학부모 대상
- 관리자+선생님 대상
- 전체 대상
- 링크/CTA
- 이미지 실패 fail-safe
- role/pool authorization
- 중복 등록 방지
- 등록 실패 시 작성 데이터 유지
