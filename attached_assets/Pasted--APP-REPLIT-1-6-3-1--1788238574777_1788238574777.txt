# 긴급 수정 — 1.6.3 포함 학생목록 로딩 장애 점검

현재 운영/테스트에서 아래 장애 제보가 있습니다.

## 증상 1
선생님 일지 작성 화면에서
`학생별 추가 일지` 영역이 계속

`학생 정보를 불러오는 중...`

상태에 머물고 학생 목록이 표시되지 않음.

첨부 화면 기준으로 일지 공통입력 영역은 렌더링되지만,
반 학생 목록 조회가 완료되지 않는 것으로 보임.

## 증상 2
반 배정/학생 배정 관련 화면에서도
학생 목록 조회 문제가 있을 가능성이 있으므로 같이 점검 필요.

이번 작업은
**1.6.3 운영 버전 영향 포함 긴급 장애 점검**입니다.

---

# 목표

아래를 반드시 확인하십시오.

1. 일지 작성 화면의 학생 목록 조회 API
2. 반 배정 화면의 학생 목록 조회 API
3. 두 기능이 공통으로 사용하는 서버 쿼리/권한/응답 구조
4. 1.6.3에서 정상 작동하던 계약과 현재 서버 계약 차이
5. 최근 서버 변경으로 인한 regression 여부

---

# 1. 일지 작성 학생목록 경로 추적

첨부 증상 화면의 실제 route/component부터 추적하십시오.

확인:

- 어떤 endpoint 호출하는지
- 요청 URL
- HTTP method
- query params
- class_id / schedule_id / swimming_pool_id 전달 여부
- JWT role
- teacher_id
- 현재 반 담당자 기준 필터
- loading state 종료 조건
- error state 처리
- empty array 처리

특히 UI가 무한히

`학생 정보를 불러오는 중...`

에 머무는 조건을 찾으십시오.

반드시 다음을 구분하십시오.

- API 요청 자체가 안 나감
- API 4xx
- API 5xx
- 응답은 왔으나 parsing 실패
- response shape mismatch
- students가 null/undefined
- loading flag reset 누락

# 2. 실제 서버 endpoint 확인

일지 작성에서 사용하는 학생목록 endpoint의
서버 route/service를 직접 추적하십시오.

확인:

- route
- controller
- service/query
- DB table
- join
- WHERE 조건
- status filter
- class assignment filter
- tenant filter

특히 아래 상태값이 최근 변경되었는지 확인하십시오.

- active
- normal
- pending
- withdrawn
- resigned
- delayed
- current class assignment

기존 정상 회원이 필터에서 전부 빠지는 조건이 있는지 확인하십시오.

# 3. 반 배정 학생목록도 별도 점검

반 배정 화면에서 학생을 선택하거나 배정할 때 사용하는
학생목록 조회 경로를 전수 확인하십시오.

반드시 확인:

- 전체 회원 목록
- 미배정 회원 목록
- 기존 반 배정 회원 목록
- 반 변경 시 조회
- 검색 결과
- pagination/limit
- active status filter

일지 작성과 동일 API를 공유하면
공통 장애 여부 확인.

다른 API면 각각 독립적으로 테스트하십시오.

---

# 4. 1.6.3 계약 비교

현재 서버와
**1.6.3 앱이 기대하는 response shape**
를 비교하십시오.

예:

기존:

{
  students: [
    { id, name }
  ]
}

현재:

{
  data: {
    students: [...]
  }
}

또는

studentId

vs

id

같은 계약 변경 여부 확인.

최근 아래 변경 영향 특히 확인:

- students[{id,name}] 계약
- teacher diary 학생 전달 구조
- 반 담당자 권한 변경
- parent/student request 작업
- membership/status 변경
- class assignment query 변경
- 멀티테넌트 swimming_pool_id 조건

# 5. 서버 로그 확인

가능한 read-only 범위에서
최근 장애 요청 로그 확인.

찾아야 할 것:

- endpoint
- status code
- error message
- SQL error
- unauthorized
- forbidden
- invalid UUID
- undefined class id
- relation/join failure
- timeout

개인정보 출력 금지.

학생 이름/전화번호 등은 마스킹하십시오.

# 7. 원인 확정 후 최소 수정

원인이 확인되면
**최소 범위 수정만 수행**하십시오.

금지:

- 대규모 refactor
- 학생/반 구조 변경
- DB schema 변경
- migration
- 권한정책 재설계
- unrelated code 수정

가능하면 기존 1.6.3 계약을 깨지 않는
**backward-compatible fix**
로 처리하십시오.

최우선 목표:

> 1.6.3 앱이 현재 production API를 그대로 호출해도
> 정상 학생목록이 나오게 할 것.

# 8. 로딩 무한대 방어

서버 문제와 별개로
앱에서도 무한 로딩이 가능한지 확인하십시오.

현재처럼 실패했는데 계속

필요하면 최소 수정:
