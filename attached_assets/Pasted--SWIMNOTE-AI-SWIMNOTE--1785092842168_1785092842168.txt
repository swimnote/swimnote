# SWIMNOTE 앱 — AI 일지 구조 개선 사전 설계 조사 요청

이번 요청은 구현 작업이 아닙니다.

현재 실제 SWIMNOTE 앱 코드베이스를 직접 조사한 뒤,
AI 일지 기능의 다음 작업을 어떻게 진행해야 하는지
구체적인 설계 보고서만 작성해주세요.

==================================================
현재 개발 원칙
==================================================

SWIMNOTE 개발은 항상 다음 순서를 지킵니다.

1. 실제 코드 조사
2. Replit 설계 보고서 제출
3. 사용자와 설계 검토
4. 수정 범위 확정
5. 한 단계만 구현
6. 실제 Production 실행 검증
7. 스크린샷 제출
8. 다음 단계 승인

코드 수정만으로 완료 처리하지 않습니다.

현재 Production에서 정상 동작하는 기능은
절대 깨뜨리면 안 됩니다.

기존 구조를 유지하면서
필요한 기능만 독립적으로 추가해야 합니다.

==================================================
AI Engine 현재 상태
==================================================

SWIMNOTE AI Engine 측 점검 결과:

준비된 항목:

- Knowledge 검색
- 하이브리드 검색
- 벡터 + 키워드 검색
- RRF
- Prompt Engine
- 할루시네이션 방지
- LLM 호출
- 재시도
- Circuit Breaker
- 토큰 사용량 수집
- Production 배포 구조

아직 준비 중인 항목:

- Teacher Diary 전용 API
- 구조화 JSON 프롬프트
- 앱 사용자 JWT 인증
- request_id API 연동
- 표준 오류 코드
- AI request log

따라서 앱은 현재 실제 엔진과 연결하지 않고
Dummy AI 기반 구조를 먼저 완성할 예정입니다.

향후 목표 구조:

DiaryContextBuilder
→ DiaryAIProvider
→ SwimNoteDiaryAIProvider
→ Teacher Diary API
→ DiaryAIValidator
→ DiaryAIParser
→ DiaryApplyAdapter
→ 기존 일지 state
→ 기존 저장 버튼

AI는 직접 저장하지 않습니다.

AI 결과는 기존 화면 state에만 적용하고,
저장은 반드시 기존 저장 로직을 그대로 사용합니다.

==================================================
현재 알려진 앱 구조
==================================================

기존 조사 결과상 현재 구조는 다음과 같습니다.

BaseAIModal
→ AIContext.Provider
→ DiaryAIContent
→ useDiaryAI
→ generateDiary
→ 더미 string 결과
→ onInsert(text)

기존 일지 구조:

공통 일지:
- commonContent
- editContent

학생별 일지:
- studentNotes
- editNotes
- editNewNotes

기존 저장 흐름은 이미 공통 일지와 학생별 일지를 지원합니다.

절대 수정하지 않을 대상:

- handleSave
- handleEditSave
- 기존 Diary API
- 기존 저장 흐름
- POST /diaries
- PUT /diaries/:id
- DELETE /diaries/student-notes/:id

학생 ID 타입은 기존 코드 기준으로 string입니다.

AI 요청에는 학생 이름을 보내지 않고,
student_id 또는 student_refs만 전송하는 방향입니다.
