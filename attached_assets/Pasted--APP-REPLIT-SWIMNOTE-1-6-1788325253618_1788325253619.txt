2. CLIENT LOGIN TRACE
============================================================

현재:

SessionContext.unifiedLogin()

을 크게 바꾸지 말고
최소 diagnostic trace 추가 여부를 검토.

로그인 시 생성:

login_request_id

예:
login_<uuid>

서버에 가능하면 header 전달:

X-Request-Id: login_<uuid>

기존 request-id convention이 있으면 그것 재사용.

4. CLIENT ERROR CATEGORY
============================================================

현재 fetch throw를 모두 network_error로 묶는 구조를
진단 관점에서 세분화할 수 있는지 조사.

최소 내부 diagnostic category:

ABORT_TIMEOUT
FETCH_NETWORK_ERROR
HTTP_4XX
HTTP_5XX
INVALID_JSON
INVALID_RESPONSE
AUTH_ERROR
POST_LOGIN_ERROR

사용자에게 보여주는 기존 문구는
이번 작업에서 바꾸지 않아도 됨.

중요:
진단 코드만 세분화.

이 둘을 반드시 분리.

============================================================
7. SERVER BOOT ID
============================================================

서버 프로세스 시작 때:

boot_id = random UUID

boot_started_at
process pid if safe
git commit SHA if environment provides
service version

를 1회 로그.

각 health/auth diagnostic log에
boot_id를 포함할 수 있으면 포함.

목적:

장애 전후 boot_id가 바뀌면
process restart/deploy를 즉시 확인.

============================================================
8. SERVER UPTIME
============================================================

Health endpoint 또는 내부 로그에서:

process.uptime()

확인 가능하게.

예:

GET /api/healthz

response에 기존 contract를 깨지 않는 additive metadata로
아래를 넣을 수 있는지 검토:

{
  ok: true,
  uptime_seconds: ...,
  boot_id: ...,
  version: ...
}

단 보안상 노출 부적절한 값은 제외.

기존 1.6.3 parser에 영향 없는 additive only.

9. DEPLOY / RESTART 판별
============================================================

서버 startup log에:

SERVER_BOOT
boot_id
started_at
commit/version

남김.

다음 장애 발생 시:

장애시각 직전/직후 SERVER_BOOT 존재
→ restart/deploy 가능성 매우 높음.

boot_id 유지
+ login request 자체 미도달
→ client/DNS/TLS/network 가능성.

10. LOGIN REQUEST REACHABILITY 판별
============================================================

ABC 로그 없음

→ HTTP 요청이 server route까지 도달하지 않음.

후보:
DNS/TLS/TCP/Render edge/device network.

SERVER:
ABC 수신

→ network connection 자체는 성공.

그 다음 status/elapsed 기준으로
server/auth 문제 판별.

18. 장애 발생 시 판정표 작성
============================================================

완료보고에 아래 decision matrix를 반드시 작성.

예:

CLIENT timeout + SERVER request 없음
→ network/render edge/server unavailable

CLIENT fetch throw + SERVER request 없음
→ DNS/TLS/TCP/device network

SERVER request 있음 + 500
→ backend

SERVER request 있음 + 401
→ auth/account

SERVER request 있음 + long latency
→ server/DB latency

boot_id changed around incident
→ restart/deploy

boot_id unchanged + no server request
→ network path

HTTP 200 + client parse fail
→ client contract/parser

AUTH success + post-login fail
→ RevenueCat/subscription/post-login
