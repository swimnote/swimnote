최종 승인 및 처리 기준

아래 기준으로 작업을 진행하세요.

이번 작업은 날짜 시스템을 통일하는 작업이며,
기존 화면과 기존 기능을 새로 만들거나 변경하는 작업이 아닙니다.

작업 범위에 포함된 날짜 처리 로직과
반 배정 모달의 첫 수업일 선택 기능만 수정합니다.

==================================================

1. 기존 suspended / withdrawn 데이터 마이그레이션

먼저 실제 데이터의 건수와 날짜 복원 가능 여부를 확인하세요.

다음 순서로 처리합니다.

① withdrawn 회원

withdrawn_at이 존재하고
기존 student_class_history의 left_at이 NULL인 경우에는

left_at = withdrawn_at

으로 보정합니다.

left_at은 제외 시작일이라는 방식 B 기준을 사용합니다.

예)

withdrawn_at = 2026-08-01

→ 7/31까지 표시

→ 8/1부터 미표시

이미 left_at이 있는 데이터는 변경하지 않습니다.

② suspended 회원

left_at이 NULL인 suspended 회원은
임의로 오늘 날짜를 입력하지 않습니다.

다음 자료에서 실제 연기 시작일을 복원할 수 있는지 먼저 확인합니다.

- 상태 변경 기록
- 수정 로그
- 예약 적용 날짜
- archived 또는 effective 관련 데이터
- 기존 일정 및 출결 기록
- 기타 날짜를 확인할 수 있는 DB 기록

실제 연기 시작일을 확인할 수 있는 회원만
해당 날짜를 left_at으로 보정합니다.

실제 연기 시작일을 확인할 수 없는 회원은
추측해서 수정하지 않습니다.

해당 회원의 수와 식별 가능한 목록을 먼저 보고하세요.

날짜를 확인하지 못한 suspended 회원이 남아 있다면
현재 상태값을 다시 전체 날짜 필터로 사용하는 임시 처리는 하지 않습니다.

과거 기록을 훼손할 수 있기 때문입니다.

날짜가 확인되지 않은 회원을 어떻게 수동 보정할지
별도로 보고한 후 처리합니다.

③ 마이그레이션 안전 원칙

- 실행 전 DB 백업
- 변경 대상 건수 기록
- 변경 전 값 기록
- 변경 후 값 기록
- 이미 left_at이 있는 데이터는 덮어쓰지 않음
- 자동 추측 금지
- 기존 일지, 출결, 사진 데이터 삭제 금지

서버 운영 배포 전에
기존 suspended/withdrawn 데이터가 새로운 날짜 조회 조건에서
현재 스케줄에 잘못 나타나지 않는 상태인지 확인해야 합니다.

==================================================

2. 연기 후 복귀 처리 방식

연기 후 복귀할 때마다 관리자가 반을 다시 배정해야 하는 현재 방식은 사용하지 않습니다.

연기는 퇴원이나 미배정이 아니라
기존 반에서 일정 기간 수업을 쉬는 상태입니다.

따라서 복귀 시 기존 반으로 자동 복귀하도록 처리합니다.

처리 방식:

연기 시작일

→ 기존 student_class_history의 left_at을 연기 시작일로 설정

연기 기간

→ 어느 정규 수업에도 표시하지 않음

복귀일

→ 연기 전 마지막으로 소속되었던 반을 기준으로
새 student_class_history row 생성

새 row:

- student_id = 기존 회원
- class_group_id = 연기 전 마지막 반
- enrolled_at = 복귀일
- left_at = NULL
- swimming_pool_id = 동일 수영장

예)

기존 A반

8/1부터 연기

8/15 복귀

기존 history:

A반 enrolled_at = 기존 첫 수업일
A반 left_at = 2026-08-01

신규 history:

A반 enrolled_at = 2026-08-15
A반 left_at = NULL

결과:

- 7/31까지 A반 표시
- 8/1~8/14 미표시
- 8/15부터 A반 다시 표시

복귀와 동시에 다른 반으로 이동시키는 경우에는
자동으로 이전 반을 생성하지 않고
선택한 새 반으로 history row를 생성합니다.

복귀일은 실제 적용 날짜를 사용해야 하며,
단순히 API를 실행한 오늘 날짜를 무조건 사용하면 안 됩니다.

기존 복귀 화면이나 상태 변경 과정에
복귀 적용일을 선택하는 기능이 이미 있다면 그 값을 사용하고,
없다면 날짜 시스템에 필요한 최소 범위에서 복귀일을 받을 수 있도록 처리합니다.

다만 기존 모달 크기, 스크롤, 버튼 위치, 탭, 글자, 레이아웃은 변경하지 않습니다.

3. 통합 날짜 기준 최종 확정

student_class_history의 left_at은

‘마지막 참여일’이 아니라
‘제외가 시작되는 날짜’

로 통일합니다.

전체 공통 조건:

h.enrolled_at <= 수업날짜

AND

(h.left_at IS NULL OR h.left_at > 수업날짜)

현재 students.status의 suspended 또는 withdrawn 값은
과거 날짜의 회원 포함 여부를 판단하는 조건으로 사용하지 않습니다.

완전 삭제 데이터만

s.deleted_at IS NULL

조건으로 제외합니다.

이 날짜 기준을 다음 기능에 동일하게 적용합니다.

- 일간 스케줄
- 주간 스케줄
- 월간 스케줄
- 출결
- 일지 작성 대상
- 학부모 일지
- 반 이동
- 미배정
- 연기
- 복귀
- 퇴원

기능마다 다른 비교식을 만들지 않습니다.

가능하면 공통 날짜 판정 함수 또는 공통 쿼리 구조로 묶어
모든 기능이 같은 기준을 사용하도록 구현합니다.

==================================================

4. 기존 enrolled_at 데이터

기존 회원의 enrolled_at은
실제 첫 수업일을 확실하게 확인할 수 없는 경우 자동 수정하지 않습니다.

신규 반 배정부터는

등록일과 첫 수업일을 분리하고

student_class_history.enrolled_at에는
관리자가 선택한 첫 수업일을 저장합니다.

기존 enrolled_at 수동 수정 화면은
이번 작업 범위에 추가하지 않습니다.

기존 데이터 수정 기능이 필요하면 추후 별도 작업으로 진행합니다.

5. 배포 순서

기능별로 날짜 기준이 다른 중간 상태를 만들지 마세요.

다음 순서로 진행합니다.

1. 기존 suspended/withdrawn 데이터 사전 점검
2. 안전하게 복원 가능한 데이터 마이그레이션 준비
3. 서버 코드 전체 수정
4. 로컬 및 테스트 환경에서 통합 테스트
5. DB 백업
6. 승인된 데이터 마이그레이션 실행
7. 서버 변경 사항 Render.com 한 번에 배포
8. 앱 첫 수업일 선택 기능 최소 수정
9. OTA 배포
10. 실제 앱 전체 검증

today-schedule, attendance, diary, parent 등을
각각 따로 운영 서버에 배포하여
날짜 기준이 일시적으로 달라지는 상태를 만들지 않습니다.

6. 기존 UI 및 기능 보호

이번 작업에서는 다음 항목을 임의로 변경하지 않습니다.

- 기존 기능
- 모달 크기
- 모달 위치
- 모달 내부 레이아웃
- 모달 스크롤
- 화면 스크롤 방식
- 탭 구조
- 탭 글자
- 글자 줄바꿈
- 글자 깨짐
- 폰트 크기
- 버튼 위치
- 버튼 크기
- 아이콘
- 색상
- 여백
- 화면 전환
- 기존 권한
- 기존 UX
- 날짜 시스템과 관계없는 컴포넌트

코드 정리나 리팩토링을 이유로
기존 화면 또는 정상 작동 중인 기능을 변경하지 않습니다.

허용되는 화면 수정은 다음과 같습니다.

- 반 배정 모달에 첫 수업일 선택 기능 추가
- 복귀일 입력이 기존 구조에 전혀 없다면 날짜 입력 기능 최소 추가

이 경우에도 기존 모달의 크기, 스크롤, 버튼 위치, 탭 및 전체 레이아웃을 그대로 유지합니다.

화면 변경이 불가피하다면
임의로 수정하지 말고 수정 전에 대상과 이유를 보고하세요.
