1. 최종 운영 정책
━━━━━━━━━━━━━━━━━━━━━━

매월 1일 자동 시작.

각 pool + report_month별 최종 발급대상을 확정한 뒤
전체 대상의 1차 분석을 진행한다.

원칙:

1. 한 회원 실패가 다른 회원 처리를 중단시키지 않는다.
2. 한 수영장 실패가 다른 수영장 처리를 중단시키지 않는다.
3. 성공한 report는 즉시 보존한다.
4. 성공한 report는 recovery 과정에서 다시 분석하지 않는다.
5. 1차 실패 건만 별도로 누적한다.
6. 실패했다고 즉시 같은 건을 무한 retry하지 않는다.
7. 전체 1차 처리는 계속 진행한다.
8. 1차 종료 후 실패 건을 집계한다.
9. 실패가 있으면 슈퍼관리자에게 PUSH로 보고한다.
10. 원인 확인/수정 후 실패 건만 recovery한다.
11. recovery에서도 기존 성공 건은 건드리지 않는다.
12. 각 pool은 다른 pool과 독립적으로 READY가 될 수 있다.
13. 해당 pool의 최종 발급조건 대상이 100% 정상 귀결되면 READY.
14. READY가 되면 해당 수영장 관리자에게 자동 PUSH.
15. 관리자 PUSH는 pool + report_month 기준 정확히 1회.
16. 슈퍼관리자가 정상 pool의 발행을 일일이 승인하지 않는다.
17. 슈퍼관리자는 실패/미완료 예외만 관리한다.

━━━━━━━━━━━━━━━━━━━━━━
2. 1차 완료 후 슈퍼관리자 실패 보고
━━━━━━━━━━━━━━━━━━━━━━

1차 전체 processing이 끝난 뒤
미완료가 존재하면 슈퍼관리자에게 집계 PUSH가 필요하다.

예:

[AI 성장리포트 1차 발행 결과]

전체 487개 수영장
발급대상 146,210명
정상완료 146,178명

미완료:
18개 수영장 / 32명

주요 원인:
Provider 오류 17
UNKNOWN 8
데이터 처리 오류 7

정상 완료된 리포트는 보존되었습니다.
미완료 건의 원인 확인 및 재실행이 필요합니다.

실제 구현에서는 PII나 AI 원문을 PUSH에 포함하지 않는다.

동일 cycle/동일 단계에 대한 중복 PUSH 방지가 필요하다.

실패 건별 상세 원인은
기존 super-admin API/화면 또는 최소한의 조회 가능한 구조에서
확인할 수 있어야 한다.

계획서에서는 현재 기존 기능으로 가능한 부분과
추가가 필요한 부분을 구분할 것.

━━━━━━━━━━━━━━━━━━━━━━
3. Recovery
━━━━━━━━━━━━━━━━━━━━━━

슈퍼관리자가 원인을 확인/수정한 뒤
미완료 건만 recovery할 수 있어야 한다.

기존 batch-recovery 경로가 안전하게 재사용 가능하면
새 recovery 시스템을 만들지 말고 기존 것을 재사용한다.

절대 금지:

- 전체 cycle 재분석
- 기존 성공 report 재분석
- denominator 축소
- 실패를 임의 exclusion으로 변경
- UNKNOWN 자동 재분석
- 새 request_id 무제한 생성
- 무한 retry

UNKNOWN은 현재 ENGINE 안전계약을 유지한다.

운영자 recovery가 필요한 경우
어떤 상태에 대해 어떤 절차로
새 분석을 명시적으로 허가해야 하는지
현재 APP/ENGINE 계약 기준으로 계획서에 정확히 기술한다.

ENGINE 코드를 수정하는 계획은 세우지 말 것.

━━━━━━━━━━━━━━━━━━━━━━
4. Pool별 자동 READY + 관리자 PUSH
━━━━━━━━━━━━━━━━━━━━━━

전체 수영장이 끝날 때까지 기다리지 않는다.

예:

A pool 300/300
→ READY
→ 관리자 PUSH

B pool 299/300
→ NOT READY
→ recovery 대상

C pool 412/412
→ READY
→ 관리자 PUSH

B의 마지막 1건이 recovery 성공하여 300/300이 되는 순간:

→ reconciliation
→ READY
→ 관리자 PUSH

관리자 PUSH 예시:

[이번 달 AI 성장리포트 발행 완료]

이번 달 회원들의 AI 성장리포트 발행이 완료되었습니다.
SWIMNOTE에서 확인해 주세요.

기존 readiness outbox/dedupe를 최대한 재사용한다.

pool + report_month 기준 중복 PUSH 금지.

━━━━━━━━━━━━━━━━━━━━━━
5. DATA_ACCUMULATING 정책 검토
━━━━━━━━━━━━━━━━━━━━━━

현재 9월 cycle에 3건 존재:

registry COMPLETE
analysis_status = DATA_ACCUMULATING

ENGINE 확인 결과:

- ENGINE 장애 아님
- 해당 snapshot/request의 정상 최종 결과
- 현재 입력에서 성장리포트를 작성할 유효 근거 부족
- 같은 입력을 반복해도 기존 결과 replay
- 추가 유효 근거 없는 재분석은 의미 없음

현재 월간 정책은
“발급조건을 충족한 대상에게 100% 성장리포트 발행”
이므로 이 3건 때문에 READY가 영구 차단되어서는 안 된다.

하지만:

- AI 성공으로 위장 금지
- failure로 위장 금지
- withdrawal exclusion으로 위장 금지
- denominator에서 제거 금지

현재 APP의 리포트 UI/저장/발행 구조를 확인해서
다음 중 어떤 방식이 최소 변경이며 안전한지 제안할 것:

A.
DATA_ACCUMULATING 회원에게
‘이번 달은 성장 판단에 필요한 충분한 변화 근거가 아직 축적되지 않았습니다’
형태의 근거부족형 정상 월간 리포트를 발행

B.
별도의 정상 final disposition으로 처리하되
학부모에게 어떤 형태로 표시/발행할지 정의

목표는 해당 회원도 월간 발행 대상에서 사라지지 않고
정상적인 사용자 경험을 갖게 하는 것이다.

구현은 아직 하지 말고
현재 코드 기준 추천안을 제시한다.

6. 비용 및 retry 관측
━━━━━━━━━━━━━━━━━━━━━━

이번 단계에서 복잡한 비용 시스템을 새로 만들 필요는 없다.

다만 현재 APP/ENGINE에 존재하는 정보만으로:

- 최초 분석 비용
- recovery/retry로 추가 발생한 provider 호출
- 실패 후 추가 비용

을 어느 정도 구분할 수 있는지 확인한다.

기존 ledger/API로 충분하면 재사용한다.

부족하다면 최소 추가 필드/집계만 제안한다.

목적:
향후 “재시도 때문에 실제 얼마가 추가로 사용됐는지”
슈퍼관리자가 파악할 수 있도록 하는 것.

이번 구현계획에서 대형 비용 대시보드로 범위를 확장하지 말 것.

━━━━━━━━━━━━━━━━━━━━━━
7. 비정상 대량 실패 보호
━━━━━━━━━━━━━━━━━━━━━━

개별 실패 몇 건 때문에 전체 1차 작업을 중단하지 않는다.

다만 ENGINE/API/provider 전체 장애처럼
동일 계열 실패가 비정상적으로 연속/대량 발생하는 경우
수십만 건을 계속 호출하는 것도 금지해야 한다.

현재 코드에 이미 이를 방지할 수 있는
circuit breaker / failure threshold / pause 구조가 있는지 확인한다.

있으면 재사용.

없다면 이번 월간 growth-report worker에만 적용 가능한
최소 구조를 제안한다.

구체 threshold 값은 임의 확정하지 말고
configurable하게 설계한다.
