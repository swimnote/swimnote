SWIMNOTE 선생님 사진·영상 홈 화면 UI 회귀 및 저장용량 집계 오류 수정

현재 전체 앨범 사진은 정상적으로 표시되지만,
사진·영상 홈 화면에 다음 문제가 발생했습니다.

1. 상단 제목이 iOS 상태바 시간과 겹침
2. 앨범 카드 위치가 위로 올라가고 크기가 지나치게 커짐
3. 실제 사진이 존재하는데 하단 사용량이 사진 0개, 0 B로 표시됨

이번 작업 범위는 위 세 가지 수정입니다.
전체 앨범 조회 로직은 다시 망가뜨리지 마세요.

==================================================
1. 현재 화면 기준 UI 문제
==================================================

첨부된 실제 화면을 기준으로 수정하세요.

현재 문제:

- “사진 & 영상” 제목이 상태바의 7:22 시간과 겹침
- 화면 상단 safe area가 적용되지 않은 것으로 보임
- 네 개의 앨범 카드가 화면 너비와 높이를 과도하게 차지함
- 카드 간격이 좁고 상단에 몰려 있음
- 카드 하단 설명 문구가 카드 경계와 너무 가까움
- 업로드 제한사항 박스와 앨범 카드 사이 여백이 과도하거나 불균형함
- 하단 탭바까지 전체 화면 밀도가 지나치게 큼

==================================================
2. 상단 safe area 수정
==================================================

photos.tsx 최상위 화면 구조를 확인하세요.

다음을 점검:

- SafeAreaView 사용 여부
- useSafeAreaInsets 사용 여부
- paddingTop을 하드코딩했는지
- StatusBar 영역을 무시하는 View가 있는지
- ScrollView가 safe area 안쪽에서 시작하는지
- 헤더가 absolute position인지
- iOS에서 contentInsetAdjustmentBehavior가 비활성화돼 있는지

수정 원칙:

- 제목은 상태바 아래에서 시작
- iPhone Dynamic Island, 노치, 일반 상태바 모두 대응
- 제목 상단 여백은 insets.top 기준
- 고정 숫자 paddingTop으로 임시 해결하지 말 것
- Android에서도 과도한 상단 여백이 생기지 않을 것

권장 구조 예시:

const insets = useSafeAreaInsets();

<View style={[
  styles.container,
  { paddingTop: insets.top }
]}>

또는 SafeAreaView edges={["top"]} 사용

단, 기존 공통 Screen/Header 컴포넌트가 있다면
그 구조를 재사용하세요.

==================================================
3. 앨범 카드 크기 축소 및 위치 재정렬
==================================================

현재 네 개 카드:

- 전체사진 업로드
- 전체영상 업로드
- 내사진앨범
- 내영상앨범

을 2열 그리드로 유지하되 크기를 줄이세요.

수정 목표:

- 카드가 화면 폭의 약 절반을 차지하되 좌우 여백 확보
- 카드 높이를 현재보다 약 20~30% 축소
- 아이콘 박스 크기 축소
- 제목 글자 크기 소폭 축소
- 설명 문구 크기 축소 또는 lineHeight 조정
- 카드 내부 상하 padding 축소
- 프리미어 배지가 카드 밖으로 튀어나오지 않음
- 카드 4개가 화면 상단을 과도하게 점유하지 않음

레이아웃 권장 기준:

- 화면 좌우 padding: 16~20
- 카드 사이 gap: 12~16
- 카드 width:
  (screenWidth - horizontalPadding*2 - gap) / 2
- 카드 aspect ratio 또는 minHeight 사용
- 고정 width/height 하드코딩보다 화면 너비 기반 계산
- 제목은 한 줄 유지 가능하면 유지
- 설명 문구는 최대 1~2줄
- 카드 전체 높이 일관성 유지

현재 화면처럼 카드가 거의 정사각형 대형 패널로 보이지 않게 하세요.

5. 저장용량 집계 오류 조사
==================================================

현재 실제 사진이 전체 앨범에 표시되는데도:

사진 0개
영상 0개
총 사용량 0 B
이번 달 0 B

로 표시됩니다.

이건 UI 숫자 표시 문제가 아니라
사용량 데이터 소스가 전체 앨범 데이터와 분리되어 있거나,
API 응답 매핑이 잘못됐을 가능성이 큽니다.

다음 흐름을 전부 확인하세요.

1. 사용량 영역이 어떤 API를 호출하는지
2. API 요청이 실제 발생하는지
3. 응답 status가 200인지
4. 응답 JSON 필드명이 무엇인지
5. 프론트 타입과 필드명이 일치하는지
6. center_id / uploader_id / teacher_id 조건이 잘못됐는지
7. attached 사진을 사용량에서 제외하는지
8. file_size가 null 또는 string으로 오는지
9. byte 합계 계산에서 NaN이 발생하는지
10. 앱 상태에 값이 실제로 저장되는지

==================================================
6. 사용량의 확정 집계 기준
==================================================

“내 업로드 사용량”은 로그인한 선생님이 업로드한
삭제되지 않은 모든 사진·영상 기준으로 집계하세요.

포함:

- uploaded
- attached
- detached

제외:

- is_deleted=true
- 실제 삭제 완료된 파일
- 다른 선생님 업로드
- 다른 센터 데이터

집계 항목:

photoCount
photoBytes
videoCount
videoBytes
totalBytes
monthlyUploadedBytes

총 사용량:

photoBytes + videoBytes

이번 달:

해당 월에 업로드한 파일의 byte 합계

일지에 첨부됐는지 여부는 저장용량 집계와 무관합니다.

==================================================
7. 서버 쿼리 확인
==================================================

사용량 API에서 다음 조건을 확인하세요.

잘못된 예:

WHERE diary_id IS NULL
WHERE status = 'uploaded'
WHERE attached = false
WHERE student_id IS NULL

이런 조건이면 이미 일지에 첨부된 사진이 집계에서 빠집니다.

권장 개념:

WHERE center_id = :centerId
AND uploader_id = :teacherUserId
AND is_deleted = false
AND media_type IN ('image', 'video')

집계 예시:

COUNT(*) FILTER (WHERE media_type='image') AS photo_count
COALESCE(SUM(file_size) FILTER (WHERE media_type='image'), 0) AS photo_bytes
COUNT(*) FILTER (WHERE media_type='video') AS video_count
COALESCE(SUM(file_size) FILTER (WHERE media_type='video'), 0) AS video_bytes
COALESCE(SUM(file_size), 0) AS total_bytes

이번 달:

created_at >= date_trunc('month', now())

DB 실제 컬럼명에 맞게 구현하세요.

==================================================
8. file size 저장 상태 확인
==================================================

앨범에는 사진 row가 있지만 file_size가 0 또는 null일 수 있습니다.

Production DB에서 실제 사진 row 3~5개를 조회해 다음을 보고하세요.

- media id
- media type
- status
- file size
- storage key
- uploader id
- center id
- created at
- is deleted

만약 기존 row의 file_size가 null이라면:

1. 신규 업로드부터 정확한 파일 크기를 저장
2. 기존 파일은 R2 또는 저장소 metadata로 backfill 가능한지 확인
3. backfill 불가하면 기존 row 수는 표시하되 byte 용량은 별도 처리
4. null을 무조건 0으로 숨기지 말고 원인을 보고

업로드 API에서 다음을 확인하세요.

- 이미지 선택 결과의 fileSize
- multipart upload Content-Length
- 서버 수신 buffer size
- R2 object size
- DB file_size 저장

클라이언트가 전달한 숫자만 믿지 말고
가능하면 서버 또는 저장소가 확인한 실제 byte 값을 저장하세요.

9. API 응답 구조 통일
==================================================

사용량 API 응답을 다음처럼 명확히 통일하세요.

{
  "photoCount": 12,
  "photoBytes": 18439221,
  "videoCount": 2,
  "videoBytes": 92388411,
  "totalBytes": 110827632,
  "monthlyUploadedBytes": 30488210,
  "quotaBytes": 1073741824,
  "usagePercent": 10.3
}

snake_case를 반환한다면 프론트 mapper에서 확실하게 camelCase로 변환하세요.

현재 화면에 “현재 1% 사용 중”이 표시되는데
동시에 총 사용량이 0 B인 것은 서로 모순입니다.

usagePercent와 totalBytes가
서로 다른 API나 다른 상태값을 읽는지 확인하세요.

반드시 하나의 동일한 usage 응답을 기준으로 렌더링하세요.

==================================================
10. 로딩·오류 상태
==================================================

사용량 API를 불러오기 전에는 0 B를 확정값처럼 표시하지 마세요.

상태 분리:

- loading: “사용량 계산 중…”
- success: 실제 숫자 표시
- empty: 사진 0개 / 0 B
- error: “사용량을 불러오지 못했습니다” + 재시도

API 오류를 0으로 대체하지 마세요.

다음 패턴 검색:

catch(() => setUsage(defaultZero))
catch { return zeroUsage }
response?.data || zeroUsage

오류를 0으로 숨기지 마세요.

12. 테스트
==================================================

테스트 1
사진 1장 업로드
→ 사진 1개
→ photoBytes > 0
→ totalBytes > 0

테스트 2
사진 3장 업로드
→ 사진 3개
→ 합계 byte 정확

테스트 3
사진을 일지에 첨부
→ 전체 앨범 계속 표시
→ 사용량 숫자 그대로 유지

테스트 4
사진 삭제
→ 사진 수 1 감소
→ 총 사용량 감소

테스트 5
영상 업로드
→ 영상 수 1 증가
→ videoBytes 반영
→ totalBytes 증가

테스트 6
앱 종료 후 재실행
→ 동일 사용량 표시

테스트 7
사용량 API 실패
→ 0 B가 아니라 오류 상태 표시

테스트 8
기존 사진 row file_size=null
→ 원인 보고
→ 신규 업로드는 정상 size 기록
→ 가능한 경우 backfill 수행

테스트 9
iPhone 현재 첨부 화면과 동일 기기
→ 제목 상태바 겹침 없음
→ 카드 크기 정상
→ 탭바 가림 없음

테스트 10
Android 소형 화면
→ 카드 2열 유지
→ 텍스트 잘림 없음
