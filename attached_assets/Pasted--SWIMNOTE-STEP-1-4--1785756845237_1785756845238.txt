1. 상태 변경과 반 이탈 정책을 일치시킬 것

현재 admin.ts 수정안은 suspended/withdrawn 상태에서:

- student_class_history.left_at은 종료
- students.class_group_id와 assigned_class_ids는 유지

하도록 설계되어 있다.

이 상태는 데이터가 서로 모순된다.

history 종료는 “해당 날짜부터 그 반 소속이 아님”을 뜻하므로,
현재 배정 필드도 동일 정책으로 처리되어야 한다.

각 상태별 실제 서비스 정책을 표로 확정한다.

| 상태 | 반 소속 유지 여부 | history 종료 | class_group_id | assigned_class_ids |
|---|---|---|---|---|
| suspended | 확정 | 확정 | 확정 | 확정 |
| withdrawn | 확정 | 확정 | 확정 | 확정 |
| archived | 확정 | 확정 | 확정 | 확정 |
| unassigned | 확정 | 확정 | 확정 | 확정 |
| inactive | 확정 | 확정 | 확정 | 확정 |
| pending | 확정 | 확정 | 확정 | 확정 |

원칙:

A. 반 이탈 상태라면
- history 종료
- class_group_id = NULL
- assigned_class_ids = []
- 필요 시 schedule_labels 초기화
를 동일 transaction에서 수행한다.

B. 반 소속 유지 상태라면
- history를 종료하지 않는다.
- 현재 배정 필드도 유지한다.

history만 종료하고 현재 배정을 남기는 조합은 금지한다.

기존 선생님 화면과 관리자 화면에서 각 상태가 실제로 어떤 의미로 사용되는지 Repository UI 문구와 요청 body까지 확인해서 확정한다.

2. today-schedule 전체 반 목록 fallback 제거
━━━━━━━━━━━━━━━━━━━━━━

현재 제안:

allGroups가 비어 있으면 sortedItems 기반 당일 반 목록 fallback

이 방식은 금지한다.

이유:
전체 반 목록이 아직 로딩 중인 순간에 반이동을 누르면,
실제로 이동할 반이 있어도 “이동 가능한 반 없음”으로 잘못 표시된다.

최종 정책:

- allGroups 로딩 중:
  반이동 버튼 비활성 또는 로딩 표시
- allGroups 조회 성공:
  담당 선생님 전체 반 목록 전달
- allGroups 조회 성공 + 실제 타 반 0개:
  “이동 가능한 반이 없습니다”
- allGroups 조회 실패:
  오류 메시지 + 재시도
- sortedItems 당일 반 목록으로 fallback 금지

판정:

A. signal 지원
→ AbortController 사용

B. signal 미지원
→ 공통 apiRequest를 우회한 직접 fetch를 임의 도입하지 않는다.
→ request sequence ID 방식 권장

예:

const requestSeqRef = useRef(0);

const seq = ++requestSeqRef.current;
setStudentsByDate(undefined);

const result = await apiRequest(...);

if (seq !== requestSeqRef.current) return;
setStudentsByDate(result);

4. historyUtils transaction 타입 정확히 확정
━━━━━━━━━━━━━━━━━━━━━━

다음 타입은 그대로 사용하지 않는다.

tx: typeof superAdminDb

이유:
db client와 transaction callback 객체는 타입이 다를 수 있다.

Repository에서 기존 db.transaction callback 타입 사용 사례를 확인하고,
컴파일 가능한 타입을 확정한다.

가능한 방식:

A.
type DbTransaction =
  Parameters<Parameters<typeof db.transaction>[0]>[0];

B.
유틸이 실제로 필요한 메서드만 가진 최소 인터페이스 정의

interface HistoryTx {
  execute: typeof db.execute;
}

단, 실제 Drizzle 타입과 맞는지 타입체크로 검증해야 한다.

추가 확인:

- students.ts와 admin.ts가 동일한 db 인스턴스를 사용하는지
- superAdminDb를 import해야 하는지
- 일반 db와 superAdminDb를 혼용하면 tenant isolation 문제가 없는지
- historyUtils는 새 transaction을 열지 않고 전달받은 tx만 사용해야 함
