# 보호자 전화번호 즉시 저장 및 추가 학부모 자동 승인·연결 최종 점검

현재 학생 상세의 학부모 연락처 기능에 두 가지 문제가 있습니다.

문제 1.

보호자 2 전화번호를 수정하고 저장해도
첫 번째 저장에서는 화면에 즉시 반영되지 않습니다.

같은 번호를 두 번 또는 세 번 다시 입력하고 저장해야
최종적으로 변경되는 경우가 있습니다.

문제 2.

보호자 2 전화번호를
이미 가입한 학부모 계정의 전화번호로 입력했을 때,

- 해당 학부모가 즉시 자동 승인되는지
- 동일 학생에게 즉시 연결되는지
- 보호자 1과 동일한 학부모 서비스를 받는지

정확한 구조 확인이 필요합니다.

이번 작업에서는 두 문제를 하나의 흐름으로 분석하고 수정하세요.

목표 흐름:

전화번호 입력
→ 저장 1회
→ 서버 저장 완료
→ 최신 학생 상세 재조회
→ 화면 즉시 변경
→ 동일 번호 학부모 계정 검색
→ 계정이 있으면 즉시 학생 연결 및 승인
→ 보호자 1과 동일한 서비스 제공

==================================================
1. 저장을 두세 번 해야 반영되는 정확한 원인 확인
==================================================

먼저 왜 첫 번째 저장에서 변경되지 않는지 정확한 원인을 찾으세요.

다음 가능성을 모두 확인하세요.

- 저장 함수가 이전 state 값을 전송하는지
- setState 직후 변경 전 state를 API body에 사용하는지
- modal input state와 parentPhones state가 분리되어 동기화되지 않는지
- onChangeText 값이 저장 함수에 즉시 전달되지 않는지
- 저장 버튼이 stale closure를 참조하는지
- 저장 요청 후 학생 상세 재조회가 누락됐는지
- 재조회는 했지만 await 없이 모달을 먼저 닫는지
- API 성공 후 로컬 state가 구버전 데이터로 다시 덮어써지는지
- optimistic update와 서버 재조회가 경쟁하는지
- React Query 또는 로컬 캐시가 이전 값을 반환하는지
- 보호자 배열 index가 잘못 매핑되는지
- 보호자 2 수정인데 보호자 1 필드 또는 잘못된 slot을 보내는지
- 서버에서 update 후 응답이 변경 전 값을 반환하는지
- DB transaction commit 전에 재조회하는지
- 화면 focus effect가 이전 데이터를 다시 불러오는지
- PATCH 요청이 중복 실행되거나 첫 요청이 취소되는지

표면적으로 저장 버튼을 여러 번 호출하게 만들지 마세요.

한 번의 저장으로 완료되어야 합니다.

==================================================
2. 저장 버튼 1회 처리 구조
==================================================

저장 버튼을 한 번 누르면 다음 순서로만 처리되게 하세요.

1. 현재 입력창의 최신 값을 직접 읽음
2. 전화번호 정규화
3. 유효성 검사
4. 저장 버튼 중복 탭 방지
5. PATCH 요청 1회
6. 서버의 DB 저장 완료 대기
7. 서버 응답 확인
8. 최신 학생 상세 API 재조회
9. parent phone과 연결 상태를 서버 결과로 전체 교체
10. 변경된 전화번호가 화면에 표시된 것을 확인한 뒤 모달 종료
11. 성공 안내
12. 저장 버튼 활성화 복구

다음 방식은 금지합니다.

- setPhone(value) 호출 직후 기존 phone state를 API에 전송
- API 요청 완료 전에 성공 처리
- API 성공 전 모달 닫기
- 이전 로컬 state로 학생 정보를 다시 덮어쓰기
- 첫 저장 실패를 숨기고 사용자가 재입력하도록 방치
- 저장 버튼 여러 번 탭으로 우연히 성공시키는 구조

==================================================
3. 전화번호 문자열 처리
==================================================

전화번호는 처음부터 끝까지 문자열로 처리하세요.

입력:

01062102386

서버 저장:

01062102386

화면 표시:

010-6210-2386

확인 대상:

- TextInput value
- onChangeText
- request body
- validation schema
- DB column
- API response
- UI formatter

다음 사용 금지:

- Number(phone)
- parseInt(phone)
- +phone
- 숫자형 DB 컬럼
- 앞자리 0을 제거하는 로직

현재 저장된 `62102386` 데이터가 있다면
이 값이 DB 데이터인지 로컬 상태인지 확인하고 정확히 보고하세요.

잘못된 8자리 번호를 임의로 `010`과 합쳐 복구하지 마세요.
실제 입력값과 서버 저장 이력을 기준으로 처리하세요.

==================================================
4. 자동 승인과 자동 연결의 정의
==================================================

이번 기능에서 사용하는 용어를 명확히 구분하세요.

가입 대기:

- 학생에게 보호자 전화번호는 등록됨
- 해당 번호의 학부모 앱 계정이 없거나
- 학생 연결 관계가 아직 없음

연결됨:

- 해당 전화번호와 일치하는 학부모 계정이 존재
- 학생-학부모 연결 관계가 존재
- 해당 학부모가 자신의 앱에서 학생을 조회할 수 있음

자동 승인:

- 관리자가 별도의 승인 버튼을 누르지 않아도
- 학생에게 사전 등록된 보호자 전화번호와
  학부모 가입 계정의 인증된 전화번호가 일치하면
- 학생-학부모 연결이 즉시 생성되는 것

단순히 전화번호를 저장하고
`가입 대기` 배지만 표시하는 것은 자동 승인이 아닙니다.

==================================================
5. 이미 가입한 학부모 번호 입력 시 즉시 연결
==================================================

보호자 2 입력 번호와 동일한 학부모 계정이 이미 존재한다면
저장 요청 안에서 다음 처리를 완료하세요.

1. 전화번호 정규화
2. 인증된 학부모 계정 검색
3. 현재 센터 또는 tenant 범위 검증
4. 해당 학생과 기존 연결이 있는지 확인
5. 연결이 없다면 학생-학부모 연결 생성
6. 연결이 이미 있다면 중복 row를 만들지 않음
7. 연결 상태를 `연결됨`으로 반환
8. 학생 상세 재조회 시 즉시 `연결됨` 표시
9. 보호자 1 연결 유지
10. 학부모 앱에서 동일 학생 즉시 조회 가능

대표 보호자 값을 보호자 2로 교체하는 방식은 금지합니다.

학생 1명에 대해 보호자 1과 보호자 2가
각각 독립된 연결 관계를 가져야 합니다.

==================================================
6. 아직 가입하지 않은 번호 입력 시 처리
==================================================

보호자 2 번호의 학부모 계정이 아직 없다면:

1. 전화번호 저장
2. 상태는 가입 대기
3. 보호자 1 연결 유지
4. 이후 해당 번호로 학부모가 가입하고 전화번호 인증을 완료하면
5. 학생의 보호자 등록 번호와 비교
6. 일치하는 학생 자동 검색
7. 학생-학부모 연결 즉시 생성
8. 별도 관리자 승인 없이 연결 완료
9. 학부모 앱에서 학생 즉시 확인
10. 학생 상세 상태도 연결됨으로 변경

학부모 가입 시 자동 연결 로직이 없다면 추가하세요.

단, 전화번호 인증 없이
사용자가 임의로 입력한 번호만으로 연결하지 마세요.

학부모 계정의 인증된 전화번호를 기준으로 연결하세요.

==================================================
7. 수정된 번호와 기존 연결 처리 정책
==================================================

보호자 2가 이미 연결된 상태에서 전화번호를 다른 번호로 수정하면
다음 정책을 적용하세요.

기존 번호 A가 보호자 계정 A와 연결된 상태에서
새 번호 B로 변경하는 경우:

1. 기존 보호자 계정 A와 학생 연결을 자동으로 B 계정에 이전하지 않음
2. 기존 A 연결을 유지할지 해제할지 현재 정책을 명확히 결정
3. 권장 정책은 번호 변경 확인 후 기존 A 연결 해제
4. 새 번호 B 계정이 이미 존재하면 B와 학생 연결 생성
5. B 계정이 없으면 가입 대기
6. 보호자 1 연결에는 영향 없음
7. 기존 일지와 학생 기록은 삭제하지 않음

사용자에게 다음과 같은 경고를 표시하세요.

"이미 연결된 보호자 연락처입니다.
전화번호를 변경하면 기존 보호자의 학생 연결이 해제될 수 있습니다."

실제 적용 정책을 완료 보고에 정확히 설명하세요.

==================================================
8. 보호자 1과 보호자 2의 동일 서비스 확인
==================================================

보호자 2가 연결되면 보호자 1과 동일하게 다음을 조회해야 합니다.

- 학부모 홈
- 공통 일지
- 학생 개별 일지
- 사진
- 영상
- 공지
- 앨범
- 출결
- 일정
- 교육 프로그램
- 수영정보
- 레벨
- 진도
- 알림

조회 기준을 확인하세요.

잘못된 기준:

- parent_phone_1만 조회
- 대표 보호자 ID만 조회
- 첫 번째 연결 row만 조회
- 학생 테이블의 단일 parent_id만 조회

정상 기준:

현재 로그인한 학부모 계정
→ student-parent 연결 관계 확인
→ 연결된 모든 학생 데이터 조회

보호자 1과 보호자 2는
같은 학생에 연결된 독립적인 학부모 계정이어야 합니다.

==================================================
9. 서버에서 즉시 확인 가능한 응답 구조
==================================================

PATCH 요청 성공 응답에는 최소한 다음 정보를 포함시키세요.

예시:

{
  success: true,
  studentId: "...",
  parentPhones: [
    {
      slot: 1,
      phone: "01040560220",
      formattedPhone: "010-4056-0220",
      connectionStatus: "connected",
      parentUserId: "..."
    },
    {
      slot: 2,
      phone: "01062102386",
      formattedPhone: "010-6210-2386",
      connectionStatus: "connected" 또는 "pending",
      parentUserId: "..." 또는 null
    }
  ]
}

클라이언트는 임의로 연결 상태를 추정하지 말고
서버가 반환한 실제 연결 상태를 사용하세요.

PATCH 응답 후 학생 상세 GET도 다시 실행하여
서버 데이터가 동일한지 확인하세요.

==================================================
10. 저장 상태와 중복 탭 방지
==================================================

저장 처리 중에는:

- 저장 버튼 비활성화
- 로딩 표시
- 중복 PATCH 요청 방지
- modal을 임의로 닫지 못하게 하거나 안전하게 처리

저장 성공 시:

- 최신 서버 데이터 반영
- 모달 닫기
- 성공 안내

저장 실패 시:

- 모달 유지
- 입력값 유지
- 기존 학생 상세 데이터 유지
- 잘못된 번호를 목록에 반영하지 않음
- 정확한 오류 메시지 표시
- 저장 버튼 다시 활성화

==================================================
11. 오류 메시지 구분
==================================================

모든 오류를 "네트워크 오류"로 표시하지 마세요.

구분:

- fetch 자체 실패: 네트워크 오류
- 400: 전화번호 형식 오류
- 401/403: 권한 오류
- 404: 학생 또는 API 없음
- 409: 동일 학생 내 중복 번호
- 422: validation 오류
- 500: 서버 저장 또는 연결 처리 오류

서버 응답의 실제 오류 메시지가 있으면 표시하세요.

==================================================
12. 실제 서버/API 검증
==================================================

정적 분석만으로 정상이라고 결론 내리지 마세요.

가능하면 정상 인증 토큰으로 API 통합 테스트를 수행하세요.

인증 문제로 실제 API 호출이 불가능하다면
코드상 확인과 실기기 검증 필요를 구분해 보고하세요.

필수 테스트:

테스트 A — 저장 1회

1. 보호자 2 수정창 열기
2. 01062102386 입력
3. 저장 버튼 1회
4. PATCH 1회만 발생
5. 서버에 01062102386 저장
6. 학생 상세에 즉시 010-6210-2386 표시
7. 두 번째·세 번째 입력 불필요

테스트 B — 기존 가입 계정

1. 01062102386과 일치하는 인증된 학부모 계정 준비
2. 학생 보호자 2에 번호 저장
3. 즉시 student-parent 연결 생성
4. 학생 상세에 연결됨 표시
5. 학부모 앱에서 학생 조회

테스트 C — 미가입 계정

1. 가입되지 않은 번호 저장
2. 가입 대기 표시
3. 해당 번호로 학부모 가입 및 전화번호 인증
4. 자동 연결
5. 관리자 추가 승인 불필요

테스트 D — 보호자 1 유지

1. 보호자 1 연결됨
2. 보호자 2 추가 또는 수정
3. 보호자 1 연결 유지
4. 보호자 1 서비스 정상

테스트 E — 동일 서비스

보호자 1과 보호자 2에서 각각:

- 같은 일지
- 같은 사진
- 같은 공지
- 같은 출결
- 같은 일정
- 같은 레벨

조회 확인

테스트 F — 저장 실패

1. 서버 오류 발생
2. 모달 유지
3. 입력값 유지
4. 목록에는 잘못된 번호 미반영
5. 재시도 1회로 정상 저장 가능

13. 로그로 확인할 내용
==================================================

개인정보 전체를 운영 로그에 남기지 마세요.

개발 환경에서만 마스킹하여 확인하세요.

예:

010-****-2386

확인할 로그:

- 저장 버튼 실행 횟수
- PATCH 요청 횟수
- 요청한 slot
- 마스킹된 전화번호
- HTTP status
