1. eligible-occurrences API 실존 확인
━━━━━━━━━━━━━━━━━━━━━━

GET /teacher/makeups/:makeupId/eligible-occurrences?class_group_id=...

다음을 실제 코드로 제출:

- 서버 라우트 파일

- 함수 시작·종료 라인
- Request query
- Response JSON
- 인증·pool 권한 검증
- 해당 API가 언제 구현됐는지 git SHA

API가 존재하지 않으면 현재 구현은 미완성이므로 즉시 보고하고 멈춘다.

2. occurrence 생성 로직 검증
━━━━━━━━━━━━━━━━━━━━━━

서버 또는 클라이언트 중 어디서 회차를 생성하는지 명확히 제출한다.

각 occurrence가 다음 조건을 만족하는지 확인:

- occurrence_date >= absence_date
- occurrence_date <= expire_at
- 선택 반의 schedule_days와 실제 요일 일치
- Asia/Seoul 날짜 기준
- 오늘 포함
- 과거 포함
- 미래 포함
- 동일 class_group_id + occurrence_date 중복 제거
- 비활성·삭제된 반 제외
- 다른 수영장 반 제외

실제 생성 함수와 날짜 비교식을 원문으로 제출한다.

━━━━━━━━━━━━━━━━━━━━━━
3. 정원 마감 반 반환 확인
━━━━━━━━━━━━━━━━━━━━━━

기존 eligible-classes에는

HAVING available_slots > 0

조건이 있었다.

eligible-occurrences 또는 반 목록 조회에서 정원 마감 반이 실제로 반환되는지 확인한다.

필수 결과:

- 미래 회차 + available_slots <= 0:
  기존 정책대로 저장 차단
- 오늘·과거 회차 + available_slots <= 0:
  목록 표시
  경고 후 complete-direct 허용

단순히 클라이언트에서 is_full 배지만 표시하고
서버 응답에서 정원 마감 반이 빠진다면 구현 실패다.

실제 SQL의 HAVING/WHERE 조건을 제출한다.

━━━━━━━━━━━━━━━━━━━━━━
4. 저장 API 서버 검증 확인
━━━━━━━━━━━━━━━━━━━━━━

다음 API의 실제 서버 코드를 확인한다.

- PATCH /teacher/makeups/:id/assign
- PATCH /teacher/makeups/:id/complete-direct

다음 조건을 서버가 검증하는지 표로 제출:

1. 날짜 형식
2. 결석일 이전 차단
3. 만료일 이후 차단
4. 해당 반 수업 요일인지
5. 같은 swimming_pool 소속인지
6. 반 active 여부
7. completed/cancelled 상태 재처리 차단
8. 미래 정원 마감 저장 차단
9. 오늘·과거 정원 초과 사후 처리 허용
10. 동일 요청 재시도 중복 방지

클라이언트 분기만으로 처리하고 서버 검증이 없다면 미완성이다.
