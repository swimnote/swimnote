0. 절대 혼동 금지 — 발급월과 분석월
━━━━━━━━━━━━━━━━━━━━━━

AI 성장리포트는 "발급월"과 "분석대상월"이 다르다.

공식 규칙:

발급월 M
→ 분석대상월 M-1

예:

2026-10-05 발급
= 2026년 9월 수업내역을 분석한
"2026년 9월분 AI 성장리포트"

절대로 10월 수업내역을 분석하면 안 된다.

2026-11-05 발급
= 2026년 10월분

2026-12-05 발급
= 2026년 11월분

코드 내부에서도
issueMonth / reportMonth / analysisMonth 등의 의미가
혼동되지 않도록 확인한다.

기존 변수명을 대규모 리팩터링할 필요는 없지만,
잘못 해석될 가능성이 있는 곳에는
최소한의 명확한 주석/헬퍼를 사용한다.

테스트에서 반드시 이 관계를 고정한다.

━━━━━━━━━━━━━━━━━━━━━━
1. 발급 대상 V1.0
━━━━━━━━━━━━━━━━━━━━━━

무료 월간 AI 성장리포트의 기본 대상은:

A. 전월에 해당 수영장에서 수강했고
B. 다음 달 1일에도 계속 수강 상태이며
C. 인정수업이 3회 이상이고
D. 유효한 학생별 개인 일지가 1건 이상이며
E. 실제 발급일인 5일에도 active인 회원

이다.

현재 시스템에 학생별 월별 결제/재등록 완료를
독립적으로 증명하는 source of truth가 없으므로,

"다음 달에도 계속 수강"

의 시스템 판정은 V1.0에서:

- 다음 달 1일 기준 active
- 해당 수영장의 반 재원 이력이 계속 유효

로 고정한다.

단순 active만으로 판정하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
2. 인정수업 계산 — 절대 기준
━━━━━━━━━━━━━━━━━━━━━━

인정수업은 다음 의미로 계산한다.

인정수업
= 해당 분석월의 예정수업
- 결석 처리된 수업
+ 해당 분석월에 인정되는 완료 보강

핵심 원칙:

결석 표시가 없는 예정수업
= 출석으로 인정

결석
= 해당 예정수업 1회 차감

완료된 보강
= 인정수업 1회 추가

따라서 "결석 횟수" 자체가
발급 제외 기준이 아니다.

최종 인정수업이 3회 이상인가가 기준이다.

예:

월 4회 예정
결석 0
→ 인정수업 4
→ 통과

월 4회 예정
결석 1
→ 인정수업 3
→ 통과

월 4회 예정
결석 1 + 완료보강 1
→ 인정수업 4
→ 통과

월 4회 예정
결석 2 + 완료보강 0
→ 인정수업 2
→ 제외

주2회 / 월 8회 예정
결석 2
→ 인정수업 6
→ 통과

그러므로
"결석 2회 이상이면 제외"
같은 별도 규칙을 만들지 마라.

오직 최종 인정수업 >= 3을 사용한다.

같은 원수업에 대한 데이터 중복이나
같은 보강을 두 번 세어
double count하지 않는지도 확인한다.

━━━━━━━━━━━━━━━━━━━━━━
3. 유효 개인 일지
━━━━━━━━━━━━━━━━━━━━━━

분석대상월에
해당 학생에게 귀속된 유효한 개인 일지가
최소 1건 있어야 한다.

기존의 유효 일지 정의:

- 해당 학생 귀속
- 미삭제
- 비어 있지 않음
- 실제 문자/숫자 내용 존재

를 유지한다.

공통 수업내용만 있고
해당 학생의 개인 기록이 없는 경우를
개인 일지 1건으로 임의 계산하지 않는다.

최소 기준:
validStudentDiaryCount >= 1

━━━━━━━━━━━━━━━━━━━━━━
4. 월 데이터 경계 — KST 고정
━━━━━━━━━━━━━━━━━━━━━━

모든 월간 성장리포트 데이터는
Asia/Seoul 기준 반개방 구간으로 계산한다.

2026년 9월분:

>= 2026-09-01 00:00:00 KST
<  2026-10-01 00:00:00 KST

즉:

9/1 00:00 포함
9/30 23:59:59... 포함
10/1 00:00 제외

현재 조사에서 발견된
UTC 문자열을 YYYY-MM-DD로 잘라
< 2026-09-30 등으로 비교하면서
9월 30일 전체가 빠지는 경로를 수정한다.

일지
출석
보강
성장 이벤트
엔진 snapshot

등 "분석대상월 데이터"라고 정의된 모든 경로가
동일한 월 경계를 사용하도록 한다.

과거 데이터가 분석월 snapshot에
무제한으로 섞이는 경로도 확인하여
V1.0 월 범위와 일치시킨다.

단,
장기 추세용 데이터처럼 명시적으로 과거 데이터가
필요한 별도 필드가 존재한다면
월간 수업자료와 섞어 임의 제거하지 말고
그 용도를 보고한다.

━━━━━━━━━━━━━━━━━━━━━━
5. 전월 수강 여부
━━━━━━━━━━━━━━━━━━━━━━

다음 달에 active라는 이유만으로
전월 리포트를 만들면 안 된다.

예:

9월 수강 O / 10월 계속 수강 O
→ 9월분 후보

9월 수강 O / 10월 계속 수강 X
→ 자동발급 제외

9월 수강 X / 10월 신규등록 O
→ 9월분 자동발급 제외

9월 중도등록 / 10월 계속 수강
→ 9월 실제 대상기간의 인정수업 >=3
   AND 개인 일지 >=1이면 가능

즉 신규 회원에게
가입 전 달 리포트가 생성되는 일이 없어야 한다.

━━━━━━━━━━━━━━━━━━━━━━
6. 1일과 5일 상태 판정
━━━━━━━━━━━━━━━━━━━━━━

1일:
다음 달 계속 수강 대상 여부를 판정하고
분석 준비/생성을 진행할 수 있다.

5일 실제 자동발급 직전:
학생의 현재 active 상태를 다시 확인한다.

1일 active
→ 3일 퇴원/휴회
→ 5일 inactive
→ 자동 PUBLISHED/PUSH 제외

1일 active
→ 5일에도 active
→ 다른 조건 충족 시 정상 발급

이를 위해 복잡한 별도 퇴원 추적 시스템을 만들지 않는다.

"5일 발급 직전 현재 상태 확인"
한 번으로 처리한다.

━━━━━━━━━━━━━━━━━━━━━━
7. 5일 자동발급의 정의
━━━━━━━━━━━━━━━━━━━━━━

조건을 충족하고
AI ENGINE 분석이 정상 성공하고
응답 검증 및 DB 저장이 완료되면:

PUBLISHED
→ 학부모 피드 노출
→ 학부모 PUSH

까지 자동으로 진행한다.

관리자가 별도 "발송" 버튼을 눌러야
PUBLISHED 되는 구조는
무료 월간 AI 성장리포트 V1.0 정책과 맞지 않는다.

단:

EXCLUDED
FAILED
PROCESSING
RETRY_WAIT
엔진 응답 검증 실패
필수 결과 저장 실패

상태는 절대로 자동 PUBLISHED하지 않는다.

PUSH 실패가 이미 정상 PUBLISHED된 리포트를
rollback시키지는 않는다.

동일 report/cycle/student에 대한
중복 PUBLISHED 및 중복 PUSH를 방지한다.

━━━━━━━━━━━━━━━━━━━━━━
8. 발급 이후 퇴원
━━━━━━━━━━━━━━━━━━━━━━

5일에 정상적으로 PUBLISHED된 후
학생이 퇴원하더라도

이미 발급된 과거 AI 성장리포트를
퇴원 처리 과정에서 삭제하지 않는다.

예:

10/5 9월분 정상 발급
10/6 퇴원

→ 9월분 PUBLISHED 리포트 보존

현재 withdraw 서비스가
기발급 growth_reports까지 삭제한다면
PUBLISHED 리포트 보존 정책에 맞게 최소 수정한다.

단,
미완성/임시/분석 중 데이터의 퇴원 처리까지
임의로 정책 확장하지 말고
필요하면 현재 동작을 보고한다.

━━━━━━━━━━━━━━━━━━━━━━
9. 기존 Production BLOCKER 함께 수정
━━━━━━━━━━━━━━━━━━━━━━

이전 조사에서 확인된 아래 문제도
이번 V1.0 기준으로 수정한다.

A.
Oct 1 cycle OPEN 실패 원인:

ANY(($1,$2)::text[])

형태의 잘못된 SQL 파라미터 처리.

0개 / 1개 / 복수 이름

B.

C.
9월 30일 전체 누락 가능성이 있는
날짜 경계 오류.

D.
무료 월간 성장리포트가
관리자 수동 발송을 기다리는 현재 경로.

V1.0 자동 PUBLISHED/PUSH로 수정.

10. batch 완료 의미
━━━━━━━━━━━━━━━━━━━━━━

단순히 대상 row를 준비했다고
"성장리포트 발급 완료"라고 표시하지 않는다.

최소한 운영상 다음 상태를 구분할 수 있어야 한다.

eligible
excluded
analysis_pending / processing
published
failed

기존 DB/상태값으로 표현 가능하면
새 구조를 만들지 않는다.

batch preparation 완료와
실제 PUBLISHED 완료를 혼동하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
11. AI ENGINE 호출
━━━━━━━━━━━━━━━━━━━━━━

APP/API에서 ENGINE 호출 구조 자체를
이번 WP에서 임의 변경하지 않는다.

현재 ENGINE은 별도 용량 검증 WP를 진행할 예정이다.

APP 분석 concurrency가 hardcoded라면
최소 변경으로 설정 가능하게 만든다.

하지만 이번 WP에서 임의로
20 → 다른 숫자로 확정하지 않는다.

Production ENGINE 설정이나
Render Compute Plan도 변경하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
12. 복구/idempotency
━━━━━━━━━━━━━━━━━━━━━━

이미 존재하는 2026년 9월 cycle이 있다면
새 cycle을 중복 생성하지 않는다.

기존 ACTIVE cycle을 재사용할 수 있어야 한다.

성공한 결과가 있다면 보존한다.

재실행하더라도:

- report 중복 생성 금지
- 동일 학생 중복 분석 결과 overwrite 사고 금지
- 중복 PUBLISHED 금지
- 중복 parent PUSH 금지

가 보장되어야 한다.

이번 WP에서는 Production 실제 재실행은 하지 않는다.

안전한 복구 절차만 보고한다.
