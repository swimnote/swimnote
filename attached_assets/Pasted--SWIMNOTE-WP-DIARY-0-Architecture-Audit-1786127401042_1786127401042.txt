[장애 1]
AI 개별일지 장문 내용 잘림
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

실기기에서 확인된 현상:

전체일지:
내용이 길어지면 TextInput 높이가 자연스럽게 증가하여
전체 내용을 한 번에 볼 수 있음.

개별일지:
약 2줄 높이로 제한되어
AI가 생성한 긴 내용이 화면에서 잘림.

목표:

개별일지도 전체일지와 동일하게:

- multiline
- 내용 길이에 따라 자동 높이 증가
- 전체 문장 한 번에 확인
- 학생별 독립 수정
- 학생 카드별 명확한 구분
- 학생 20명이어도 20명 모두 아래로 계속 이어짐
- 바깥 전체 ScrollView를 내려 마지막 학생까지 확인/수정
- 개별 TextInput 안에서 작은 별도 스크롤을 반복해서 쓰는 구조는 지양
- 학생 A 수정이 학생 B 내용에 영향 주지 않음

아직 UI 수정하지 말고
전체일지 TextInput과 개별일지 TextInput의 실제 구현 차이를 조사한다.

확인:

multiline
numberOfLines
height
minHeight
maxHeight
scrollEnabled
overflow
textAlignVertical
onContentSizeChange
contentSize
style
parent View height
ScrollView 구조
KeyboardAvoidingView 구조

"왜 전체일지는 늘어나고 개별일지는 2줄에서 잘리는가"를
정확한 코드 line으로 확정한다.

[AI PIPELINE AUDIT]
전체일지 / 개별일지 분리 무결성
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

최근 AI Engine에서 문장을 덜 AI스럽고
자연스럽게 출력하도록 문체 관련 변경이 있었다.

그 변경 자체는 정상 작업이며
임의로 rollback하지 않는다.

다만 다음 전체 경로를 점검한다.

교사 음성/텍스트
→ 앱 요청 생성
→ students context
→ AI Engine
→ common/student 분리
→ 수영 DB/커리큘럼 검색
→ Prompt Builder
→ LLM 최종 문장 생성
→ Engine 구조화 JSON
→ 앱 API response
→ request_id 검증
→ student_ref/student_id 검증
→ 앱 state
→ 전체일지/개별일지 입력창
→ 수정
→ 일지에 삽입
→ 기존 일지 저장

각 단계의:

- 실제 파일
- 실제 함수
- 실제 Contract

를 제출한다.

특히 최종 Engine 응답 구조를 원문으로 확인한다.

예상 개념:

result.common

result.students[
  {
    student_ref,
    content
  }
]

하지만 실제 Repository Contract를 기준으로 제출한다.

확인 사항:

1. common과 student 결과가 실제로 분리되는가
2. 학생별 결과가 ID/ref 기반인가
3. 배열 index 기반 매핑이 남아 있는가
4. 이름 문자열 매칭만 사용하는 위험한 경로가 있는가
5. 중복 student_ref 차단 여부
6. unknown student_ref 차단 여부
7. request_id mismatch 차단 여부
8. 학생별 content가 API 과정에서 truncate되는가
9. substring / slice / maxLength / numberOfLines 등으로 잘리는가
10. 20명일 때 학생 결과 누락 가능성이 있는가
11. 학생 A 결과가 학생 B로 섞일 가능성이 있는가
12. 최근 문체 변경이 Contract를 변경했는가

[장애 2]
일지 작성 완료 후 스케줄러 "일지완료" 표시 안 됨
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현상:

선생님이 실제 일지를 작성하고 저장했는데
스케줄러/오늘수업 화면에서
"일지완료" 표시가 나타나지 않는다는 보고가 있음.

다음 전체 경로 조사:

일지 작성 화면
→ 저장 버튼
→ API Request
→ Diary DB 저장
→ 저장 성공 response
→ 스케줄러 데이터 조회
→ diary 존재 여부 판단
→ 일지완료 상태 계산
→ UI badge/텍스트

반드시 확인:

1. 일지 저장 테이블
2. 일지를 식별하는 key
   - diary_id
   - class_group_id
   - lesson_date
   - teacher_id
   - 기타
3. 스케줄러가 일지완료를 판정하는 Source of Truth
4. 저장한 일지와 스케줄러 회차가 같은 class/date로 매칭되는가
5. timezone/KST 문제 가능성
6. 저장 후 scheduler refetch/invalidate 여부
7. 앱 state cache 문제
8. 화면 재진입 시에도 완료 표시가 안 되는지 코드상 가능성
9. 보강 학생 포함 여부가 완료 판정에 영향을 주는지
10. 일반 수업과 일회성/보강 수업의 차이

UI에서 임의로 완료=true 처리하는 수정 금지.

실제 저장 데이터 Source of Truth를 찾아야 한다.

[장애 3]
사진 첨부 일지 → 지난일지에서 사진 없음
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현상:

일지 작성 시 사진을 첨부하고 저장했는데

지난일지 화면에서:

"등록된 사진이 없습니다"

라고 표시된다는 보고가 있음.

전체 경로:

사진 선택
→ 이미지 upload
→ R2/스토리지 저장
→ upload response
→ 사진 URL/key/id
→ diary save payload
→ DB 저장/relationship
→ 지난일지 API
→ diary detail/list response
→ 앱 사진 필드 매핑
→ 사진 UI

확인:

1. 실제 사진 업로드 endpoint
2. 업로드 성공 response contract
3. 일지 저장 요청의 사진 필드명
4. 서버가 실제 저장하는 사진 컬럼/테이블
5. 사진과 diary의 연결 key
6. 지난일지 조회 API가 사진을 JOIN/SELECT 하는지
7. API response의 사진 필드명
8. 앱 지난일지가 어떤 필드명을 읽는지
9. URL normalization 문제
10. R2 public URL / signed URL 문제
11. 사진 자체는 존재하지만 relation만 누락되는지
12. DB에는 정상인데 앱만 못 읽는지
13. 신규 일지와 과거 일지의 schema 차이가 있는지

세 경우를 반드시 구분:

A.
사진 자체 저장 실패

B.
사진 저장 성공 + 일지 연결 실패

C.
DB 연결 정상 + 조회/API/UI 실패

증거 없이 하나로 단정 금지.
