2. BUG-3 삭제 로직 안전 수정
━━━━━━━━━━━━━━━━━━━━━━

가장 중요한 정책:

selected.size === 0

은 절대로

“전체 사진 삭제”

의 의미가 되어서는 안 됩니다.

현재 숨겨진 fallback:

0개 선택
→ 전체 IDs selected에 삽입
→ 수천 장 삭제

경로를 제거하십시오.

선택삭제는 반드시:

selected.size > 0

일 때만 활성화.

0개 선택이면 삭제 버튼:

- disabled
또는
- 아무 동작 없음

으로 처리.

현재 전체앨범에 별도 전체삭제 기능은 필요하지 않습니다.

4. BUG-4 업로드 순서 수정
━━━━━━━━━━━━━━━━━━━━━━

현재:

sort_order = origIndex

는 이미 저장되고 있습니다.

따라서 새 컬럼/DB migration을 만들지 마십시오.

하지만:

ORDER BY DATE_TRUNC('second', created_at)

같은 임의 시간 절삭 방식은 사용하지 마십시오.

서로 다른 upload batch가 같은 초에 생성되면
섞일 수 있기 때문입니다.

먼저 direct-upload finalize 한 번이
한 업로드 묶음 전체를 처리하는지 확인하십시오.

그렇다면 같은 finalize batch에서 생성되는 사진에는
하나의 공통 batch timestamp를 사용하도록 하십시오.

예:

const batchCreatedAt = new Date()

를 finalize 시작 시 한 번 만들고
해당 finalize의 모든 row에 동일하게 적용.

그 다음 teacher-all 조회는
기존 데이터 의미를 깨지 않는 범위에서:

created_at DESC
→ 같은 created_at 내 sort_order ASC
→ 안정적인 ID tie-breaker

순으로 정렬하십시오.

즉 새 업로드 묶음은 최신 묶음부터 표시되고,
같은 묶음 안에서는 origIndex 순서가 보존되어야 합니다.

기존 DB schema로 해결하십시오.
migration 금지.

만약 기존 schema에 이미 upload_session/batch 식별자가
저장되고 있다면 새 timestamp 방식보다
그 기존 batch 기준을 우선 사용하십시오.
