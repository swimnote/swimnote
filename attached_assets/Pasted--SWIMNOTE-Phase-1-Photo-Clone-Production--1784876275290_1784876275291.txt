[SWIMNOTE 일지 사진 중복 연결 버그 수정 — Phase 1 Photo Clone 방식]

추가 분석 설계를 검토했습니다.

현재 Production 앱의 긴급 버그를 해결하기 위해
Phase 1의 Photo Clone 방식을 적용하십시오.

단, 단순히 오류가 발생하지 않게 만드는 수준이 아니라
아래 요구사항과 정합성 조건을 모두 만족하도록 구현하십시오.

이번 수정에서도 실제 Production 앱 검증 전에는
절대 ‘완료’라고 보고하지 마십시오.

==================================================
1. 확정된 정상 동작 요구사항
==================================================

사진 A 한 장을 다음 위치에 동시에 사용할 수 있어야 합니다.

- 반 공통 일지
- 학생 1 개별 일지
- 학생 2 개별 일지
- 학생 3 개별 일지

정상 결과:

- 공통 일지에는 사진 A가 표시됨
- 학생 1 개별 일지에도 사진 A가 표시됨
- 학생 2 개별 일지에도 사진 A가 표시됨
- 학생 3 개별 일지에도 사진 A가 표시됨
- 서버 오류가 발생하지 않음
- 개별 사진이 공통 사진으로 이동하지 않음
- 다른 학생의 연결을 삭제해도 나머지 연결은 유지됨
- R2 실제 파일은 중복 복사하지 않음

동일 사진 선택을 UI에서 막는 방식은 금지합니다.

==================================================
2. Photo Clone 구조
==================================================

R2의 실제 파일은 1개만 유지하고,
photo_assets_meta의 연결용 row만 각 연결 대상별로 생성하십시오.

예시:

원본 row:
- id: photo_A
- object_key: photos/.../abc.jpg
- source_photo_id: NULL
- is_clone: false

공통 연결:
- 원본 row 또는 공통 전용 clone row 사용

학생 1 연결:
- id: photo_A_clone_1
- object_key: 원본과 동일
- source_photo_id: photo_A
- is_clone: true
- student_note_id: note_1
- student_id: student_1

학생 2 연결:
- id: photo_A_clone_2
- object_key: 원본과 동일
- source_photo_id: photo_A
- is_clone: true
- student_note_id: note_2
- student_id: student_2

학생 3도 동일한 방식으로 처리하십시오.

==================================================
3. DB 컬럼 추가
==================================================

photo_assets_meta에 아래 컬럼을 추가하십시오.

- source_photo_id text NULL
- is_clone boolean NOT NULL DEFAULT false

가능하면 source_photo_id는
photo_assets_meta.id를 참조하는 self FK로 구성하십시오.

기존 데이터는 모두:

- source_photo_id = NULL
- is_clone = false

상태로 유지되어야 합니다.

기존 데이터 손실이나 전체 재작성은 금지합니다.

==================================================
4. 원본 사진 식별 규칙
==================================================

클론의 클론이 계속 생성되지 않도록
항상 최상위 원본 사진을 식별하십시오.

규칙:

- source_photo_id가 NULL이면 자기 자신이 원본
- source_photo_id가 존재하면 그 source_photo_id를 원본으로 사용
- clone row를 다시 복제할 때도 최종 원본 ID를 source_photo_id로 저장

예:

photo_A
→ clone_1 source_photo_id=photo_A
→ clone_1을 다른 학생에게 연결 요청

새로운 clone_2도:

source_photo_id=photo_A

로 저장해야 합니다.

clone_1을 source로 저장하지 마십시오.

==================================================
5. 공통 사진 연결 처리
==================================================

attachPhotosToDiary에서 기존처럼 무조건:

student_id = NULL
student_note_id = NULL

로 기존 row를 덮어쓰지 마십시오.

사진이 이미 개별 일지에 연결된 상태라면
기존 row의 연결 정보를 공통으로 변경하지 말고,
동일 object_key를 사용하는 공통 연결용 clone row를 생성하십시오.

처리 기준:

A. 사진이 draft이고 아무 곳에도 연결되지 않은 경우
→ 기존 row를 공통으로 연결 가능

B. 이미 동일 일지의 공통 사진으로 연결된 경우
→ 성공으로 간주하고 중복 생성하지 않음

C. 이미 개별 일지 또는 다른 일지에 연결된 경우
→ 기존 row를 덮어쓰지 않고 공통 연결용 clone 생성

중요:

기존 개별 사진을 공통 사진으로 변환하면 안 됩니다.

==================================================
6. 개별 사진 연결 처리
==================================================

attachPhotosToStudentNote 처리 기준:

A. 사진이 아직 연결되지 않은 draft인 경우
→ 기존 row를 해당 학생 note에 연결 가능

B. 이미 동일 student_note_id에 연결된 경우
→ 성공으로 간주
→ 중복 row 생성 금지

C. 이미 공통 일지에 연결된 경우
→ 동일 object_key의 clone row를 생성하여 학생 note에 연결

D. 이미 다른 학생 note에 연결된 경우
→ 동일 object_key의 clone row를 생성하여 현재 학생 note에 연결

기존 row의 student_id와 student_note_id를
다른 학생 값으로 덮어쓰는 것은 금지합니다.

==================================================
7. Idempotency 및 중복 방지
==================================================

저장 버튼을 여러 번 누르거나
네트워크 오류 후 재시도해도
같은 연결 row가 계속 생성되면 안 됩니다.

논리적 중복 기준:

- 원본 사진 ID
- diary_id
- student_note_id
- student_id

동일 조합의 연결 row가 이미 있다면
새 clone을 만들지 말고 기존 연결을 성공으로 반환하십시오.

필요하면 idempotency를 위한 컬럼 또는
조회 후 INSERT 구조를 적용하십시오.

동시 요청에서도 중복이 생기지 않도록
트랜잭션 또는 DB 제약조건을 검토하십시오.

단순한 프론트 중복 방지만으로 처리하지 마십시오.

==================================================
8. 부분 실패 처리
==================================================

학생 1, 2, 3에게 같은 사진을 연결할 때
학생 2의 요청만 실패하더라도:

- 공통 사진 상태 유지
- 학생 1 연결 유지
- 학생 3 연결 유지
- 학생 2 연결만 실패 상태
- 다른 row의 scope 변경 금지

재시도 시에는
실패한 학생 2 연결만 다시 생성되어야 합니다.

저장 재시도 과정에서
공통 attach와 이미 성공한 학생 attach를 다시 실행하더라도
서버가 이를 정상적인 idempotent 요청으로 처리해야 합니다.

==================================================
9. 삭제 및 연결 해제 규칙
==================================================

가장 중요한 정합성 조건입니다.

연결 하나를 삭제한다고
공유 중인 R2 실제 파일을 바로 삭제하면 안 됩니다.

예:

사진 A를 학생 1, 2, 3이 사용 중일 때
학생 1의 연결을 삭제해도:

- 학생 2 사진 유지
- 학생 3 사진 유지
- 공통 사진 유지
- R2 object 유지

삭제 순서:

1. 대상 photo_assets_meta 연결 row 삭제 또는 detached 처리
2. 동일 원본 계열 row가 남아 있는지 확인
3. 사용 중인 row가 하나라도 있으면 R2 object 유지
4. 원본 및 모든 clone 연결이 완전히 제거된 경우에만 R2 삭제 가능

아래 API를 모두 점검하십시오.

- diary detach
- note detach
- bulk delete
- 일지 삭제
- 학생 개별 일지 삭제
- 사진 영구 삭제
- draft 정리 작업
- archived media 정리 작업

==================================================
10. 스토리지 사용량 계산
==================================================

같은 R2 파일을 공유하는 clone row의 file_size를
각각 합산하면 안 됩니다.

스토리지 사용량은 실제 R2 파일 기준으로 한 번만 계산하십시오.

권장 기준:

- source_photo_id IS NULL인 원본만 합산

단, 원본 row가 제거되고 clone만 남는 구조가 가능하다면
단순히 source_photo_id IS NULL 조건만 사용하면 누락될 수 있습니다.

따라서 실제 구현 구조에 맞춰 다음 중 하나를 선택하십시오.

A. 원본 row는 모든 clone이 제거될 때까지 유지

또는

B. object_key DISTINCT 기준으로 용량 계산

스토리지 계산 쿼리와 삭제 정책을 함께 제시하십시오.

==================================================
11. 수정 화면 복원
==================================================

일지 수정 화면에 다시 들어왔을 때
각 사진은 연결된 위치에 정확히 표시되어야 합니다.

- 공통 연결 row → 공통 사진 영역
- 학생 1 연결 row → 학생 1 개별 영역
- 학생 2 연결 row → 학생 2 개별 영역

object_key가 같다는 이유로
첫 번째 사진 한 장만 반환하거나
공통 사진으로 합치면 안 됩니다.

화면 복원은 photo row ID와 연결 정보 기준으로 처리하십시오.

동일 object_key를 가진 여러 row도
각 연결 위치별로 정상 반환되어야 합니다.

==================================================
12. 기존 오류 데이터 처리
==================================================

이미 오류가 발생하여
개별 사진이 공통 사진으로 저장된 기존 일지가 있을 수 있습니다.

자동으로 복구 가능한지 분석하십시오.

단, 근거 없이 공통 사진을 개별 사진으로 이동하지 마십시오.

복구에 필요한 student_note_id 정보가 DB나 로그에 남아 있지 않다면
자동 복구가 불가능하다고 명확히 보고하십시오.

기존 데이터 정리 스크립트는
실제 변경 전 대상 row 목록을 먼저 출력하는 dry-run 방식으로 작성하십시오.

사용자 승인 없이 Production 데이터를 일괄 수정하지 마십시오.
