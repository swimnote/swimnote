# [DIARY TEMPLATE → CURRICULUM MATERIALIZATION IMPLEMENTATION — MULTI-POOL CORRECTION]

중요 설계 정정.

Toykids는 최초 Production 검증 대상일 뿐이며
시스템의 curriculum source 기준이 아니다.

SWIMNOTE Parent Curriculum Search는
모든 X 수영장에 대해 tenant별로 독립적으로 작동해야 한다.

==================================================
1. 최종 권위 기준
==================================================

검색 요청 기준:

parent
→ selected student_id
→ server verifies student ownership
→ student's swimming_pool_id
→ 해당 swimming_pool_id의 실제 diary template set
→ 해당 pool의 curriculum_items
→ Parent Curriculum Search

절대로 Toykids template set을
다른 수영장에 공통 source로 사용하지 않는다.

parent가 임의 pool_id를 전달해서 scope를 바꿀 수 없게 한다.

server가 student relation에서 pool_id를 확정한다.

==================================================
2. SOURCE OF TRUTH
==================================================

각 수영장의 실제 커리큘럼 원본:

그 수영장이 "일지작성" 화면에서 실제 사용할 수 있도록
생성/등록된 diary_templates.

중요:

단순히

scope='global'

조건만 하드코딩하지 않는다.

현재 diary 작성 서버가
특정 pool에 대해 어떤 template들을 반환하는지
실제 existing resolver/query를 확인한다.

Parent Curriculum materializer는
가능하면 그와 동일한 effective-template selection rule을
공유하거나 재사용한다.

목표:

Teacher Diary가 보는 curriculum
=
Parent Curriculum Search가 보는 curriculum

==================================================
3. TENANT ISOLATION
==================================================

각 swimming_pool_id별 완전 분리.

예:

Pool A templates
→ Pool A curriculum_version
→ Pool A curriculum_items

Pool B templates
→ Pool B curriculum_version
→ Pool B curriculum_items

절대 금지:

- 다른 pool template 혼입
- 다른 pool curriculum_items 검색
- Toykids 데이터를 default fallback으로 사용
- global template를 모든 X pool에 무조건 공유
- pool 미등록 시 다른 pool curriculum으로 fallback

==================================================
4. MANAGED VERSION도 POOL별
==================================================

각 pool마다 diary-template managed version을 독립 관리.

예:

Pool A
(pool_A, diary-templates-v1)

Pool B
(pool_B, diary-templates-v1)

같은 version_name은 가능하나
swimming_pool_id가 다르면 별도 version.

식별 기준:

swimming_pool_id
+
managed version identity

기존 schema/constraint 확인 후 구현.

==================================================
5. MATERIALIZATION
==================================================

각 pool의 effective diary template:

1 template
→ 1 curriculum_item

mapping은 기존 계획 유지.

단 모든 item에는 반드시:

- swimming_pool_id
- curriculum_version_id
- source_template_id

가 정확히 연결되어야 한다.

source_template_id 단독 UNIQUE 금지 가능성 검토.

권장 duplicate protection:

(swimming_pool_id, source_template_id)
WHERE source_template_id IS NOT NULL

==================================================
6. ELIGIBILITY도 POOL별
==================================================

각 수영장마다 독립 계산.

해당 student's swimming_pool_id 기준:

active searchable curriculum_items >= 300
→ eligible=true

<300
→ CURRICULUM_NOT_READY

예:

A = 420 → eligible
B = 315 → eligible
C = 180 → NOT_READY

다른 pool item을 합산하여 300을 넘기는 것 절대 금지.

==================================================
7. AI SEARCH도 동일 POOL
==================================================

eligibility만 pool별이고
실제 검색이 global이면 안 된다.

반드시:

eligibility pool
=
curriculum search pool
=
student evidence pool

동일해야 한다.

즉 selected student의 pool_id가
전체 request lifecycle의 tenant authority.

==================================================
8. TEMPLATE 변경 동기화
==================================================

수영장 A의 template 변경:

→ A curriculum_items만 갱신.

수영장 B 영향 0.

신규 template
→ 해당 pool item upsert

수정
→ 해당 pool item update

inactive
→ 해당 pool item inactive

teacher/private override 등
실제 curriculum source가 아닌 template은
현재 diary resolver 정책에 맞게 제외.

==================================================
9. 최초 BACKFILL
==================================================

시스템은 특정 pool 전용으로 구현하지 않는다.

generic 함수 예:

syncDiaryTemplatesToCurriculumItems(poolId)

형태로 모든 X pool에서 재사용 가능해야 한다.

Toykids:

pool_1780849364252_l9k44rbk3

는 최초 Production 검증 대상으로만 사용.

Toykids-specific ID/condition을 코드에 하드코딩 금지.

==================================================
10. NORMAL / X 정책
==================================================

X pool:
effective curriculum >=300일 때 검색 허용.

Normal pool:
template가 아무리 많아도
Parent AI Curriculum Search 차단.

제품 정책 변경 없음.

==================================================
11. IMPORTANT AUDIT BEFORE IMPLEMENTATION
==================================================

구현 전에 매우 짧게 확인:

현재 일지작성 화면/server가

"이 pool에 보여줄 diary templates"

를 결정하는 정확한 resolver/query가 무엇인지 확인.

그 로직이 이미 함수화돼 있다면 재사용.

없다면 materializer와 diary route가
같은 selection helper를 공유하도록 최소 추출.

광범위 refactor 금지.
