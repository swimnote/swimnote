[학부모 연결 예외 승인 경로 — 범위 확정]

방금 작업 중단 지시는 취소한다.

현재 구현 중인 기능 중
“정상 자동가입 라인”은 절대 변경하지 않고,
자동연결에 실패하여 승인대기에 남은 학부모를 구조하는
예외 승인 경로만 구현한다.

━━━━━━━━━━━━━━━━━━━━━━
1. 정상 가입 라인은 절대 변경하지 않는다
━━━━━━━━━━━━━━━━━━━━━━

현재 Production에 배포 완료된 정상 경로:

SMS 인증
→ 인증 전화번호와 선택 수영장의 등록 보호자 전화번호 일치
→ 학생 이름 입력값과 무관하게 자동승인
→ 같은 전화번호의 형제/자매 자동연결
→ students.name으로 표시

이 경로는 현재 정상 동작하므로 수정하지 않는다.

기준 Production 기능:
52f5529195100034d79c5f87505a32d5b8d5d4ef

정상 자동연결 성공 사용자가
새 관리자 승인 경로를 거치게 만들면 안 된다.

━━━━━━━━━━━━━━━━━━━━━━
2. 이번 기능의 대상
━━━━━━━━━━━━━━━━━━━━━━

오직 정상 자동연결에 실패하여
승인대기 상태에 남은 학부모만 대상이다.

예:

- 수영장에 등록된 보호자 전화번호 오류
- 학부모 실제 인증번호와 등록번호 불일치
- 기존 회원정보 불일치
- 자동 matching 불가
- 기타 정상적인 자동승인 조건을 만족하지 못함

이런 사용자가 승인받지 못하고
계속 미연결 상태로 남는 문제를 해결한다.

━━━━━━━━━━━━━━━━━━━━━━
3. 학부모 요청 → 관리자 PUSH
━━━━━━━━━━━━━━━━━━━━━━

승인대기 학부모가 연결 확인/승인을 요청할 수 있게 한다.

요청 시:

현재 선택한 수영장의 관리자에게만
“학부모 연결 확인 요청” PUSH를 보낸다.

다른 수영장 관리자에게 보내면 안 된다.

중복 클릭으로 PUSH가 반복 발송되지 않도록
기존 알림 구조를 이용한 적절한 dedupe는 허용한다.

현재 구현한 10분 중복 방지가
이 목적만 수행한다면 유지 가능하다.

정상 자동가입 사용자에게는 이 PUSH가 발생하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
4. 관리자 승인 = 강제승인이 아니라 정보 확인 후 연결
━━━━━━━━━━━━━━━━━━━━━━

관리자가 승인대기 요청을 열었을 때
자동연결이 실패한 학부모의 정보를 확인할 수 있어야 한다.

목적은:

“자동승인이 왜 안 됐는지 확인하고,
수영장에 등록된 올바른 학생과 연결”

하는 것이다.

관리자가 확인할 수 있는 정보는
현재 시스템에 존재하는 필요한 최소 정보만 사용한다.

불필요한 개인정보를 새로 노출하지 않는다.

관리자가 선택/확인한 학생이
현재 관리자 자신의 pool 소속인지 서버에서 반드시 검증한다.

━━━━━━━━━━━━━━━━━━━━━━
5. 학생 선택 검색창 제거
━━━━━━━━━━━━━━━━━━━━━━

학생 이름 검색창은 제거한다.

- 검색 TextInput 제거
- 검색 state/filter 제거
- 자동 keyboard 호출 제거

필요한 학생 목록/정보는
키보드 없이 바로 확인 가능하게 한다.

단, 관리자가 올바른 학생을 확인할 수 있는
기존 학생 선택 기능 자체를 없애서는 안 된다.

━━━━━━━━━━━━━━━━━━━━━━
6. 정보 확인창은 허용
━━━━━━━━━━━━━━━━━━━━━━

현재 구현 중인 “정보 확인창”은
승인대기 예외 경로에서만 사용하는 조건으로 유지 가능하다.

관리자가 최종 연결 전에 최소한 다음을 구분할 수 있어야 한다.

- 학부모 요청 정보
- 인증된 전화번호가 있는 경우 그 인증 상태
- 선택하려는 수영장 등록 학생
- 수영장에 등록된 보호자 정보와의 일치/불일치 여부

중요:

계정에 적힌 전화번호를
SMS 인증된 번호인 것처럼 표시하면 안 된다.

인증 근거가 있는 번호와
단순 계정 등록 번호를 명확히 구분한다.

━━━━━━━━━━━━━━━━━━━━━━
7. 관리자 확인 후 승인
━━━━━━━━━━━━━━━━━━━━━━

관리자가 올바른 학생임을 확인하고 [확인/승인]했을 때만
guardian/student 관계를 생성한다.

서버에서 최종 저장 직전에 다시 확인:

- 요청이 아직 pending인지
- 관리자 pool과 학생 pool이 동일한지
- 학생이 실제 존재하는지
- 이미 동일 관계가 있는지
- 승인 대상 request와 선택 student가 유효한지

중복 관계 생성 금지.

다른 pool 학생 연결 절대 금지.

기존 approved 관계를 훼손하지 않는다.

학생 status를 임의로 변경하지 않는다.

기존 보호자 pointer를 임의로 덮어쓰지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
8. 전화번호 불일치는 이 예외 경로에서는 허용 가능
━━━━━━━━━━━━━━━━━━━━━━

중요한 정책 구분:

정상 자동승인:
SMS 인증 전화번호 일치가 필수.

관리자 수동 확인 승인:
전화번호 불일치 때문에 자동승인이 실패했더라도
관리자가 실제 회원정보를 확인하고
올바른 학생임을 명시적으로 확인했다면
연결할 수 있다.

즉 관리자 예외 승인에서
전화번호 불일치 자체를 무조건 승인 불가 사유로 만들지 않는다.

그렇지 않으면
수영장에 전화번호가 잘못 등록된 사용자를
구조할 방법이 없어지기 때문이다.

단,
전화번호 불일치 사실은 관리자에게 명확하게 보여준다.

자동으로 전화번호를 수정하지 않는다.
학생정보를 자동 변경하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
9. stale pending 정리는 별도로 제한
━━━━━━━━━━━━━━━━━━━━━━

이미 정상 자동연결되어 approved 관계가 존재하는데
과거 pending 요청만 남아 있는 경우에 한해서만
stale pending 정리를 허용한다.

반드시 각 행마다 다시 검증:

- 동일 parent
- 동일 student
- approved 관계 실제 존재
- 해당 pending이 그 관계와 명확하게 대응

하는 경우에만 정리한다.

추측 matching 금지.
이름 유사도 기반 정리 금지.
전화번호만 보고 임의 정리 금지.

조금이라도 애매하면 그대로 둔다.

대량 삭제 금지.

정리 전 대상 목록과 건수를 보고하고,
정리 후 동일하게 결과를 보고한다.

━━━━━━━━━━━━━━━━━━━━━━
10. 기존 구현 중 유지 가능한 것
━━━━━━━━━━━━━━━━━━━━━━

현재 중간보고의 다음 구현은
위 정책과 정확히 일치한다면 유지 가능:

- 승인대기 전용 정보 확인창
- 관리자 자신의 pool로만 요청/PUSH
- 10분 중복 PUSH 방지
- 승인 직전 서버 재검증
- 저장 실패 시 rollback
- 기존 승인 관계 보존
- 학생 status 미변경
- 보호자 pointer 미변경

하지만 정상 자동가입 경로까지
이 로직으로 변경하면 안 된다.

12. 검증
━━━━━━━━━━━━━━━━━━━━━━

반드시 최소 시나리오 검증:

A.
정상 SMS 전화번호 일치
→ 기존처럼 즉시 자동연결
→ 관리자 요청/PUSH 없음

B.
전화번호 불일치
→ 자동승인 안 됨
→ pending
→ 학부모 확인 요청
→ 해당 pool 관리자 PUSH

C.
관리자가 올바른 학생 확인
→ 승인
→ 관계 생성
→ pending 종료

D.
전화번호 불일치 상태라도
관리자가 회원정보를 확인하고 올바른 학생을 선택
→ 예외 승인 가능

E.
다른 pool 학생 선택
→ 서버 거절

F.
이미 approved 관계 존재
→ 중복 관계 생성 없음

G.
학생 status 변경 없음

H.
기존 보호자 pointer 변경 없음

I.
PUSH 요청 반복 클릭
→ 중복 발송 방지

J.
이미 정상 연결됐지만 stale pending만 존재
→ 명확한 동일 관계일 때만 정리

K.
애매한 stale pending
→ 유지

L.
학생 검색창 없음
→ 키보드 자동 표시 없음
→ 학생 확인/선택 가능
