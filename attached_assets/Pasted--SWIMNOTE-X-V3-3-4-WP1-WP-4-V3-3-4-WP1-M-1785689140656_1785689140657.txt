━━━━━━━━━━━━━━━━━━━━━━
1. Migration 사전 검증 쿼리 실행 시점 수정
━━━━━━━━━━━━━━━━━━━━━━

현재 사전 검증 쿼리는 다음 컬럼을 조회한다.

global_template_set_id

하지만 이 컬럼은 M-E-2에서 신규 추가되므로,
Migration 실행 전에는 존재하지 않아 쿼리 자체가 실패한다.

현재 쿼리:

SELECT id, scope, swimming_pool_id, global_template_set_id
FROM diary_templates
WHERE scope NOT IN ('global', 'teacher')
   OR swimming_pool_id IS NULL;

수정:

[1차 사전 검증 — M-E 실행 전]

SELECT id, scope, swimming_pool_id
FROM diary_templates
WHERE scope NOT IN ('global', 'teacher')
   OR swimming_pool_id IS NULL;

예상 결과: 0 rows

그다음 M-E-2에서 global_template_set_id 컬럼을 추가한 후,
CHECK 추가 직전에 2차 검증을 수행한다.

[2차 검증 — M-E-2 이후, M-E-3 이전]

SELECT id, scope, swimming_pool_id, global_template_set_id
FROM diary_templates
WHERE NOT (
  (
    scope = 'x_global'
    AND swimming_pool_id IS NULL
    AND global_template_set_id IS NOT NULL
  )
  OR
  (
    scope IN ('global', 'teacher')
    AND swimming_pool_id IS NOT NULL
    AND global_template_set_id IS NULL
  )
);

예상 결과: 0 rows

기존 데이터에서는 아직 x_global 행이 없으므로
기존 global/teacher 행의 정합성만 통과하면 된다.

━━━━━━━━━━━━━━━━━━━━━━
2. Migration 오류를 catch 후 계속 진행하는 구조 금지
━━━━━━━━━━━━━━━━━━━━━━

현재 M-E 예시는 각 명령에 다음 구조를 사용한다.

.catch((e) => console.error(...))

이 방식은 M-E-1이 실패해도 M-E-2~M-E-5가 계속 실행되어
부분 Migration 상태가 발생할 수 있다.

WP1 Migration에서는 각 단계의 오류를 삼키지 않는다.

금지:

await db.execute(...).catch(() => {});

권장:

try {
  await db.transaction(async (tx) => {
    await tx.execute(...);
    await tx.execute(...);
  });
} catch (error) {
  console.error('[SWIMNOTE X WP1 Migration failed]', error);
  throw error;
}

다만 PostgreSQL의 다음 명령은 Transaction 안에서 실행 가능한지
현재 Migration Runner 기준으로 확인한다.

- ALTER TABLE
- DO $$ 블록
- CREATE INDEX
- CREATE FUNCTION

전체 WP1을 하나의 대형 Transaction으로 묶기 어렵다면
최소한 의존성이 있는 묶음별로 실패 즉시 중단한다.

권장 묶음:

Group 1:
M-A ENUM
M-B swimming_pools 컬럼

Group 2:
M-C global_template_sets
M-D 인덱스
M-E diary_templates 변경·CHECK·FK

Group 3:
M-F audit_entity_versions
M-G audit_logs

Group 4:
M-H parent_ai_daily_usage
M-H2 parent_ai_usage_reservations

Group 5:
M-I growth_events
M-J growth_reports

어떤 단계든 실패하면 이후 단계 실행 금지.
로그만 남기고 성공처럼 서버를 시작하면 안 된다.

━━━━━━━━━━━━━━━━━━━━━━
3. Match Token key_id 테스트 충돌 수정
━━━━━━━━━━━━━━━━━━━━━━

현재 검증 순서는 다음과 같다.

1. key_id 지원 여부 검사
2. HMAC 검사

따라서 지원되지 않는 key_id로 변조하면
INVALID_MATCH_TOKEN이 아니라
MATCH_TOKEN_KEY_NOT_SUPPORTED가 먼저 반환된다.

현재 두 번째 테스트:

parsed.key_id = 'match_key_v2'
예상: INVALID_MATCH_TOKEN

이 테스트는 실제 구현 순서와 충돌한다.

수정:

[지원하지 않는 key 테스트]

key_id = 'match_key_v99'
→ MATCH_TOKEN_KEY_NOT_SUPPORTED

[서명 변조 테스트]

지원되는 key_id는 그대로 두고
confidence, curriculum_item_id, expires_at 중 하나를 변경한다.

예:

const parsed = decode(token);
parsed.confidence = 0.99;
const tampered = encode(parsed);

예상:
INVALID_MATCH_TOKEN

정책:

- 지원되지 않는 key_id는 KEY_NOT_SUPPORTED
- 지원되는 key_id이지만 payload 또는 hmac 변조는 INVALID_MATCH_TOKEN
- malformed token은 INVALID_MATCH_TOKEN

━━━━━━━━━━━━━━━━━━━━━━
4. Parent AI request_id 재시도·소유권 검증 보완
━━━━━━━━━━━━━━━━━━━━━━

현재 API 진입 코드에서는 request_id만 조회한다.

SELECT status
FROM parent_ai_usage_reservations
WHERE request_id = ...

하지만 동일 request_id가 다른 parent_account_id에 연결된 경우를
반드시 차단해야 한다.

조회 컬럼:

SELECT
  request_id,
  parent_account_id,
  usage_date,
  status
FROM parent_ai_usage_reservations
WHERE request_id = ...

검증:

existing.parent_account_id !== 현재 인증 parentAccountId
→ 409 REQUEST_ID_OWNERSHIP_MISMATCH

상태별 재시도 정책:

COMPLETED
→ 예외 코드 200을 throw하지 않는다.
→ 저장된 결과가 있으면 정상적인 멱등 응답 반환

RESERVED
→ 동일 요청이 처리 중이라는 응답
→ 409 REQUEST_ALREADY_IN_PROGRESS
또는 기존 처리 결과 polling 정보 반환

FAILED / BLOCKED / EXPIRED
→ 동일 request_id 재사용 금지
→ 새 request_id를 발급받아 다시 요청하도록 안내

또한 다음 경쟁 상태를 처리한다.

두 요청이 같은 request_id로 동시에 진입:

1. 둘 다 기존 행 없음 확인
2. 둘 다 INSERT 시도
3. 하나만 성공
4. 다른 하나는 PRIMARY KEY 충돌

PRIMARY KEY 충돌을 일반 500으로 처리하지 말고,
충돌 후 기존 reservation을 다시 조회하여 상태별 멱등 응답을 반환한다.

권장 방식:

INSERT INTO parent_ai_usage_reservations (...)
VALUES (...)
ON CONFLICT (request_id) DO NOTHING
RETURNING request_id;

반환 0 rows:
→ 기존 reservation 조회
→ parent 소유권 검증
→ 기존 상태에 맞는 응답

reservation 생성과 parent_ai_daily_usage.reserved_count 증가는
반드시 동일 Transaction 안에서 처리한다.
