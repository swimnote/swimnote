Critical UX Bug 최종 수정

이번 수정의 핵심 원칙

“일지 삭제”와 “새 일지 작성”은 완전히 독립된 사용자 명령입니다.

삭제 성공 후 작성 화면, 작성 모달, 빈 폼을 자동으로 열지 마세요.
사용자가 별도로 ‘일지 작성’ 버튼을 눌렀을 때만 새 작성 플로우를 시작해야 합니다.

현재 현상

1. 지난 일지에서 삭제 클릭
2. 잠시 화면이 멈춤
3. 삭제된 일지가 다시 보이거나 다른 일지 화면이 나타남
4. 관리자 모드 등 다른 화면을 다녀온 후에야 삭제된 것으로 보임
5. 삭제 직후 화면 상태가 불명확함
6. 삭제 후 작성 화면 또는 다른 화면으로 자동 전환됨

목표 동작

삭제 클릭
→ 확인
→ 삭제 중 표시
→ DELETE API 성공
→ 해당 일지 즉시 목록에서 제거
→ 서버 목록과 재동기화
→ 현재 지난 일지 화면 유지
→ 완료

삭제 후 새 작성 화면으로 자동 이동하지 않습니다.

필수 수정 사항

1. 삭제 중 UI 상태

confirmDelete()에 명확한 deleting 상태를 두세요.

삭제 시작 시:
- 삭제 버튼 비활성화
- 중복 클릭 차단
- 버튼 또는 해당 일지 카드에 ‘삭제 중…’ 표시
- 전체 화면이 멈춘 것처럼 보이지 않게 처리

삭제 중에는:
- write 모드 전환 금지
- edit 모드 전환 금지
- router 이동 금지
- 다른 modal 자동 표시 금지

2. 삭제 성공 후 즉시 화면 반영

DELETE API에서 성공 응답을 받은 직후:

- 삭제된 diary ID를 현재 화면 목록에서 제거
- selectedDiary가 해당 ID라면 null 처리
- editDiaryId가 해당 ID라면 null 처리
- diarySet에서 해당 diary 제거
- detail query cache 제거
- history/list query cache 갱신

사용자가 화면을 나갔다 돌아오거나 새로고침하지 않아도 즉시 삭제된 상태가 보여야 합니다.

3. 서버 재조회는 백그라운드 검증으로 처리

삭제 성공 후 서버 목록을 재조회하되,
재조회가 끝날 때까지 삭제된 일지를 다시 화면에 표시하지 마세요.

권장 순서:

DELETE 성공
→ 로컬 목록에서 즉시 제거
→ history 화면 유지
→ 백그라운드 refetch
→ 서버 결과로 최종 동기화

refetch 중 기존 stale 데이터가 잠깐 다시 나타나는 flicker가 없어야 합니다.

다음을 확인하세요.

- keepPreviousData
- placeholderData
- stale query cache
- useEffect의 setDiaries
- focus refetch
- 화면 진입 시 이전 cache 복원

삭제된 ID는 refetch 완료 전까지 tombstone 또는 deletedIds 상태로 차단해도 됩니다.

4. 삭제 후 화면 전환 전부 제거

confirmDelete(), useEffect, load(), 상태 분기에서 아래 로직을 전부 조사하세요.

- setView("write")
- setMode("write")
- router.push(...)
- router.replace(...)
- router.back()
- openWriteDiary()
- empty diary 자동 생성
- today diary 없음에 따른 자동 write 전환

삭제 성공이 원인이 되어 실행되는 위 로직은 제거하세요.

삭제 후 화면은 반드시:

- 삭제 전 보고 있던 history/list 화면
또는
- 해당 날짜의 일지 목록 화면

을 그대로 유지해야 합니다.

5. 빈 상태 화면

해당 날짜의 마지막 일지를 삭제했다면,
작성 폼을 자동으로 띄우지 말고 빈 상태를 보여주세요.

예시:

“이 날짜에 작성된 일지가 없습니다.”

그리고 별도의 버튼:

“일지 작성”

을 보여주세요.

이 버튼을 사용자가 눌렀을 때만 write 화면으로 이동합니다.

새 modal을 자동으로 띄우지 마세요.

6. 삭제 실패

DELETE 실패 시:

- 기존 일지는 화면에 그대로 유지
- 삭제 중 상태 해제
- 화면 이동 없음
- 작성 화면 전환 없음
- 오류 메시지만 표시

7. 비동기 상태 충돌 점검

다음 상태가 서로 덮어쓰지 않도록 확인하세요.

- deleting
- diaries
- diarySet
- selectedDiary
- editDiaryId
- currentView
- myDiaryExists
- React Query result
- useFocusEffect
- load()
- refetch()

특히 삭제 성공 후 늦게 끝난 이전 load() 요청이
삭제 전 데이터를 다시 setDiaries하는 문제가 없는지 확인하세요.

필요하면:
- request sequence ID
- AbortController
- deletedIds filter
- mutation timestamp

중 하나로 오래된 응답 반영을 막으세요.

필수 테스트

A.
지난 일지 삭제
→ 삭제 중 표시
→ 성공 직후 해당 일지 사라짐
→ 화면 이동 없음
→ 새로고침 없이 삭제 유지

B.
해당 날짜 마지막 일지 삭제
→ 빈 상태 화면 표시
→ 작성 폼 자동 표시 없음
→ ‘일지 작성’ 버튼만 표시

C.
삭제 성공 후 10초 대기
→ 삭제된 일지 재등장 없음

D.
삭제 성공 후 관리자 모드 이동 후 복귀
→ 계속 삭제 상태 유지

E.
삭제 직후 앱 화면 포커스 변경
→ stale 데이터 재등장 없음

F.
삭제 API 실패
→ 일지 그대로 유지
→ 작성 화면 이동 없음

G.
사용자가 삭제 후 직접 ‘일지 작성’ 클릭
→ 그때만 새 작성 화면 진입
→ 동일 날짜 새 일지 정상 작성

최종 보고서에 포함

1. 삭제 후 자동 화면 전환을 발생시킨 정확한 코드 위치
2. 삭제가 늦게 표시된 원인
3. stale 데이터가 다시 나타난 원인
4. 수정 파일
5. 삭제 성공 직후 UI 상태 변화 순서
6. 서버 refetch 처리 방식
7. A~G 테스트 결과

완료 기준

삭제 버튼을 누르면 사용자가 다른 화면에 다녀오지 않아도
삭제 성공 직후 해당 일지가 즉시 사라져야 합니다.

삭제 후에는 어떤 작성 화면이나 모달도 자동으로 나타나면 안 됩니다.

새 일지 작성은 오직 사용자가 별도의 ‘일지 작성’ 버튼을 눌렀을 때만 시작되어야 합니다.
