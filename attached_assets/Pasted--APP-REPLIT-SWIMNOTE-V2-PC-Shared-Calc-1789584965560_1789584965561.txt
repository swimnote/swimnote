2. Calculator와 Service를 분리
━━━━━━━━━━━━━━━━━━━━━━

기존 제안:

settlement-calculator.ts

추가는 승인합니다.

단 계산식만 공통화하고
각 route가 DB 조회를 따로 작성하게 두지 마십시오.

최종 구조 권장:

src/lib/settlement-calculator.ts

역할:
순수 계산만 담당.

- 날짜/slot 계산
- 학생 CAP
- student auto amount
- teacher allocation
- largest remainder
- aggregate

DB 접근 금지.

그리고:

src/lib/settlement-service.ts

추가 검토/구현.

역할:

- pool/month 기준 필요한 DB 데이터 로드
- students
- weekly_count
- pricing
- student_class_history
- class_groups
- completed makeup
- 저장된 monthly_settlements
- calculator 호출
- StudentCalculation 생성
- TeacherAggregation 생성
- PoolAggregation 생성

즉:

“무슨 데이터를 읽는가”
=
Settlement Service

“그 데이터로 얼마를 계산하는가”
=
Settlement Calculator

로 분리합니다.

3. ROUTE에 계산식 금지
━━━━━━━━━━━━━━━━━━━━━━

settlement.ts route handler는:

- 인증
- 권한
- month/teacher parameter validation
- Settlement Service 호출
- HTTP response

까지만 담당.

route 안에 다음 금지:

- pricing 계산식
- weekly_count 변환 계산
- CAP 계산
- teacher allocation 비율
- rounding
- student aggregation
- pool total 계산

이 모든 것은 Service/Calculator에서 처리.

4. 공통 핵심 함수 하나
━━━━━━━━━━━━━━━━━━━━━━

가능하면 핵심 진입점을 하나로 만드십시오.

calculatePoolSettlement({
  poolId,
  settlementMonth
})

결과:

{
  students,
  teachers,
  poolSummary,
  unpricedStudents

실제 함수명은 repository convention에 맞게 조정 가능.

GET /settlement/calculator
POST /settlement/save
GET /settlement/reports

가 서로 다른 계산기를 만들지 않고
동일한 계산 진입점을 재사용하는 것입니다.

5. SAVE는 클라이언트 금액을 신뢰하지 않음
━━━━━━━━━━━━━━━━━━━━━━

매우 중요.

APP/PC에서:

auto_amount
allocated_amount
final_amount

를 계산해서 서버에 보내고
그 값을 그대로 저장하는 구조 금지.

클라이언트가 보내야 하는 핵심은:

- settlement_month
- adjustment_amount
- adjustment_reason
- adjustment_memo

등 사람이 입력한 값.

서버는 저장 시:

1. 현재 Settlement Service로 AUTO 재계산
2. teacher allocation 재계산
3. 클라이언트 adjustment 결합
4. final amount 서버 계산
5. auto_amount_snapshot 저장
6. student_details snapshot 저장

해야 합니다.

즉 서버가 최종 금액을 확정합니다.

6. 다중 선생님 학생 — 확정 모델
━━━━━━━━━━━━━━━━━━━━━━

학생은 특정 선생님 한 명 소유라고 가정하지 않습니다.

순서:

1.
학생별 전체 regular slot 계산

2.
completed makeup 추가

3.
학생 전체 billable_count CAP

4.
학생 auto_amount 딱 1회 계산

5.
regular slot 비율로 teacher allocation

반드시:

SUM(
  student.teacher_allocations.allocated_amount
)
=
student.student_auto_amount

학생이 몇 명의 선생님 수업에 들어가도
월수강료 중복 발생 금지.

7. 보강 정책
━━━━━━━━━━━━━━━━━━━━━━

completed makeup:

학생의 billable_count에는 포함.

하지만 teacher revenue allocation ratio에는 제외.

예:

김선생 regular 3
박선생 regular 2
이선생 makeup 1

student service count:
6

매출 allocation:
김 : 박 = 3 : 2

이선생:
회원매출 배분 없음.

대신 별도 운영지표:

completed_makeup_performed_count = 1

표시 가능.
