[학부모 연결 자동승인 조건 변경 전 READ-ONLY 조사]

목적:
현재 학부모 가입/연결 승인 로직을 정확히 조사한다.

아직 수정하지 않는다.

최종적으로 변경하려는 정책은 다음과 같다.

━━━━━━━━━━━━━━━━━━━━━━
[확정하려는 정책]
━━━━━━━━━━━━━━━━━━━━━━

수영장에서 학생을 미리 등록할 때 저장해둔
학부모 전화번호와

학부모가 가입/연결할 때 인증한 전화번호가 일치하면

학생 이름 입력값과 관계없이 자동승인되도록 한다.

즉:

AUTO APPROVAL 핵심 조건 =
학부모 전화번호 일치

학부모가 가입 과정에서 입력한 학생 이름은
자동승인 여부를 결정하는 matching key로 사용하지 않는다.

연결 성공 후 학부모에게 보여주는 학생 이름은
학부모가 입력한 문자열이 아니라
수영장에 이미 등록된 student의 실제 이름을 사용한다.

예:

수영장 DB:

박하윤
학부모 전화번호 010-XXXX-1234

박유하
학부모 전화번호 010-XXXX-1234

학부모 가입:

전화번호 010-XXXX-1234
학생 이름 입력 "박하윤 박유하"
또는 이름 오타
또는 한 아이 이름만 입력

→ 이름 때문에 승인대기로 보내지 않는다.

→ 전화번호가 수영장 등록정보와 일치하므로
해당 전화번호에 연결된 실제 학생 record를 기준으로 연결한다.

→ 학부모 화면에서는

박하윤
박유하

처럼 수영장 DB의 실제 학생 이름으로 표시되어
형제/자매를 구분할 수 있어야 한다.

━━━━━━━━━━━━━━━━━━━━━━
1. 현재 구현 READ-ONLY 조사
━━━━━━━━━━━━━━━━━━━━━━

현재 Production 기준 source에서 다음 전체 경로를 추적한다.

학부모 회원가입
→ 전화번호 인증/정규화
→ 학생 이름 입력
→ 연결 요청 생성
→ 학생 후보 검색
→ 자동 matching
→ 자동승인 / 승인대기 판정
→ guardian/student 관계 생성
→ 학부모에게 학생 표시

정확한:

- 파일
- 함수
- API endpoint
- DB table/column
- matching 조건
- approval 조건

을 찾아라.

추측하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
2. 현재 자동승인이 막히는 정확한 이유
━━━━━━━━━━━━━━━━━━━━━━

첨부 화면에서 보이는 것처럼:

학부모 이름: 박하윤 박유하
학생 후보: 서윤희

등 이름 확인이 필요하다고 나오는 경우가
어떤 코드 조건 때문에 승인대기로 떨어지는지 찾는다.

특히 조사:

- student name exact match 여부
- guardian name match 여부
- phone match 여부
- phone normalization
- 한 전화번호에 여러 student가 있을 때 처리
- multiple candidate 처리
- ambiguous match 처리
- pending request 생성 조건
- 자동승인 조건

현재 이름이 어떤 matching key로 사용되는지 정확히 확인한다.

━━━━━━━━━━━━━━━━━━━━━━
3. 전화번호 기준 연결이 가능한 현재 DB 구조 확인
━━━━━━━━━━━━━━━━━━━━━━

수영장에서 학생 등록 시 저장하는 학부모 전화번호가
어느 table/column에 저장되는지 확인한다.

그리고 학부모 가입 시 인증된 전화번호와
동일한 방식으로 비교 가능한지 확인한다.

전화번호 normalization도 확인한다.

예:

01012345678
010-1234-5678
+82...

등이 현재 어떤 canonical format으로 비교되는지 확인한다.

새 전화번호 시스템을 만들지 않는다.

기존 normalization 함수를 재사용할 수 있는지 확인한다.

━━━━━━━━━━━━━━━━━━━━━━
4. 형제/자매 케이스 조사
━━━━━━━━━━━━━━━━━━━━━━

가장 중요하다.

동일한 학부모 전화번호가:

Student A
Student B

두 학생에게 등록돼 있을 경우
현재 DB 구조에서 두 학생 모두 안전하게 조회 가능한지 확인한다.

그리고 전화번호가 일치했을 때:

guardian
→ Student A
→ Student B

두 관계를 생성하는 것이
현재 relationship 모델/API에서 가능한지 확인한다.

이미 연결된 학생이 있으면 중복 관계를 만들지 않아야 한다.

학생마다 서로 다른 pool에 속하는 경우가 가능한지도 확인하고,
현재 pool isolation/연결 정책이 어떻게 처리하는지 보고한다.

이번 조사에서는 정책을 새로 만들지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
5. 학생 이름 표시 Source of Truth 확인
━━━━━━━━━━━━━━━━━━━━━━

학부모 APP에서 학생 이름을 표시할 때

현재:

가입 시 학부모가 입력한 이름

인지,

students table의 실제 등록 이름

인지 추적한다.

변경 후에는 반드시:

students의 수영장 등록 이름

이 표시 Source of Truth가 되어야 한다.

이미 그렇게 되어 있다면 수정할 필요 없다고 보고한다.

━━━━━━━━━━━━━━━━━━━━━━
6. 보안상 중요한 조건 확인
━━━━━━━━━━━━━━━━━━━━━━

정책 변경 후에도:

“아무 전화번호나 입력해서 다른 아이를 연결”

할 수 있어서는 안 된다.

반드시 조사:

학부모가 사용하는 전화번호가
실제 SMS/OTP 인증된 전화번호인지

그리고 자동연결에서 사용하는 번호가
그 인증 완료 전화번호인지.

사용자가 직접 텍스트 필드에 임의 입력한 번호만으로
자동승인되는 구조라면 반드시 BLOCKER로 보고한다.

이번 조사에서는 수정하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
7. 최소 수정안 작성
━━━━━━━━━━━━━━━━━━━━━━

코드는 아직 수정하지 않는다.

조사 결과를 바탕으로:

“전화번호 일치만 자동승인 matching key로 사용하고
학생 이름 입력은 승인 판정에서 제거”

하기 위해 실제로 수정해야 하는
최소 파일/함수만 제시한다.

중요:

관리자 승인관리 UI 변경 금지
학부모 UI 디자인 변경 금지
회원가입 전체 개편 금지
DB schema 변경은 정말 필요한 경우가 아니면 금지
학생 등록 방식 변경 금지
기존 연결된 guardian/student 관계 변경 금지
성장리포트 관련 변경 금지
AI ENGINE 관련 변경 금지
PC 기능 변경 금지
다른 승인 시스템 변경 금지

오직:

학부모 ↔ 학생 자동연결 승인 조건

만 대상으로 한다.

━━━━━━━━━━━━━━━━━━━━━━
8. 반드시 검증할 예상 시나리오
━━━━━━━━━━━━━━━━━━━━━━

수정은 하지 말고
현재 구조에서 아래 정책을 구현할 수 있는지 판단한다.

CASE A
수영장 학생:
박하윤 / parent phone 01011112222

가입 학부모:
인증 phone 01011112222
입력 학생명 박하윤

예상:
자동승인

CASE B
수영장 학생:
박하윤 / 01011112222

가입:
인증 phone 01011112222
입력 학생명 오타

예상:
자동승인
표시 이름 = 박하윤

CASE C
수영장 학생:
박하윤 / 01011112222
박유하 / 01011112222

가입:
인증 phone 01011112222
입력 학생명 "박하윤 박유하"

예상:
두 학생 모두 연결
표시 = 박하윤 / 박유하

CASE D
위 형제 데이터에서
학부모가 학생명 하나만 입력

예상:
전화번호 기준으로 두 학생 모두 연결 가능한지 조사

CASE E
전화번호 불일치
학생 이름만 정확히 일치

예상:
자동승인 금지

CASE F
전화번호 일치
학생 이름 완전히 다른 이름

예상:
자동승인
표시 이름은 수영장 DB 학생 이름

CASE G
인증되지 않은 임의 전화번호

예상:
자동승인 금지

CASE H
이미 한 학생이 동일 guardian에 연결됨

예상:
중복 relationship 생성 없이
나머지 해당 학생만 정상 연결
