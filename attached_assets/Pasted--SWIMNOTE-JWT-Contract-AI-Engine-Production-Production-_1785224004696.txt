JWT 발급 주체 확인 다음을 정확히 보고하십시오. - JWT를 누가 발급하는지 - SWIMNOTE 서버가 발급하는지 - 외부 인증 서비스가 발급하는지 - 앱이 직접 생성하는 구조인지 - access token과 refresh token이 각각 존재하는지 앱이 JWT를 직접 생성해서는 안 됩니다. 현재 실제 구현만 보고하십시오. ================================================== 3. JWT 최종 계약 추출 현재 실제 코드 기준으로 아래 항목을 확정하십시오. 필수 보고 항목 - 서명 알고리즘 - secret 또는 public key 방식 - issuer - audience - subject - expiration - clock tolerance - access token 만료시간 - refresh token 만료시간 - JWT Header 구조 - JWT Payload Claims - 사용자 ID claim 이름 - 센터 ID claim 이름 - 역할 claim 이름 - 권한 claim 이름 - 이메일 claim 존재 여부 - 토큰 버전 claim 존재 여부 값이 코드에 존재하지 않으면 미사용 이라고 보고하십시오. 추측하여 추가하지 마십시오. ================================================== 4. 실제 Payload 예제 보고 민감정보를 마스킹한 실제 구조로 보고하십시오. JWT Header 예시 { "alg": "실제 값", "typ": "JWT" } JWT Payload 예시 { "실제_claim": "마스킹된 실제 값" } 실제 토큰 원문은 보고하지 마십시오. secret, private key, 서명값도 절대 출력하지 마십시오. ================================================== 5. 사용자 및 역할 계약 확인 AI Engine이 Teacher Diary 요청 권한을 확인하려면 현재 앱의 역할 계약을 알아야 합니다. 다음을 실제 코드 기준으로 보고하십시오. - 운영자 role 값 - 선생님 role 값 - 학부모 role 값 - 슈퍼관리자 role 값 - 역할이 문자열인지 숫자인지 - Teacher Diary 호출이 허용되는 역할 - Whisper 호출이 허용되는 역할 - 센터 소속 확인 방식 - 사용자 활성 상태 확인 방식 새 role 이름을 만들지 마십시오. ================================================== 6. Authorization Header 계약 현재 앱이 API 요청 시 사용하는 형식을 보고하십시오. 예시 Authorization: Bearer <access_token> 다음을 확인하십시오. - Bearer 대소문자 - 공백 형식 - 토큰 저장 위치 - API Client가 자동 첨부하는지 - 로그인하지 않은 요청 처리 - 토큰 만료 시 처리 - 401 응답 시 처리 - refresh 후 재시도 여부 ================================================== 7.
