━━━━━━━━━━━━━━━━━━━━━━━━━━

가장 중요합니다.

관리자 “검수”와 “발송”은 서로 다른 개념입니다.

검수:
관리자가 리포트를 읽어봤는지 표시하는 상태

발송:
완성된 리포트를 학부모에게 공개하는 액션

따라서:

검수하지 않았다고 발송을 막지 않습니다.

관리자가 전체 선택 후 발송하면
선택된 “발송 가능한 완성 리포트”는
검수 여부와 관계없이 모두 PUBLISHED 처리되어야 합니다.

정책:

완성된 리포트
→ 검수 안 함
→ 발송 가능

완성된 리포트
→ 검수 확인
→ 발송 가능

검수 여부는 발송 eligibility 조건이 아닙니다.

2. 관리자 검수 상태를 발송 상태와 분리

4. UI 상태 의미 재정리
━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 “검수대기”와 “발송대기”가
별도 lifecycle처럼 보이는데,
이번 정책에서는 관리자 검수 여부가
발송 가능 여부를 결정하지 않습니다.

따라서 sendable report 표시:

→ “검수 대기”

admin_reviewed_at IS NOT NULL
→ “검수 확인”

→ “발송 완료”

DISCARDED / 발급 제외
→ 기존 의미 유지

FAILED

가능하면 기존 상단 KPI의

“검수 확인”

━━━━━━━━━━━━━━━━━━━━━━━━━━

“검수 여부”는 절대로 조건에 넣지 마십시오.

발송 가능 여부는
리포트가 실제로 완성되어 있는지만 봅니다.

canonical helper 하나를 만드십시오.

예:

isGrowthReportSendable(report)

최소 조건:

- 같은 pool
- deleted_at IS NULL
- 발급 제외 아님
- discarded 아님
- FAILED 아님
- AI 분석 진행 중 아님

- 시스템 validation 완료
- 이미 PUBLISHED가 아니라면 publish 가능

현재 lifecycle에 READY_TO_SEND가 canonical 상태라면
완료된 리포트는 시스템 단계에서
READY_TO_SEND까지 자동 도달해야 합니다.

관리자가 읽었는지는
READY_TO_SEND 전환 조건에 포함하지 마십시오.

“관리자가 아직 읽지 않음”이라는 의미로 사용되고 있다면
그 설계를 수정하십시오.

AI/system validation과
관리자 human read 여부는 분리하십시오.

그런데 기존 서버 구조에는
“선택한 report ID 목록”을 한 번에 보내는
정식 endpoint가 없는 이력이 있습니다.

APP에서 83건을 for-loop 돌며
개별 send API를 83번 호출하는 방식이면 제거하십시오.

한 번의 bulk request로 처리하십시오.

기존 endpoint를 확장하는 것을 우선:

POST /admin/growth-reports/bulk-send

body 예:

  "year": 2026,

report_ids가 있으면:
→ 그 ID들만 대상

report_ids가 없으면:
→ 해당 월 전체 sendable reports 대상
(기존 호환성 유지가 필요한 경우)

━━━━━━━━━━━━━━━━━━━━━━━━━━
7. Bulk Send는 DB Transaction으로 처리
━━━━━━━━━━━━━━━━━━━━━━━━━━

83개를 하나씩 HTTP send하지 마십시오.

서버에서 한 transaction으로:

BEGIN

1. report_ids를
   pool_id + id 조건으로 SELECT ... FOR UPDATE

2. cross-pool ID 제거/거부

3. sendable predicate 적용

4. sendable rows:
   product_status = PUBLISHED
   published_at = COALESCE(published_at, NOW())
   updated_at = NOW()

5. audit log 기록

COMMIT

그 후 학부모 notification/push 수행.

83건이면
한 번의 DB publish operation으로 끝나야 합니다.

━━━━━━━━━━━━━━━━━━━━━━━━━━
8. Push 실패와 “리포트 발송 실패”를 분리
━━━━━━━━━━━━━━━━━━━━━━━━━━

이 부분도 매우 중요합니다.

학부모에게 리포트가 공개되는 기준:

product_status = PUBLISHED
published_at IS NOT NULL

입니다.

Push token이 없거나
FCM/APNs push가 실패했다고 해서
리포트 발송을 FAILED로 롤백하지 마십시오.

순서:

DB PUBLISHED COMMIT
↓
Parent API에서 즉시 조회 가능
↓
notification row 생성
↓
push 전송 시도

push 실패:
- PUBLISHED 유지
- 발송완료 유지
- push 로그만 failed
- 필요하면 알림 재시도

즉:

“발송완료 83 / Push 실패 2”

는 가능하지만

“Push 실패 2 → 리포트 발송 실패 2”

가 되어서는 안 됩니다.

승인된 보호자가 0명이거나
push token이 없어도
리포트 자체는 PUBLISHED 처리됩니다.
