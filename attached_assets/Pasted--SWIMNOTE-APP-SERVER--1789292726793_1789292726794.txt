6. 과거 notification은 set-based INSERT
━━━━━━━━━━━━━━━━━━━━━━

JS loop로 리포트 하나씩 INSERT하지 마십시오.

가능하면:

INSERT INTO notifications (...)
SELECT ...
FROM growth_reports
WHERE
  student_id = ?
  AND swimming_pool_id = ?
  AND product_status = 'PUBLISHED'
  AND deleted_at IS NULL
ON CONFLICT (type, ref_id, recipient_id)
WHERE type = 'GROWTH_REPORT_PUBLISHED'
DO NOTHING
RETURNING ...

방식으로 한 번에 처리하십시오.

기존 partial unique index를 그대로 사용합니다.

DB migration 없음.

7. notification 날짜 — 매우 중요
━━━━━━━━━━━━━━━━━━━━━━

과거 리포트 notification을
승인일 기준 NOW()로 만들지 마십시오.

그렇게 하면 보호자 알림함에
과거 리포트 수십 개가 오늘 발급된 것처럼 보입니다.

각 notification:

created_at =
growth_reports.published_at

를 우선 사용.

published_at이 비정상적으로 NULL이면
해당 row는 PUBLISHED 정책 이상이므로
임의 NOW() 처리하지 말고 로그 후 skip 또는 기존 정책에 맞게 처리.

따라서 과거 알림은
알림함에서도 원래 발급 시점 순서에 위치해야 합니다.

━━━━━━━━━━━━━━━━━━━━━━
8. PUSH는 최신 1건만
━━━━━━━━━━━━━━━━━━━━━━

소급 notification 전체에 push 금지.

이번 backfill에서 실제 신규 INSERT된 notification 중
가장 최신 PUBLISHED report 1건만 push 후보로 사용합니다.

중요:

ON CONFLICT 때문에 신규 INSERT가 0건이면
push도 보내지 않습니다.

즉 이미 소급처리가 완료된 보호자를
재승인/API retry했다고 push가 또 가면 안 됩니다.

Push 문구는
최신 리포트가 반드시 “지난달”이라고 단정하지 마십시오.

권장:

제목:
“확인할 수 있는 성장리포트가 있습니다”

본문:
“아이의 성장리포트를 SWIMNOTE에서 확인해보세요.”

deep link:
해당 최신 Growth Report 또는
Growth Report History 화면

현재 앱 routing convention에 맞춰 결정.

11. 필수 테스트
━━━━━━━━━━━━━━━━━━━━━━

A.
학생에게 과거 PUBLISHED report 3개
신규 parent 승인
→ 과거 report 3개 전부 Parent History에서 조회
→ notification 3개 생성
→ created_at 각각 원래 published_at
→ push 1건만

B.
동일 parent 승인 API 재호출
→ notification 추가 0
→ push 추가 0

C.
기존 PUBLISHED 3개 중 notification 1개 이미 존재
→ 나머지 2개만 INSERT
→ 중복 0

D.
PUBLISHED 0개
→ notification 0
→ push 0
→ 승인 정상

E.
deleted report
→ notification 생성 금지

F.
PUBLISHED 아닌 report
→ notification 생성 금지

G.
다른 pool report
→ 생성 0

H.
한 학생 보호자 2명
→ 새로 승인된 parent만 backfill
→ 기존 parent에게 재push 금지

I.
한 parent가 형제 2명 승인
→ 학생별 독립 처리
→ cross-student 혼합 없음

J.
push token 없음
→ notifications 정상 생성
→ 승인 정상
→ hook 성공 취급 가능

K.
hook 내부 오류
→ parent approval 유지
→ 승인 API 정상 완료
→ 오류 로그 존재
