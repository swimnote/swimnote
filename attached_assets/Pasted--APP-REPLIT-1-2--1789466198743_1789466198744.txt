두 가지입니다.

기존에 논의했던 보강 “삭제/숨김” 기능은 만들지 마십시오.

1. 관리자 출결 관리 메뉴 제거

“출결 관리”

진입 메뉴만 제거하십시오.

출결 시스템 자체를 삭제하는 것이 아닙니다.

변경 금지:

- attendance DB
- attendance API
- Teacher 출결
- 성장리포트 출결 계산
- 기존 출결 데이터

관리자 메뉴 UI에서만 제거합니다.

2. 관리자 보강 역할
━━━━━━━━━━━━━━━━━━━━━━

기본 원칙은 그대로 유지합니다.

Teacher:
= 실제 보강 운영

- 일정 결정
- 반/시간 배정
- 변경
- 완료 등

Pool Admin:
= 전체 보강 감독 + 예외 상태조정

관리자는 여전히:

- 보강 날짜 배정
- 수업 스케줄에 직접 삽입

- 완료 처리

를 하지 않습니다.

단,

보강 권리의 최종 예외처리를 위해:

대기 ↔ 만료

상태만 수동 변경할 수 있습니다.

3. 자동 만료 정책 유지
━━━━━━━━━━━━━━━━━━━━━━

현재 수영장 보강정책에 따라:

대기
→ 유효기간 경과
→ 자동 만료

되는 기존 로직은 절대 변경하지 마십시오.

자동 만료 scheduler / policy / 계산식을
새로 만들거나 변경하지 않습니다.

기존 정책이 SoT입니다.

4. 관리자 수동 변경
━━━━━━━━━━━━━━━━━━━━━━

관리자 보강 화면에서:

[대기 상태]

→ “만료 처리”

가능.

[만료 상태]

→ “대기로 복원”

가능.

딱 이 두 방향만 허용합니다.

다음 상태는 이번 기능으로 변경하지 마십시오.

- 배정됨
- 진행중
- 완료
- 취소
- transfer/handover
- 기타 기존 operational status

즉:

PENDING / WAITING
↔
EXPIRED

에 해당하는 현재 실제 status 값만 사용하십시오.

먼저 현재 DB/code에서 사용하는 canonical status 이름을 확인하고
기존 값 그대로 사용하십시오.

새 status 이름을 임의로 만들지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
5. 만료 → 대기 복원 시 중요
━━━━━━━━━━━━━━━━━━━━━━

이미 만료된 보강은
기존 expire_at이 과거일 가능성이 있습니다.

단순히 status만 pending으로 바꾸면
다음 자동 만료 처리에서 즉시 다시 EXPIRED가 될 수 있습니다.

따라서 현재 자동 만료 구현을 먼저 확인하십시오.

만료 → 대기 복원 시:

해당 swimming pool의
현재 “보강 가능 기간” 정책을 그대로 재사용하여

복원 시점부터 정상적인 새 유효기간을 적용하십시오.

예:

기존 정책이 복원/발생 시점으로부터 N일 방식이라면
현재 동일 정책으로 expires_at을 재계산.

새로운 기간 규칙을 만들지 마십시오.

복원된 보강도 이후에는
다시 기존 자동 만료 정책의 적용을 받아야 합니다.

━━━━━━━━━━━━━━━━━━━━━━

기존 EXPIRED 상태로 변경하십시오.

원본 결석/보강 record는 삭제하지 않습니다.

Hard delete 금지.
