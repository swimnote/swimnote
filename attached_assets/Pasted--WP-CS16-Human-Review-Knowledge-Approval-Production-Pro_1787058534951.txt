[WP-CS16 — Human Review / Knowledge Approval & Production Promotion Governance]

목적:
CS12에서 생성된 PENDING Knowledge Candidate와
향후 Support Knowledge Candidate가
자동으로 ACTIVE가 되지 않고,

반드시 승인권한을 가진 사람이
근거 / Role / Mode / Scope / Action / Policy / Conflict / Freshness를 검토한 뒤

APPROVE
REJECT
REQUEST_EDIT

중 하나의 명시적 결정을 내려야만
운영 Knowledge로 승격될 수 있도록
Human-in-the-loop Knowledge Governance를 완성한다.

이번 WP의 핵심:

AI가 Knowledge를 생성할 수는 있다.
그러나 AI가 Production Truth를 스스로 확정할 수는 없다.

==================================================
0. 절대 원칙
==================================================

1. 새로운 OpenAI/LLM 호출 추가 금지.
2. CS12 PENDING 21개 Candidate를 자동 ACTIVE 처리 금지.
3. 이번 WP에서도 Production DB write 금지.
4. 테스트를 위해 실제 ACTIVE Knowledge를 변경하지 말 것.
5. 승인권한을 client claim으로 신뢰하지 말 것.
6. 승인/거절/수정 결정은 server-authoritative role 기준.
7. 승인 이력은 감사 가능해야 함.
8. 승인 전 Candidate는 retrieval/grounding에서 계속 제외.
9. 승인 과정에서 Role/Mode/Pool scope를 넓히지 말 것.
10. 불명확한 Candidate는 APPROVE가 아니라 REVIEW_REQUIRED.

==================================================
3. STATUS MODEL
==================================================

최소 상태:

PENDING
APPROVED
REJECTED
EDIT_REQUIRED
ACTIVE

가능하면:

ARCHIVED
SUPERSEDED

기존 schema와 충돌하지 않게 조정.

중요:

APPROVED와 ACTIVE를 반드시 분리할 필요가 있는지
현재 deployment workflow 기준으로 판단.

만약 승인 즉시 ACTIVE 구조가 더 단순하면:

PENDING
REJECTED
ACTIVE

로 유지 가능.

단,
어떤 경우든 PENDING→ACTIVE는
명시적 human approval 없이는 절대 불가.

==================================================
5. APPROVAL CHECKLIST
==================================================

APPROVE 전에 최소 검증:

SOURCE
- 근거 source 존재
- source가 candidate 내용 지원

IMPLEMENTATION
- 실제 앱/서버 기능 존재
- 존재하지 않는 메뉴/기능 없음

ROLE
- intended role 정확

MODE
- NORMAL/X/X_PENDING scope 정확

POOL
- global/pool-specific scope 정확

ACTION
- 안내 action이 실제 수행 가능

POLICY
- 환불/탈퇴/결제/권한 등 policy claim 검증

SECURITY
- 민감정보/내부정보 노출 없음

GROUNDING
- Candidate 내용이 source 범위를 초과하지 않음

CONFLICT
- 기존 ACTIVE Knowledge와 HARD conflict 없음

FRESHNESS
- source/version이 현재 유효

이 중 blocker가 있으면 APPROVE 불가.

==================================================
6. APPROVAL VALIDATION — SERVER SIDE
==================================================

UI 체크만 믿지 말 것.

APPROVE 요청 시 서버가 최소 재검증:

candidate exists
status == PENDING 또는 허용 상태
actor role allowed
role/mode/scope valid
candidate not already rejected/archived
no unresolved hard conflict
source/provenance exists if required

가능하면 transaction 사용.

동시 승인 요청에서도
중복 ACTIVE 생성되지 않게 함.

10. EDIT WORKFLOW
==================================================

Candidate 수정 기능이 있다면:

원본 candidate 내용을 덮어써
history를 잃지 않게 하는지 검사.

최소:

edited_by
edited_at

또는 audit history.

수정 후 자동 ACTIVE 금지.

수정된 Candidate는 재검토 필요.

==================================================
11. REJECT WORKFLOW
==================================================

REJECTED Candidate는:

- retrieval 제외
- grounding 제외
- approval queue에서 상태 분리
- 자동 재생성/자동 재활성화 금지

reason 기록.

예:

UNSUPPORTED_SOURCE
NOT_IMPLEMENTED
WRONG_ROLE
WRONG_MODE
POLICY_UNVERIFIED
DUPLICATE
CONFLICT
OUTDATED
SECURITY_RISK
OTHER

==================================================
12. EXISTING ACTIVE CONFLICT CHECK
==================================================

CS15 knowledge-governance 재사용.

Candidate 승인 전에:

HARD_CONFLICT
AUTHORITY_CONFLICT
VERSION_CONFLICT
CONTEXT_CONFLICT

검사.

HARD_CONFLICT unresolved:
APPROVE 금지.

VERSION_CONFLICT:
새 Candidate가 실제 최신 source인지 확인 후
기존 item supersede candidate로 처리.

자동으로 기존 ACTIVE 삭제/수정 금지.

==================================================
13. SUPERSEDE WORKFLOW
==================================================

새 Candidate가 기존 ACTIVE를 대체하는 경우:

new candidate
→ human approval
→ new ACTIVE

기존 Knowledge는:

ARCHIVED 또는 SUPERSEDED

처리를 명시적으로 수행.

가능하면:

supersedes_id
superseded_by_id

연결.

중간 상태에서 두 개가 동시에 ACTIVE가 되어
충돌하지 않도록 transaction 검토.

==================================================
16. GLOBAL VS POOL-SPECIFIC
==================================================

CS12 Candidate는 현재 scope=global.

global Candidate 승인권한과
향후 pool-specific Candidate 승인권한을 구분.

global:
super_admin/platform_admin only 권고.

pool-specific:
실제 정책이 정해져 있다면 별도 정의.

정책이 없으면:
NOT_IMPLEMENTED / REVIEW_REQUIRED.

임의로 pool_admin approval 권한 창작 금지.

18. SAFE ACTIVATION
==================================================

승인 후 Knowledge가 ACTIVE가 되는 코드 path가 있다면
반드시 확인:

status='active'
일 때만 retrieval.

PENDING→ACTIVE 후에만 검색됨.

같은 request transaction에서
approval과 retrieval이 race condition을 만들지 않는지 검사.

이번 WP에서는 production에 실제 활성화하지 않음.

fixture/mock DB에서만 검증.

19. ROLLBACK
==================================================

잘못 승인된 Knowledge를 되돌리는 경로 확인.

가능하면:

ACTIVE → ARCHIVED

또는 equivalent.

일반 user/teacher/pool_admin은 rollback 불가.

rollback도 audit log 남김.

Rollback 후 retrieval에서 즉시 제외.

27. ISSUE SEVERITY
==================================================

P0:
- unauthorized user can activate global Knowledge
- cross-pool approval/IDOR
- auto promotion without human approval
- malicious content activation path

P1:
- hard conflict candidate can become ACTIVE
- no-source candidate activation
- role/mode mismatch activation
- rejected candidate silently reactivated

P2:
- missing audit metadata
- incomplete revision history
- freshness review weakness

P3:
- UI/wording/reviewer UX

P0/P1 남으면 CS16_CLOSE = NO.
