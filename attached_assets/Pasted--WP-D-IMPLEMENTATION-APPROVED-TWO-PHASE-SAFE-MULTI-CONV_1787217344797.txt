2. getOrCreateConversation() 수정 — 중요
==================================================

현재:

INSERT ...
ON CONFLICT (parent_account_id, student_id)
DO UPDATE ...

구조는 UNIQUE 제거 후 사용할 수 없다.

WP-D에서 이 의존성을 제거한다.

conversation_id가 없는 구버전 요청의 fallback:

1. parent_account_id + student_id + status='active'
   기준 최신 conversation 조회

2. 존재하면 해당 conversation 사용

3. 없으면 신규 conversation 생성

즉 기존 앱은 계속
"최근/default conversation 하나"를 사용하는 것처럼 동작.

ON CONFLICT(parent_account_id, student_id)
의존 금지.

==================================================
3. FALLBACK CONCURRENCY
==================================================

conversation_id 없는 구버전 요청이 동시에 최초 진입할 경우
불필요한 conversation 여러 개가 생기지 않도록 보호한다.

가능하면 기존 transaction/pool 패턴 안에서:

- parent_account_id + student_id 단위 advisory lock
또는
- 동등한 최소 동시성 보호

사용 검토.

목적:

구버전 앱 fallback에서만
동시 최초 요청으로 conversation이 중복 생성되는 것을 방지.

새 대화 API는 의도적으로 복수 conversation 생성 가능.

==================================================
14. ROLLBACK 주의
==================================================

migration 후 실제 복수 conversation이 생성된 이후에는
기존 UNIQUE를 단순히 다시 추가할 수 없다.

따라서 rollback plan을:

"무조건 UNIQUE 재생성"

으로 보지 않는다.

Migration 직후,
아직 복수 conversation 생성 전까지만
UNIQUE 복원이 단순 rollback 가능.

복수 conversation 생성 이후 rollback 필요 시
데이터 보존 계획이 별도로 필요.

기존 conversation 삭제해서 UNIQUE 맞추는 방식 금지.
