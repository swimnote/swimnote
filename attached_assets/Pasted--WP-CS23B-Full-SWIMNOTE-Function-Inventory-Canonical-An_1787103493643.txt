[WP-CS23B — Full SWIMNOTE Function Inventory & Canonical Answer Database]

목적:

SWIMNOTE 전체 Repository를 실제 코드 기준으로 전수 조사하여

1. 전체 기능 Function Tree
2. 고객센터에서 답변해야 할 모든 Answer Topic
3. Canonical Answer 원본
4. 역할/모드/권한
5. 실제 UI 경로
6. 오류/복구
7. 정책 공백

을 완성한다.

이번 WP의 목표는:

“예상질문을 만드는 것”

이 아니라

“무엇에 대해 어떤 정답을 가지고 있어야 하는가”

를 완전히 확정하는 것이다.

이번 단계 완료 후 다음 WP에서
각 Canonical Answer에 대해 수천 개의 예상질문 Variant를 생성한다.

0. 절대 원칙
━━━━━━━━━━━━━━━━━━━━━━

1. 기억으로 기능 작성 금지.
2. 과거 기획서만 보고 현재 기능이라고 판단 금지.
3. 실제 Repository / DB schema / routes / screens / guards 기준.
4. 미구현 기능을 구현 기능으로 표시 금지.
5. UI 이름은 실제 label 확인.
6. 존재하지 않는 메뉴/버튼/경로 창작 금지.

11. STATIC KNOWLEDGE vs DYNAMIC DATA 구분
━━━━━━━━━━━━━━━━━━━━━━

매우 중요.

A. STATIC KNOWLEDGE

예:

“보강 신청 가능 기간은 어떻게 되나요?”

→ 정해진 규칙이면 Canonical Answer.

B. DYNAMIC DATA

예:

“우리 아이 보강 신청됐어요?”

→ 현재 DB 조회가 필요한 질문.

이런 질문은 Canonical Answer에
사용자 데이터를 저장하지 않는다.

대신:

answer_mode:
DYNAMIC_DB

가 현재 schema에 필요하다고 판단되면
이번 WP에서는 IMPLEMENTATION_PROPOSAL로만 기록.

Schema 변경은 하지 않는다.

Dynamic 질문 예:

내 아이 현재 진도
내 문의 상태
내 결제 상태
내 보강 신청 상태
현재 X entitlement
특정 회원 출결 상태

Static Answer와 반드시 분리.

23. 중복 제거
━━━━━━━━━━━━━━━━━━━━━━

비슷한 질문이 여러 기능에서 나온다고
정답을 무조건 복제하지 않는다.

예:

사진이 안 보여요

원인이:

parent student link
empty album
signed URL fail
network

등으로 다르면 분리 가능.

반대로 동일 해결법이면
하나의 Canonical Answer에
복수 utterance가 연결되도록 설계.
