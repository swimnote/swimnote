1. 현재 확인된 문제
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

문제 A.

현재 선생님이 학부모 요청 카드의

[업무 처리]

버튼만 눌러도 학부모 Push/알림이

"보강 요청이 처리됐습니다"
"상담 요청이 처리됐습니다"

형태로 전달된다.

하지만 업무 처리 버튼을 누른 시점은
실제 업무가 완료된 것이 아니다.

이 시점은:

"선생님이 요청을 확인했다"

는 의미여야 한다.

문제 B.

[업무 처리] 버튼이 연한 민트/반투명 형태라
disabled 버튼처럼 보인다.

활성 업무 버튼답게 네이비로 변경한다.

문제 C.

선생님 홈 우측 봉투 버튼은
새 쪽지/학부모 요청 미리보기만 보여준다.

미읽음이 0건이면 빈 Bottom Sheet만 보이고
과거 쪽지/처리된 학부모 요청을 보기 위해서는
설정 → 쪽지보관함으로 들어가야 한다.

홈 봉투 버튼에서도 항상
기존 쪽지보관함 전체 화면으로 들어갈 수 있어야 한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. 가장 중요한 상태 의미 분리
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

다음 3개를 절대 혼동하지 않는다.

READ / ACKNOWLEDGED
= 선생님이 요청을 확인함

DONE
= 실제 요청 업무가 처리 완료됨

REJECTED
= 요청을 처리하지 못함 / 거절

[업무 처리] 버튼을 누르는 것만으로
status를 done으로 만들면 안 된다.

업무 화면으로 이동하는 것도
done 처리가 아니다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. 업무 처리 버튼 클릭 시 동작
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 request가 unread인 경우:

[업무 처리]
↓
기존 read endpoint 실행

PATCH /teacher/parent-requests/:id/read

↓
is_read_by_teacher = true

↓
학부모에게 "확인 알림" 1회 생성/Push

↓
해당 request_type에 연결된 기존 업무 화면으로 이동

중요:

status = pending 유지.

done/rejected 변경 금지.

이미 읽은 요청에서 업무 처리 버튼을 다시 눌렀을 때는
같은 확인 알림을 또 보내지 않는다.

즉 확인 알림은 최초 unread → read 전환 시 1회만.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. 확인 알림 문구 — 요청 종류에 맞춤
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

request_type 실제 값:

absence
postpone
makeup
withdrawal
counseling
inquiry

각 타입별 사용자 표시명을 기존 REQUEST_TYPE label과 맞춘다.

최종 학부모 알림 예:

absence:
title:
"결석 신청을 확인했습니다"

body:
"선생님이 결석 신청을 확인했습니다."

postpone:
title:
"연기 신청을 확인했습니다"

body:
"선생님이 연기 신청을 확인했습니다."

makeup:
title:
"보강 요청을 확인했습니다"

body:
"선생님이 보강 요청을 확인했습니다."

withdrawal:
title:
"퇴원 신청을 확인했습니다"

body:
"선생님이 퇴원 신청을 확인했습니다."

counseling:
title:
"상담 요청을 확인했습니다"

body:
"선생님이 상담 요청을 확인했습니다."

inquiry:
title:
"문의를 확인했습니다"

body:
"선생님이 문의 내용을 확인했습니다."

현재 앱의 실제 한국어 label convention이 다르면
그 label을 그대로 재사용한다.

임의의 다른 명칭을 새로 만들지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. 실제 처리완료 알림은 그대로 유지
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

기존:

pending
→ done

일 때의

"보강 요청이 처리됐습니다"
"상담 요청이 처리됐습니다"

같은 결과 알림은 유지한다.

즉 학부모 입장에서는:

요청 전송
↓
선생님 최초 확인
→ "선생님이 보강 요청을 확인했습니다."

↓ 실제 업무 진행

처리 완료
→ "보강 요청이 처리됐습니다."

흐름이어야 한다.

REJECTED도 기존 결과 알림 유지.

확인 알림과 처리완료 알림은 서로 다른 이벤트다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. 확인 Notification DB 저장
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 notifications schema와 기존 INSERT pattern을 재사용한다.

새 DB schema 금지.

확인 알림은 기존 notifications에 저장해서
Push만 잠깐 보이고 사라지는 구조로 만들지 않는다.

논리적으로 별도 type 사용:

예:
parent_request_acknowledged

단 현재 notification type naming convention을 확인하고
동일 규칙을 사용한다.

ref_type:
request

ref_id:
requestId

학부모가 알림을 눌렀을 때
기존 요청 화면 / 내 요청 탭으로 연결 가능해야 한다.

중복 방지:

is_read_by_teacher false → true
실제 최초 전환에서만 INSERT + Push.

이미 true면 재전송 금지.

시간 기반 1시간 중복 방지보다
read transition 자체를 기준으로 한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
7. 기존 read endpoint 재사용 우선
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재:

PATCH /teacher/parent-requests/:id/read

handler를 확인한다.

가장 단순한 구조는 이 handler에서:

기존 row 조회
↓
previous is_read_by_teacher 확인
↓
false인 경우 read UPDATE
↓
확인 notification INSERT
↓
Push
↓
response

이다.

단 기존 read endpoint의 다른 정상 기능을
망가뜨리지 않는다.

별도 신규 endpoint는 불필요하면 만들지 않는다.

17. 구현 CASE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CASE 1

→ 선생님 unread 표시

CASE 2
보강 요청 최초 [업무 처리]
→ is_read_by_teacher=true

CASE 3
CASE 2 직후 학부모 Push:
"보강 요청을 확인했습니다"
"선생님이 보강 요청을 확인했습니다."

업무 처리 버튼 클릭만으로
status done 되지 않음

→ 확인 Push 중복 없음
