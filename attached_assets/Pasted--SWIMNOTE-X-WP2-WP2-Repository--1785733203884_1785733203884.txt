# SWIMNOTE X — WP2 최종 보완 지시 (최종 검수)

WP2 최종 정정 설계서를 검토했습니다.

전체 구조는 적절하며 Repository 조사도 충분합니다.

다만 아래 항목은 구현 전에 반드시 수정하거나 확인해야 합니다.

코드 수정은 하지 말고 **설계서만 최종 보완하여 다시 제출**하십시오.

---

## 1. GET /pools/x-mode의 super_admin 설계 재검토

현재 설계:

```text
super_admin
→ ?pool_id 필수
```

Repository 조사 결과만으로는

```
super_admin가 query parameter로 조회해야 한다.
```

는 근거가 없습니다.

확인하십시오.

* 기존 super_admin Route들은 query 사용인지
* path parameter 사용인지
* body 사용인지

Repository 패턴과 동일하게 맞추십시오.

WP2에서 새로운 규칙을 만들지 마십시오.

---

## 2. Error.code 사용 방식 검토

현재 설계

```ts
const err = new Error(...)
err.code = ...
```

Repository에서 실제 사용하는 패턴인지 확인하십시오.

만약 Repository에

```
throw new Error(...)
return res.status(...)
```

패턴만 존재한다면

Error.code를 새로 도입하지 마십시오.

가능하면 Route 내부에서 직접 분기하는 구조를 사용하십시오.

---

## 3. correlation_id 생성 방식

현재

```
crypto.randomUUID()
```

를 생성하도록 되어 있습니다.

Repository에는 correlation_id 생성 규칙이 존재하지 않습니다.

따라서

WP2에서는

```
correlation_id = null
```

로 두는 것이 더 일관적인지,

아니면 UUID 생성이 필요한지

장단점을 비교하여 최종 선택 근거를 작성하십시오.

새로운 표준을 만드는 것은 최소화하십시오.

---

## 4. ip_hash 생성 방식 확인

현재

```
sha256(clientIp)
```

를 사용하도록 되어 있습니다.

하지만 조사 내용에는

auth.ts에서 salt(id)를 함께 사용하는 코드도 존재합니다.

다음을 확인하십시오.

* audit_logs에서 사용하는 ip_hash 규칙이 기존에 있는지
* 단순 sha256인지
* salt 포함인지

기존 규칙이 있다면 그대로 재사용하십시오.

새 규칙을 만들지 마십시오.

---

## 5. request_id = null 정책

현재는

```
request_id = null
```

입니다.

다음을 확인하십시오.

Repository에서

```
x-request-id
request-id
```

헤더를 사용하는 공통 미들웨어가 있는지 조사하십시오.

없다면 null 유지.

있다면 기존 방식을 그대로 재사용하십시오.

## 6. xmode-guard 위치 확인

```

```

```
middlewares/auth.ts
```

아니면 개별 파일로 분리하는 패턴인지

확인 후

기존 구조를 따르십시오.

파일 수를 불필요하게 늘리지 마십시오.

## 7. Route 위치 최종 확인

GET /x-mode를

```
GET /my-pools 이후
```

삽입한다고 되어 있습니다.

최종 확인하십시오.

삽입 위치 기준:
