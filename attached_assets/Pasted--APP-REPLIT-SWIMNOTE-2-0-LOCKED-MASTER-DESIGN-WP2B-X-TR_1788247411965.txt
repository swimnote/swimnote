==================================================
0. LOCKED X TRIAL POLICY
==================================================

X Trial은 다음 정책으로 최종 확정되어 있습니다.

센터당 최초 1회.

기간:
3일

자동 유료전환:
NO

결제수단 사전등록:
NO

RevenueCat 표준 Trial:
사용하지 않음

구현 방식:
SERVER-SIDE GRANT

Trial의 목적:

"센터 전체 X 구축 체험"이 아니라
"즉시 사용 가능한 AI 기능 체험"

입니다.

==================================================

별도 센터 맞춤 구축 없이 즉시 사용할 수 있는 기능만 허용합니다.

예:

- AI 일지
- 공통 전문 DB 기반 AI 기능
- 즉시 가능한 학부모 AI 기능
- 기존 데이터 기반 AI 분석
- X 기능 Preview
- 샘플/체험 성장분석

중요:

실제 어떤 기능을 열지 현재 XModeGuard / route 구조를 기준으로
최소 안전범위로 구현하십시오.

Replit이 임의로 Trial 기능을 추가하지 마십시오.

2. X TRIAL에서 금지할 기능
==================================================

Trial에서는 아래 센터 맞춤 구축 작업을 절대 허용하지 않습니다.

- 센터 커리큘럼 입력
- 센터 커리큘럼 업로드
- 센터 교육체계 구축
- 센터별 커리큘럼 매핑
- X 전용 템플릿 세팅
- 센터 맞춤 성장체계
- 센터별 데이터 구축
- 정식 성장리포트 발급 설정
- 기타 운영자/사람의 수동 세팅이 필요한 X 구축

결제 성공 후에만:

X_SETUP_PENDING
→ 센터별 세팅
→ X_SETUP_ACTIVE

흐름으로 진행.

4. X TRIAL DB MODEL
==================================================

swimming_pools에 최소한 다음 컬럼을 추가하십시오.

x_trial_started_at TIMESTAMPTZ NULL
x_trial_ends_at TIMESTAMPTZ NULL
x_trial_used_at TIMESTAMPTZ NULL

의미:

x_trial_started_at
= 현재 Trial 시작시각

x_trial_ends_at
= Trial 만료시각

x_trial_used_at
= 이 센터가 Trial을 한 번 사용했음을 영구적으로 기록

중요:

센터당 1회 제한 때문에
Trial 종료 후 x_trial_started_at / ends_at를 초기화하더라도
x_trial_used_at은 유지되어야 합니다.

Trial 재사용 방지 source of truth:

x_trial_used_at IS NOT NULL

5. TRIAL 활성화 조건
==================================================

신규 endpoint:

POST /billing/x-trial-activate

또는 현재 route naming convention에 맞는 최소 endpoint.

활성화 가능 조건:

- authenticated admin/operator
- 해당 pool 권한 보유
- x_trial_used_at IS NULL
- 현재 X paid entitlement 없음
- current X manual entitlement 없음
- x_force_disabled 상태가 아님
- 이미 active trial 상태 아님

조건 위반 시 명확한 error code 반환.

예:

X_TRIAL_ALREADY_USED
X_TRIAL_ALREADY_ACTIVE
X_TRIAL_NOT_AVAILABLE_WHILE_PAID
X_TRIAL_FORCE_DISABLED

실제 naming convention에 맞추되 의미는 유지.

==================================================
6. TRIAL 시작 처리
==================================================

Trial 시작 시 하나의 transaction으로:

x_trial_started_at = NOW()
x_trial_ends_at = NOW() + INTERVAL '3 days'
x_trial_used_at = NOW()

설정.

중요:

x_manual_entitlement=true를 Trial 자체의 source of truth로 쓰지 마십시오.

이유:

manual entitlement는 기존 super-admin 수동 X 권한과 의미가 다릅니다.

Trial 여부는 반드시
x_trial_started_at / x_trial_ends_at / x_trial_used_at
기준으로 구분하십시오.

기존 x_manual_entitlement semantics를 오염시키지 마십시오.

7. TRIAL ACTIVE 판단
==================================================

공통 helper/selector를 두는 것을 우선.

개념:

isXTrialActive(pool) =
x_trial_started_at IS NOT NULL
AND x_trial_ends_at > NOW()
AND x_force_disabled = false
AND x_paid_entitlement = false
AND x_manual_entitlement = false

기존 paid/manual 권한이 있으면
Trial보다 항상 우선.

권한 우선순위:

1. force_disabled
2. paid/manual entitlement
3. x_trial active
4. normal/basic

기존 실제 코드 우선순위가 있으면
최소 변경으로 맞추되 이 의미를 유지.

8. TRIAL 만료 방식
==================================================

중요:

Trial 만료를 반드시 background worker에만 의존하지 마십시오.

3일이 지나면
다음 API 요청/Mode 조회 시에도
즉시 expired로 판단되어야 합니다.

즉 source of truth:

x_trial_ends_at <= NOW()
→ Trial inactive

worker/cron은 cleanup 또는 상태정리 보조수단일 뿐.

worker가 죽어도 Trial이 계속 열리는 구조 금지.

필요하면:

lazy expiration
+
optional cleanup job

구조 사용.

11. PAID 사용자의 Trial 금지
==================================================

이미 X paid/manual 권한이 있는 센터가
Trial endpoint를 호출하면 거부.

Trial은 결제 전 체험용.

기존 paid X 사용자가:

해지
→ 만료
→ Trial 요청

하더라도 x_trial_used_at 상태와 별개로,
Trial 최초 사용 여부 정책만 적용.

단 과거 Trial을 안 썼더라도
이미 X를 유료 사용한 센터에게 무료 Trial을 허용할지는
LOCKED DESIGN상 "최초 체험" 목적에 맞지 않으므로
유료 X 구매 이력이 있는 센터는 Trial 불가로 처리하십시오.

가능한 source:

xmode_purchased_at IS NOT NULL
→ Trial unavailable

26. 1.6.3 BACKWARD COMPATIBILITY
==================================================

1.6.3 앱은 x_trial을 모릅니다.

따라서 기존 1.6.3 response contract가
x_trial 때문에 깨지면 안 됩니다.

원칙:

- 기존 필드 삭제 금지
- enum 강제 변경으로 parsing crash 금지
- 기존 앱이 모르는 신규 field는 additive
- 기존 앱이 mode 문자열을 strict parsing한다면
  1.6.3 endpoint에는 기존 compatible mode를 유지하는 방법 검토

매우 중요:

2.0 앱은 x_trial을 인식해야 하지만
1.6.3 앱이 `mode="x_trial"` 때문에 깨질 가능성이 있다면
API version/client compatibility를 확인하고 안전하게 처리.

완료보고에 반드시:

1.6.3 MODE COMPATIBILITY

를 별도로 기술.
