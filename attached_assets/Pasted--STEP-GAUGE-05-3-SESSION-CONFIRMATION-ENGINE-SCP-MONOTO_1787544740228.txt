5. 3-SESSION CONFIRMATION RULE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

핵심 제품 규칙:

서로 다른 실제 lesson_session 3회가
어떤 rank P 이상에서 관찰되면
P를 confirmed rank로 인정.

예:

[56, 70, 87]
→ 56 이상 3회
→ confirmed rank = 56

[56, 70, 70, 87]
→ 70 이상 3회
→ confirmed rank = 70

[78, 81, 85]
→ 78 이상 3회
→ confirmed rank = 78

[70, 87]
→ 2회뿐
→ 아직 새로운 confirmed 없음

구현 권장:

ranks DESC unique candidate 순회

각 candidate P에 대해:
count(r >= P)

최초 count >= 3인
가장 높은 P 선택.

또는 수학적으로 동일한 더 단순한 구현이 있으면 사용 가능.
단 결과가 정확히 동일해야 함.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. Active Version Percent

activeConfirmedPct:

activeConfirmedRank / activeConfirmedTotal * 100

1-decimal rounding.

activeConfirmedTotal은
현재 active version의 실제 active curriculum item count.

raw sort_order 사용 금지.

GAUGE-02 rank calculator 원칙과 동일한
1-based rank 좌표계 사용.

8. 동일 Version Monotonic
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

같은 curriculum version 안에서도
display gauge는 내려가지 않는다.

예:

existing:
active rank 70
display 70%

CPO 수정/삭제 후 newly computed:
active rank 50

raw active factual position은
현재 유효 evidence 기준 50으로 재계산 가능.

하지만:

display_confirmed_pct
→ 기존 70% 유지

즉:

activeConfirmedRank / activeConfirmedPct
= 현재 유효 3-session evidence 기준 factual confirmed position

displayConfirmedPct
= 학부모에게 보여주는 lifetime monotonic progress

둘을 혼동 금지.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. Cross-Version Monotonic
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

절대 rank 비교 금지.

예:

old version:
140 / 200 = 70%

new version:
200 / 400 = 50%

새 rank가 더 커도 display는 70% 유지.

공식:

displayConfirmedPct =
MAX(
  existing.display_confirmed_pct,
  newlyComputedActivePct
)

version 변경 감지 시:

prev_curriculum_version_id
= old active version

prev_display_pct
= old display percent

active_curriculum_version_id
= new version

새 version session < 3이면:
active rank = 0
active pct = 0
display = old display 유지

GAUGE-04 mapper 성공 이후
해당 student/pool의 confirmation을 재계산하도록 연결.

필요 시:

CREATE:
CPO upsert 성공
→ computeConfirmedProgress()

EDIT:
CPO recompute 성공
→ computeConfirmedProgress()

DELETE:
CPO invalidate/recompute 성공
→ computeConfirmedProgress()

중요:
현재 GAUGE-04가 diary 저장 안정성을 위해
fire-and-forget 정책을 사용하고 있음.

기존 Diary 저장 전체를
Gauge 오류 때문에 실패시키지 않는 원칙 유지.

즉 confirmation failure:
- diary 저장 rollback 금지
- structured error log
- gauge만 stale 상태 가능
- 재계산 가능하도록 idempotent 구현

기존 production Diary 안정성 우선.

12. Race / Idempotency
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

동일 student에 거의 동시에
수업 저장이 들어올 수 있음.

SCP UPSERT가 race로
display progress를 낮추면 안 됨.

DB UPDATE에서 가능하면:

display_confirmed_pct =
GREATEST(
  student_curriculum_progress.display_confirmed_pct,
  EXCLUDED.display_confirmed_pct
)

형태로 DB 레벨 monotonic 보호.

application에서 read→MAX→write만 하는 방식은
race 위험 있으므로 피한다.

active version fields 역시
최종 계산 시점 consistency가 깨지지 않도록
현재 project transaction/UPSERT pattern 사용.
