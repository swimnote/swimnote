[검증 허위 보고 정정 및 최종 작업 지시]

이전 완료 보고 중 다음 표현은 사실과 다릅니다.

“실기기에서 /api/v1/teacher-diary/generate 호출 성공 증거”

실제로 수행한 것은:
- grounded-test.ts로 서버 API 직접 호출
- HTTP 200 확인
- OTA 업로드 확인

수행하지 않은 것은:
- 실기기 OTA 수신 확인
- 실기기 AI 버튼 요청 확인
- 실기기 요청의 Render 로그 확인
- 실기기 Grounded Pipeline 진입 확인

따라서 앞으로 다음 용어를 엄격히 구분하십시오.

1. CODE_VERIFIED
코드만 확인한 상태

2. SCRIPT_VERIFIED
테스트 스크립트로 서버를 직접 호출한 상태

3. OTA_PUBLISHED
EAS 서버에 OTA가 업로드된 상태

4. DEVICE_APPLIED
실기기에서 해당 updateId가 실행 중인 상태

5. DEVICE_REQUEST_VERIFIED
실기기 버튼 요청이 운영 서버 로그에 실제 수신된 상태

6. DEVICE_E2E_VERIFIED
실기기 생성 → 결과 → 삽입 → 저장 → 재조회까지 확인된 상태

서로 다른 단계를 완료처럼 합쳐서 보고하지 마십시오.

현재 정확한 상태:

- 코드 grounded 설정: CODE_VERIFIED
- 정식 V1 API 서버 호출: SCRIPT_VERIFIED
- Production OTA: OTA_PUBLISHED
- 실기기 OTA 적용: 미확인
- 실기기 V1 요청: 미확인
- 실기기 Grounded Pipeline: 미확인
- 실기기 저장 E2E: 미확인

2. 실기기 증거 기준
==================================================

실기기 성공으로 인정하려면 반드시 다음이 있어야 합니다.

- 기기 실행 updateId
- OTA iOS Update ID와 일치
- 실제 버튼 탭 시 생성된 request_id
- Render 운영 로그의 동일 request_id
- request path=/api/v1/teacher-diary/generate
- AUTH_SUCCESS
- REQUEST_VALIDATED
- GroundedPipelineRunner 진입
- generation_mode
- template_ids
- knowledge_ids
- RESPONSE_SENT

스크립트 호출 request_id를 실기기 request_id처럼 보고하지 마십시오.

==================================================
3. Grounded Pipeline 품질 수정
==================================================

현재 SCRIPT_VERIFIED A/B/C 결과에는 다음 문제가 있습니다.

A. “자유형”
- 입력에 없는 발차기·호흡·자세·스트로크·태도 생성
- TEMPLATE_ASSISTED 과잉 판정

B. 배영 발차기 + 학생 다리 통증
- 입력에 없는 향상·연습 권고·부상 예방 추론

C. 학생 무릎 굽힘
- 학생 개인 오류가 공통 일지에 혼입
- 입력에 없는 자세·개선·추가 교정 생성

다음 원칙을 코드로 강제하십시오.

- candidate와 used template 분리
- 실제 사용 template_ids는 TOP_K_USAGE 기준
- 사용 기준 미달이면 INPUT_ONLY
- 학생별 관찰은 common에 포함 금지
- 학생 관찰이 없으면 학생별 내용 생성 금지
- Template 내용 전체 복사 금지
- 교사 입력과 실제 근거의 교집합만 사용
- 입력에 없는 태도·향상·다음 계획 생성 금지

==================================================
4. template_ids 검증
==================================================

모든 요청에서 반복된 tpl_0~tpl_4가 실제 DB ID인지 확인하십시오.

각 ID에 대해:
- DB row 존재
- table
- center_id
- title
- score
- matched fields
- 실제 prompt 사용 여부

mock, fixture, placeholder이면 운영 경로에서 제거하십시오.

candidate_ids와 실제 used template_ids를 분리하십시오.

==================================================
5. 검증 결과 정직하게 표시
==================================================

grounding_validation score=0.5인데 PASS로 쓰는 방식은 금지합니다.

다음을 명확히 보고하십시오.

- score 범위
- PASS threshold
- WARNING threshold
- FAIL threshold
- unsupported claim 수
- student-to-common leak 수
- invented evaluation 수
- invented next plan 수

HTTP 200 유지 여부와 검증 status는 별개입니다.
