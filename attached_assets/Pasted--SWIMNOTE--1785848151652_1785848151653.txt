[SWIMNOTE 보강 만료 표시 정책 — 기간이 지나도 목록 유지하도록 수정]

정책을 최종 확정한다.

현재 보강 정책의 만료일 계산 기능은 그대로 유지한다.

- 이번 달 말까지
- 다음 달 말까지
- 고정 일수
- 주당 수업 횟수별 월간 보강 한도

위 정책 설정과 expire_at 계산은 수정하지 않는다.

변경할 핵심 정책:

보강 만료일이 지나도 보강 세션을 삭제하거나
보강 대기 목록에서 완전히 숨기지 않는다.

기간이 지난 보강은 기존 목록에 계속 표시하고
상태만 “기간 지난 보강”으로 구분한다.

━━━━━━━━━━━━━━━━━━━━━━
1. 최종 상태 정책
━━━━━━━━━━━━━━━━━━━━━━

보강 세션 상태는 다음처럼 표시한다.

만료 전:

보강 대기

만료 후:

기간 지난 보강

판정 기준은 서버의 Asia/Seoul 날짜를 사용한다.

예:

expire_at이 2026-08-31 23:59:59인 경우

- 2026-08-31까지: 보강 대기
- 2026-09-01부터: 기간 지난 보강

중요:

- DB 행 삭제 금지
- 자동 cancelled 처리 금지
- 자동 completed 처리 금지
- 목록에서 제외 금지
- 학생별 보강 이력 유지
- 기존 expire_at 값 유지

━━━━━━━━━━━━━━━━━━━━━━
2. DB status 처리 방식 조사 후 최소 변경
━━━━━━━━━━━━━━━━━━━━━━

먼저 현재 실제 코드를 확인한다.

확인 항목:

1. makeup_sessions.status에 expired 값이 실제 존재하는지
2. 만료 Worker 또는 조회 API가 status를 expired로 변경하는지
3. expire_at이 지난 행을 WHERE 조건으로 제외하는지
4. expired 상태를 API에서 제외하는지
5. DB에서 실제 DELETE가 실행되는 경로가 있는지

판정에 따라 최소 변경한다.

권장안 A — 이미 expired 상태를 사용하는 경우:

- status='expired' 행을 삭제하지 않음
- 보강 목록 API에 expired도 포함
- 클라이언트에서 “기간 지난 보강”으로 표시

권장안 B — status 변경 없이 expire_at만 비교하는 경우:

- 기존 status='waiting' 유지 가능
- 서버 응답 또는 클라이언트 계산으로 is_expired 표시
- 화면 라벨만 “기간 지난 보강”으로 표시

대규모 Migration은 금지한다.

현재 구조에서 신규 컬럼 없이 구현 가능하면
신규 컬럼·테이블을 만들지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
3. 보강 목록 API
━━━━━━━━━━━━━━━━━━━━━━

현재 보강 대기 목록 API에서 다음과 같은 필터가 있다면 수정한다.

금지되는 필터 예:

WHERE expire_at >= NOW()

또는:

WHERE status = 'waiting'

만 사용해서 expired를 제외하는 구조

최종 조회 대상:

- waiting이며 아직 만료되지 않은 보강
- waiting이지만 expire_at이 지난 보강
- 기존 expired 상태가 있다면 expired 보강

completed, cancelled는 기존 탭·목록 정책을 유지한다.

응답에는 가능하면 다음 값을 포함한다.

{
  status: "waiting" | "assigned" | "completed" | "cancelled" | "expired",
  expire_at: "...",
  is_expired: true | false
}

기존 Contract 영향을 줄이려면
`is_expired`만 optional 필드로 추가한다.

판정:

is_expired =
  status === 'expired'
  OR
  expire_at < KST 현재 시각

━━━━━━━━━━━━━━━━━━━━━━
4. 화면 표시
━━━━━━━━━━━━━━━━━━━━━━

현재 보강 대기 목록 안에서 함께 표시한다.

별도의 “만료된 보강” 탭은 이번 수정에서 만들지 않는다.

정렬 순서:

1. 정상 보강 대기
2. 기간 지난 보강

각 그룹 안에서는 오래된 결석일 또는 만료일 순으로 정렬한다.

정상 보강:

- 기존 디자인 유지
- 만료일까지 남은 기간 표시 가능

기간 지난 보강:

- 배지: “기간 지난 보강”
- 만료일 표시
- 일반 보강과 시각적으로 구분

예:

기간 지난 보강
만료일: 2026.08.31

색상은 회색 또는 주황 계열로 구분하되
글자가 흐려서 읽기 어렵게 만들지 않는다.

학생 이름·원래 반·결석일 등 기존 정보는 그대로 표시한다.

━━━━━━━━━━━━━━━━━━━━━━
5. 기간 지난 보강의 처리 권한
━━━━━━━━━━━━━━━━━━━━━━

기간이 지났더라도 목록에서 다음 기능은 유지한다.

- 보강반 선택
- 오늘·과거 보강 완료
- 미래 보강 예약
- 직접 완료
- 취소

단, 기간 지난 보강을 처리할 때 확인 Alert를 띄운다.

문구:

“보강 가능 기간이 지난 항목입니다.
실제 수업 운영상 보강을 진행하는 경우에만 처리해 주세요.”

버튼:

[취소]
[그래도 처리]

서버가 현재 expire_at 이후 저장을 차단한다면
임의로 클라이언트만 우회하지 않는다.

다음을 서버 정책으로 확정한다.

- 기간 지난 보강도 관리자·선생님이 명시적으로 확인하면 처리 가능
- 클라이언트 Alert만 신뢰하지 않음
- API 요청에 만료 항목 처리 의도가 명확히 전달되어야 함

권장 요청 필드:

allow_expired: true

서버:

- 만료된 세션인데 allow_expired !== true → 409 MAKEUP_EXPIRED_CONFIRM_REQUIRED
- allow_expired === true → 기존 저장 검증 계속 수행 후 허용

단, 기존 서버에 이미 만료 후 처리 허용 구조가 있다면
신규 Contract를 만들지 말고 기존 구조를 유지한다.

먼저 실제 서버 차단 여부를 확인한 뒤 최소 수정한다.

━━━━━━━━━━━━━━━━━━━━━━
6. 보강 정책 설정 화면 유지
━━━━━━━━━━━━━━━━━━━━━━

다음 기능은 그대로 유지한다.

- end_of_month
- next_month_end
- fixed_days
- make_up_expiry_days
- 주 1회 월간 한도
- 주 2회 월간 한도
- 주 3회 월간 한도
- calcExpireAt()

정책 설정의 의미는 삭제 시점이 아니라
“정상 보강 가능 기간의 종료일”로 사용한다.

정책 화면 설명 문구를 다음처럼 조정한다.

기존 의미가 “만료 시 보강 삭제”로 보인다면 수정:

“설정한 기간이 지나면 보강 목록에서
‘기간 지난 보강’으로 표시됩니다.
항목은 자동으로 삭제되지 않습니다.”

━━━━━━━━━━━━━━━━━━━━━━
7. 월 변경 시 동작
━━━━━━━━━━━━━━━━━━━━━━

예:

8월 결석
expire_at = 8월 31일

8월 31일까지:

보강 대기

9월 1일부터:

기간 지난 보강

목록에는 계속 존재해야 한다.

앱 재시작, 월 변경, 날짜 변경, 서버 재배포 후에도
동일 항목이 계속 조회되어야 한다.

월이 바뀌는 순간 목록에서 사라졌다가
다른 화면에 나타나는 방식은 금지한다.
