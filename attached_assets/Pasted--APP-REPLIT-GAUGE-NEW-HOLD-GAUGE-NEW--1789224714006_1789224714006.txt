2. level PATCH의 fire-and-forget 방식은 승인하지 않음
━━━━━━━━━━━━━━━━━━━━━━

보고서에는:

level UPDATE
→ res.json()
→ 이후 비동기 computeConfirmedProgress()

이 방식은 사용하지 마십시오.

핵심 요구조건은:

"선생님이 레벨을 변경하면
그 레벨 floor가 즉시 현재 gauge에 반영"

입니다.

응답을 먼저 보낸 뒤 비동기로 재계산하면:

* 바로 재조회 시 이전 gauge 노출 가능
* 재계산 실패를 API 성공으로 숨길 수 있음
* Runtime race 가능

이 생깁니다.

두 level PATCH의 실제 코드를 다시 확인하고,

레벨 UPDATE
→ gauge fresh recompute 완료
→ 정상 저장 확인
→ response

순서로 동작할 수 있는 가장 안전한 방식을 제안하십시오.

가능하다면 같은 transaction 또는
일관성이 보장되는 service 경계에서 처리하십시오.

단, DB 구조상 transaction에 넣는 것이 부적절하다면 이유를 코드 기준으로 설명하십시오.

`res.json()` 이후 fire-and-forget은 최종안에서 제거하십시오.
