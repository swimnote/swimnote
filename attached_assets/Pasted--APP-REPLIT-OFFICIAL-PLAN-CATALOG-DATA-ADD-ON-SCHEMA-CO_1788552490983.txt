4. 올바른 schema 방식
============================================================

가장 우선:

BASE/X PLAN과
DATA ADD-ON이 동일 table을 사용해도
각 타입에 맞지 않는 field는 NULL 허용이 가능하도록 설계.

예:

plan_type=base/x
→ member_limit 사용

plan_type=data_addon
→ member_limit=NULL

plan_type=data_addon
→ storage quota 관련 실제 field 사용

단 현재 architecture를 조사하여
더 적절한 existing add-on table/entity가 이미 있으면 그것을 사용.

999999 / -1 / 0 등
의미 없는 sentinel 값으로 해결 금지.

5. 필요하면 정식 additive schema migration
============================================================

member_limit 또는 storage field의 NOT NULL 제약이
구형 단일-tier 구조 때문에 존재하고
신규 BASE/X/DATA architecture와 충돌한다면:

정식 migration으로 schema를 교정.

예:

member_limit nullable 전환

또는

plan_type에 맞는 별도 quota field/table 사용.

정확한 선택은 repository usage audit 후 결정.

runtime boot DDL 금지.

Production 실행 금지.
