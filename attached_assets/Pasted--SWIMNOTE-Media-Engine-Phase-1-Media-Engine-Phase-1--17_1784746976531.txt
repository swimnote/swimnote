# SWIMNOTE Media Engine Phase 1 완료 후 검증·안정화 작업 지시문

현재 Media Engine Phase 1 서버 구조와 주요 클라이언트 연동 작업이 완료되었습니다.

완료된 항목:

- photo_assets_meta.media_status 컬럼 추가
- 관련 인덱스 4개 추가 및 기존 데이터 백필
- MediaService 신규 구현
- diary.ts auto-attach 제거
- POST /diaries/with-media 통합 저장 엔드포인트 추가
- photos.ts 주요 사진 API를 MediaService 경유로 전환
- GET /photos/diary/:diaryId 통합 조회 적용
- GET /photos/draft 신규 추가
- note-attach 시 student_id, journal_id, student_note_id 동시 설정
- parent.ts 일지 중복 반환 버그 수정
- parent 사진 조회를 MediaService 기반으로 전환
- useDiaryMedia.ts 신규 구현
- AsyncStorage 초안 저장·복원 적용
- DiaryPhotoStrip을 React Query 기반으로 전환
- 일지 저장 후 잘못된 router.back 동작 수정
- TypeScript 오류 정리

이제 새로운 기능 추가보다 먼저
기존 데이터 정합성, 권한, 트랜잭션, 캐시, 성능을 철저하게 검증합니다.

이번 작업에서는 구조를 다시 크게 변경하지 마세요.

먼저 현재 구현을 실제 운영 가능한 상태로 검증하고,
문제가 발견된 경우 원인을 특정한 뒤 최소 범위로 수정하세요.

1. 작업 목표
==================================================

4. Cleanup 실행 계획
==================================================

Dry-run 결과를 바탕으로 Cleanup SQL 또는 스크립트를 작성하세요.

즉시 실행하지 말고 먼저 계획을 보고하세요.

기본 수정 규칙:

삭제된 일지를 참조하는 사진:

- journal_id = NULL
- student_note_id = NULL
- media_status = 'detached'

student_note_id는 있으나 student_id가 NULL인 사진:

- student note에서 student_id를 확인
- 관계가 확실한 경우 해당 student_id 설정
- note와 diary 관계가 불분명하면 자동 수정하지 않고 별도 보고

attached인데 journal_id가 NULL:

- 명확한 연결 근거가 있으면 journal_id 복구
- 근거가 없으면 media_status = 'detached'

draft인데 journal_id가 존재:

- diary가 활성 상태이고 실제 연결이 정상이라면 attached로 변경
- 그렇지 않으면 journal_id 해제 후 draft 또는 detached 처리

존재하지 않는 참조:

- 참조 ID 해제
- media_status = 'detached'
- R2 파일은 유지

Cleanup 실행 조건:

- 전체 작업을 하나 또는 안전한 단위별 transaction으로 실행
- 변경 전 백업 테이블 또는 audit 기록 생성
- 수정 전후 개수 비교
- 실패 시 rollback
- 실제 삭제 금지

7. 통합 저장 Transaction 검증
==================================================

POST /diaries/with-media가 아래 작업을
하나의 DB transaction으로 처리하는지 확인하세요.

1. class_diaries INSERT
2. class_diary_student_notes INSERT
3. 공통사진 attach
4. 학생 개인사진 attach
5. audit log 기록
6. commit

강제 실패 테스트를 추가하세요.

테스트 A:

- diary INSERT 후 의도적으로 note INSERT 실패
- 결과: diary도 남지 않아야 함

테스트 B:

- note INSERT 후 photo attach 실패
- 결과: diary와 notes 모두 rollback되어야 함

테스트 C:

- 일부 개인사진 attach 후 다음 학생 attach 실패
- 결과: 앞서 연결된 사진도 원래 상태로 rollback되어야 함

테스트 D:

- 중복 photo ID 전달
- 같은 사진이 두 번 연결되지 않아야 함

테스트 E:

- 다른 pool의 photo ID 전달
- 전체 요청 실패 및 rollback

테스트 F:

- 이미 다른 활성 일지에 attached된 사진 전달
- 명시적인 충돌 오류 반환
- 기존 연결은 유지

테스트 결과에 DB 전후 상태를 포함하세요.

11. Reservation / Draft 사진 검증
==================================================

다음 흐름을 실제로 테스트하세요.

1. 선생님이 반 A, 날짜 D 사진 4장 업로드
2. 사진 상태가 draft인지 확인
3. journal_id와 student_note_id가 NULL인지 확인
4. 일지 작성 화면 진입
5. GET /photos/draft로 사진 4장 후보 표시
6. 사진 3장 선택, 1장 제외
7. 일지 저장
8. 선택한 3장만 attached
9. 제외한 1장은 draft 유지
10. 다음 일지 작성 시 남은 draft 사진이 후보로 표시

추가 검증:

- 다른 반에서는 표시되지 않음
- 다른 날짜에서는 표시되지 않음
- 다른 pool에서는 표시되지 않음
- 권한 없는 선생님에게 표시되지 않음
- 같은 선생님의 여러 업로드가 중복 표시되지 않음

Draft 조회는 attached 조회와 OR 조건으로 섞지 마세요.

12. React Query 캐시 검증
==================================================

DiaryPhotoStrip의 query key와 invalidation 범위를 점검하세요.

확인할 query key 예시:

- ["diary-media", diaryId, studentId, parentMode]
- ["draft-media", poolId, classId, lessonDate]

검증 흐름:

1. 일지 상세 진입
2. 사진 데이터 조회
3. 뒤로 이동
4. 다시 진입
5. 캐시 데이터 즉시 표시 여부 확인
6. 불필요한 중복 요청 여부 확인
7. 사진 attach
8. setQueryData 또는 invalidate 후 즉시 화면 반영
9. 서버 데이터와 최종 동기화 확인

반드시 확인할 사항:

- attach 완료 후 화면 재진입 없이 사진 표시
- 삭제 후 캐시에서 즉시 제거
- Parent 캐시와 Teacher 캐시 권한 데이터 혼합 없음
- 학생별 Parent 캐시 분리
- diaryId가 없는 작성 단계에서 잘못된 캐시 키 생성 없음
- 실패 응답이 영구 캐시되지 않음
- 화면 이동마다 API가 반복 호출되지 않음
- staleTime과 gcTime이 과도하지 않음

네트워크 요청 횟수를 실제 로그로 기록하세요.

- serverPhotoId가 있는 사진은 서버 데이터 사용
- localUri가 유효하면 로컬 미리보기 사용
- localUri가 사라졌으면 깨진 이미지 대신 오류 상태 표시
- 업로드 중이었던 사진 재시도 가능
- 이미 업로드된 사진이 중복 업로드되지 않음
- 다른 날짜 초안과 섞이지 않음

초안 키에는 최소한 다음이 포함되어야 합니다.

- poolId
- classGroupId
- lessonDate
- teacherId 또는 계정 범위

15. 업로드 동시성 및 UI 반응성 테스트
==================================================

사진 업로드 테스트:

- 1장
- 5장
- 10장
- 20장

네트워크 조건:

- 정상 Wi-Fi
- 느린 네트워크
- 업로드 중 일시적 네트워크 끊김
- 한 파일만 실패
- 서버 presign 실패
- R2 업로드 실패

확인:

- UI 입력이 멈추지 않음
- 스크롤 가능
- 텍스트 작성 가능
- 사진별 진행상태 표시
- 실패한 파일만 재시도 가능
- 성공한 파일 재업로드 없음
- 중복 DB 레코드 없음
- 업로드 순서가 바뀌어도 최종 정렬 정상

동시 업로드 제한은 3~5개 범위로 설정하세요.

현재 업로드 큐가 없다면
대규모 구조 변경 전에 최소한 동시성 제한과 개별 재시도부터 구현하세요.

==================================================
16. Background Upload Queue 검토
==================================================

현재 구조가 단순 Promise.all인지 확인하세요.

사진 10장 이상에서 다음이 필요합니다.

- concurrency limit
- 개별 진행 상태
- 개별 실패 처리
- retry count
- exponential backoff 또는 제한된 재시도
- 중복 요청 방지
- 앱 종료 시 draft 복원

권장 기본값:

- 동시 업로드 3개
- 자동 재시도 2회
- 이후 수동 재시도
- mediaUuid 기준 idempotency

이번 단계에서 완전한 OS 백그라운드 업로드까지 확장할 필요는 없습니다.

우선 앱이 열린 상태에서 안정적으로 동작하는 업로드 큐를 구현하세요.

17. 저장 후 화면 이동 검증
==================================================

다음 진입 경로를 모두 확인하세요.

1. Teacher 일지 메뉴에서 직접 진입
2. 미작성 일지 목록에서 진입
3. 반 상세 화면에서 진입
4. 스케줄러에서 진입
5. 명시적 backTo 파라미터가 있는 진입

기본 동작:

- 저장 성공 후 history 화면 유지
- 2초 후 홈으로 이동하지 않음
- classGroupId만 존재한다고 router.back하지 않음

예외:

- 명시적 returnTo 또는 backTo가 있는 경우에만 지정 화면으로 복귀
- 저장 완료 전에 화면 이동시키지 않음
- 중복 navigation 실행 금지

19. 성능 목표
==================================================

아래 항목을 실제 측정하세요.

1. 사진 선택 후 local preview 표시 시간
목표: 100ms 이내

2. 저장 버튼 후 history 화면 전환
목표: 300ms 내외

3. 텍스트 일지 저장 API
목표: 일반 조건 1초 이내

4. 사진 attach 완료 후 UI 반영
목표: 성공 응답 후 200ms 이내

5. DiaryPhotoStrip 캐시 hit
목표: 즉시 표시

6. Parent 일지 목록 API
목표: 일반 데이터 기준 500ms 내외

7. draft 사진 조회
목표: 일반 조건 300~500ms 내외

8. 사진 10장 업로드 중 JS/UI thread 멈춤 여부
목표: 사용자 입력 및 스크롤 유지

실제 파일 업로드 시간은 네트워크 영향을 받으므로
서버 처리시간과 전송시간을 분리해서 보고하세요.
