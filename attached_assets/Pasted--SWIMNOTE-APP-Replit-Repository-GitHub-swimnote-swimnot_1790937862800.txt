1. 최종 운영 흐름
━━━━━━━━━━━━━━━━━━━━━━

월간 first-pass 완료

→ 실패/UNKNOWN 집계
→ 슈퍼관리자에게 예외 보고
→ 운영자가 원인 수정
→ 슈퍼관리자에서 “미완료 전체 재시도 승인”
→ 서버가 그 시점의 eligible 대상 cohort 고정
→ 서버측 batch recovery 시작
→ 각 대상별 기존 안전 계약 적용
→ 성공은 즉시 보존 및 batch에서 제외
→ 실패/UNKNOWN만 잔존
→ batch 중단/재시작 시 이어서 처리
→ pool별 100% 귀결
→ READY
→ 관리자 PUSH

브라우저가 모든 대상을 개별 호출하는 구조 금지.

3. 승인 시 cohort 고정
━━━━━━━━━━━━━━━━━━━━━━

운영자가 전체 재시도를 승인한 순간:

- report_month
- 선택된 pool scope
- failure/recovery eligibility 조건

을 기준으로 복구 cohort를 서버에서 고정합니다.

이후 화면 pagination이나 브라우저 종료와 무관하게
동일 batch가 계속 처리되어야 합니다.

승인 이후 새로 발생한 예외를
기존 batch에 몰래 추가하지 마세요.

새 예외는 다음 recovery batch/round 대상입니다.

4. 대상별 처리 계약
━━━━━━━━━━━━━━━━━━━━━━

각 대상은 상태에 따라 기존 계약을 사용합니다.

일반 retryable failure:
→ 기존 failed-only recovery

UNKNOWN:
→ 기존 operator-approved UNKNOWN reissue 계약

INSUFFICIENT_EVIDENCE:
→ 제외

generated COMPLETE:
→ 제외

PUBLISHED:
→ 제외

policy exclusion:
→ 제외

이미 성공한 대상:
→ 절대 재실행 금지

UNKNOWN 대량 승인에서도
대상별로 독립적인:

- original_request_id
- recovery_operation_id
- new_request_id
- lineage

를 유지합니다.

1,700건을 하나의 ENGINE request로 묶지 마세요.

10. UNKNOWN 안전성
━━━━━━━━━━━━━━━━━━━━━━

운영자가 “전체 재시도 승인”을 실행했다는 것이
UNKNOWN 각각의 명시적 operator approval 근거가 됩니다.

그러나 각 UNKNOWN은 여전히
기존 ENGINE 계약대로 별도 operation/new request를 사용합니다.

한 번의 batch 승인으로
UNKNOWN 안전장치를 해제하거나
기존 request를 retryable=true로 변경하면 안 됩니다.

새 attempt가 다시 UNKNOWN이 되면:

→ 해당 target만 unresolved
→ 자동 2차 reissue 금지
→ 다음 operator recovery round 승인 필요

예:

이어야 합니다.
