1. 최종적으로 만들려는 UX
━━━━━━━━━━━━━━━━━━━━━━

현재 정책은 이미 다음과 같다.

SMS 인증된 학부모 전화번호
=
선택한 수영장의 students.parent_phone1~4 중 하나

이면

학생 이름 입력과 관계없이 자동승인/자동연결한다.

같은 전화번호의 형제·자매가 있으면
동일 pool 안에서 모두 연결한다.

따라서 정상적으로 보호자 전화번호가 등록된 학부모는
원칙적으로 관리자 승인대기에 남지 않아야 한다.

관리자가 직접 처리해야 하는 것은 주로:

- 학생 보호자 전화번호 미등록
- 보호자 전화번호 오등록
- 신규회원이라 학생 기본정보가 아직 불완전
- 기타 자동매칭 불가능한 예외

인 경우다.

최종적으로 원하는 관리자 흐름:

학부모 연결 → 대기
→ 승인 버튼
→ 학생 선택 목록을 띄우지 않음
→ 해당 요청과 관련된 학생 개인정보/회원정보 확인 화면 표시
→ 관리자가 누락된 보호자 전화번호 등 필요한 정보를 확인/입력
→ 확인
→ 해당 요청 학부모와 즉시 연결 및 승인 완료

즉 관리자가
“승인 → 학생 다시 검색/선택 → 승인”
하는 구조를 제거하려는 것이다.

단, 아직 수정하지 말고 현재 구조와 실데이터를 먼저 조사한다.

2. 현재 Production 승인대기 실데이터 조사
━━━━━━━━━━━━━━━━━━━━━━

현재 화면에는 학부모 연결 대기 약 12건이 보인다.

Production DB를 READ-ONLY로 조회해서
현재 실제 pending 요청 전부를 조사한다.

개인정보 원문을 완료보고에 출력하지 말 것.
이름/전화번호 전체 노출 금지.

각 pending 요청에 대해 내부적으로 다음을 대조:

A. 요청 pool_id
B. 요청 학부모의 서버 인증 전화번호
C. 요청 시 입력한 child_name_raw
D. 해당 pool students에서
   parent_phone1~4 중 인증 전화번호와 일치하는 학생 존재 여부
E. 일치 학생 수
F. 이미 approved parent_students 관계가 존재하는지
G. 학생 status
H. 삭제/퇴원/보관 상태 여부
I. pending이 만들어진 시점
J. 현재 Production 자동연결 배포 전/후 요청인지

분류해서 숫자로 보고:

1. 현재 정책이라면 자동승인 가능한 정상 매칭 건
2. 전화번호 미등록 때문에 매칭 불가
3. 전화번호 불일치/오등록 가능
4. 이미 approved인데 pending만 남아 있는 건
5. 동일 전화번호 다자녀 매칭 건
6. 학생 자체를 특정하기 어려운 건
7. 기타 예외

특히:

현재 Production에 이미 배포된
phone-only auto approval 로직 기준이라면
자동승인됐어야 할 pending이 남아 있는지 확인한다.

왜 남아 있는지도 코드/생성시점 기준으로 원인을 찾는다.

절대 실제 승인처리하지 말 것.
이번 단계는 READ-ONLY다.

3. 기존 pending 자동복구 가능성 조사
━━━━━━━━━━━━━━━━━━━━━━

현재 대기 목록 중:

- SMS 인증 전화번호가 확인되고
- 같은 pool의 students.parent_phone1~4와 일치하고
- 현재 정상 학생이고
- 기존 정책상 자동승인 조건을 충족하는 건

기존 새 auto-link 로직을 이용해
안전하게 자동승인/연결할 수 있는지 조사한다.

중요:

기존 pending 데이터를
무조건 일괄 승인하는 설계 금지.

반드시 현재 Production의
“인증된 전화번호 + 같은 pool 등록 전화번호”
조건을 다시 만족하는 건만 대상이어야 한다.

다자녀라면 동일 pool의 같은 인증 전화번호 학생들을
기존 정책대로 모두 연결할 수 있는지도 확인한다.

이미 approved 관계가 있으면 중복 생성하지 않아야 한다.

학생 status나 기존 보호자 pointer를
자동복구 과정에서 변경하면 안 된다.

조사 후:

SAFE AUTO-RECOVERABLE PENDING = N건

형태로 숫자만 보고한다.

아직 실행하지 않는다.

5. “학생 개인정보창 → 확인 → 즉시 승인” 설계 가능성 조사
━━━━━━━━━━━━━━━━━━━━━━

새 화면을 무조건 만들지 말 것.

현재 SWIMNOTE에 이미 존재하는
학생 개인정보/회원정보 수정 UI를 먼저 찾는다.

관리자가 회원관리 등에서 사용하는 기존 학생정보 편집 화면 중:

- 학생 이름
- 보호자 전화번호
- 반
- 필요한 기본 회원정보

를 수정하는 기존 화면/컴포넌트/API가 있는지 조사한다.

가능하면 그것을 재사용하는 설계를 우선한다.

목표:

pending 요청에서 승인 클릭
→ 해당 학생 정보 화면
→ 전화번호가 빠져 있으면 관리자가 입력
→ 확인/저장
→ 저장 성공 후 동일 pending 요청에 대해
   방금 저장된 번호와 학부모의 인증 전화번호를 서버에서 다시 비교
→ 일치하면 즉시 approved 관계 생성
→ pending 승인 완료
→ 승인관리 목록에서 제거

중요:
관리자가 입력한 번호라고 해서 무조건 승인하면 안 된다.

저장 후에도 서버가 반드시:

pending 요청의 인증된 학부모 전화번호
=
해당 학생의 저장된 parent_phone1~4

를 재검증한 뒤 승인해야 한다.

6. 학생을 아직 특정할 수 없는 신규회원 예외 조사

신규회원이라:

- 학생 레코드는 있지만 정보가 부족한 경우
- 학생 레코드 자체가 아직 없는 경우
- pending child_name_raw만 있고 어떤 학생인지 확정할 수 없는 경우

를 각각 조사한다.

학생이 이미 특정된 경우에는
학생 선택 목록 없이 개인정보창으로 바로 갈 수 있다.

하지만 student_id 자체를 안전하게 특정할 수 없는 요청에서
잘못된 학생 개인정보창을 임의로 열면 안 된다.

이 경우 현재 SWIMNOTE의 신규회원 등록/학생 생성 구조를 조사해서

어떤 최소 UX가 필요한지 설계만 제안한다.

예:
pending 요청의 이름/전화번호 정보를 보여주면서
신규 학생 등록 또는 기존 학생 확인으로 이어지는 방식.

단,
이번 조사 단계에서 구현하지 않는다.
