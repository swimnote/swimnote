원인 확정 — 삭제된 동일 일지가 클라이언트 stale state로 계속 표시됨

실제 화면 증거:

지난일지 카드:
[DEV] id=cd_1784770363546... | del=false

같은 카드 삭제 시 서버 응답:
"이미 삭제된 일지입니다."

즉,

서버/DB에서는 해당 diary_id가 이미 is_deleted=true인데,
클라이언트 화면은 삭제 전 객체를 del=false 상태로 계속 렌더링하고 있습니다.

또한 해당 스케줄 아래 상태도
"일지 미작성"으로 돌아가지 않고
계속 "일지 작성" 상태로 표시됩니다.

새 일지 생성 문제가 아닙니다.
동일 diary_id의 stale client state 및 다중 캐시 동기화 문제입니다.

==================================================

1. 이미 삭제된 응답도 성공 처리

DELETE 응답이 다음 중 하나라면 모두 삭제 성공으로 처리하세요.

- HTTP 200 삭제 완료
- HTTP 404 이미 없음
- HTTP 409 또는 별도 코드 + "이미 삭제된 일지입니다."
- response body에서 alreadyDeleted=true

이 경우 오류 문구를 모달 안에 남기지 말고:

- 삭제 모달 즉시 닫기
- 해당 diary_id를 지난일지 배열에서 제거
- 선택된 diary state 초기화
- 관련 날짜/반의 diary existence state 초기화
- 관련 캐시 모두 invalidate
- 백그라운드 재조회

멱등 삭제로 처리해야 합니다.

삭제 요청을 여러 번 보내도
최종 UI 상태는 항상 "삭제됨"이어야 합니다.

==================================================

2. 지난일지 화면의 실제 상태 출처 추적

현재 카드가 어떤 배열에서 렌더링되는지 정확히 확인하세요.

예:

- diaries
- pastDiaries
- historyDiaries
- selectedGroup.diaries
- cachedDiaries
- groupedDiaries
- scheduleDiaries
- diaryMap
- Context state
- route params
- AsyncStorage
- persisted store

삭제 성공 또는 이미 삭제 응답 직후,
동일 diary_id를 모든 관련 상태에서 제거하세요.

예시 원칙:

setDiaries(prev =>
  prev.filter(diary => diary.id !== deletedDiaryId)
)

단일 화면 배열만 제거하지 말고
동일 ID를 보유할 수 있는 모든 캐시와 파생 상태를 확인하세요.

==================================================

3. 서버 재조회 결과로 화면 상태를 교체

DELETE 이후 GET 응답을 기존 배열에 merge하지 마세요.

잘못된 예:

setDiaries(prev => merge(prev, response.diaries))

이 방식은 서버 응답에 없는 삭제된 기존 객체를 남길 수 있습니다.

정상 방식:

setDiaries(
  response.diaries.filter(diary => diary.is_deleted !== true)
)

즉, 네트워크 최신 응답으로 전체 배열을 교체하세요.

삭제된 ID가 GET 응답에 없으면
기존 클라이언트 배열에서도 반드시 사라져야 합니다.

==================================================

4. del=false 개발 표시 원인 확인

현재 카드에 표시된:

del=false

값이 실제 API의 is_deleted 값인지,
클라이언트에서 기본값 false를 넣은 것인지 확인하세요.

특히 다음 코드를 찾으세요.

is_deleted ?? false
isDeleted || false
del: false
mapDiary(...)
normalizeDiary(...)

서버 응답에 is_deleted가 없다는 이유로
기존 stale 객체에 false를 유지하는지 확인하세요.

일반 사용자 조회에서는 삭제된 일지 자체가 반환되면 안 됩니다.

==================================================

5. 스케줄러 일지 상태 동기화

삭제 후에도 해당 일정 밑에
"일지 미작성"이 나오지 않고
계속 "일지 작성" 상태로 표시됩니다.

스케줄러가 일지 존재 여부를 판단하는 데이터 출처를 추적하세요.

예:

- diarySet
- diaryDates
- diaryByScheduleId
- hasDiary
- writtenScheduleIds
- diaryCount
- completedDiaryMap
- schedule.diary
- local memoized Set

삭제 성공 또는 이미 삭제 응답 후:

- 삭제된 diary_id 제거
- 해당 class_group_id + lesson_date 키 제거
- diarySet 재생성
- scheduler query invalidate
- scheduler data refetch

예:

const key = `${classGroupId}:${lessonDate}`

삭제 후 해당 key가 Set/Map에 남지 않아야 합니다.

==================================================

6. "일지 작성" 문구 의미 검토

현재 일정 밑 상태가 실제로

- 작성된 일지가 있음
- 작성 버튼
- 미작성 상태

중 무엇을 뜻하는지 확인하세요.

삭제된 후에는 정확히 다음 상태로 돌아가야 합니다.

"일지 미작성"

그리고 사용자가 누르면 새 일지를 작성할 수 있어야 합니다.

삭제된 diary_id를 근거로
"작성됨" 상태를 유지하면 안 됩니다.

==================================================

7. 앱 재실행 hydration 확인

앱 재실행 후 삭제된 카드가 다시 나타나는 원인을 확인하세요.

다음 저장소를 전수 검색하세요.

- AsyncStorage
- persisted Context
- Zustand persist
- custom API cache
- scheduler persisted state
- navigation params
- initialData
- hydration
- cached response

앱 시작 시 서버 GET보다 먼저
저장된 지난일지 배열을 복원하고 있는지 확인하세요.

복원하더라도 서버 최신 응답이 오면
반드시 배열 전체를 교체해야 합니다.

삭제된 ID가 영구 저장소에 있다면 제거하세요.

==================================================

8. 캐시 키 전수 무효화

삭제 시 다음 유형의 캐시를 모두 무효화하세요.

- /diaries
- /diaries/:id
- /diaries?class_group_id=...
- /diaries?lesson_date=...
- teacher history
- scheduler
- unwritten diary
- written diary set
- admin diary list
- parent diary list

단순 exact match가 아니라
diary 관련 prefix 및 scheduler 관련 키를 모두 포함해야 합니다.
