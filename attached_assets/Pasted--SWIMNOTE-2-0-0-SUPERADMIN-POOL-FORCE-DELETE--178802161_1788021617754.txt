[SWIMNOTE 2.0.0 — SUPERADMIN POOL FORCE DELETE / 즉시삭제]

목표:

슈퍼관리자가 특정 수영장을
즉시 완전 삭제할 수 있는 기능을 제공한다.

사용 사례:

1. 잘못 생성/가입된 테스트 수영장
2. 가입 정보를 완전히 초기화해야 하는 수영장
3. 수영장 운영자가 변경되어 기존 데이터를 완전히 폐기하고
   신규 가입부터 다시 시작해야 하는 경우
4. 중복/오가입된 수영장 정리

이번 작업은 release/v2.0.0에서만 진행.

1.6.3 APP 수정 금지.

1. 기존 기능 존재 여부 먼저 조사
==================================================

Superadmin 관련 repository 전체 조사:

- swimming pool delete
- force delete
- hard delete
- pool deactivate
- owner/admin delete
- tenant delete
- account delete
- superadmin pool management

확인:

A. 기존 UI 버튼 존재 여부
B. 기존 API endpoint 존재 여부
C. soft delete인지 hard delete인지
D. 어떤 테이블까지 삭제하는지
E. 실제 FK cascade 여부
F. R2/file storage까지 처리하는지

기존 기능이 있으면 새로 중복 구현하지 않는다.

먼저 실제 기능 범위를 검증하고,
아래 요구사항보다 부족하면 보강한다.

2. 기능 정의
==================================================

Superadmin 전용:

"수영장 즉시 삭제"

대상은:

pool_id

하나의 전체 tenant.

수영장 관리자 계정만 삭제하고
학생/회원 데이터가 남는 방식 금지.

삭제 성공 후 해당 pool_id와 관련된
서비스 데이터가 운영 DB에서 남아 있지 않아야 한다.

7. 데이터 소유권 주의
==================================================

Pool-First 구조 기준:

일반 학부모 account가 해당 pool 전용 account라면
해당 pool 삭제와 함께 삭제 가능.

하지만 관리자/선생님의
명시적 multi-pool account가 존재할 수 있다.

따라서 account 자체를 무조건 DELETE하지 않는다.

반드시 조사:

해당 account가 다른 active pool membership도 보유?

YES:
→ 현재 pool membership/tenant relation만 삭제
→ global identity/account 유지

NO:
→ 해당 account가 정말 이 pool 전용이면
   현재 auth architecture 기준으로 안전하게 삭제

즉 다른 수영장 계정을 절대 삭제하지 않는다.

8. 전화번호 사용 금지
==================================================

삭제 대상 결정에 phone 사용 금지.

절대:

WHERE phone = ?

으로 관련 account를 싹 삭제하지 않는다.

삭제 범위 결정은:

pool_id
account_id
FK relation

기준.

같은 전화번호로 다른 수영장에 가입된 계정:

영향 0.

12. 결제 / 구독
==================================================

삭제 전에 해당 pool의:

- subscription
- X entitlement
- RevenueCat/App Store/Play entitlement relation
- pending payment

확인.

외부 결제 provider에서 자동 환불/취소까지 할지는
현재 기존 정책을 조사.

임의 환불 금지.

최소한 SWIMNOTE 내부 tenant entitlement는
더 이상 active로 남지 않아야 한다.

외부 구독이 남는 경우
삭제 전 BLOCK하거나 명확한 경고를 표시.

13. Transaction
==================================================

가능한 DB 삭제는 transaction으로 처리.

중간 실패 시:

반쯤 삭제된 tenant

가 생기지 않게 한다.

삭제 순서는 실제 FK dependency 기준.

가능하면:

BEGIN
→ dependent records
→ memberships/accounts
→ swimming_pool
→ COMMIT

외부 storage/AI 삭제는
안전한 orchestration 구조 사용.
