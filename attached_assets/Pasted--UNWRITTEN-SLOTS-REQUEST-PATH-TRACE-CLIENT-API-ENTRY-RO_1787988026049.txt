2. TRACE CLIENT REQUEST
==================================================

두 selector 각각 확인.

HOME:
GET /diaries/unwritten-slots

DIARY:
GET /diaries/unwritten-slots?includeWritten=true

확인:

A.
apiRequest에 실제 전달되는 path

B.
최종 fetch URL

예:
https://<actual-api-host>/api/diaries/unwritten-slots

C.
Authorization header가 실제 포함되는지

secret/token 값 출력 금지.
presence만 확인:

authorization_present=true/false

D.
fetch가 실제 실행되는지

E.
HTTP response status

F.
response body의 안전한 요약

G.
fetch 자체 exception이면:
error name/message

==================================================
4. TRACE SERVER ENTRY
==================================================

현재 [unwritten-slots] logging이
handler 내부에만 있다면
route 진입 직전 또는 handler 첫 줄에
딱 1개 entry log 추가.

예:

[unwritten-slots-entry] {
  request_id,
  includeWritten,
  authenticated: true
}

중요:

DB query 전에 무조건 찍혀야 함.

또한 requireAuth보다 앞에서 막힐 가능성 확인.

필요하면 auth middleware 실패 시
기존 안전한 status/log 확인.

새 auth logging 시스템 만들지 말 것.

5. CHECK ACTUAL API BASE URL
==================================================

매우 중요.

현재 production 앱의 apiRequest가
실제로 어느 서버를 호출하는지 확인.

반드시 보고:

API_BASE_URL

단,
secret 포함 금지.

확인:

- production swimnote-api URL인지
- development URL인지
- stale URL인지
- custom domain인지
- /api prefix가 중복/누락되지 않는지

예:

base:
https://example.onrender.com/api

path:
/diaries/unwritten-slots

final:
https://example.onrender.com/api/diaries/unwritten-slots

형태가 맞는지 확인.

6. CHECK API REQUEST CONTRACT
==================================================

apiRequest 함수 signature 확인.

예:

apiRequest(token, path)

인지

apiRequest(path, options)

인지.

두 selector가
현재 helper를 올바른 인자 순서로 호출하는지 확인.

특히:

UnwrittenScheduleSheet
SessionSelectorSheet

두 파일의 실제 호출을 나란히 비교.

둘 다 동시에 실패하므로
공통 helper 호출 방식 오류 가능성 확인.

==================================================
7. CHECK RESPONSE PARSING
==================================================

서버가 200을 줘도 client가 실패할 수 있음.

확인:

실제 response가:

{ slots: [...] }

인지.

client가:

data.slots

를 읽는지.

혹시 apiRequest가 이미 body를 unwrap해서
array 자체를 반환하는데
다시 data.slots를 읽는 등의 contract mismatch가 있는지 확인.

반대로:

{
  success: true,
  data: {
    slots: [...]
  }
}

같은 구조인데
client가 잘못 읽는지도 확인.

실제 apiRequest 구현과
실제 route response를 대조.

추측 금지.
