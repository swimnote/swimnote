# SWIMNOTE 보호자 가입 시스템 Production E2E 최종 검증

## 작업 목적

보호자 가입, 자동 연결, 관리자 수동 연결, 추가 보호자 가입 및 기존 학생 병합 연결 흐름을 실제 Production 앱에서 끝까지 검증합니다.

이번 작업의 핵심은 코드 수정이 아니라 실제 운영 흐름 검증입니다.

단, 실제 테스트에서 명백한 버그가 확인된 경우에만 최소 범위로 수정하고 다시 처음부터 재검증하십시오.

API 200 응답이나 DB 값 확인만으로 완료 처리하지 마십시오.

──────────────────────────────
1. 사전 백업 및 테스트 데이터 준비
──────────────────────────────

실제 운영 회원에게 영향을 주지 않는 Production 테스트용 데이터를 준비합니다.

테스트용 항목:

- 테스트 수영장 또는 안전하게 사용할 수 있는 동일 pool
- 기존 테스트 학생 1명
- 기존 보호자 전화번호 1개
- 추가 보호자 전화번호 parent_phone2
- 추가 보호자 전화번호 parent_phone3
- 추가 보호자 전화번호 parent_phone4
- 자동 연결 실패용 미등록 전화번호 1개
- 동명이인 테스트 학생 2명
- 다중 전화번호 후보 테스트 학생 2명

실제 회원 데이터 수정 금지.

테스트 전 관련 레코드 상태를 기록하고, 테스트 종료 후 불필요한 테스트 데이터만 정리하십시오.

──────────────────────────────
2. 최초 보호자 가입 자동 연결
──────────────────────────────

실제 보호자 앱에서 다음 흐름을 수행합니다.

1. 보호자 회원가입
2. 이름 입력
3. 자녀 이름 입력
4. 기존 학생의 parent_phone과 같은 전화번호 사용
5. 가입 완료
6. 보호자 홈 진입

확인:

- 기존 Student에 자동 연결
- 신규 Student 생성 없음
- parent_students 관계 1개 생성
- 기존 학생 이름 표시
- 반 표시
- 레벨 또는 진도 정보 표시
- 일지 목록 접근 가능
- 출결 목록 접근 가능
- 다른 학생 정보 노출 없음

──────────────────────────────
3. 추가 보호자 가입 자동 연결
──────────────────────────────

기존 학생에 등록된 아래 번호로 각각 실제 가입합니다.

- parent_phone2
- parent_phone3
- parent_phone4

각 가입에서 확인:

- 같은 기존 Student에 연결
- 신규 Student 생성 없음
- 기존 보호자 계정과 신규 보호자 계정이 동시에 같은 학생 조회 가능
- parent_students 중복 없음
- 기존 학생의 반, 레벨, 일지, 출결 데이터 유지
- 첫 번째 보호자의 연결이 끊기지 않음

──────────────────────────────
4. 미연결 가입자 관리자 처리
──────────────────────────────

기존 학생 전화번호와 일치하지 않는 번호로 가입합니다.

가입 시 자녀 이름은 기존 학생 이름과 동일하게 입력합니다.

관리자 앱에서 확인:

- 미연결 학부모 목록에 표시
- 미연결 배지 표시
- 가입자 이름 표시
- 가입자 전화번호 표시
- 가입일 표시
- 가입 시 입력한 자녀 이름 표시
- 값이 없을 때도 섹션이 숨겨지지 않고 ‘정보 없음’ 표시

‘기존 학생과 연결’을 누른 후 확인:

- 가입 시 입력한 자녀 이름이 검색어로 자동 입력
- 같은 pool 학생만 표시
- 학생 이름, 반, 레벨 표시
- 보호자 이름과 전화번호가 마스킹되어 표시
- 연결된 보호자 수 표시
- 연결 전 확인 모달 표시
- 선택한 기존 Student에만 연결
- 신규 Student 생성 없음

──────────────────────────────
5. 수동 연결 완료 후 상태
──────────────────────────────

관리자 수동 연결 직후 확인:

- 관리자 미연결 목록에서 제거 또는 연결 완료 상태로 변경
- parent_v2_pending.status = matched
- student_registration_requests.status = approved
- parent_students 관계 생성
- 같은 요청 재호출 시 중복 관계 생성 없음

보호자 앱에서:

1. 앱 새로고침
2. 로그아웃
3. 재로그인

세 경우 모두 기존 학생이 표시되는지 확인합니다.

일지와 출결도 실제 화면에서 직접 열어 확인하십시오.

──────────────────────────────
6. 동명이인 구분
──────────────────────────────

같은 pool에 이름이 동일한 학생 2명을 준비합니다.

관리자 기존 학생 검색에서 확인:

- 두 학생 모두 별도 결과로 표시
- 반으로 구분 가능
- 레벨로 구분 가능
- 마스킹된 보호자 정보로 구분 가능
- 관리자가 선택하지 않은 학생에게 연결되지 않음

잘못 선택할 가능성이 높다면 UI를 대규모 변경하지 말고 위험 요소를 보고하십시오.

──────────────────────────────
7. 다중 전화번호 후보
──────────────────────────────

같은 pool의 학생 2명에게 동일한 추가 보호자 전화번호를 등록합니다.

해당 번호로 보호자 가입 후 확인:

- 임의 자동 연결 금지
- pending 유지
- 신규 Student 생성 없음
- 서버 경고 로그 기록
- 관리자가 수동으로 올바른 학생을 선택 가능

테스트 종료 후 중복 전화번호 테스트 데이터는 원상 복구하십시오.

──────────────────────────────
8. Tenant 격리 실검증
──────────────────────────────

다른 pool에 같은 이름 및 같은 전화번호 학생을 준비하거나 기존 안전한 테스트 데이터를 사용합니다.

확인:

- 자동 연결 시 다른 pool 학생 제외
- 관리자 검색에서 다른 pool 학생 제외
- 다른 pool의 studentId를 직접 넣어 연결 요청하면 403
- 다른 pool의 parentId를 직접 넣어 연결 요청하면 403
- 현재 pool 데이터에는 변화 없음

super_admin 경로와 pool_admin 경로를 구분하여 결과를 기록하십시오.

──────────────────────────────
9. 재가입 및 중복 계정
──────────────────────────────

같은 전화번호로 다시 가입을 시도합니다.

상태별로 확인:

- 이미 승인된 계정
- pending 계정
- 기존 자동 연결 완료 계정
- 로그아웃된 기존 계정

확인:

- 새로운 parent_accounts 레코드가 중복 생성되지 않음
- 적절한 로그인 또는 기존 계정 안내 제공
- 기존 학생 연결 유지
- 기존 parent_students 관계 유지

동시 가입 Race Condition은 안전한 테스트 방식이 가능한 경우에만 수행하십시오.

실제 운영 장애 위험이 있으면 코드와 DB 제약을 분석하여 결과만 보고하십시오.

──────────────────────────────
10. 이전 보안 수정 회귀 테스트
──────────────────────────────

이번 보안 수정으로 아래 기능이 깨지지 않았는지 실제 화면 또는 API 흐름에서 확인합니다.

- 보강 목록 조회
- 보강 필터링
- 인계 보강 등록
- 인계 보강 목록
- 교사 허브 조회
- 관리자 대시보드
- 학생 검색
- 보호자 상세 조회

특히 sql.raw를 파라미터 바인딩으로 변경한 API에 500 오류나 빈 결과 문제가 없는지 확인하십시오.

──────────────────────────────
11. parent_accounts 전화번호 제약 조사
──────────────────────────────

이번 단계에서는 DB Unique 제약을 바로 추가하지 마십시오.

아래만 조사하여 보고합니다.

- parent_accounts 전화번호 컬럼명
- 저장 형식
- 가입 전 정규화 여부
- 동일 번호가 현재 여러 레코드에 존재하는지
- 전화번호가 전역 계정 식별자인지 pool별 식별자인지
- 탈퇴 계정 전화번호 재사용 정책
- 소셜 가입 계정과 전화번호 계정 관계
- DB-level unique 적용 시 충돌할 기존 데이터
- 권장 인덱스 형태

예:

- UNIQUE(phone_normalized)
- UNIQUE(pool_id, phone_normalized)
- 부분 인덱스
- 현재 구조 유지

근거 없이 Migration을 생성하지 마십시오.

──────────────────────────────
12. 완료 조건
──────────────────────────────

아래 흐름이 실제 Production 앱에서 끝까지 동작해야 완료입니다.

기존 학생 등록
→ 첫 보호자 가입
→ 자동 연결
→ 추가 보호자 가입
→ parent_phone2/3/4 자동 연결
→ 미연결 보호자 가입
→ 관리자 자녀 이름 확인
→ 기존 학생 검색
→ 수동 연결
→ 보호자 앱 재로그인
→ 기존 학생 확인
→ 일지 확인
→ 출결 확인

완료 보고서에는 다음을 포함하십시오.

1. 테스트한 실제 앱 빌드 및 환경
2. 테스트 계정과 데이터는 개인정보를 마스킹해 기록
3. 각 시나리오 PASS/FAIL
4. 신규 Student 생성 여부
5. parent_accounts 중복 여부
6. parent_students 중복 여부
7. pending 및 registration 상태 변화
8. tenant 격리 결과
9. 재가입 결과
10. 보강·교사 허브 회귀 테스트 결과
11. parent_accounts 전화번호 Unique 제약 조사 결과
12. 발견한 버그와 수정 내용
13. 실제 관리자 앱 스크린샷
14. 실제 보호자 앱 스크린샷
15. 실제 DB 검증 근거

실제 앱 화면 스크린샷 없이 완료 처리하지 마십시오.
