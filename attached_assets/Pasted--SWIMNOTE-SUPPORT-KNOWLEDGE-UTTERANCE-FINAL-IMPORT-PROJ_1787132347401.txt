--------------------------------------------------

기존 완료 상태:
- NEW 1,051
- INSERT 1,051
- SAME 0
- CONFLICT 0
- duplicate intent_id 0
- 신규 row 전부 status=pending
- AUTO_ACTIVE = NO
- ACTIVE overwrite = NO

따라서 이번에는 Canonical 1,051개를 다시 중복 INSERT하지 않는다.

먼저 Production DB에서 v1.1 intent_id 1,051개가 실제 존재하는지 확인한다.

확인:
- 1,051개 모두 존재
- duplicate intent_id 0
- 기존 imported row status가 예상대로 pending인지
- knowledge_id 매핑에 사용할 id가 정상 존재하는지

Canonical 파일은 이번 Utterance import의 참조 검증용으로 사용한다.

단,
원본 utterance 문구 자체는 수정하지 않는다.

--------------------------------------------------
3. 중복 / 충돌 처리
--------------------------------------------------

support_intent_utterances 현재 Production 데이터를 먼저 조회한다.

각 첨부 row를 다음으로 분류:

A. NEW
- 동일 utterance 또는 동일 normalized_utterance가 없음
→ INSERT

B. SAME
- 동일 intent_id + 동일 normalized_utterance가 이미 존재
→ SKIP

C. CONFLICT
- 동일 normalized_utterance가 다른 intent_id에 연결되어 있음
→ INSERT 금지
→ conflict 목록으로 보고

D. BROKEN_REFERENCE
- intent_id 또는 knowledge_id가 Production Canonical과 맞지 않음
→ INSERT 금지
→ 목록으로 보고

절대로 conflict를 임의로 다른 intent에 연결하지 말 것.

--------------------------------------------------
4. 실제 Import
--------------------------------------------------

가능하면 transaction 사용.

BEGIN

→ Canonical 1,051개 reference 검증
→ Utterance 13,700개 parse
→ Production normalizeQuery 기준 normalized 값 검증
→ NEW / SAME / CONFLICT / BROKEN_REFERENCE 분류
→ NEW만 support_intent_utterances에 INSERT
→ 신규 row status=pending 유지
→ 자동 ACTIVE 금지

COMMIT

중간 오류 발생 시 ROLLBACK.
