A. 기존 사용자 기기에 이미 쌓인 대용량 이미지/미디어 캐시를

사진 조회/업로드 때문에 수 GB씩 로컬 저장공간이

1. 먼저 실제 API/라이브러리 검증
━━━━━━━━━━━━━━━━━━━━━━

코드 수정 전에 현재 설치 버전 기준으로 확인한다.

expo-image
expo-image-picker
expo-file-system
expo-image-manipulator

각 라이브러리에서 공식적으로 지원하는:

- disk cache clear API
- cachePolicy
- 임시 picker 파일 lifecycle

을 현재 package version 기준으로 확인한다.

추측으로 private directory path를 하드코딩하지 않는다.

특히:

com.hackemist.SDImageCache

이 디렉터리를 문자열 경로만 보고 직접 삭제하기 전에
어떤 라이브러리가 관리하는 cache인지 코드/package를 통해 확정한다.

가능하면 라이브러리 공식 clear API를 우선 사용한다.

━━━━━━━━━━━━━━━━━━━━━━
2. Cleanup V2 — 기존 이미지 캐시 정리
━━━━━━━━━━━━━━━━━━━━━━

실측에서 확인된:

com.hackemist.SDImageCache
2.38GB

를 안전하게 제거한다.

expo-image 또는 현재 이미지 라이브러리에서 제공하는
공식 disk cache clear API가 있다면 그것을 우선 사용한다.

예:

Image.clearDiskCache()

단 실제 현재 설치 버전에서 API 존재 여부와
사용법을 확인한 뒤 적용한다.

이 작업은 서버/R2 사진을 삭제하는 것이 아니다.

로컬 이미지 캐시만 삭제한다.

삭제 후 필요한 사진은 서버/R2 URL에서 다시 로드되어야 한다.

━━━━━━━━━━━━━━━━━━━━━━
3. ImagePicker 894MB 원인 조사 후 정리
━━━━━━━━━━━━━━━━━━━━━━

실측:

ImagePicker
894.4 MB / 482개

이 영역이 매우 크다.

먼저 실제 디렉터리 구조와 생성 주체를 확인한다.

다음 조건을 모두 만족하는 경우에만 Cleanup V2 대상으로 포함:

1. SWIMNOTE가 ImagePicker를 통해 만든 temporary/cache copy임
2. R2 업로드 완료 데이터와 독립적임
3. DB에서 해당 local URI를 영구 source로 사용하지 않음
4. draft 또는 진행 중 upload가 참조하고 있지 않음

위 조건 확인 없이 ImagePicker 디렉터리 전체 삭제 금지.

안전성이 확인되면
오래된 picker temporary cache를 Cleanup V2에서 제거한다.

━━━━━━━━━━━━━━━━━━━━━━
4. 진행 중 Upload 보호
━━━━━━━━━━━━━━━━━━━━━━

가장 중요.

Cleanup V2 실행 순간:

업로드 중인 사진
업로드 대기 queue
재시도 대기 파일

이 있다면 해당 파일은 절대 삭제하면 안 된다.

UploadQueueContext 및 관련 queue persistence를 조사해서

현재 active/pending/retry job이 참조하는 local URI는
cleanup 대상에서 제외한다.

필요하다면:

업로드 queue가 비어 있을 때만
ImagePicker temp cleanup을 실행한다.

안전성을 확정할 수 없으면
V2 1차에서는 ImagePicker cleanup을 하지 말고 보고한다.

2.38GB image disk cache 정리만 먼저 하는 것도 허용한다.

━━━━━━━━━━━━━━━━━━━━━━
5. 앞으로 이미지 조회 캐시 정책 수정
━━━━━━━━━━━━━━━━━━━━━━

학부모/선생님이 서버 사진을 단순히 조회하는 것만으로
disk cache가 무제한 증가하는 구조를 차단한다.

현재 SWIMNOTE에서 서버/R2 이미지를 렌더링하는
ExpoImage/Image 컴포넌트를 전수 조사한다.

특히:

parent/home
parent/swim-diary
parent/photos
DiaryPhotoStrip

및 선생님 사진/일지 화면.

모든 화면을 무조건 cachePolicy="none"으로 바꾸지 않는다.

성능과 네트워크 사용량도 고려한다.

원칙:

피드/일지처럼 재조회 성능이 필요한 화면은
memory 중심 정책을 검토한다.

예:
cachePolicy="memory"

현재 expo-image 버전에서 지원 여부 확인 후 사용.

목표:

앱을 종료한 뒤에도 수개월 동안
사진 수천 장이 disk에 계속 쌓이는 구조를 제거한다.

━━━━━━━━━━━━━━━━━━━━━━
6. 앞으로 ImagePicker temp 누적 차단
━━━━━━━━━━━━━━━━━━━━━━

사진 선택 → 압축 → 업로드 과정 전체를 다시 추적한다.

업로드 성공 후:

SWIMNOTE가 생성한 temporary copy만 삭제.

업로드 실패 후:

retry가 필요한 파일이면 즉시 삭제 금지.

retry가 완전히 종료되거나 사용자가 취소한 경우에만 삭제.

원본 사진앱 파일은 절대 삭제 금지.

PHAsset / MediaLibrary 원본 삭제 금지.

8. V2 실행 위치
━━━━━━━━━━━━━━━━━━━━━━

앱 시작 직후 UI를 막지 않는
fire-and-forget 방식 유지 가능.

단 대용량 cache 삭제 때문에
앱 startup crash/freeze가 발생하면 안 된다.

필요하면 로그인 완료 이후 또는
RootNav 안정화 이후 실행.

동시에 두 번 실행되지 않도록 lock 적용.
