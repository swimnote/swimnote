1. 핵심 정책
━━━━━━━━━━━━━━━━━━━━

자동승인과 관리자 수동승인을 완전히 분리합니다.

자동승인:
서버가 충분히 안전하게 학생을 유일하게 식별할 수 있을 때만 실행.

수동승인:
자동승인에 실패했더라도 관리자가 실제 학생을 선택하고 승인하면 연결.

자동승인 실패는
"관리자 승인 금지"가 아닙니다.

━━━━━━━━━━━━━━━━━━━━
2. 자동승인 — 기존 안전조건 유지
━━━━━━━━━━━━━━━━━━━━

현재 정상인 normalization 유지:

- 이름 trim
- 이름 내부 공백 제거
- lowercase
- 전화번호 숫자 normalization
- parent_phone1~4 비교
- pool_id 제한
- 동명이인 자동승인 금지
- 전화번호 불일치 자동승인 금지

중요:

조사안의

"박새연/박세아 → 박새연"

처럼 `/` 앞 문자열을 임의로 선택하여
자동승인하는 로직은 추가하지 마십시오.

`A/B`가 어떤 의미인지 서버가 확정할 수 없으므로
자동승인 대상으로 만들지 않습니다.

이런 경우는 pending으로 유지하고
관리자가 학생을 선택하여 승인합니다.

━━━━━━━━━━━━━━━━━━━━
3. pending_reason=NULL 문제 수정
━━━━━━━━━━━━━━━━━━━━

현재 26건은 매칭 시도가 학부모의
getParentStatusV2() 호출에 의존할 수 있는 상태입니다.

가입신청이 생성된 뒤
학부모가 다시 상태조회해야만 매칭이 시도되는 구조에
의존하지 않도록 수정하십시오.

POST /auth/pool-join-request 처리 과정에서

신청 저장
→ 자동매칭 시도
→ 성공 시 approved 연결
→ 실패 시 정확한 pending_reason 저장

까지 서버에서 완료되어야 합니다.

신규 신청이 이유 없이
pending_reason=NULL 상태로 방치되지 않게 합니다.

단, 기존 26건을 임의 승인하지 마십시오.

기존 NULL pending 건은
안전한 기존 자동매칭 규칙으로 재시도 가능한
관리자용/서버용 처리 방법을 검토하고 테스트하십시오.

━━━━━━━━━━━━━━━━━━━━
4. 관리자 수동승인 수정
━━━━━━━━━━━━━━━━━━━━

현재 문제:

name_mismatch
→ matched_student_id = NULL
→ 승인 클릭
→ 서버가 같은 이름으로 다시 검색
→ 다시 실패
→ 승인 불가능

이 구조를 제거합니다.

수동승인 API가 선택된 student_id를 받을 수 있게 합니다.

PATCH /admin/parent-v2-pending/:id

승인 예:

{
  "action": "approve",
  "student_id": "<관리자가 선택한 실제 student.id>"
}

서버는 student_id가 전달되면
이름 자동매칭을 다시 요구하지 않습니다.

대신 반드시 검증:

1. student 존재
2. student.swimming_pool_id === pending.pool_id
3. parent 존재
4. 요청 관리자에게 해당 pool 권한 존재
5. 기존 parent_students 연결 확인
6. 중복 생성 방지

검증 통과:

parent_students
→ approved

parent_v2_pending
→ matched

matched_student_id
→ 선택한 student_id

기존 pending_reason은 감사/원인 확인용으로
보존 가능한지 현재 구조에 맞춰 처리하십시오.

5. 관리자 UI — 학생 선택
━━━━━━━━━━━━━━━━━━━━

name_mismatch 등으로
matched_student_id가 없는 신청에서
[승인]을 누르면 그냥 실패시키지 마십시오.

해당 수영장의 학생을 선택할 수 있는
최소한의 학생 선택 UI를 띄웁니다.

목표:

학부모 신청
박세연/박세아
010-....

[거절] [승인]

승인 선택
↓

학생 선택

검색: [ 학생 이름 ]

박세연
박세아
...

↓

박세연 선택

↓

최종 승인

학생 목록은 반드시 현재 pool 학생만 조회합니다.

기존 학생 검색 API를 재사용할 수 있으면
새 API를 만들지 마십시오.

학생 수가 최대 1,000명일 수 있으므로
전체 목록을 무조건 한 화면에 렌더링하지 말고
기존 검색 구조가 있다면 그것을 재사용하십시오.

━━━━━━━━━━━━━━━━━━━━
6. 이미 matched_student_id가 있는 경우
━━━━━━━━━━━━━━━━━━━━

자동매칭 과정에서 student가 특정되어 있지만
관리자 확인만 필요한 요청이라면

기존처럼 승인 버튼 한 번으로 처리합니다.

불필요하게 학생 선택창을 띄우지 않습니다.

즉:

matched_student_id 있음
→ [승인]
→ 바로 승인

matched_student_id 없음
→ [승인]
→ 학생 선택
→ 승인

━━━━━━━━━━━━━━━━━━━━
7. rejected → approved 허용
━━━━━━━━━━━━━━━━━━━━

거절은 영구 봉쇄가 아닙니다.

거절됨 탭에서도
관리자가 다시 확인하여 승인할 수 있게 합니다.

rejected 카드:

[승인]

필요하면 기존 rejection 정보는 표시 유지.

승인 시:

matched_student_id 있음
→ 바로 승인 가능

matched_student_id 없음
→ 학생 선택
→ 승인

서버:

pending → matched 허용
rejected → matched 허용

단 이미 정상적으로 matched/approved 된 요청에
중복 승인 요청이 들어오면
중복 parent_students row를 생성하지 마십시오.

idempotent하게 처리 가능한 구조인지 확인하여 적용합니다.

━━━━━━━━━━━━━━━━━━━━
8. 거절 처리
━━━━━━━━━━━━━━━━━━━━

pending → rejected 허용.

이미 rejected인 요청을 다시 reject하는 것은
오류를 만들 필요 없이 현재 상태 유지가 가능한지 검토.

이미 정상 승인된 요청을 단순히
pending request PATCH로 rejected 처리하여
기존 parent_students 연결을 끊는 기능은 만들지 마십시오.

"승인 취소/학부모 연결 해제"는 별도 기능입니다.

이번 작업 범위 아님.

9. 사용자 표시 문구 개선
━━━━━━━━━━━━━━━━━━━━

현재:

자동승인 실패: 학생 이름 불일치

는 내부 실패처럼 보여 사용자/관리자에게
불필요하게 오류 느낌이 강합니다.

관리자 화면에서는 다음처럼 변경:

학생 이름 확인 필요
전화번호 확인 필요
동명이인 확인 필요
학생 연결 확인 필요

예:

기존
"자동승인 실패: 학생 이름 불일치"

변경
"학생 이름 확인 필요"

이것은 시스템 장애가 아니라
관리자 확인이 필요한 요청이라는 의미로 표시합니다.

서버의 pending_reason 코드 자체는 유지합니다.

11. 필수 테스트
━━━━━━━━━━━━━━━━━━━━

CASE 1
정확한 이름 + 정확한 보호자 전화번호
→ 자동승인

CASE 2
이름 공백 차이 + 정확한 전화번호
→ 자동승인

CASE 3
전화번호 하이픈 차이
→ 자동승인

CASE 4
이름 불일치
→ pending
→ 관리자 승인
→ 학생 선택
→ approved 성공

CASE 5
"A/B" 형태 이름
→ 임의 자동승인 금지
→ pending
→ 관리자 학생 선택
→ approved

CASE 6
전화번호 불일치
→ pending
→ 관리자 확인 후 정확한 학생 선택
→ approved

CASE 7
동명이인
→ 자동승인 금지
→ 관리자 학생 선택

CASE 8
다른 pool의 student_id를 강제로 전송
→ 서버 403/400
→ 연결 생성 0

CASE 9
rejected 요청
→ 거절됨 탭
→ 승인
→ approved 성공

CASE 10
rejected + matched_student_id 없음
→ 학생 선택
→ 승인 성공

CASE 11
이미 approved된 동일 parent/student 재승인
→ duplicate row = 0

CASE 12
신규 가입
→ 학부모가 상태조회하지 않아도
자동매칭 또는 pending_reason 결정

CASE 13
기존 pending_reason=NULL 건 재시도
→ 안전조건 충족 건만 자동연결
→ 불확실한 건 pending 유지

CASE 14
기존 approved 학부모 로그인/학생조회
→ 회귀 없음
