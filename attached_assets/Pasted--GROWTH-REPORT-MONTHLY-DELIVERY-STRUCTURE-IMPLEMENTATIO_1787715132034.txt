0. 먼저 AUTO-PUBLISH SAFETY 최소 확인
==================================================

수정 전에
autoApproveAndPublishForDelivery(report)
및 직전 caller만 read-only 확인.

5일 SYSTEM_MONTHLY_AUTO publish 전에
실제로 아래를 검증하는지 보고:

- student.status = active
- report_period = 정확한 previous month
- product_status = REVIEW_REQUIRED
- analysis_status가 완료 계열
- grounding_status가 publish-safe
- growth_framing_status가 PASS
- report_content 존재/유효
- deleted report 아님

이미 모두 검증하면 그대로 사용.

누락된 조건이 있으면
그 조건만 최소 추가.

REVIEW_REQUIRED라는 상태만으로 자동 승인 금지.

1. PARENT FEED에 GROWTH REPORT 통합
==================================================

현재 parent feed API가:

class_diaries
+
student_photos

를 합치는 기존 구조를 유지하면서

+
PUBLISHED growth_reports

를 추가.

별도 물리 feed table 생성 금지.

Growth Report item은 기존 피드 response contract 안에서
명확한 item type으로 구분.

예:
type = GROWTH_REPORT
또는 현재 feed naming convention에 맞는 실제 값.

반드시 실제 기존 타입 구조 확인 후 사용.
새 naming 추측 금지.

Growth Report feed item 최소 정보:

- report_id
- student_id
- report_period
- published_at
- type
- detail route/deep link에 필요한 식별자

정렬:
기존 feed와 published_at/date 기준으로 자연스럽게 섞임.

==================================================
3. FEED IDEMPOTENCY
==================================================

Growth Report는 physical feed row를 새로 만들지 않음.

growth_reports의 PUBLISHED record를
feed response에 projection하는 방식 사용.

따라서 같은 report_id가
한 feed response에 중복 포함되지 않도록
deterministic merge/dedup 적용.

DB migration 불필요.

==================================================
4. PUSH EXACT-ONCE DB CONSTRAINT
==================================================

현재:

notifications
SELECT existing
→ INSERT

방식은 race condition 존재.

최종 요구:
동일 growth report에 동일 recipient push 최대 1회.

최소 migration 추가.

현재 notifications schema/index를 먼저 확인하고
기존 데이터와 충돌 여부 확인.

목표 unique key:

(type, ref_id, recipient_id)

단,
이 조합이 Growth Report 외 다른 notification type에도
의미적으로 안전한지 먼저 확인.

전체 notification system에 적용하면 충돌 가능성이 있으면
GROWTH_REPORT_PUBLISHED에만 적용 가능한
partial unique index 사용.

예시 개념:
UNIQUE (type, ref_id, recipient_id)
WHERE type = 'GROWTH_REPORT_PUBLISHED'

실제 DB dialect/schema에 맞춰 작성.

기존 duplicate row가 존재하면
migration 실행 전 STOP하고 보고.
임의 삭제 금지.

==================================================
5. PUSH INSERT RACE SAFE
==================================================

DB unique constraint가 들어간 뒤
notifyGrowthReportPublished()가
unique conflict를 정상적인 "already sent"로 처리하도록 수정.

중복 충돌을 500 error로 만들지 말 것.

기존 SELECT pre-check는 유지해도 되지만
최종 보장은 DB constraint.
