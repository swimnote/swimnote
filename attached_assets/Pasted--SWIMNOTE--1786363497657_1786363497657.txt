[SWIMNOTE 선생님 모드 — 보강대기 학생 초경량 실시간 인덱스 추가]

목적:

선생님 모드의 "보강대기" 목록에 학생이 많아질 경우
스크롤만으로 학생을 찾기 어려운 문제를 해결한다.

이번 기능은 거대한 검색 화면이나 별도 검색 페이지가 아니다.

보강대기 화면 맨 위에 붙는
"아주 가볍고 빠른 학생 이름 인덱스"
를 만든다.

핵심 UX:

검색창 터치
→ 키보드 올라옴
→ 학생 이름 입력
→ 입력 즉시 목록 실시간 필터링
→ 검색 버튼 없음
→ 키보드가 떠 있어도 목록 확인 가능
→ 목록/바깥 영역 터치 또는 스크롤
→ 키보드 즉시 내려감
→ 바로 학생 선택/스크롤 가능

1. 위치
━━━━━━━━━━━━━━━━━━━━━━

보강대기 목록 최상단에
작은 검색 인덱스를 배치한다.

화면의 큰 영역을 차지하면 안 된다.

별도 검색 화면 금지.
전체화면 Modal 금지.
큰 검색 카드 금지.

보강대기 화면의 일부처럼 자연스럽게 들어가야 한다.

예:

┌──────────────────────────┐
│  학생 이름 검색          🔍 │
└──────────────────────────┘

[기존 보강대기 학생 목록]

단 위 도형을 그대로 디자인하지 말 것.

현재 SWIMNOTE 디자인 규칙에 맞게
심플하게 구현한다.

━━━━━━━━━━━━━━━━━━━━━━

권장:

높이 약 36~42px 범위.

- 큰 카드 금지
- 과한 round 금지
- 진한 배경 금지
- 그림자 금지
- 검색 버튼 금지
- "검색"이라는 별도 실행 버튼 금지

placeholder:

"학생 이름 검색"

정도.

Pretendard 적용.

━━━━━━━━━━━━━━━━━━━━━━
3. 실시간 필터
━━━━━━━━━━━━━━━━━━━━━━

검색 실행 버튼을 만들지 않는다.

TextInput의 값이 변경되는 즉시:

searchText
→ local filter
→ visibleStudents

로 화면을 바로 갱신한다.

예:

전체:
김민수
김서준
박태웅
서태웅
이민재

"서"
입력 즉시:

김서준
서태웅

"서태"
입력 즉시:

서태웅

검색 버튼을 누르는 과정 없음.

4. 서버 검색 금지 원칙
━━━━━━━━━━━━━━━━━━━━━━

현재 보강대기 목록을 이미 화면에서 받아온 상태라면
검색 문자 입력 때마다 API 호출하지 않는다.

현재 로드된 배열에서 local filter를 우선한다.

이유:

- 즉각 반응
- 서버 부하 없음
- 네트워크 지연 없음
- 검색 UX 단순화

단 현재 화면이 pagination/부분 로드 구조라서
전체 학생이 client에 존재하지 않는다면
실제 코드 확인 후 먼저 보고한다.

추측하여 구현하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
5. 검색 대상
━━━━━━━━━━━━━━━━━━━━━━

기본 검색:

student.name

학생 이름 기준.

최소 요구:

- 한글 이름
- 이름 일부
- 성
- 가운데/마지막 글자

모두 includes 방식으로 검색 가능.

예:

서태웅

검색:

"서" → 검색됨
"태" → 검색됨
"웅" → 검색됨
"태웅" → 검색됨

trim 처리.

공백 입력은 빈 검색과 동일.

대소문자 영문 이름이 존재한다면
case-insensitive 처리.

━━━━━━━━━━━━━━━━━━━━━━
6. 검색 중 정렬
━━━━━━━━━━━━━━━━━━━━━━

검색했다고 기존 학생 순서를 임의 변경하지 않는다.

현재 보강대기 목록의 정렬 순서를 그대로 유지하면서
조건에 맞지 않는 학생만 제외한다.

검색 결과를 새로운 가나다순으로 재정렬하지 않는다.

현재 정렬 정책 보호.

━━━━━━━━━━━━━━━━━━━━━━
7. 키보드 동작 — 매우 중요
━━━━━━━━━━━━━━━━━━━━━━

검색창 터치:

→ 키보드 정상 표시
→ TextInput focus

검색 중에도
학생 목록이 키보드 위에서 정상적으로 보여야 한다.

키보드가 목록을 전부 덮지 않도록
현재 화면 구조에 맞는 KeyboardAvoiding 처리를 검토.

단 전체 화면 레이아웃을 과하게 밀어올리지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
8. 검색 버튼 없음
━━━━━━━━━━━━━━━━━━━━━━

keyboard return key를 눌러야 검색되는 구조 금지.

onSubmitEditing 기반 검색 금지.

입력 한 글자마다 바로 filter.

returnKeyType은 필요하면 "done" 사용 가능하지만
검색 실행과 연결하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
9. 바깥 화면 터치 → 키보드 즉시 닫기
━━━━━━━━━━━━━━━━━━━━━━

핵심 UX.

키보드가 올라와 있는 상태에서
학생 목록이나 검색창 바깥을 터치하면:

Keyboard.dismiss()

즉시 실행.

그 뒤 터치한 학생의 onPress가
먹히지 않으면 안 된다.

즉:

첫 번째 터치:
키보드만 닫힘

두 번째 터치:
학생 선택

이런 구조 금지.

가능하면 첫 터치에서:

키보드 닫힘
+
학생 선택

둘 다 정상 작동해야 한다.

━━━━━━━━━━━━━━━━━━━━━━
10. 스크롤 → 키보드 닫기
━━━━━━━━━━━━━━━━━━━━━━

학생 목록을 손가락으로 스크롤하기 시작하면
키보드가 자연스럽게 내려가야 한다.

FlatList라면 예:

keyboardDismissMode="on-drag"

또는 플랫폼에 맞는 안전한 equivalent.

keyboardShouldPersistTaps 설정도 확인.

목표:

키보드 때문에 학생 리스트 조작이 막히면 안 됨.

━━━━━━━━━━━━━━━━━━━━━━
11. keyboardShouldPersistTaps
━━━━━━━━━━━━━━━━━━━━━━

학생 item을 눌렀을 때
키보드가 떠 있어도 onPress가 정상 동작해야 한다.

현재 List component에 적절하게:

keyboardShouldPersistTaps="handled"

또는 실제 구조상 더 적절한 값을 적용.

무조건 값만 넣지 말고
현재 FlatList/ScrollView nesting 구조 확인 후 결정한다.

━━━━━━━━━━━━━━━━━━━━━━
12. 학생 선택
━━━━━━━━━━━━━━━━━━━━━━

검색 결과에서 학생을 탭하면
현재 기존 보강대기 학생 선택 동작을 그대로 실행.

검색 전/후 학생 선택 로직을 따로 만들지 않는다.

기존 onPress 재사용.

검색은 "보이는 목록을 줄이는 기능"일 뿐이다.

보강 신청/배정 로직은 절대 변경하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
13. 키보드 내려간 후 검색어 유지
━━━━━━━━━━━━━━━━━━━━━━

바깥 화면 터치나 스크롤로
키보드만 내려가도 검색어는 유지한다.

예:

검색어 "서태"
→ 서태웅만 표시

스크롤 터치
→ 키보드 내려감
→ 검색어 "서태" 유지
→ 서태웅 결과 유지

검색어를 지우는 동작과
키보드를 닫는 동작은 분리한다.

━━━━━━━━━━━━━━━━━━━━━━
14. 검색 초기화
━━━━━━━━━━━━━━━━━━━━━━

검색어가 있을 때만
아주 작은 X(clear) 아이콘을 표시할 수 있다.

X 탭:

searchText = ""

→ 전체 보강대기 학생 즉시 복원.

큰 "초기화" 버튼 금지.

X가 없어도 TextInput 기본 clearButtonMode가
현재 플랫폼에서 적절하다면 그것을 우선 검토.

iOS/Android 양쪽 동작을 고려.

━━━━━━━━━━━━━━━━━━━━━━
15. Empty State
━━━━━━━━━━━━━━━━━━━━━━

두 종류를 구분한다.

A. 실제 보강대기 학생 0명

→ 기존 empty UI 유지.

B. 학생은 있는데 검색 결과 0명

→ 가볍게:

"검색 결과가 없습니다."

표시.

실제 보강대기 0명 메시지와 혼동하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
16. 검색창이 스크롤되면 안 되는지 조사
━━━━━━━━━━━━━━━━━━━━━━

검색 인덱스는 학생이 많아져도
계속 접근 가능해야 하는 목적이다.

따라서 가능하면:

목록 위에 고정

또는

sticky header

방식을 검토.

단 현재 화면 구조상 고정할 경우
레이아웃 충돌이 발생하면 억지로 sticky 처리하지 않는다.

현재 구조를 확인해서:

- fixed header
- ListHeaderComponent
- stickyHeaderIndices

중 가장 단순하고 안정적인 구조 선택.

검색창 하나 때문에
화면 구조 전체를 재작성하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
17. 디자인
━━━━━━━━━━━━━━━━━━━━━━

Simple is best.

검색창이 기능의 주인공처럼 보이면 안 된다.

주인공은 학생 목록이다.

검색창:

- 얇음
- 작음
- 가벼움
- 눈에 띄지만 과하지 않음

검색 아이콘도 작게.

SWIMNOTE 기존 Navy 기반.

과한 민트/그라디언트 금지.

검색창 내부에 설명 텍스트 여러 개 금지.

━━━━━━━━━━━━━━━━━━━━━━
18. 성능
━━━━━━━━━━━━━━━━━━━━━━

학생 수가 많아져도
입력할 때 버벅이지 않도록 한다.

useMemo 등으로:

filteredStudents

계산 권장.

예:

const filteredStudents = useMemo(() => {
  const q = searchText.trim().toLowerCase();
  if (!q) return waitingStudents;

  return waitingStudents.filter(...)
}, [waitingStudents, searchText]);

단 실제 변수명은 현재 코드에 맞춘다.

과도한 debounce 불필요.

로컬 필터라면 입력 즉시 반응해야 한다.

━━━━━━━━━━━━━━━━━━━━━━
19. 상태 초기화
━━━━━━━━━━━━━━━━━━━━━━

보강대기 화면을 나갔다가 다시 들어왔을 때
검색어를 유지할지 현재 화면 UX를 검토.

기본 권장:

화면을 새로 진입하면 검색어 초기화.

다른 학생을 찾으러 다시 들어왔는데
이전 검색 때문에 목록 일부만 보이는 혼란 방지.

단 기존 navigation cache 구조를 먼저 확인.
