[SWIMNOTE 학부모 요청 — 업무별 양방향 대화 스레드 설계 및 구현]

목표:

parent_student_requests의 각 요청 1건마다
독립적인 "업무 대화 스레드"를 제공한다.

기존 업무카드는 커지지 않는다.
전체 대화는 요청별 Modal에서만 표시한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 핵심 원칙
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

학부모 요청 1건
= parent_student_requests 1건
= 업무 대화 스레드 1개

업무 상태와 대화를 분리한다.

업무 상태:
pending / done / rejected

대화:
학부모 메시지
선생님 메시지
시스템 메시지

메시지를 보냈다는 이유로
업무 상태를 자동 done 처리하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. 새 메시지 저장 구조
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

기존 parent_student_requests.content를
대화 로그로 덧붙여 사용하지 않는다.

요청별 메시지 저장 구조를 별도로 만든다.

예상 테이블:

parent_request_messages

필수 개념 필드:

id

pool_id
sender_type
sender_id
message_type
content
created_at

sender_type:
parent
teacher
system

message_type:
message
system

실제 Repository/DB convention을 확인해서
현재 naming 규칙에 맞춘다.

Migration이 필요하면
기존 schema와 충돌 없는 최소 Migration으로 구현한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. 기존 최초 요청 내용
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

parent_student_requests.content는
"최초 요청 원문"으로 그대로 유지한다.

업무 대화 Modal을 열면
최초 메시지로 해당 content를 보여준다.

이를 위해 기존 데이터를
강제로 parent_request_messages에 복제할 필요는 없다.

렌더 시:

최초 요청 content
+
이후 parent_request_messages

를 시간순으로 보여줄 수 있다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

6. 학부모 업무 대화 Modal
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 학부모:

알림
→ 내 요청
→ 요청 카드

요청 카드를 누르면
동일 request_id의 업무 대화 Modal을 연다.

학부모도:

선생님 메시지 확인
메시지 재회신

가능.

단 업무 상태 변경 권한은 없다.

학부모는 done/rejected를 변경할 수 없다.

7. API
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 구조를 확인하고 최소 API 추가.

예:

GET
/parent-requests/:requestId/messages

POST
/parent-requests/:requestId/messages

Teacher/Parent 모두 같은 resource를 사용하되
서버에서 role/ownership을 검증한다.

POST body:

{
  content: string
}

sender는 client body를 신뢰하지 말고
JWT/session에서 서버가 결정한다.

8. 권한
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Parent:

자신에게 연결된 자녀의 request만
읽기/메시지 전송 가능.

Teacher:

현재 visibility 정책상 볼 수 있는 학생의 request만
읽기/메시지 전송 가능.

다른 pool 접근 금지.

Admin 정책은 현재 필요하면 read 가능 여부만
기존 권한 체계에 맞춰 판단.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. 시스템 메시지
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

업무 이벤트도 같은 대화에 기록한다.

예:

선생님 최초 확인:
"선생님이 보강 요청을 확인했습니다."

업무 완료:
"보강 요청이 처리됐습니다."

거절:
"보강 요청을 처리하지 못했습니다."

이 메시지는:

sender_type = system
message_type = system

으로 저장.

Push/notification과 대화 기록은 별개.

Push:
사용자에게 새 이벤트 알림.

request message:
업무 안의 영구 기록.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
10. 요청 유형별 문구
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

결석 신청

postpone:
연기 신청

makeup:
보강 요청

withdrawal:
퇴원 신청

counseling:
상담 요청

inquiry:
문의

시스템 메시지는 request_type에 맞춰 생성한다.

예:

"선생님이 보강 요청을 확인했습니다."
"보강 요청이 처리됐습니다."

모든 요청을
"요청이 처리됐습니다"
한 문구로 통일하지 않는다.

12. 학부모 재회신
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

학부모가 같은 스레드에서 답장:

메시지 DB 저장
→ 담당 선생님 unread 증가
→ 홈 봉투 badge 증가
→ 쪽지보관함 학부모 요청 카드 unread 표시

기존 Messenger 공지로 복제 금지.

parent request thread 안에서만 처리.

13. 업무 처리와 회신 조합
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

선생님 처리 완료 시:

회신 텍스트가 비어 있으면
→ system message만 저장
→ 기존 처리완료 notification/push

회신 텍스트가 있으면
→ teacher message 저장
→ system completion message 저장
→ 학부모에게 결과 notification/push

즉 선생님은 필요하면:

"8월 18일 17시 반으로 배정했습니다."

같은 전달사항을 같이 남길 수 있다.

단 단순 메시지 전송과 업무 완료를 구분한다.

기존 unread 기능을 깨지 않는다.
