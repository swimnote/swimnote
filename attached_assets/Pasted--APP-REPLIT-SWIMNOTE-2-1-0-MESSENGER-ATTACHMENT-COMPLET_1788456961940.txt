# SWIMNOTE 2.1.0
# MESSENGER ATTACHMENT COMPLETE FIX
# + MEMBER PHONE CALL LINK
# + IOS OTA

이번 작업은 메신저 첨부 기능을 실제 사용 가능한 상태까지 완성하는 작업이다.

현재 발견된 문제와 요구사항을 모두 한 번에 처리한다.

============================================================
최종 작업 범위
============================================================

A. 첨부 버튼
→ 앨범 / 파일 선택

B. 현재 파일 업로드 시 발생하는
"Fetch failed"
정확한 원인 조사 및 수정

C. 파일 업로드
→ 상대방 메신저에서도 파일 표시
→ 상대방이 다운로드/저장 가능

D. 사진 업로드
→ 메신저 안에서 사진 미리보기 표시
→ 상대방도 사진 확인
→ 사진 다운로드/저장 가능

E. 사진 다중 선택
→ 여러 장을 한 번에 선택
→ 한 번에 업로드
→ 메신저에서 묶음 형태로 표시

F. 회원정보카드 전화번호
→ 전화번호 탭 시 전화걸기 연결

============================================================
중요 원칙
============================================================

이번 작업은 UI만 흉내 내는 작업이 아니다.

반드시 실제 데이터 흐름:

선택
→ 업로드
→ 서버/Object Storage 저장
→ 메시지 저장
→ 상대방 수신
→ 상대방 표시
→ 다운로드/저장

까지 END-TO-END로 검증한다.

특히 현재 발생하는:

Fetch failed

를 임시 catch로 숨기거나
에러 메시지만 바꾸는 방식 금지.

정확한 ROOT CAUSE를 찾아서 수정한다.

============================================================
B. "FETCH FAILED" ROOT CAUSE 조사
============================================================

현재 파일 선택 후 업로드 과정에서:

Fetch failed

발생.

절대 추측해서 수정하지 말 것.

실제 실행 경로를 따라가며
어디서 실패하는지 먼저 특정한다.

============================================================
B-1. 반드시 확인
============================================================

클라이언트:

- picker result URI
- file:// URI 여부
- 파일명
- MIME type
- size
- FormData 생성
- FormData append 형식
- request endpoint
- auth header
- Content-Type 처리
- multipart boundary
- fetch 호출 시점
- response status
- response body

서버:

- 실제 attachment endpoint 존재 여부
- 현재 production route와 client endpoint 일치 여부
- 인증 통과 여부
- multipart parser
- upload middleware
- body size 제한
- MIME 제한
- Object Storage upload
- R2/S3 credential
- object key 생성
- DB message INSERT
- response JSON

특히 React Native multipart에서
Content-Type을 수동 지정해서 boundary가 깨지는 문제인지도 확인.

단:
이것이 원인이라고 가정하지 말고 실제 코드/로그로 확인.

============================================================
C-2. 상대방 다운로드
============================================================

중요:

업로드한 파일은
"보낸 사람 기기에만 존재하는 local URI"
를 저장하면 안 된다.

메시지에는 반드시
서버/Object Storage에서 다시 접근 가능한
attachment reference가 있어야 한다.

상대방 메신저에서도:

파일 bubble 탭
→ 파일 다운로드/열기

가능해야 함.

============================================================
C-3. Private storage 유지
============================================================

Object Storage가 private 구조라면
bucket을 public으로 바꾸지 말 것.

기존 SWIMNOTE 보안 정책에 맞게:

- authenticated download endpoint

또는

- 서버가 생성하는 signed URL / presigned URL

등 현재 구조에 맞는 방법 사용.

영구 public URL로 보안을 약화시키지 말 것.

============================================================
C-4. iOS 파일 저장
============================================================

파일 다운로드 시:

iOS에서 실제 파일을 받을 수 있어야 함.

가능하면:

다운로드
→ native share/save UI
→ "파일에 저장"

가능하도록 처리.

기존 Expo FileSystem / Sharing 구조가 있으면 재사용.
