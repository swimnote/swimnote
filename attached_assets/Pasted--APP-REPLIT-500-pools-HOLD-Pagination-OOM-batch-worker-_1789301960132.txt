A.

기존 ACTIVE cycle이면 early return

B.

중간 실패 후 다음 실행에서
`INSERT ... ON CONFLICT DO NOTHING`

둘 다 동시에 성립할 수 없습니다.

중요한 종료조건:

scheduler가 학생 INSERT 중간에 죽어도
다음 실행에서 **누락 학생을 다시 ensure**할 수 있어야 합니다.

기존 ACTIVE cycle이라고 해서
학생 report row ensure 단계까지 건너뛰면 안 됩니다.

2. Scheduler lock heartbeat 추가
━━━━━━━━━━━━━━━━━━━━━━

확인된 현재 상태:

* lock TTL = 600초
* refreshLock() 함수 이미 존재
* Scheduler에서는 호출하지 않음
* 500 pools / 200,000 INSERT 가정 시
  4ms/INSERT만 잡아도 약 800초

따라서 500 pools 목표에서는
TTL보다 실행시간이 길어질 가능성이 실제 존재합니다.

새 lock 시스템을 만들지 마십시오.

이미 존재하는:

`refreshLock(...)`

을 재사용하십시오.

Scheduler 실행 중 약 60초 간격 또는
pool loop의 적절한 지점에서 TTL을 갱신하십시오.

조건:

* 같은 scheduler lock만 갱신
* 기존 acquire/release 구조 유지
* refresh 실패 시 무조건 정상이라고 계속 진행하지 말 것
* owner/token 구조가 현재 존재한다면 그대로 준수

TTL 자체를 크게 늘리는 방식으로 해결하지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
3. 학생 INSERT는 pool 단위 bulk화

반드시 기존 의미 유지:

`ON CONFLICT DO NOTHING`

즉:

* 기존 row 덮어쓰기 금지
* 이미 생성된 report 보존
* 재실행 idempotent 유지

500 pools 전체를 하나의 거대한 INSERT로 만들지 마십시오.

**pool 단위 또는 안전한 chunk 단위**로만 처리하십시오.
