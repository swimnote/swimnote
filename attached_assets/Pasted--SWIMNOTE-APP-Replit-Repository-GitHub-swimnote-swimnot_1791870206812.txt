9. session_type Contract
━━━━━━━━━━━━━━━━━━━━━━

Production DB에 이미 존재하는 session_type을
Drizzle/schema application model에도 정확하게 반영합니다.

먼저 실제 기존 writer에서 사용하는 값들을 확인하세요.

신규 write에서는 session_type을
명시적으로 결정해서 저장해야 합니다.

예:

regular class attendance
→ regular

makeup attendance
→ 현재 기존 코드/도메인에서 사용하는 명시적 canonical value

기존 코드에 makeup용 값이 이미 있으면 그것을 재사용.
새 문자열을 임의로 만들지 마세요.

클라이언트가 임의 session_type을 보내면
그 값을 그대로 신뢰하지 말고
서버가 endpoint/context를 기준으로 결정/검증합니다.

10. Partial Unique Contract
━━━━━━━━━━━━━━━━━━━━━━

legacy NULL 데이터를 건드리지 않으면서
신규 명시적 attendance만 DB가 보호하도록 합니다.

migration 직전 READ ONLY preflight:

WHERE
class_group_id IS NOT NULL
AND session_type IS NOT NULL

범위에서

(student_id, class_group_id, date, session_type)

duplicate가 0인지 확인.

0이 아니면 HOLD.

0이면
해당 범위에 대한 partial unique index/constraint를 적용하세요.

목적:

기존 NULL legacy는 그대로 보존

BUT

앞으로 명시적 class + session_type으로 생성되는 출석은
DB 레벨에서 중복 생성 불가.

현재 발견된 2026-07-20 duplicate는
session_type=NULL이므로
이번 partial unique 대상에서 제외되어 그대로 보존됩니다.

11. Atomic Attendance Write
━━━━━━━━━━━━━━━━━━━━━━

기존:

SELECT
→ 없으면 INSERT

식의 race 가능한 check-then-insert에만
의존하지 않도록 합니다.

신규 canonical attendance는
DB unique identity와 원자적인 UPSERT/충돌 처리를 사용하세요.

핵심:

student + class + date + session_type

이 동일하면
동시에 두 요청이 와도 두 row를 만들지 않습니다.

기존 row의 status 변경이면
같은 canonical row를 update.

다른 class라면
같은 student/date여도 별개 row.

예:

A / 2026-10-13 / TUE_CLASS / regular
A / 2026-10-13 / THU_CLASS / regular

→ 둘 다 존재 가능.

12. Legacy Read Compatibility
━━━━━━━━━━━━━━━━━━━━━━

과거 attendance 조회가 깨지면 안 됩니다.

session_type=NULL 또는 class=NULL인
기존 legacy row도 history 화면에서는 계속 조회 가능.

단 신규 write 과정에서
임의로 첫 legacy row를 선택하여 덮어쓰지 마세요.

canonical key가 불명확한 legacy row를 수정해야 하는
기존 workflow가 있다면
row id 기반으로 명확하게 처리하거나
conflict로 안전하게 중단.

이번 작업에서 legacy row 자동 upgrade는 하지 마세요.
