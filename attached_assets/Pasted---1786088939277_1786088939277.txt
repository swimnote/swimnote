D. 보강과 요청 시스템의 경계
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

반드시 다음 경계를 유지한다.

실제 보강 업무 데이터:

makeup_sessions

학부모 요청 데이터:

parent_student_requests

두 시스템은 동일한 데이터가 아니다.

학부모 요청은:

"보강을 해달라는 요청"

이고,

makeup_sessions는:

"실제 보강 업무 상태"

이다.

이번 작업은 makeup_sessions 기반
기존 보강 기능 회귀 조사다.

parent_student_requests를 맞추기 위해
makeup_sessions 정책을 바꾸지 않는다.

반대로

makeup_sessions 문제를 해결하기 위해
parent_student_requests 구조를 바꾸지도 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

link-result는 기존 보강 기능을 변경하는 기능이 아니다.

목적:

이미 처리된 실제 업무 결과
↓
학부모 요청
↓
연결

따라서 link-result 때문에:

makeup_sessions expire_at 변경

등을 수행하면 안 된다.

이번 조사에서도 link-result 구현 자체를 수정하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
F. PHASE 1 영향 조사는 READ-ONLY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"최근 PHASE 1이 보강 코드에 미친 diff"

항목은 반드시 READ-ONLY Git 비교만 한다.

허용:

git diff

금지:

Write

자동 수정

PHASE 1 파일을 발견했다고 해서
"정리할 부분이 있다"며 수정하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
G. 공용 파일 수정도 금지
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

보강 코드가 어떤 공용 helper/API utility를 사용하더라도

그 공용 파일을 수정하면
학부모 요청/알림/메신저에 영향을 줄 가능성이 있다.

따라서 이번 조사에서는:

apiRequest 공용 구현
SessionContext
navigation 공용 코드
auth
JWT
공용 notification helper
공용 request helper
공용 API client

등은 READ-ONLY다.

캐시 문제가 의심되더라도
apiRequest 전역 캐시를 수정하지 않는다.

원인이 실제로 캐시로 CONFIRMED되더라도
이번 단계에서는:

"보강 endpoint에 한정하여 어떻게 복구할지"

최소 수정안을 보고만 한다.

실제 수정은 별도 승인 후 수행한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

link-result

중 하나라도 영향을 받을 가능성이 있는가?

YES라면:

수정 실행 금지.

더 좁은 보강 전용 복구 방법을 찾는다.

이번 복구의 기본 원칙:

"보강만 고치고 다른 기능은 0줄 변경"

J. Git 변경 감시
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

조사 시작 시:

git status --short

조사 종료 직전 다시:

git status --short

실행.

시작 당시 존재하지 않았던 변경이
조사 중 하나라도 생겼으면:

즉시 작업 중단.

어떤 파일이 변경됐는지 보고.

Commit 금지.
reset 금지.
checkout 금지.
restore 금지.

사용자 승인 없이
변경을 되돌리는 Git 명령도 실행하지 않는다.

특히 Replit auto-commit이 발생하면:

즉시 중단.

Commit SHA
Commit message
포함 파일

만 보고한다.

추가 Git 조작 금지.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
