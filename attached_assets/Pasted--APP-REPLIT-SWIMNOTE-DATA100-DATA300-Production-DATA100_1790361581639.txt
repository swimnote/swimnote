[SWIMNOTE — DATA100 / DATA300 추가 저장공간 구독 Production 구현]

DATA100 / DATA300 구조 조사 승인합니다.

이제 실제 구현을 진행하십시오.

확정 제품 정책:

DATA100
com.swimnote.data100.monthly
→ 현재 플랜 기본 저장공간 +100GB

DATA300
com.swimnote.data300.monthly
→ 현재 플랜 기본 저장공간 +300GB

DATA는 SWIMNOTE/X 메인 구독을 대체하지 않는
독립 add-on입니다.

사용자 확인:
DATA 구독 그룹은 메인 SWIMNOTE/X 구독 그룹과 별도입니다.

중요:
DATA100 / DATA300이 서로 동일한 DATA Subscription Group에 있고
동시에 하나만 active가 되는 구조인지 실제 Store 설정을 확인하십시오.

만약 DATA100과 DATA300이 서로 별도 그룹이라
동시 구독이 가능한 상태라면
구매 CTA 활성화 전에 HOLD 보고하십시오.

[CANCELLATION]

자동갱신 취소만 된 상태.

결제된 subscription period가 남아 있으면:

- DATA 추가용량 그대로 유지
- 업로드 계속 가능
- 기존 media 유지
- 자동삭제 금지

[EXPIRATION]

실제 DATA 구독이 만료되는 순간:

- DATA 추가용량 즉시 제거
- 현재 메인 플랜 기본용량으로 즉시 복귀
- 현재 사용량 > 새 허용량이면 즉시 업로드 차단
- 초과 media purge job 즉시 생성
- 오래된 사진/영상부터 삭제 시작
- 현재 사용량 <= 허용량이 되면 삭제 종료

유예기간 없음.

“즉시 삭제”는 webhook HTTP 요청 안에서
수백 GB를 동기 삭제한다는 뜻이 아니라

만료 시:
quota 즉시 감소
+
upload 즉시 차단
+
purge job 즉시 시작

을 의미합니다.

중요:

3. extra_storage_gb는 ADDITIVE 증가 방식 금지
━━━━━━━━━━━━━━━━━━━━━━

현재 코드의:

extra_storage_gb += 100
extra_storage_gb += 300

방식은 최종 구현에서 사용하지 마십시오.

DATA100/300 중 하나만 active인 정책이므로
항상 canonical 값으로 SET하십시오.

DATA100 active:
extra_storage_gb = 100

DATA300 active:
extra_storage_gb = 300

DATA 없음 / expired:
extra_storage_gb = 0

이렇게 해야:

- duplicate webhook
- restore
- product change
- retry

때 storage가 200/400/600GB 등으로
잘못 누적되지 않습니다.

data_addon_tier와
extra_storage_gb는
같은 transaction에서 일관되게 갱신.

5. RevenueCat DATA event 처리
━━━━━━━━━━━━━━━━━━━━━━

기존 processDataWebhookEvent()를 완성합니다.

INITIAL_PURCHASE:

RevenueCat이 실제 활성 product를
data100으로 확인:

- data_addon_tier='data100'
- data_addon_status='active'
- data_addon_started_at
- data_addon_expires_at
- extra_storage_gb=100

data300이면 동일하게 300.

MAIN subscription_tier 변경 금지.

RENEWAL:

- active 유지
- expires_at 갱신
- extra_storage_gb는 canonical 100/300으로 SET

UNCANCELLATION:

- active 복구
- 현재 DATA 상품 기준 storage 유지
- purge 생성 금지

CANCELLATION:

- data_addon_status='cancelled'
- expires_at 유지/갱신
- extra_storage_gb 유지
- upload 유지
- purge 생성 금지

BILLING_ISSUE:

RevenueCat/Store에서 entitlement가 아직 active/grace이면:

- storage 유지
- 삭제 금지

EXPIRATION:

- data_addon_status='expired'
- data_addon_tier 상태는 history 의미로 보존 가능하나
  effective add-on은 inactive 처리
- extra_storage_gb=0
- 새 effective quota 즉시 계산
- 초과 시 upload_blocked=true
- purge job 생성

━━━━━━━━━━━━━━━━━━━━━━
6. PRODUCT_CHANGE — 매우 중요
━━━━━━━━━━━━━━━━━━━━━━

DATA100 ↔ DATA300 변경에서
PRODUCT_CHANGE webhook의 new_product_id만 보고
즉시 quota를 바꾸지 마십시오.

Store에서 실제로 새 상품이
“현재 active product”가 된 시점을 기준으로 적용.

특히:

DATA300 → DATA100 downgrade가
다음 갱신일부터 적용되는 경우

PRODUCT_CHANGE 이벤트 순간에
300→100으로 줄여서 media 삭제하면 안 됩니다.

반대로 DATA100→DATA300 upgrade가
즉시 effective라면
RevenueCat이 실제 active product를
300으로 확인한 시점에 300 적용.

현재 RevenueCat event payload / CustomerInfo /
기존 verified server sync 구조 중
가장 신뢰할 수 있는 canonical active-product 판정을 재사용.

Client가 보낸 productId만 믿고
quota 변경 금지.

━━━━━━━━━━━━━━━━━━━━━━

effectiveStorage =
basePlanStorage
+

그대로 유지.

예:

effective quota =
새 base storage + active DATA

로 즉시 재계산.

만약 메인 플랜 감소로
새 quota를 초과하게 된다면

실제 변경 effective 시점에
동일 storage enforcement를 적용.

이번 DATA 구현 때문에
메인 결제 lifecycle을 재설계하지 마십시오.
