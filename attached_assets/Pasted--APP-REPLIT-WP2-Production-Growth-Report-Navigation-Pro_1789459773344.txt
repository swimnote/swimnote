[보낼 곳: APP REPLIT]

WP2 Production 장애 수정 — 학생상세 교육기록 + Growth Report + Navigation

사용자가 실제 Production APP에서 직접 확인한 결과
WP2는 완료 상태가 아닙니다.

이번 작업에서는 조사만 하고 멈추지 마십시오.

반드시:

실제 Production 흐름 추적
→ Root Cause 확정
→ 최소 수정
→ 테스트
→ 필요한 배포
→ Production 재확인

까지 한 번에 완료하십시오.

중요:

보강 관리 화면은 사용자가 실제 Production에서
정상 동작을 확인했습니다.

MAKEUP 관련 코드/API/UI는 이번 작업에서 절대 수정하지 마십시오.

이번 작업 범위는 아래 3개뿐입니다.

1. 학생상세 → 일지 History
2. 학생상세/알림 → Growth Report
3. 학생상세 전체 Back Navigation

2. 제품 기준 — 절대 변경 금지
━━━━━━━━━━━━━━━━━━━━━━

Diary와 Growth Report는 모두:

STUDENT-OWNED EDUCATIONAL RECORD

입니다.

과거 작성 teacher 소유가 아닙니다.

현재 Teacher가 해당 student에 접근 가능한 상태라면:

학생의 과거~현재 기록을 볼 수 있어야 합니다.

즉:

DATA OWNERSHIP = student_id

ACCESS = current teacher → student access

입니다.

과거 diary 작성자가 현재 teacher인지 여부로
History를 제한하면 안 됩니다.

Growth Report도 동일합니다.

PUBLISHED Report는:

현재 해당 학생 접근권한이 있는 teacher
→ 과거 담당자 시절 Report까지 조회 가능.

━━━━━━━━━━━━━━━━━━━━━━
3. DIARY — 실제 Root Cause부터 추적
━━━━━━━━━━━━━━━━━━━━━━

대상 실제 화면:

teacher/student-detail
→ 일지 보기
→ diary-index

먼저 코드 수정 전에 실제 호출을 확인하십시오.

확인:

1. student-detail에서 diary-index로 전달하는 실제 params
2. student_id가 실제 해당 학생 ID인지
3. diary-index가 호출하는 endpoint
4. request URL/query
5. JWT role
6. HTTP status
7. response body
8. SQL/route filter
9. teacher_id / writer_id / class_id filter가 걸려 있는지
10. student_id 기준 History가 실제 어떻게 조회되는지

특히:

“현재 teacher가 작성한 diary”

를 조회하고 있는지,

아니면:

“현재 teacher가 접근 가능한 student의 diary”

를 조회하고 있는지

정확히 구분하십시오.

학생 상세의 일지 History는 반드시:

현재 student access 확인
+
student_id 기준
+
과거~현재 기록

이어야 합니다.

현재 teacher가 작성하지 않은 과거 일지도 포함해야 합니다.

단:

현재 접근권한 없는 teacher에게
과거 작성 기록이라는 이유만으로 열어주면 안 됩니다.

현재 access check는 유지하십시오.

기존 일반 Diary 업무화면과
학생상세 History의 목적이 다르면

일반 Diary 흐름을 망가뜨리지 말고
student History 경로만 정확하게 고치십시오.

━━━━━━━━━━━━━━━━━━━━━━
4. GROWTH REPORT HISTORY — Production 실패 추적
━━━━━━━━━━━━━━━━━━━━━━

대상:

학생상세
→ 성장리포트 보기

현재 APP에서 실제 호출하는:

GET /teacher/students/:studentId/growth-reports

를 추적하십시오.

Production에서 실제로:

- 최종 URL
- studentId
- JWT role
- HTTP status
- response body
- Render backend log

를 확인하십시오.

추측으로 수정하지 마십시오.

확인해야 할 대표 가능성:

- APP API base/path 오류
- route mount path 오류
- role/auth mismatch
- canTeacherAccessStudent 실패
- studentId mismatch
- poolId mismatch
- query column/status mismatch
- response contract와 APP parsing mismatch

중 실제 원인만 수정하십시오.

정상 목표:

현재 접근 가능한 student
+
PUBLISHED
+
deleted_at IS NULL

→ 과거~현재 History 200

0건이면:

“발행된 성장리포트가 없습니다.”

API 실패일 때만:

“리포트 목록을 불러올 수 없습니다.”

5. GROWTH REPORT DETAIL — canonical route
━━━━━━━━━━━━━━━━━━━━━━

다음 endpoint가 Teacher canonical Detail입니다.

GET /teacher/growth-reports/:reportId

학생상세 History에서 들어와도
Notification에서 들어와도
반드시 동일 endpoint / 동일 screen을 사용해야 합니다.

실제 Production 좋아요 알림을 기준으로 확인하십시오.

notification:

type = growth_report_like

ref_id = 실제 reportId

알림 클릭

→ teacher-gr-detail?reportId={ref_id}

→ GET /teacher/growth-reports/:reportId

전체 연결을 실제 코드에서 추적하십시오.

확인:

1. messages-inbox가 실제 ref_id를 reportId로 넘기는지
2. route param 이름이 화면과 일치하는지
3. APP detail 화면이 실제 동일 reportId로 API 호출하는지
4. API route mount가 맞는지
5. teacher access check가 현재 student access를 정상 인정하는지
6. product_status=PUBLISHED인지
7. response contract와 UI parser가 일치하는지

좋아요 notification을 위한 별도 Report 화면을 만들지 마십시오.

학생상세에서 들어가는 Detail과
알림에서 들어가는 Detail은
무조건 같은 화면이어야 합니다.
