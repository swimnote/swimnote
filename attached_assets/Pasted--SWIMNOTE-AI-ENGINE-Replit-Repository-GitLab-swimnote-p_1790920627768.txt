1. 핵심 불변조건
━━━━━━━━━━━━━━━━━━━━━━

기존 UNKNOWN request는 절대 변경하지 않습니다.

기존:

status = FAILED
provider_state = UNKNOWN
retryable = false

를 그대로 보존합니다.

금지:

- 기존 UNKNOWN을 retryable=true로 변경
- 기존 request_id 재사용
- provider_state 강제 초기화
- FAILED 상태 삭제
- 기존 registry row 덮어쓰기
- 결과가 있었던 것처럼 COMPLETE 처리
- 자동 recovery
- background retry

UNKNOWN recovery는 반드시
명시적 operator-approved reissue여야 합니다.

2. 새 attempt 방식
━━━━━━━━━━━━━━━━━━━━━━

운영자가 승인하면:

OLD UNKNOWN REQUEST
        ↓
명시적 recovery authorization
        ↓
NEW REQUEST_ID
        ↓
새 analysis attempt

구조로 처리합니다.

새 request는 기존 요청과 다음 lineage를
영속적으로 연결해야 합니다.

- original_request_id
- replacement/new_request_id
- recovery_operation_id 또는 동등한 stable idempotency key
- recovery_generation
- reason = OPERATOR_APPROVED_UNKNOWN_REISSUE
- authorized_at
- 기존 identity
- payload_hash

기존 UNKNOWN은 history로 그대로 남깁니다.

━━━━━━━━━━━━━━━━━━━━━━
3. 실행 허용 조건
━━━━━━━━━━━━━━━━━━━━━━

다음 조건을 모두 만족해야만 reissue를 허용합니다.

원본 request가:

- registry에 존재
- status = FAILED
- provider_state = UNKNOWN
- retryable = false
- final stored result 없음

그리고 새 요청의 입력이 원본과:

- pool identity 일치
- student/report identity 일치
- contract/snapshot identity 일치
- canonical payload_hash 일치

해야 합니다.

가능하면 기존 ENGINE의
canonical hashing / identity validation을 그대로 재사용하세요.

APP가 context_fingerprint를 보내지 못하더라도
ENGINE이 payload로 검증 가능한 기존 fingerprint가 있다면
ENGINE 내부에서 동일성 검증에 사용하세요.

불일치하면 provider 호출 전에 거부합니다.

━━━━━━━━━━━━━━━━━━━━━━
5. Idempotency — 최우선
━━━━━━━━━━━━━━━━━━━━━━

이 endpoint 자체가 timeout/crash/retry되어도
provider 중복 호출이 발생하면 안 됩니다.

같은 recovery_operation_id 재호출:

→ 기존 replacement attempt 상태 반환
→ 새 request 생성 금지
→ 새 provider dispatch 금지

같은 original_request_id에 대해
동일 recovery operation이 동시에 두 번 들어와도:

→ replacement attempt 하나만 생성
→ provider dispatch 최대 1회

동일 operation_id인데
new_request_id / payload_hash / identity가 다르면:

→ CONFLICT

멀티 인스턴스에서도 DB constraint/transaction을 이용해
중복 실행을 차단하세요.

메모리 lock만으로 해결하지 마세요.

━━━━━━━━━━━━━━━━━━━━━━
6. Provider dispatch 안전성
━━━━━━━━━━━━━━━━━━━━━━

새 attempt는 기존 crash-safety 계약을 그대로 사용합니다.

provider 호출 전에
새 request의 영속 상태와 lineage가 먼저 확보되어야 합니다.

기존 ENGINE의:

- registry
- provider_state
- provider ledger
- stable paid-call identity
- COMPLETE replay
- PROCESSING protection
- UNKNOWN safety

를 재사용하세요.

새 attempt 자체가 다시 UNKNOWN이 되면:

→ UNKNOWN 그대로 보존
→ 자동 재시도 금지
→ 또 다른 operator 승인 없이는 재호출 금지

UNKNOWN을 없애기 위해
안전장치를 약화시키지 마세요.

━━━━━━━━━━━━━━━━━━━━━━
7. 결과 처리
━━━━━━━━━━━━━━━━━━━━━━

새 attempt가 정상 COMPLETE:

→ 신규 request에 정상 result 저장
→ old UNKNOWN은 변경하지 않음
→ lineage를 통해 original → replacement 관계 확인 가능

새 attempt가 DATA_ACCUMULATING:

→ 기존 DATA_ACCUMULATING 계약 그대로 반환
→ UNKNOWN으로 변환하지 않음

새 attempt가 확정 retryable failure:

→ 기존 일반 retry 계약 적용 가능

새 attempt가 다시 실행 불확실:

→ provider_state=UNKNOWN
→ 자동 retry 차단

이번 단계에서는 APP DB에 결과를 쓰는 기능은 만들지 않습니다.
