SWIMNOTE 보강 날짜 범위 수정 — 설계 보완 지시

현재 제출한 계획은 아직 구현 승인하지 않는다.

핵심 방향은 맞지만 서버 강제 검증, 관리자 경로 조사, KST 날짜 계산이 누락됐다. 코드 수정 없이 아래 내용을 보완한 최종 설계서만 제출한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 날짜 규칙 최종 확정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

당월·이월·선보강·늦은 보강 모두 동일 규칙을 사용한다.

기준은 결석일이나 만료일이 아니라 KST 오늘이다.

허용 범위:

- 최소 날짜: KST 오늘 - 14일
- 최대 날짜: KST 오늘 + 28일
- 오늘 포함
- 양 끝 날짜 포함

포함 일수는 43일이다.

예:

오늘이 2026-08-06이면

- 허용 시작: 2026-07-23
- 허용 종료: 2026-09-03

이 범위 안에서 반의 정규 수업 요일이며 수영장 휴일이 아닌 회차만 반환한다.

결석일 이전인지 이후인지는 더 이상 제한 조건으로 사용하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. 서버 이중 검증 필수
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

GET eligible-occurrences에서만 범위를 제한하면 안 된다.

공통 검증 함수 validateMakeupOccurrence에서도 반드시 동일 범위를 검사해야 한다.

필수 검증:

occurrenceDate < KST 오늘 - 14일
→ HTTP 400
→ error: MAKEUP_DATE_OUT_OF_RANGE

occurrenceDate > KST 오늘 + 28일
→ HTTP 400
→ error: MAKEUP_DATE_OUT_OF_RANGE

메시지 예시:

"보강일은 오늘 기준 2주 전부터 4주 후까지 선택할 수 있습니다."

따라서 기존 조건:

occurrenceDate <= absence_date 차단

은 제거하되, 그 자리에 오늘 기준 범위 검증을 추가한다.

직접 API 호출로 범위 밖 날짜를 배정할 수 없어야 한다.

assign과 complete-direct가 모두 validateMakeupOccurrence를 거쳐 동일하게 보호되는지 증명한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. assign / complete-direct 분기 유지
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 분기는 유지한다.

- 미래 날짜: assign
- 오늘 또는 과거 날짜: complete-direct

이유:

assign:
- status='assigned'
- 출석 즉시 기록 안 함

complete-direct:
- status='completed'
- attendance 즉시 기록

단, 다음 사례를 각각 명시해 설계한다.

1. 결석 예정일보다 앞선 미래 날짜
   예: 결석 예정 8/20, 보강 8/17
   → 미래이므로 assign

2. 오늘 날짜에 즉시 보강
   → complete-direct

3. 오늘 이전 14일 이내의 과거 보강
   → complete-direct

4. 15일 이전
   → 공통 검증에서 400

5. 29일 이후
   → 공통 검증에서 400

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. expire_at 정책 재확인
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

새 규칙에서는 eligible-occurrences의 날짜 범위를 expire_at으로 자르지 않는다.

하지만 makeup_sessions 자체의 사용 가능 상태나 만료 처리 로직이 별도로 존재할 수 있다.

다음 내용을 직접 확인하여 제출한다.

- expired 항목이 현재 어떤 조건으로 선택 가능해지는지
- allowExpired가 어느 API에서 어떻게 전달되는지
- 이월 처리된 expired 항목만 허용되는지
- 일반적으로 완전히 만료·폐기된 보강까지 선택 가능해지는 위험은 없는지
- status가 waiting/expired/carried_over 등 어떤 값일 때 assign 또는 complete-direct가 가능한지

날짜 선택 범위 변경 때문에 폐기된 보강권까지 되살아나면 안 된다.

`날짜 범위`와 `보강권 유효 상태`를 별도 검증으로 유지한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. KST 날짜 계산 방식
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Render 서버 로컬 타임존에 의존하는 날짜 계산 금지.

다음 중 기존 Repository에 이미 존재하는 방식을 우선 사용한다.

- kstTodayStr()
- KST 날짜 문자열 가감 helper
- UTC 기준 순수 YYYY-MM-DD 연산 helper

`new Date(y, m - 1, d)` 후 서버 로컬 getFullYear/getMonth/getDate에 의존하는 새 코드를 중복 작성하지 않는다.

기존 날짜 helper를 조사하고 재사용 가능한 함수와 파일을 제출한다.

새 helper가 필요하면:

- 함수명
- 입력·출력
- KST 경계 보장 방식
- 월말·연말·윤년 처리
- 테스트 항목

을 설계한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. 관리자 보강 경로 조사 완료
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 보고서에는:

admin 보강 화면 — 영향 있음, 조사 필요

라고 되어 있으므로 아직 수정 파일을 teachers.ts 1개로 확정할 수 없다.

Repository 전체에서 다음을 검색한다.

- eligible-occurrences
- validateMakeupOccurrence
- DATE_BEFORE_OR_ON_ABSENCE
- ASSIGN_REQUIRES_FUTURE_DATE
- COMPLETE_DIRECT_REQUIRES_TODAY_OR_PAST
- makeup assignment
- complete-direct

확인할 영역:

- teacher route
- admin route
- 앱 teacher makeups 화면
- 앱 admin makeups 화면
- ClassDetailSheet 보강 배정
- 기타 보강 배정 모달

제출:

호출 화면 | 호출 API | 날짜 후보 출처 | 서버 검증 함수 | 수정 필요 여부

관리자와 선생님이 같은 API를 사용하면 근거를 제시한다.

다른 API를 사용하면 해당 경로까지 수정 설계에 포함한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
7. 일지 연동 구조 추가 검증
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 분석에서 확정되지 않은 부분을 더 조사한다.

상황:

- 특정 반·날짜의 class_diary가 이미 존재
- 기존 학생들의 일지와 학부모 발행 완료
- 이후 과거 날짜에 보강 학생이 추가됨
- 보강 학생만 개인 일지를 추가 작성·발행해야 함
- 기존 학생들의 일지·푸시는 다시 발생하면 안 됨

다음을 실제 Route와 함수명으로 제출한다.

1. 기존 diary 조회 API
2. 기존 diary에 student_note를 추가하는 정확한 API
3. 해당 API가 이미 존재하는지
4. student_note 추가 시 기존 common_content가 변경되는지
5. 기존 학생 notes가 변경되는지
6. 새 보강 학생 note만 INSERT 가능한지
7. 중복 student_id note 방지 조건
8. 추가된 학생에게만 푸시를 보내는 API 또는 함수
9. 기존 학생에게 푸시가 재전송될 가능성
10. 학부모 피드에서 동일 diary 안에 새 학생 note가 정상 노출되는지
11. 이미 읽은 기존 학부모의 읽음 상태가 초기화되는지
12. 교사 UI에서 과거 일지를 열어 새 보강 학생만 추가할 수 있는지

“가능하다”는 코드 경로와 API가 확인된 경우에만 확정한다.

현재 UI나 발행 트리거가 없으면 이번 날짜 수정과 분리하여 별도 Task로 제안하되, 임의 구현하지 않는다.

8. 수정 파일 목록은 조사 후 확정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 예상:

artifacts/api-server/src/routes/teachers.ts

하지만 다음 조사 결과에 따라 달라질 수 있다.

- 앱이 서버 응답 범위를 임의로 다시 필터링한다면 앱 파일 추가
