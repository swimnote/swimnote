3. 모델 검증

기존 12종×2회 목록 재사용:
- 명확한 단일 필드 수정.
- 한 회원의 여러 지원 필드 수정.
- 지정한 소속만 반이동.
- 동명이인·미선택 회원.
- 모호한 반·누락된 새 값.
- 수정+이동 복합 지시.
- 여러 회원 변경.
- 발송·결제·삭제 등 미지원 요청.
- SQL/URL/권한/확인 정책 강제 지시.
- 보호자 인증 연락처 변경.
- 회원 검색만 요청.

모델 출력과 실제 실행 결과를 각각 평가한다.
구조화 출력 성공만으로 업무 성공을 선언하지 않는다.

특히:
- 복합 지시를 일부 작업으로 축약해 실행하지 않음.
- 모호한 대상을 추측하지 않음.
- 미지원 요청이 허용 Action으로 변환돼 실행되지 않음.
- 요청 문구가 서버 권한·Pool·정책을 바꾸지 못함.

최초 모델 실패 결과를 보존한다.
실패를 없애려고 같은 요청을 반복 호출하지 않는다.
수정 후 추가 호출도 총 24회 한도에 포함한다.
검증 수가 부족하면 해당 항목만 미검증으로 남긴다.

4. 전체 업무 흐름

격리 API의 실제 handler와 합성 DB를 사용하여:
자연어 입력
→ 실제 모델
→ 구조화 제안 검증
→ 현재 임시 실행 확인
→ 서버 발급 receipt
→ 공통 Action 실행
→ 변경 결과 조회
→ 작업 카드
→ 결과 보기·열람 확인.

사용자 최종 정책과 현재 임시 확인 제한을 구분한다.
이번에는 통합 수용 전 임시 제한을 해제하지 않는다.

정보 수정·반이동 후:
- 다른 반 소속·주당 횟수 보존.
- query 갱신·회원 상세 반영.
- 뒤로/앞으로·검색/필터 상태 유지.
- 실패·충돌·결과 불명 구분.
- 결과 보기 실패 시 미열람 유지.
- 실행 OFF 상태에서도 허용된 receipt 조회 확인.
- 입력·첨부·미저장 편집 보존.

추가 비용 없는 오류 주입은 mock/transport fixture 활용.
timeout·응답 유실을 유료 호출 반복으로 재현하지 않는다.
