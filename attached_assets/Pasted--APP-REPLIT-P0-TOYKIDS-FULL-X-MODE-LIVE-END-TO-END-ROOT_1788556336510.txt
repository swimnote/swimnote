CASE A — LIVE API가 x가 아님
============================================================

Production API 응답이:

x_pending
normal
또는 override 미반영

이면 서버 문제.

아래를 정확히 추적:

1. Production route가 어떤 resolver를 호출하는가
2. computeMode()를 실제 사용하는가
3. x_management_override를 SELECT하는가
4. DB row → mapper → service → route에서 필드가 누락되는가
5. snake_case / camelCase mapping 누락 여부
6. select projection에 컬럼 누락 여부
7. stale alternate resolver가 존재하는가
8. route가 old compute path를 사용하는가
9. Render build artifact가 최신 source를 실제 포함하는가

중요:

canonical resolver에는 override가 있어도
route query에서 x_management_override를 읽지 않으면
undefined가 들어가 기존 resolver로 떨어질 수 있음.

이 부분 반드시 실제 확인.

ROOT CAUSE를 코드 line까지 확정 후
최소 수정.

============================================================

그 경우 server는 정상.

실제 흐름:

→ pool/current pool fetch
→ X mode fetch
→ ModeContext
→ persisted/cache state
→ navigation
→ X feature guards

다음을 확인:

1. ModeContext가 어떤 field를 읽는가
2. mode === 'x'를 실제 반영하는가
3. effectiveX만 보는 별도 guard가 있는가
4. xmode_config_status === READY를 앱에서 다시 검사하는가
5. CURRICULUM_PENDING이면 client가 x_pending으로 덮어쓰는가
6. RevenueCat/local subscription을 client가 추가로 검사하는가
7. AsyncStorage / persisted Zustand / query cache 등에 old x_pending이 남는가
8. 로그인 후 refetch가 되는가
9. app foreground 시 refetch되는가
10. current pool switching 시 stale mode를 쓰는가
11. navigation root가 mode 변경을 반영하는가
12. X screens 자체에 별도 prerequisite guard가 있는가
