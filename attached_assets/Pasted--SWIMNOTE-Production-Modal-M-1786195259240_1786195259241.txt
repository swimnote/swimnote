[SWIMNOTE 업무 대화 실기기 오류 수정 — 바로 구현]

현재 Production 실기기 확인 결과다.

업무 대화 Modal 자체는 정상적으로 열린다.
하지만 Modal에서 메시지를 입력하고 전송하면 새 메시지가 대화에 들어가지 않는다.

추가로 학부모 요청 카드의
"탭하여 업무 대화 보기"
문구는 제거하고 명확한 [대화] 버튼으로 변경한다.

이번 작업은 조사 보고만 하지 말고
원인 확인 → 수정 → 검증 → Production 배포까지 바로 진행한다.

FIX-1. 업무 대화 메시지 전송 불가
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 증상:

1. 업무 대화 Modal 정상 오픈
2. 기존 요청 내용/대화 조회 가능
3. TextInput 타이핑 가능
4. 메시지 전송 시 새 메시지가 대화에 추가되지 않음

반드시 실제 전체 경로를 추적한다.

Teacher:
RequestThreadModal.tsx
→ POST /parent-requests/:requestId/messages
→ 서버 route
→ parent_request_messages INSERT
→ response
→ Modal state 반영 또는 GET 재조회

Parent:
ParentRequestThreadModal.tsx
→ 동일 POST
→ INSERT
→ response
→ state 반영 또는 GET 재조회

다음 항목을 실제 코드로 확인한다.

- requestId가 POST URL에 정상 전달되는가
- POST body contract가 서버와 앱에서 일치하는가
- Authorization/JWT가 정상 전달되는가
- teacher/parent role 판별이 정상인가
- request ownership/visibility 검사에서 차단되지 않는가
- INSERT가 실제 실행되는가
- INSERT 실패가 catch에서 숨겨지고 있지 않은가
- 서버 response shape와 앱 파싱이 일치하는가
- POST 성공 후 새 메시지를 local state에 추가하는가
- 또는 POST 성공 후 messages GET을 다시 호출하는가
- 전송 직후 TextInput만 비우고 메시지 목록 refresh를 안 하는 문제인지 확인
- parent_request_messages 실제 컬럼과 INSERT contract 일치 여부 확인

추측으로 한 줄 수정하지 말 것.

POST → INSERT → RESPONSE → UI REFRESH
전체 chain에서 최초 실패 지점을 확인하고 수정한다.

FIX-2. 전송 UX
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

정상 동작은 다음과 같아야 한다.

메시지 입력
→ 전송
→ 서버 저장 성공
→ 해당 메시지가 즉시 대화창 마지막에 표시
→ 입력창 clear
→ 마지막 메시지 위치로 scroll

저장 실패 시:

입력 내용을 임의로 삭제하지 않는다.
사용자가 실패를 알 수 있게 오류 표시.

중복 탭으로 동일 메시지가 여러 번 저장되지 않도록
sending guard 유지/추가.

Teacher와 Parent 양쪽 동일하게 적용한다.

FIX-3. 학부모 요청 카드 UI 변경
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 notifications.tsx 요청 카드에 있는

"탭하여 업무 대화 보기"

문구를 완전히 제거한다.

카드 전체 Pressable로 Modal을 여는 UX에 의존하지 않는다.

대신 요청 카드 하단에 명확한 버튼:

를 추가한다.

버튼 탭:
→ 해당 requestId
→ ParentRequestThreadModal 오픈

기존 요청 유형/내용/상태 표시를 깨지 않는다.

버튼 디자인은
비활성처럼 보이는 반투명 스타일 금지.

SWIMNOTE 기존 UI 톤에 맞는
명확한 활성 버튼으로 만든다.

카드 내용 영역을 불필요하게 크게 만들지 않는다.
