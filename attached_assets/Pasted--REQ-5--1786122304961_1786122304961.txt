[REQ-5] 선생님별 보강 대상 분리 — 현재 담당반 기준
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SWIMNOTE 선생님 보강 화면에서는
수영장 전체 학생의 보강을 보여주지 않는다.

각 선생님은
현재 자신에게 배정되어 있는 반의 학생 보강만 조회한다.

이 정책은 보강 시스템의 최종 Visibility 정책이다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 기본 Visibility 기준
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Teacher A가 현재 담당하는 class_group에
학생 X가 등록되어 있다면:

학생 X의 waiting / expired 보강
→ Teacher A에게 표시.

Teacher B가 학생 X의 현재 담당반과 관계없다면:

학생 X의 보강
→ Teacher B에게 표시하지 않음.

즉:

전체 pool의 makeup_sessions
→ 선생님별 현재 담당반 학생 기준으로 필터.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. original_teacher_id를 Visibility 기준으로 사용하지 않는다
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

original_teacher_id의 의미:

“보강이 발생했을 당시 담당했던 선생님”

이라는 역사 기록으로 유지한다.

하지만 현재 보강 목록 표시 여부를
original_teacher_id 하나로 결정하지 않는다.

예:

7월:
학생 X → Teacher A 담당

8월:
학생 X → Teacher B 반으로 이동

7월에 발생한 미처리 보강이 8월까지 이월됨.

현재 보강 대기 화면:

Teacher B → 학생 X의 이월 보강 표시
Teacher A → 학생 X가 더 이상 자신의 담당 학생이 아니라면 표시하지 않음.

즉 이월 보강도
“현재 학생 소속”을 기준으로 보인다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. 현재 담당반 Source of Truth
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

새 설계에서는
학생의 현재 담당 선생님을 결정하는 Source of Truth를
Repository 실제 구조에서 하나로 확정한다.

후보를 추측하지 말고 Architecture Audit에서 확인:

student 현재 class membership
class_groups.teacher_id
co_teacher_ids
student_class_history의 active record
기타 실제 현재 반 연결 구조

최종적으로:

Student
→ Current Active Class
→ Current Teacher(s)

경로를 하나로 정의한다.

과거 class 또는 종료된 membership을
현재 visibility에 사용하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. 부담임/공동 담당 선생님
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 SWIMNOTE에서 co_teacher_ids가
실제 공동 담당 선생님을 의미한다면:

주담임
+
현재 등록된 부담임/공동 담당

모두 해당 반 학생의 보강을 볼 수 있도록 설계한다.

단 과거 co_teacher 기록은 제외.

현재 active class의 현재 teacher 관계만 사용.

Architecture Audit의 실제 class 구조를 근거로
정확한 규칙을 설계서에 제출한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. 보강 인계는 별도 개념
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

handoff는
학생의 담당반을 변경하는 기능이 아니다.

handoff의 의미:

특정 보강 업무를 다른 선생님에게 넘김.

따라서 기본 Visibility:

현재 담당반 선생님

+

해당 makeup_session의 handed_to_teacher_id가 존재한다면
인계받은 선생님도 해당 보강을 처리할 수 있도록
명확한 예외 규칙을 설계한다.

중요:

original_teacher
current class teacher
handoff teacher

세 개를 섞지 않는다.

각각:

original_teacher
= 역사 기록

current class teacher
= 기본 visibility

handoff teacher
= 특정 업무 처리 예외

로 분리한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. 기간 지난 보강에도 동일 적용
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

waiting뿐 아니라 expired에도
동일한 선생님 분리 정책을 적용한다.

예:

학생 X가 현재 Teacher B 담당반.

7월 expired 보강 존재.

8월 Teacher B 보강 화면:

기간 지난 보강 (1건)
학생 X

표시.

수영장 다른 선생님 화면에는 표시하지 않음.

expired라는 이유로 pool 전체에 공개하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
7. Admin은 예외
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

관리자는 기존처럼
해당 swimming_pool 전체 보강을 관리할 수 있다.

Teacher:

현재 담당반 학생만.

Admin:

Pool 전체.

Teacher API와 Admin API의 Visibility를 명확히 분리한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
8. 보강반 배정 대상과 학생 Visibility를 혼동하지 않는다
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

중요:

“어떤 학생의 보강을 내가 볼 수 있는가”

와

“그 학생을 어느 반에 보강으로 넣을 수 있는가”

는 다른 정책이다.

학생 Visibility:
→ 현재 담당반 기준.

보강 대상 반:
→ 같은 수영장 내 보강 가능한 반 기준.

따라서 Teacher A가 자신의 학생 X를 보더라도
보강 배정 시 Teacher B의 반을 선택할 수 있는 기존 정책이 있다면
그 기능은 별도로 유지한다.

정원이 FULL이어도 보강 추가 가능 정책도 그대로 유지.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. 최종 Teacher Waiting Query 목표
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

개념적으로:

makeup_sessions
WHERE
    same swimming_pool
AND status IN ('waiting', 'expired')
AND cancelled_at IS NULL
AND student belongs to one of
    current logged-in teacher's active classes

+

handoff 정책에 따른 명시적 예외

구조로 설계한다.

단 실제 SQL은
현재 DB schema와 active membership 구조를 확인한 뒤 작성한다.

original_teacher_id만으로 필터하는 구조 금지.

pool 전체를 반환하는 구조도 금지.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
10. 반드시 테스트
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CASE A

Teacher A 반:
학생 1, 학생 2

Teacher B 반:
학생 3, 학생 4

→ A 보강 화면:
학생 1,2만

→ B 보강 화면:
학생 3,4만


CASE B

학생 1이 A반 → B반 이동.

이전 보강 미처리.

→ 현재 B에게 표시
→ A에서는 제거.


CASE C

학생의 지난달 expired 보강 존재.

현재 B반.

→ B의 “기간 지난 보강”에 표시.


CASE D

현재 공동담당 A+B 반.

→ 정책상 공동담당이 맞다면 A/B 모두 표시.


CASE E

handoff A → C

→ 기본 현재 담당자 visibility와
handoff 처리 권한이 설계대로 동작.


CASE F

Admin

→ 전체 학생 보강 표시.


CASE G

Teacher A 학생을
Teacher B 담당반에 보강 배정.

→ 가능.

학생 visibility와 보강 대상반 visibility를 혼동하지 않음.


CASE H

Teacher A 학생
→ 정원 5/5인 다른 반 선택

→ 보강 추가 가능.

REQ-4 유지.
