문제 1.
관리자 쪽의 기존 메뉴가 현재

"공지사항 발송"

이라는 이름으로 되어 있다.

그런데 현재 이 영역/공지함에는
슈퍼관리자가 관리자에게 발송한 SWIMNOTE 공지도 들어오고,
동시에 관리자가 학부모에게 공지를 발송하는 기능도 존재한다.

따라서 단순 "발송" 화면의 의미가 아니다.

사용자 요구사항:

기존
"공지사항 발송"

→

"공지사항 관리"

로 명칭 변경.

단, 텍스트만 바꾸고 끝내지 말고
현재 관리자 공지 화면이 실제로

A. 슈퍼관리자 → 관리자 공지 수신/조회
B. 관리자 → 학부모 공지 작성/발송/관리

두 역할을 어떻게 처리하고 있는지 조사한다.

두 종류의 공지가 한 화면에 존재하는 것이
현재 데이터/API 구조상 정상 설계인지도 확인하고,
사용자가 헷갈리지 않도록 현재 화면 구조를 검토한다.

기존 관리자→학부모 공지 발송 기능은 절대 깨뜨리지 마라.

━━━━━━━━━━━━━━━━━━━━━━
문제 2.
━━━━━━━━━━━━━━━━━━━━━━

선생님 공지함에는
슈퍼관리자가 발송한 공지가 정상적으로 들어왔다.

하지만 슈퍼관리자가

텍스트 + 대표 이미지

형태로 발송했는데
선생님 공지함에서는 이미지가 표시되지 않는다.

이것도 바로 UI에 Image 컴포넌트를 추가하지 마라.

먼저 전체 경로를 추적한다.

슈퍼관리자 공지 등록
→ POST /notices
→ DB notices.image_urls
→ R2 object_key
→ GET notices 관련 API
→ API response image field
→ 선생님 공지함 fetch
→ client mapping
→ notice detail/list UI
→ 이미지 URL 생성
→ Image render

다음을 확인한다.

1. DB에는 image_urls가 정상 저장되어 있는가
2. 저장값이 R2 object key인가 full URL인가
3. API가 선생님에게 image_urls를 반환하는가
4. API serializer/mapping 과정에서 이미지가 제거되지 않는가
5. 앱 client type에 image_urls가 정의되어 있는가
6. fetch 이후 mapping에서 누락되는가
7. 공지함 list/detail 중 어느 화면에서 이미지를 지원하는가
8. signed/public URL 변환이 필요한 구조인가
9. NoticePopupCard에서 사용하는 이미지 처리 방식과
   공지함에서 사용하는 방식이 다른가
10. 관리자/선생님/학부모가 동일 공지를 받을 때
    이미지 표현 계약이 서로 다른가

정확한 root cause를 찾은 뒤 수정한다.

================================
A. 관리자
================================

확인:

슈퍼관리자
→ 관리자 대상 공지 발송
→ 관리자 공지함 도착
→ 이미지 포함 여부
→ 앱 시작 popup 대상 여부
→ pending
→ popup
→ seen

그리고

관리자
→ 학부모 대상 기존 공지 발송

경로도 별도로 추적한다.

두 공지 시스템이

- 같은 DB table을 쓰는지
- 다른 table을 쓰는지
- 같은 API인지
- 다른 API인지
- 같은 화면에서 합쳐지는지

정확하게 보고한다.

관리자 메뉴
"공지사항 발송"
→ "공지사항 관리"

변경 위치도 모두 찾는다.

B. 선생님
================================

현재 실제 확인:

슈퍼관리자 공지
→ 공지함 도착 성공
→ 대표 이미지 표시 실패

확인:

슈퍼관리자

================================
C. 학부모
================================

현재 사용자는 학부모 계정에 새 테스트 공지를 보내지 않았다.

따라서 Production 사용자에게
임의 테스트 공지를 발송하지 마라.

대신 코드/API/DB 구조와 기존 테스트 가능한 범위에서
학부모 흐름을 같이 조사한다.

확인:

1. 슈퍼관리자 → 학부모 공지
2. 관리자 → 학부모 기존 공지
3. 두 종류가 학부모 공지함에서 어떻게 구분/통합되는지
4. 슈퍼관리자 공지의
   - title
   - content
   - image
   - CTA/link
   가 학부모 공지함에서 정상 표현 가능한 구조인지
5. eligible/unseen 슈퍼관리자 공지가
   학부모 /notices/pending에 정상 포함되는 구조인지
6. 학부모 앱 시작 시 NoticePopup이 실제 mount되는지
7. auth/session/role 준비 후 pending 조회가 가능한지
8. 실제 표시 이후에만 seen 처리되는지
9. 기존 관리자→학부모 공지 읽음 처리와
   슈퍼관리자 popup seen 처리가 섞이지 않는지

Production 학부모에게 실제 공지를 보내는 테스트는 하지 않는다.

가능한 범위에서
코드/테스트 계정/자동화 테스트로 검증한다.

4. isLoading=false 전환 후 실제 재호출되는가
5. fetched/shown/initialized ref가 먼저 잠기는가
6. /pending이 실제 공지를 반환하는가
7. pending이 빈 배열이면 왜 빈 배열인지
8. notice_dismissals가 popup 표시 전에 생성되는 경로가 있는가
9. setVisible(true)까지 실제 도달 가능한가
10. 다른 RN Modal과 presentation 충돌이 있는가
11. onShow가 호출되는가
12. popup을 보지 못했는데 seen이 기록될 가능성이 있는가
