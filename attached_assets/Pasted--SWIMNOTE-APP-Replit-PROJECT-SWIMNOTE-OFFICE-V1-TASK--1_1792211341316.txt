사용자가 제공한 아카2000 화면에서 어린이 수영장에 필요한
정보·업무 연결 방식만 추출하여 OFFICE 구현설계에 포함한다.

기존 고정계획서의 Stage 순서·제품 목표는 유지한다.
현재 Stage 3의 공통 Action 구현을 보존하고,
회원 수정·반이동·실제 AI 연결 전에 회원 상세 기반을 보완한다.

직전 “Stage 3 첫 AI Vertical Slice 통합 구현” 지시문은
이번 보완 완료 전 실행하지 않는다.
이미 시작된 변경이 있다면 삭제하거나 되돌리지 말고
현재 상태와 이번 보완의 관계를 기록한다.

2. PC·모바일 공통 원칙
────────────────────

- PC와 모바일 메뉴를 동일하게 만들 필요 없음.
- PC는 직원의 회원·수강·수납·매출 등 운영 업무 중심.
- 모바일은 보호자·강사·관리자 역할에 필요한 기능 중심.
- 동일 회원·수강·청구·결제 기록은 공통 기준 사용.
- PC 전용 정보를 모바일에 무조건 노출하지 않음.
- 역할별 조회·수정·내보내기 권한 구분.
- 회원 상세와 전체 업무 메뉴에 별도 중복 장부를 만들지 않음.
- 앱 구독/IAP와 수영장 회원 수강료 결제를 분리.

이번에는 모바일 코드·DB schema를 변경하지 않는다.
공통 데이터 확장이 필요한 항목과 호환성 영향은 설계에 명시한다.

────────────────────
3. OFFICE 메뉴 지도
────────────────────

아래는 최종 기능 분류이며 이번 전부 구현하라는 뜻이 아니다.

홈:
오늘 현황·재원·출결·미납·재등록 예정·보강·처리할 업무.
요약에서 해당 목록으로 이동.

회원관리:
전체/재원/등록 예정/연기/지난회원.
신규등록·재등록·회원 상세·검색·필터·내보내기.

수업·출결:
반·요일/시간·담당 강사·정원·배정·반이동.
출결·보강·연기.

청구·수납:
수강료 조건·청구 생성·납부 등록·결제 요청.
납입 조회·미납·할인·부분 납부·취소·환불·증빙.

매출·정산:
기간별 수납·환불·미납。
반별·결제수단별·처리자별 집계·내보내기.
장래 지출 기록은 기존 계획 범위와 대조하여 별도 구분.

상담·안내:
상담 기록·후속 연락 대상·푸시/문자 준비·발송 이력.

차량관리:
차량·기사·승하차 장소·요일별 탑승 명단·운행 정보.

교육·성장:
기존 일지·커리큘럼·진도·레벨·성장리포트.

AI 매니저:
자연어 업무 요청·작업 상태·실행 확인·결과 열람·보관함.

설정·지원:
수영장·직원/권한·상품/요금·알림/결제 설정·도움·문의.

메뉴 검색·즐겨찾기는 확장 대상으로 기록한다.
미구현 메뉴를 대량 활성화하거나 빈 업무 화면을 양산하지 않는다.

교재 판매·학교 시험/성적·희망학교·직장·사내우편·FTP 등은
현재 OFFICE 핵심 요구에서 제외한다.
아카2000의 디자인·버튼명·복잡한 창 구조를 그대로 복제하지 않는다.

────────────────────
4. 회원 상세 화면
────────────────────

기존 Drawer:
빠른 조회용으로 유지.
“전체 회원정보” 진입 제공.

전체 회원정보:
중앙 업무 영역을 사용하는 넓은 전용 화면.
기존 AI 매니저와 정상 layout 흐름으로 공간 분할.
AI를 덮거나 별도 제품 창을 만들지 않는다.

상단 요약:
- 회원 이름·재원 상태.
- 현재 반·수강 기간.
- 청구/수납 연결 후 다음 납부기한·미납액.
- 중요 메모 표시.

미연결 금액을 0원이나 미납 없음으로 표시하지 않는다.

정보 분류:
① 기본정보
이름·사진·생년월일·성별·학교/학년·등록일·회원 상태.

② 보호자·연락처
보호자 이름/관계·주/추가 연락처·주소·가족 연결.
알림 수신 대상·앱 연결·동의 상태.

③ 수강·반
상품·주당 횟수·요일/시간·소속 반·담당 강사.
수영 레벨·수강 기간·배정/이동/연기/퇴원 이력.
複数 반 소속을 단일 반 필드로 축소하지 않는다.

④ 청구·납입
청구 목록·납부 내역·미납·할인·부분 납부.
취소/환불·증빙·기간 조회·내보내기。

⑤ 출결·보강
출결·결석·보강 예정/사용·연기 내역.

⑥ 차량
이용 여부·요일별 승하차·차량·인솔 참고사항.

⑦ 메모·상담
작성일·작성자·유형·내용·중요 표시·검색.
회원 전체 메모와 청구별 수납 메모 분리.

⑧ 교육·성장
기존 일지·진도·레벨·성장리포트 연결.

⑨ 활동 이력
정보 변경·반이동·발송·직원/AI 처리 기록.

수업 안전에 필요한 참고사항은 필요한 범위와 열람 권한을 설계한다.
아직 없는 동의·건강·가족 데이터를 기본 동의/정상으로 추정하지 않는다.

화면 구성:
- 상위 탭 + 세부 섹션 접기/펼치기.
- 핵심 정보를 거대한 입력 폼 하나에 몰아넣지 않음.
- 짧은 작업은 보조 modal 한 겹으로 처리.
- 다중 modal의 연속 중첩 금지.
- 긴 설명·미완성 탭이 업무 화면을 차지하지 않도록 구성.

────────────────────
5. 청구·납입 공통 설계
────────────────────

서로 구분할 개념:
- 상품/수강료 조건.
- 청구와 청구 항목.
- 실제 납부 및 청구에 대한 반영.
- 실제 결제 승인 거래.
- 할인·조정·취소·환불·이월.
- 증빙과 변경 이력.

수강료 조건:
기준 금액·회원 적용 금액·할인 방식/값/사유.
적용 시작/종료·청구 주기·청구일·납부기한.

청구 만들기:
대상 회원·수강 기간·청구 항목·금액·납부기한·메모.
첫 등록의 초기 청구·일할 계산은 정책 미확정으로 구분.
월별/횟수제 등 지원 여부는 기존 계획·계약에 맞춰 결정.
반복 청구의 중복 생성 방지 필요성을 기록.

변경 적용 범위:
- 이번 청구만.
- 다음 청구부터 수강료 조건 변경.
이미 납부한 거래를 현재 조건 변경으로 덮어쓰지 않음.

납부:
일자·금액·수단·처리자·연결 청구·반영 금액.
부분 납부·여러 청구에 대한 납부 관계 고려.
납부 기록 등록과 실제 카드 승인 버튼을 구분.

취소·환불:
장부 정정·실제 승인 취소·환불·이월을 구분.
원 거래·금액·사유·처리자·처리 상태 연결.
사유 없는 이력 삭제나 과거 금액 덮어쓰기 금지.

조회:
회원별 납입 이력.
전체/반별/회원별 미납 현황.
기간·기준일·현재/지난회원·상품/반·수단·처리자 필터.
인원·청구 건수·거래 건수·금액 구분.
납입률/미납률은 분모와 기준 명시.
순수납·청구·미납을 모두 같은 “매출”로 취급하지 않음.

영수증·현금영수증·가상계좌·결제 연동은
실제 제공자·기존 계획에 따른 후속 범위로 구분한다.

이번에는 위 결제 기능·자동 청구·DB schema를 구현하지 않는다.

────────────────────
6. 공통 목록·내보내기
────────────────────

공통 기준:
검색·필터·정렬·건수·로딩·빈 상태·실패·재시도.
페이지 이동·복귀 시 조회 상태 보존.

엑셀:
- 기본 범위는 현재 검색/필터 결과 전체.
- 현재 페이지만/선택 행과 구분.
- 조회 권한과 내보내기 권한 적용.
- 열 정의·건수·조건·기준 시각 표시.
- 전화번호 앞자리 0·식별자·날짜·금액 보존.
- 수식으로 해석되는 입력의 안전한 출력.
- 메뉴와 AI가 같은 조회·출력 기준 사용.

이번에는 기존 export를 재사용 후보로 매핑한다.
미구현 export를 성공 버튼이나 가짜 파일로 만들지 않는다.

────────────────────
7. 이번 실제 구현 범위
────────────────────

A. 넓은 회원 상세 업무 화면.
B. 기존 Drawer의 전체 정보 진입.
C. 기존 데이터로 가능한 기본정보·보호자·수강정보·발행 이력 재배치.
D. 기존 메모가 있으면 독립 섹션으로 표시.
E. 메모·상담·청구·수납 등 후속 정보의 확장 경계 정리.
F. 기존 공통 Action/Navigation에 전체 회원 상세·탭 목적지 연결.
G. 검색·필터·스크롤·선택·뒤로/앞으로 상태 보존.

현재 데이터 계약에 있는 필드만 실제 조회에 연결한다.
신규 endpoint가 필요한 기능은 이번에 임의 연결하지 않는다.
불필요한 개인 필드를 포함한 광범위 API 조회 확대 금지.

미존재 필드:
다른 의미의 기존 필드에 우겨넣거나 localStorage로 별도 저장하지 않는다.
미연결과 실제 빈 값을 구분한다.
후속 전체 화면 구성은 합성 fixture로 검증하되
실제 제품에 가짜 회원·청구·메모·결제 기록을 넣지 않는다.

현재 조회 가능 탭을 우선 노출한다.
미연결 영역은 명확한 준비 상태로 최소 표시하거나
확장 설계에 남기되 빈 탭을 대량 노출하지 않는다.

편집·AI 실행·결제까지 이번에 선개발하지 않는다.
기존 Desktop 업무 쓰기 차단 유지.

8. 구현 전 데이터 대응표
────────────────────

다음 표를 관련 코드 범위에서 확인해 문서에 작성한다:

요구 항목 /
기존 field·API /
원천 데이터 /
조회·수정 가능 여부 /
PC·모바일 적용 /
필요 권한 /
현재 Stage 또는 후속 Stage /
미확정 계약.

운영 DB·실계정 조회 없이 source와 schema 정의로 확인한다.
동명이인·보호자 공유·複数 반·지난회원도 고려한다.
미확인을 존재하지 않는다고 단정하지 않는다.

표 작성 후 이번 구현 가능 범위는 계속 진행한다.
일부 신규 데이터 계약이 없다는 이유로 전체를 HOLD하지 않는다.

────────────────────
9. 검증 및 전달
────────────────────

변경 영향 범위만 검증:
- 목록 → Drawer → 전체 회원정보.
- 뒤로/앞으로·직접 OPEN·탭 이동·동일 대상 재선택.
- 조회 상태·선택·스크롤·AI 초안/첨부 보존.
- 이전 세션/회원의 늦은 응답 격리.
- 없는 회원·권한 거부·조회 실패·미연결/빈 상태 구분.
- AI 일반/접기/크게 보기에서 넓은 상세 화면 접근성.
- 긴 이름·여러 보호자·複数 반·긴 메모의 합성 fixture.
- 좁은/낮은 창에서 탭·입력·목록·스크롤 가독성.
- 기존 Web 회원 화면 영향 범위 회귀.
- 관련 타입검사·필요 빌드·diff check.

기존 Action·Stage 2 통과 증거 재사용.
전체 suite·설치/로그인 수용 검사는 반복하지 않는다.
