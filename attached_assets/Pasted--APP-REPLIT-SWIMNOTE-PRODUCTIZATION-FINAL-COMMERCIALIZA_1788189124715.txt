1. 기존 감사의 4개 사실충돌 먼저 해결
==================================================

A. BULK REGISTER

이전 코드 감사:
bulk-register.tsx 존재,
1행 오류가 전체 업로드를 막는 HIGH stress 보고.

최근 감사:
Excel/CSV Bulk Import NOT_IMPLEMENTED라고 보고.

둘 중 무엇이 실제 release/v2.0.0 사실인지 확정.

반드시 보고:
- 파일
- route
- parser
- API
- 실제 지원 format
- 현재 최대 rows
- 현재 required columns
- 현재 import 동작

기능이 존재하면 절대 새로 만들지 않는다.
기존 구현을 상품화 수준으로 강화한다.

B. TERMINOLOGY SEARCH

프로젝트에는 이미:
- terminology backend
- Engine search
- 1,222 terminology production dataset
- teacher route/UI 작업

이 존재했던 이력이 있다.

현재 release/v2.0.0에서 실제 위치를 다시 찾아라.

최근 감사처럼 "미구현"이라고 추정하지 않는다.

확인:
- teacher entry
- parent entry
- shared components
- shared API gateway
- Engine endpoint
- feature gate

기존 구현이 있으면 재사용한다.

최종 정책:
수영·훈련용어 검색은 AI 호출 기능이 아니므로
Normal/X COMMON.

Parent + Teacher 모두 사용 가능해야 한다.

C. STUDENT STATUS vs POOL STATUS

최근 감사 안에서 모순이 있다.

한 곳에서는 pool_status를
수영장 subscription status라고 했고,

다른 곳에서는:
expired = 학생 재등록 대상
suspended = 학생 휴회
로 사용했다.

절대 이 가정을 사용해서
재등록 기능을 만들지 않는다.

실제 schema에서:

- swimming pool subscription status
- student/member enrollment status
- lesson enrollment
- registration period
- start/end date
- renewal
- withdrawal
- suspension
- rejoin

을 완전히 분리해서 확정한다.

재등록은 반드시 학생/회원 lifecycle 데이터로 계산한다.

D. GROWTH_EVENTS

현재 diary save 시 X에서 기록되는 growth_events가:

- 단순 수업/진도 사실 이벤트인지
- AI Growth용 semantic event인지
- 둘이 혼합되어 있는지

실제 schema/service/consumer 기준으로 조사한다.

Normal Basic Growth를 위해
무조건 gate 한 줄만 제거하지 않는다.

데이터 의미가 혼합되어 있으면:

COMMON_BASIC
X_AI

event type/scope를 명시적으로 분리한다.

2. BULK MEMBER IMPORT 상품화 완성
==================================================

기존 Bulk가 있으면 그것을 고친다.

최종 상품 요구사항:

필수 컬럼:
- name
- phone

두 개만으로 최대 1,000명 등록.

optional:
- class
- level
- memo 등 기존 지원 필드

다음 모두 허용:

- 같은 이름
- 같은 전화번호
- 같은 이름+같은 전화번호
- 형제 동일 보호자번호
- 기존 회원과 전화번호 동일
- 파일 내부 중복

학생은 독립 student_id 생성.

중복은 ERROR가 아니라 WARNING.

단,
guardian/parent login account 중복처리는
학생 생성과 분리한다.

1 bad row 때문에 999 valid rows 실패 금지.

Partial Success 필수.

테스트:

1000 valid
999 valid + 1 invalid
duplicate phone 100
same name+phone
siblings
phone normalization
double submit
same file explicit retry
network retry

최종:
total/success/warning/failed contract.
