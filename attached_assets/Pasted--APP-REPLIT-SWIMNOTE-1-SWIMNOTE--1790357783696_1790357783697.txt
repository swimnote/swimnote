[SWIMNOTE — 구독 완료 후 회원 사용량 표시 정리 + 결제 성공 후 1회 앱 재실행]

실기기에서 SWIMNOTE 구독 결제가 실제 성공한 것을 확인했습니다.

이번 작업은 아래 2가지만 최소 수정합니다.

1. 회원 사용량 표시에서 내부 무제한 sentinel(999999) 제거
2. 실제 구독 구매 성공 후 앱을 1회 재실행하여 구독상태 안정 반영

가격/상품/RevenueCat 구조 자체는 변경하지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
1. 현재 문제 — 999999 노출
━━━━━━━━━━━━━━━━━━━━━━

현재 SWIMNOTE 기본 플랜에서
회원 제한을 내부적으로 999999 등의 큰 숫자로 표현하면서

홈 화면 통합 사용량에:

0/999999명

처럼 표시되고 있습니다.

이 값은 내부 구현값일 뿐
사용자에게 보여줄 숫자가 아닙니다.

UI에서 절대 999999를 노출하지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
2. 최종 회원 사용량 표시 정책
━━━━━━━━━━━━━━━━━━━━━━

플랜별 표시를 아래처럼 고정합니다.

[SWIMNOTE 기본플랜]

회원수 제한 숫자 표시 금지.

예:

회원 사용량
0명

또는 기존 카드 문맥에 맞게:

0명
현재 회원

처럼

“현재 등록/사용 중인 회원수”만 표시.

금지:

0/999999명
0/무제한명
0/∞명

즉 SWIMNOTE에서는
분모 자체를 표시하지 않습니다.

━━━━━━━━━━━━━━━━━━━━━━

6. 결제 성공 후 앱 1회 재실행
━━━━━━━━━━━━━━━━━━━━━━

사용자가 실제 구독 구매를 완료한 후
구독상태가 모든 화면에 안정적으로 반영되도록

구매 성공 flow 마지막에
앱을 1회 reload 하십시오.

중요:

Apple/Google 결제창에서
결제가 성공했다는 것만으로 즉시 reload 금지.

반드시 다음 순서:

1. RevenueCat purchase 성공
2. CustomerInfo 확인/갱신
3. syncRcToServer 성공
4. 서버 subscription tier/status 반영 성공
5. 필요한 refreshPool / refreshMode 처리
6. 그 다음 앱 1회 reload

━━━━━━━━━━━━━━━━━━━━━━
7. reload 방식
━━━━━━━━━━━━━━━━━━━━━━

현재 Expo 환경에서 이미 검증된
Updates.reloadAsync()

등 프로젝트의 기존 reload helper가 있다면
그 방식을 재사용하십시오.

새 native restart library 추가 금지.

Native build가 필요하게 만드는 방식 금지.

━━━━━━━━━━━━━━━━━━━━━━
8. 사용자 UX
━━━━━━━━━━━━━━━━━━━━━━

구매 성공 직후:

“구독이 완료되었습니다.
새 구독 정보를 적용하기 위해 앱을 다시 시작합니다.”

정도의 짧은 안내 후 reload.

기존 confirm/modal infrastructure가 있으면 재사용.

너무 긴 설명 금지.

X 구매에 이미 존재하는
XRestartRequiredModal이 있다면

중복된 두 개의 재시작 UX가 뜨지 않도록
구매 성공 후 재시작 flow를 하나로 통일하십시오.

SWIMNOTE 구매도 동일하게
성공 동기화 후 1회 reload.

━━━━━━━━━━━━━━━━━━━━━━
9. 절대 재실행하면 안 되는 경우
━━━━━━━━━━━━━━━━━━━━━━

아래는 reload 금지:

- 사용자 결제 취소
- Store error
- pending/deferred
- RevenueCat purchase 실패
- syncRcToServer 실패
- 서버 subscription 반영 실패

실제 성공이 확정된 경우에만 reload.

━━━━━━━━━━━━━━━━━━━━━━
10. 무한 reload 방지
━━━━━━━━━━━━━━━━━━━━━━

중요:

앱 실행 시 CustomerInfo를 읽었다고
자동 reload 하면 안 됩니다.

reload trigger는 오직:

“사용자가 이번 세션에서 실제 purchase를 완료했고
server sync까지 성공한 직후”

에만 실행.

앱 재실행 후 subscription 상태를 읽으면서
다시 reload되는 loop가 절대 없어야 합니다.

필요하면 handler-local ref/flag 등
최소한의 one-shot guard 사용.

새 persistent state 설계 금지.

━━━━━━━━━━━━━━━━━━━━━━
11. Restore Purchases
━━━━━━━━━━━━━━━━━━━━━━

이번 요구는 “신규 구매 완료 후 재실행”입니다.

restore flow는 현재 정상 구조를 유지하십시오.

복원 성공 후 현재 코드가
refreshMode/refetch만으로 안정적이라면
이번 작업 때문에 억지로 reload를 추가하지 마십시오.

별도 문제 발견 시에만 보고.
