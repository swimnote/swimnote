이번 인증/회원가입 문제는 1.6.3만 임시 수정하지 말고,
현재 운영 중인 1.6.3과 개발 중인 2.0.0 모두에서 동일 문제가 재발하지 않도록
공통 인증/가입 로직 기준으로 확실하게 수정한다.

현재 확인된 root cause:

문제 1
- teacher 계정 identifier가 @ 없는 문자열일 수 있음
- 기존 /auth/login이 @ 포함 여부에 따라 분기하면서 teacher를 못 찾는 경우 발생
- reset-password 자체는 정상인데, 변경 후 login resolver가 teacher 계정을 못 찾아 로그인 실패

문제 2
- 동일 보호자가 같은 pool에서 두 번째 자녀를 등록할 때
  alreadyInPool=true이면 parent-register가 409 반환
- 형제/자매 추가 연결 flow가 없음
- 기존 parent account에 두 번째 child relation을 붙여야 하는데 신규가입 중복으로 취급함

목표:
1.6.3과 2.0.0 모두 같은 backend/auth contract를 사용해
이 문제가 어느 버전에서도 발생하지 않도록 공통 root fix한다.

중요:
- 1.6.3은 stable production
- 2.0.0은 release/v2.0.0
- shared API 변경은 두 버전 모두 backward-compatible해야 함
- 1.6.3에만 하드코딩/분기 패치 금지
- 2.0.0에만 별도 구현 금지
- 같은 기능은 공통 server/auth logic 하나로 해결
- Production DB 임의 수정 금지
- 개인정보/비밀번호/hash 원문 로그 금지

2. Teacher login/root fix — 공통 수정
==================================================

/auth/login 또는 실제 공통 login resolver를 기준으로 수정한다.

정책:

identifier에 @가 있든 없든
우선 실제 user/teacher/admin의 login identifier 컬럼으로 정확히 조회한다.

잘못된 기존 방식:
if identifier.includes('@') ...
else pool_admin slug ...

이런 형태로 role 조회를 문자열 형식에 의존하지 않는다.

정상 우선순위 예:

1. canonical identifier/email lookup
2. teacher/user 계정 확인
3. admin 계정 확인
4. direct lookup 실패한 경우에만 pool slug fallback

단,
현재 실제 schema와 기존 login 정책을 조사해서
collision이 없고 backward-compatible한 순서를 확정한다.

반드시 확인:
- @ 없는 teacher identifier
- @ 있는 teacher email
- pool_admin slug
- 동일 문자열이 email과 slug에 동시에 존재할 가능성
- inactive/deleted account
- wrong password
- role mismatch
- pool/tenant scope

비밀번호 비교는 기존 단일 hash policy만 사용한다.

3. Forgot/reset password — 1.6.3 + 2.0.0 E2E
==================================================

reset-password 자체가 정상이라고 가정하지 말고
두 앱 버전에서 E2E를 다시 확인한다.

각 버전:

1. 비밀번호 찾기
2. 본인 확인
3. 새 비밀번호 설정
4. DB hash 실제 변경 확인
5. 이전 비밀번호 실패
6. 새 비밀번호 성공
7. 앱 종료/재실행 후 로그인 성공

확인:
- reset 대상 account ID
- login 대상 account ID 동일
- 동일 password hashing function 사용
- double hash 없음
- affected row 확인
- 실패인데 success UI 표시 안 함
- 1.6.3와 2.0.0이 서로 다른 client helper를 쓰는 경우 둘 다 수정

가능하면 auth client helper를 공통화한다.

==================================================
4. Parent registration/root fix — 형제/자매 지원
==================================================

같은 보호자가 같은 pool의 여러 자녀를 연결하는 것은 정상 케이스다.

따라서:
alreadyInPool=true
≠ registration error

정책:

기존 parent account + same pool membership가 있어도
새로운 student를 연결할 수 있어야 한다.

정상 flow:

1. parent identity 확인
2. pool membership 확인
3. student match
4. 이미 연결된 child인지 확인
5. 미연결 child면 linkParentToStudent
6. 바로 매칭 가능하면 linked
7. 승인 필요하면 waiting/pending
8. 중복 child link만 idempotent 처리
9. parent account 새로 중복 생성 금지

절대:
- same pool membership만 보고 409
- 형제 수에 따라 제한
- 첫 child 등록 후 두 번째 child 가입 차단

하지 않는다.

==================================================
5. 1.6.3 / 2.0.0 client 호환성
==================================================

server response를 두 버전 모두 받을 수 있게 유지한다.

확인:
- 1.6.3이 기대하는 status code/body
- 2.0.0이 기대하는 status code/body
- linked
- waiting
- already_linked
- validation error

필요하면 새 필드는 additive하게 추가한다.

기존 필드 삭제/rename 금지.

1.6.3이 409를 에러로 처리하던 부분이 있고
server가 201 linked/waiting으로 바뀌면
기존 1.6.3 화면이 정상 처리하는지 반드시 확인한다.

만약 1.6.3 client 수정이 꼭 필요하면
그 사실을 명확히 보고하고 임의 OTA하지 않는다.

2.0.0 client도 동일하게 확인한다.
