[긴급 감리 — SwimNote iOS 문서 및 데이터 22.21GB 원인 조사]

현재 실제 iPhone 저장공간 확인:

SwimNote version: 1.6.2
앱 크기: 73.3MB
문서 및 데이터: 22.21GB

이 상태는 원인 조사가 필요하다.

SWIMNOTE의 의도된 사진/영상 저장 정책:

1. 사용자가 사진/영상을 선택 또는 촬영
2. 서버/R2 업로드
3. DB에는 서버상의 file URL / metadata 저장
4. 업로드 성공 이후 기기에 원본 또는 업로드용 복사본을
   영구적으로 계속 축적하지 않는다.
5. 피드/앨범/일지 재조회는 서버 URL을 기준으로 한다.
6. 로컬 캐시가 필요하다면 제한적·임시적으로만 사용한다.

중요:
현재 22.21GB의 원인을 아직 특정하지 않았다.

추정으로 코드 수정하지 말고
먼저 실제 저장 경로와 lifecycle을 전수 조사한다.

E. cacheDirectory 조사
━━━━━━━━━━━━━━━━━━━━━━

cacheDirectory도 조사한다.

캐시라고 해서 무조건 안전하다고 판단하지 않는다.

SWIMNOTE 자체에서:

- cache 파일을 계속 생성하는지
- 동일 사진을 중복 cache하는지
- cache eviction 정책이 있는지
- 최대 용량 제한이 있는지
- TTL이 있는지
- logout 시 삭제하는지
- upload 성공 후 삭제하는지

확인한다.

━━━━━━━━━━━━━━━━━━━━━━
F. 사진 clone/cache 기능 집중 조사
━━━━━━━━━━━━━━━━━━━━━━

현재 프로젝트에서 과거 사진 clone/cache 관련 작업이 있었으므로
해당 구현을 집중 조사한다.

다음 구조가 있는지 확인:

remote URL
→ local download
→ permanent local copy
→ 이후 계속 보존

특히 사진 여러 장을 일지마다 로컬로 복제하고 있다면
22GB 증가의 직접 후보가 될 수 있다.

그러나 코드 증거 없이 원인으로 확정하지 않는다.

M. 정상 목표 구조
━━━━━━━━━━━━━━━━━━━━━━

조사 후 수정 설계는 다음 원칙을 만족해야 한다.

SERVER/R2
= 영구 media source

DB
= URL + 필요한 metadata

DEVICE
= 업로드 과정에서 필요한 임시 파일 또는 제한된 cache만 허용

업로드 성공 후 불필요한 임시 파일:
DELETE

실패/취소 후 불필요한 임시 파일:
DELETE

cache:
상한/정리 정책 필요

persistent document directory:
사용 이유가 명확한 파일 외 media 영구 축적 금지

N. 기존 22.21GB 처리도 별도 조사
━━━━━━━━━━━━━━━━━━━━━━

중요:

앞으로 파일이 안 쌓이게 수정하는 것만으로는
이미 사용자 기기에 쌓인 22.21GB가 없어지지 않을 수 있다.

따라서 기존 버전에서 생성된 orphan/local media를
안전하게 식별해서 삭제할 수 있는지 조사한다.

절대 하면 안 되는 것:

앱 document/cache 전체 무차별 삭제.

로그인 정보,
draft,
필요한 설정,
미업로드 자료 등까지 날릴 위험이 있다.

SWIMNOTE가 생성한 불필요한 media만
정확하게 식별할 수 있는 cleanup migration이 가능한지 조사한다.
