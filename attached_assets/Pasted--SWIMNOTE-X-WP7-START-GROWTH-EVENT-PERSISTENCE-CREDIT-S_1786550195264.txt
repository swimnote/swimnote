6. X MODE ONLY
━━━━━━━━━━━━━━━━━━━━

growth_event 자동 저장은
이번 WP에서는 X Mode에만 적용.

기존 일반 SWIMNOTE diary 저장:

절대 동작 변경 금지.

NON-X:
→ 기존 diary save
→ growth_event 생성 안 함

X:
→ 기존 diary save 성공
→ growth_event 생성

X 판정은 기존 resolver 재사용.

새 entitlement 판단 로직 금지.

━━━━━━━━━━━━━━━━━━━━
7. SAVE TRANSACTION / CONSISTENCY
━━━━━━━━━━━━━━━━━━━━

가장 중요.

Diary 본체 저장이 실패했는데
growth_event만 남으면 안 됨.

가능하면 기존 DB transaction 내부에서:

1. diary save
2. student diary/feedback save
3. growth_event insert

처리.

현재 구조상 같은 transaction이 불가능하면
실제 구조를 먼저 보고하고
가장 안전한 방식 사용.

절대:

growth_event 성공
+ diary 실패

상태 만들지 말 것.

━━━━━━━━━━━━━━━━━━━━
8. IDEMPOTENCY / DUPLICATE 방지
━━━━━━━━━━━━━━━━━━━━

같은 diary save 요청 재시도 때문에
growth_event가 중복 생성되면 안 됨.

기존 request_id / diary_id / source_id /
unique constraint를 활용.

동일 source diary + student + event가
중복 insert되지 않게 구현.

새 unique constraint가 필요하다면
먼저 기존 schema 확인 후 STOP/보고.

application-level check만으로 충분한지
실제 구조 기준 판단.

━━━━━━━━━━━━━━━━━━━━
9. STUDENT 단위
━━━━━━━━━━━━━━━━━━━━

Growth Event는 학생별 데이터.

COMMON 수업 내용이 있다고 해서
모든 학생에게 무조건 동일한 성장 사실을
복제하면 안 됨.

기존 diary 구조에서:

COMMON = 전체 수업 내용
STUDENT feedback = 학생별 관찰

을 구분.

학생별 Growth Event는
실제 해당 student와 연결 가능한 사실만 저장.

COMMON 중 실제 전체 학생에게 적용되는
수업 context를 저장할 필요가 있다면
schema의 event/source 구조 안에서만 처리.

임의 복제 금지.
