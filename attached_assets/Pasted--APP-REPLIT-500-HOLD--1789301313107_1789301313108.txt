1. Batch Lock TTL — 최우선 재확인
   ━━━━━━━━━━━━━━━━━━━━━━

기존 Production 설계에서는:

* Batch lock TTL = 10분
* batch 실행 중 lock 계속 갱신
* 약 1분 단위 heartbeat/renew

구조가 이미 구현된 것으로 보고되어 있습니다.

그런데 이번 보고서는:

`lock TTL 600초 + 500 pool 순차처리 → TTL 초과`

라고 평가했습니다.

둘이 충돌합니다.

현재 Production 코드에서 실제로 확인하십시오.

제출:

* lock acquire 함수
* TTL
* lock renew/heartbeat 함수 존재 여부
* renew 주기
* owner/token 검증 여부
* 500 pools 처리 loop 동안 heartbeat가 계속 실행되는지
* 작업 종료 시 release 방식
* Render multi-instance에서도 동일한 보호가 되는지

**heartbeat가 실제 존재하고 정상 갱신된다면 이 항목은 CLOSED**입니다.

TTL을 임의로 늘리지 마십시오.

heartbeat가 없거나 실제 loop에서 작동하지 않을 때만 blocker로 보고하십시오.

━━━━━━━━━━━━━━━━━━━━━━
2. Pagination — “500 pools = OOM” 주장 재검증
━━━━━━━━━━━━━━━━━━━━━━

500개의 pool row를 배열로 읽는 것 자체는
메모리 폭탄이라고 볼 근거가 부족합니다.

각 조회마다 실제로 확인하십시오.

특히:

`growth-report-scheduler.ts`
`growth-report-batch-worker.ts`

에서 각 배열의:

* 예상 최대 row 수
* row에 포함되는 주요 컬럼
* scope
* 배열 lifetime
* 다음 pool로 넘어갈 때 참조가 해제되는지
* 전체 pool 데이터를 한 배열에 누적하는지
* 전체 reports를 한 번에 메모리에 잡는 부분이 있는지

를 구분하십시오.

다음처럼 보고하십시오.

A.
eligible pools 500개 배열

→ 실제 메모리 위험 여부

B.
pool별 students 배열

→ pool 처리 후 버려지는지
→ 전체 pools students가 누적되는지

C.
finalize reports 조회

→ 한 번에 최대 몇 건까지 반환 가능한지

D.
발송 대상 조회

→ 한 번에 최대 몇 건까지 반환 가능한지

**500이라는 숫자만 보고 pagination 필요라고 판정하지 마십시오.**

실제로 수만~수십만 rows가 한 배열에 동시에 잡힐 가능성이 있는 조회만 blocker 후보로 분류하십시오.

3. N+1 — 실제 가장 유력한 병목 후보
━━━━━━━━━━━━━━━━━━━━━━

다음은 실제 Capacity 병목 후보로 인정합니다.

* 학생별 growth_reports INSERT
* pool별 batch_jobs INSERT
* 학생마다 SELECT + UPDATE/INSERT

다만 바로 bulk rewrite하지 마십시오.

먼저 현재 코드 기준으로 월 200,000 report 생성 시
DB round-trip 수를 계산하십시오.

예:

* pool 1개당 query 수
* 학생 1명당 query 수
* report 200,000건 생성 시 대략적인 query count

가능하다면 현재 Production의 실제:

* DB query latency
* scheduler cycle 처리시간
* batch creation 처리시간
* DB CPU/connection 사용상태

도 개인정보 없이 확인하십시오.

그 결과:

**20만/96h 처리량에 직접 영향을 줄 정도의 병목이면**
최소 범위 bulk INSERT/UPSERT 방안을 제안합니다.

아니면 현 구조 유지합니다.

4. Progress Update 경쟁
━━━━━━━━━━━━━━━━━━━━━━

현재 학생 처리 concurrency는 최대 3 수준입니다.

`batch_jobs` 같은 동일 row에 동시 UPDATE가 발생한다고 해서
즉시 "lock 폭증"이라고 판단하지 마십시오.

확인:

* UPDATE가 atomic SQL인지
* read → modify → write 구조인지
* lost update 가능성이 있는지
* row lock 대기 실측이 존재하는지
* 한 job당 최대 동시 writer 수

실제 correctness 문제나 lock wait가 없다면
이번 Capacity blocker에서 제외하십시오.
