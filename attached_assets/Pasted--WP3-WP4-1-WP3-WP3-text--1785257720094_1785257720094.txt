# WP3 검토 결과 및 WP4 통합 테스트 승인서

## 1. WP3 검토 결과

WP3는 통과합니다.

확인된 완료 항목:

```text
학생 이름 로그 제거
학생 ref 전체 로그 제거
STT 원문 로그 제거
일지 본문 로그 제거
전체 AI 응답 로그 제거
Authorization 및 Token 로그 제거
pool_id·class_id 실제 값 로그 제거
모든 개발 로그 __DEV__ 제한
JSON 파싱 실패 Contract 오류 처리
JSON 파싱 실패 자동 재시도 차단
Contract 오류 자동 재시도 차단
Stale 응답 조용히 폐기
Stale 응답이 현재 화면을 ERROR로 바꾸지 않음
중복 요청 차단 유지
Unmount 후 State 변경 방지 유지
```

WP3 구현은 승인합니다.

---

# 2. WP4 목적

WP4는 실제 SWIMNOTE 앱과 실제 SWIMNOTE AI Engine 사이의 통합 검증 단계입니다.

이번 단계에서는 새로운 구조를 설계하지 않습니다.

확인할 핵심은 다음 세 가지입니다.

```text
1. 앱 Request가 실제 AI Engine Contract와 일치하는가
2. AI Engine Response가 앱의 표준 Response Contract와 일치하는가
3. AI 기능 실패 시 기존 Diary 작성과 저장 기능이 유지되는가
```

---

# 3. WP4 작업 원칙

WP4는 먼저 테스트하고, 필요한 최소 수정만 합니다.

작업 순서:

```text
실제 API 연결 확인
↓
Request 확인
↓
Response 확인
↓
오류 시나리오 확인
↓
기존 Diary 회귀 확인
↓
필요한 최소 수정
↓
재테스트
↓
완료 보고
```

관련 없는 리팩터링은 금지합니다.

# 4. WP4 시작 전 확인 항목

실제 테스트 전에 다음 환경을 확인합니다.

```text
EXPO_PUBLIC_AI_ENGINE_URL 실제 값
개발 환경 AI Engine URL
Production AI Engine URL
Bearer Token 발급 상태
교사 계정 swimming_pool_id 존재 여부
테스트 반 class_id
테스트 학생 수
AI Engine 배포 버전
AI Engine의 teacher_diary endpoint
```

민감정보와 실제 ID 값은 완료 보고서에 그대로 쓰지 않습니다.

다음 형식으로만 보고합니다.

```text
AI Engine URL configured: yes/no
Bearer Token attached: yes/no
pool_id present: yes/no
class_id present: yes/no
student_count: number
```

# 5. 실제 Endpoint 확인

다를 경우 앱에서 임의로 추측해 변경하지 말고 다음을 보고합니다.

```text

차이

```

실제 API 명세가 확인된 경우에만 최소 수정합니다.

# 6. 실제 Request Contract 검증

실제 전송 Request가 다음 구조인지 확인합니다.

```json
{
  "request_id": "diary_xxx",
  "schema_version": "1.0",
  "feature": "teacher_diary",
  "locale": "ko-KR",
  "input": {
    "text": "교사 입력 원문"
  },
  "context": {
    "pool_id": "pool_xxx",
    "class_id": "class_xxx",
    "lesson_date": "YYYY-MM-DD",
    "student_refs": [
      "student_001"
    ],
    "students": [
      {
        "ref": "student_001",
        "name": "학생 전체 이름"
      }
    ]
  }
}
```

완료 보고서에는 원문과 실제 이름을 출력하지 않습니다.

다음만 보고합니다.

```text
request_id present
schema_version value
feature value
locale value
input_length
pool_id_present
class_id_present
lesson_date_present
student_refs_count
students_count
student_refs와 students[].ref 일치 여부
```

# 7. 실제 Response Contract 검증

AI Engine이 실제로 반환하는 Response를 확인합니다.

목표 표준:

```json
{
  "request_id": "요청과 동일",
  "schema_version": "1.0",
  "result": {
    "common": "공통 일지",
    "students": [
      {
        "student_ref": "student_001",
        "content": "학생별 일지"
      }
    ]
  },
  "usage": {
    "input_tokens": 0,
    "output_tokens": 0,
    "total_tokens": 0
  }
}
```

완료 보고서에는 실제 일지 내용을 넣지 않습니다.

다음 표로 보고합니다.

| 항목              | 실제 반환     | 표준 일치 |
| --------------- | --------- | ----- |
| request_id      | 있음/없음     |       |
| schema_version  | 값         |       |
| result.common   | string 여부 |       |
| result.students | array 여부  |       |
| student_ref     | 있음/없음     |       |
| student_id      | 있음/없음     |       |
| content         | 있음/없음     |       |
| feedback        | 있음/없음     |       |
| usage           | 있음/없음     |       |

# 8. Legacy Flag 판단

현재:

```ts
const ALLOW_LEGACY_RESPONSE_WITHOUT_REQUEST_ID = true;
```

입니다.

WP4 실제 테스트 결과에 따라 처리합니다.

## AI Engine이 request_id를 정상 반환하는 경우

최소 3회 이상의 정상 요청에서 모두 request_id를 반환하고, 요청 ID와 응답 ID가 일치하면:

```ts
const ALLOW_LEGACY_RESPONSE_WITHOUT_REQUEST_ID = false;
```

로 변경하는 것을 권장합니다.

단, 현재 운영 중인 구형 AI Engine 또는 다른 환경이 같은 앱을 사용한다면 바로 제거하지 말고 환경별 호환 여부를 보고합니다.

## AI Engine이 request_id를 반환하지 않는 경우

Flag를 유지합니다.

그리고 다음을 보고합니다.

```text
AI Engine 수정이 필요한지
앱 Legacy 호환을 얼마나 유지해야 하는지
AI Engine 담당 Agent에게 전달할 Contract 수정 내용
```

앱에서 응답 request_id를 임의 생성하거나 채우지 않습니다.

# 9. pool_id 검증

현재 `swimming_pool_id`는 optional입니다.

WP4에서는 최소 두 경우를 확인합니다.

## Case A — pool_id가 있는 정상 교사 계정

기대:

```text
pool_id 전송
AI Engine 정상 처리
```

## Case B — pool_id가 없는 경우

실제 테스트 계정을 만들거나 사용할 수 있으면 테스트합니다.

확인할 결과:

```text
AI Engine 허용
AI Engine 400 반환
AI Engine 401/403 반환
AI Engine 내부 오류
```

pool_id가 없는 경우 앱은 현재 빈 문자열을 전송합니다.

이 정책은 WP4 결과에 따라 다음 중 하나로 결정합니다.

```text
A. AI Engine이 optional로 허용
B. 앱이 요청 전 차단
C. Session에서 pool_id를 반드시 보장
D. API Server를 통해 pool_id를 보완
```

이번 WP4에서 임의 정책을 확정하지 말고 실제 결과와 권장안을 보고합니다.

# 10. 통합 테스트 시나리오

## T1. 공통 내용만 입력

입력 예시 의미:

```text

```

확인:

```text

공통 Draft 생성
학생별 Draft 비어 있어도 정상
적용 버튼 정상
기존 Diary 저장 정상
```

---

## T2. 학생 한 명만 언급

입력 예시 의미:

```text

```

확인:

```text

AI Engine이 student_ref 반환
정확한 학생 Draft에 연결
다른 학생 기존 입력 유지
```

앱이 이름을 분석했는지 여부도 확인합니다.

```text
앱은 전체 학생 목록만 전송
학생 매칭은 AI Engine에서 수행
```

# 11. 새 요청 Abort 로그 확인

WP3에서 보고된 항목을 WP4에서 확인합니다.

시나리오:

```text
요청 A 실행
새 요청 B 실행
A는 new-request로 abort
```

권장 로그 흐름:

```text
A request_started
A request_aborted reason=new-request
B submit_started
B request_started
B request_succeeded
```

중요한 것은 로그 개수보다 실제 동작입니다.

통과 기준:

```text
A가 Draft를 변경하지 않음
B가 정상 처리됨
A가 현재 State를 ERROR로 바꾸지 않음
```

로그 하나가 누락되더라도 기능이 정확하면 WP4 실패로 판단하지 않습니다.

# 12. 실제 AI Engine Contract 차이 처리

테스트 중 앱과 AI Engine Contract가 다르면 임의로 앱만 맞추지 않습니다.

차이별 처리:

## 앱 Request가 잘못된 경우

```text
앱 최소 수정
재테스트
```

## AI Engine Response가 표준과 다른 경우

다음을 보고합니다.

```text
현재 AI Engine Response
표준 Response
호환 가능한지
AI Engine 수정이 필요한지
앱 Legacy 처리가 필요한지
```

AI Engine이 수정되어야 할 문제를 앱에서 계속 우회 처리하지 않습니다.

예:

```text
request_id 미반환
student_ref 미반환
중복 학생 결과
알 수 없는 학생 ref
```

이 문제는 AI Engine Agent에게 전달해야 합니다.

# 18. WP4 이후 처리

WP4 통과 후에도 바로 Production 배포하지 않습니다.

다음 순서로 진행합니다.

```text
WP4 완료 보고
↓
검토
↓
필요 시 앱 또는 AI Engine 수정
↓
최종 통합 재검증
↓
배포 승인
```

WP4가 끝나면 WP5 커리큘럼 조사로 자동 진행하지 않습니다.

WP5는 별도 승인 후 시작합니다.
