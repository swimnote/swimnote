[SWIMNOTE 긴급 통합 수정 — 7월 보강 누락 복구 + 보강 확정·취소 화면 스크롤 불가]

현재 운영 앱에서 아래 두 오류가 확인됐다.

오류 A — 7월 보강 대기 누락

- 7월까지 존재하던 미처리 보강 학생들이 보강 대기 목록에 나타나지 않음
- 현재는 8월 결석으로 생성된 보강만 표시됨
- 정책상 만료일은 유지하지만, 기간이 지나도 삭제하거나 숨기지 않고
  “기간 지난 보강”으로 계속 표시하기로 확정함

오류 B — 보강 확정·취소 화면 스크롤 불가

- 스케줄러 반 상세 화면 하단의 “보강 학생” 영역은 일부 보임
- 보강 확정 또는 취소 화면을 열면 아래쪽으로 스크롤되지 않음
- 학생 또는 버튼이 화면 아래에 잘려 접근할 수 없음
- 이전에 FlatList·모달 제스처 구조를 수정했는데
  보강 관련 서브화면 또는 서브시트에는 동일 수정이 누락된 것으로 보임

이번 작업은 두 오류를 함께 원인 확정하고 최소 수정한다.

Commit / Push / Render 배포 / OTA / 운영 DB 수정은

개인정보는 보고서에서 이름 일부 마스킹한다.

필수 집계:

SELECT status, COUNT(*)
FROM makeup_sessions
WHERE swimming_pool_id = :poolId
GROUP BY status
ORDER BY status;

필수 7월 조회:

SELECT
  id,
  student_id,
  student_name,
  status,
  absence_date,
  expire_at,
  assigned_date,
  completed_at,
  cancelled_at,
  can_expire,
  created_at
FROM makeup_sessions
WHERE swimming_pool_id = :poolId
  AND absence_date >= '2026-07-01'
  AND absence_date < '2026-08-01'
ORDER BY absence_date, created_at;

확인 결과를 다음으로 분류한다.

A-1. DB에 status='expired'로 존재
A-2. DB에 status='waiting'이지만 expire_at만 경과
A-3. completed / cancelled로 변경됨
A-4. 실제 DELETE되어 존재하지 않음
A-5. 다른 swimming_pool_id에 존재
A-6. 보강 세션 자체가 생성되지 않았음

추측하지 말고 실제 결과로 판정한다.

4. 7월 데이터 복구 원칙
━━━━━━━━━━━━━━━━━━━━━━

CASE 1 — DB에 존재하지만 조회에서 제외

→ 조회 조건만 수정한다.

최종 조회 대상:

- waiting + 만료 전
- waiting + expire_at 경과
- expired
- 현재 달 이전 미처리 보강

completed / cancelled는 기존 탭 정책 유지.

CASE 2 — status='expired'로 남아 있음

→ expired도 보강 대기 목록에 포함하고
  is_expired=true로 반환한다.

CASE 3 — waiting이지만 expire_at 경과

→ status를 임의 변경하지 않아도
  is_expired=true로 계산하여 표시한다.

CASE 4 — 실제 DELETE됨

→ 즉시 임의 INSERT 금지.

먼저 다음 자료로 복구 가능성을 조사한다.

- attendance 결석 기록
- pool_event_logs
- audit_logs
- server logs
- class_change_logs
- 기존 backup
- Render/Postgres backup
- deleted row archive
- webhook/event history

복구 가능한 원본이 확인될 때만
복구 SQL 초안을 제출한다.

사용자 승인 없이 실행 금지.

CASE 5 — 보강 세션 자체가 생성되지 않음

→ attendance 결석 기록과 보강 정책을 근거로
  누락 대상 목록만 산출한다.

자동 생성·재생성은 승인 후 별도 실행한다.

- 메인 FlatList의 ListFooterComponent 안에서는
  일반 View + map으로 작은 목록만 렌더하거나

  메인 학생 목록과 보강 학생 목록을 하나의 SectionList로 통합한다.

세로 FlatList 안에 세로 FlatList를 중첩하지 않는다.

권장안 A — SectionList

<SectionList
  sections={[
    { title: "학생 목록", data: sortedStudents, type: "student" },
    { title: "보강 학생", data: makeupStudents, type: "makeup" },
  ]}
  renderItem={...}
  renderSectionHeader={...}
  style={{ flex: 1, minHeight: 0 }}
  contentContainerStyle={{
    paddingBottom: bottomInset + 80,
  }}
  keyboardShouldPersistTaps="always"
  showsVerticalScrollIndicator={false}
/>

권장안 B — 단일 FlatList 혼합 데이터

type RowItem =
  | { type: "student"; student: StudentItem }
  | { type: "makeupHeader" }
  | { type: "makeup"; makeup: MakeupSession };

data에 학생과 보강 학생을 순서대로 넣고
단일 FlatList가 전체 스크롤을 담당한다.

보강 확정·취소 서브시트라면:

<Animated.View style={subSheet}>
  <View style={dragHandleArea}>...</View>
  <View style={header}>...</View>
  <FlatList
    data={...}
    style={{ flex: 1, minHeight: 0 }}
    contentContainerStyle={{
      paddingBottom: bottomInset + 80,
    }}
    keyboardShouldPersistTaps="always"
    showsVerticalScrollIndicator={false}
  />
</Animated.View>

학생 또는 보강 목록 영역에는 panHandlers를 적용하지 않는다.

8. 하단 여백 및 Safe Area

9. 보강 확정·취소 후 스크롤 상태

사용자 제보:

“보강 확정 or 취소 화면 아래로 스크롤 안 됨”

따라서 다음 상태를 각각 검증한다.

1. 보강 학생 선택 전
2. 보강 학생 선택 후
3. 보강반 선택 화면
4. 날짜 선택 화면
5. 보강 확정 확인 화면
6. 보강 취소 확인 화면
7. 처리 성공 후 목록 갱신
8. 처리 실패 후 원래 화면 복귀

상태가 바뀔 때:

- scrollEnabled가 false로 남지 않는지
- loading overlay가 제거되는지
- pointerEvents="none"이 복구되는지
- FlatList ref가 잘못된 offset에 남는지
- 서브시트 높이가 이전 단계 값으로 남는지
- pending state가 해제되는지

확정·취소 후 `finally`에서 반드시 확인한다.

- loading false
- pending 해제
- overlay 제거
- pointerEvents 복구
- scrollEnabled true
