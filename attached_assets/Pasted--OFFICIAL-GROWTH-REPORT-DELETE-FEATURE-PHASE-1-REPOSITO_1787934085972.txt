[앱]

OFFICIAL GROWTH REPORT DELETE FEATURE
PHASE 1 — REPOSITORY INSPECTION + IMPLEMENTATION DESIGN ONLY

목표:
이미 발급된 AI 성장 리포트를
관리자가 정식으로 삭제할 수 있는 기능을 설계한다.

이 기능은 테스트용 maintenance 기능이 아니라
실제 운영에서 사용할 공식 기능이다.

삭제 시:
- Growth Report 본체 삭제
- 해당 리포트 좋아요 삭제
- 해당 리포트 댓글 삭제
- 해당 리포트 관련 notification 삭제
- 선생님에게 보이던 해당 좋아요/댓글/반응도 제거
- 학부모 feed/history/detail에서 제거
- 동일 학생/동일 월 리포트 재발급 가능

이번 단계는 설계만.
코드 수정 금지.
DB write 금지.
production data 변경 금지.

==================================================
7. DELETE 방식 설계
==================================================

다음 중 실제 schema에 가장 안전한 방식 판단:

A. HARD DELETE
B. SOFT DELETE
C. 기존 lifecycle 상태 기반 DELETE

중 하나 추천.

이번 기능 요구사항:

- 삭제 후 parent feed/history/detail에서 완전히 사라져야 함
- 좋아요/댓글도 완전히 제거
- 관련 알림 제거
- 같은 월 재발급 가능
- orphan 0

기존 schema가 hard delete에 적합하면
불필요한 soft-delete 설계 금지.

==================================================
8. TRANSACTION DESIGN
==================================================

삭제는 반드시 하나의 DB transaction으로 설계.

실제 dependency 기준으로
정확한 delete order 제시.

예시일 뿐:

1. reaction notifications
2. comments
3. likes
4. published notification
5. 기타 dependent rows
6. growth_report

실제 FK/cascade 기준으로 수정.

중간 실패 시 전체 rollback.

==================================================
9. AUTHORIZATION
==================================================

누가 삭제할 수 있어야 하는지
기존 앱 역할 체계 기준으로 설계.

우선 요구:

- 수영장 운영자/admin: 자신의 pool report 삭제 가능
- super_admin: 필요 시 전체 가능
- teacher: 삭제 불가
- parent: 삭제 불가

기존 authorization helper/pattern이 있으면 재사용.

다른 pool report 삭제 절대 불가.
