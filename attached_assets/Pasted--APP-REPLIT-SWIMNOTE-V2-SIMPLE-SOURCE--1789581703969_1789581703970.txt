[보낼 곳: APP REPLIT]

[SWIMNOTE 정산 V2 — SIMPLE SOURCE 설계 보정]

중요한 방향 수정입니다.

이번 정산 자동계산은
여러 데이터를 섞어 추론하는 시스템으로 만들지 않습니다.

자동계산에는
명확한 하나의 기준점을 둡니다.

━━━━━━━━━━━━━━━━━━━━━━
1. 핵심 원칙
━━━━━━━━━━━━━━━━━━━━━━

정산 자동계산의 PRIMARY SOURCE는:

“해당 월 시간표에 등록되어 있는
학생의 수업회수”

입니다.

즉 기본 자동매출은
스케줄/시간표 기준입니다.

attendance
holiday
cancellation
temp transfer
기타 기록을

각각 가져와
금액 계산에 계속 더하고 빼는 구조를 만들지 마십시오.

숫자의 근거가
한눈에 설명 가능해야 합니다.

━━━━━━━━━━━━━━━━━━━━━━
2. 정산 기준을 하나로 정의
━━━━━━━━━━━━━━━━━━━━━━

우리가 원하는 개념:

[MONTHLY SCHEDULE ROSTER]

학생이 해당 월
어느 반에
어느 기간 동안 등록되어 있었고

그 반의 시간표 기준으로
몇 회 수업 대상이었는가.

이것이 자동매출의 기준입니다.

현재 DB에서 이를 가장 안정적으로 계산하기 위해

student_class_history
+
class_groups.schedule_days

두 구조가 필요하다면 사용할 수 있습니다.

하지만 이것을
서로 다른 정산 Source 두 개로 취급하지 마십시오.

둘을 합쳐서 만드는

“월별 시간표 등록 회수”

하나를
정산 Source of Truth로 정의하십시오.

즉:

student_class_history
= 그 학생이 언제 그 반에 있었는지

schedule_days
= 그 반 수업 요일이 무엇인지

를 이용해

monthly_scheduled_sessions

하나만 산출합니다.

그 이후 자동매출은
이 값만 기준으로 계산합니다.

━━━━━━━━━━━━━━━━━━━━━━
3. ATTENDANCE는 매출 계산에서 제외
━━━━━━━━━━━━━━━━━━━━━━

attendance는 자동매출 금액 계산에 사용하지 않습니다.

이유:

선생님이 출결을 누락하면
매출이 0 또는 감소하는 구조가 되면 안 됩니다.

attendance는:

- 출석 관리
- 실제 수업 확인
- 향후 통계

용으로 유지.

정산 자동매출의 Source of Truth로 사용 금지.

━━━━━━━━━━━━━━━━━━━━━━
4. 휴일 / 휴강 / 취소
━━━━━━━━━━━━━━━━━━━━━━

이번 V2 자동매출에서
별도 holiday/cancellation 데이터를 찾아
자동으로 차감하는 복잡한 로직을 만들지 마십시오.

시간표 자체가 수정되어
해당 수업이 사라지는 구조라면
시간표 변경 결과만 자연스럽게 반영.

그렇지 않고
실제 운영상 특정 날짜만 휴강된 경우에는

이번 V2에서는
선생님 manual adjustment로 처리합니다.

자동계산 엔진이
여러 달력/공지/출결을 조합해서
“이날은 수업 안 했겠지”라고 판단하면 안 됩니다.

━━━━━━━━━━━━━━━━━━━━━━
5. 완료 보강만 유일한 명시적 예외
━━━━━━━━━━━━━━━━━━━━━━

사용자 요구:

정규 계산 대상이 5회이고
완료 보강 1회가 있으면

5 + 1 = 6회

로 계산합니다.

따라서 자동 계산의 유일한 별도 추가 Source는:

makeup_sessions
status = completed

입니다.

WAITING
EXPIRED
취소
미완료

등은 0회.

즉 공식은 단순하게:

scheduled_count
= 시간표 기준 학생 정규 수업회수

completed_makeup_count
= 완료된 보강회수

service_count
=
scheduled_count
+
completed_makeup_count

billable_count
=
MIN(service_count, standard_session_count)

auto_amount
=
billable_count × per_session_amount

이 공식에서 더 이상 다른 데이터를
자동으로 가감하지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
6. 정상 월수업료 CAP
━━━━━━━━━━━━━━━━━━━━━━

예:

주2회

정상 월 수업료:
220,000

기준 회수:
8

1회 기준:
27,500

정규 5 + 보강 1
→ 6회
→ 165,000

정규 8 + 보강 1
→ 9회가 아니라
billable_count cap = 8
→ 220,000

정규 9
→ cap 8
→ 220,000

정상 월수업료를
자동계산이 초과하지 않습니다.

추가 결제를 실제로 받은 경우만
선생님이 +조정합니다.

━━━━━━━━━━━━━━━━━━━━━━
7. 학생별 가격 매핑
━━━━━━━━━━━━━━━━━━━━━━

반드시 하나의 명확한 규칙으로 정하십시오.

student
→ pricing_type
→ monthly_fee
→ standard_session_count
→ per_session

현재 DB에서
학생의 주1/주2/주3 또는 custom 가격유형을
어떻게 결정할 수 있는지 확인하십시오.

여러 후보를 동시에 계산하지 마십시오.

현재 구조에서 가장 명확한 하나를 선정하십시오.

만약 학생별 pricing_type이 저장되어 있지 않고
반의 schedule_days 개수로만 결정해야 한다면

그 사실을 명확히 보고하십시오.

예:

주1 반 → weekly_1
주2 반 → weekly_2
주3 반 → weekly_3

같은 단일 규칙.

custom_1/custom_2는
현재 학생과 연결하는 명확한 필드가 없다면
자동 추측하지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
8. 중간 등록 / 중간 퇴원
━━━━━━━━━━━━━━━━━━━━━━

이것도 시간표 Source 안에서 처리합니다.

student_class_history로:

effective_start
effective_end

만 정하고

그 기간 안의
schedule_days 수업일만 count.

즉:

9/15 등록
→ 9/15 이후 시간표 회수만 계산

9/18 퇴원
→ 퇴원 기준 이전 시간표 회수만 계산

별도 attendance 보정 없음.

━━━━━━━━━━━━━━━━━━━━━━
9. 반 이동
━━━━━━━━━━━━━━━━━━━━━━

반 이동도 동일합니다.

학생의 class history 기간을 기준으로

이전 반 기간
→ 이전 반 시간표

새 반 기간
→ 새 반 시간표

만 계산.

같은 날짜를
두 반에서 중복 계산하지 않도록

student_class_history의
enrolled_at / left_at 의미를 확인해서

기간 규칙 하나를 확정하십시오.

예:

[enrolled_at, left_at)

형태.

━━━━━━━━━━━━━━━━━━━━━━
10. 선생님 수업시수는 별도
━━━━━━━━━━━━━━━━━━━━━━

회원 매출과
선생님 실제 수업시수는 분리합니다.

회원매출:
시간표에 등록된 학생 기준.

수업시수:
실제 class session 개수 기준.

한 반 학생 5명
수업 1회

→ 매출 학생 5명 각각 계산
→ 선생님 수업시수는 1회.

보강:
완료 보강 1건
→ 실제 담당 선생님 수업시수 +1.

보강을 다른 선생님이 진행해도
학생의 회원매출 귀속 자체를
보강 선생님에게 넘기지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
11. 수동조정이 예외처리 담당
━━━━━━━━━━━━━━━━━━━━━━

자동계산이 모르는 모든 현실 변수:

- 할인
- 이벤트
- 체험
- 회수결제
- 추가결제
- 특별 수강료
- 휴강 관련 금액조정
- 기타

는 manual adjustment로 처리합니다.

자동엔진을 복잡하게 하지 않습니다.

학생별:

auto_amount
+
adjustment_amount
=
final_amount

사유:

discount
trial
collect
other

+ memo.

12. 관리자 반영 규칙
━━━━━━━━━━━━━━━━━━━━━━

선생님 미저장:

reflected_amount
=
current_auto_amount

선생님 저장:

reflected_amount
=
saved_final_amount

관리자 전체:

각 선생님의 reflected_amount를
단순 SUM.

다른 보정 로직 추가 금지.

━━━━━━━━━━━━━━━━━━━━━━
13. 저장 후 시간표 변경
━━━━━━━━━━━━━━━━━━━━━━

저장 당시:

auto_amount_snapshot

을 보존.

현재:

current_auto_amount

를 동일한 단일 계산식으로 다시 계산.

둘이 다르면:

has_changed = true

조회 시 동적 계산.

snapshot_changed boolean 저장은
우선 만들지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━

- attendance

- notice
- diary
- payment records

“이 학생이 이 달 시간표상 몇 회 수업 대상이었는가?”

입니다.

여기에:

“완료된 보강 몇 회인가?”

만 더합니다.

그 뒤 cap.

끝입니다.
