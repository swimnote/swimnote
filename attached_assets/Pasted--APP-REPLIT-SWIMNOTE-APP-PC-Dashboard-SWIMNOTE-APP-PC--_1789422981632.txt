[보낼 곳: APP REPLIT]

SWIMNOTE APP + PC Dashboard의 마지막 핵심 정리 작업입니다.

이전의
「SWIMNOTE APP + PC 통합 권한·교육기록 교통정리 설계보고서」
조사 결과를 기반으로 설계를 수정·확정합니다.

이번에는 코드 수정하지 마십시오.
배포하지 마십시오.
DB migration 하지 마십시오.

목표는 딱 2개입니다.

1. 보강 관리 구조 최종 확정
2. 성장리포트 ownership / 열람 / 알림 경로 최종 확정

이 두 개는 현재 SWIMNOTE APP 완성 단계의 마지막 핵심 퍼즐입니다.

복잡한 기능 추가보다
운영자가 실제로 헷갈리지 않는
단순하고 명확한 구조를 우선합니다.

━━━━━━━━━━━━━━━━━━━━━━
0. 가장 중요한 제품 원칙 수정
━━━━━━━━━━━━━━━━━━━━━━

기존의:

APP + WEB ONE SYSTEM

원칙은 유지합니다.

하지만 의미를 다음과 같이 정확히 수정합니다.

[APP FIRST / PC ASSIST]

SWIMNOTE 모바일 APP
= 현장 운영의 주 시스템

SWIMNOTE X PC Dashboard
= 관리자 사무업무를 돕는 보조 시스템

PC Dashboard는 모바일 APP을 대체하지 않습니다.

PC에 우선 배치할 기능:

- 대량 입력/수정
- Excel import/export
- 다수 회원 빠른 조회
- 관리자가 업무 중 PC에서 빠르게 확인해야 하는 것
- 전체 현황 / 누락 / 밀림 / 예외 확인
- 성장리포트 검수·발행 같은 관리자 업무

반대로:

- 선생님의 실제 수업운영
- 일일 스케줄 관리
- 보강 일정 결정
- 현장에서 즉시 처리하는 업무

는 APP이 중심입니다.

APP 기능을 무조건 PC에 1:1 복제하지 마십시오.

공통이어야 하는 것은:

- 데이터 의미
- ownership
- 권한
- 상태
- API contract
- workflow

이지,

모든 기능과 버튼을
APP/PC 양쪽에 똑같이 만드는 것이 아닙니다.

1. 보강 — 최종 철학
━━━━━━━━━━━━━━━━━━━━━━

보강에서 역할을 명확하게 분리합니다.

[TEACHER]

선생님이 실제 보강 운영의 책임자입니다.

기존 APP 흐름을 유지합니다.

선생님이 자기 담당 범위에서:

- 보강 대상 확인
- 보강 일정 결정
- 보강 반 선택
- 실제 스케줄에 배정
- 일정 변경
- 취소
- 완료 처리

등 실제 보강 업무를 직접 합니다.

관리자가 선생님의 보강 일정까지 대신 관리하게 만들지 마십시오.

그렇게 되면:

선생님 일정
+
관리자가 정한 일정

이 섞여 운영이 더 복잡해지고,
현재 APP 보강 기능의 의미가 사라집니다.

━━━━━━━━━━━━━━━━━━━━━━
2. pool_admin 보강 역할 = 최종관리 / 감독
━━━━━━━━━━━━━━━━━━━━━━

pool_admin은 보강을 직접 운영하는 사람이 아닙니다.

pool_admin의 역할:

자기 수영장 전체 보강 현황을 보고

"보강이 정상적으로 처리되고 있는가"

를 감독하는 것입니다.

관리자가 중요하게 봐야 하는 것:

- 현재 미처리 보강
- 아직 일정이 잡히지 않은 보강
- 오래 밀린 보강
- 기한 임박 보강
- 기간 만료 예정 보강
- 이미 기간이 지나 소멸될 보강
- 필요하면 선생님별 미처리 현황

단,

기한/소멸 기준은
현재 실제 DB와 기존 보강 정책을 먼저 확인하십시오.

새로운 만료 정책이나 계산식을 임의로 만들지 마십시오.

기존 필드/정책이 있다면 그것을 SoT로 사용합니다.

즉:

pool_admin
= MONITOR / SUPERVISE

teacher
= OPERATE

입니다.

4. 관리자 보강 UI 목표
━━━━━━━━━━━━━━━━━━━━━━

APP 관리자 화면과
PC Dashboard 관리자 화면 모두

"보강 운영 화면"

이 아니라

"보강 현황 관리 화면"

으로 정리합니다.

관리자에게 가장 먼저 보여야 하는 것은:

- 전체 미처리 수
- 오래 밀린 보강
- 만료 임박
- 만료/소멸 대상

입니다.

필요한 경우:

- 학생
- 현재 담당 선생님
- 원래 결석일
- 현재 상태
- 예정된 보강일
- 잔여 기한

등 기존 데이터 범위에서
관리자가 상황을 판단할 수 있는 정보만 표시합니다.

관리자가 이 화면에서
직접 스케줄을 집어넣게 만들지 마십시오.

PC Dashboard에서는 특히:

"선생님 대신 처리하는 화면"

이 아니라

"전체를 빠르게 훑고 문제만 발견하는 화면"

이어야 합니다.

기존 PC Dashboard에
pool_admin용 배정/취소/완료/transfer 버튼이 있다면
최종 구현에서는 제거 또는 비노출 대상입니다.

5. 기존 보강 Root Cause는 유지
━━━━━━━━━━━━━━━━━━━━━━

이전 조사에서 확인된:

GET /admin/makeups

내

callerRole !== 'super_admin'

pool_admin도 teacher scope로 좁혀지는 문제는

최종 구현 방향은:

pool_admin:
pool_id 전체 조회

teacher:
기존 teacher scope

입니다.

단,

조회 권한 확대와
mutation 권한 확대를 혼동하지 마십시오.

pool_admin이 전체를 "본다"
≠
pool_admin이 전체를 "조작한다"

입니다.

13. Production Growth Report 오류 — 반드시 사실확인
━━━━━━━━━━━━━━━━━━━━━━

"성장리포트를 불러오지 못했습니다."

실제 Error가 남아 있습니다.

이전 보고서의:

"growth_reports 테이블이 없을 가능성이 가장 높다"

는 아직 가설입니다.

이 가설만으로 migration 하지 마십시오.

실제 failing request 1회 기준으로:

- Request URL
- HTTP status
- response body
- Render backend error
- 실제 SQL/route error

만 확인해서
Root Cause를 확정하십시오.

0건은 Error가 아닙니다.

0건이면:

"발행할 성장리포트가 없습니다."

API 실패일 때만:

"성장리포트를 불러오지 못했습니다."

가 되어야 합니다.

Production DB migration은
실제로 누락이 확인될 때만 제안하십시오.
