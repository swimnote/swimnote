# 관리자 권한 부여·회수 최종 계획 보완 요청 (실행 전 마지막 수정)

현재 제출한 계획서는 이전보다 크게 개선되었으며,
전체 방향은 승인 가능합니다.

다만 실제 운영과 향후 SWIMNOTE X 공통 권한 엔진으로
사용하기 위해 아래 사항을 반드시 보완한 후
최종 수정을 진행하세요.

이번 답변은 코드 수정이 아니라
계획 보완 및 수정 반영입니다.

==================================================
1. DB 권한 확인 실패 시 절대 통과시키지 마세요.
==================================================

현재 requireRole 수정안에는 다음 코드가 있습니다.

.catch(err => {
    console.error(...);
    next();
});

이 구조는 승인할 수 없습니다.

DB 오류가 발생했는데
관리자 API를 그대로 실행하면
권한 검증이 우회됩니다.

권한 시스템은 Fail Open이 아니라
Fail Closed 원칙을 따라야 합니다.

수정 방향:

DB 조회 실패 시

HTTP 503

예)

{
  "success": false,
  "code": "ROLE_CHECK_FAILED",
  "message": "권한 확인에 실패했습니다."
}

을 반환하세요.

DB 장애 시
관리자 API는 실행되면 안 됩니다.

==================================================
2. pool_admin 캐시 정책 재검토
==================================================

현재

ROLE_CACHE_TTL = 30초

입니다.

권한 회수는
실시간 보안 기능입니다.

현재는

clearPoolAdminCache(userId)

를 호출하므로 대부분 문제가 없지만,

향후 Render 다중 인스턴스,
확장 서버,
로드밸런서 환경에서는
다른 인스턴스 캐시는 제거되지 않습니다.

다음 두 가지 중 하나를 선택하세요.

A.

pool_admin 권한은 캐시 없이
항상 DB 조회

또는

B.

TTL을 매우 짧게

예)

3~5초

정도로 축소

그리고
선택한 이유를 설명하세요.

==================================================
3. ROLE_REVOKED 처리를 AuthContext에 직접 몰아넣지 마세요.
==================================================

현재 구조

apiRequest
↓

ROLE_REVOKED

↓

AuthContext

↓

switch-role

↓

router

↓

Alert

↓

Storage

↓

cache clear

이렇게 되면

teacher

pool_admin

swimnote_x

등 역할이 늘어날수록
AuthContext가 비대해집니다.

다음 구조를 권장합니다.

RoleManager

↓

handleRoleRevoked()

↓

AuthContext는 RoleManager만 호출

이번 수정에서
RoleManager 파일을 새로 만들 필요는 없지만,

향후 권한 처리를 분리하기 쉽도록
코드를 작성하세요.

Role 관련 로직을
AuthContext 곳곳에 흩뿌리지 마세요.

==================================================
4. ROLE_REVOKED를 공통 권한 시스템으로 설계하세요.
==================================================

이번에는

ROLE_REVOKED

만 사용하지만,

향후 SWIMNOTE X에서
같은 시스템을 사용할 예정입니다.

따라서
권한 오류 코드는
확장 가능한 구조로 작성하세요.

예)

ROLE_REVOKED

ROLE_DISABLED

CENTER_DISABLED

LICENSE_EXPIRED

ROLE_NOT_ALLOWED

등을 쉽게 추가할 수 있도록
enum 또는 상수 구조를 검토하세요.

이번 작업에서
모든 코드를 구현할 필요는 없지만

ROLE_REVOKED만 하드코딩된
일회성 구조는 만들지 마세요.

==================================================
5. 이번 권한 엔진은 SWIMNOTE X의 기반입니다.
==================================================

이번 수정은

관리자 권한 기능만을 위한 수정이 아닙니다.

향후

Teacher

Pool Admin

SWIMNOTE X

AI Bundle

Premium Bundle

등 모든 권한 제어의
공통 엔진이 됩니다.

따라서

pool_admin

만을 위한 특수 코드가 아니라

역할(Role)

권한(Bundle)

현재 모드(Active Role)

를 확장할 수 있도록
작성하세요.

==================================================
6. 나머지 계획은 승인합니다.
==================================================

다음 내용은 그대로 진행하세요.

- 취소 버튼 UI 수정
- handleGrant / handleRevoke try-catch-finally
- optimistic update 제거
- users.role 대신 users.roles 기준 조회
- requireRole 내부 DB 권한 검증
- ROLE_REVOKED 반환
- teacher 자동 복귀
- 서버 우선, OTA 후 배포
- 테스트 계획

==================================================
7. 수정 후 제출 형식
==================================================

수정 완료 후

다음 항목만 간단히 보고하세요.

1.
DB 오류 시 ROLE_CHECK_FAILED 처리 완료 여부

2.
캐시 정책

- 캐시 제거
또는
- TTL 몇 초

3.
RoleManager 분리 여부
또는 향후 분리 가능한 구조인지

4.
ROLE_REVOKED 공통 권한 코드 적용 여부

5.
실제 수정 파일 목록

계획 승인 후
서버 수정 → 서버 배포 → OTA 순으로 진행하세요.

추가 기능은 구현하지 말고
이번 범위만 수정하세요.
