[SWIMNOTE SUPPORT — WP-CS12 FAQ / KNOWLEDGE / SOLUTION CANDIDATE GENERATION]

## 1. 목적

WP-CS11에서 확정된 Support Coverage Gap을
실제로 답변 가능한 Support DB 후보로 변환한다.

현재 CS11 baseline:

TOTAL = 75
COVERED_ACTIVE = 7
COVERED_PENDING = 1
PARTIAL = 46
MISSING = 21
UNCLASSIFIED = 0

P0 MISSING = 10.

이번 WP의 목표는:

Coverage Gap
→ 실제 APP/Server source 확인
→ 적합한 Support Candidate 설계
→ PENDING 저장

이다.

Candidate 종류:

FAQ
KNOWLEDGE
SOLUTION

필요한 경우 KNOWN_ISSUE 후보의 입력자료는 정리할 수 있으나
WP-CS15 Known Issue lifecycle 구현까지 진행하지 않는다.

절대 자동 ACTIVE 하지 않는다.

## 5. CANDIDATE TYPE 결정

각 Gap마다 실제 문의 성격을 보고
적합한 유형 하나 또는 필요한 조합을 선택한다.

### FAQ

제품 설명
정상적인 사용방법
정책
기본 절차

예:

"탈퇴는 어떻게 하나요?"
"알림 권한은 어디서 켜나요?"

### KNOWLEDGE

기능 설명
권한 조건
mode 차이
상태 의미
정책/제약조건

예:

특정 역할에서는 어떤 데이터가 보이는지.

### SOLUTION

문제 해결이 필요한 증상.

구조:

symptom
conditions
diagnostic
root_cause if actually known
solution_steps
verification
escalation

예:

"출결 메뉴가 안 보여요"
"데이터가 안 보여요"

### KNOWN ISSUE 관련

현재 장애 여부가 필요한 항목은
가짜 장애 FAQ를 만들지 않는다.

현재 장애가 없는데:

"현재 서버 장애가 발생했습니다"

같은 답변 생성 금지.

대신 필요한 경우:

* 장애 확인 방법
* 장애 시 사용자 안내 contract
* escalation route

등의 candidate만 생성.

실제 incident state는 WP-CS15에서
`super_incidents`와 연결한다.

## 6. SOURCE / PROVENANCE 필수

Candidate마다 반드시 실제 source가 있어야 한다.

허용 source 예:

* 실제 frontend route/screen
* 실제 UI text
* 실제 server route
* 실제 permission guard
* 실제 auth logic
* 실제 DB state
* 실제 app settings behavior
* 실제 OS permission integration
* 실제 subscription implementation
* 실제 SWIMNOTE product policy
* 기존 ACTIVE Knowledge
* 기존 documented operational rule

금지:

* 일반적인 앱 상식으로 SWIMNOTE 기능 추측
* GPT 자체 지식
* 존재하지 않는 버튼/화면
* 아직 구현되지 않은 기능을 현재 기능처럼 설명
* 가격/환불정책 임의 생성
* 장애 상태 추측
* role/mode 접근권한 추측

source가 부족하면:

`SOURCE_GAP`

으로 남기고
candidate를 억지로 생성하지 않는다.

## 7. P0 10개 처리 계약

### 7.1 AUTH_ACCOUNT_WITHDRAWAL

실제 앱에서:

* 탈퇴 기능 존재 여부
* route/screen
* role 제한
* server endpoint
* 데이터 처리 방식
* 현재 사용자에게 안내 가능한 범위

확인.

실제 source 범위 안에서 FAQ/Knowledge candidate 생성.

탈퇴 데이터 보존/삭제 정책을 추측하지 않는다.

---

### 7.2 AUTH_POOL_ACCESS_DENIED

실제 pool access/auth guard 확인.

사용자가 접근 거부를 만났을 때:

* 가능한 실제 원인
* 사용자가 확인할 수 있는 것
* 관리자 확인이 필요한 것
* escalation 조건

을 Solution candidate로 구조화.

cross-pool 접근을 해결책으로 우회하지 않는다.

---

### 7.3 ATTENDANCE_PERMISSION_DENIED

실제 attendance permission/role guard 확인.

role별 실제 접근 가능 범위를 근거로
Solution 또는 Knowledge candidate 생성.

권한 없는 사용자에게
권한 우회법 안내 금지.

---

### 7.4 NOTIFICATION_PERMISSION_OS

현재 앱의 실제 push permission 흐름과
iOS/Android 구현을 확인.

실제 앱에서 안내 가능한
OS 권한 설정 절차만 작성.

플랫폼별 경로가 다르면
하나의 거짓 공통경로로 합치지 않는다.

---

### 7.5 DATA_NOT_VISIBLE_ROLE_MISMATCH

실제 role/context에 따라
데이터가 숨겨지는 구조 확인.

증상
→ role/context 확인
→ 정상 제한인지 오류인지
→ 사용자 조치
→ escalation

형태의 Solution candidate.

---

### 7.6 DATA_NOT_VISIBLE_FILTER

실제 filter/search/date/status UI 확인.

존재하는 필터만 안내.

"필터 초기화" 기능이 실제 없으면
그 버튼을 만들어내지 않는다.

---

### 7.7~7.10 KNOWN ISSUE 계열

* SERVER_API
* AI_PROVIDER
* PUSH
* BILLING

이번 WP에서는
현재 장애를 만들어내지 않는다.

각 영역의:

* 정상 사용자 troubleshooting
* 장애 가능성 확인
* Known Issue 조회 필요 여부
* human escalation 조건

에 필요한 Support candidate를 만든다.

실제 live incident 여부를 답하는 기능은
CS15에서 마감한다.

## 8. PARTIAL 46 처리

CS11에서 PARTIAL의 대부분은:

Frontend Map WHERE_IS 존재
하지만
HOW_TO / ERROR / SOLUTION 부족

으로 확인됐다.

각 PARTIAL에 대해 먼저 판단:

A. WHERE_IS만 있으면 충분한 기능
→ 추가 candidate 불필요

B. HOW_TO가 launch에 필요
→ FAQ/Knowledge candidate

C. 실제 failure 가능성이 높음
→ Solution candidate

D. 둘 다 필요
→ 각각 candidate 가능

단 같은 정보를 표현만 바꿔
FAQ row 여러 개로 복제하지 않는다.

Query synonym/alias는 CS14 책임.

## 9. 중복 방지

Candidate 생성 전에 기존:

ACTIVE
PENDING
INACTIVE
ARCHIVED

전부 exact/semantic-equivalent 수준에서 확인.

동일 의미 candidate 중복 생성 금지.

기존 PENDING이 충분하면 재사용.

기존 ACTIVE가 gap을 실제로 커버한다면
CS11 classification과의 discrepancy를 보고하되
불필요한 새 candidate 생성 금지.

## 10. ROLE / MODE / SCOPE

이번 WP에서 임의로 role policy를 새로 정의하지 않는다.

실제 auth/source에 명백히 확인되는 범위만 기록.

Actual JWT roles:

* pool_admin
* sub_admin
* teacher
* parent_account

legacy `parent` 혼용에 주의.

CS13에서 전체 Role/Mode/Scope Integrity Audit를 별도로 수행하므로
애매한 항목은:

`ROLE_SCOPE_REVIEW_REQUIRED`

표시 가능.

단 명백한 parent/admin leakage candidate는 만들지 않는다.

Normal/X/x_pending도
실제 source가 있는 범위만 지정.

## 12. ANSWER 작성 품질

FAQ/Knowledge candidate의 answer는:

* 실제 사용자에게 바로 보여줄 수 있는 자연스러운 한국어
* 짧고 명확
* 실제 앱 기준
* 없는 기능 창작 금지
* 내부 개발용 용어 노출 최소화
* 내부 route명/DB명 불필요하게 노출 금지

하지만 provenance에는
실제 source를 명확히 남긴다.

Solution은 사용자 답변문만 저장하는 것이 아니라
기존 Solution 구조에 맞게:

symptom
diagnostic
steps
verification
escalation

을 최대한 구조적으로 저장한다.

## 13. SECURITY

절대 금지:

* 다른 pool 데이터 확인 유도
* admin 기능을 parent에게 안내
* X-only 관리기능을 Normal 사용자에게 일반기능처럼 안내
* 내부 server secret/API key 노출
* JWT/debug 정보 사용자 답변에 포함
* 개인정보가 candidate answer에 포함

Candidate는 재사용 가능한 일반 Support 지식이어야 한다.

## 14. FAILURE HANDLING

억지 candidate 생성 금지.

다음으로 표시:

SOURCE_GAP
IMPLEMENTATION_GAP
POLICY_GAP
ROLE_SCOPE_REVIEW_REQUIRED

필요한 경우 후속 WP 입력으로 남긴다.

이것 때문에 CS12 전체를 무조건 HOLD하지 않는다.

단 P0에서 사용자에게 위험한 잘못된 안내를 만들 가능성이 있는
critical source gap은 명확히 보고한다.

## 16. PRODUCTION WRITE 정책

Candidate를 production DB에 넣는 작업이라면:

* PENDING only
* 최소 write
* 기존 row 삭제 금지
* 기존 ACTIVE 수정 금지
* idempotent 생성
* 중복 방지
* provenance 보존

가능하면 기존 seed/import/create mechanism 재사용.

새 migration은 이번 WP 기본 scope가 아니다.

Production에 쓰지 않고
candidate artifact만 만드는 기존 architecture라면
그 구조를 그대로 사용.

실제 repository source of truth를 따른다.

---

## 17. DEPLOYMENT

이번 WP가 server/client runtime code를 변경하지 않고
candidate data만 생성하는 구조라면
불필요한 OTA 금지.

Server code 변경이 실제 필요했다면:

* commit
* test
* deploy 필요 여부 보고

하지만 candidate generation 때문에
관련 없는 앱 OTA를 보내지 않는다.
