# SWIMNOTE Teacher Diary 전체 계획 공유 및 Repository별 책임 범위 검토 요청

## 이번 요청의 목적

SWIMNOTE Teacher Diary를 단순한 STT 문장 정리 기능이 아니라, 다음 정보를 결합하여 학부모에게 전달할 수 있는 완성된 수영 수업 일지를 만드는 시스템으로 변경합니다.

```text
선생님의 실제 관찰
+
해당 수영장의 커리큘럼
+
오늘 수업 과정
+
학생별 현재 진도와 완료 이력
+
수영장이 승인한 일지 Template
+
SWIMNOTE 수영교육 Knowledge
↓
GPT가 학부모용 완성 문장으로 조립
```

현재 SWIMNOTE 앱 Repository와 Production AI Engine Repository가 분리되어 있습니다.

이번 요청은 구현 지시가 아닙니다.

동일한 전체 계획을 앱 Replit과 AI Engine Replit 양쪽에 전달하여, 각 Repository가 실제로 어디까지 책임질 수 있는지 확인하기 위한 기술 검토 요청입니다.

자신의 Repository에 없는 구조를 추측하지 마십시오.

자신이 확실하게 구현할 수 있는 범위, 상대 Repository가 담당해야 하는 범위, 양쪽이 겹치는 범위, Contract 확정이 필요한 범위를 구분하여 보고하십시오.

# 2. 핵심 제품 정의

Teacher Diary는 다음 기능이 아닙니다.

```text
음성
→ STT
→ 문장 다듬기
```

목표는 다음과 같습니다.

```text
선생님이 짧게 관찰 내용을 말함
↓
학생과 공통 내용을 정확히 분리
↓
학생이 현재 배우는 수영장별 커리큘럼 확인
↓
관련 Template와 Knowledge 조회
↓
관찰 사실을 벗어나지 않는 범위에서 교육적 맥락 보강
↓
학부모가 이해할 수 있는 충분한 길이의 일지 생성
```

일지는 보통 다음 세 층으로 구성할 수 있습니다.

```text
1. 선생님이 실제로 말한 관찰
2. 해당 학생이 현재 배우는 커리큘럼 설명
3. 해당 교육과정의 목적과 수업 의미
```

다음 내용은 근거 없이 생성하면 안 됩니다.

```text
선생님이 관찰하지 않은 오류
확인되지 않은 오류 원인
실제로 하지 않은 교정
실제로 하지 않은 드릴
확인되지 않은 향상
학생의 감정·성격·태도 추측
다음 진도 확정
```

# 3. 시스템 책임 원칙

## 앱의 기본 역할

```text
음성 또는 텍스트 입력
Whisper STT
수업과 학생 Context 확보
AI Request 생성
Production AI Engine 호출
AI Draft 표시
선생님 수정·재생성·적용
기존 Diary 저장
```

## AI Engine의 기본 역할

```text
Request 검증
이름 매칭
Common / Student 분리
Observation 구성
커리큘럼 조회와 범위 확정
Template Search
Knowledge Search
GPT 재료 구성
최종 일지 생성
Output 검증
표준 Response 반환
```

단, 위 구분은 아직 최종 확정이 아닙니다.

각 Repository의 실제 데이터 보유 위치와 현재 코드 구조를 확인한 뒤 책임 경계를 제안하십시오.

# 4. 목표 Request Context

최종 필드명은 양쪽 Repository 검토 후 확정합니다.

목표 개념은 다음과 같습니다.

```json
{
  "request_id": "req_xxx",
  "feature": "teacher_diary",
  "input": {
    "text": "오늘은 자유형 호흡을 연습했습니다. 태웅이는 호흡이 조금 늦었습니다."
  },
  "context": {
    "organization_ref": "center_xxx",
    "class_ref": "class_xxx",
    "lesson_ref": "lesson_xxx",
    "lesson_date": "2026-07-29",
    "student_refs": [
      "student_xxx"
    ],
    "students": [
      {
        "ref": "student_xxx",
        "name": "서태웅"
      }
    ]
  }
}
```

확정 원칙:

```text
앱은 학생의 전체 이름만 전달
앱에서 given_name을 생성하지 않음
성 제거, 부분 이름, 조사, 호칭 처리는 AI Engine Name Matcher 담당
STT에서 학생 이름을 찾거나 학생별 문장을 앱에서 분리하지 않음
```

기존 호환성을 위해 당분간 다음을 병행할 수 있습니다.

```text
student_refs
+
students[{ref,name}]
```

두 필드의 장기 통합 여부는 별도 검토합니다.

# 5. 단계별 목표 책임

## A. App Input and Context

확인할 내용:

```text
교사 음성 입력 위치
Whisper 호출 위치
STT 원문 보유 위치
organization_ref 보유 여부
class_ref 보유 여부
lesson_ref 또는 lesson_date 보유 여부
선택 학생의 ref와 name 보유 여부
오늘 수업 커리큘럼 보유 여부
학생별 현재 진도 보유 여부
학생별 완료 이력 보유 여부
```

각 데이터가 앱에 있는지, 앱 API Server에 있는지, Production AI Engine에서 조회 가능한지 구분하십시오.

## B. State Parser

초기 상태는 COMMON입니다.

```text
학생 이름 등장 전
→ COMMON

학생 이름 등장
→ 해당 학생으로 전환

다른 학생 이름 등장
→ 대상 학생 변경

“전체” 등장
→ COMMON으로 복귀

같은 학생 재등장
→ 기존 학생 segments에 추가
```

## C. Name Matcher

```text
전체 이름
이름만 발화
조사 포함 이름
호칭 포함 이름
공백 이름
외국 이름
동명이인
미등록 이름
```

을 처리합니다.

모호한 이름은 임의 선택하지 않습니다.

## D. Observation

선생님이 실제로 말한 사실만 보존합니다.

Observation 단계에서 수영 지식, 원인, 교정법, 드릴을 추가하지 않습니다.

## E. Curriculum Resolver

다음을 확인합니다.

```text
해당 수영장의 커리큘럼
반의 오늘 공통 수업 과정
학생별 현재 진행 과정
학생별 완료 이력
최근 수업 과정
선생님이 직접 지정한 오늘 과정
```

추천 우선순위:

```text
선생님이 확인한 오늘 과정
> 오늘 수업에 연결된 과정
> 학생의 현재 진행 과정
> 최근 수업 과정
> 완료 이력
```

완료 이력은 배경 Context이며, 오늘 일지의 중심 내용을 자동 결정하는 근거로 사용하지 않습니다.

## F. Curriculum Scope Guard

Template Search와 Knowledge Search의 검색 범위를 다음 안으로 제한합니다.

```text
오늘 수업 과정
+
학생의 현재 진도
```

현재 배우지 않는 기술이나 아직 배우지 않은 후속 진도를 임의로 가져오지 않습니다.

## G. Template Search

Template는 다음 역할을 담당합니다.

```text
수영장이 승인한 일지 표현
SWIMNOTE가 승인한 문장 구조
교육 내용을 학부모에게 설명하는 형식
```

Template는 Knowledge와 동일한 데이터가 아닙니다.

## H. Knowledge Search

Knowledge는 다음 역할을 담당합니다.

```text
커리큘럼 목적
기술의 교육적 의미
관찰 내용과 직접 연결되는 설명
```

Knowledge Search는 Curriculum Scope Guard가 허용한 범위 안에서만 수행합니다.

## I. Diary Slot Builder

GPT에게 원문과 검색 결과를 무정형으로 전달하지 않고, 일지에 필요한 재료를 구조화합니다.

예:

```json
{
  "student_ref": "student_xxx",
  "lesson_topic": "자유형 호흡",
  "curriculum_context": "팔 동작과 호흡 연결 단계",
  "observations": [
    "호흡 시작이 늦었습니다."
  ],
  "teaching_focus": [
    "동작 순서와 호흡 타이밍을 안정적으로 연결"
  ],
  "observed_progress": [],
  "next_focus": []
}
```

근거가 없는 필드는 빈 배열 또는 빈 문자열로 유지합니다.

## J. GPT

GPT의 역할:

```text
구조화된 재료를 학부모용 문장으로 연결
공통 일지 생성
학생별 일지 생성
정해진 JSON Schema 반환
```

GPT의 금지 역할:

```text
학생 이름 식별
학생별 대상 분리
커리큘럼 선택
Template 검색
Knowledge 검색
관찰하지 않은 사실 생성
원인 추측
실행하지 않은 교정이나 드릴 생성
향상 여부 추측
```

가능하면 요청당 GPT 호출은 1회로 유지합니다.

## K. Output Validator

```text
JSON Schema
허용된 student_ref
중복 student_ref
누락 학생
학생 간 내용 혼재
Common 자동 복사
null과 잘못된 타입
추가 필드
문자열 길이
```

를 검증합니다.

## L. Teacher Review UX

목표 UX:

```text
반과 학생 자동 표시
↓
오늘 커리큘럼 자동 추천
↓
선생님 확인 또는 수정
↓
음성 또는 텍스트 입력
↓
AI 일지 만들기
↓
공통 일지 검토
↓
학생별 일지 검토
↓
수정 또는 다시 생성
↓
기존 일지 입력란에 적용
↓
저장
```

AI 결과는 자동 저장하지 않습니다.

# 7. 겹치는 책임 보고

# 9. Contract 경계 제안

다음 Contract를 각각 제안하십시오.

```text
App → AI Engine Request
AI Engine 내부 Parser Output
Curriculum Resolver Output
Template Search Output
Knowledge Search Output
Diary Slot Builder Output
GPT Structured Output
AI Engine → App Response
App Draft → Existing Diary Save
```

각 Contract에 대해 다음을 작성하십시오.

```text
필드
타입
필수 여부
Source of Truth
생성 책임
검증 책임
누락 처리
호환 방식
```

자신의 Repository 외부에 해당하는 Contract도 필요한 필드 수준까지 제안할 수 있지만, 상대 시스템의 실제 구현을 추측해서는 안 됩니다.

검토할 UX:

```text
오늘 커리큘럼 자동 추천
선생님의 커리큘럼 확인
커리큘럼 수동 변경
AI 생성 시작
처리 상태
공통 Draft
학생별 Draft
개별 수정
전체 다시 생성
특정 학생만 다시 생성
기존 입력과 AI 결과 충돌 처리
일지 입력란에 적용
저장
AI 실패 후 수동 작성 유지
```

각 UX 항목에 대해 다음을 구분하십시오.

```text
앱 UI 책임

양쪽 Contract 필요
```

# 11. 권장 일지 생성 규칙

공통 일지와 학생별 일지는 일반적으로 각각 2~4문장을 목표로 합니다.

단, 문장 수를 맞추기 위해 근거 없는 내용을 생성하지 않습니다.

사용 가능한 내용:

```text
실제 Observation
현재 커리큘럼의 명칭
현재 커리큘럼의 교육 목적
오늘 수업과 직접 관련된 Knowledge
승인된 Template 표현
```

사용 불가능한 내용:

```text
관찰하지 않은 학생 상태
확인되지 않은 원인
실제로 하지 않은 연습
실제로 하지 않은 교정
근거 없는 향상
근거 없는 다음 계획
```
