증상:

1.
선생님 모드
학생정보 → 모자레벨 → 변경

현재:
실패 모달 발생

2.
예전에 수정했던
“선생님이 학생 모자레벨을 변경하면
학부모 화면에도 즉시 새 모자레벨이 표시되는 동작”
이 깨진 것으로 보임.

이번 작업은
조사 → root cause 확정 → 최소 수정 → 회귀 테스트
까지 한 번에 진행한다.

Render deploy / OTA publish는 마지막에 하지 말고 STOP.

1. 현재 레벨 변경 전체 흐름 추적
━━━━━━━━━━━━━━━━━━━━

Teacher 학생정보 화면에서
모자레벨 변경 버튼부터 시작해서 실제 저장까지 끝까지 추적.

확인:

APP UI
→ level picker/modal
→ mutation 함수
→ API endpoint
→ server route
→ DB update
→ response
→ local cache/state invalidation
→ teacher UI refresh
→ parent UI refresh

실제 파일명/함수명 기준으로 추적할 것.

추측 금지.

2. 실패 모달 원인 확정
━━━━━━━━━━━━━━━━━━━━

실패 모달이 뜨는 실제 원인을 확인.

반드시 확인:

- 어떤 API 호출이 실패하는지
- HTTP status
- server error code
- response body
- request payload
- student_id
- pool_id
- selected level id
- auth/role validation
- tenant scope validation
- level belongs-to-pool validation
- DB constraint
- deprecated field/API 사용 여부
- 2.0.0에서 contract가 바뀌었는지

가능하면 실제 reproduce해서 로그 확보.

개인정보/secret 출력 금지.

━━━━━━━━━━━━━━━━━━━━
3. 수영장별 레벨 기준 확인
━━━━━━━━━━━━━━━━━━━━

SWIMNOTE 글로벌 색상 상수로 처리하면 안 됨.

관리자가 pool별로 설정한 level list가 source of truth인지 확인.

확인:

- level id
- display name
- color
- order/index
- active status

Teacher가 선택한 level이
해당 student.pool_id의 level인지 반드시 검증.

━━━━━━━━━━━━━━━━━━━━
4. 기존 “학부모 즉시 반영” 구현 추적
━━━━━━━━━━━━━━━━━━━━

git history / 기존 코드에서
예전에 수정된 동작을 찾는다.

목표:

Teacher가 student.current_level을 변경하면
Parent 화면에서도 앱 재설치/재로그인 없이
새 레벨이 정상 표시되어야 함.

확인:

- parent student profile/home이 어느 endpoint를 읽는지
- teacher 변경 endpoint와 같은 source field를 갱신하는지
- query cache key
- invalidation/refetch
- staleTime
- navigation focus refetch
- optimistic update 여부
- websocket/realtime event 여부
- parent home/profile 각각 다른 cache를 쓰는지

“예전에 됐었다”는 전제로
현재 회귀 지점을 git history까지 확인할 것.

━━━━━━━━━━━━━━━━━━━━
5. source of truth 확인
━━━━━━━━━━━━━━━━━━━━

반드시 하나의 canonical student level source를 확인.

예:
students.current_level_id
또는 실제 현재 schema의 equivalent

Teacher 화면과 Parent 화면이
서로 다른 legacy field를 읽고 있으면
그게 root cause인지 확인.

중복 필드 동기화 방식으로 땜질하지 말고
canonical field 기준으로 정리.

단:
대규모 migration은 금지.
현재 구조에서 최소 수정.

━━━━━━━━━━━━━━━━━━━━
6. 수정 원칙
━━━━━━━━━━━━━━━━━━━━

우선순위:

A.
Teacher level update 실패 원인 수정

B.
저장 성공 시 Teacher 화면 즉시 새 level 반영

C.
Parent가 다음 조회/focus/refetch 시
동일 canonical level을 즉시 읽음

D.
가능하면 기존 cache invalidation/realtime 구조 재사용

새로운 별도 상태 시스템 만들지 말 것.
