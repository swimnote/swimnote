1. 먼저 API CACHE를 최우선 확인
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 SWIMNOTE apiRequest에 GET cache가 존재해 온 이력이 있다.

기존 구조에서:

cache key = token + "::" + path
TTL ≈ 30초

가 존재했다.

따라서 반드시 현재 실제 apiRequest 구현을 확인한다.

특히 아래 GET이 cache 대상인지 확인:

GET /parent-requests/:requestId/messages

그리고 현재 2초 polling에서:

fetchMessages()
→ apiRequest()
→ 실제 network fetch

인지,

fetchMessages()
→ apiRequest()
→ 30초 cached Response

인지 확정한다.

현재 증상:

상대 메시지 도착
→ polling에서는 안 나타남
→ 내가 POST
→ POST 후 fetchMessages
→ 상대 메시지까지 같이 나타남

은 POST가 관련 GET cache를 bust하거나
POST 직후 fresh fetch가 발생하는 경우와 일치할 수 있다.

반드시 실제 cache code로 CONFIRMED/REJECTED 판정한다.

추측만 하고 다른 구조를 추가하지 말 것.

2. 업무대화 GET은 stale cache 금지
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

업무대화는 실시간성 데이터다.

GET:

/parent-requests/:requestId/messages

는 30초 stale cache를 사용하면 안 된다.

최종 요구:

Modal visible
→ 2초 polling
→ 실제 최신 server response

가 되어야 한다.

단 전역 apiRequest cache를 제거하지 않는다.

다른 화면 전체 cache 정책 수정 금지.

해결은 최소 범위로 한다.

우선순위:

A. apiRequest가 endpoint-specific no-cache/bypass option을 이미 지원하면 사용

또는

B. messages endpoint에 대해서만 cache 제외

또는

C. fetchMessages에서 현재 프로젝트 convention에 맞는
network-only 호출 사용

가장 단순한 기존 구조를 선택.

절대:

clearApiCache()를 2초마다 전역 호출

하는 식으로 해결하지 않는다.
