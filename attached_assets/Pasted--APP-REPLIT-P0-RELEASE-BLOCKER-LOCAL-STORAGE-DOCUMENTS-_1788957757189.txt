[보낼 곳: APP REPLIT]

[P0 RELEASE BLOCKER — LOCAL STORAGE / DOCUMENTS & DATA LEAK AUDIT + FIX]

실제 iPhone에서 확인된 심각한 문제:

SWIMNOTE 1.6.3
- 앱 크기: 약 65.4MB
- 문서 및 데이터: 26.75GB

SWIMNOTE 2.1.0
- 앱 크기: 약 65.6MB
- 문서 및 데이터: 897.9MB

앱 바이너리 크기는 정상.
문제는 "문서 및 데이터"의 비정상 누적.

사용자 정책:
SWIMNOTE는 사진/영상/캐시 때문에
사용자 iPhone 저장공간을 계속 잠식하면 안 된다.

목표:

1. 로컬 저장소가 어디에서 증가하는지 전수 추적
2. 사진/영상 업로드 후 임시파일 자동 삭제
3. 압축/리사이즈 결과물 자동 삭제
4. 영구보관이 불필요한 파일은 documents가 아니라 cache 사용
5. 앱이 장기 사용돼도 로컬 데이터가 무한 증가하지 않게 함
6. 기존 사용자에게 이미 쌓인 불필요 파일도 안전하게 정리할 수 있게 함

광범위한 앱 기능 수정 금지.
서버/R2 구조 변경 금지.
사진/영상 원본 서버 데이터 삭제 금지.

3. 영상 업로드
━━━━━━━━━━━━━━━━━━━━━━

영상은 특히 P0.

확인:

picker/camera
→ local temp copy
→ compression/transcode 여부
→ upload
→ R2

완료 후
앱이 생성한 temp video 삭제.

수백 MB~수 GB 파일이
documentDirectory에 남으면 FAIL.

업로드 실패 시에도
retry에 필요한 최소시간 외에는
고아 temp가 영구 누적되면 안 됨.

4. DOCUMENT DIRECTORY 사용 정책
━━━━━━━━━━━━━━━━━━━━━━

원칙:

documentDirectory
= 사용자가 명시적으로 앱 안에서 계속 보존해야 하는 데이터만.

cacheDirectory
= 다시 생성/download 가능한 데이터.

다시 서버에서 받을 수 있는:

- thumbnail
- image preview
- downloaded image
- temp upload copy
- compressed image
- video temp
- PDF preview
- generated temporary file

는 가능하면 cacheDirectory 사용.

기존에 documents에 저장 중이면
필요성 판단 후 cache로 이동.

━━━━━━━━━━━━━━━━━━━━━━
5. UPLOAD SUCCESS CLEANUP
━━━━━━━━━━━━━━━━━━━━━━

모든 media upload에서 공통 cleanup 보장.

try/finally 형태 권장:

temp files 생성
→ upload
→ finally
→ 앱 생성 temp file delete

단:
실패 후 사용자가 즉시 retry해야 하는 구조라면
필요한 file lifecycle을 정확히 설계.

무조건 삭제해서 retry 기능 파손 금지.

공통 helper가 가능하면 최소 범위로 재사용.

예:
cleanupLocalTempFiles(paths)

━━━━━━━━━━━━━━━━━━━━━━
6. CACHE LIMIT
━━━━━━━━━━━━━━━━━━━━━━

cache가 무한 증가하면 안 됨.

앱 시작 또는 적절한 시점에:

- 오래된 temp/cache 파일
- upload 임시파일
- preview
- generated temp

를 정리.

권장:
- age 기준
- prefix 기준
- 앱이 생성한 directory만

절대 사용자/필수 앱 데이터 전체 delete 금지.

예:

swimnote-temp/
swimnote-upload/
swimnote-cache/

같은 전용 directory가 있다면 그 안만 관리.

없으면 기존 path 분석 후 안전한 범위 설정.

7. 기존 1.x 사용자 누적 데이터
━━━━━━━━━━━━━━━━━━━━━━

중요.

1.6.3 사용자의 Documents & Data가
26GB까지 증가한 실제 사례가 있음.

2.x 업데이트 후에도
iOS app sandbox가 유지되면
기존 파일이 그대로 남을 수 있음.

따라서 legacy temp/cache 경로를 확인.

안전하게 식별 가능한
legacy SWIMNOTE 임시파일만
1회 cleanup migration 가능하게 구현.

금지:

- AsyncStorage 전체 삭제
- SQLite/DB 삭제
- 로그인 정보 삭제
- user settings 삭제
- 다운로드 보존 정책상 필요한 파일 삭제
- Photos library 접근/삭제

오직 명백한 old temp/media cache.

9. STORAGE BUDGET
━━━━━━━━━━━━━━━━━━━━━━

목표:

일반 사용 상태에서
로컬 Documents & Data가
사진/영상 사용량에 비례해 무한 증가하지 않음.

기본 정책:

- temp upload: 업로드 후 제거
- thumbnails/previews: cache
- generated PDF/temp: 사용 후 제거 또는 cache

정확한 하드 cap을 임의로 정하지 말고,
무한 누적이 없는 구조를 목표로.
