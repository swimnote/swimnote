[P0 HOTFIX — SUSPICIOUS_DUPLICATE_STUDENT_NOTES 정상 일지 저장 차단 수정]

목표:
Teacher Diary 저장 시
정상적인 공통 수업내용/짧은 메모 때문에
`SUSPICIOUS_DUPLICATE_STUDENT_NOTES`
가 발생하여 저장이 막히는 문제를 최소 수정한다.

중요:
- 중복 방지 안전장치 전체 제거 금지
- AI provenance/safety 구조 훼손 금지
- 광범위 refactor 금지
- 이번 오류만 최소 수정
- 출시 직전 hotfix로 처리

━━━━━━━━━━━━━━━━━━━━━━
1. ROOT CAUSE TRACE
━━━━━━━━━━━━━━━━━━━━━━

먼저 정확히 찾을 것:

- `SUSPICIOUS_DUPLICATE_STUDENT_NOTES` 발생 위치
- 어떤 payload/notes 비교 조건에서 throw 되는지
- COMMON 내용 복제인지
- student-specific note 비교인지
- 짧은 입력(".", 한 글자, 공백 유사값)이 duplicate로 판정되는지
- AI 생성 결과가 동일한 경우인지
- 저장 직전 normalized text 비교인지

로그/코드 기준으로 원인 확정 후 수정.

추측 수정 금지.

━━━━━━━━━━━━━━━━━━━━━━
2. 정책
━━━━━━━━━━━━━━━━━━━━━━

허용해야 하는 정상 케이스:

A.
동일한 수업에서 여러 학생에게
공통 수업내용이 동일하게 들어가는 경우

B.
COMMON 내용이 각 학생 일지에 반복되는 경우

C.
학생별 개별 메모가 비어 있거나 매우 짧은 경우

예:
"."
"-"
공백
짧은 한두 글자 메모

D.
같은 반 학생들이 실제로 동일한 기술/드릴을 수행하여
일지 일부 또는 전체 문장이 우연히 같은 경우

이런 경우 저장을 막으면 안 됨.

━━━━━━━━━━━━━━━━━━━━━━
3. 계속 막아야 하는 비정상 케이스
━━━━━━━━━━━━━━━━━━━━━━

안전장치는 유지.

다음과 같은 경우만 suspicious duplicate 후보:

- 서로 다른 학생 ID인데
- student-specific 원문/AI output이
- 충분한 길이를 가진 상태에서
- 동일 request 내 비정상적으로 완전 동일하고
- COMMON/shared content로 설명되지 않으며
- parser routing 또는 학생 귀속 오류 정황이 있는 경우

즉:
"같은 문장" 자체가 금지 조건이면 안 됨.

중복 탐지는
콘텐츠 유사도 검사보다
학생 귀속 무결성 검사에 가깝게 좁힐 것.

━━━━━━━━━━━━━━━━━━━━━━
4. SHORT / EMPTY NOTE RULE
━━━━━━━━━━━━━━━━━━━━━━

normalized student note가 아래면
duplicate guard 대상에서 제외:

- empty
- whitespace only
- punctuation only
- 의미 없는 placeholder
- 매우 짧아 uniqueness 판단이 불가능한 값

정확한 최소 길이 기준은
현재 데이터/로직을 보고 보수적으로 정할 것.

단순히 임의로 20자/30자 같은 값부터 박지 말고
현재 guard 구조에 맞게 최소 수정.

━━━━━━━━━━━━━━━━━━━━━━
5. COMMON 처리
━━━━━━━━━━━━━━━━━━━━━━

Teacher Diary parser 계약:

COMMON
→ 이름 호출 시 학생 전환
→ "전체"로 COMMON 복귀

COMMON에서 나온 내용이
여러 학생 final note에 포함되는 것은 정상.

따라서 duplicate comparison 시
가능하면:

final rendered note 전체끼리 비교하지 말고

- student-specific segment
또는
- provenance/routing metadata

를 기준으로 판정.

공통 부분 때문에 duplicate 판정되면 FAIL.

8. ERROR UX
━━━━━━━━━━━━━━━━━━━━━━

정상 사용 중 이 내부 코드가
사용자 화면에 그대로 노출되지 않도록 확인.

`SUSPICIOUS_DUPLICATE_STUDENT_NOTES`

같은 내부 에러 코드를
선생님에게 raw string으로 직접 보여주지 말 것.

만약 실제 safety anomaly가 발생하면
사용자 메시지는 자연스럽게:

"일지 저장 중 학생별 내용 확인이 필요합니다.
내용을 확인한 뒤 다시 저장해주세요."

정도로 처리.

내부 로그에는 원래 error code 유지 가능.
