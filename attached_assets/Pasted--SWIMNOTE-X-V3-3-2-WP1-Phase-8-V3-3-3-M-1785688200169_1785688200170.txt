1. diary_templates.scope에 x_global 허용 처리 누락
━━━━━━━━━━━━━━━━━━━━━━

현재 Repository의 diary_templates.scope에는 기존 값이 존재한다.

- global
- teacher

V3.3.2에서는 신규 값 x_global을 사용하지만,
Migration에는 scope 타입 또는 CHECK 제약을 확장하는 작업이 없다.

실제 scope 구현 방식을 확인하여 반드시 다음 중 맞는 방식으로 수정한다.

A. PostgreSQL ENUM이면:
ALTER TYPE ... ADD VALUE IF NOT EXISTS 'x_global';

B. CHECK 제약이면:
기존 CHECK 제거 후
scope IN ('global','teacher','x_global')로 재생성

C. 단순 TEXT이고 제약이 없으면:
별도 변경 없이 사용 가능하다는 것을 Repository 기준으로 명시

확인 없이 x_global 값을 INSERT하면 안 된다.

또한 DB 정합성 제약을 추가한다.

- scope='x_global'
  → swimming_pool_id IS NULL
  → global_template_set_id IS NOT NULL

- scope IN ('global','teacher')
  → swimming_pool_id IS NOT NULL
  → global_template_set_id IS NULL

ADD CONSTRAINT IF NOT EXISTS 문법은 사용하지 말고
DO $$ + pg_constraint 조회 패턴을 사용한다.

━━━━━━━━━━━━━━━━━━━━━━
2. global_template_set_id Foreign Key 누락
━━━━━━━━━━━━━━━━━━━━━━

M-E에서는 global_template_set_id 컬럼만 추가하고
실제 Foreign Key를 추가하지 않았다.

다음 FK를 추가한다.

diary_templates.global_template_set_id
→ global_template_sets.id
ON DELETE RESTRICT

DO $$ 블록에서 pg_constraint를 확인한 후 추가한다.

global_template_sets.version_name도 중복 방지를 위해 UNIQUE 처리한다.

CREATE UNIQUE INDEX IF NOT EXISTS
uniq_global_template_sets_version_name
ON global_template_sets(version_name);

3. Global Template 롤백 정책 충돌
━━━━━━━━━━━━━━━━━━━━━━

기존 정책에서는 ARCHIVED 세트를 다시 ACTIVE로 전환하여
이전 세트로 롤백할 수 있도록 했다.

하지만 현재 activateGlobalTemplateSet() 코드는:

if (target.status === 'ARCHIVED')
  throw CANNOT_ACTIVATE_ARCHIVED

로 되어 있어 롤백이 불가능하다.

정책을 다음으로 확정한다.

- DRAFT → ACTIVE 가능
- ARCHIVED → ACTIVE 가능
- ACTIVE → 재활성화 요청은 ALREADY_ACTIVE
- 새 세트 활성화 시 기존 ACTIVE는 ARCHIVED
- 이전 ARCHIVED 세트를 활성화하는 것이 롤백 방식

따라서 CANNOT_ACTIVATE_ARCHIVED 조건을 제거한다.

대상 status는 다음만 허용한다.

status IN ('DRAFT','ARCHIVED')

5. match_token의 상태·설정 버전 변조 방지
━━━━━━━━━━━━━━━━━━━━━━

현재 match_token에는 confidence만 포함되고
다음 값은 포함되지 않는다.

- confidence_config_version
- matching_algorithm_version
- growth_match_status

응답의 growth_match_status를 앱이 변경해 보낼 수 있으므로
서버는 앱이 전달한 상태를 신뢰하면 안 된다.

MatchTokenV2Payload에 추가한다.

- confidence_config_version
- matching_algorithm_version

growth_match_status는 토큰 생성 시 confidence와 설정값을 기준으로
서버가 계산하고, 저장 시 다시 서버가 산출한다.

앱이 보낸 growth_match_status는 표시용일 뿐이며
DB 저장 상태의 근거로 사용하지 않는다.

저장 시:

signed confidence
+ signed confidence_config_version
+ 서버 설정 조회

를 기준으로 다음 중 하나를 서버가 결정한다.

- AUTO_ACCEPTED
- PENDING_REVIEW
- DISCARDED

설정 버전이 더 이상 존재하지 않으면:
MATCH_CONFIG_NOT_FOUND
오류 또는 안전한 PENDING_REVIEW 처리 정책을 명시한다.

6. match_token 멱등 처리 계약 보완
━━━━━━━━━━━━━━━━━━━━━━

match_token_id UNIQUE만으로 재사용은 차단할 수 있지만,
다음 두 상황을 구분하는 로직이 필요하다.

A. 동일 token + 동일 diary_note 재시도
→ 기존 성공 결과 반환
→ 200 멱등 처리

B. 동일 token + 다른 diary_note
→ 409 MATCH_TOKEN_ALREADY_USED

INSERT ... ON CONFLICT DO NOTHING만으로는
A와 B를 구분할 수 없다.

충돌 시 기존 growth_event를 조회하여:

existing.diary_note_id === current.diary_note_id
→ 기존 event 반환

다르면:
→ 409

처리한다.

추가 고유 제약도 유지한다.

UNIQUE 또는 Partial Unique:

(diary_note_id, student_id, curriculum_item_id, source)

현재 M-I에는 source 컬럼도 빠졌으므로 추가한다.

source TEXT NOT NULL DEFAULT 'teacher_ai'
CHECK (
  source IN ('teacher_ai','teacher_manual','parent_ai','video_ai')
)

7. Parent AI reservation의 요청별 멱등성과 장애 복구
━━━━━━━━━━━━━━━━━━━━━━

현재 parent_ai_daily_usage는 집계값만 저장하므로
서버가 reservation 후 비정상 종료되면 reserved_count가 계속 남는다.

또한 동일 request_id가 재시도될 때
예약이 중복 증가할 수 있다.

다음 신규 테이블 또는 동등 구조가 필요하다.

parent_ai_usage_reservations

- request_id TEXT PRIMARY KEY
- parent_account_id
- usage_date
- status:
  RESERVED | COMPLETED | FAILED | BLOCKED | EXPIRED
- reserved_at
- completed_at
- expires_at
- prompt_tokens
- completion_tokens
- estimated_cost_krw
- error_code

처리 규칙:

1. request_id로 reservation INSERT
2. 동일 request_id 재요청이면 기존 상태 반환
3. RESERVED 상태만 parent_ai_daily_usage.reserved_count에 포함
4. 성공:
   RESERVED → COMPLETED
   reserved_count -1
   completed_count +1

5. 실패:
   RESERVED → FAILED
   reserved_count -1
   failed_count +1

6. Intent 차단:
   RESERVED → BLOCKED
   reserved_count -1
   intent_blocked_count +1

7. 일정 시간 이상 남은 RESERVED:
   Worker가 EXPIRED 처리
   reserved_count 복구

reservation 상태 변경과 daily_usage 집계 변경은
같은 DB Transaction에서 처리한다.

집계 숫자만으로 요청 생명주기를 관리하면 안 된다.

8. audit_logs system actor와 스키마 정합성
━━━━━━━━━━━━━━━━━━━━━━

현재 audit_logs.actor_id는 NOT NULL이다.

그러나 actor_type='system'인 자동 변경에서는
actor_id가 없을 수 있다.

수정:

actor_id TEXT NULL 허용

정합성 CHECK:

CHECK (
  (actor_type = 'system' AND actor_id IS NULL)
  OR
  (actor_type <> 'system' AND actor_id IS NOT NULL)
)

actor_type 허용값도 실제 TypeScript와 맞춘다.

- super_admin
- pool_admin
- teacher
- parent
- system

실제 단일 entity_version만으로는 복합 PK에 대한 FK가 아니다.

정확한 표현:

audit_logs의
(entity_type, entity_id, entity_version)는
audit_entity_versions에서 원자적으로 발급받은 감사 버전이다.

실제 FK는 두지 않는다.
audit_entity_versions는 현재 카운터이고,
audit_logs는 이력 스냅샷이다.
