[P0 — AUTH IDENTITY INTEGRITY / GLOBAL LOGIN ID UNIQUE]

실제 테스트 중 로그인 계정이 섞일 수 있는 버그 발견.

문제:
현재 login_id / username 계열 값에 전역 중복 제약이 없거나,
로그인 조회가 중복 row 중 하나를 선택할 가능성이 있음.

결과:
같은 아이디가 여러 pool/account에 존재하면
로그인 후 다른 수영장/다른 사용자 context로 연결될 위험.

목표:
SWIMNOTE 로그인 아이디는 전체 시스템에서 전역 UNIQUE로 고정.

1. 현재 로그인 식별자 정확히 파악
━━━━━━━━━━━━━━━━━━━━━━

실제 코드/DB에서 로그인에 사용하는 필드 확인:

- username
- login_id
- email
- phone
- user_id
- 기타

회원가입/로그인/초대/관리자 생성 경로 전체에서
어떤 필드가 실제 credential identifier인지 확정.

추정 금지.

━━━━━━━━━━━━━━━━━━━━━━
2. Production 중복 데이터 조사
━━━━━━━━━━━━━━━━━━━━━━

Production DB에서 로그인 식별자 기준:

GROUP BY normalized_login_id
HAVING COUNT(*) > 1

전수 조사.

제출:
- 중복 login_id
- user_id
- pool_id
- role
- created_at
- active 여부

PII는 완료보고에서 마스킹.

절대 먼저 UNIQUE constraint 추가하지 말 것.
기존 중복 row가 있으면 migration 실패하거나
운영 계정을 깨뜨릴 수 있음.

━━━━━━━━━━━━━━━━━━━━━━
3. NORMALIZATION 정책
━━━━━━━━━━━━━━━━━━━━━━

아이디 비교는 canonical normalize 후 수행.

최소:
- trim
- lowercase (영문 대소문자 구분 안 할 경우)

예:
TestUser
testuser
 testuser

를 동일 아이디로 취급할지
현재 제품정책 기준으로 확정.

로그인/회원가입/중복검사/DB constraint가
같은 normalization 규칙을 사용해야 함.

━━━━━━━━━━━━━━━━━━━━━━
4. DB GLOBAL UNIQUE
━━━━━━━━━━━━━━━━━━━━━━

중복 데이터 정리 후
로그인 식별자에 DB-level global UNIQUE 적용.

중요:
(pool_id, login_id) UNIQUE 금지.

원하는 정책:
전체 SWIMNOTE에서 login_id 하나 = 사용자 한 명.

예:
UNIQUE(normalized_login_id)

DB 자체가 마지막 방어선이 되어야 함.

━━━━━━━━━━━━━━━━━━━━━━
5. 회원가입 중복검사
━━━━━━━━━━━━━━━━━━━━━━

회원가입 화면에 아이디 입력 시:

- debounce 가능
- 서버 API로 사용 가능 여부 확인
- 사용 가능
- 이미 사용 중

표시.

단 프론트 확인 결과만 믿지 말 것.

최종 POST register 시 서버에서 다시 검사.

중복이면:
409 LOGIN_ID_ALREADY_EXISTS

명확한 사용자 메시지:
"이미 사용 중인 아이디입니다."

6. 모든 계정 생성 경로 동일 적용
━━━━━━━━━━━━━━━━━━━━━━

다음 경로 전부 확인:

- 관리자 회원가입
- 선생님 계정 생성
- 초대코드 가입
- 학부모 계정 생성
- Super Admin 계정 생성/수정
- 테스트 계정 생성
- legacy import
- bulk register에서 로그인 계정 생성 여부

어떤 경로에서도 중복 login_id 생성 불가.

━━━━━━━━━━━━━━━━━━━━━━
7. LOGIN QUERY 안전화
━━━━━━━━━━━━━━━━━━━━━━

로그인 서버 조회가:

SELECT ... WHERE login_id = ?
LIMIT 1

형태로 중복 가능성을 숨기면 안 됨.

UNIQUE 적용 후 정확히 0 or 1 row.

기존 중복이 남아있는 migration 전 기간에는:
count > 1이면 로그인 실패시키고
AUTH_IDENTITY_CONFLICT 로그 남길 것.

임의 첫 row 선택 금지.

━━━━━━━━━━━━━━━━━━━━━━
8. USER ↔ POOL 연결
━━━━━━━━━━━━━━━━━━━━━━

로그인 성공 후 pool은 login_id로 다시 찾지 말고:

authenticated user_id
→ memberships
→ authorized pool

순서로 결정.

검증:
- user_id가 다른 pool user로 바뀌지 않음
- membership이 여러 개면 명시적 pool selection 또는 canonical current_pool 사용
- login_id만으로 pool_id 결정 금지

━━━━━━━━━━━━━━━━━━━━━━

━━━━━━━━━━━━━━━━━━━━━━

자동 삭제/자동 merge 금지.

필요하면 한쪽 login_id를 변경.

정정 전 영향 목록 제출.
