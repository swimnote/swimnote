# 관리자 권한 부여·회수 수정 계획 보완 요청

현재 제출한 계획서는 일부 승인할 수 있지만,
권한 회수 즉시 반영 문제를 “수정 불필요”로 판단한 부분은 승인할 수 없습니다.

이번 기능의 핵심은 단순히 roles 배열을 수정하는 것이 아니라,

관리자가 권한을 회수하면
해당 교사가 더 이상 관리자 기능을 사용할 수 없어야 한다는 것입니다.

현재 조사 결과에 따르면:

- requireAuth는 JWT 서명과 token version만 확인
- requireRole("pool_admin")은 JWT의 role만 확인
- 관리자 API 요청 시 DB의 최신 roles를 확인하지 않음
- 회수 전 발급된 pool_admin JWT는 최대 30일간 유효
- 앱을 재시작하지 않으면 관리자 API를 계속 호출할 수 있음

이 상태에서 “앱 재시작 시 교정되므로 수정 불필요”라고 판단하면 안 됩니다.

권한 회수는 사용자가 앱을 재시작하는지 여부와 관계없이
서버에서 즉시 효력이 발생해야 합니다.

현재 계획을 실행하지 말고 아래 내용을 반영한 최종 수정 계획서를 다시 제출하세요.

==================================================
1. 반드시 수정해야 하는 항목
==================================================

다음 4개 항목을 모두 수정 대상에 포함하세요.

1. 취소 버튼 UI 개선
2. handleGrant / handleRevoke 오류 처리
3. 교사 목록 조회를 users.role이 아닌 교사 소속과 roles 기준으로 변경
4. 관리자 권한 회수 즉시 반영

4번은 선택 사항이 아닙니다.

==================================================
2. 권한 회수 즉시 반영 조건
==================================================

관리자가 교사의 pool_admin 권한을 회수한 직후부터
다음이 보장되어야 합니다.

- 기존 pool_admin JWT를 가지고 있어도 관리자 API 접근 차단
- 관리자 화면에서 다음 API 요청 시 403 또는 ROLE_REVOKED 반환
- 앱은 해당 응답을 받으면 관리자 모드를 종료
- 선생님 모드로 전환
- 관리자 메뉴 제거
- 선생님 권한과 수업 데이터는 유지
- 다시 로그인해도 관리자 모드가 나타나지 않음

앱 재시작을 조건으로 삼지 마세요.

==================================================
3. 서버 권한 검증 방식
==================================================

현재 프로젝트에서 변경 범위가 가장 작은 방법을 적용하세요.

권장 방식:

pool_admin 전용 API에
DB의 최신 users.roles를 확인하는 미들웨어를 추가합니다.

예:

requireAuth
→ requireRole("pool_admin")
→ requireDbRoleCheck("pool_admin")
→ 실제 라우트 실행

requireDbRoleCheck는 다음을 확인해야 합니다.

1. JWT userId로 users 조회
2. users.roles에 pool_admin이 현재 존재하는지 확인
3. 해당 권한이 없으면 403 반환
4. 응답 코드 또는 body에 ROLE_REVOKED 포함

예:

{
  "success": false,
  "code": "ROLE_REVOKED",
  "message": "관리자 권한이 회수되었습니다."
}

단순히 switch-role 엔드포인트에서만 DB 권한을 확인하면 부족합니다.

기존 관리자 JWT로 호출할 수 있는
모든 pool_admin 전용 API의 실제 진입점에서
최신 DB 권한을 검증해야 합니다.

==================================================

pool_admin 권한이 필요한 서버 라우트를 전부 조사하세요.

예:

- 수업 관리
- 선생님 관리
- 회원 관리
- 반 관리
- 일지 관리
- 출결 관리
- 결제 또는 정산
- 설정
- 관리자 권한 부여/회수

각 라우트가 현재 어떤 미들웨어를 사용하는지 보고하세요.

다음 중 어떤 방식으로 일괄 적용할지 계획에 포함하세요.

A. pool_admin router 상단에 공통 DB 권한 미들웨어 적용  
B. requireRole 내부에서 pool_admin일 때 DB roles 추가 확인  
C. 별도 requireCurrentRole 미들웨어 적용

중복 수정이 적고 누락 위험이 가장 낮은 방식을 선택하세요.

==================================================
5. 클라이언트 강제 복귀 처리
==================================================

앱의 apiRequest 또는 공통 응답 처리부에서

HTTP 403 + code === "ROLE_REVOKED"

를 감지하면 다음 순서로 처리하도록 계획하세요.

1. 저장된 pool_admin 토큰 폐기
2. 현재 사용자 권한 재조회
3. teacher 역할이 있으면 teacher 모드로 전환
4. 관리자 스택 제거
5. 선생님 홈으로 이동
6. 안내 메시지 표시

메시지:

"관리자 권한이 회수되어 선생님 모드로 전환되었습니다."

각 화면마다 따로 처리하지 말고
가능하면 공통 API 처리부에서 처리하세요.

==================================================
6. 권한 부여 후 즉시 사용
==================================================

권한 부여도 앱 재시작에 의존하지 않는 방향을 우선 검토하세요.

관리자 권한 부여 후 교사 앱에서:

- /auth/me
- 권한 목록 재조회
- 또는 앱 활성화 시 roles 재조회

를 통해 관리자 전환 메뉴가 나타나게 할 수 있는지 확인하세요.

현재 앱 구조상 어렵다면
재로그인 또는 앱 재시작이 필요한 이유를 정확히 설명하세요.

다만 권한 회수 즉시 차단은 반드시 서버에서 보장해야 합니다.

==================================================
7. handleGrant와 handleRevoke 분리 확인
==================================================

현재 계획서에는 handleGrant만 중심적으로 작성되어 있습니다.

실제 코드에서 부여와 회수가 동일 함수의 grant boolean으로 처리되는지,
별도 함수인지 확인하세요.

두 작업 모두 다음을 보장해야 합니다.

- try/catch/finally
- 실행 중 버튼 비활성화
- 중복 탭 방지
- 실제 HTTP 오류 표시
- 실패 시 로컬 상태 변경 금지
- 성공 후 서버 목록 재조회
- 성공 응답의 roles 상태 사용

==================================================
8. optimistic update 재검토
==================================================

현재 보고서에는 성공 후 optimistic update를 한 뒤
백그라운드 재조회한다고 되어 있습니다.

권한 기능은 서버 상태가 기준이어야 합니다.

권장 순서:

API 성공
→ 서버 응답의 최신 roles 확인
→ 목록 즉시 갱신
→ 전체 목록 재조회
→ 서버 결과로 최종 교체

API가 실패했는데 화면만 부여 또는 회수된 것처럼 보이면 안 됩니다.

==================================================
9. 목록 조회 조건
==================================================

다음 변경 방향은 승인합니다.

u.role = 'teacher'
→ u.roles @> ARRAY['teacher']

하지만 이것만으로 충분한지 확인하세요.

정상 목록 조건:

- 현재 센터의 승인된 teacher invite 또는 membership 존재
- roles에 teacher 포함
- pool_admin 권한 보유 여부와 관계없이 표시
- 현재 활성 role이 pool_admin이어도 표시
- 센터 소유자 제외
- 다른 센터 사용자 제외
- super_admin 제외

최종 SQL 조건을 계획서에 포함하세요.
