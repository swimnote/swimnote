# SWIMNOTE SUPPORT DIRECT ANSWER ARCHITECTURE

## PRE-IMPLEMENTATION REVIEW ONLY

### 중요

이번 작업에서는 **코드를 수정하지 마십시오.**

먼저 현재 SWIMNOTE Repository / Database / Support Pipeline을 실제로 조사하고,
아래 설계가 현재 구조에 어떻게 들어가야 가장 안전하고 단순한지 검토하십시오.

이번 단계의 목적은:

> 구현 전에 Architecture / Schema / Migration / Routing / Cost / Security / Existing Code Reuse 여부를 확정하는 것

입니다.

코딩은 검토보고 승인 이후 별도 WP에서 진행합니다.

# 1. 최종 목표

SWIMNOTE 고객지원은 최종적으로 다음 3단계로 동작해야 합니다.

```text
사용자 질문
        ↓
────────────────────────
1차 — DIRECT DB ANSWER
────────────────────────
예상질문 / Intent 검색
        ↓
확실한 정답 존재
        ↓
Canonical Answer DB에서 즉시 반환
        ↓
GPT 호출 없음
        ↓
사용자에게 답변
```

Direct DB로 해결되지 않으면:

```text
────────────────────────
2차 — GROUNDED GPT
────────────────────────
관련 SWIMNOTE Knowledge 검색
        ↓
검색된 근거만 GPT에 전달
        ↓
GPT가 자연어 답변 생성
        ↓
사용자에게 답변
```

그래도 해결하지 못하거나 사용자가 직접 상담을 원하면:

```text
────────────────────────
3차 — HUMAN SUPPORT
────────────────────────
사용자 "직접 문의하기"
        ↓
Support Case 생성/연결
        ↓
Super Admin에게 알림
        ↓
Super Admin이 문의 확인
        ↓
직접 답변
        ↓
기존 동일 상담 Conversation에 답변 표시
        ↓
사용자 Push/알림
```

핵심 원칙:

```text
DB → GPT → HUMAN
```

GPT가 1차 답변기가 아닙니다.

# 2. 왜 이 구조를 만드는가

현재 Support 시스템에는:

* Support Knowledge
* Grounding
* GPT 답변
* Human escalation
* Case
* Trace
* Approval Governance
* Super Admin Review

등의 기반이 이미 존재합니다.

하지만 단순한 질문까지 GPT를 사용하거나,
Knowledge가 없으면 Human escalation으로 바로 내려갈 수 있습니다.

앞으로는 다음처럼 구성합니다.

예:

사용자:

> X모드 가격 얼마야?

DB:

```text
INTENT = X_MODE_PRICE
```

정답이 존재하면:

```text
canonical_answer
→ 즉시 반환
```

GPT 호출:

```text
0
```

예:

```text

X.PRICE
```

```text
[공식 확정 가격]

source_type:
APPROVED_POLICY

source_ref:
[...]

roles:
[...]

modes:
[...]

answer_mode:
DIRECT_DB

risk:
HIGH

status:
ACTIVE
```

# 7. 중요한 구조 원칙

예상 질문마다 답변을 복제하지 않습니다.

잘못된 구조:

```text
X모드 얼마야 → 답변 A
X모드 가격 → 답변 A
X 가격 알려줘 → 답변 A
X 이용료 → 답변 A
X 구독료 → 답변 A
```

정답 문장이 다섯 번 저장되는 구조는 금지합니다.

올바른 구조:

```text
X_MODE_PRICE
    ↓
Canonical Answer 1개
```

그리고:

```text
X모드 얼마야
X모드 가격
X 가격 알려줘
X 이용료
X 구독료
```

모두:

```text
intent_id = X_MODE_PRICE
```

를 가리킵니다.

# 8. 예상 질문 DB

예상 질문은 상당히 많아질 예정입니다.

예:

```text
intent:
X_MODE_PRICE

utterances:

"x모드 가격 얼마야"
"x 얼마야"
"x모드 비용"
"스윔노트x 가격 알려줘"
"엑스모드 가격"
"x 구독료 얼마야"
"x 이용료"
"x모드 한 달 얼마야"
```

한 Intent당 대략:

```text
5~20 variants
```

초기 예상:

```text
Canonical Answers:
약 100~500개

Expected Questions:
약 1,000~10,000개
```

정확한 개수는 Function Inventory 이후 결정합니다.

# 9. 권장 DB 개념

새 DB 구조를 그대로 만들라는 뜻이 아닙니다.

먼저 현재 DB를 조사하고,
기존 schema를 최대한 재사용하십시오.

개념적으로 필요한 것은 두 가지입니다.

## A. Canonical Knowledge

가능하면 기존:

```text
support_knowledge_items
```

재사용.

필요한 개념:

```text
knowledge_id
intent_id
category
feature
canonical_answer

source_type
source_ref

affected_roles
affected_modes

answer_mode

status
revision
```

## B. Question Variants

예:

```text
support_intent_utterances
```

개념:

```text
id
intent_id

utterance
normalized_utterance

keywords / aliases

language

weight

status
```

단 현재 Repository에 동일 기능을 할 수 있는 table/schema가 이미 있다면
새 테이블을 만들지 말고 재사용 가능성을 우선 검토하십시오.

# 10. Question Matching

추천 검색 순서:

```text
사용자 질문
    ↓

1. normalize
    ↓

2. exact normalized match
    ↓ 실패

3. high-confidence variant/alias match
    ↓ 실패

4. keyword / full-text / trigram / existing semantic retrieval
    ↓

confidence 충분
    ↓
Canonical Intent
```

confidence가 충분하지 않으면
틀린 Direct Answer를 주면 안 됩니다.

그 경우 기존 Grounded GPT로 내려갑니다.

```text

X 모드
엑스모드
스윔노트x
스윔노트 X
```

```text

얼마
요금
이용료
구독료
금액
```

띄어쓰기와 간단한 오타도 고려합니다.

단 Normalizer가 의미를 변경하면 안 됩니다.

# 14. 복합 질문

예:

> X모드 가격하고 일반버전과 뭐가 다른지도 알려줘.

가능한 경우:

```text
X_MODE_PRICE
X_MODE_COMPARE
```

두 Intent를 찾습니다.

이 경우:

### 방법 A

Template/direct composition이 안전하면
LLM 없이 두 정답 조합.

### 방법 B

자연어 설명이 필요한 경우:

```text
Canonical Answer A
Canonical Answer B
        ↓
GPT
```

GPT에는 이 두 Knowledge만 제공합니다.

# 15. 기존 GPT 역할

GPT는 제거하지 않습니다.

GPT의 위치를:

```text
1차
```

가 아니라

```text
2차
```

로 변경합니다.

최종:

```text
DIRECT DB
    ↓ 실패

GROUNDED GPT
    ↓ 실패/사용자 요청

HUMAN
```

# 16. AI Grounding

기존 Grounding Pipeline 유지.

GPT는:

```text
DB에서 확보한 verified Knowledge 범위
```

안에서만 답변.

금지:

```text
가격 창작
정책 창작
UI 창작
환불 창작
장애 단정
```

# 17. Human Support

DB도 해결하지 못하고
GPT 답변 후에도 사용자가 해결되지 않았다면:

사용자가:

```text
[직접 문의하기]
```

버튼 선택.

그러면:

```text
Support Case 생성
또는 existing open case 재사용
```

# 18. Super Admin 알림

직접 문의가 발생하면
Super Admin에게 알림이 가야 합니다.

검토해야 할 것:

현재 Repository에 이미:

```text
support case notification
super admin notification
push
badge
web notification
```

중 무엇이 구현되어 있는지.

최종 목표:

```text
Human Support Requested
        ↓
Super Admin notified
```

관리자가 확인할 정보:

```text
conversation_id
case_id

user role
pool

original question

Direct DB attempt
matched intent if any

GPT answer
GPT confidence

user additional message

created_at
```

PII 최소화.

# 19. 직접 문의 버튼

GPT 답변 후:

```text
도움이 되었나요?

[해결됐어요]
[직접 문의하기]
```

형태 고려.

이미 비슷한 UI가 있다면 재사용.

사용자가 직접 문의를 선택하면
그때 Human Case로 전환.

AI가 모든 실패를 자동 Human case로 만들 필요는 없습니다.

---

# 20. 동일 Conversation 유지

직접 문의로 넘어가도
새 상담 UI를 열 필요가 없습니다.

현재 AI 문의 Conversation을 유지.

```text
AI
↓
Human Pending
↓
Super Admin reply
```

가 같은 대화에서 이어지는 구조.

# 21. Case 중복 금지


목표:

```text

```

또는 현재 schema에 가장 적합한 equivalent.

# 29. 구현 전에 제안해야 할 최종 Architecture

검토 후 아래 형식으로
추천 architecture를 제출하십시오.

```text
USER QUESTION

↓ normalize

↓ Direct Matcher

↓ Intent

↓ Canonical Answer
   ├ exact/high-confidence
   │ → DIRECT DB
   │
```
