3. 이번 구현

A. 회원정보 수정
- 넓은 회원 상세에 항목별 편집·저장·취소 연결.
- 기존 API가 실제 지원하는 일반 필드를 확인하여 명시.
- 기본정보·일반 연락처·기존 회원 메모를 우선 대상으로 한다.
- 기존 계약이 없는 필드를 임의 필드나 localStorage에 저장하지 않는다.
- 로그인/인증용 번호·권한·결제정보 변경은 제외.
- 미저장 상태에서 이동/닫기 시 저장·버리기·계속 편집 구분.
- 저장 실패 시 입력 유지.

B. 반이동
- 대상 회원·변경할 기존 소속·목적 반을 명확히 지정.
- 복수 반 중 다른 소속은 유지.
- 기존 정원·시간·상태·권한 규칙 적용.
- 동명이인·모호한 반·변경 범위 불명확 시 질문/선택.
- 변경 전후와 실제 서버 결과를 작업 카드로 보고.

C. AI 연결 기반
자연어
→ 허용된 구조화 Action
→ 서버의 입력·사용자·Pool·권한·업무 정책 검증
→ canonical Service/API
→ 결과 확인
→ 작업 카드·관련 query 갱신·결과 보기.

- 메뉴와 AI가 같은 Action 및 업무 검증 사용.
- 기존 APP AI 경로가 적합하면 재사용.
- 필요한 최소 APP 서버 변경은 로컬 구현에 포함.
- 모델의 임의 URL/API/SQL 실행 금지.
- 모델이 사용자·Pool·권한·확인 정책을 지정하지 못하게 함.
- 키는 서버에만 유지.
- 개인정보 전체를 모델로 일괄 전송하지 않음.
- 키워드 분기·가짜 답변을 실제 AI로 표시하지 않음.

4. 저장 안전성

- 기존 revision/조건부 갱신·중복 실행 방지 계약 확인.
- 클라이언트의 사전 비교만으로 충돌 안전하다고 주장하지 않는다.
- 필요 시 기존 호출과 호환되는 최소 서버 보완.
- schema 변경이 필수라면 해당 저장 경로만 보류하고 근거 보고.
- 응답 유실 시 변경을 무작정 재실행하지 않음.
- 확인할 수 없으면 결과 불명으로 표시.
- SSE·재조회가 미저장 입력을 덮어쓰지 않음.
- 로그아웃·회원/Pool 교체·늦은 응답 격리.
- 실제 성공과 결과 확인 전에는 완료 표시 금지.

5. 결과·Navigation

- 완료 후 강제 화면 이동 없음.
- 작업 카드의 결과 보기로 해당 회원·탭 이동.
- 변경 후 정상 조회 증거가 있어야 결과 열람 처리.
- 뒤로가기는 이전 화면·검색·필터·스크롤 복원.
- 뒤로가기를 데이터 변경 취소로 사용하지 않음.
- 기존 Stage 2 배치·입력·첨부·클릭 상태 유지.

6. 검증과 활성화 경계

합성 회원·반·격리 DB fixture와 mock 모델로 통합 검증:
- 검색·대상 선택·정보 수정·반이동·결과 조회.
- Web/메뉴/AI의 공통 실행 경로.
- 권한·cross-pool·잘못된 입력·모호한 대상.
- 복수 반 보존·동시 변경·중복 요청·응답 유실.
- 실제 편집 입력 보존·실패·세션 교체·늦은 응답.
- 기존 Web 회원 수정·반 배정 영향 범위 회귀.

운영 DB 연결이 없는 환경임을 확인하고 검증한다.
변경 영향 테스트·관련 타입검사·필요 빌드 수행.
기존 전체 타입 오류와 신규 오류를 구분.
변경 없는 전체 suite·Stage 2 CSS·설치 검사는 반복하지 않는다.

Desktop 쓰기 허용은 검증된 정확한 경로·method만 최소 확장.
미배포 서버 의존 기능은 기본 비활성.
운영 서버로 새 쓰기 요청이 나가지 않도록 유지한다.
실제 AI 전송은 승인된 통합 배포 전 활성화하지 않는다.
