Production에 기존 row가 존재할 수 있으므로

Production에 row가 0건이면
그 사실을 근거로 단순화 가능.

이번 WP에서는 migration 작성만 하고
Production 적용은 하지 않는다.

==================================================
6. FAILED RETRY FIX
==================================================

현재 버그:

FAILED row 존재
→ quota reserved_count +1
→ INSERT reservation ON CONFLICT DO NOTHING
→ 기존 row FAILED 유지
→ 성공 후 reservation COMPLETED update 실패

수정 목표:

FAILED request_id 재시도 시
atomic하게:

FAILED
→ RESERVED

로 상태 전환한 요청만
새 reservation을 획득할 수 있어야 한다.

동시에:

- reserved_at 갱신
- completed_at null
- error_code null
- usage period 현재 period와 정합

필요 시 expires_at 갱신.

중요:

quota counter increment와
FAILED→RESERVED 전환 사이 race condition 금지.

가능하면 transaction 안에서 처리.

==================================================
7. FAILED RETRY SUCCESS
==================================================

FAILED retry 후 ENGINE 성공 시:

reservation:
RESERVED → COMPLETED

usage:
reserved_count -1
completed_count +1

정확히 1회만.

최종 reservation status가
FAILED로 남으면 안 됨.

==================================================
8. COMPLETED RETRY FIX
==================================================

현재 버그:

COMPLETED request_id
→ isRetry=true
→ route가 무시
→ ENGINE 재호출
→ completed_count +1

절대 금지.

COMPLETED request_id 재요청 시:

ENGINE 재호출 금지.
quota 변경 금지.

이미 저장된 conversation/message에서
동일 request_id의 ASSISTANT message를 찾아
기존 성공 결과를 반환.

가능한 범위에서 기존 저장 데이터 재사용.

==================================================
9. COMPLETED RESPONSE REPLAY
==================================================

동일 request_id COMPLETED retry 응답은
새 GPT/ENGINE 결과가 아니라
기존 persisted result를 사용.

필요 데이터:

- assistant content
- safe metadata
- current usage status

현재 message metadata만으로
current_progress/next_step 등 전체 원 응답을
완전히 복원할 수 없는지 확인.

복원 불가능하다면:

A. safe response payload를 message metadata에 저장하도록
   최소 확장

또는

B. 별도 result JSON 저장

중 기존 구조에 가장 작은 변경을 선택.

단 raw ENGINE trace/prompt/knowledge documents 저장 금지.

15. IMPORTANT REQUEST FLOW
==================================================

route 순서를 재검토.

동일 request_id가 COMPLETED인지 확인하는 로직은
새 quota reservation보다 먼저 동작해야 함.

Canonical:

auth
→ ownership
→ request_id prior state 확인

IF COMPLETED:
   persisted result replay
   quota 차감 없음
   ENGINE 호출 없음
   RETURN

ELSE:
   eligibility
   quota reservation
   conversation/user message
   ENGINE
   validation
   assistant save
   finalize quota
