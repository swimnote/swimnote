[긴급 조사 — 2026년 9월 AI 성장리포트가 2026-10-05 정상 자동 발급되는지 Production Readiness 검증]

이번 작업은 수정부터 하지 않는다.

"2026년 9월 수업 데이터를 대상으로 하는 AI 성장리포트가
2026년 10월 5일에 실제 Production에서 정상 자동 발급되는가?"

를 코드에 날짜가 있다는 수준이 아니라
실제 end-to-end 실행 가능성 기준으로 검증한다.

APP/API Repository의 실제 코드, Production 설정, DB 상태,
scheduler/worker/job/API 연결을 조사한다.

AI ENGINE 영역을 추측하지 말고
APP/API가 AI ENGINE에 무엇을 어떤 계약으로 요청하는지만 확인한다.

Production 데이터 수정 금지.
강제 리포트 생성 금지.

1. 공식 발급 정책부터 코드와 대조
━━━━━━━━━━━━━━━━━━━━━━

현재 제품 정책:

- 대상 월: 2026년 9월
- 자동 발급일: 2026년 10월 5일
- 지난달 수업내용을 기반으로 생성
- 무료 AI 성장리포트
- 다음 달 재등록이 완료된 대상 회원에게 제공
- 앱 내 피드 형식으로 제공
- 푸시알림 전송
- PDF 저장 가능

이 정책이 현재 Production 코드와 정확히 일치하는지 확인한다.

특히 "10월 5일"을 단순 날짜 비교만 하지 말고
timezone이 Asia/Seoul 기준으로 정확히 언제 실행되는지 확인한다.

2. 자동 발급 Trigger 조사
━━━━━━━━━━━━━━━━━━━━━━

실제 자동 발급 시작점부터 찾는다.

확인:

- cron
- scheduler
- worker
- queue
- Render Cron Job
- API internal job
- 외부 scheduler
- 기타 실제 trigger

정확히 어떤 코드가
매월 5일 발급을 시작하는지 찾는다.

보고:

1. scheduler 위치
2. 실행 주기
3. timezone
4. 2026-10-05 실제 예상 실행시각(KST)
5. scheduler가 Production에서 실제 활성화되어 있는지
6. 환경변수/secret 누락 여부
7. scheduler 실패 시 retry 여부
8. 중복 실행 방지 방식

"코드가 존재한다"와
"Production에서 실제 실행되도록 연결되어 있다"를 구분한다.

3. 9월 리포트 대상자 선정 검증
━━━━━━━━━━━━━━━━━━━━━━

2026-09-01 ~ 2026-09-30 데이터를 대상으로
누가 10월 5일 무료 리포트를 받는지 실제 selection logic을 확인한다.

특히:

- 재등록 판정 기준
- active/inactive 상태
- 퇴원생 처리
- 신규 회원
- 중도 등록
- 수업 데이터 없는 회원
- 일지 부족 회원
- pool isolation
- 중복 회원
- 이미 발급된 회원
- 관리자/선생님 테스트 계정 제외 여부

를 현재 코드 기준으로 확인한다.

Production DB는 READ ONLY로
가능하다면 실제 9월 대상 예상 인원 수를 계산한다.

개인정보는 보고하지 않는다.

예:

데이터 부족 제외 N명
최종 예상 발급 N명

형태로만 보고한다.

4. 데이터 cutoff 검증
━━━━━━━━━━━━━━━━━━━━━━

9월 리포트에 들어가는 데이터 기간을 정확히 확인한다.

반드시:

2026-09-01 00:00:00
~
2026-09-30 23:59:59...

의 의미가 DB timezone과 일치하는지 확인한다.

UTC 저장이라면 KST 월 경계 변환이 정확한지 검증한다.

10월 1~5일 수업 데이터가
9월 리포트에 섞이면 안 된다.

반대로 9월 30일 늦은 시간 데이터가
timezone 때문에 빠져도 안 된다.

5. APP/API → AI ENGINE 계약 확인
━━━━━━━━━━━━━━━━━━━━━━

대상자 선정 후
APP/API가 AI ENGINE에 무엇을 보내는지 확인한다.

확인:

- endpoint
- request schema
- report month
- student identifier
- pool/tenant identifier
- 수업일지/평가 데이터 전달 방식
- 인증
- timeout
- retry
- concurrency
- rate limit
- 실패 응답 처리
- partial failure 처리

AI ENGINE 내부 판단은 여기서 추측하지 않는다.

APP/API가 기대하는 response schema도 정확히 보고한다.

6. 생성 결과 저장 경로
━━━━━━━━━━━━━━━━━━━━━━

AI ENGINE 응답 이후:

AI ENGINE result
→ APP/API
→ DB 저장
→ report record
→ feed
→ parent visibility
→ push
→ PDF

전체를 추적한다.

특히 하나가 실패했을 때:

- 리포트는 생성됐는데 DB 저장 실패
- DB에는 있는데 feed 없음
- feed는 있는데 push 없음
- push만 실패
- PDF만 실패

등을 어떻게 처리하는지 확인한다.

7. 중복 발급 / 재실행 안전성
━━━━━━━━━━━━━━━━━━━━━━

10월 5일 job이 중간 실패 후 다시 실행되어도
같은 학생의 9월 리포트가 2개 생기면 안 된다.

확인:

- idempotency key
- UNIQUE constraint
- report_month + student
- job state
- duplicate prevention

실제 구현을 보고한다.

8. 실패 복구 가능성
━━━━━━━━━━━━━━━━━━━━━━

10월 5일 일부 리포트가 실패하면:

- 자동 retry 되는가
- 몇 회인가
- 어느 간격인가
- 실패 대상만 재처리 가능한가
- 전체를 다시 돌려야 하는가
- 운영자가 수동 재실행 가능한가
- 재실행 시 중복 방지가 되는가

확인한다.

9. Push 검증
━━━━━━━━━━━━━━━━━━━━━━

리포트 생성 완료 후
학부모에게 실제 push가 언제 발생하는지 확인한다.

"생성 요청" 시점이 아니라
"정상 저장/발급 완료" 이후에만 push되어야 한다.

push 실패가 report 생성 자체를 rollback시키는지도 확인한다.

━━━━━━━━━━━━━━━━━━━━━━
10. 10월 5일 예상 처리량
━━━━━━━━━━━━━━━━━━━━━━

Production READ ONLY 데이터 기준으로
가능하면 예상 대상 수를 계산한다.

그리고 현재 APP/API 쪽에서:

- 한 번에 몇 건
- batch size
- concurrency
- queue depth
- timeout
- retry

로 처리하는지 확인한다.

AI ENGINE capacity 판단은 하지 말고
APP/API가 엔진에 발생시키는 예상 호출량/패턴만 계산한다.
