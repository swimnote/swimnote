# WP0 검토 결과 및 WP1 작업 승인

WP0는 통과합니다.

확인된 실제 구조와 설계 문서가 대부분 일치하며, 이번 WP1 수정 대상은 아래 한 파일로 제한합니다.

```text
components/ai/features/diary/useDiaryAI.ts
```

기존 Diary Save, Whisper, Voice Recorder, Diary 화면 구조는 수정하지 않습니다.

---

# WP1 작업 승인 범위

이번에는 아래 항목만 구현합니다.

```text
1. request_id 생성
2. Request Body에 request_id 추가
3. context.students[{ref,name}] 추가
4. 기존 student_refs 병행 유지
5. TeacherDiaryAIRequest 타입 명시
6. Request 전송 전 최소 검증
```

승인되지 않은 다른 작업은 진행하지 않습니다.

---

# 1. request_id 생성 방식 수정

기존 제안:

```text
Date.now() + Math.random()
```

만 단독으로 사용하는 방식은 채택하지 않습니다.

먼저 현재 Expo/React Native 환경에서 다음 사용 가능 여부를 확인합니다.

```ts
crypto.randomUUID()
```

사용 가능하면 이를 우선 사용합니다.

예:

```ts
function createDiaryRequestId(): string {
  if (
    typeof globalThis.crypto !== 'undefined' &&
    typeof globalThis.crypto.randomUUID === 'function'
  ) {
    return `diary_${globalThis.crypto.randomUUID()}`;
  }

  return createFallbackDiaryRequestId();
}
```

`crypto.randomUUID()`를 사용할 수 없는 환경에서는 외부 패키지를 바로 추가하지 말고, Repository 내 기존 ID 생성 Utility가 다시 없는지 확인한 후 fallback을 구현합니다.

Fallback에는 최소한 다음 요소를 조합합니다.

```text
현재 시각
고해상도 또는 증가 카운터
충분한 난수
```

예시 방향:

```ts
let diaryRequestSequence = 0;

function createFallbackDiaryRequestId(): string {
  diaryRequestSequence += 1;

  const time = Date.now().toString(36);
  const sequence = diaryRequestSequence.toString(36);
  const random = Math.random().toString(36).slice(2, 12);

  return `diary_${time}_${sequence}_${random}`;
}
```

단순히 `Date.now() + Math.random()`을 문자열로 붙이는 구현은 금지합니다.

# 2. request_id 재사용 정책

다음 정책을 구현합니다.

```text
사용자가 새로 AI 생성 버튼을 누름
→ 새로운 request_id 생성

같은 요청 안에서 네트워크 자동 재시도
→ 동일 request_id 유지

사용자가 다시 생성 버튼을 누름
→ 새로운 request_id 생성
```

중요:

`generateDiary()` 내부 재시도마다 새 request_id를 생성하면 안 됩니다.

request_id는 한 번의 사용자 생성 요청이 시작될 때 생성하고, 해당 요청의 모든 자동 재시도에서 동일하게 유지합니다.

```json

  "schema_version": "1.0",

  "locale": "ko-KR",
  "input": {

    "pool_id": "pool_xxx",
    "class_id": "class_xxx",
    "lesson_date": "2026-07-29",
    "student_refs": [
      "student_001"
    ],
    "students": [
      {
        "ref": "student_001",
        "name": "서태웅"
      }
    ]
  }
}
```

# 4. TeacherDiaryAIRequest 타입

기존 타입 구조와 충돌하지 않는 위치에 한 번만 정의합니다.

중복 타입 파일을 만들지 않습니다.

권장 형태:

```ts
interface TeacherDiaryAIRequest {
  request_id: string;
  schema_version: '1.0';
  feature: 'teacher_diary';
  locale: 'ko-KR';
  input: {
    text: string;
  };
  context: {
    pool_id: string;
    class_id: string;
    lesson_date: string;
    student_refs: string[];
    students: Array<{
      ref: string;
      name: string;
    }>;
  };
}
```

현재 실제 API Contract에서 `pool_id`가 optional인 경우, 임의로 required 처리하지 말고 현재 화면에서 반드시 확보되는지 먼저 확인합니다.

확보되지 않을 수 있다면 타입과 Validator에서 그 사실을 명확하게 보고해야 합니다.

# 5. students 생성 규칙

현재 전달받은 학생 데이터를 그대로 사용합니다.

```ts
const students = options.students.map((student) => ({
  ref: student.id,
  name: student.name,
}));

const studentRefs = students.map((student) => student.ref);
```

금지:

```text
이름 trim 외 의미 변경
성 제거
given_name 생성
조사 제거
별명 생성
이름 정규화
학생 순서 임의 변경
```

이름 앞뒤 공백이 실제 데이터 오류로 존재한다면, 이번 WP에서 임의 수정하지 말고 보고만 합니다.

# 6. Request 사전 검증

AI 호출 전 다음만 검증합니다.

```text
request_id가 비어 있지 않음
input.text.trim()이 비어 있지 않음
class_id 존재
lesson_date 존재
students 배열 존재
각 students[].ref 존재
각 students[].name 존재
student_refs와 students[].ref가 순서와 값 기준으로 동일
```

`pool_id`가 현재 화면 구조에서 항상 존재하는지 WP1 구현 중 다시 확인합니다.

존재하지 않을 수 있다면 임의 문자열이나 class_id로 대체하지 않습니다.

이 경우 실제 코드 상태와 권장 처리안을 완료 보고서에 명시합니다.
