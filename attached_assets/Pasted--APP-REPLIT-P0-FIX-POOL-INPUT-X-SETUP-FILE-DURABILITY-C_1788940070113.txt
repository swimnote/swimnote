3. FILE DB WRITE — ATOMIC 처리
━━━━━━━━━━━━━━━━━━━━━━

대상:

- curriculum
- website
- logo
- photo

현재 upload 흐름을 정확히 확인한 뒤
DB mutation은 transaction으로 묶는다.

특히 curriculum/website/logo:

기존:

1. R2 upload
2. 기존 is_current=false
3. 신규 x_setup_files INSERT

DB transaction 안에서 최소:

- 신규 file row INSERT
- 이전 current row UPDATE
- 관련 submission 상태 UPDATE

가 함께 commit되게 한다.

신규 insert 실패 시:

기존 current 상태 rollback.

즉:

current file 0 상태가 생기면 FAIL.

4. R2 UPLOAD → DB FAILURE 보상
━━━━━━━━━━━━━━━━━━━━━━

R2와 PostgreSQL을
하나의 transaction으로 묶을 수 없으므로
compensating action을 구현한다.

권장 흐름:

1. R2 object upload
2. DB transaction 실행
3. DB transaction 성공
   → 완료
4. DB transaction 실패
   → 방금 업로드한 신규 R2 object cleanup 시도
   → 실패 로그/audit 남김
   → 사용자에게 upload 실패 반환

중요:

기존/과거 R2 object는 절대 삭제 금지.

cleanup 대상은
이번 request가 방금 생성한
신규 uncommitted object 하나뿐.

cleanup 실패하더라도
기존 데이터 손상 금지.

그리고 cleanup failure는
추적 가능한 error/event log를 남긴다.

━━━━━━━━━━━━━━━━━━━━━━
5. VERSION RACE 제거
━━━━━━━━━━━━━━━━━━━━━━

현재:

SELECT MAX(submission_version)+1

만으로 version 부여하는 구조는 금지.

동시 요청에도 같은 pool/file_type에서
version 번호가 절대 중복되지 않게 수정.

가능한 최소 안전 구조 선택:

A.
DB advisory lock / row lock

또는

B.
transaction + locked sequence source

또는

C.
UNIQUE(pool_id,file_type,submission_version)
+
safe retry

현재 schema/Drizzle 구조에 가장 적은 변경으로 구현.

반드시 DB UNIQUE constraint 추가 권장:

(pool_id, file_type, submission_version)

단 photo가 현재 version=1 고정이라면
그대로 UNIQUE를 걸면 여러 photo가 충돌하므로
photo 정책을 별도로 고려.

따라서:

- curriculum
- website
- logo

의 versioned file과
photo multi-file 구조를 구분해서 설계.

임의로 photo 기능 파손 금지.

11. FAILURE TEST
━━━━━━━━━━━━━━━━━━━━━━

반드시 fault injection 또는 안전한 테스트 방식으로:

CASE A

R2 upload 성공
→ DB INSERT 강제 실패

기대:
- request 실패
- 기존 current 그대로
- 신규 DB row 없음
- 신규 R2 object cleanup 성공
  또는 cleanup 실패가 로그로 추적됨

CASE B

신규 DB INSERT 실패

기대:
기존 is_current=true 유지.

CASE C

같은 pool에서 curriculum 동시 upload 2건

기대:
- version 서로 다름
- current 정확히 하나
- R2 key 서로 다름

CASE D

parse 실패

기대:
- 원본 DB/R2 보존
- 기존 active curriculum 유지
- READY/ACTIVE 잘못 변경 없음

CASE E

photo DB insert 실패

기대:
- 신규 R2 object orphan 방지
- 기존 photo 영향 없음

CASE F

pool basic info 변경

기대:
- current value 변경
- audit에서 before/after 확인 가능

CASE G

approve/reject

기대:
actor + action + before/after 추적.
