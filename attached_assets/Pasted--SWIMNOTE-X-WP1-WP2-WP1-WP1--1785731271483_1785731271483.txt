현재 상태:

```text
Production Migration: 실행 완료
운영 DB 변경: 적용 완료
코드 구현: 완료
자동 Commit: 발생
Push: 미실행
배포: 미실행

Rollback: 불필요
```

다음 미실행 항목은 해결 완료로 표시하지 말고 잔여 회귀검증 항목으로 보존하십시오.

* 정상 로그인
* 일반 AI 일지 생성
* 일반 Diary Save
* initPoolDb/initSuperDb 실패 Mock

이 항목을 해결하기 위해 임의 계정 생성, 기존 계정 활성화, 테스트 프레임워크 추가 또는 코드 리팩터링을 하지 마십시오.

금지:

* 서버 재시작
* Render 배포

3. 다음 작업
━━━━━━━━━━━━━━━━━━━━━━

다음 작업은 **WP2 X모드 상태·권한 Backend 설계서 제출**입니다.

아직 구현하지 마십시오.

WP2 목표:

* 서버가 수영장별 X모드 상태를 판정
* 서버 상태를 최종 기준으로 사용
* 일반모드의 X API 접근 차단
* 향후 앱 Mode Context가 사용할 읽기 Contract 제공

최종 판정식:

```text
xmode_entitlement = true
AND
xmode_config_status = READY
→ X모드
```

그 외:

```text
xmode_entitlement = true
AND
xmode_config_status != READY
→ X 준비중

xmode_entitlement = false
→ 일반모드
```

앱이나 클라이언트 전달값으로 X모드를 임의 활성화하면 안 됩니다.

6. Mode 응답 Contract
━━━━━━━━━━━━━━━━━━━━━━

앱이 로그인 후 조회할 최소 Contract를 설계하십시오.

필요 정보:

* pool_id
* mode
* entitlement
* config_status
* capabilities

단, capabilities 항목을 임의로 확장하지 마십시오.

현재 PART 1에서 필요한 최소 capability만 제안하고, 각 항목이 어느 WP에서 실제 활성화되는지 표시하십시오.

예시 형식을 참고하되 그대로 확정하지 마십시오.

```json
{
  "pool_id": "pool_xxx",
  "mode": "normal | x_pending | x",
  "xmode_entitlement": false,
  "xmode_config_status": "NOT_CONFIGURED",
  "capabilities": {}
}
```

기존 API Contract를 깨지 않는 별도 조회 API인지, 기존 응답에 optional 필드로 추가할지 비교하십시오.

7. API Guard 설계
━━━━━━━━━━━━━━━━━━━━━━

WP2에서는 X 기능 자체를 구현하지 않습니다.

다만 향후 X 전용 API를 보호할 공통 Guard를 설계합니다.

제출:

* Guard 파일 위치
* Guard 함수
* poolId 추출 방식
* 사용자의 pool 접근 권한 검증 순서
* entitlement 확인 순서
* config status 확인 순서
* 일반모드 접근 오류
* X 준비중 접근 오류
* super_admin 예외 여부
* 직접 URL 호출 차단 방식

권장 검증 순서:

```text
인증
→ 사용자 pool 접근 권한
→ pool 존재
→ entitlement
→ config status
→ capability
```

승인 전 구현하지 마십시오.

9. 오류 코드 설계
━━━━━━━━━━━━━━━━━━━━━━

기존 AppError 구조와 오류 응답 형식을 조사하십시오.

WP2에 필요한 오류를 기존 규칙에 맞춰 제안하십시오.

검토 대상:

* POOL_NOT_FOUND
* POOL_ACCESS_DENIED
* XMODE_NOT_ENTITLED
* XMODE_NOT_READY
* XMODE_ACCESS_REQUIRED

기존 오류 코드 체계와 맞지 않으면 기존 체계를 우선하십시오.

새 오류 코드를 코드에 추가하지 말고 설계서에서만 제출하십시오.

* 기존 JWT 변경 여부
* 기존 수영장 조회 영향
* 기존 관리자 API 영향
* 기존 교사 API 영향
* 기존 학부모 API 영향
* 기존 RevenueCat 처리 영향
* 일반모드에서 추가 DB 조회 발생 여부
* X 상태 조회 실패 시 일반기능 차단 여부

원칙:

```text
X 상태 조회 오류가 발생해도
일반모드 기존 기능을 임의로 X모드로 처리하지 않음
```

다만 인증 또는 필수 DB 오류를 숨기는 fallback도 추가하지 마십시오.
