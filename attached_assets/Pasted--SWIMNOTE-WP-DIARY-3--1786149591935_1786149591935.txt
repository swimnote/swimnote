SWIMNOTE — WP-DIARY-3
일지 사진 미표시 + 사진 중복사용 구조 조사
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이번 WP에는 두 가지 요구사항이 있다.

A. 일지에 첨부한 사진이
   이전 일지/상세에서 "등록된 사진이 없습니다"로 나오는 문제

B. 이미 다른 일지에서 사용한 사진을
   "사용중"으로 막지 말고
   여러 일지에서 같은 사진을 중복 선택/표시할 수 있게 변경

이번 단계에서는 우선 구조 조사.
원인 확정 전 코드 수정 금지.

━━━━━━━━━━━━━━━━━━━━
1. 사용자 요구사항 확정
━━━━━━━━━━━━━━━━━━━━

같은 사진 원본 1개를 여러 일지에서 사용할 수 있어야 한다.

예:

사진 P1

월요일 일지 D1
→ P1 사용

목요일 일지 D2
→ 같은 P1 다시 사용 가능

추가 일지 D3
→ 같은 P1 다시 사용 가능

결과:

D1 → P1 표시
D2 → P1 표시
D3 → P1 표시

기존 D1에서 사진이 사라지거나
D2로 연결이 이동하면 안 된다.

즉:

"사진은 일지에 소유되는 것이 아니라
여러 일지에서 참조할 수 있는 미디어 자산"

방식으로 동작해야 한다.

━━━━━━━━━━━━━━━━━━━━
2. 현재 "사용중" 판정 위치 조사
━━━━━━━━━━━━━━━━━━━━

Repository 전체에서 다음 검색:

"사용중"
"isUsed"
"used"
"journal_id"
"diary_id"
"diary-attach"
"photo_ids"

반드시 확인:

- 사진 선택 모달 파일
- "사용중" Badge 렌더 위치
- 선택 disabled 조건
- 이미 사용한 사진을 판단하는 데이터 필드
- 서버가 사용중 사진을 제외하는지
- 앱 UI만 막고 있는지

정확한 파일/라인 제출.

━━━━━━━━━━━━━━━━━━━━
3. 현재 사진 Source of Truth 조사
━━━━━━━━━━━━━━━━━━━━

현재 감사 기준으로는:

POST /photos/diary-attach

후

photo_assets_meta.journal_id = diary_id

구조로 파악되어 있다.

현재 실제 코드/DB schema를 다시 확인.

반드시 제출:

photo_assets_meta 주요 컬럼:
- id
- journal_id
- student 관련 연결
- media_status
- 기타 diary 연결 컬럼

중요:

journal_id가 단일 FK/단일 값이면
현재 구조는 기본적으로 사진 1개 ↔ 일지 1개 구조일 가능성이 있다.

이 경우 UI의 "사용중" 제한만 제거하면 안 된다.

왜냐하면:

P1.journal_id = D1

상태에서 D2에 붙일 때

P1.journal_id = D2

로 UPDATE하면
D1 연결이 사라질 수 있기 때문이다.

반드시 확인할 것.

━━━━━━━━━━━━━━━━━━━━
4. diary-attach 서버 로직 조사
━━━━━━━━━━━━━━━━━━━━

POST /photos/diary-attach 전체 코드 제출.

확인:

현재가

UPDATE photo_assets_meta
SET journal_id = diaryId
WHERE id IN (...)

방식인지,

별도 관계 테이블에 INSERT하는 방식인지 확인.

같은 photo_id를 두 번째 diary_id에 attach하면
현재 어떤 일이 발생하는지 코드로 설명.

A.
기존 journal_id 덮어쓰기

B.
중복 attach 거부

C.
별도 관계 row 생성

D.
기타

중 하나로 판정.

5. 일지 상세 사진 조회 조사
━━━━━━━━━━━━━━━━━━━━

실제 SQL/서비스 경로 확인.

현재 상세에서

"등록된 사진이 없습니다"

가 나오는 원인 조사.

확인:

- journal_id = diary_id 조회인지
- media_status 조건

6. 올바른 목표 데이터 모델 검토
━━━━━━━━━━━━━━━━━━━━

요구사항상 최종 관계는:

PHOTO N:M DIARY

가 되어야 한다.

즉:

사진 1개 → 여러 일지
일지 1개 → 여러 사진

가능해야 한다.

현재 DB가 photo_assets_meta.journal_id 단일 컬럼만 사용한다면
가장 안전한 구조를 제안할 것.

예시:

diary_photo_links
- id
- diary_id
- photo_id
- created_at

UNIQUE(diary_id, photo_id)

이런 연결 테이블 방식 검토.

주의:
이 이름/구조를 그대로 구현하라는 의미는 아니다.
현재 schema와 기존 photo 관계 테이블을 먼저 조사하고
이미 적합한 관계 테이블이 있으면 재사용할 것.

불필요한 신규 테이블 생성 금지.

━━━━━━━━━━━━━━━━━━━━
7. 하위 호환성 필수 조사
━━━━━━━━━━━━━━━━━━━━

기존 Production 일지 사진을 절대 깨뜨리면 안 된다.

조사:

- 기존 journal_id 데이터 건수
- 기존 diary 상세 조회 방식
- 기존 album/photo 화면에서 journal_id 사용 여부
- 삭제 로직에서 journal_id를 사용하는지
- 학생별 사진 연결과 충돌 여부

새 N:M 구조가 필요하다면:

기존 데이터 migration 방법까지 설계.

기존 사진이 사라지거나
기존 일지에서 사진이 없어지는 변경 금지.

━━━━━━━━━━━━━━━━━━━━
8. UI 목표
━━━━━━━━━━━━━━━━━━━━

사진 선택 화면:

현재:

사진 P1
[사용중]
선택 불가

변경 목표:

사진 P1
이미 다른 일지에 연결되어 있어도
정상 선택 가능.

"사용중" Badge는
일지 중복사용 제한을 의미한다면 제거.

필요하다면 정보 표시만 할 수 있으나
선택 disabled 금지.

같은 일지 안에서 동일 photo_id를
두 번 선택하는 것은 금지.

즉:

D1 + P1 = 가능
D2 + P1 = 가능

D1 안에 P1 두 번 = 불가

9. 삭제 동작 조사
