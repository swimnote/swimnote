[SWIMNOTE 앱 업데이트 시스템 최종 구현 지시]

목표

1. 새로운 EAS 네이티브 빌드가 출시되면 구버전 사용을 강제로 차단
2. 업데이트 및 OTA 적용 후 기존 로그인 유지
3. 설정 화면의 수동 업데이트 확인 버튼은 숨기되 기능과 코드는 보존
4. OTA 발견 시 모달 표시 → 다운로드 → 앱 재시작
5. 업데이트 실패로 사용자가 앱에 영구 진입하지 못하는 상황 방지

이번 작업은 SWIMNOTE 앱과 SWIMNOTE API Server에 구현합니다.

==================================================
1. 업데이트 유형을 반드시 분리
==================================================

A. 네이티브 앱 강제 업데이트

용도:
- 새로운 EAS Build/App Store/Play Store 버전 설치가 필요한 경우
- runtimeVersion 변경
- 네이티브 라이브러리 변경
- 기존 앱과 서버의 호환성이 깨지는 경우

동작:
- 현재 앱 버전이 minimum_supported_version보다 낮으면 앱 사용 차단
- 닫기 버튼 없는 강제 업데이트 모달 표시
- 업데이트 버튼으로 App Store 또는 Play Store 이동
- 뒤로가기와 배경 터치로 닫히지 않음

B. OTA 업데이트

용도:
- 동일 runtimeVersion에서 가능한 JS/UI/로직 수정

동작:
- 업데이트 발견
- 업데이트 안내 모달 표시
- 사용자가 ‘업데이트’ 선택
- fetchUpdateAsync()
- 다운로드 성공
- reloadAsync()
- 새 OTA로 앱 재시작
- 로그인 유지

두 업데이트를 같은 의미로 처리하지 마십시오.

==================================================
2. 서버 버전 정책 API
==================================================

서버에 앱 버전 정책 조회 API를 구현하거나 기존 설정 API를 재사용하십시오.

예시:

GET /api/app-version-policy?platform=ios

응답:

{
  "platform": "ios",
  "latest_version": "1.7.0",
  "minimum_supported_version": "1.7.0",
  "force_update": true,
  "store_url": "<iOS App Store URL>",
  "message": "안정적인 서비스 이용을 위해 최신 버전으로 업데이트해 주세요.",
  "updated_at": "..."
}

Android도 별도 정책을 지원하십시오.

필수 원칙:

- latest_version: 최신 권장 버전
- minimum_supported_version: 이 버전 미만은 사용 금지
- force_update: 강제 차단 활성화 여부
- 버전 비교는 문자열 비교가 아니라 semantic version 비교
- 서버 장애 시 무조건 앱을 차단하지 않음
- 마지막 정상 정책값을 로컬에 캐시할 수 있음
- 단, 캐시가 없고 서버 조회에 실패하면 앱 사용을 허용하고 오류 로그만 남김

==================================================
3. 강제 업데이트 모달
==================================================

현재 앱 버전 < minimum_supported_version이고 force_update=true이면:

제목:
필수 업데이트

내용:
새로운 버전이 출시되었습니다.
안정적인 서비스 이용을 위해 최신 버전으로 업데이트해 주세요.

버튼:
업데이트

규칙:

- 닫기 버튼 없음
- 배경 터치 닫기 금지
- iOS swipe dismiss 금지
- Android back button 차단
- 다른 화면 진입 금지
- 업데이트 버튼으로 해당 플랫폼 Store 이동
- Store에서 앱으로 돌아오면 버전 정책 재확인
- 업데이트 완료 전까지 동일 모달 유지

운영자·선생님·학부모 모두 동일하게 적용합니다.

==================================================
4. 기존 로그인 절대 유지
==================================================

네이티브 업데이트와 OTA 적용 과정에서 다음을 절대 실행하지 마십시오.

- AsyncStorage.clear()
- SecureStore 삭제
- auth token 삭제
- refresh token 삭제
- user/session 삭제
- 강제 logout
- AuthContext 초기화 과정에서 저장 세션 제거
- OTA reload를 401/403으로 오인하여 세션 삭제

OTA의 Updates.reloadAsync()는 앱 JS를 다시 로드할 뿐입니다.
로그인 정보는 기존 영구 저장소에서 다시 복구해야 합니다.

앱 재시작 후 순서:

1. 저장된 인증정보 로드
2. /auth/me 또는 기존 세션 검증
3. 정상 세션이면 기존 로그인 화면으로 복귀
4. 실제 401일 때만 인증 만료 처리

업데이트 확인 실패, OTA 실패, 버전 정책 API 실패를
로그아웃 사유로 사용하지 마십시오.

==================================================
5. OTA 업데이트 모달
==================================================

앱 실행 후 인증정보 복구와 기본 화면 준비가 끝난 다음 OTA를 확인하십시오.

사용 API:

- Updates.checkForUpdateAsync()
- Updates.fetchUpdateAsync()
- Updates.reloadAsync()

동작:

1. 앱 실행
2. 저장된 로그인 복원
3. OTA 확인
4. update.isAvailable=false
   → 아무것도 표시하지 않음
5. update.isAvailable=true
   → OTA 업데이트 모달 표시
6. ‘업데이트’ 버튼
   → 다운로드 진행
7. 다운로드 완료
   → “업데이트를 적용하기 위해 앱을 다시 시작합니다.”
8. Updates.reloadAsync()
9. 최신 OTA로 재시작
10. 기존 로그인 세션 복원

모달 문구:

제목:
업데이트가 있습니다

내용:
더 안정적인 사용을 위해 최신 업데이트를 적용합니다.
업데이트가 완료되면 앱이 자동으로 다시 시작됩니다.

버튼:
업데이트

다운로드 중:

- 버튼 중복 클릭 차단
- 진행 상태 표시
- 모달 닫기 차단
- fetch 중복 호출 금지

다운로드 실패:

- 앱을 강제 종료하지 않음
- “업데이트를 불러오지 못했습니다. 다시 시도해 주세요.”
- 다시 시도 버튼 제공
- 기존 앱은 계속 사용할 수 있게 할지 여부는 OTA 중요도 정책에 따라 구분

==================================================
6. OTA 선택/필수 정책
==================================================

OTA도 두 등급으로 구분할 수 있게 설계하십시오.

OPTIONAL:
- 나중에 버튼 허용 가능
- 현재는 사용하지 않아도 됨

REQUIRED:
- 닫기 불가
- 다운로드 및 reload 전까지 사용 차단

초기 SWIMNOTE 운영 정책:

- 운영상 치명적 버그 수정 OTA: REQUIRED
- 일반 UI 개선 OTA: OPTIONAL 또는 백그라운드 적용

서버 또는 OTA metadata로 required 여부를 관리할 수 있게 하되,
처음부터 복잡한 관리 화면을 만들 필요는 없습니다.

==================================================
7. 설정의 업데이트 확인 버튼 숨김
==================================================

현재 설정 화면의 ‘업데이트 확인’ 버튼은 사용자 UI에서 제거하십시오.

단:

- 업데이트 체크 함수 삭제 금지
- 관련 Hook/Service 삭제 금지
- 관리자 디버그 용도로 다시 노출 가능하게 보존
- hidden flag 또는 feature flag로 visibility만 false 처리
- 앱 시작 자동 업데이트 체크는 계속 작동

예:

SHOW_MANUAL_UPDATE_BUTTON = false

또는 서버 feature flag 사용.

==================================================
8. 반드시 지켜야 할 배포 순서
==================================================

가장 중요합니다.

1단계:
현재 설치된 구버전과 호환되는 runtimeVersion별로
‘강제 업데이트 검사 기능’을 OTA로 먼저 배포

2단계:
구버전 기기에서 해당 OTA 수신 여부 확인

3단계:
새 EAS Build 생성

4단계:
App Store/Play Store 심사 및 출시 완료 확인

5단계:
Store에 실제 새 버전이 공개된 뒤에만
minimum_supported_version을 새 버전으로 올림

6단계:
구버전 앱 실행
→ 강제 업데이트 모달
→ Store 이동
→ 새 버전 설치
→ 기존 로그인 유지 확인

금지:

- Store 출시 전에 minimum_supported_version부터 올리는 행위
- 강제 업데이트 기능이 없는 구버전을 먼저 차단하는 행위
- 새 runtime OTA만 배포하고 구 runtime 사용자를 방치하는 행위

==================================================
9. 구 runtimeVersion 대응 조사
==================================================

현재 운영 중인 iOS와 Android 빌드별로 조사하십시오.

- app version
- build number/versionCode
- runtimeVersion
- channel
- 현재 수신 가능한 OTA branch
- 강제 업데이트 기능 포함 여부

강제 업데이트 기능이 없는 구 runtime이 존재하면
각 runtime에서 받을 수 있는 마지막 호환 OTA를 먼저 배포하십시오.

호환 OTA를 받을 수 없는 아주 오래된 네이티브 빌드가 있다면
그 빌드는 앱 내부 모달로 강제할 수 없으므로 별도 대응 방안을 보고하십시오.

==================================================
10. 업데이트 루프 방지
==================================================

다음 무한 반복을 막으십시오.

OTA 확인
→ 다운로드
→ reload
→ 동일 OTA를 다시 신규 업데이트로 인식
→ 다시 reload

다음 값을 기준으로 현재 실행 업데이트를 식별하십시오.

- Updates.updateId
- runtimeVersion
- channel
- isEmbeddedLaunch

동일 updateId는 다시 적용하지 않습니다.

reloadAsync 호출도 1회만 허용하십시오.

==================================================
11. 테스트
==================================================

A. 최신 네이티브 버전
→ 강제 업데이트 모달 없음

B. 최소 버전 미만
→ 닫을 수 없는 강제 업데이트 모달

C. 업데이트 버튼
→ 정확한 Store 페이지 이동

D. Store 업데이트 후 재실행
→ 모달 해제

E. 기존 로그인 상태에서 App Store 업데이트
→ 로그인 유지

F. 기존 로그인 상태에서 OTA
→ reload 후 로그인 유지

G. OTA 존재
→ 모달 표시 → 다운로드 → reload

H. OTA 없음
→ 모달 없음

I. OTA 다운로드 실패
→ 로그인 유지, 재시도 가능

J. 정책 API 장애
→ 앱 전체 차단 및 로그아웃 금지

K. 설정 화면
→ 업데이트 확인 버튼 미표시

L. 내부 함수
→ 자동 체크에서 정상 호출

M. iOS swipe/backdrop dismiss
→ 강제 모달 닫기 불가

N. Android back button
→ 강제 모달 닫기 불가

O. 동일 OTA
→ 재부팅 반복 없음

P. 인증 만료
→ 업데이트 실패와 구분하여 기존 인증 정책대로 처리
