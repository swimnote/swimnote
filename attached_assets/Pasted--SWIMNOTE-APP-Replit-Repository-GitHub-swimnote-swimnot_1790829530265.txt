0. 확정 운영 정책 — 변경 금지
━━━━━━━━━━━━━━━━━━━━━━

매월 발급월 M의 1일:
→ 전월 M-1 리포트 cycle 자동 준비
→ 대상자 산출
→ 분석 시작

1일~4일:
→ snapshot 생성
→ ENGINE 분석
→ 결과 저장
→ retryable 실패 재시도
→ crash/restart recovery
→ 성공 결과 보존
→ 중복 ENGINE/GPT 호출 방지
→ 관리자 검토용 완성 리포트 준비

5일:
→ 관리자 화면에서 해당 월 완성 리포트 전체 목록 확인 가능
→ 관리자에게 월 1회
  "AI 성장리포트 발송 준비가 완료되었습니다"
  성격의 준비완료 PUSH 발송

중요:

5일은 학부모 자동 발행일이 아니다.

관리자가 리포트 목록과 내용을 확인한 후
관리자가 승인/발송 동작을 해야만
학부모에게 공개한다.

관리자 승인/발송 전에는 절대:

- PUBLISHED 전환
- 학부모 성장리포트 본문 공개
- 학부모 feed 노출
- 학부모 PUSH

가 발생하면 안 된다.

관리자는:
- 전체 완성 목록 확인
- 개별 상세 확인
- 개별 발송
- 일괄 발송

이 가능해야 한다.

━━━━━━━━━━━━━━━━━━━━━━
1. 기존 자동 publisher 정책 제거/전환
━━━━━━━━━━━━━━━━━━━━━━

현재 5일 02:00 KST 이후:

REVIEW_REQUIRED
READY_TO_SEND
APPROVED

등의 성공 리포트를 관리자 승인 없이
PUBLISHED로 바꾸는 자동 publisher 경로가 있다.

이 동작을 제거하거나
"관리자 준비완료 처리" 역할로 전환한다.

절대 관리자 승인 없이 PUBLISHED 하지 않는다.

기존 publisher의 유용한 기능:

- eligibility 재검증
- active/nondeleted 재검증
- quality guard
- 중복 방지

는 폐기하지 말고
공통 발행 guard로 재사용한다.

━━━━━━━━━━━━━━━━━━━━━━
2. 관리자 발행을 유일한 학부모 공개 경로로 통일
━━━━━━━━━━━━━━━━━━━━━━

관리자 개별 발송/일괄 발송 경로를
무료 월간 성장리포트의 공식 발행 경로로 통일한다.

발행 직전에 반드시 공통 검증:

- COMPLETE 계열 analysis_status
- eligibility_version >= 현재 V1 기준
- exclusion_code 없음
- recognized lessons >= 3
- student-specific source >= 1
- 유효 report/fact/SNS
- grounding/framing PASS 또는 REVISED_PASS
- 현재 student active
- nondeleted
- 동일 pool
- class-history continuation
- 아직 PUBLISHED 아님

을 수행한다.

수동 send라고 해서
자동 publisher보다 약한 조건으로 발행되면 안 된다.

개별 발송과 일괄 발송 모두
동일한 공통 guard를 사용한다.

━━━━━━━━━━━━━━━━━━━━━━
3. 관리자 준비완료 상태
━━━━━━━━━━━━━━━━━━━━━━

"batch COMPLETED"와
"관리자에게 보여줄 리포트 준비 완료"를 동일하게 취급하지 않는다.

해당 월의 대상 report들을 기준으로
관리자 검토 가능 상태를 계산한다.

다음은 각각 명확하게 구분한다.

- 분석 성공/검토 가능
- 발급조건 미충족 EXCLUDED
- 데이터 부족
- retry 진행 중
- terminal FAILED
- 이미 PUBLISHED

5일까지 처리 가능한 항목을 최대한 완료하고
관리자 화면에서는 각 상태를 정확히 보여준다.

한두 건의 terminal FAILED 때문에
나머지 정상 리포트 전체를 관리자에게 숨기지 않는다.

관리자는:
- 정상 완성 목록
- 제외 수
- 실패 수
- 데이터 부족 수
- 처리 상태

를 구분해서 확인할 수 있어야 한다.

━━━━━━━━━━━━━━━━━━━━━━
4. 관리자 준비완료 PUSH
━━━━━━━━━━━━━━━━━━━━━━

매월 5일 관리자 검토 단계가 열리면
해당 pool 관리자에게 월 1회 준비완료 PUSH를 보낸다.

의미:

"이번 달 AI 성장리포트 발송 준비가 완료되었습니다.
리포트를 확인해 주세요."

정확한 카피는 기존 알림 스타일에 맞춘다.

중복 PUSH 금지.

pool + report_period + notification type 기준으로
멱등성을 보장한다.

서버 restart 또는 job 재실행으로
같은 관리자에게 같은 월 준비완료 PUSH가 반복되면 안 된다.

단, notification 저장 후 실제 PUSH 전송 실패는
재시도 가능한 상태로 관리한다.

━━━━━━━━━━━━━━━━━━━━━━
5. retry terminal 결함 수정
━━━━━━━━━━━━━━━━━━━━━━

현재 retry_count가 max에 도달한 뒤에도
OPEN/READY_FOR_ANALYSIS가 남을 수 있는 결함을 수정한다.

retryable 실패:

attempt 증가
→ max 미만이면 retry 대기
→ max 도달 시 terminal FAILED

로 종료한다.

MAX_RETRY_EXCEEDED를
성공 analyzed 집계에 포함하지 않는다.

FAILED는 자동 분석 대상에서 제외한다.

관리자/명시적 recovery 경로가 아닌 이상
무한 반복하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
6. crash/restart 및 duplicate GPT 비용 보호
━━━━━━━━━━━━━━━━━━━━━━

동일 논리 분석 작업의:

- request_id
- canonical snapshot
- snapshot hash

를 재시도 가능한 형태로 저장/재사용한다.

timeout/crash/watchdog 때문에
같은 입력에 매번 새 request_id와
새 snapshot.created_at/hash를 생성하지 않는다.

동일 report/version/input이면
동일 분석 identity를 재사용한다.

이미 성공 결과가 있으면 ENGINE을 다시 호출하지 않는다.

ENGINE 처리 후 APP 저장 과정에서 crash가 발생해도
가능한 한 동일 request/hash로 recovery한다.

stale CAS 보호는 유지한다.

목표:

같은 논리 작업에 대한
중복 ENGINE/GPT 비용을 APP에서 최대한 차단한다.

10. PUSH 신뢰성
━━━━━━━━━━━━━━━━━━━━━━

학부모 발행 PUSH:

관리자 발송 성공
→ PUBLISHED
→ notification claim
→ PUSH

구조를 멱등하게 유지한다.

notification row가 생성된 뒤
실제 PUSH provider 전송이 실패한 경우에도
재전송 가능한 상태를 갖도록 보완한다.

PUBLISHED 자체는 PUSH 실패로 rollback하지 않는다.

동일 학부모/동일 report에
중복 PUSH는 보내지 않는다.

관리자 준비완료 PUSH에도 같은 원칙을 적용한다.
