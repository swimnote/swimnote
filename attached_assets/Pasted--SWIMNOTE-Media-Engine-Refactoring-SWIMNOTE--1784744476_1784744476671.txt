# SWIMNOTE Media Engine Refactoring 최종 구현 지시문

이번 작업은 단순 버그 패치가 아니라
SWIMNOTE의 사진·미디어 구조를 장기적으로 안정화하는 핵심 리팩토링입니다.

기존 조사 보고서와 Media Engine 설계안을 기준으로 구현하되,
아래 수정 원칙을 반드시 반영하세요.

이번 작업의 목표는 다음과 같습니다.

1. 사진 중복, 누락, 삭제 사진 재표시를 완전히 제거
2. Teacher와 Parent가 동일한 Media Engine을 사용
3. 사진 업로드와 일지 작성이 거의 동시에 체감되도록 응답속도 개선
4. 일지 작성 중 UI가 멈추지 않도록 비동기 구조 개선
5. 일지뿐 아니라 앨범, 공지, 쪽지, 영상까지 확장 가능한 범용 Media Engine 구축
6. 기존 앱 기능과 현재 사용자 흐름을 최대한 유지하면서 안전하게 전환

==================================================
0. 작업 원칙
==================================================

- 증상만 개별 수정하지 마세요.
- photo_assets_meta를 미디어의 단일 Source of Truth로 사용하세요.
- 기존 데이터를 손상시키지 마세요.
- DB 변경과 API 변경은 하위 호환성을 고려하세요.
- 기존 화면이 갑자기 동작하지 않도록 단계적으로 전환하세요.
- 중간 실패로 일지만 저장되거나 사진만 연결되는 불완전 상태가 생기지 않도록 하세요.
- 구현 전 현재 코드 기준으로 변경 영향 범위를 다시 확인하세요.
- 구현 후 반드시 회귀 테스트와 성능 측정을 수행하세요.

==================================================
1. 최종 Media 데이터 규칙
==================================================

photo_assets_meta를 모든 미디어 연결의 기준으로 사용합니다.

공통 일지 사진:

journal_id = diary_id
student_note_id = NULL
student_id = NULL
media_status = 'attached'

학생 개인 일지 사진:

journal_id = diary_id
student_note_id = note_id
student_id = student_id
media_status = 'attached'

업로드 완료 후 아직 일지에 연결되지 않은 사진:

journal_id = NULL
student_note_id = NULL
media_status = 'draft'

일지에서 분리됐지만 파일은 유지하는 사진:

journal_id = NULL
student_note_id = NULL
media_status = 'detached'

삭제 또는 장기 미사용 사진:

media_status = 'archived'

모든 Teacher·Parent 일지 조회는
media_status = 'attached'인 사진만 반환해야 합니다.

status 컬럼을 이미 다른 용도로 사용 중이면
충돌 여부를 확인한 뒤 media_status 컬럼을 별도로 추가하세요.

==================================================
2. Media UUID
==================================================

모든 미디어 레코드는 변경되지 않는 고유 식별자를 가져야 합니다.

기존 photo_assets_meta.id가 이미 전역적으로 유일하고
업로드·재연결·삭제·복구 과정에서도 절대 변경되지 않는다면
그 값을 media_uuid로 사용해도 됩니다.

그 조건이 보장되지 않으면 media_uuid 컬럼을 추가하세요.

media_uuid는 다음에 사용합니다.

- 중복 제거
- Optimistic UI와 서버 응답 매칭
- 재시도
- 삭제
- 복구
- 캐시 업데이트
- 업로드 중복 방지

동일 media_uuid가 동일 일지 조회 결과에 두 번 포함되지 않도록 보장하세요.

==================================================
3. Reservation 방식의 임시 사진 구조
==================================================

기존 auto-attach를 단순 제거하지 마세요.

SWIMNOTE 현장에서는 선생님이 수업 중 사진을 여러 번 촬영한 뒤
수업이 끝난 후 일지를 작성할 수 있습니다.

따라서 업로드된 사진을 임시 예약 상태로 보관하세요.

업로드 시 다음 정보를 저장하세요.

- pool_id
- class_id
- lesson_date
- uploaded_by
- media_status = 'draft'
- reservation_key 또는 동일 목적의 식별 정보
- created_at

일지 작성 화면에서는 해당 조건에 맞는 draft 사진을 즉시 불러옵니다.

조건 예시:

- 동일 pool_id
- 동일 class_id
- 동일 lesson_date
- 동일 업로더 또는 해당 반 접근 권한
- media_status = 'draft'

단, 자동으로 일지에 강제 연결하지 마세요.

작성 화면에서 자동으로 후보 사진을 보여주되,
선생님이 제외하거나 선택을 확인할 수 있어야 합니다.

일지 저장 시 실제 선택된 사진만 attached 상태로 전환하세요.

5. 사진 조회 규칙 통일
==================================================

Teacher와 Parent는 동일한 getDiaryPhotos 결과를 사용하세요.

기본 조회:

SELECT pam.*
FROM photo_assets_meta pam
JOIN class_diaries cd
  ON cd.id = pam.journal_id
 AND cd.is_deleted = false
WHERE pam.journal_id = $diaryId
  AND pam.pool_id = $poolId
  AND pam.media_status = 'attached'

공통사진:

student_note_id IS NULL
AND student_id IS NULL

개인사진:

student_note_id IS NOT NULL
AND student_id IS NOT NULL

Teacher:

- 해당 반 또는 일지에 접근 권한이 있으면 공통+개인 전체 조회 가능

Parent:

- 공통사진 전체
- 개인사진은 자신의 자녀 student_id에 해당하는 것만 반환

Parent 필터는 student_note_id만 보지 말고
student_id와 note/diary 관계를 함께 검증하세요.

==================================================
6. 일지 삭제 규칙
==================================================

일지 삭제 시 연결된 사진을 그대로 attached 상태로 남기지 마세요.

권장 규칙:

- class_diaries.is_deleted = true
- 해당 diary_id의 photo_assets_meta:
  - journal_id = NULL
  - student_note_id = NULL
  - media_status = 'detached'
- student_id는 원본 개인앨범 소속 보존이 필요하면 유지 가능
- 일지 조회 API에서는 detached 사진을 절대 반환하지 않음
- 앨범에서는 detached 사진을 다시 선택 가능

삭제 작업과 사진 해제는 하나의 DB transaction 안에서 처리하세요.

중간 실패 시 전체 rollback해야 합니다.

7. 일지 저장 Transaction
==================================================

기존의

POST /diaries
→ diary-attach
→ note-attach

분리 구조에서 발생할 수 있는 불완전 상태를 제거하세요.

가능하면 서버에 통합 저장 서비스 또는 통합 endpoint를 만드세요.

예시:

POST /diaries/with-media

Body:

{
  class_group_id,
  lesson_date,
  common_content,
  student_notes: [
    {
      student_id,
      note_content,
      photo_ids
    }
  ],
  common_photo_ids
}

서버 transaction:

1. class_diaries INSERT
2. student notes INSERT
3. common photo attach
4. student photo attach
5. audit log 기록
6. commit

어느 단계에서든 실패하면 전체 rollback하세요.

기존 POST /diaries는 하위 호환을 위해 유지할 수 있지만,
신규 클라이언트는 통합 저장 방식을 사용하도록 전환하세요.

8. 업로드 성능 구조
==================================================

사용자는 사진 업로드가 끝날 때까지 화면이 멈추는 느낌을 받아서는 안 됩니다.

최종 흐름:

1. 사진 선택 또는 촬영
2. localUri로 즉시 미리보기 표시
3. 백그라운드 presign 요청
4. 여러 사진 병렬 업로드
5. 업로드 완료 후 서버 photo record 확정
6. 일지 저장 시 batch attach
7. React Query cache 즉시 업데이트
8. 백그라운드 서버 재검증

여러 장 업로드 시 순차 업로드하지 말고
적절한 동시성 제한을 둔 병렬 업로드를 사용하세요.

권장 동시 업로드 수:

- 3~5개

네트워크가 느린 경우에도
텍스트 입력과 화면 조작은 계속 가능해야 합니다.

10. React Query 기반 캐시 통합
==================================================

직접 Map 기반 캐시를 새로 만들지 마세요.

기존 앱이 React Query를 사용 중이면
queryClient를 단일 캐시 계층으로 사용하세요.

권장 query key:

['diary-media', diaryId]

['draft-media', poolId, classId, lessonDate]

['student-diary-media', diaryId, studentId]

필수 사용:

- queryClient.setQueryData
- queryClient.invalidateQueries
- mutation onMutate
- mutation onError
- mutation onSettled

attach 성공 직후 setQueryData로 화면을 즉시 갱신하고,
백그라운드 invalidate로 서버 상태를 확인하세요.

Teacher와 Parent가 같은 query key를 무조건 공유할 필요는 없지만,
같은 Media DTO와 동일한 MediaService 결과를 기반으로 해야 합니다.

권한에 따라 응답 범위가 다르므로
Parent 캐시는 studentId를 포함해 분리하세요.

15. 기존 버그 수정
==================================================

반드시 아래 7개 버그를 모두 해결하세요.

버그 1:
GET /photos/group/:classId?date=의 삭제 일지 필터 누락

조치:
- class_diaries.is_deleted = false 필수
- attached 사진은 journal_id 기준으로 조회
- draft 사진은 class_id + lesson_date + media_status='draft'로 별도 조회
- OR 조건으로 attached와 draft를 섞지 말 것

버그 2:
일지 삭제 후 photo_assets_meta.journal_id 유지

조치:
- transaction 안에서 detached 처리

버그 3:
note-attach 시 student_id 미설정

조치:
- student_note_id, student_id, journal_id 동시 설정
- note와 student 관계 검증

버그 4:
selectedAlbumIds와 selectedAlbumPhotos 상태 불일치

조치:
- useDiaryMedia 단일 상태로 통합

버그 5:
attach 완료 후 PhotoStrip 즉시 갱신 안 됨

조치:
- mutation 성공 즉시 React Query setQueryData
- 이후 background invalidate

버그 6:
classGroupId 파라미터만으로 router.back 실행

조치:
- classGroupId 존재 여부를 외부 진입 판단 기준에서 제거
- 명시적 backTo 또는 returnTo 파라미터만 사용
- 기본 저장 후 history 화면 유지

버그 7:
Parent UNION 중복

조치:
- diary_id 기준 dedup
- DISTINCT ON 또는 ROW_NUMBER 사용
- 같은 diary_id는 한 번만 반환
- is_makeup_diary는 별도 계산

18. 범용 Media Engine 구조
==================================================

MediaService를 일지 전용 이름과 구조로 제한하지 마세요.

21. 성능 목표
==================================================

개발 환경과 실제 네트워크 차이를 구분해서 측정하세요.

목표 체감 성능:

- 사진 선택 후 local preview: 100ms 이내
- 일지 저장 버튼 후 history 화면 전환: 300ms 이내
- 텍스트 일지 서버 저장: 일반 조건 1초 이내
- attach 완료 후 UI 반영: 완료 즉시 또는 200ms 이내
- 사진 4장 업로드: 네트워크 제외 앱 UI 블로킹 없음
- 목록 API: 일반 데이터 기준 500ms 내외 목표
- PhotoStrip 캐시 hit: 즉시 표시

사진 파일 실제 업로드 시간은 네트워크와 파일 크기에 따라 달라질 수 있으므로,
업로드가 진행 중이어도 사용자는 일지 작성과 화면 이동을 계속할 수 있어야 합니다.

22. 테스트 시나리오
==================================================

아래 시나리오를 모두 자동 또는 수동 테스트하세요.

1.
공통사진 2장 + 개인사진 2장 저장
→ Teacher 총 4장
→ 해당 Parent는 공통 2장 + 본인 자녀 개인사진만 표시

2.
일지 삭제
→ 기존 일지 화면에서 사진 미노출
→ 같은 날짜 새 일지 작성 시 이전 사진 자동 혼입 없음
→ detached 사진은 앨범에서 재선택 가능

3.
그룹사진을 특정 학생 개인사진으로 연결
→ student_id와 student_note_id 모두 설정
→ 해당 학부모에게 표시
→ 다른 학부모에게 미표시

4.
앨범 선택 모달 여러 번 진입
→ 기존 선택 유지
→ 선택 해제 정확
→ ID와 객체 상태 불일치 없음

5.
사진 attach 완료
→ 화면 재진입 없이 PhotoStrip 즉시 갱신

6.
미작성 일지 화면에서 진입
→ 저장 후 history 유지
→ 명시적 backTo가 있을 때만 지정 화면 복귀

7.
정규 수업과 보강이 같은 diary를 참조
→ Parent 목록에 한 번만 표시

8.
업로드 중 앱 화면 이동
→ draft 유지
→ 복귀 시 진행 상태 복원

9.
사진 10장 동시 업로드
→ UI 멈춤 없음
→ 실패한 사진만 재시도 가능
→ 중복 레코드 없음

10.
서버 저장 중 한 단계 실패
→ transaction rollback
→ 불완전 diary/media 연결 없음

24. 구현 승인
==================================================

위 방향으로 구현을 진행하세요.

최종 결정:

- 일지 삭제 시 사진은 제거하지 않고 detached 상태로 보존
- 기존 단순 auto-attach는 제거
- 대신 class_id + lesson_date 기반 Reservation/draft 후보 시스템 적용
- 사진은 선생님이 작성 화면에서 확인한 항목만 실제 일지에 연결
- 캐시는 직접 Map이 아니라 React Query 사용
- 일지·노트·사진 연결은 가능한 한 단일 DB transaction으로 처리
- MediaService는 일지 전용이 아니라 향후 확장 가능한 범용 구조로 설계
- 현재 앱의 사용자 흐름은 유지하되 저장 후 history 화면을 기본값으로 사용

Phase 1부터 순서대로 구현하고,
각 Phase 완료 시 변경사항과 테스트 결과를 보고한 뒤 다음 단계로 진행하세요.
