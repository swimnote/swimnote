Replit 크레딧을 아끼기 위해
퇴원처리와 직접 연결된 코드만 따라간다.

━━━━━━━━━━━━━━━━━━━━━━
1. 현재 퇴원 버튼 위치 확인
━━━━━━━━━━━━━━━━━━━━━━

APP에서 실제 퇴원처리를 실행할 수 있는 위치만 찾는다.

반드시 확인:

A. 관리자 회원/학생정보 화면
B. 선생님 회원/학생정보 화면
C. 스케줄러에서 학생을 눌렀을 때 나오는 화면

특히 스케줄러는 다음 중 현재 어느 구조인지 확인한다.

- 스케줄러에서 바로 퇴원 가능
- 스케줄러 → 학생/회원정보 → 퇴원 가능
- 퇴원 기능 자체가 없음

추가 퇴원 버튼이 발견되면 위치만 보고한다.

UI 전체를 조사하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
2. “버튼 눌러도 반응 없음” 원인 추적
━━━━━━━━━━━━━━━━━━━━━━

실제로 존재하는 각 퇴원 버튼에 대해서만:

버튼
→ onPress
→ handler
→ API 호출
→ 서버 route
→ 실제 퇴원 처리

경로를 짧게 추적한다.

다음 중 어디가 문제인지 특정한다.

- 버튼 handler 미연결
- confirmation/modal 문제
- APP 함수 오류
- API 호출 안 됨
- 잘못된 endpoint/payload
- 권한 문제
- 서버 오류
- DB 처리 오류
- 처리됐지만 화면 refresh가 안 됨
- 기타

추측하지 말고 코드 근거로 판정한다.

━━━━━━━━━━━━━━━━━━━━━━
3. 기존 SWIMNOTE 퇴원 정책 확인
━━━━━━━━━━━━━━━━━━━━━━

새 정책을 만들지 않는다.

현재 코드/DB에 이미 구현되어 있거나
프로젝트 내부에 명시된 기존 퇴원 정책만 확인한다.

최소 확인:

- 퇴원 시 학생 status가 어떻게 되는지
- 반/수업 배정은 어떻게 되는지
- 학부모와 학생 연결은 어떻게 되는지
- 퇴원 직후 학부모 앱에서 해당 학생이 계속 보이는지/숨겨지는지
- 퇴원 후 학생/학부모 정보 보존기간이 존재하는지
- 내가 기억하는 “약 1개월 후 정보 삭제” 정책이 실제 코드 또는 프로젝트 자료에 존재하는지

30일이라고 임의로 가정하지 않는다.

기간이 코드에 있으면 정확한 기간과 위치만 보고한다.

삭제/cleanup scheduler가 실제 퇴원 흐름에 연결돼 있을 때만 확인한다.
관련이 없으면 더 조사하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
4. 다자녀 학부모만 안전성 확인
━━━━━━━━━━━━━━━━━━━━━━

퇴원 학생에게 형제/자매가 있고
같은 학부모 계정에 연결되어 있을 경우:

한 학생 퇴원 때문에
다른 재원 학생이나 학부모 계정 전체가
삭제/차단되는 구조인지 아닌지만 확인한다.

관련 없는 개인정보 삭제 체계 전체를 조사하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
5. 권한 확인
━━━━━━━━━━━━━━━━━━━━━━

현재 코드상:

- 관리자 퇴원 가능 여부
- 선생님 퇴원 가능 여부

만 확인한다.

사용자 요구 목표는
관리자와 허용된 선생님이 학생정보에서
정상적으로 퇴원처리할 수 있는 것이다.

현재 구현과 다르면 차이만 보고한다.

━━━━━━━━━━━━━━━━━━━━━━
6. Production에서는 읽기만
━━━━━━━━━━━━━━━━━━━━━━

필요한 경우에만 Production을 READ-ONLY로 확인한다.

실제 회원 퇴원 테스트 금지.
실제 데이터 수정 금지.

코드만으로 원인이 확인되면
Production 추가 조사도 하지 않는다.
