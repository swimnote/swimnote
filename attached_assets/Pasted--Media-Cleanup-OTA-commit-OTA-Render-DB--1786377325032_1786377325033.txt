[긴급 재조사 — Media Cleanup OTA 후 앱 용량이 전혀 감소하지 않음]

중요:
수정/commit/OTA/Render/DB 변경 금지.
이번 단계는 원인 측정만 한다.

현재 상황:

Media cleanup OTA를 production에 배포했으나
실제 여러 선생님 기기에서 앱 저장공간이 그대로다.

예:
- 현재 사용자 기기 약 3.62GB 그대로
- 다른 선생님 기기들도 cleanup 전후 용량 변화 없음
- 기존에는 6GB / 22GB 사례도 확인됨

따라서 기존 원인 확정을 폐기하지는 않되,
"documentDirectory의 diary_*/swim_*가 전체 대용량의 주범"
이라는 가정은 다시 검증한다.

1. Cleanup 실제 실행 여부부터 확인
━━━━━━━━━━━━━━━━━━━━━━

현재 production OTA에 들어간:

runLegacyMediaCleanup()

의 실제 실행 경로를 조사.

확인:

A. RootNav가 실제 production 앱 시작 시 mount 되는가
B. useEffect가 실행되는가
C. cleanup 호출 전에 return/조건문이 있는가
D. FileSystem API가 현재 Expo 55 / expo-file-system 버전에서
   실제 정상 작동하는 API인가
E. exception이 발생해도 현재
   .catch(() => {})
   때문에 완전히 숨겨지고 있지 않은가

현재 코드는 오류를 삼키고 있으므로
"실행됐다고 코드상 보인다"는 답변 금지.

실제 성공 여부를 확인할 방법을 찾아라.

2. cleanup flag 조사
━━━━━━━━━━━━━━━━━━━━━━

@swimnote:media_cleanup_v1

정확한 저장값과 기록 조건 조사.

확인:

- cleanup 시작 전에 flag가 찍히는지
- directory scan 실패인데도 flag가 찍힐 가능성
- matched=0인데 completed 처리되는지
- failed=0 / matched=0 상황에서 completed 처리되는지
- 이미 flag=true인 기기는 다시 검사하지 않는지

특히:

"cleanup이 아무 파일도 못 찾았는데
completed=true가 되어 영원히 재실행되지 않는 구조"

가능성 반드시 확인.

6. Cache가 실제 주범인지 재조사
━━━━━━━━━━━━━━━━━━━━━━

실제 여러 기기에서 GB 단위가 그대로이므로 재검증.

특히 SWIMNOTE는 일지/앨범에서
많은 사진을 반복 조회한다.

- expo-image 실제 cachePolicy 기본값
- disk cache 사용 여부
- cacheDirectory 위치
- cache TTL/size 제한
- clearDiskCache API 존재 여부
- 앱별 cache가 iOS Settings의
  Documents & Data에 포함되는지

그리고 현재 SWIMNOTE에서
사진/영상 조회만으로 cache가 누적될 수 있는지 다시 판정.
