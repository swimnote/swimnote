# 관리자 권한 부여·회수 기능 수정 전 최종 설계 검증 요청

현재 제출한 진단과 수정 계획은 일부 방향은 맞지만,
관리자 권한 회수의 즉시 효력과 role/roles/JWT 관계가 충분히 검증되지 않았습니다.

이 기능은 실제 운영 권한과 연결된 중요 기능이므로
지금 바로 수정하지 마세요.

먼저 아래 항목을 코드와 DB 구조 기준으로 다시 조사하여
최종 실행 계획서를 제출하세요.

==================================================
1. 현재 권한 구조 전체 조사
==================================================

다음 값이 각각 어떤 의미로 사용되는지 확인하세요.

- users.role
- users.roles
- JWT의 role
- JWT의 roles
- 앱의 현재 모드
- 로그인 응답의 역할 정보
- 관리자 API 인증 미들웨어
- 선생님 API 인증 미들웨어

각 값에 대해 다음을 보고하세요.

1. 어디서 저장되는지
2. 어디서 변경되는지
3. 어디서 권한 판단에 사용되는지
4. 앱 화면 전환에 어떤 값이 사용되는지
5. 서버 API 접근 허용에 어떤 값이 사용되는지

role과 roles 중 어느 것이

- 계정의 보유 권한
- 현재 선택한 모드

인지 명확하게 정의하세요.

현재 두 필드가 서로 다른 권한 판단에 혼용되고 있다면
해당 위치를 전부 보고하세요.

==================================================
2. 기존 진단 내용 재검증
==================================================

현재 보고된 문제:

1. handleGrant에 catch가 없어 오류 메시지가 표시되지 않음
2. 취소 버튼이 배경과 구분되지 않음
3. 권한 부여 시 roles만 갱신되고 role은 teacher로 유지됨
4. 관리자 모드로 바뀐 교사가 목록 조회에서 제외됨
5. 회수 시 roles에서만 제거되어 실제 관리자 모드가 남을 수 있음

각 항목을 실제 코드 위치와 함께 다시 확인하세요.

단순 추측이 아니라 다음을 명시하세요.

- 파일
- 함수
- 조건문
- API
- DB 업데이트문
- 화면에서 발생하는 실제 결과

==================================================
3. JWT 즉시 회수 가능 여부 확인
==================================================

가장 중요한 확인입니다.

현재 JWT가 발급된 뒤 서버가 매 요청마다
DB의 최신 role/roles를 확인하는지 조사하세요.

다음 중 어느 구조인지 명확히 보고하세요.

A.
JWT 내부 권한만 신뢰함

B.
JWT의 userId로 DB 사용자를 매 요청마다 조회하고
최신 role/roles를 검사함

C.
일부 API는 JWT만 사용하고
일부 API는 DB도 조회함

현재 계획서에는

“role을 teacher로 바꾸면 다음 API 호출에서 JWT가 자동 만료된다”

고 되어 있습니다.

이 동작이 실제 코드로 구현되어 있는지 확인하세요.

구현되어 있지 않다면
자동 만료된다고 보고하면 안 됩니다.

==================================================
4. 권한 회수의 즉시 효력 설계
==================================================

관리자가 선생님의 관리자 권한을 회수하면
다음이 즉시 성립해야 합니다.

1. 신규 관리자 API 요청 차단
2. 관리자 화면 신규 진입 차단
3. 현재 관리자 화면 사용 중이라면 선생님 모드로 복귀
4. 관리자 전용 메뉴 제거
5. 기존 선생님 계정과 수업 데이터는 유지
6. 다시 로그인할 때도 관리자 모드가 나타나지 않음

이를 보장하는 방법을 설계하세요.

가능한 구조 예:

- 서버가 관리자 API 요청마다 최신 DB 권한 확인
- 권한 버전 또는 token_version 사용
- 사용자 세션 무효화
- 짧은 access token + refresh token 재검증
- 권한 회수 후 클라이언트 권한 재조회
- 403 또는 ROLE_REVOKED 응답 시 선생님 모드 강제 복귀

현재 프로젝트에 가장 적합하고 변경 범위가 작은 방법을 제안하세요.

단순히 DB의 role만 변경하고
기존 JWT가 알아서 무효화된다고 가정하면 안 됩니다.

==================================================
5. 권한 부여의 실제 동작 확인
==================================================

권한 부여 후 반드시 다음이 가능해야 합니다.

1. roles에 pool_admin 권한 추가
2. 선생님 계정은 유지
3. 선생님 모드와 관리자 모드를 전환 가능
4. 관리자 모드에서 실제 관리자 홈 진입 가능
5. 관리자 API 호출 가능
6. 기존 센터 또는 tenant 범위를 벗어나지 않음
7. 슈퍼관리자 권한은 부여되지 않음

“앱을 재시작해야 한다”는 방식이 반드시 필요한지도 확인하세요.

가능하면 다음 구조를 우선 검토하세요.

권한 부여 완료
→ 현재 사용자 정보 또는 권한 목록 재조회
→ 앱 재시작 없이 모드 전환 메뉴 갱신

앱 재시작이 기술적으로 필수인 경우에만
재시작 안내를 사용하세요.

==================================================
6. 권한 회수 대상이 목록에서 사라지는 문제
==================================================

현재 목록 조건:

AND u.role = 'teacher'

이 조건 때문에 현재 모드가 pool_admin인 사용자가
목록에서 사라진다는 진단을 검증하세요.

다만 단순히 다음처럼 바꾸기 전에:

AND u.role IN ('teacher', 'pool_admin')

이 목록이 실제로 어떤 계정을 조회해야 하는지 정의하세요.

정상 기준:

- 해당 센터에 승인된 선생님 계정
- 관리자 권한이 부여된 선생님도 포함
- 순수 운영자 계정이나 센터 소유자는 제외
- 다른 센터 사용자는 제외
- 슈퍼관리자는 제외

가능하면 role이 아니라
교사 소속 또는 teacher membership 관계를 기준으로 조회하세요.

현재 시스템에서 가장 정확한 소속 기준을 조사해서 계획서에 포함하세요.

==================================================
7. role과 roles의 최종 정책
==================================================

권장 구조를 검토하세요.

예시:

roles
= 사용자가 보유한 역할 목록
예: ["teacher", "pool_admin"]

activeRole 또는 현재 세션 role
= 현재 앱에서 사용 중인 모드
예: "teacher" 또는 "pool_admin"

단일 users.role 컬럼을 현재 모드와 영구 권한 양쪽에
동시에 사용하지 마세요.

현재 DB 구조를 크게 바꾸지 않고 해결할 수 있다면
그 방법을 우선 제안하세요.

DB 변경이 필요하면
마이그레이션 범위와 기존 사용자 영향도 보고하세요.

==================================================
8. 부여 및 회수 API 응답 구조
==================================================

권한 부여 성공 응답에는 최소 다음을 포함하세요.

{
  success: true,
  userId: "...",
  roles: ["teacher", "pool_admin"],
  adminGranted: true,
  activeRole: "teacher",
  requiresReauth: false 또는 true
}

권한 회수 성공 응답에는 최소 다음을 포함하세요.

{
  success: true,
  userId: "...",
  roles: ["teacher"],
  adminGranted: false,
  activeRole: "teacher",
  sessionsInvalidated: true 또는 false
}

클라이언트가 성공 여부를 임의로 추정하지 말고
서버의 최신 권한 상태를 사용하도록 설계하세요.

==================================================
9. UI 멈춤 현상 수정 계획
==================================================

다음 UX를 적용하세요.

실행 전:

- 확인 모달
- 취소 버튼과 실행 버튼 명확히 구분

실행 중:

- 실행 버튼 비활성화
- 로딩 표시
- 중복 요청 방지
- 모달을 임의로 닫지 않음

성공 시:

- 서버 최신 권한 상태로 목록 갱신
- 성공 메시지 표시
- 모달 종료

실패 시:

- 모달 또는 오류 안내 유지
- 실제 HTTP 오류 메시지 표시
- 버튼 다시 활성화
- 목록 상태를 성공한 것처럼 변경하지 않음

handleGrant뿐 아니라
handleRevoke에도 동일한 에러 처리와 중복 탭 방지를 적용하세요.

10. 실제 기능 테스트 계획
==================================================

수정 전 테스트 계획서를 먼저 제출하세요.

테스트 A — 권한 부여

1. 일반 선생님 계정 준비
2. 관리자 권한 부여
3. DB roles 확인
4. 앱 모드 전환 메뉴 확인
5. 관리자 모드 진입
6. 관리자 API 호출 성공 확인
7. 선생님 모드 복귀 확인

테스트 B — 관리자 모드 중 권한 회수

1. 선생님이 관리자 모드 사용 중
2. 원장이 권한 회수
3. 해당 계정의 신규 관리자 API 호출 차단
4. 관리자 화면에서 선생님 모드로 복귀
5. 관리자 메뉴 제거
6. 선생님 수업 기능 유지

테스트 C — 앱 종료 없이 회수

1. 관리자 모드 화면을 켜둔 상태
2. 다른 기기에서 권한 회수
3. 다음 관리자 API 요청 차단
4. ROLE_REVOKED 또는 403 처리
5. 선생님 모드 강제 복귀

테스트 D — 앱 재실행 후 확인

1. 권한 부여 계정 앱 재실행
2. 관리자 모드 표시
3. 권한 회수 계정 앱 재실행
4. 관리자 모드 미표시

테스트 E — 목록 유지

1. 선생님 모드
2. 관리자 권한 보유
3. 현재 관리자 모드 사용 중

세 상태 모두 관리자 추가/승계 목록에서
회수 가능한 대상이면 정상적으로 표시되는지 확인

테스트 F — 네트워크 오류

1. 권한 부여 요청 실패
2. 오류 메시지 표시
3. UI 멈춤 없음
4. 권한이 부여된 것처럼 표시되지 않음

5. 권한 회수 요청 실패
6. 오류 메시지 표시
7. 기존 권한 상태 유지

11. 권한 범위 확인
==================================================

pool_admin 권한을 받은 선생님이
자신이 소속된 센터만 관리할 수 있는지 확인하세요.

다음 접근은 금지되어야 합니다.

- 다른 센터 학생
- 다른 센터 선생님
- 다른 센터 수업
- 다른 센터 결제
- 슈퍼관리자 기능
- 전체 시스템 설정

tenant 또는 pool_id 검증이
각 관리자 API에 적용되어 있는지 계획서에 포함하세요.

12. 수정 범위 제한
==================================================

현재 단계에서는 코드를 수정하거나 배포하지 마세요.

먼저 조사와 계획서만 제출하세요.

예상 변경 범위:

- 관리자 권한 부여/회수 화면
- 권한 부여/회수 API
- 교사 목록 조회
- 서버 인증 및 권한 미들웨어
- 앱 역할 전환 또는 권한 재조회 처리

필요하지 않은 다음 기능은 건드리지 마세요.

- 학생 관리
- 학부모 연결
- 일지
- 출결
- 반배정
- 결제
- 보강
- 알림
- 슈퍼관리자 기능
