[SWIMNOTE — Multi-Pool Membership 계정 구조 개편 / 관리자·선생님·학부모 공통]

목표:

현재 SWIMNOTE 회원가입/로그인 구조를 수정하여
한 사용자 계정이 여러 수영장에 동시에 가입할 수 있도록 한다.

대상 역할:

- 관리자
- 선생님
- 학부모

모두 동일한 Multi-Pool Membership 구조를 사용한다.

==================================================
0. 최종 정책
==================================================

SWIMNOTE의 사용자 계정과 수영장 소속을 분리한다.

구조:

USER ACCOUNT
  ↓
POOL MEMBERSHIP
  ↓
ROLE

예:

user_001
  ├─ pool_A / admin
  ├─ pool_B / teacher
  ├─ pool_C / teacher
  └─ pool_D / parent

즉 한 사람이:

- 여러 수영장을 운영할 수 있음
- 여러 수영장에서 파트타임 선생님으로 일할 수 있음
- 여러 수영장에 자녀를 보낼 수 있음
- 수영장별로 서로 다른 역할을 가질 수 있음

==================================================
1. 로그인 ID 정책
==================================================

login_id / username은 시스템 전체에서 UNIQUE.

동일 login_id 중복 생성 금지.

하지만:

- 전화번호가 같다는 이유
- 이름이 같다는 이유
- 다른 수영장에 이미 가입했다는 이유
- 기존 수영장에서 퇴원/퇴사 처리가 안 됐다는 이유

로 신규 수영장 가입을 막지 않는다.

중요:

사용자 Account는 전역 사용자다.

수영장 가입 여부는 별도 Membership으로 판단한다.

==================================================
2. 기존 구조 먼저 감사
==================================================

코드 수정 전에 현재 repository/DB에서 다음 실제 구조를 확인한다.

- users
- swimming_pools
- admins
- teachers
- parents
- parent/student relation
- teacher invitation
- admin signup
- parent signup
- login/auth
- JWT
- pool_id
- role
- currentPool/currentRole 관련 상태
- middleware / authorization
- DB UNIQUE constraints

현재 user row에:

pool_id
role

등이 직접 묶여 있다면
어디에서 사용되는지 전수 확인.

추측하지 않는다.

==================================================
3. Membership 데이터 모델
==================================================

기존 schema와 충돌하지 않는 가장 작은 변경으로 구현한다.

권장 개념:

user_pool_memberships

최소:

id
user_id
pool_id
role
status
created_at
updated_at

role:

admin
teacher
parent

필요하면 현재 앱의 실제 role enum을 그대로 따른다.

UNIQUE:

(user_id, pool_id, role)

동일 사용자가
같은 pool / 같은 role membership을 중복 생성하는 것만 막는다.

다른 pool은 허용.

==================================================
4. 같은 Pool에서 복수 Role
==================================================

같은 사람이 같은 수영장에서:

admin + parent

teacher + parent

등 복수 역할을 가질 수 있도록
DB 구조상 막지 않는다.

단 UI/현재 제품 정책상 아직 필요하지 않은 경우에도
데이터 구조는 복수 role을 지원하도록 한다.

==================================================
5. 기존 사용자 Migration
==================================================

기존 사용자를 깨지 않도록 migration한다.

현재 각 user의 기존:

pool
role

정보를 읽어

user_pool_memberships

에 1:1 초기 membership 생성.

검증:

기존 사용자 수
기존 role/pool 연결
생성 membership 수

누락 = 0

기존 로그인은 migration 후에도 그대로 동작해야 한다.

==================================================
6. 기존 데이터 삭제 금지
==================================================

이번 migration에서:

users 삭제 금지
students 삭제 금지
classes 삭제 금지
class_diaries 삭제 금지
parent/student links 삭제 금지
teacher data 삭제 금지
admin data 삭제 금지

기존 컬럼이 legacy가 되더라도
이번 작업에서 바로 DROP하지 않는다.

신규 membership 구조 안정화 후
별도 청소 작업으로 처리한다.

==================================================
7. Authentication
==================================================

로그인은 USER ACCOUNT 기준.

로그인 성공 후:

이 사용자가 접근 가능한 membership 목록을 가져온다.

예:

[
  { pool_id: A, role: admin },
  { pool_id: B, role: teacher },
  { pool_id: C, role: parent }
]

사용자가 마지막으로 사용한 pool/role이 유효하면
그 context로 진입.

없으면:

membership 1개
→ 자동 진입

membership 2개 이상
→ 수영장/역할 선택 화면 또는 선택 UI 제공

==================================================
8. 현재 Context
==================================================

앱 runtime에서 반드시:

currentPoolId
currentRole

을 명확하게 관리한다.

중요:

user.role
user.pool_id

를 전역 단일값처럼 믿는 기존 코드가 있으면
membership context 기준으로 변경.

==================================================
9. Authorization 보안
==================================================

클라이언트가 pool_id를 보냈다는 이유만으로 허용하지 않는다.

모든 pool-scoped API는:

authenticated user
+
requested/current pool
+
required role

을 membership DB에서 확인한다.

예:

관리자 API:

user_pool_memberships에서

user_id
pool_id
role=admin
active

membership 존재 확인.

선생님 API도 동일.

학부모 API도 동일.

다른 pool 데이터 접근 차단.

Tenant isolation 절대 유지.

==================================================
10. 관리자 회원가입
==================================================

기존 계정이 없는 경우:

Account 생성
→ Pool 생성/선택
→ admin membership 생성

기존 계정이 있는 경우:

새 Account 중복 생성이 아니라
기존 Account에 새 pool의 admin membership을 추가할 수 있어야 한다.

여러 지점 운영:

한 Account에서 여러 admin memberships 가능.

==================================================
11. 선생님 가입 / 초대
==================================================

선생님 초대코드 또는 현재 실제 초대 방식 유지.

기존 사용자라면:

Account 중복 생성 금지
→ 해당 pool에 teacher membership 추가

신규 사용자라면:

Account 생성
→ teacher membership 추가

A수영장 teacher라고 해서
B수영장 teacher 가입을 막지 않는다.

==================================================
12. 학부모 가입
==================================================

학부모도 동일.

기존 계정이 있더라도
새로운 수영장에 parent membership 추가 가능.

A수영장에서 자녀 연결이 남아 있어도
B수영장 가입/인증 가능.

기존 수영장이:

퇴원처리 안 함
연결 해제 안 함
학생 record 유지

상태여도 다른 pool 가입에 영향 없어야 한다.

==================================================
13. Parent ↔ Student 연결
==================================================

Student는 pool tenant별 별도 record 유지.

같은 실제 아이가:

Pool A
student_A

Pool B
student_B

로 존재할 수 있음.

자동 merge 금지.

A수영장의:

일지
사진
출결
성장데이터

를 B수영장과 공유하지 않는다.

Parent Account만 두 membership에 접근할 수 있다.

==================================================
14. 수영장 전환 UI
==================================================

membership이 2개 이상이면
현재 앱의 적절한 공통 위치에:

현재 수영장 ▼

전환 기능을 제공한다.

표시 예:

토이키즈스윔클럽
비타스위밍
ABC수영장

선택하면:

currentPoolId 변경
→ 해당 pool에 존재하는 role 확인
→ 해당 role UI/data reload

==================================================
15. Role 전환
==================================================

동일 pool에서 role이 여러 개인 사용자라면:

현재 역할 전환 지원.

예:

토이키즈스윔클럽
  관리자
  학부모

단 기존 UI 구조를 불필요하게 크게 변경하지 말고
현재 navigation architecture에 가장 작은 방식으로 추가.

==================================================
16. 로그인 직후 동작
==================================================

Membership 0개:

가입/수영장 연결 안내

Membership 1개:

자동 진입

Membership 여러 개:

마지막 사용한 유효 membership이 있으면 자동 복원.

처음이거나 저장값이 무효면
수영장 선택.

==================================================
17. last selected membership
==================================================

가능하면 Account 또는 local secure storage에:

last_pool_id
last_role

저장.

단 서버 authorization에는 절대 이 값을 신뢰하지 않는다.

UI convenience 용도만.

==================================================
18. 회원가입 중복 판정 수정
==================================================

현재 signup에서 다음 같은 중복 차단이 존재하는지 전수 조사:

phone already exists
parent already belongs to pool
teacher phone exists
admin phone exists
student guardian exists

각 validation을 분리한다.

Account uniqueness와
Pool Membership uniqueness를 혼동하지 않는다.

중복 판정:

login_id already used
→ 차단

같은 user + 같은 pool + 같은 role
→ 이미 가입된 수영장 안내

같은 user + 다른 pool
→ 허용

같은 user + 같은 pool + 다른 role
→ 허용

==================================================
19. 전화번호 정책
==================================================

전화번호는 인증/연결에 사용할 수 있지만
"한 전화번호 = 한 수영장" 제약을 두지 않는다.

현재 DB에 phone UNIQUE constraint가 있다면
왜 필요한지 조사.

로그인 ID가 별도 존재하고
제품 보안상 phone 전역 UNIQUE가 필요하지 않다면
multi-pool 가입을 막는 constraint를 제거/완화.

단 기존 인증 흐름 영향 확인 후 수행.

==================================================
20. JWT / Session
==================================================

JWT 안에 단일 pool_id / role을 영구 계정 속성처럼 넣고 있다면 수정 검토.

권장:

user_id = identity

pool_id / role = active membership context

서버에서 membership 재검증.

기존 token contract를 최대한 깨지 않도록
backward-compatible하게 변경.

{

POST /me/context

또는 앱 로컬 context 전환 방식 사용.

현재 architecture에 더 적합한 방법 선택.

22. 가입 UX
==================================================

회원가입/수영장 추가 개념을 분리한다.

기존 Account 보유자는
"새 회원가입"을 반복하는 대신:

수영장 추가
또는
초대코드 입력

으로 membership을 추가할 수 있게 한다.

단 기존 회원가입 entry에서도
이미 존재하는 Account를 감지하면
로그인 후 수영장 추가 경로로 자연스럽게 연결.

==================================================
23. 기존 사용자의 UX 회귀 금지
==================================================

현재 한 수영장만 사용하는 대부분 사용자는
기존과 거의 동일하게 보여야 한다.

membership 1개면
불필요한 pool 선택 화면을 매번 보여주지 않는다.

24. 테스트 시나리오
==================================================

반드시 E2E:

A.
1 user
Pool A admin
Pool B admin
→ 둘 다 접근 가능

B.
1 user
Pool A teacher
Pool B teacher
Pool C teacher
→ 세 곳 전환 가능

C.
1 user
Pool A parent
Pool B parent
→ 양쪽 student 각각 접근 가능
→ 데이터 혼합 없음

D.
1 user
Pool A admin
Pool B teacher
Pool C parent
→ role별 UI 정상

E.
같은 user + same pool + same role 재가입
→ 중복 membership 생성 안 됨

F.
같은 user + same pool + 다른 role
→ 가능

G.
다른 사용자가 동일 login_id 가입
→ 차단

H.
Pool A 사용자가 임의로 Pool B API 호출
membership 없음
→ 403

I.
기존 단일 pool 사용자
→ 로그인 회귀 없음
