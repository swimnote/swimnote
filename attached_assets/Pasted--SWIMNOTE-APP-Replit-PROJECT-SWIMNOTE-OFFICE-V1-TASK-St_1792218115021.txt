2. 완료 기록의 보존·재실행 정책 보완

현재 구조에서 다음을 실제 코드로 확인한다.
- 이미 완료된 요청의 기록이 삭제된 뒤
  같은 유효 request ID로 실행 요청이 오면 어떻게 되는가.
- client 재전송 차단 외에 서버가 중복 실행을 막을 근거가 있는가.
- request ID 시각을 caller가 임의 변경할 수 있는 범위.
- 재확인 24시간과 서버의 실행 수락 기간이 어떻게 연결되는가.

기록 부재를 “처음 요청”으로 간주하여 재실행할 수 있다면
그 위험을 단순 문서 경고만으로 종료하지 않는다.

기존 구조로 보장 가능한 최소 수정안을 적용한다.
내구성 있는 별도 receipt/tombstone 저장이 필요하면
schema·migration 초안과 테스트를 로컬 파일로 준비한다.
운영 DB에는 적용하지 않는다.
새 저장 구조를 도입할 경우 기존 테이블 활용과 비교해 근거를 남긴다.

완료 기록에는 불필요한 개인정보 원문을 저장하지 않는다.
보존·삭제 정책과 중복 방지 보장 기간을 일치시킨다.
무기한 또는 전역 exactly-once를 주장하지 않는다.

3. 신규 실행 중단과 결과 확인 분리

- AI 해석 중단.
- 신규 업무 변경 중단.
- 기존 요청의 결과 조회.

위 세 동작을 분리한다.

이미 발급된 요청의 결과를 읽기 전용으로 확인할 수 있도록
최소 receipt 조회 경로를 마련한다.

권한 회수·사용자 비활성화·다른 Pool 요청은 계속 차단한다.
구 서버로 rollback하면 조회 경로 자체가 없을 수 있다는 한계는 유지.
결과 조회 실패·기록 없음·기간 만료를 미처리로 해석하지 않는다.

대신 관련 writer 목록과 실제 적용 가능한 경계를 명시한다.

첫 쓰기 수용은:

현재 계정은 실제 운영 계정이므로 테스트 대상으로 전환하지 않는다.
운영 회원 생성·수정·반이동·삭제 금지.

운영 인증을 우회하는 코드가 제품에 들어가지 않게 분리한다.
