2. 1.6.3 일반가입 전화번호 분기
============================================================

기존 일반 학부모 가입 flow는 최대한 유지.

전화번호 입력/검증 시:

normalized_phone 계산.

서버에서:

same swimming_pool_id
+
same normalized phone

기존 parent_accounts 확인.

분기:

A.
기존 account 없음
→ 현재 일반가입 그대로 진행.

B.
기존 account 있음
AND kakao_id 없음
→ 기존 duplicate 가입 정책 그대로.
현재 동작 변경 금지.

C.
기존 account 있음
AND kakao_id 존재
→ KAKAO_MIGRATION_REQUIRED

→ 임시 Kakao→일반계정 전환 flow로 이동.

5. UNIQUE PHONE 문제 해결
============================================================

현재 DB 정책:

same pool
+
same normalized phone

duplicate parent row:
금지.

따라서 migration은 반드시
하나의 DB transaction 안에서 처리.

원칙:

BEGIN

1.
기존 Kakao parent account lock
가능하면 SELECT ... FOR UPDATE

2.
다시 조건 확인:

same pool
same phone
kakao_id exists
아직 migration 안 됨

3.
기존 Kakao account의 phone uniqueness를
안전하게 해제할 수 있는 기존 archive/deactivate 방식 확인.

임의 문자열 형식 invent 금지.

현재 schema에 적합한 archive 방식이 없다면
먼저 정확한 안전 설계 보고.

4.
새 일반 parent_accounts 생성:

새 parent id
original phone
new general credential
same swimming_pool_id

5.
모든 parent ownership references를
old_parent_id → new_parent_id로 이전.

6.
기존 Kakao account는
로그인 불가능한 archived/retired 상태로 전환.

7.
kakao_id는 history용으로 old account에 보존 가능.

8.
COMMIT

어느 단계든 실패:
ROLLBACK

부분 migration:
절대 금지.

8. migration idempotency
============================================================

같은 사용자가 가입 버튼을 두 번 누르거나
network retry가 발생해도:

새 일반계정 2개 생성:
NO

데이터 두 번 이전:
NO

반드시 idempotent.

기존 시스템에서 request_id /
idempotency mechanism이 있으면 재사용.

새 DB schema는 가능하면 만들지 말 것.

필요하다면 기존 audit/history 구조 사용 가능 여부 확인.
