============================================================
1. 확정 데이터 정책
============================================================

학생에게 일지를 귀속할 수 있는 최소 날짜는:

"현재 해당 수영장에 이 학생 회원 레코드가 등록된 날짜/시각"

이다.

즉:

diary.created_at 또는 실제 수업/일지 기준시각
<
student/member enrollment/registration timestamp

이면

그 일지는 해당 학생의 기록이 아니다.

반드시 제외.

예:

회원 등록:
2026-09-02

일지:
2026-09-01
→ EXCLUDE

일지:
2026-08-18
→ EXCLUDE

일지:
2026-09-02 이후
→ 기존 정상 귀속 조건을 충족하면 INCLUDE

============================================================

추측해서 새로운 날짜 필드 만들지 말 것.

현재 schema에서 실제 회원 등록 기준값 확인:

예시 후보:
- students.created_at
- members.created_at
- enrolled_at
- registered_at
- joined_at
- enrollment date
- 기타 현재 실제 사용하는 회원 등록일 필드

첨부 화면의:

"등록일: 2026. 9. 2."

가 어떤 DB field에서 나오는지 추적.

그 field를 이번 cutoff의 source of truth로 사용.

완료보고에 정확한 table.column 명시.

3. 왜 과거 일지가 붙었는지 ROOT CAUSE 조사
============================================================

현재 2026-09-02 등록 학생에게
8월/9월1일 일지가 붙는 이유를 정확히 확인.

가능성을 추측으로 고치지 말 것.

실제 조사:

- student_id 직접 귀속인지
- 이름 matching인지
- class membership 기준인지
- pool 전체 diary lookup인지
- reused/ref ID 문제인지
- parent/member join 문제인지
- diary student mapping table 때문인지

ROOT CAUSE를 실제 코드/DB schema 기준으로 보고.

즉:

등록 전 일지 → 학부모 노출 0

9. 이름 동일 학생 오염 방지
============================================================

특히 반드시 확인.

과거에 같은 이름의 학생이 있었거나
퇴원 후 새로 등록된 경우에도

이름만 같다는 이유로
예전 일지가 신규 학생에게 붙어서는 안 됨.

Diary ownership은 가능한 경우
stable student/member ID + pool + valid enrollment period
기준이어야 한다.

이름 matching만으로 귀속:
금지.

============================================================
10. 재등록 / 퇴원 후 재가입
============================================================

현재 schema와 기존 정책을 확인해서
재등록 학생도 잘못된 과거기간이 섞이지 않게 할 것.

이번 WP에서 새 회원 생애주기 아키텍처를 만들지는 말 것.

다만 현재 시스템에
명확한 신규 member/student record가 생성되는 재등록이라면

그 새 record의 등록일 이전 기록은
그 새 record에 귀속시키지 않는다.

기존 동일 record를 계속 사용하는 구조라면
현재 enrollment/status history를 조사하고
임의 변경하지 말고 완료보고에 정확히 명시.

============================================================

Normal과 X에서 공유되면

Normal 따로
X 따로
중복 구현 금지.

X에서만 AI report가 추가로 diary를 수집한다면
그 report source에도 동일 cutoff 재사용.

12. SERVER-SIDE ENFORCEMENT
============================================================

핵심 필터는 가능하면
공통 server/service/query layer에서 적용.

각 UI마다:

if date < registrationDate hide

식으로 반복 구현하지 말 것.

목표:

"이 학생의 diary history를 달라"

라는 모든 주요 서버 경로가
기본적으로 registration cutoff를 준수하도록 만들 것.

다만 다른 목적의 전체 pool historical diary 조회까지
무조건 잘라내면 안 됨.

학생별 귀속 조회에 적용.

============================================================
13. DATE/TIME 처리
============================================================

등록일이 날짜만 저장되는지
timestamp로 저장되는지 실제 schema 확인.

날짜만 존재한다면
기존 앱의 KST 날짜 규칙을 따라
임의 UTC 하루 밀림이 생기지 않도록 처리.

예:

등록일 2026-09-02인데
timezone 때문에
2026-09-01 일지가 통과하는 문제 금지.

현재 프로젝트의 KST normalization 재사용.
