SWIMNOTE 댓글·반응 기능 Production 서버 실제 저장 실패 긴급 수정

현재 실제 production 앱 테스트 결과:

- 학부모가 좋아요를 눌렀지만 선생님 화면은 좋아요 0명
- 학부모가 감사합니다를 눌렀지만 선생님 화면은 감사합니다 0명
- 댓글 전송은 계속 “전송에 실패했습니다”
- 선생님 댓글 화면은 댓글 0개
- 프론트 UI는 보이지만 서버 저장과 조회가 전혀 연결되지 않음

이번에는 코드 수정 보고가 아니라
실제 production API 요청, production DB row, 선생님 조회까지 증명하세요.

==================================================
1. Production API host 확인
==================================================

학부모 앱의 댓글·반응 요청이 실제 어느 서버로 가는지 로그로 출력하세요.

필수 로그:

[CLIENT API REQUEST]
apiHost=
endpoint=
method=
diaryId=
studentId=
reactionType=
tokenExists=

확인:

- preview 서버로 요청하는지
- localhost 또는 Replit 주소를 호출하는지
- swimnote.kr/api production 서버를 호출하는지
- /api prefix 중복 여부
- OTA 환경변수가 production 값을 쓰는지

실제 앱의 API host를 보고하세요.

==================================================

4. Production DB 스키마 직접 확인
==================================================

Production DB에서 실제로 확인하세요.

diary_messages:

- parent_comment_id 존재
- student_id 존재
- message_type 존재
- nullable/default 확인
- 기존 NOT NULL 컬럼 확인

diary_reactions:

- 테이블 존재
- reaction_type 컬럼
- CHECK constraint
- unique constraint
- diary_id
- student_id
- parent_user_id

다음 SQL 결과를 보고하세요.

SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name IN ('diary_messages', 'diary_reactions');

SELECT conname, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid IN (
  'diary_messages'::regclass,
  'diary_reactions'::regclass
);

“마이그레이션 코드가 있다”가 아니라
production DB에 실제 적용됐는지 증명하세요.

8. diaryId 일치 확인
==================================================

학부모가 보고 있는 일지 ID와
선생님 지난 일지 카드 ID가 같은지 비교하세요.

학부모 화면 로그:

[PARENT DIARY]
diaryId=

선생님 화면 로그:

[TEACHER DIARY CARD]
diaryId=

반응 DB row:

diaryId=

세 값이 정확히 같아야 합니다.

같은 날짜·같은 반인데 diary row가 여러 개 존재하면
학부모는 A diary에 반응하고 선생님은 B diary를 보고 있을 수 있습니다.

Production DB에서 동일 class_group_id + lesson_date의 active diary row를 조회하세요.

SELECT id, class_group_id, lesson_date, is_deleted, created_at
FROM class_diaries
WHERE class_group_id = :classGroupId
AND lesson_date = :lessonDate
ORDER BY created_at;

active row가 여러 개면 반응과 댓글이 다른 diaryId로 분산될 수 있으므로
중복 active diary 문제를 먼저 해결하세요.

==================================================

선생님 지난 일지 API의 실제 production 응답을 제출하세요.

{

두 경우를 구분해서 보고하세요.

10. 댓글 INSERT 기존 컬럼 충돌 확인
==================================================

diary_messages가 기존 쪽지 테이블이라면
student_id, parent_comment_id, message_type만 추가해도
기존 NOT NULL 컬럼 때문에 INSERT가 실패할 수 있습니다.

특히 확인:

- sender_id NOT NULL
- receiver_id NOT NULL
- sender_role
- receiver_role
- content/message/body 컬럼명
- teacher_id
- parent_id
- read_at
- center_id
- diary_id

댓글 INSERT가 실제 스키마의 모든 필수 컬럼을 채우는지 확인하세요.

필요하면 기존 쪽지 테이블 재사용을 중단하고
별도 diary_comments 테이블을 생성하세요.

댓글 시스템이 핵심 기능이므로,
기존 쪽지 스키마를 억지로 재사용해 계속 오류가 나면 안 됩니다.

권장 별도 테이블:

diary_comments

- id
- center_id
- diary_id
- student_id
- author_user_id
- author_role
- parent_comment_id
- body
- is_deleted
- created_at
- updated_at
