0. 제품 목적
━━━━━━━━━━━━━━━━━━━━━━

이번 기능은 회계 프로그램이나
정확한 카드결제 매출 시스템이 아닙니다.

목적은:

“현재 실제 스케줄과 회원 구성을 바탕으로
선생님이 담당하고 있는 회원들의
월 기준 매출을 자동 계산해서 보여주는 것”

입니다.

그 후 현실에서 발생하는:

- 할인
- 체험수업
- 회수결제
- 특수결제
- 월 중간 등록
- 월 중간 퇴원
- 기타 예외

중 자동 계산으로 정확히 알 수 없는 금액은

선생님이 직접 조정하여 저장합니다.

즉:

AUTO CALCULATION
+
MANUAL ADJUSTMENT
=
REFLECTED REVENUE

구조입니다.

현재 단계에서:

- 급여 계산
- 세금
- 원천징수
- 실제 카드 결제
- 인센티브 지급액

까지 만들지 않습니다.

우선 정확한
“선생님별 월 매출 계산 기반”
을 만드는 것이 목표입니다.

━━━━━━━━━━━━━━━━━━━━━━
1. 반드시 분리할 두 지표
━━━━━━━━━━━━━━━━━━━━━━

“수업시수”와 “회원 매출”을 같은 숫자로 취급하지 마십시오.

두 개를 별도 지표로 설계하십시오.

A. 선생님 수업시수

예:
이번 달 실제 담당 수업 횟수 / 시간

이는 향후 인센티브 계산 등에 사용할 수 있는
업무량 지표입니다.

B. 회원 수업회수 기반 매출

학생별:

정상 수업 단가
×
해당 월 계산 대상 수업회수

로 산출하는 매출 지표입니다.

학생 여러 명이 한 그룹 수업에 있어도
선생님의 “수업 1시간”과
“학생 5명의 매출”은 다른 개념입니다.

절대 하나로 합치지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
2. 기본 수업료 정책
━━━━━━━━━━━━━━━━━━━━━━

각 수영장은 미리
정상 수업료 기준을 설정합니다.

예를 들어 실제 정책이:

주 1회
→ 정상 월 수업료

주 2회
→ 정상 월 수업료

주 3회
→ 정상 월 수업료

형태라면 이를 기준으로 합니다.

현재 SWIMNOTE DB/API에
이미 수강료/횟수별 가격 설정 구조가 있는지 먼저 조사하십시오.

있으면 재사용.

없다면 새 구조를 바로 만들지 말고
최소 설계안을 제안하십시오.

중요:

가격 숫자를 코드에 하드코딩하지 마십시오.

pool별 설정값이어야 합니다.

보고할 것:

- 현재 수강료 관련 table/column
- 주1/주2/주3 등 빈도 정보가 어디에 저장되는지
- 현재 학생별 주당 수업횟수를 어떻게 알 수 있는지
- 기존 구조 재사용 가능 여부

━━━━━━━━━━━━━━━━━━━━━━
3. 단가 계산 원칙
━━━━━━━━━━━━━━━━━━━━━━

우리가 원하는 개념은:

정상 월 수업료
÷
정상 포함 수업회수
=
정상 1회 기준금액

입니다.

예:

주2회 정상 월 수업료
÷
정상 월 기준 회수
=
1회 기준금액

그 뒤 실제 해당 월 계산 대상 회수 × 1회 기준금액.

다만 여기서 중요한 문제가 있습니다.

예:

주2회 회원이므로
일반적으로 월 8회 기준인데

월 중간 등록 등으로
실제 계산 대상 수업이 5회이고

보강 완료가 1회 있으면

5 + 1 = 6회

기준으로 계산해야 합니다.

그러나 5주가 있는 달에
정규수업이 9회 잡혔다고 해서
정상 월 수업료보다 자동 매출을 과도하게 올리면
실제 결제정책과 어긋날 수 있습니다.

따라서 아래를 조사해서
가장 오차가 적은 규칙을 제안하십시오.

예시 후보:

A.
월 정상 기준회수
주1=4
주2=8
주3=12
등으로 고정하고
정상 월 수업료 / 기준회수

B.
해당 월 실제 스케줄 발생회수를 denominator로 사용

C.
정상 기준회수를 사용하되
정규 자동금액은 정상 월 수업료를 초과하지 않도록 cap

D.
다른 현재 운영 데이터에 더 적합한 방식

임의 선택하지 말고
현재 SWIMNOTE 데이터와
어린이수영장 일반 월 수강료 구조에 가장 맞는 안을 제안하십시오.

특히:

5주차
공휴일
휴강
중도등록
중도퇴원

에서 금액이 어떻게 되는지 예시를 포함하십시오.

━━━━━━━━━━━━━━━━━━━━━━
4. 월별 “실제 계산 대상 수업회수”
━━━━━━━━━━━━━━━━━━━━━━

가장 중요한 조사입니다.

정산 계산에서 단순히:

현재 students.class_group_id

만 보고 계산하면 안 됩니다.

월 중간:

- 신규 등록
- 반 이동
- 퇴원
- 선생님 변경

이 있을 수 있습니다.

따라서 현재 Production에서 아래 데이터를 조사하십시오.

- students
- class_groups
- student_class_history
- schedule_days
- attendance
- holidays / 휴강
- makeup_sessions
- 기타 실제 수업 발생을 알 수 있는 데이터

각각이 어떤 정보를 보존하는지 확인하십시오.

그리고 학생 A가
해당 월 어느 날짜에
어느 선생님 수업에 속했는지를
가장 정확히 복원할 수 있는 Source of Truth를 제안하십시오.

━━━━━━━━━━━━━━━━━━━━━━
5. 후보 계산 방식 비교
━━━━━━━━━━━━━━━━━━━━━━

다음 세 방식을 실제 현재 데이터 기준으로 비교하십시오.

[방식 1]
현재 스케줄표만 사용

[방식 2]
스케줄
+
student_class_history

[방식 3]
스케줄
+
student_class_history
+
attendance / holiday / cancellation / makeup

각 방식에 대해:

- 장점
- 오차 발생 조건
- 현재 DB로 구현 가능 여부
- 월 중간 등록/퇴원 반영 여부
- 과거 월 재계산 가능 여부

를 비교하고

최종적으로 하나를
RECOMMENDED SOURCE OF TRUTH

로 선정하십시오.

이번 설계의 가장 중요한 결과입니다.

━━━━━━━━━━━━━━━━━━━━━━
6. 중간 등록 / 퇴원
━━━━━━━━━━━━━━━━━━━━━━

사용자 요구:

스케줄에 회원이 중간에 들어오거나 나가면
그 달 매출 계산에도 바로 반영되어야 합니다.

예:

주2회 회원.

9월 1일부터 재원:
→ 월 전체 계산

9월 15일 등록:
→ 9월 15일 이후 계산 대상 수업만 포함

9월 18일 퇴원:
→ 퇴원일까지의 계산 대상 수업만 포함

가능하면:

enrolled_at
left_at

같은 실제 이력 날짜를 기준으로 계산합니다.

현재 DB에서 가능한지 확인하십시오.

현재 학생의 최신 class_group_id만 사용하여
과거를 추측하지 마십시오.

━━━━━━━━━━━━━━━━━━━━━━
7. 보강
━━━━━━━━━━━━━━━━━━━━━━

보강은 반드시 실제 완료된 수업만 계산합니다.

예:

정규 계산 대상 5회
+
완료된 보강 1회

=
6회

WAITING
EXPIRED
CANCELLED
미완료

상태는 매출 계산 회수에 넣지 않습니다.

현재 makeup_sessions 상태값과
“실제 완료”를 의미하는 canonical status를 확인하십시오.

또한 보강 선생님이
원래 담당 선생님과 다를 수 있습니다.

따라서 조사하십시오.

보강 1회 매출/수업시수를:

A. 원래 담당선생님
B. 실제 보강을 진행한 선생님

중 누구에게 귀속시키는 것이
현재 데이터 구조상 자연스러운지.

사용자 요구의 기본 방향은:

“실제로 그 수업을 진행한 선생님의 수업시수”

가 되어야 합니다.

단 회원 월매출 귀속과
교사의 실제 수업시수 귀속은
서로 다를 수 있으므로
두 개를 분리해서 설계하십시오.

━━━━━━━━━━━━━━━━━━━━━━
8. 중복 집계 방지
━━━━━━━━━━━━━━━━━━━━━━

한 학생이:

- 여러 반
- 여러 선생님
- 공동담당
- 반 이동
- 보강 선생님 변경

상태일 수 있습니다.

동일 학생의 동일 수업 1건이
두 선생님 매출에 중복 집계되면 안 됩니다.

현재:

class_groups.teacher_user_id
co_teacher_ids
original_teacher_id
assigned_teacher_id
transferred_to_teacher_id

등 실제 필드를 확인하고

Regular Session
Makeup Session

각각의 deterministic ownership rule을 제안하십시오.

10. 선생님 수동 조정
━━━━━━━━━━━━━━━━━━━━━━

자동 계산은 수정하지 않습니다.

각 학생별:

AUTO AMOUNT
→ 읽기 전용

ADJUSTMENT
→ 선생님 입력

FINAL
=
AUTO + ADJUSTMENT

형태를 권장합니다.

조정은:

양수
음수
0

모두 가능.

예:

할인
→ -20,000

체험수업 추가
→ +20,000

회수결제 등
→ 실제 상황에 맞게 +/-

조정 사유도 남길 수 있게 설계하십시오.

권장 사유:

- 할인
- 체험
- 회수결제
- 기타

+ 자유 메모.

이번 단계에서 사유 분류를 과도하게 늘리지 마십시오.

11. 저장의 의미
━━━━━━━━━━━━━━━━━━━━━━

선생님이 저장하기 전에는:

LIVE AUTO CALCULATION

입니다.

즉 현재 스케줄/회원 상태가 바뀌면
자동 계산값도 다시 계산됩니다.

선생님이 조정을 입력하고 저장하면:

해당 월의
TEACHER SAVED REVENUE

가 생깁니다.

관리자는 이를 우선 반영합니다.

중요:

자동 계산값과
선생님 저장값을 덮어써서 하나로 만들지 마십시오.

둘 다 볼 수 있어야 합니다.

예:

자동 계산
1,450,000

선생님 조정
-70,000

선생님 저장 반영매출
1,380,000

12. 선생님 저장 후 스케줄 변경
━━━━━━━━━━━━━━━━━━━━━━

중요한 edge case입니다.

예:

선생님이 9월 정산을 저장한 뒤
학생 1명이 추가되거나 퇴원.

이때:

기존 저장값을 몰래 덮어쓰면 안 됩니다.

설계안에서 최소한 관리자에게:

현재 자동 계산
vs
선생님 저장 반영액

차이를 볼 수 있게 하십시오.

가능하면:

“저장 후 스케줄 변경 있음”

또는

현재 자동계산과 저장 snapshot 차이

를 알 수 있는 최소 방식도 제안하십시오.

단 복잡한 버전관리 시스템까지 만들지 마십시오.

AUTO

14. 관리자 전체 매출

자동 계산 전체 매출

선생님 조정 총액

최종 반영 전체 매출

을 구분하십시오.

FINAL REFLECTED TOTAL:

각 선생님마다

SAVED 있으면 saved total

없으면 current auto total

을 사용해서 합산.

모든 선생님이 정산을 제출할 때까지
기다릴 필요가 없습니다.
