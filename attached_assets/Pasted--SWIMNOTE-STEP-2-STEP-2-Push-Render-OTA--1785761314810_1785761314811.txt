2. KST 날짜 함수 안정성 재검수
━━━━━━━━━━━━━━━━━━━━━━

현재 kstTodayStr()이 아래 방식이면 재검토한다.

new Date(
  new Date().toLocaleString("en-US", { timeZone: "Asia/Seoul" })
)

서버 로케일 문자열을 다시 Date로 파싱하는 구조는 피한다.

우선순위:

1. Repository에 이미 존재하는 KST YYYY-MM-DD 유틸 재사용
2. 없으면 Intl.DateTimeFormat(...).formatToParts() 방식
3. 외부 라이브러리가 이미 설치되어 있으면 기존 라이브러리 재사용

요구 결과:
- 서버 실행 지역·로케일과 무관
- 00:00~08:59 KST에도 정확한 한국 날짜
- 반환 형식 YYYY-MM-DD
- 테스트 케이스 제출

임의 신규 패키지 설치 금지.

4. 상태 변경 서버 로직 검수
━━━━━━━━━━━━━━━━━━━━━━

각 endpoint 실제 diff에서 아래를 확인해 표로 제출한다.

- transaction 안에서 SELECT FOR UPDATE 수행 여부
- 잠금 후 최신 row를 사용하는지
- history 종료와 students UPDATE가 동일 transaction인지
- 전체 반 이탈 경로에서 closeAllActiveClassHistory 사용 여부
- 특정 반 이탈에서 closeClassHistory 사용 여부
- suspended / withdrawn / archived / unassigned 처리 결과
- inactive / pending / active 배정값 유지 여부
- 응답 Contract가 바뀌지 않았는지

특히 remove-from-class + new_status가
허용되지 않은 new_status까지 전체 반 이탈 처리하지 않도록
기존 validation/allowlist를 실제 코드에서 확인한다.

6. 타입체크 증빙
━━━━━━━━━━━━━━━━━━━━━━

프로젝트 전체에 기존 오류가 있으므로
단순히 “수정 파일 오류 없음”이라고만 쓰지 않는다.

제출:

1. 실행 명령
2. 전체 출력 또는 오류 파일 목록
3. 이번 수정 6개 코드 파일이 오류 목록에 없는지
4. 수정 전 기준 오류와 수정 후 기준 오류 비교
5. 신규 오류 수: 0인지

가능하면 기존 오류 baseline과 diff를 비교한다.

7. Git 상태와 Rollback 수정
━━━━━━━━━━━━━━━━━━━━━━

다음 명령 결과를 제출한다.

git status --short

그 결과를 기준으로 Rollback을 작성한다.

- tracked 수정 파일: git restore <file>
- untracked 신규 파일: rm <file>
- tracked 삭제 파일: git restore <file>

아직 Commit 전이므로
git rm --cached를 무조건 사용하지 않는다.
