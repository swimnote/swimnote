[보낼 곳: APP REPLIT]

SWIMNOTE PRODUCTIZATION
FINAL OWNER PURCHASE-VALUE AUDIT

이번 작업은 코드 수정 작업이 아니다.

지금까지 구현된 release/v2.0.0 전체 코드와
앞서 수행한 PRODUCTIZATION BASELINE,
NORMAL/X PRODUCT BOUNDARY AUDIT,
현재 기능 구조를 다시 검토해서

"수영장 사장이 SWIMNOTE를 실제로 구매하고,
기존 프로그램에서 갈아타고,
계속 비용을 지불하게 만드는 데
아직 부족한 기능이 무엇인가"

를 기술/상품 양쪽 관점에서 최종 감사한다.

단순히 기능 아이디어를 많이 제시하지 않는다.

==================================================
최상위 상품 원칙
==================================================

SWIMNOTE 상품화 제1원칙:

"SWIMNOTE를 사용하는 모든 수영장의 매출이 올라야 한다."

일반 SWIMNOTE도 완성형 수영장 운영 SaaS여야 한다.

Normal과 X의 차이는
기본 기능 유무가 아니다.

COMMON:
- 회원관리
- 매출관리
- 신규회원관리
- 재등록
- 이탈관리
- 학부모관리
- Push
- 기본 성장/진도
- 관리자 편의
- 교사 비AI 편의
- 수동 문자/공지/일지
- 공유
- Curriculum 기본 기능
- 수영·훈련용어 검색
- 기본 Dashboard

X:
동일 COMMON 기능
+
AI 자동화/분석/검색/리포트

가능하면 같은 기능을 Normal/X 두 벌 만들지 않는다.

상위 공통 기능 하나를 구현하고
X에서는 AI 버튼/AI 카드만 capability에 따라 노출한다.

AI API는 UI hide뿐 아니라
server entitlement도 검증한다.

==================================================
1. 구매 이유 AUDIT
==================================================

현재 SWIMNOTE를
수영장 원장에게 5분 동안 보여준다고 가정한다.

실제 코드 기준으로 원장이 즉시 느낄 수 있는:

A. 매출 증가 이유
B. 비용 절감 이유
C. 업무시간 절감 이유
D. 학부모 만족 증가 이유
E. 기존 프로그램에서 갈아탈 이유

를 각각 찾아라.

각 항목:

STRONG
MEDIUM
WEAK
NONE

평가.

==================================================
2. 구매를 막는 요소
==================================================

수영장 사장이:

"좋긴 한데 굳이 바꿀 필요가 있나?"

라고 생각할 가능성이 있는 이유를 찾는다.

예:

- 기존 회원 이전 어려움
- 초기 설정 많음
- 교육과정 등록 어려움
- 기능 위치 복잡
- 직원 교육 필요
- 학부모 가입 과정 어려움
- 기존 서비스와 차이 부족
- 매출효과가 눈에 안 보임
- 데이터 이전 위험
- 비용 대비 가치 불명확

실제 코드/UI 기준으로 TOP 15.

3. Revenue Leakage Audit
==================================================

수영장에서 돈을 놓칠 수 있는 모든 상황을 찾고
SWIMNOTE가 현재 막아주는지 평가한다.

반드시 검토:

- 문의 후 연락 누락
- 체험 예약 누락
- 체험 후 미등록
- 재등록 미완료
- 장기결석
- 퇴원징후
- 빈자리 방치
- 대기회원 방치
- 보강/요청 불만
- 학부모 소통 부족
- 추천회원 추적 불가
- 수강상태 누락
- 미납/결제상태 관리
- 휴회 후 복귀 누락
- 퇴원 후 재가입 기회 누락

각 항목:

CURRENTLY_SOLVED
PARTIAL
NOT_SOLVED

==================================================
4. 신규회원 Funnel 검토
==================================================

현재 구조에서:

LEAD
→ CONTACTED
→ TRIAL_RESERVED
→ TRIAL_COMPLETED
→ REGISTERED

흐름을 구현할 기반이 있는지 조사한다.

현재 없는 경우
기존 member/student 구조를 최대한 재사용하는
최소 설계를 제안한다.

반드시 검토:

- 문의자
- 상담상태
- 희망요일
- 희망시간
- 희망레벨
- 체험일
- 담당자
- 마지막 연락일
- 다음 연락일
- 등록전환 여부
- 미등록 이유

불필요한 CRM을 만들지 않는다.

수영장 영업에 필요한 최소값만.

5. CLASS CAPACITY / EMPTY SEAT AUDIT
==================================================

현재 반 정원/학생 수/시간표 데이터로:

- 반 정원
- 현재 등록 인원
- 남은 자리
- 만석
- 빈자리

계산 가능한지 조사.

원장에게:

"현재 판매 가능한 자리"

를 보여줄 수 있는지 검토.

예:

화 16시 초급 — 1자리
목 17시 중급 — 2자리

추가로:

대기회원과 빈자리 matching

을 AI 없이 구현할 수 있는지 검토.

6. WAITLIST AUDIT
==================================================

현재 대기회원 개념이 있는지 조사.

없다면 최소 구조 제안:

WAITING
CONTACTED
OFFERED
ACCEPTED
DECLINED
EXPIRED

빈자리 발생 시
관리자에게 대상자를 보여주는 구조를 제안.

자동 문자 발송은 필수 아님.

Normal:
직접 연락

X:
향후 AI 문구/추천 보조 가능.

8. Referral / Sharing AUDIT
==================================================

학부모 만족이
신규회원으로 연결되는 구조가 있는지 조사.

최소 COMMON 후보:

- 소개자 기록
- referral source
- 공유
- 공유 CTA
- 신규 회원 등록 시 소개자 연결
- 월별 소개 등록 수

AI 필요 없음.

과도한 포인트/보상시스템은 제안하지 않는다.

12. Switching Cost Audit
==================================================

다른 수영장 프로그램에서
SWIMNOTE로 갈아타는 난이도를 평가.

특히:

- 회원 1,000명 Bulk
- 이름+전화번호 only
- 반 배정
- 기존 사진
- 기존 일지
- Curriculum
- 선생님
- 학부모 초대

중

"없으면 실제 계약을 포기할 가능성이 높은 Migration 기능"

을 선정.

모든 데이터 이전 기능을 만들지는 않는다.

구매 결정에 정말 필요한 것만 제안.
