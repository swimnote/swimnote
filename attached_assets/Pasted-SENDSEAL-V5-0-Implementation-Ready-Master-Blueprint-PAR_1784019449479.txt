0. 문서 목적
==================================================

이 문서는 SENDSEAL을 실제 제품으로 개발하기 위한 통합 설계서다.

SENDSEAL은 단순한 파일 업로드 앱이나 링크 공유 서비스가 아니다.

SENDSEAL은 발신자가 지정한 수신자에게 대용량 원본 파일을 전달하고,
수신자가 파일을 실제 기기에 다운로드한 뒤 수령 완료를 승인하면,
전달 완료 사실을 기록하고 서버 원본을 삭제하는 1:1 디지털 전달 서비스다.

본 문서는 다음 목적을 가진다.

1. 기획자가 서비스 구조를 일관되게 이해할 수 있도록 한다.
2. 디자이너가 화면과 상태를 동일한 기준으로 설계할 수 있도록 한다.
3. 모바일 개발자가 iOS·Android 기능을 같은 정책으로 구현할 수 있도록 한다.
4. 백엔드 개발자가 상태 머신·API·DB·Queue를 일치시켜 구현할 수 있도록 한다.
5. 운영자가 신고·삭제·보안·장애 상황을 처리할 수 있도록 한다.
6. 플랫폼 연동 사업자가 SENDSEAL 전송 엔진을 별도 서비스에 연결할 수 있도록 한다.
7. 10GB 일반 전송과 100GB 대용량 전송을 동일한 코어에서 처리할 수 있도록 한다.

이 문서의 우선순위는 다음과 같다.

1순위:
실제 구현 가능성

2순위:
대용량 전송 안정성

3순위:
수신자 지정과 전달 증빙

4순위:
원본 자동 삭제와 개인정보 최소 보유

5순위:
사용자 경험의 단순함

문서 원칙:

- 설명만 있는 기능은 넣지 않는다.
- 상태·DB·API·화면이 연결되지 않는 기능은 제거한다.
- 100GB 업로드는 부가 기능이 아니라 핵심 요구사항으로 본다.
- iOS·Android 백그라운드 전송은 선택 사항이 아니라 필수 구현으로 본다.
- 업로드 완료와 다운로드 가능 상태를 분리한다.
- 다운로드 완료와 수령 완료를 분리한다.
- 수령 완료와 원본 삭제 완료를 분리한다.
- 삭제 실패를 성공으로 표시하지 않는다.
- 모든 주요 상태 변경은 감사 가능하도록 기록한다.

문서 버전:

SENDSEAL V5.0

기존 V4.0 또는 V4.1 문서와 충돌하는 경우
V5.0을 우선 적용한다.

1. 서비스 정체성
==================================================

서비스명:

SENDSEAL

한국어 표기:

센드실

고정 서비스 설명:

"온라인 등기우편"

핵심 정의:

SENDSEAL은 발신자가 지정한 수신자에게 파일을 전달하고,
수신자가 정상적으로 다운로드한 뒤 수령 완료를 승인하면,
전달 완료 기록을 생성하고 서버 원본을 삭제하는
1:1 디지털 전달 서비스다.

SENDSEAL이 아닌 것:

- 공개 파일 공유 서비스
- 불특정 다수 링크 배포 서비스
- 장기 클라우드 저장소
- 협업 문서 편집 서비스
- 소셜 피드 서비스
- 무제한 백업 서비스
- P2P 메신저
- 이메일 첨부 대체만을 목적으로 한 단순 업로더

SENDSEAL의 핵심 차이:

일반 파일 공유는
"링크를 만들고 상대에게 보내는 구조"다.

SENDSEAL은
"수신자를 먼저 지정하고 전달 상태를 끝까지 기록하는 구조"다.

핵심 흐름:

발신자
→ 전송 생성
→ 지정 수신자 등록
→ 크레딧 예약
→ 백그라운드 업로드
→ 업로드 완료
→ 서버 검증
→ 보안 검사
→ 다운로드 가능 상태
→ 수신자 알림
→ 수신자 다운로드
→ 다운로드 완료 확인
→ 수령 완료 승인
→ 전달 완료증 생성
→ 서버 원본 삭제
→ 삭제 검증
→ 전달 종료

핵심 원칙:

1. 공유가 아니라 전달
2. 링크가 아니라 지정 수신자
3. 저장이 아니라 전달 종료까지의 임시 보관
4. 업로드 완료와 전달 가능 상태 분리
5. 다운로드 완료와 수령 완료 분리
6. 수령 완료 전까지 오류 복구 지원
7. 수령 완료 후 원본 삭제
8. 삭제 성공 여부를 별도로 검증
9. 원본 파일 장기 보관 금지
10. 메타데이터와 증빙은 정책에 따라 별도 보관
11. 사용자에게 기술 용어를 최소 노출
12. 모든 핵심 흐름은 앱을 닫아도 복구 가능해야 함

서비스 핵심 문장:

"파일이 올라간 순간이 아니라,
상대방이 정상적으로 받고 확인한 순간 전달이 끝난다."

서비스 가치:

발신자 가치:
- 대용량 원본 전달
- 업로드 완료 확인
- 수신자 다운로드 가능 확인
- 다운로드 완료 확인
- 수령 완료 확인
- 전달 완료증 확보
- 서버 원본 삭제 확인

수신자 가치:
- 링크 탈취 위험 감소
- 지정된 본인만 다운로드
- 원본 화질 유지
- 이어받기
- 여러 저장 위치 지원
- 수령 완료 전 재확인 가능
- 전달 종료 전 추가 기기 다운로드 가능

사업자 가치:
- 전송 건별 과금
- 플랫폼 엔진 연동
- 전문 납품 시장 진입
- 대용량 파일 전달 차별화
- 수령 완료 기반 신뢰 서비스 구축

- 최대 100GB 전달
- 원본 화질 유지
- 지정 수신자 1명
- 다운로드 완료 기록
- 수령 완료 승인
- 전달 완료증
- 원본 자동 삭제
- 납품 흐름 단순화

2-3. 대표 사용 시나리오
------------------------------------------

시나리오 A:
웨딩 사진작가가 고객에게 RAW와 보정본 65GB 전달

흐름:
작가가 대용량 전송 선택
→ 파일 65GB 선택
→ 고객 전화번호 지정
→ 10크레딧 결제
→ 백그라운드 업로드
→ 업로드 완료 Push
→ 보안 검사 완료
→ 고객에게 다운로드 가능 Push
→ 고객 다운로드
→ 고객 수령 완료
→ 작가에게 수령 완료 Push
→ 서버 원본 삭제
→ 전달 완료증 생성

시나리오 B:
수영 강사가 학부모에게 4K 레슨 영상 3GB 전달

흐름:
SWIMNOTE에서 학부모 선택
→ SENDSEAL 엔진 호출
→ 플랫폼 지갑 차감
→ 영상 업로드
→ 학부모 알림
→ 다운로드
→ 수령 완료
→ SWIMNOTE에 전달 완료 상태 반환

시나리오 C:
일반 사용자가 가족에게 20GB 여행 영상 전달

흐름:
대용량 전송 선택
→ 가족 전화번호 지정
→ 업로드
→ 상대방 앱 설치
→ 전화번호 인증
→ 기존 Transfer 자동 연결
→ 다운로드
→ 수령 완료

==================================================

------------------------------------------
3-1. ROLE_USER
------------------------------------------

일반 사용자.

가능 기능:

- 전화번호 가입
- 기기 등록
- 파일 전송
- 파일 수신
- 일반 전송 선택
- 대용량 전송 선택
- 수신자 지정
- 크레딧 구매
- 무료 전송 사용
- 업로드 진행 확인
- 업로드 일시정지
- 네트워크 대기
- 업로드 취소
- 수신 파일 다운로드
- 다운로드 이어받기
- 수령 완료
- 같은 기기 재확인
- 다른 기기 추가 다운로드
- 다운로드 확인증 조회
- 전달 완료증 조회
- 신고
- 계정 탈퇴

제한:

- 다른 사용자 원본 접근 불가
- 공개 링크 생성 불가
- 수신자 변경은 업로드 시작 전까지만 가능
- 다운로드 시작 후 발신자 임의 취소 불가
- 삭제 완료 파일 복구 불가

------------------------------------------
3-2. ROLE_SUPPORT_ADMIN
------------------------------------------

고객지원 관리자.

가능 기능:

- 사용자 문의 조회
- 계정 상태 확인
- 전송 상태 확인
- 오류 코드 확인
- 업로드·다운로드 진행 상태 확인
- 알림 발송 이력 확인
- 삭제 작업 상태 확인
- 재처리 요청 등록

제한:

- 전화번호 원문 조회 불가
- 파일 원본 접근 불가
- 사용자 파일 다운로드 불가
- 계정 영구 정지 불가
- 수신자 변경 불가
- 크레딧 임의 지급 불가
- 삭제 상태 임의 완료 처리 불가

------------------------------------------
3-3. ROLE_SECURITY_ADMIN
------------------------------------------

보안 및 신고 담당 관리자.

가능 기능:

- 신고 검토
- 위험 계정 확인
- 보안 검사 결과 확인
- 전송 임시 차단
- 계정 일시 제한
- 계정 영구 제한 요청
- Legal Hold 등록 요청
- 증거 메타데이터 보존
- 개인정보 원문 조회 요청
- 적법한 절차에 따른 관계기관 대응

필수 통제:

- 개인정보 원문 조회 시 사유 입력
- 모든 조회 감사 로그 생성
- 대량 조회 금지
- 파일 원본 직접 열람은 별도 승인 필요
- 승인 없는 원본 다운로드 불가

------------------------------------------

------------------------------------------

최고 관리자.

가능 기능:

- 가격 설정
- 최대 용량 설정
- 크레딧 상품 설정
- 위험 점수 정책 설정
- 관리자 권한 부여
- 관리자 권한 회수
- 서비스 긴급 중단
- 전송 강제 차단
- 강제 삭제
- Legal Hold 승인
- 운영 정책 변경
- 관리자 감사 로그 조회

제한 원칙:

- 최고 관리자도 원본 파일에 기본 접근하지 못함
- 원본 접근은 별도 승인·사유·감사 로그 필요
- 사용자 전화번호 원문은 기본 마스킹

------------------------------------------
3-5. PLATFORM_CLIENT
------------------------------------------

SENDSEAL 엔진을 호출하는 외부 또는 자체 플랫폼.

예:

- SWIMNOTE
- MUSCLENOTE
- 향후 기업 서비스
- 교육기관 플랫폼
- 촬영 납품 플랫폼

가능 기능:

- 플랫폼 사용자 식별
- 지정 수신자 전달 요청
- 플랫폼 지갑 차감
- 플랫폼별 용량 제한
- 플랫폼별 전송 템플릿
- 플랫폼별 브랜딩
- 전달 상태 Webhook 수신
- 수령 완료 상태 수신
- 삭제 완료 상태 수신

제한:

- 플랫폼은 SENDSEAL 원본에 직접 접근하지 않음
- 플랫폼 자체 권한과 SENDSEAL 권한을 분리
- 플랫폼별 API Key와 Secret 분리
- 플랫폼별 Rate Limit 분리
- 플랫폼별 전송 한도 분리

전송 버튼을 누르면 잔액을 검사한다.

잔액 충분:

크레딧 예약
→ 업로드 세션 생성
→ 업로드 시작

잔액 부족:

결제 화면
→ 크레딧 구매
→ 전송 화면 복귀
→ 사용자가 다시 전송 확인
→ 업로드 시작

자동 업로드 금지:

결제 완료 직후 모바일 데이터로 자동 업로드하지 않는다.

- 업로드 실패
- R2 오류
- 무결성 검증 실패
- 보안 검사 차단
- 서버 내부 오류
- 용량 한도 초과
- 결제 검증 실패

다음 경우 환불하지 않음:

- 업로드 성공
- 보안 검사 통과
- 수신자 다운로드 가능 상태 전환
- 수신자가 다운로드하지 않음
- 전송 유효기간 만료
- 수신자가 수령 완료를 누르지 않음

유료 서비스 완료 기준:

원본 업로드 완료
+ 서버 객체 검증 완료
+ 보안 검사 통과
+ 수신자 다운로드 가능 상태 전환

5-4. 업로드 완료 UX
------------------------------------------

발신자 Push:

"업로드가 완료되었습니다.
파일 확인이 끝나면 수신자에게 다운로드 알림이 전송됩니다."

보안 검사 완료 후 발신자 Push:

"파일 전달 준비가 완료되었습니다.
수신자가 지금 다운로드할 수 있습니다."

수신자 Push:

"새 파일이 도착했습니다.
지금 다운로드할 수 있습니다."

핵심:

업로드 완료 직후 수신자에게 다운로드 가능 알림을 보내지 않는다.

반드시 다음이 완료된 뒤 수신자에게 알림을 보낸다.

- R2 Object 검증
- 파일 메타데이터 검증
- MIME·Magic Byte 검사
- 허용 파일 정책 확인
- 필수 보안 검사

10. 전송 유형 선택
==================================================

SENDSEAL은 파일 선택 전에 전송 유형을 먼저 선택하게 한다.

전송 유형:

1. 일반 전송
2. 대용량 전송

------------------------------------------
10-1. 일반 전송
------------------------------------------

표시 문구:

일반 전송
최대 10GB
3크레딧 / 300원

추천 대상:

- 사진
- 문서
- 일반 영상
- 짧은 4K 영상
- 소용량 RAW 묶음
- 레슨 영상

기본 추천:

일반 전송

이유:

- 대부분의 일반 사용자에게 충분함
- 사용자가 불필요하게 대용량 요금을 선택하지 않도록 함
- 가격 이해가 쉬움

------------------------------------------
10-2. 대용량 전송
------------------------------------------

표시 문구:

대용량 전송
최대 100GB
10크레딧 / 1,000원

추천 대상:

- 대량 RAW
- 웨딩 촬영 원본
- 4K 장시간 영상
- 영상 프로젝트 소스
- 공연·행사·대회 원본
- 상업 납품 파일

대용량 전송 선택 시 추가 안내:

"업로드는 백그라운드에서 진행됩니다.
앱을 닫아도 완료된 부분은 유지되며,
업로드가 끝나면 자동으로 알려드립니다."

------------------------------------------
10-3. 실제 용량 검사
------------------------------------------

파일 선택 후 서버가 최종 용량을 확인한다.

검사 항목:

- 전체 파일 수
- 파일별 크기
- 총 바이트
- 전송 유형 한도
- 금지 파일 포함 여부
- 사용자 계정 제한
- 플랫폼별 한도

일반 전송에서 10GB 초과:

"선택한 파일은 일반 전송 한도를 초과했습니다.
대용량 전송으로 변경하면 최대 100GB까지 보낼 수 있습니다."

버튼:

[대용량 전송으로 변경]
[파일 다시 선택]

대용량 전송에서 10GB 이하:

자동으로 일반 전송으로 변경하지 않는다.

안내:

"현재 파일은 일반 전송으로도 보낼 수 있습니다."

버튼:

[일반 전송 300원]
[대용량 전송 유지]

------------------------------------------
10-4. 용량 계산 기준
------------------------------------------

용량은 10진수 기준으로 표시한다.

1GB = 1,000,000,000 bytes

서버 검증은 바이트 기준으로 한다.

클라이언트 표시:

- KB
- MB
- GB

서버 판정:

- total_bytes
- max_bytes

클라이언트 계산과 서버 계산이 다르면
서버 값을 우선한다.

11. 파일 선택 및 묶음 구조
==================================================

파일 선택 경로:

- 사진 앨범
- 시스템 파일 앱
- 카메라 촬영 후 공유
- 다른 앱의 공유 메뉴
- 플랫폼 내부 업로드
- PC 업로드는 초기 버전에서 지원하지 않음

------------------------------------------
11-1. 다중 파일 선택
------------------------------------------

여러 파일을 하나의 ZIP으로 묶지 않는다.

Transfer Bundle 구조:

전송 1건
└ 파일 1
└ 파일 2
└ 파일 3
└ 파일 4

각 파일은 개별 R2 Object로 저장한다.

이유:

- 파일별 재시도 가능
- 파일별 Hash 검증 가능
- 부분 실패 복구 가능
- 파일별 저장 위치 분기 가능
- 대용량 단일 ZIP 생성 불필요
- 모바일 임시 저장공간 절약

------------------------------------------
11-2. 전송 제목
------------------------------------------

기본 제목:

첫 번째 파일명 또는 날짜 기반 자동 생성

예:

2026-07-14 파일 전달

사용자 수정 가능.

제목 제한:

- 최대 60자
- 제어문자 금지
- HTML 금지
- 줄바꿈 금지
- 이모지는 허용 가능하나 길이 계산은 Unicode 기준

------------------------------------------
11-3. 파일 수 제한
------------------------------------------

초기 권장 제한:

일반 전송:
최대 500개

대용량 전송:
최대 2,000개

관리자 설정 가능.

파일 수가 과도하면:

- 메타데이터 처리 증가
- 확인증 PDF 과대
- 다운로드 UX 복잡
- 보안 스캔 Queue 증가

따라서 용량 한도와 별도로 파일 수 한도를 둔다.

11-5. 파일 변경 감지

12. Share Extension 및 외부 앱 연동
==================================================

Share Extension은 100GB 파일을 직접 업로드하지 않는다.

핵심 원칙:

Share Extension은
파일 바이트 전송을 담당하지 않는다.

역할:

1. 공유된 파일 URI 확보
2. 보안 범위 접근 권한 획득
3. 임시 전달 메타데이터 생성
4. 메인 앱 실행 또는 업로드 대기열 등록
5. 실제 업로드는 메인 앱 또는 OS 백그라운드 전송 서비스가 수행

------------------------------------------
12-1. iOS Share Extension
------------------------------------------

구조:

외부 앱
→ Share Extension
→ App Group 공유 저장소에 메타데이터 기록
→ 메인 앱 호출
→ 메인 앱이 URLSession Background Upload 생성

주의:

- Extension 내부에서 100GB 복사 금지
- 메모리 내 전체 파일 로드 금지
- Data(contentsOf:) 금지
- 파일 URL만 전달
- 보안 범위 북마크 또는 복사 전략 검토
- 앱 실행 전 권한 만료 가능성 처리

------------------------------------------
12-2. Android Share Intent
------------------------------------------

구조:

외부 앱
→ ACTION_SEND 또는 ACTION_SEND_MULTIPLE
→ Content URI 수신
→ persistable permission 가능 여부 확인
→ 메인 앱 전송 작성 화면
→ WorkManager 업로드 등록

주의:

- URI 권한 만료 처리
- 임시 파일 복사 최소화
- 대용량 파일 전체 메모리 로드 금지
- ContentResolver 스트림 기반 처리

------------------------------------------
12-3. Handoff 실패
------------------------------------------

메인 앱 호출 실패 시:

- 임시 전송 Draft 저장
- 다음 앱 실행 시 복구
- 공유된 파일 접근권한 유효성 검사
- 유효하지 않으면 재선택 요청

13. 파일명 처리
==================================================

발신자 원본 파일명은 변경하지 않는다.

R2 Object Key는 UUID 기반으로 생성한다.

예:

transfers/{transfer_id}/files/{file_id}

메타데이터:

- original_name
- delivered_name
- prefix
- prefix_applied
- normalized_name
- extension
- detected_extension

------------------------------------------
13-1. 접두사
------------------------------------------

발신자는 선택적으로 접두사를 추가할 수 있다.

예:

원본:
IMG_1042.MOV

접두사:
SWIMNOTE_

수신 이름:
SWIMNOTE_IMG_1042.MOV

접두사 제한:

- 최대 30자
- 경로 구분자 금지
- 제어문자 금지
- 앞뒤 공백 제거
- 운영체제 금지문자 제거

------------------------------------------
13-2. 중복 파일명
------------------------------------------

같은 이름이 여러 개 있으면
수신 저장 시 충돌을 해결한다.

정책:

IMG_0001.JPG
IMG_0001 (2).JPG
IMG_0001 (3).JPG

원본 메타데이터는 유지한다.

------------------------------------------
13-3. 접두사 제거
------------------------------------------

수신자 옵션:

[발신자가 추가한 접두사 제거 후 저장]

서버에 저장된 original_name을 사용한다.

문자열 추측으로 제거하지 않는다.

14. 수신자 지정
==================================================

수신자는 1명만 지정한다.

지정 방법:

1. 최근 수신자
2. 즐겨찾기
3. 연락처 선택
4. 전화번호 직접 입력
5. 초대 링크 공유

------------------------------------------
14-1. 가입 수신자
------------------------------------------

수신자가 가입자이면:

- phone_lookup_hmac로 사용자 확인
- recipient_user_id 연결
- Transfer 권한 생성
- 업로드 완료 전 알림은 발송하지 않음
- AVAILABLE 이후 Push 발송

------------------------------------------
14-2. 미가입 수신자
------------------------------------------

미가입자이면:

- invitation 생성
- recipient_phone_hmac 저장
- invitation_token 생성
- 설치 링크 생성
- 문자 또는 카카오톡 공유
- 설치 후 전화번호 인증
- 기존 Transfer 자동 연결

중요:

초대 링크만으로 다운로드할 수 없다.

필수 조건:

- 전화번호 인증
- 지정 수신자 번호 일치
- 초대 토큰 유효
- Transfer 미만료
- Transfer AVAILABLE 이상
- 사용자 계정 정상

------------------------------------------
14-3. 초대 토큰
------------------------------------------

초대 토큰 정책:

- 충분한 난수
- 원문 DB 저장 금지
- token_hash 저장
- 유효기간 설정
- 사용 후 상태 변경
- 재사용 제한
- Transfer와 결합
- 전화번호 HMAC와 결합

------------------------------------------
14-4. 수신자 변경
------------------------------------------

업로드 시작 전:

변경 가능

업로드 시작 후:

기본적으로 변경 불가

예외:

- 업로드 전체 취소
- 새 Transfer 생성
- 관리자 보안 조치

이유:

- 권한 혼선 방지
- 알림 오발송 방지
- 증빙 무결성 유지
- Transfer ID 일관성 유지

15. 전송 견적
==================================================

클라이언트는 업로드 전에 견적 API를 호출한다.

API:

POST /v1/transfers/quote

요청:

{
  "mode": "LARGE",
  "totalBytes": 65000000000,
  "fileCount": 240,
  "recipientPhoneHmac": "..."
}

응답:

{
  "allowed": true,
  "mode": "LARGE",
  "maxBytes": 100000000000,
  "requiredCredits": 10,
  "freeEntitlementAvailable": false,
  "fileCountAllowed": true,
  "accountAllowed": true,
  "warnings": []
}

거부 예:

{
  "allowed": false,
  "reason": "TRANSFER_MODE_LIMIT_EXCEEDED",
  "maxBytes": 100000000000
}

서버는 견적 시 다음을 검사한다.

- 전송 유형
- 총용량
- 파일 수
- 계정 상태
- 위험 점수
- 수신자 상태
- 플랫폼 한도
- 무료 entitlement
- 정책 제한
- 일일 사용량

------------------------------------------
16-1. 잔액 충분
------------------------------------------

크레딧 예약은 DB 트랜잭션으로 처리한다.

23. 100GB 업로드 기본 원칙
==================================================

SENDSEAL의 대용량 업로드는
앱 화면을 계속 켜두는 구조가 아니다.

사용자는 업로드를 시작한 뒤
앱을 백그라운드로 보내거나 종료할 수 있다.

운영체제와 SENDSEAL 업로드 엔진은
완료된 Part를 유지하면서
가능한 범위에서 업로드를 계속하고,
중단되면 다음 실행 시 이어서 전송한다.

핵심 흐름:

파일 선택
→ 전송 생성
→ 크레딧 예약
→ Multipart 초기화
→ 백그라운드 업로드 등록
→ Part 단위 업로드
→ ETag 저장
→ 앱 종료 또는 네트워크 중단
→ 완료된 Part 조회
→ 미완료 Part만 재개
→ 모든 파일 업로드 완료
→ Complete Multipart
→ R2 Object 검증
→ 발신자 업로드 완료 알림
→ 보안 검사
→ AVAILABLE
→ 수신자 다운로드 가능 알림

핵심 원칙:

1. 100GB를 하나의 HTTP 요청으로 전송하지 않는다.
2. 파일을 Part로 나누어 업로드한다.
3. 완료된 Part는 다시 전송하지 않는다.
4. 앱 종료 후 서버 상태를 기준으로 복구한다.
5. 클라이언트 로컬 상태만 신뢰하지 않는다.
6. Presigned URL 만료 시 새 URL을 발급한다.
7. 업로드 완료와 다운로드 가능 상태를 분리한다.
8. 서버 검증 전 수신자에게 다운로드 알림을 보내지 않는다.
9. 업로드 완료 알림과 전달 준비 완료 알림을 분리한다.
10. 100GB 전체 업로드 실패 시 처음부터 재시작하지 않는다.

24. iOS 백그라운드 업로드 엔진
==================================================

iOS 대용량 업로드는
URLSession Background Transfer를 필수로 사용한다.

Expo Task Manager 또는 Background Fetch만으로
100GB 업로드를 구현하지 않는다.

------------------------------------------
24-1. 기본 구성
------------------------------------------

필수 구성:

- URLSessionConfiguration.background
- 고유 background session identifier
- URLSession delegate
- AppDelegate background event completion handler
- 업로드 작업과 fileId/partNumber 매핑
- 앱 재실행 후 기존 Task 복원
- App Group 또는 로컬 DB 상태 저장
- Keychain 기반 인증 토큰 보관
- 서버 Resume 상태 동기화

세션 식별자 예:

com.sendseal.upload.background.{user_id}

주의:

사용자별로 무제한 세션을 생성하지 않는다.

권장:

- 앱 전체 업로드 세션 1개
- Task Description에 transferId/fileId/partNumber 저장
- 로컬 DB와 서버 메타데이터로 연결

------------------------------------------
24-2. iOS Part 업로드
------------------------------------------

각 Part는 별도의 임시 파일 또는 파일 범위 데이터로 준비한다.

권장 우선순위:

1. 원본 파일에서 Part 범위 임시 파일 생성
2. URLSession uploadTask(with:fromFile:)
3. 완료 후 임시 Part 파일 삭제

금지:

- 64MB Part를 반복적으로 Data 객체에 전체 로드
- 100GB 전체 파일을 메모리에 로드
- Extension 메모리에서 업로드
- 앱 프로세스에만 의존하는 일반 uploadTask

임시 Part 파일 경로 예:

Library/Caches/SendSealParts/{transferId}/{fileId}/{partNumber}.part

임시 파일 관리:

- Part 업로드 직전 생성
- 업로드 완료 후 삭제
- 실패 시 재사용 가능
- 일정 기간 지난 고아 Part 자동 삭제
- 앱 저장공간 부족 시 생성 중단
- 원본 파일 접근 불가 시 사용자에게 재선택 요청

------------------------------------------
24-3. iOS 앱 종료 시 동작
------------------------------------------

앱이 백그라운드로 이동:

- URLSession이 업로드 계속
- 진행률은 delegate 이벤트로 기록
- Push나 로컬 알림은 필요 시 표시

앱이 시스템에 의해 종료:

- URLSession Background Task는 운영체제가 계속 처리 가능
- 완료 이벤트는 앱 재실행 또는 background event 전달 시 처리
- 로컬 DB와 서버 상태를 재동기화

사용자가 앱을 강제 종료한 경우:

iOS 정책에 따라 Background Transfer가 중단될 수 있다.

따라서 사용자 안내:

"앱을 강제로 종료하면 업로드가 일시정지될 수 있습니다.
일반적으로 앱을 닫거나 화면을 잠그는 것은 괜찮습니다."

앱 재실행 시:

1. 기존 URLSession Task 목록 조회
2. Task Description 매핑
3. 서버 Multipart 상태 조회
4. 완료 Part 비교
5. 중복 Task 취소
6. 미완료 Part 재등록

------------------------------------------
24-4. iOS Background Event 처리
------------------------------------------

AppDelegate:

application(_:handleEventsForBackgroundURLSession:completionHandler:)

처리 원칙:

- completionHandler를 저장
- URLSession delegate에서 모든 이벤트 처리 완료 후 호출
- 서버 part-complete API 호출
- 로컬 DB 반영
- 다음 Part 예약
- 모든 파일 완료 시 multipart complete 트리거

중요:

completionHandler를 너무 일찍 호출하지 않는다.

------------------------------------------
24-5. iOS 네트워크 정책
------------------------------------------

URLSession Configuration:

- allowsCellularAccess
- waitsForConnectivity
- isDiscretionary 정책 검토
- sessionSendsLaunchEvents 활성화
- timeoutIntervalForResource 충분히 설정

Wi-Fi 전용:

allowsCellularAccess = false

Wi-Fi + 모바일:

allowsCellularAccess = true

사용자 설정 변경 시:

- 신규 Task부터 적용
- 기존 Task는 취소 후 Resume 정책에 따라 재등록 가능
- 완료 Part는 유지

25-2. Android 작업 구조
------------------------------------------

→ FileUploadWorker

단일 파일마다 Work를 무제한 생성하지 않는다.

권장 단위:

- 취소·재개 단순화

------------------------------------------
25-3. Foreground Service
------------------------------------------

장시간 대용량 업로드는
Foreground Service 알림을 반드시 표시한다.

필수:

- 알림 채널 생성
- Android 버전별 Foreground Service Type 검토
- 사용자에게 현재 진행 상태 표시
- 서비스 시작 제한 대응
- 백그라운드 실행 제한 준수

앱이 종료되어도:

- WorkManager가 조건 충족 시 재실행
- 완료된 Part는 서버 기준으로 유지
- Foreground Service 재생성
- 미완료 Part부터 재개

------------------------------------------
25-4. Android Content URI
------------------------------------------

외부 앱에서 받은 URI는
persistable URI permission을 가능한 경우 확보한다.

불가능한 경우:

- 업로드 시작 전에 앱 전용 저장소로 안전하게 복사
- 복사 공간 부족 검사
- 대용량 복사가 불가능하면 사용자에게 파일 앱에서 다시 선택하도록 안내

원칙:

- 전체 파일 메모리 로드 금지
- InputStream 또는 FileDescriptor 기반 Range 읽기
- Part 단위 스트림 처리

------------------------------------------
25-5. Doze 및 배터리 최적화
------------------------------------------

Doze Mode에서 작업이 지연될 수 있다.

대응:

- Foreground Service
- WorkManager 재시도
- Network Constraint
- 지수 백오프
- 사용자 알림

배터리 최적화 예외를 강제 요구하지 않는다.

필요 시 안내:

"기기 제조사의 배터리 절약 설정으로 업로드가 지연될 수 있습니다."

26. Part 업로드 실행
==================================================

------------------------------------------
26-1. Part 준비
------------------------------------------

각 Part 정보:

- part_number
- byte_start
- byte_end
- size_bytes
- local_temp_path 또는 range source
- presigned_url
- expires_at
- retry_count

Part 상태:

PENDING
PREPARING
READY
UPLOADING
COMPLETED
FAILED_RETRYABLE
FAILED_FINAL

------------------------------------------
26-2. 업로드 요청
------------------------------------------

HTTP Method:

PUT

요청 Body:

해당 Part 바이트

필수 헤더:

Presigned URL 생성 조건에 맞는 헤더만 사용

주의:

서명에 포함되지 않은 임의 헤더 추가 금지

응답 성공:

- HTTP 200
- ETag 수집
- 서버 part-complete API 호출

------------------------------------------
26-3. Part 완료 API
------------------------------------------

POST /v1/files/{id}/multipart/part-complete

요청:

{
  "multipartUploadId": "uuid",
  "partNumber": 17,
  "etag": "\"abc123\"",
  "sizeBytes": 67108864,
  "completedAt": "2026-07-14T12:00:00Z"
}

서버 처리:

1. 사용자 권한
2. Transfer 상태
3. Multipart 상태
4. Part 번호 유효성
5. 중복 완료 여부
6. ETag 저장
7. 진행률 갱신
8. 감사 이벤트 기록

Idempotency:

같은 Part 완료 요청이 반복되면
동일 결과를 반환한다.

------------------------------------------
26-4. ETag 처리
------------------------------------------

ETag는 문자열 원형을 보존한다.

저장:

- 따옴표 포함 여부 정규화
- R2 Complete Multipart 요구 형식 유지
- 중복 Part 번호 UNIQUE

주의:

Multipart Object의 최종 ETag를
파일 전체 MD5로 간주하지 않는다.

파일 무결성은 별도 SHA-256 또는 정책 기반 Hash로 검증한다.

==================================================

API:

GET /v1/files/{id}/multipart/resume

응답:

{
  "fileId": "uuid",
  "multipartUploadId": "uuid",
  "status": "UPLOADING",
  "chunkSize": 67108864,
  "totalParts": 1600,
  "completedParts": [
    {
      "partNumber": 1,
      "etag": "\"etag-1\"",
      "sizeBytes": 67108864
    },
    {

7. 만료 URL 재발급

UNIQUE(multipart_upload_id, part_number)

동일 Part 동시 업로드 방지:

==================================================
35. 파일 전체 무결성 Hash
==================================================

SHA-256 정책:

가능하면 클라이언트에서 파일 전체 SHA-256 계산.

단, 100GB 모바일 파일의 전체 Hash는
시간·배터리·추가 읽기 비용이 크다.

권장 정책:

A. 발신자 기기에서 업로드와 동시에 Streaming SHA-256 계산
B. 계산 중간 상태 저장은 일반적으로 어렵기 때문에 파일 단위 완료 시 확정
C. 서버 검증 Worker가 필요 시 R2 객체를 스트리밍하며 Hash 계산
D. 고위험 또는 증빙 요구 파일은 서버 Hash 필수
E. 대용량 저위험 미디어는 정책에 따라 업로드 중 클라이언트 Hash + 크기 검증 조합 사용

무결성 상태:

PENDING
VERIFIED
FAILED
NOT_FULLY_VERIFIED

확인증에 Hash를 포함하려면
VERIFIED 상태가 필요하다.

67. 운영 아키텍처 기본 원칙
==================================================

SENDSEAL 운영 구조는 API 서버 하나에 모든 작업을 몰아넣지 않는다.

동기 처리:

- 인증
- 권한 확인
- 견적
- 크레딧 예약
- Transfer 생성
- Presigned URL 발급
- 상태 조회
- 수령 완료 요청 접수

비동기 처리:

- 보안 검사
- Push 발송
- PDF 생성
- 삭제 작업
- 삭제 검증
- 만료 처리
- 업로드 중단 정리
- 위험 점수 계산
- 통계 집계
- IAP 환불 처리
- Legal Hold 반영
- 감사 로그 장기 저장

핵심 원칙:

1. 사용자 요청 응답과 장시간 작업을 분리한다.
2. Worker 장애가 API 장애로 번지지 않게 한다.
3. 모든 비동기 작업은 재시도 가능해야 한다.
4. 작업 중복 실행을 전제로 멱등성을 보장한다.
5. 성공 여부를 DB 상태와 감사 로그로 남긴다.
6. 삭제 작업은 성공 확인 전 완료 처리하지 않는다.
7. Queue 지연을 운영 대시보드에 표시한다.
8. 비동기 작업은 우선순위를 가진다.

------------------------------------------
68-1. upload-verification-queue
------------------------------------------

트리거:

Transfer의 모든 파일 Multipart Complete 성공

작업:

- R2 HEAD 검증
- 파일 수 검증
- 총용량 검증
- Object Key 확인
- 누락 Object 확인
- size mismatch 확인
- 무결성 상태 갱신

성공:

VERIFYING_UPLOAD
→ UPLOAD_VERIFIED

실패:

재시도 가능:
VERIFYING_UPLOAD 유지

최종 실패:
UPLOAD_FAILED

------------------------------------------
68-2. security-scan-queue
------------------------------------------

작업:

- MIME 검사
- Magic Byte 검사
- 금지 포맷
- Hash 정책 검사
- 악성코드 검사
- 위험 점수 입력
- 수동 검토 분기

우선순위:

1순위:
일반 전송 10GB 이하

2순위:
대용량 전송 중 저위험 미디어

3순위:
고위험 파일

4순위:
수동 검토 필요

고위험 파일은 사용자 대기 시간이 길어질 수 있으므로
별도 Worker Pool로 분리한다.

- 필수 데이터 누락
- Object 영구 부재

권장 백오프:

1회: 10초
2회: 30초
3회: 2분
4회: 10분
5회: 30분
6회 이후: 운영자 검토

Dead Letter Queue:

- 최대 재시도 초과
- 데이터 불일치
- 예상하지 못한 예외
- 삭제 실패 장기 지속

75. Legal Hold
==================================================

Legal Hold는 법적 보존 요청 또는 수사·분쟁 대응을 위해
자동 삭제를 일시 중단하는 기능이다.

필드:

- id
- transfer_id
- reason
- authority_reference
- requested_by
- approved_by
- starts_at
- expires_at
- status

상태:

REQUESTED
APPROVED
ACTIVE
RELEASED
EXPIRED
REJECTED

Legal Hold 활성 시:

- 자동 삭제 중단
- deletion_job BLOCKED_BY_LEGAL_HOLD
- 사용자 화면에는 보안상 상세 사유 비노출 가능
- 관리자 감사 로그 필수
- 해제 시 삭제 재개

주의:

Legal Hold는 관리자 임의 보관 기능이 아니다.
