[SWIMNOTE 슈퍼관리자 — 테스트 운영처 삭제 전 정밀 확인]

목적:
현재 슈퍼관리자 '운영처 관리'에 총 12개 운영처가 존재한다.

이 중 아래 5개는 실제 사용/보존 대상이므로 절대 삭제하면 안 된다.

[절대 보존 — 5개]
1. 심사용 관리자
2. 토이키즈스윔클럽
3. 스윔노트 공식
4. 키즈앤쿠아
5. 경인여대수영장

위 5개를 제외한 나머지 7개는 개발/테스트 과정에서 생성된 테스트 운영처로 파악하고 있다.

예:
- 울산 북구국민체육센터
- SWIMNOTE Demo Pool
- CC Gate Pool A
- TEST 계열
- 기타 Replit 개발/테스트 과정에서 생성된 운영처

하지만 이번 단계에서는 절대 삭제하지 마라.

먼저 Production DB의 실제 데이터를 조사해서
'보존 5개 + 삭제 후보 7개'가 정확히 맞는지 확정 보고해야 한다.

━━━━━━━━━━━━━━━━━━━━━━
1. Production DB 기준 전체 운영처 조사
━━━━━━━━━━━━━━━━━━━━━━

슈퍼관리자 화면 표시값만 보고 판단하지 말고,
실제 Production DB의 canonical pool/organization/tenant 테이블을 기준으로 조사한다.

현재 존재하는 전체 운영처를 정확히 조회한다.

각 운영처별로 최소 다음을 보고한다.

- 운영처 DB ID / pool_id
- 운영처명
- 코드가 있다면 code
- 담당자/owner 표시값
- 상태
- 플랜
- 생성일
- 회원 수
- 관리자 계정 수
- 선생님 계정 수
- 학부모 계정 수
- 관련 class 수
- 관련 diary/feed 수
- 관련 attendance 수
- 관련 media/file 수
- 결제/subscription 관련 데이터 존재 여부
- X MODE 관련 데이터 존재 여부
- 삭제 시 연결되어 영향을 받는 주요 테이블

확인할 수 없는 항목은 추측하지 말고
'확인하지 못함'으로 표시한다.

━━━━━━━━━━━━━━━━━━━━━━
2. 절대 보존 5개 식별
━━━━━━━━━━━━━━━━━━━━━━

아래 5개를 Production DB에서 정확한 ID로 식별한다.

- 심사용 관리자
- 토이키즈스윔클럽
- 스윔노트 공식
- 키즈앤쿠아
- 경인여대수영장

이름이 조금 다르게 저장되어 있거나
중복된 운영처가 존재한다면 임의 판단하지 말고 보고한다.

이 5개와 연결된 데이터는 어떠한 경우에도 수정/삭제하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
3. 나머지 7개 삭제 후보 확인
━━━━━━━━━━━━━━━━━━━━━━

전체가 정확히 12개이고
위 보존 대상이 정확히 5개라면
나머지 7개를 삭제 후보로 분류한다.

각 삭제 후보에 대해:

- 정확한 운영처명
- 정확한 DB ID
- 생성일
- 테스트 데이터로 판단할 수 있는 근거
- 실제 사용자/운영 데이터 존재 여부
- 삭제 시 같이 삭제되거나 orphan이 될 데이터
- R2/media 파일 존재 여부
- auth/user 계정 영향
- subscription/payment 영향

을 확인한다.

특히 '울산 북구국민체육센터' 및
Replit이 개발 테스트 과정에서 만든 운영처가
어떤 ID인지 명확히 식별한다.

이름만 보고 삭제 대상으로 확정하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
4. 삭제 로직 사전 조사
━━━━━━━━━━━━━━━━━━━━━━

현재 SWIMNOTE에서 운영처 삭제가 어떤 방식인지 조사한다.

- hard delete인지
- soft delete인지
- deleted_at/status 방식인지
- cascade FK가 설정되어 있는지
- application-level cleanup인지
- 회원/반/출결/일지/미디어/알림 등의 처리 방식
- 사용자 계정 처리 방식
- R2 object 처리 방식
- subscription/payment 기록 처리 방식
- audit/history 보존 여부

현재 슈퍼관리자에 '삭제 예정' 기능이 있다면
그 기능의 실제 동작도 확인한다.

운영처 row만 삭제해서
연결 데이터가 orphan으로 남는 방식은 사용하면 안 된다.

━━━━━━━━━━━━━━━━━━━━━━
5. 이번 단계 절대 금지
━━━━━━━━━━━━━━━━━━━━━━

이번 지시는 삭제 실행 지시가 아니다.

절대 하지 말 것:

- Production 운영처 DELETE
- soft delete 실행
- 삭제 예정 상태 변경
- 회원 삭제
- user/auth 계정 삭제
- class 삭제
- diary/feed 삭제
- attendance 삭제
- media/R2 삭제
- subscription/payment 수정 또는 삭제
- DB migration
- schema 변경
- 코드 수정
- Production deploy
- OTA

오직 조사 및 삭제 영향 분석만 한다.

━━━━━━━━━━━━━━━━━━━━━━
6. 완료보고
━━━━━━━━━━━━━━━━━━━━━━

다음 형식으로 보고한다.

A. Production 전체 운영처 수

B. 전체 운영처 목록
각 운영처:
- name
- pool_id
- owner
- created_at
- status
- plan
- members
- 주요 연결 데이터 요약

C. 절대 보존 5개
각각 정확한 pool_id 포함

D. 삭제 후보
정확히 몇 개인지 표시하고
각각:
- name
- pool_id
- 테스트 데이터 근거
- 연결 데이터 규모
- 실제 사용자 데이터 가능성
- 삭제 영향

E. 울산 북구국민체육센터 확인 결과

F. Replit/개발 테스트 생성 운영처 확인 결과

G. 현재 운영처 삭제 메커니즘
- hard/soft delete
- cascade
- auth
- DB child records
- R2
- payment/subscription
- audit/history

H. 안전한 삭제 방법 제안
실제 실행은 하지 말고,
확인된 schema와 관계를 기준으로
7개 테스트 운영처를 완전히 정리하려면
어떤 순서와 방법이 필요한지만 제시한다.

I. 최종 확인 문장

반드시 마지막에 다음 형식으로 작성:

"보존 대상 5개: [실제 DB 이름 + ID]"
"삭제 후보 N개: [실제 DB 이름 + ID]"
"아직 삭제하지 않았습니다."

중요:
이번 조사 결과를 사용자가 확인하고
별도로 삭제 승인을 내리기 전까지
어떠한 데이터도 삭제하지 마라.
