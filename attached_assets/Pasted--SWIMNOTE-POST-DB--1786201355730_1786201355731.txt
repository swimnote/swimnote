[SWIMNOTE 업무대화 실시간 갱신 수정 지시]

현재 확인된 상태
- 선생님 ↔ 학부모 업무대화 메시지 POST 전송 정상
- DB 저장 정상
- 모달을 닫았다 다시 열면 상대방 메시지 정상 조회
- 문제: 대화 모달을 계속 열어둔 상태에서는 새 메시지가 화면에 나타나지 않음
- 따라서 현재 문제는 송수신/DB/API 문제가 아니라 열린 Thread Modal의 메시지 갱신 문제임

목표
업무대화 모달을 열어둔 상태에서도 양쪽 대화가 자연스럽게 갱신되도록 수정한다.

중요:
기존 업무요청/알림/읽음/완료/거절/업무처리/navigation/API 계약을 변경하지 않는다.
WebSocket 등 대규모 구조 변경은 이번 작업에서 하지 않는다.
최소 수정으로 구현한다.

==================================================
FIX-1. 선생님 업무대화 모달 자동 갱신
==================================================

대상:
RequestThreadModal.tsx

현재 메시지 최초 조회 함수와 state 구조를 먼저 확인한다.

모달 visible=true인 동안에만
기존 GET
/parent-requests/:requestId/messages
를 주기적으로 다시 호출한다.

권장 polling:
약 2초 간격

조건:
- visible=false이면 polling 즉시 중단
- requestId 없으면 실행 금지
- 컴포넌트 unmount 시 interval 반드시 clear
- 동일 요청에 interval 중복 생성 금지
- polling 조회 중 전체 화면 loading UI를 반복 표시하지 말 것
- polling 실패 한 번으로 모달을 닫거나 Alert를 반복 표시하지 말 것
- 기존 메시지는 유지하고 다음 polling에서 재시도 가능해야 함

==================================================
FIX-2. 학부모 업무대화 모달 자동 갱신
==================================================

대상:
ParentRequestThreadModal.tsx

선생님 모달과 동일한 방식으로 적용.

visible=true 동안 약 2초마다 기존 GET API 재조회.

모달 닫기/unmount 시 polling 제거.

==================================================
FIX-3. 내가 보낸 메시지는 즉시 표시
==================================================

POST 성공 후 다음 polling까지 기다리지 않게 한다.

선생님/학부모 양쪽 모두:

메시지 POST 성공
→ 즉시 messages 재조회
→ 화면 갱신
→ 입력창 clear

가능하다면 POST 응답이 생성된 message object를 정상 반환하고 있는지도 확인한다.

단, API Contract를 불필요하게 변경하지 말 것.

현재 POST 응답만으로 안전하게 state append할 수 없다면
POST 성공 직후 기존 GET을 한 번 호출하는 방식을 사용한다.

중복 bubble이 생기지 않아야 한다.

==================================================
FIX-4. 자동 스크롤
==================================================

새 메시지가 추가되면 대화창이 최신 메시지 위치를 보여주도록 한다.

FlatList라면:
scrollToEnd()

ScrollView라면:
scrollToEnd({ animated: true })

단,
polling마다 메시지 변화가 없는데 계속 강제 스크롤하지 말 것.

메시지 개수 또는 마지막 message id가 실제로 변경됐을 때만 실행하는 방식 우선.

==================================================
FIX-5. Race / 중복 요청 방지
==================================================

polling GET이 아직 진행 중인데 다음 interval이 실행되어
동일 GET이 겹치지 않도록 방어한다.

예:
fetchingRef.current

GET 시작:
fetchingRef.current = true

finally:
fetchingRef.current = false

이미 true이면 해당 polling cycle skip.

POST 중복 탭 방지용 sending 상태도 기존 구현을 확인하고,
없다면 최소한의 sending guard 적용.

==================================================
FIX-6. 읽음 처리 유지
==================================================

GET /messages 조회 시 상대방 메시지를 읽음 처리하는 현재 서버 동작을 그대로 유지한다.

따라서 상대방이 모달을 열어놓은 상태라면
polling GET으로 새 메시지를 받아오면서 기존 읽음 처리도 정상 수행되어야 한다.

읽음 처리 API 구조를 새로 만들지 않는다.

==================================================
FIX-7. 앱 상태 고려
==================================================

가능하면 앱이 background 상태일 때 불필요한 polling을 계속하지 않도록 현재 구조를 확인한다.

최소 필수 조건은:
모달 visible일 때만 polling.

AppState까지 추가하는 것이 기존 구조를 복잡하게 만든다면 이번 수정에서는 생략 가능.

실기기 CASE
==================================================

CASE 1
선생님과 학부모가 같은 업무대화창을 동시에 연다.

CASE 2
학부모가 "안녕하세요" 전송
→ 학부모 자기 화면 즉시 표시

CASE 3
선생님은 창을 닫거나 다시 열지 않아도
약 2초 이내 "안녕하세요" 표시

CASE 4
선생님 답변 전송
→ 선생님 자기 화면 즉시 표시

CASE 5
학부모 화면도 닫았다 열지 않고 약 2초 이내 답변 표시

CASE 6
메시지가 중복 bubble로 나타나지 않음

CASE 7
polling 때문에 화면 전체 loading이 2초마다 깜빡이지 않음

CASE 8
모달 닫은 뒤 GET 요청 polling 중단

CASE 9
다른 request thread를 열었을 때 이전 request polling이 남아있지 않음

CASE 10
전송 버튼 연타로 동일 메시지 중복 전송되지 않음

CASE 11
업무처리/확인/거절 기존 기능 정상

CASE 12
일반 쪽지 및 학부모 알림 기능 회귀 없음
