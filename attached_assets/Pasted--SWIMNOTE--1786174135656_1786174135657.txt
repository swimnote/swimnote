3. 학부모 요청 Source of Truth
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

학부모 요청 원본:

parent_student_requests

를 유지한다.

학부모가 요청을 보냈다고 해서
별도의 문의 레코드를 중복 생성하여
원본을 두 개로 만들지 않는 것을 우선한다.

가능하면 문의하기 "수신함" API/UI가:

기존 문의 데이터
+
parent_student_requests

합쳐서 보여주는 구조로 구현한다.

즉:

원본 요청 데이터
= parent_student_requests

선생님 수신 UI
= 문의하기 수신함

이다.

DB schema를 새로 만드는 방식은 금지.

5. 공지로 들어가는 학부모 요청 제거
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 학부모 요청 생성 시
선생님 메신저 "공지"에 다음과 같은 카드가 생성된다:

[결석 신청] ...
[보강 요청] ...

이 경로를 정확히 찾아 제거한다.

중요:

제거 대상은 오직:

"parent request 생성 때문에 messenger notice/공지에
복제되는 경로"

뿐이다.

기존 관리자/선생님 일반 공지 기능
기존 messenger notice
기존 시스템 공지
기존 반 이동 안내

절대 수정하지 않는다.

즉 공지 기능을 없애는 것이 아니다.

학부모 요청을 공지에 넣는 side effect만 제거한다.

7. 요청 상태 표시

수신함을 열었다고

10. 발신함 보호
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

11. 수신함 데이터 통합 방법
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

목표:

수신함 데이터:

+
현재 선생님에게 배정된 parent_student_requests

type InboxItem =

각 원본 ID/type을 유지한다.

DB를 하나로 합치기 위한 Migration 금지.

21. 구현 완료 조건
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

최소 코드 기준:

1. Parent request가 공지로 복제되지 않음.
2. 일반 공지 기능은 그대로 작동.
3. Parent request가 담당 선생님의 문의하기 수신함에 표시.
4. 다른 선생님에게 미표시.
5. 기존 문의 수신 데이터도 그대로 표시.
6. 기존 발신함 그대로 유지.
7. 학부모 요청 읽음 처리 가능.
8. done/rejected 처리 가능.
9. 처리 후 학부모 결과 notification/push 기존 흐름 유지.
10. unread count 계산 가능.

위 코드가 실제 구현되지 않았는데
완료 보고 금지.

23. 구현 후 검증
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

구현 완료 후에만 다음 확인.

CASE 1
학부모 결석 요청 생성
→ 선생님 공지에 새 카드 생성되지 않음.

CASE 2
담당 선생님 문의하기 > 수신함
→ 요청 표시.

CASE 3
다른 선생님
→ 요청 미표시.

CASE 4
기존 문의 데이터
→ 그대로 표시.

CASE 5
발신함
→ 기존 데이터 정상.

CASE 6
요청 읽음
→ unread 해제.

CASE 7
done
→ 학부모 결과 알림.

CASE 8
rejected
→ 학부모 결과 알림.

CASE 9
기존 Messenger 공지
→ 정상.

CASE 10
긴 요청 여러 개
→ 목록 스크롤 정상.

실기기 검증을 못 한 것은
PENDING_DEVICE_TEST로 보고.
