현재 보고서에서 반이동 버튼 오류를 사실상 원인 확정처럼 작성한 부분을 수정한다.

런타임 로그가 아직 없으므로 아래처럼 구분한다.

[확정된 사실]

- ClassDetailSheet의 반이동 버튼 onPress는 setMoveStudent(st)를 호출하도록 작성되어 있음
- SubSheetModal은 메인 Modal 내부 중첩이 아니라 Fragment 형제 구조임
- today-schedule에서 전달하는 classGroups는 sortedItems 기반의 당일 반 목록임
- 이 구조에서는 당일 반이 1개뿐이면 moveTargetClasses가 0개가 될 수 있음

[아직 미확정]

- 실제 기기에서 onPress가 호출되는지
- moveStudent 상태가 변경되는지
- SubSheetModal이 렌더링되는지
- 부모 responder가 터치를 가로채는지
- my-schedule에서도 동일 원인인지
- 버튼이 눌리지 않는 것인지, 눌렸지만 이동 대상이 0개인 것인지

오류 A의 최종 판정은 다음처럼 표시한다.

- today-schedule의 이동 대상 목록 부족: 구조적 결함 확정
- my-schedule 버튼 미작동: 런타임 로그 필요
- responder 충돌: 원인 후보
- 전체 오류 A: 부분 원인 확정 / 전체 원인 미확정

“원인 확정”이라고 단정하지 않는다.

3. 학생 상태 변경 공통 처리 함수 존재 여부 재조사
━━━━━━━━━━━━━━━━━━━━━━

현재 보고서는 다음 라우트를 각각 수정하는 방식이다.

- change-status
- remove-from-class
- move-class
- apply-pending-now

이 방식은 중복 로직이 생길 수 있다.

먼저 Repository 전체에서 아래 기능을 담당하는 공통 함수·서비스가 있는지 조사한다.

검색 대상:

- student_class_history INSERT/UPDATE
- left_at 갱신
- enrolled_at 갱신
- class_group_id 초기화
- assigned_class_ids 초기화
- status 변경
- pending change 적용
- remove from class
- move class
- class assignment service
- student assignment service
- history service

반드시 표로 제출한다.

| 처리 경로 | 실제 파일 | 실제 함수 | history 처리 | 공통 함수 사용 여부 |
|---|---|---|---|---|

확인할 경로:

1. change-status immediate
2. change-status next_month
3. remove-from-class now
4. remove-from-class future
5. move-class
6. apply-pending-now
7. 관리자 화면의 동일 처리 경로
8. 선생님 화면의 동일 처리 경로
9. 기타 status 변경 API

판정 기준:

A. 공통 함수가 존재하면
- 해당 함수 한 곳에서 history 종료 규칙을 적용
- 각 route 중복 수정 금지

B. 공통 함수가 없으면
- 신규 공통 함수 도입안 제출
- 기존 route들을 이 함수로 점진적으로 모을지
- 이번 긴급 수정 범위에서 최소 2개 경로만 고칠지
두 안을 비교해서 권장안 1개 제출

신규 공통 함수 예시 역할:

closeActiveClassAssignments({
  tx,
  studentId,
  effectiveDate,
  classIds?,
})

단, 함수명·위치는 Repository 구조 확인 후 실제 기준으로 제안한다.
추정 파일명 사용 금지.

4. today-schedule 전체 반 목록 공급 방식 재조사
━━━━━━━━━━━━━━━━━━━━━━

새 API를 추가한다는 전제부터 두지 않는다.

먼저 today-schedule 화면 또는 상위 Provider/Hook에 이미 전체 반 목록이 있는지 조사한다.

확인 대상:

- groups state
- classGroups state
- teacher classes query
- /teachers/me/classes
- 기존 React Query cache
- 스케줄러 공통 hook
- 관리자/선생님 반 목록 API
- props로 이미 내려오는 데이터
- 전역 Store/Context

다음 우선순위로 설계한다.

1순위:
이미 로드된 전체 반 목록 state 재사용

2순위:
기존 query cache 재사용

3순위:
기존 전체 반 조회 API 호출

4순위:
정말 없을 때만 신규 API 검토

최종 보고에는 아래를 포함한다.

- today-schedule이 현재 보유한 반 목록
- 당일 일정 목록과 전체 반 목록의 차이
- 기존 전체 반 query 존재 여부
- 추가 네트워크 호출 없이 해결 가능한지
- query key
- cache stale time
- 권한 범위
- 추천 최종안 1개

“API 조회 추가”라는 표현만 쓰지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
5. 오류 B 클라이언트 분리는 유지
━━━━━━━━━━━━━━━━━━━━━━

아래 설계는 유지한다.

studentListMode:
- historical
- current

historical 모드:

- studentsByDate가 있으면 해당 데이터만 사용
- undefined이면 로딩 상태
- 빈 배열이면 실제 빈 명단
- 현재 students fallback 금지

current 모드:

- 기존 현재 배정 학생 목록 사용
- 기존 동작 유지

단, historical 판정 기준을 정확히 명시한다.

예:

- 날짜 파라미터가 존재한다고 무조건 historical로 보지 않는다.
- 선택 날짜가 오늘 이전인지
- API가 date-specific snapshot 조회인지
- today-schedule은 오늘 날짜라도 date API를 사용하는지

호출처별 최종 정책표를 제출한다.

| 화면 | 선택 날짜 | 모드 | 데이터 원본 |
|---|---|---|---|
| my-schedule 과거 날짜 | 7/25 | historical | date API |
| my-schedule 오늘 | 8/3 | current 또는 historical 중 확정 | 실제 코드 기준 |
| today-schedule | 오늘 | historical 또는 current 중 확정 | 실제 코드 기준 |
| 관리자 classes 과거 날짜 | 과거 | historical | 실제 API |
| 관리자 classes 오늘 | 오늘 | 확정 필요 | 실제 코드 |

현재 보고서의 “오늘/날짜 미선택=current”는 실제 데이터 정책과 충돌할 수 있으므로 Repository 기준으로 다시 확정한다.

━━━━━━━━━━━━━━━━━━━━━━
6. 과거 명단 직접 원인 문구 정리
━━━━━━━━━━━━━━━━━━━━━━

현재 확인된 김안 사례는 다음처럼 정리한다.

[DB 확인 사실]

- 7월 25일 기준 student_class_history 조건은 충족
- 8월 3일 기준 left_at 경계로 제외
- 서버 날짜 API 시뮬레이션은 7월에 학생을 정상 반환
- 현재 students는 suspended / class_group_id=null / assigned_class_ids=[]
- 과거 UI에서 학생이 사라진 것은 date API 결과가 아니라 현재 students fallback을 사용한 결과

따라서 김안 사례의 직접 원인은:

“서버 과거 배정 이력 손실”이 아니라
“클라이언트가 과거 날짜 데이터 로딩 전 또는 부재 시 현재 학생 목록으로 fallback한 것”

으로 명확히 적는다.

다만 별도 서버 결함은 존재한다.

- change-status immediate에서 history 종료 누락
- remove-from-class new_status 즉시 처리에서 history 종료 누락

이 둘은 김안 사례의 직접 원인과 분리해서 작성한다.

정리 형식:

A. 김안 과거 명단 소실 직접 원인
→ 클라이언트 historical fallback 오류

B. 별도 발견된 서버 데이터 정합성 결함
→ 일부 상태 변경 경로 history 종료 누락

둘을 하나의 원인처럼 섞지 않는다.

━━━━━━━━━━━━━━━━━━━━━━
7. Transaction 설계 보완
━━━━━━━━━━━━━━━━━━━━━━

서버 수정안은 반드시 다음 순서를 따른다.

1. 동일 transaction 안에서 students 행 잠금
2. 현재 활성 class id 목록 확정
3. effectiveDate 기준 history 종료
4. students 상태/배정 변경
5. 변경 로그 또는 audit 기록
6. commit

확인할 것:

- `SELECT ... FOR UPDATE` 실제 Drizzle 작성 방식
- `CURRENT_DATE`와 Asia/Seoul 날짜 차이
- 서버 DB timezone
- 클라이언트가 effective_date를 보내는 경로
- 서버가 날짜를 자체 결정하는 경로
- 오늘 경계가 UTC로 하루 밀리지 않는지

즉시 처리의 날짜는 무조건 `CURRENT_DATE`라고 단정하지 않는다.
기존 서비스의 날짜 기준이 Asia/Seoul이면 동일 기준 함수 사용 여부를 확인한다.

최종 제출에는 날짜 정책표를 포함한다.
