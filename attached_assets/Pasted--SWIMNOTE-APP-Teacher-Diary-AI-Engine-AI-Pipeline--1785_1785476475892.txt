3. 앱 Request Contract
━━━━━━━━━━━━━━━━━━━━━━

최종 전송 구조:

{
  "request_id": "diary_<UUID>",
  "schema_version": "1.0",
  "feature": "teacher_diary",
  "locale": "ko-KR",
  "input": {
    "text": "<trim 처리한 교사 원문>"
  },
  "context": {
    "pool_id": "<swimming_pool_id>",
    "class_id": "<class_group_id>",
    "lesson_date": "<YYYY-MM-DD>",
    "student_refs": [
      "<student.id>"
    ],
    "students": [
      {
        "ref": "<student.id>",
        "name": "<student.name 전체>"
      }
    ]
  }
}

원칙:

- name 전체를 그대로 보냅니다.
- given_name을 생성하지 않습니다.
- 이름에서 성을 제거하지 않습니다.
- 교사 입력에서 학생 이름을 앱이 찾지 않습니다.
- 공통/학생별 문장을 앱이 분리하지 않습니다.
- 앱에서 수영 용어를 보충하지 않습니다.
- curriculum/template/knowledge를 앱이 추측하여 넣지 않습니다.
- student_refs와 students[].ref의 집합 일치 여부만 검증합니다.

현재 보고상 이 Payload는 이미 대부분 구현되어 있으므로,
AI Engine Contract와 정확히 일치하는지만 확인하십시오.

━━━━━━━━━━━━━━━━━━━━━━
4. Response Contract
━━━━━━━━━━━━━━━━━━━━━━

목표 응답:

{
  "request_id": "diary_<UUID>",
  "schema_version": "1.0",
  "feature": "teacher_diary",
  "result": {
    "common": "공통 일지",
    "students": [
      {
        "student_ref": "student_xxx",
        "content": "학생별 일지"
      }
    ]
  },
  "meta": {},
  "usage": {}
}

앱 정규화 결과:

{
  commonContent: string,
  studentNotes: [
    {
      studentId: string,
      content: string
    }
  ]
}

검증:

- response.request_id === request.request_id
- schema_version 지원 여부
- result.common string
- result.students array
- student_ref가 요청 student_refs에 존재
- student_ref 중복 없음
- content string
- common과 students 모두 비어 있으면 오류
- 알 수 없는 학생 ref가 하나라도 있으면 정상 삽입 금지

AI Engine 최종 Contract가 확정되면
dual-field 임시 호환 처리보다 정식 단일 Contract를 우선하십시오.

단, Production 전환 완료 전까지 rollback을 위해 기존 normalize 로직을 삭제하지 마십시오.

6. 인증 방식
━━━━━━━━━━━━━━━━━━━━━━

현재 앱 JWT를 그대로 AI Engine에 보낼지,
SWIMNOTE API Server를 Proxy로 사용할지는
AI Engine 리플릿의 인증 조사 결과 후 확정합니다.

직접 호출 방식:

App
→ Authorization: Bearer App JWT
→ AI Engine

Proxy 방식:

App
→ SWIMNOTE API Server
→ 인증 및 권한 검증
→ Server-to-Server Token
→ AI Engine

AI Engine이 앱 JWT를 검증할 수 없는 상태라면
직접 호출을 강행하지 마십시오.

보안상 기본 권장안은 Proxy 방식이지만,
현재 Repository와 인증 구조 조사 후 최종 결정하십시오.

━━━━━━━━━━━━━━━━━━━━━━
7. 구형 일반 GPT Endpoint
━━━━━━━━━━━━━━━━━━━━━━

현재 SWIMNOTE API Server의 일반 GPT 직접 호출은
즉시 삭제하지 마십시오.

대신 다음 상태로 분리하십시오.

- legacy endpoint: rollback 전용
- grounded endpoint: 신규 AI Engine 연결
- feature flag로 선택
- 기본값은 Preview에서만 grounded
- Production은 실기기 E2E 승인 후 전환

금지:

- 새 Engine 실패 시 사용자에게 알리지 않고 legacy GPT로 자동 우회
- Grounded 실패를 정상 AI 결과로 위장
- fallback 결과에 pipeline_mode를 grounded로 표시

Fallback이 필요한 경우 명시적으로 로그에 남기고,
Production 정책은 별도 승인받으십시오.

8. 진행 상태
━━━━━━━━━━━━━━━━━━━━━━

SEARCHING
→ GENERATING

화면 문구와 실제 서버 단계가 일치해야 합니다.
