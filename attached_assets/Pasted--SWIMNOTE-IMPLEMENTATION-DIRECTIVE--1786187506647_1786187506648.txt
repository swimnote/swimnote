0. 절대 원칙
==================================================

이번 작업은 "조사 후 보고하고 승인 대기" 작업이 아니다.

1) 시작 전에 최신 Production/Git 기준선을 확인한다.
2) 아래 요구사항을 실제 코드와 대조한다.
3) 기존 route/API/데이터 구조를 최대한 재사용하는 최소 수정안을 결정한다.
4) 문제가 확인되면 즉시 구현한다.
5) TypeCheck / Diff Gate를 통과시킨다.
6) 서버 수정이 있으면 Production Render 반영까지 한다.
7) 앱 수정이 있으면 production OTA까지 한다.
8) 마지막에 구현 결과만 최종 보고한다.

단, 조사 결과 아래 계획이 실제 Repository 구조와 충돌하거나
기존 기능을 파괴할 위험이 발견될 경우에만 구현을 중단하고 보고한다.

과거 branch/backup/hotfix로 checkout/revert 금지.
현재 최신 deploy-photo-clone 기준선에서만 작업한다.

DB Migration은 원칙적으로 금지.
기존 DB/API로 해결 가능한지 먼저 확인한다.

Force push 금지.
Preview OTA 금지.
Production 외 임의 배포 금지.

1. 현재 실기기에서 확인된 상태
==================================================

[정상]

A. 학부모가 요청을 생성할 수 있음.
B. 학부모 "내 요청"에 생성한 요청이 표시됨.
C. 선생님 홈 우측 봉투 버튼에 unread 빨간 점이 표시됨.
D. 홈의 "쪽지 · 학부모 요청" Bottom Sheet에 새 학부모 요청이 표시됨.
E. 요청이 새로 들어오면 Bottom Sheet unread 숫자가 증가함.
F. 학부모 요청이 기존 Messenger 공지 채널로 들어가던 문제는 이전 작업에서 제거됨.

즉, 요청 생성/전달 자체는 살아 있음.

[현재 문제]

문제 1.
선생님 홈 Bottom Sheet에는 신규 요청이 보이는데

선생님:
쪽지보관함
→ 학부모 요청

정식 목록에는 같은 신규 요청이 나타나지 않는다.

실기기 예:

홈 Bottom Sheet:
- 상담 요청 1건
- 보강 요청 1건

총 unread 2건 표시

그런데 쪽지보관함 > 학부모 요청에는
예전 결석 신청 1건만 표시됨.

따라서 홈 Bottom Sheet와 정식 학부모 요청 탭의 데이터가 불일치한다.

--------------------------------------------------

문제 2.
홈 Bottom Sheet의 학부모 요청 날짜가

NaN/NaN

으로 표시된다.

사용자에게 NaN / Invalid Date 등이 절대 노출되어서는 안 된다.

--------------------------------------------------

문제 3.
홈 Bottom Sheet는 요청의 일부 정보만 보여주고,
정식 학부모 요청함에서도 실제 요청을 확인/처리하는 흐름이 충분히 연결되어 있는지 재확인이 필요하다.

학부모가 보낸 실제 content가 유실되면 안 된다.

목록에서는 긴 내용 전체를 강제로 펼칠 필요는 없지만,
카드를 눌렀을 때 최소한 해당 요청의 실제 전체 내용을 확인할 수 있어야 한다.

--------------------------------------------------

문제 4.
요청 유형별 실제 업무 화면 연결이 없다.

학부모 요청은 단순 메시지가 아니라 업무 요청이다.

따라서 기존 앱에 해당 기능의 실제 업무 화면이 존재하는 경우
요청 카드에서 해당 업무 화면으로 바로 연결한다.

2. 이번 작업의 핵심 원칙 — Single Source of Truth
==================================================

홈 Bottom Sheet와

(teacher)/messages-inbox.tsx
→ "학부모 요청"

은 서로 다른 방식으로 요청을 해석하거나
별도의 임시 데이터 구조를 만들어서는 안 된다.

두 UI가 동일한 서버의 학부모 요청 데이터 Contract를 기준으로 동작하도록 한다.

우선 실제 Repository에서 다음을 확인한다.

GET /teacher/parent-requests

현재 실제 response shape
실제 필드명
created_at 필드 존재 여부
content 필드 존재 여부
request_type
student_id
student_name
parent_id / parent_name
status
is_read_by_teacher
기타 필요한 실제 필드

추측해서 필드명을 만들지 말 것.

서버의 실제 response와 두 클라이언트의 interface/parser를 직접 비교한다.

특히 이전 수정에서 서버 response가

{
  success: true,
  data: rows.rows
}

형태로 변경되었으므로
홈 Bottom Sheet와 messages-inbox가 각각 무엇을 읽고 있는지 반드시 확인한다.

3. FIX-1 — 홈과 정식 학부모 요청함 데이터 불일치 수정
==================================================

현재 증상:

홈 Bottom Sheet = 신규 요청 표시됨
messages-inbox 학부모 요청 탭 = 신규 요청 누락

원인을 실제 코드/API에서 찾고 수정한다.

반드시 확인할 것:

- 두 화면이 호출하는 endpoint
- response parsing
- d.data / raw array 차이
- 캐시 여부
- focus 시 reload 여부
- pull-to-refresh 여부
- teacher visibility 조건
- status filtering
- read/unread filtering
- student current class membership 조건

정상 목표:

같은 선생님 계정에서 동일 시점 기준

홈 Bottom Sheet에 보이는 학부모 요청
=
쪽지보관함 > 학부모 요청에 존재하는 요청

이어야 한다.

단, Bottom Sheet가 "최근/미읽음 preview"만 보여주는 구조라면
정식 수신함은 그보다 더 많은 과거 요청을 포함할 수 있다.

반대로 Bottom Sheet에는 있는데 정식 수신함에는 없는 상태는 금지한다.

정식 수신함은 pending뿐 아니라 기존 정책상 보관해야 하는
처리 완료/거절 요청도 정상적으로 확인 가능해야 한다.
