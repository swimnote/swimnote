SWIMNOTE — WP-DIARY-2
일지 저장 후 스케줄러 "일지완료" 미표시 원인 조사
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현상:

선생님이 일지를 실제로 작성하고 저장했는데
스케줄러/오늘수업 화면에서
"일지완료" 표시가 나타나지 않는 문제가 있음.

이번 단계에서는 수정하지 않는다.

목표:
일지 저장 → DB → 스케줄러 조회 → diary_done 계산 → UI 표시
전체 경로에서 실제 실패 지점을 확정한다.

━━━━━━━━━━━━━━━━━━━━
1. 저장 성공 여부부터 확인
━━━━━━━━━━━━━━━━━━━━

일지 저장 시 실제 흐름 추적:

DiaryWriteView / diary.tsx
→ POST /diaries
→ class_diaries INSERT
→ response
→ 앱 성공 처리

반드시 확인:

- 저장된 diary_id
- class_group_id
- lesson_date
- swimming_pool_id
- is_deleted
- HTTP status
- response body

운영 DB를 직접 변경하지 말고
조회만 한다.

━━━━━━━━━━━━━━━━━━━━
2. 스케줄러 완료 판정 Source of Truth 확인
━━━━━━━━━━━━━━━━━━━━

today-schedule 서버 라우트에서
"일지완료"를 어떤 기준으로 계산하는지 실제 코드 제출.

현재 Audit 기준 예상:

SELECT class_group_id
FROM class_diaries
WHERE swimming_pool_id = poolId
AND lesson_date = dateParam
AND is_deleted = false

→ diary_done = diarySet.has(class_group_id)

실제 현재 코드를 다시 확인한다.

━━━━━━━━━━━━━━━━━━━━
3. 가장 중요한 비교
━━━━━━━━━━━━━━━━━━━━

문제가 발생한 실제 일지 1건을 기준으로:

저장된 일지:
- diary_id
- class_group_id
- lesson_date

스케줄러 조회:
- 화면 날짜
- API dateParam
- 스케줄 항목 class_group_id

를 나란히 비교한다.

확인:

saved.class_group_id === schedule.class_group_id ?
saved.lesson_date === dateParam ?
pool_id 동일 ?

셋 중 하나라도 다르면 정확한 불일치 원인 제출.

━━━━━━━━━━━━━━━━━━━━
4. 날짜/KST 경로 조사
━━━━━━━━━━━━━━━━━━━━

일지 저장 날짜와
스케줄러 조회 날짜가 생성되는 전체 경로를 조사.

확인:

- targetDate 생성 방식
- dateParam 생성 방식
- new Date()
- toISOString()
- KST 변환
- UTC 변환
- 자정 경계
- 오늘/과거 날짜 작성 차이

특히 날짜가 하루 밀리는 경우가 있는지 확인.

추측 금지.

━━━━━━━━━━━━━━━━━━━━
5. class_group_id 경로 조사
━━━━━━━━━━━━━━━━━━━━

일지 작성 화면이 사용하는 class_group_id와
스케줄러 카드가 사용하는 class_group_id가
실제로 같은 ID인지 확인.

확인:

- 일반 반
- 보강 학생 포함 수업
- 일회성 반
- 반 이동
- 같은 시간의 다른 반

보강 학생이 추가됐다는 이유로
별도 class id를 사용하는지 확인.

━━━━━━━━━━━━━━━━━━━━
6. 저장 직후 즉시 표시 경로
━━━━━━━━━━━━━━━━━━━━

현재 앱의:

emitDiaryChanged({ lessonDate: ... })

→ today-schedule 구독

흐름을 실제 코드로 확인.

확인:

- event 이름
- payload
- lessonDate
- listener 등록 시점
- 현재 화면이 focus 상태일 때 반영
- diary_done을 어떤 항목에 true로 바꾸는지
- class_group_id 없이 날짜만으로 전체 반을 완료 처리하는 버그가 없는지
- 반대로 아무 반도 못 찾는 구조가 없는지

━━━━━━━━━━━━━━━━━━━━
7. 화면 재진입 시 재조회 확인
━━━━━━━━━━━━━━━━━━━━

스케줄러 화면에서:

useFocusEffect
loadOverview
API 재호출

이 실제로 동작하는지 확인.

즉시 이벤트가 실패해도
화면을 나갔다 들어왔을 때
DB 기준으로 diary_done=true가 되어야 한다.

재진입 후에도 false라면
서버/DB 매칭 문제로 좁힌다.

━━━━━━━━━━━━━━━━━━━━
8. 실기기 재현용 최소 진단 설계
━━━━━━━━━━━━━━━━━━━━

원인이 코드만으로 확정되지 않으면
진단을 문제 화면에만 붙인다.

스케줄러 카드에 임시로:

schedule.class_group_id
schedule.date
diary_done

그리고 저장 직후:

saved.diary_id
saved.class_group_id
saved.lesson_date

를 확인할 수 있게 한다.

일반 다른 화면에 진단 붙이지 않는다.
