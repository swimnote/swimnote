성장 리포트 API 처리 성능 및 목표 처리량 분석

1. 현재 처리 성능

평균 응답 시간 (추정)

단계	소요 시간	비고
Stage B 추출 (gpt-5.4-nano, 일지 N개 × 최대 3 동시)	5–15s	일지 수에 비례
KnowledgeModule 검색 (pgvector + RRF + Voyage reranker)	1–3s	
WP3–WP11 팩트 패키지 빌드 (deterministic)	2–5s	
WP12 GPT 합성 (gpt-5.4-mini, max_tokens=4096)	10–30s	가장 큰 변수
RevisionPipeline (최대 3회 retry 포함)	0–60s	검증 실패 시 증가
p50: 약 25–40초
p95: 약 70–100초
Orchestrator timeout: 120초 (코드에 고정)
실측 수치가 아닌 코드 분석 기반 추정입니다. 실측 p50/p95는 Production 로그(pino) 집계 후 정확히 확인 가능합니다.

동시 처리 가능 수

현재 Render 인스턴스 스펙: Starter 플랜, 단일 인스턴스 (0.5 vCPU, 512MB RAM).

Node.js async 특성상 HTTP 레벨 동시성은 처리 가능하지만 실질적 병목은 두 곳입니다:

OpenAI API: 각 요청이 gpt-5.4-nano (Stage B) + gpt-5.4-mini (합성) 동시 호출 → 10개 동시 요청 시 최대 30개 OpenAI 호출 동시 발생
Render Starter 메모리: 요청당 ~20–50MB 예상, 512MB 한계에서 10–15개 동시가 상한
현재 안정적 동시 처리 상한: 약 5–8개 (Starter 단일 인스턴스 기준)

Rate limit 정책

/api/v1/growth-report/analyze 엔드포인트에는 애플리케이션 레벨 rate limit 없음. OpenAI API 자체의 TPM/RPM 한도가 실질적 상한입니다.

2. 목표 처리량 달성 가능 여부

현재 조건 분석

목표: 200,000건 / 96시간
필요 처리율: 200,000 ÷ 96 ÷ 60 = 34.7건/분
현재 클라이언트 설정:
  - 동시 10개 × 5분마다 호출 = 사이클당 10건
  - 사이클당 필요: 174건 → 현재 10건 (12.4배 부족)
결론: 현재 설정으로는 불가능합니다.

현재 추정 처리율 (p50=30초 기준):

동시 10개 / 30초 = 20건/분
96시간 × 60분 × 20건/분 = 115,200건
→ 목표 200,000건의 약 58%
p50=20초 (최적 조건)로 가정해도:

10개 / 20초 × 60 = 30건/분
96시간 × 30건/분 × 60 = 172,800건 → 여전히 부족
3. 달성을 위해 필요한 업그레이드

우선순위 순으로 정리합니다.

[필수] 동시 요청 수 증가

5분마다 10개 → 5분마다 180개 이상으로 상향 필요. 단, ENGINE 측에서 동시 처리 상한 조정이 선행되어야 합니다.

[필수] Render 인스턴스 업그레이드

현재	권장
Starter (0.5 vCPU, 512MB, 1 instance)	Standard+ (2 vCPU, 2GB, 2–4 instances)
Standard 플랜 × 2인스턴스 기준 동시 30–40건 안정 처리 가능 (추정).

[권장] 호출 주기 변경

5분마다 burst → 연속 호출 (idle 없이 큐 소진 방식)로 전환 시 실효 처리율 최대화.

[선택] 배치 API

현재 배치 엔드포인트 없음. 단일 요청당 1명 학생 분석 구조이므로, 배치 지원 추가 시 오버헤드(인증, idempotency 체크)를 줄일 수 있으나 개발 공수 필요.
