```text

```

```text

```

## TC-10 — 잘못된 날짜 타입·값

다음을 각각 확인하십시오.

```json
{ "xmode_purchased_at": "not-a-date" }
```

```json
{ "xmode_purchased_at": 12345 }
```

Contract상 날짜는 `string | null`입니다.

숫자 값이 통과하면 입력 검증이 설계와 일치하지 않는 것으로 보고하십시오. 임의 수정하지 말고 중단하십시오.

7. DB 무변경 검증
━━━━━━━━━━━━━━━━━━━━━━

테스트 전후 다음 값을 읽기 전용으로 비교하십시오.

```sql
SELECT COUNT(*) FROM audit_logs
WHERE entity_type = 'swimming_pool_xmode';

SELECT COUNT(*) FROM swimming_pools
WHERE xmode_entitlement = true
   OR xmode_config_status <> 'NOT_CONFIGURED';
```

제출:

* 테스트 전 건수
* 테스트 후 건수
* 차이

이번 테스트에서는 실제 존재하는 pool을 수정하지 않으므로 두 결과에 신규 변화가 없어야 합니다.

기존 X 상태 데이터가 이미 있다면 전체 건수가 아니라 테스트 시간 이후 생성된 Audit 행이 없는지 추가 확인하십시오.

8. 일반모드 영향 검증
━━━━━━━━━━━━━━━━━━━━━━

재시작 후 최소 확인:

* health check 200
* 기존 로그인 Route 접근 가능
* 기존 `/api/pools/my` Route가 Route Not Found가 아님
* 기존 `/api/pools/my-pools` Route가 Route Not Found가 아님
* 기존 일반 Route 등록 오류 없음
* 서버 시작 중 import/circular dependency 오류 없음
* `requireXMode`가 기존 일반 Route에 연결되지 않았는지 코드 검색

인증정보가 없으면 기존 Route의 인증 실패 401까지 확인하고, 정상 기능 통과라고 과장하지 마십시오.

정확한 상태는 다음처럼 구분하십시오.

```text
Route 등록 정상
인증 미보유로 기능 본문 미검증
```

9. 구현 코드 자체 확인
━━━━━━━━━━━━━━━━━━━━━━

최종 보고서에는 요약이 아니라 다음 실제 코드를 포함하십시오.

1. `git diff` 원문
2. `lib/xmode.ts` 전체
3. `GET /pools/x-mode` 전체
4. `requireXMode` 전체
5. `PATCH /super/operators/:id/xmode` 전체

특히 확인:

* PATCH 날짜 필드가 실제로 `string | null`만 허용하는지
* `result`가 Transaction 종료 후 항상 할당되는지
* `beforeData`와 `afterData` 변수명이 일치하는지
* `requireXMode`에서 `next()` 중복 호출 가능성이 없는지
* Promise `.then().catch()`에서 응답 후 실행이 계속되지 않는지
* parent_account 조회 테이블과 사용자 ID 연결 방식이 기존 코드와 일치하는지
