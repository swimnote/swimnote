[WP-N3B — NORMAL SWIMNOTE BUTTON POSITION / GROUP / SPACING UX NORMALIZATION]

목적:

WP-N3에서 Normal SWIMNOTE 버튼의 색상/역할 체계는 정리 완료했다.

이번 WP에서는 버튼의:

- 위치
- 정렬
- 그룹
- 간격
- 크기/폭
- visual priority
- 화면 내 action hierarchy

만 정리한다.

절대:

- 기능
- onPress
- API
- route
- state
- permission
- loading
- disabled
- submit logic

는 변경하지 않는다.

==================================================
2. CORE UX PRINCIPLE
==================================================

같은 종류의 화면에서는
같은 위치에 같은 종류의 action이 있어야 한다.

예:

폼 작성 화면
→ Primary submit은 화면 하단

목록 화면
→ 생성/추가 action은 일관된 header/top action

detail 화면
→ 수정/관리 action 위치 통일

modal
→ confirm / cancel 순서 통일

현재처럼 화면마다:

- 저장이 위
- 어떤 화면은 아래
- 어떤 화면은 우측
- 어떤 화면은 카드 중간

으로 제각각이면 정리한다.

==================================================
3. PRIMARY ACTION POSITION
==================================================

PRIMARY_ACTION은
한 화면에서 가장 쉽게 찾을 수 있어야 한다.

원칙:

A. FORM / CREATE / EDIT SCREEN

저장
등록
완료
다음
적용

→ form content 이후 하단 action area 우선

가능하면:
full-width 또는 명확한 dominant width

B. LIST / HUB SCREEN

추가
생성

→ header 또는 상단 action area

C. MODAL / SHEET

확인/저장
→ modal action area

화면 중간에 뜬금없이 primary CTA가 존재하면
현재 구조 확인 후 자연스러운 action 영역으로 이동 가능.

==================================================
4. SECONDARY ACTION GROUPING
==================================================

Primary와 연관된:

취소
이전
나중에
초기화
보조 선택

은 Primary 주변에서 group.

Primary와 너무 멀리 떨어뜨리지 않는다.

권장:

[Secondary] [Primary]

또는 모바일 vertical:

[Primary]
[Secondary text action]

현재 화면 구조에 맞게 선택.

==================================================
5. DESTRUCTIVE POSITION
==================================================

삭제
탈퇴
연결해제
영구삭제

는 Primary action과 시각적/공간적으로 분리.

금지:

[삭제] [저장]

이 동일 그룹에서 같은 우선순위처럼 보이는 구조.

가능하면:

main actions

...

danger zone

으로 분리.

단 기존 confirmation flow 변경 금지.

==================================================
6. NAVIGATION ACTION
==================================================

"자세히 보기"
"관리"
"설정"
"목록 보기"

같은 navigation action을
Primary CTA와 같은 하단 full-width 버튼으로 남발하지 않는다.

가능하면:

- list row
- chevron
- small text action
- card trailing action
- header action

등 기존 layout 안에서 정리.

기능/route는 동일한 handler 재사용.

==================================================
7. HEADER ACTION STANDARD
==================================================

Header 우측 action은:

- 검색
- 알림
- 추가
- 편집
- 설정
- 로그아웃

같은 빠른 action에 사용.

같은 성격의 화면에서
header action 위치가 다르면 통일.

단:

SubScreenHeader
ParentScreenHeader

같은 공통 component가 존재하면
공통 contract를 우선한다.

Touch target 축소 금지.

==================================================
8. FORM ACTION STANDARD
==================================================

입력 form 화면 감사.

다음 문제 탐지:

- 저장 버튼이 keyboard/input 사이에 끼어 있음
- 저장 버튼이 section 중간에 있음
- primary/secondary가 서로 멀리 떨어짐
- 버튼이 scroll 끝에 너무 붙음
- safe area 미고려

가능하면:

content
→ spacing
→ action group
→ safe-area padding

순서.

하지만 sticky bottom으로 전환하는 것은
레이아웃 영향이 크므로
기존 screen 구조를 확인하고 안전할 때만.

==================================================
9. STICKY BOTTOM RULE
==================================================

기존에 sticky bottom CTA가 있는 화면:

sticky 유지.

없는 화면을 무조건 sticky로 바꾸지 않는다.

sticky 적용이 유의미한 경우라도
이번 WP에서:

keyboard avoidance
ScrollView inset
safe-area
modal overlap

리스크가 있으면 이동하지 말고
HIGH_RISK로 보고.

==================================================
10. BUTTON WIDTH / SIZE
==================================================

같은 역할에서
버튼 폭이 제각각인 경우 정리.

예:

Primary form CTA:
→ 같은 screen family에서 일관된 width

Secondary:
→ Primary보다 dominance 낮게

작은 utility action:
→ full width 금지

하지만 현재 button component contract를
불필요하게 변경하지 않는다.

==================================================
11. SPACING SYSTEM
==================================================

버튼 주변 간격을 감사.

특히:

- button-to-button gap
- card-to-action gap
- section-to-primary CTA
- bottom safe-area
- header action gap

화면마다 임의 4/7/11/13px 식으로 흩어져 있으면
현재 프로젝트 spacing token 또는
가장 가까운 기존 spacing convention을 재사용.

새 spacing system 대규모 설계 금지.

==================================================
12. ACTION GROUP ORDER
==================================================

일반적인 모바일 UX에 맞춰 순서를 통일.

Primary/Secondary:

Korean mobile app 기준으로
화면 구조에 맞게 명확한 dominant primary 유지.

Modal:

cancel / confirm 순서는
현재 앱의 공통 ConfirmModal contract를 기준으로 통일.

같은 앱 안에서 modal마다
순서가 뒤집히지 않게 한다.

14. SCHEDULER PROTECTION
==================================================

Scheduler에서:

요일별 구분색
classColor
schedule bar
monthly dot
class chip

절대 변경 금지.

Scheduler 버튼도
이번 WP에서 위치를 무리하게 재구성하지 않는다.

특히:

날짜 이동
필터
반 선택
빠른 출결 action

은 사용 빈도가 높으므로
현재 muscle memory를 최대한 유지.

스케줄러 control UI의 색상/세부 정리는 WP-N4.

이번 WP에서는
명백히 잘못 배치된 action만 정리 가능.

15. PARENT UX

하지만:

AI 리포트

피드

==================================================
16. X MODE
==================================================

X에서도 동일 화면 구조를 공유하는 경우
버튼 위치 변경은 Normal/X 공통으로 반영될 수 있다.

본 작업은 특별히 X 전용으로 지정된 경우가 아니면
Normal/X 공통 기능으로 간주.

공통 source이면:

한 곳에서 layout 수정
→ Normal/X 둘 다 검증.

중요:

X theme color 변경 금지.

==================================================
17. FUNCTION LOCK — CRITICAL
==================================================

버튼을 이동할 때
기존 element 자체를 재사용하거나
handler를 정확히 그대로 연결한다.

절대 변경 금지:

onPress
onLongPress
handler function
API endpoint
mutation
router.push
router.replace
deep link
form submit
state setter
modal state
sheet state
loading
disabled
permission check
role condition
feature gate
double-tap guard
inFlight guard
confirmation step

버튼을 "새로 만들어서 비슷한 handler 연결"하지 말고
가능하면 기존 action component를 이동.

18. CONDITIONAL RENDER PROTECTION
==================================================

버튼 위치 변경 때문에:

role condition
permission
feature availability
subscription
mode
student state
request state

조건이 깨지면 안 된다.

기존 conditional wrapper와 action을
분리하지 않는다.

==================================================
19. FORM PROTECTION
==================================================

submit button이:

<form>
Formik
React Hook Form
custom submit context
keyboard flow

등과 결합되어 있다면
DOM/component tree 이동 시 기능 영향 가능.

이 경우:

handler-based direct action이면 이동 가능.

context-sensitive submit이면
SAFE_VISUAL_MOVE 여부 확인 후 처리.

HIGH_RISK이면
무리하게 이동하지 않고 보고.

==================================================
20. MODAL / SHEET PROTECTION
==================================================

Modal/Sheet의 action button은:

modal lifecycle
dismiss
confirmation
async state

와 강하게 결합될 수 있다.

공통 modal component 안에서
spacing/order만 수정하는 것은 허용.

modal 바깥으로 button 이동 금지.

==================================================
21. UX TARGET
==================================================

최종 느낌:

- 사용자가 다음 행동을 바로 찾을 수 있음
- 한 화면 primary action은 명확함
- secondary는 primary를 방해하지 않음
- destructive는 분리
- header action은 빠른 action 중심
- navigation은 navigation답게 보임
- 버튼이 화면마다 제멋대로 떠다니지 않음

하지만:

모든 화면을 똑같은 template으로 만들지 않는다.

기능 특성에 맞는 일관성.
