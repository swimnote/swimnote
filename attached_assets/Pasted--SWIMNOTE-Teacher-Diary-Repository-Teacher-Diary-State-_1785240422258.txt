# SWIMNOTE Teacher Diary 앱 Repository 기준 세부 설계 요청

## 작업 목적

Teacher Diary의 State Parser가 AI Engine에서 학생 이름과 `student_ref`를 정확히 연결할 수 있도록 앱의 Request Contract를 보완한다.

이번 작업은 구현이 아니다.

현재 앱 Repository를 분석하여 수정 파일, 함수, Contract, 화면 영향, 저장 영향, 테스트 범위를 포함한 세부 설계서만 작성한다.

코드를 수정하거나 구현하지 마라.

---

# SWIMNOTE AI 작업 헌법

1. 앱은 AI 분석을 하지 않는다.

앱의 역할은 다음뿐이다.

* 교사 음성 입력
* Whisper STT
* STT 원문 전달
* 학생 정보 전달
* AI 호출
* AI 결과 저장

2. State Parser, Name Matcher, Observation, Template Search, Knowledge Search, GPT는 모두 AI Engine에서 처리한다.

3. 앱은 학생 이름을 감지하거나 문장을 분리하지 않는다.

4. Whisper STT 원문을 수정·요약·정제·분석하지 않고 그대로 AI Engine에 전달한다.

5. App과 AI Engine은 Request / Response Contract로만 연결한다.

6. 기존 일지 저장 구조와 기존 기능을 깨지 않도록 Backward Compatibility를 유지한다.

7. 구현 전에 반드시 다음을 먼저 작성한다.

* Sequence Diagram
* Data Flow
* Request Contract
* Response Contract
* 영향 범위
* 테스트 계획

8. 현재 구조보다 더 단순한 구조가 있다면 반드시 제안한다.

특히 다음을 줄일 수 있는지 검토한다.

* 코드 줄 수
* 변환 로직
* 중복 타입
* API 호출 수
* 데이터 복사
* 기존 저장 로직 변경

# 현재 확인된 실제 구조

현재 AI Engine 경로가 두 개 존재하는 것으로 파악됐다.

## 구 SWIMNOTE API Server

```text
artifacts/api-server/src/routes/ai.ts
```

* Repository에서 코드 확인 가능
* 자체 GPT 직접 호출
* 학생 정보를 다음과 같이 전달한 이력이 있음

```json
[
  {
    "student_id": "student_xxx",
    "student_name": "서태웅"
  }
]
```

## Production AI Engine

```text
https://swimnote.ai.kr
```

* 현재 앱이 실제 호출 중인 대상
* 현재 Request에서는 다음 정보만 전달하는 것으로 보고됨

```json
{
  "context": {
    "student_refs": [
      "student_xxx",
      "student_yyy"
    ]
  }
}
```

* 학생 이름과 `student_ref`의 대응 관계가 없어 AI Engine State Parser가 이름을 학생 ID로 변환할 수 없음

이번 설계는 반드시 **현재 앱이 실제 호출하는 Production AI Engine 경로**를 기준으로 작성한다.

# 3. Request Contract 비교 설계

AI Engine State Parser가 필요한 최소 정보는 다음이다.

```text
학생 이름 발화
↓
학생 이름 매칭
↓
student_ref 확정
```

이를 위해 아래 두 계약을 비교한다.

## 방안 A — 기존 필드 확장

```json
{
  "context": {
    "student_refs": [
      "student_xxx",
      "student_yyy"
    ],
    "student_names": {
      "student_xxx": "서태웅",
      "student_yyy": "강민수"
    }
  }
}
```

## 방안 B — students 배열 추가

```json
{
  "context": {
    "student_refs": [
      "student_xxx",
      "student_yyy"
    ],
    "students": [
      {
        "ref": "student_xxx",
        "name": "서태웅",
        "given_name": "태웅"
      },
      {
        "ref": "student_yyy",
        "name": "강민수",
        "given_name": "민수"
      }
    ]
  }
}
```

두 방안을 다음 기준으로 비교한다.

* 기존 Production Contract와의 호환성
* 앱 코드 변경량
* AI Engine 파싱 난이도
* 중복 데이터 발생 여부
* Type 안정성
* 향후 별칭 추가 가능성
* 동명이인 처리 가능성
* 한국 이름 외 이름 지원 가능성
* Backward Compatibility
* 불필요한 개인정보 전송 최소화
* 테스트 용이성

가장 단순하면서 State Parser 요구사항을 충족하는 계약을 추천한다.

단, 실제 Production AI Engine이 이미 `student_names`를 지원하거나 변경 중이라면 기존 합의와 충돌하지 않도록 그 사실을 명확히 표시한다.

---

# 4. given_name 생성 위치 검토

`given_name`이 필요하다고 판단할 경우 다음 방안을 비교한다.

## 방안 A

앱에서 성을 제거하여 `given_name`을 생성한다.

## 방안 B

앱은 전체 이름만 전달하고 AI Engine Name Matcher가 전체 이름과 부분 이름을 처리한다.

## 방안 C

앱의 회원 데이터에 이미 별도 이름 필드가 존재한다면 그 값을 전달한다.

다음 원칙을 적용한다.

* 앱은 AI 분석을 하지 않는다.
* 한국 이름을 임의로 1글자 성 + 나머지 이름으로 분리하면 복성, 외국 이름, 별칭에서 오류가 발생할 수 있다.
* 단순 문자열 가공이 Contract 정규화인지 AI 판단인지 구분한다.
* 불필요한 이름 변환 로직은 앱에 추가하지 않는다.

가장 안전하고 단순한 방안을 추천한다.

# 8. 기존 저장 로직 영향

AI Response가 기존 일지 저장 구조에 어떻게 삽입되는지 조사한다.

다음을 실제 코드 기준으로 작성한다.

```text
common
→ 공통 일지 입력 위치

students[].student_ref
→ 기존 학생 찾기

students[].content
→ 해당 학생의 일지 입력 위치
```

반드시 다음 원칙을 유지한다.

* 학생별 내용이 없으면 빈 문자열 유지
* 공통 내용을 학생별 내용에 복사하지 않음
* AI가 반환하지 않은 학생에게 내용을 생성하지 않음
* 학생 순서가 달라도 `student_ref` 기준으로 매핑
* 기존 저장 함수와 DB 구조는 가능한 한 변경하지 않음
* 저장 실패와 AI 호출 실패를 구분

수정이 필요한 파일과 함수, 수정이 불필요한 파일을 나누어 작성한다.

# 11. Backward Compatibility

다음 상황을 모두 고려한다.

* 구 AI Engine은 `student_refs`만 인식
* 신 AI Engine은 학생 이름 필드를 추가 인식
* AI Engine이 구 Response를 반환
* AI Engine이 신 Response를 반환
* 학생 이름 필드가 없는 구 앱 요청
* 일부 학생 이름이 비어 있음
* 일부 학생 `student_ref`가 없음
* Production Feature Flag 전환
* 롤백 시 기존 호출 유지

필요한 Adapter 또는 fallback이 있다면 설계하되, 공통 내용을 학생별로 복사하는 fallback은 금지한다.

# 15. 단순화 제안

현재 구조보다 더 단순한 구조가 있다면 반드시 제안한다.

특히 다음 가능성을 검토한다.

1. 기존 `options.students[]`를 별도 중간 배열 없이 Request Builder에서 바로 직렬화할 수 있는지
2. `student_refs`와 `students`를 동시에 보내지 않고 하나의 구조만으로 호환성을 유지할 수 있는지
3. 별도 `given_name` 필드 없이 AI Engine Name Matcher가 전체 이름을 처리할 수 있는지
4. Response를 새 저장 구조로 변환하지 않고 기존 저장 함수 입력 형식으로 바로 매핑할 수 있는지
5. 신규 Service 없이 기존 AI API Client 내부의 작은 순수 함수로 처리할 수 있는지
6. Feature Flag 또는 Adapter를 최소화할 수 있는지

단순화 제안은 다음을 구분하여 작성한다.

* 즉시 적용 가능
* AI Engine Contract 확정 후 가능
* 장기적으로만 가능
* 적용하면 안 되는 제안
