SWIMNOTE X — WP6 최종 설계 정정 지시

현재 제출한 WP6 차단사항 해소 조사 결과는 대부분 유효하지만, 아직 구현 승인 상태가 아니다.

코드를 수정하지 말고 아래 항목만 정정한 최종 확정 설계서를 제출하라.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. student_ref 정의 정정
    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

다음 문장을 사용한다.

* student_ref와 student_id는 동일한 값이다.
* 별도 ID 변환 또는 이름 기반 매핑은 필요 없다.
* 그러나 요청으로 받은 student_ref가 실제로 JWT pool에 속한 학생인지는 DB 검증이 반드시 필요하다.
* 검증되지 않은 student_ref를 candidate search에 사용하면 안 된다.

다음 검증 흐름을 확정하라.

1. 요청 students[].ref 수집
2. students 테이블에서 id + swimming_pool_id 기준 검증
3. deleted_at IS NULL 적용
4. 검증된 student id만 candidate search에 전달
5. 요청 ref와 검증된 ref의 차이가 발생했을 때:
    * 전체 요청 403/400 처리
    * 또는 해당 학생만 제외
        기존 AI Diary Contract와 보안 원칙을 비교하여 하나를 확정

이름 기반 보정 금지.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. class 검증 정책 확정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

context.class_id와 students.class_group_id를 무조건 동일 처리하기 전에 기존 앱 흐름을 조사하라.

확인 대상:

* 정규 반 학생
* 보강으로 다른 반에 참여한 학생
* 반 이동 적용 전 학생
* 임시 합류 학생
* 미배정 학생
* 공통 일지만 생성하는 요청

다음 중 하나로 확정한다.

A. class_id 강제 일치
B. pool 소속만 강제하고 class는 보조 검증
C. 정규 학생과 보강·합류 학생을 구분하여 검증

실제 Repository 근거 없이 선택하지 마라.

3. curriculum assignment 구조 확정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

실제 DB 구조를 기준으로 다음 흐름을 사용한다.

student
→ student_curriculum_assignments.curriculum_version_id
→ curriculum_versions
→ curriculum_items

student_curriculum_assignments에 curriculum_item_id가 있다고 가정하지 않는다.

필수 조건:

* student_curriculum_assignments.is_active=true
* deactivated_at IS NULL 또는 기존 활성 정책과 일치
* swimming_pool_id=JWT pool
* curriculum_versions가 사용 가능한 상태인지 확인
* curriculum_items.is_active=true
* curriculum_items.swimming_pool_id=JWT pool

curriculum_versions의 실제 상태 컬럼을 조회하여 ACTIVE 판정 기준을 제출한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. Confidence V1 정책
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

V1에서는 AUTO_ACCEPTED를 사용하지 않는다.

허용 상태:

* PENDING_REVIEW
* match 없음

0.50은 검증 완료된 정확도 기준이 아니라 임시 후보 기준이다.

다음과 같이 명시한다.

reviewThreshold=0.50
status=EXPERIMENTAL_V1
근거=키워드 절반 이상 일치라는 초기 보수 기준
검증 상태=NEEDS_VERIFICATION
자동 승인=금지

GrowthConfidenceConfig 이름과 필드를 확정하라.

예:

interface GrowthConfidenceConfigV1 {
version: “growth_conf_v1”;
reviewThreshold: number;
}

잘못된 설정:

* 0 미만
* 1 초과
* NaN
* 비숫자

는 초기화 또는 호출 시 명확히 실패해야 한다.

환경변수 override를 도입할지 여부도 확정한다.
근거 없는 환경변수 확장은 금지한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. WP7 필수 주의사항 기록
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

growth_events.growth_match_status의 DB 기본값이 AUTO_ACCEPTED일 수 있으므로 WP7 INSERT 시 기본값에 의존하면 안 된다.

WP7에서는 반드시 명시적으로:

growth_match_status=‘PENDING_REVIEW’

를 저장하도록 고정 주의사항에 기록한다.

WP6에서는 DB INSERT하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. candidate 결과 구조
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

실제 DB에 없는 필드를 만들지 않는다.

* display_label = curriculum_items.title
* concept_tags = 생성 금지 또는 빈 배열 반환 여부를 기존 Contract 기준으로 확정
* description = curriculum_items.description
* curriculum_item_id = curriculum_items.id
* curriculum_version_id = curriculum_items.curriculum_version_id

concept_tags가 API 1.3 필수 필드로 확정돼 있다면, 임의 추출하지 말고 빈 배열을 반환한다.

GPT 또는 LLM으로 concept_tags를 생성하지 않는다.

candidate_id의 정확한 생성 규칙을 확정한다.

candidate_id가 curriculum item DB PK를 숨기기 위한 일회성 ID라면:

* 요청별 랜덤 ID
* candidate_id → 실제 item 매핑 정보는 match_token payload에 포함
* 서버 메모리 candidateMap에 의존하지 않음
* WP7은 match_token 검증으로 curriculum_item_id를 복원

형태와 길이를 제출하되 근거 없는 규칙을 추가하지 마라.

artifacts/api-server/src/lib/match-token.ts

각 필드의 포함 여부와 이유를 표로 제출한다.

필수 보안:

* HMAC-SHA256
* MATCH_TOKEN_SECRET 전용
* JWT_SECRET fallback 금지
* 24시간 만료
* Base64URL
* timingSafeEqual
* signature 길이 확인 후 비교
* token 원문 로그 금지
* payload 로그 금지
* 이름·전화번호 금지
* malformed token 안전 처리

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
8. match_token_id 정책
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

growth_events.match_token_id에는 전체 token 문자열을 저장하지 않는다.

권장 구조:

* payload의 token_id를 저장
* token_id는 충분한 랜덤성을 가진 불투명 ID
* UNIQUE partial index로 재사용 차단
* WP7에서 동일 token_id 존재 시 replay 거부

다음 내용을 확정한다.

* token_id 생성 방식
* 길이
* prefix 여부
* 충돌 가능성
* WP7 중복 처리 오류 코드
* 만료와 replay의 처리 순서

WP6는 token 생성만 한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. MATCH_TOKEN_SECRET 정책
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

로컬 및 서버 동작:

* normal + contract 1.0: 영향 없음
* normal + contract 1.3: token 생성 없음
* x_pending + contract 1.3: token 생성 없음
* x + contract 1.0: 기존 응답, token 없음
* x + contract 1.3 + secret 없음: 503 X_MODE_TOKEN_NOT_CONFIGURED

서버 전체 기동은 중단하지 않는 lazy fail을 사용한다.

단, 운영 배포 조건:

* Render MATCH_TOKEN_SECRET=SET 증거 필수
* MATCH_TOKEN_KEY_ID 정책 확정
* secret 미검증 상태에서는 Render 배포 금지

index.ts 또는 금지 파일에 경고 코드를 추가하지 않는다.
기존 수정 허용 파일 범위 안에서만 처리한다.

pre-deploy script 추가는 WP6 공식 파일 범위 밖이므로 이번 구현에서 제외한다.
