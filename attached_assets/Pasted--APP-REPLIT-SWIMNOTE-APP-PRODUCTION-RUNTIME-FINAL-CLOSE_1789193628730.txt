1. BLOCKER — Scheduler가 현재 Production에서 죽어 있음
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

현재 보고:

swimnote-worker = suspended

그리고:

startGrowthReportScheduler()

는 IS_WORKER=true 경로에서만 실행됩니다.

swimnote-api는 Scheduler를 실행하지 않습니다.

따라서 현재 Production에서는
Growth Report Monthly Scheduler가 실제로 실행되지 않는 상태입니다.

이 상태는 절대 PASS가 아닙니다.

최종 목표:

사람이 아무것도 하지 않아도

새 report month 도래
→ cycle 생성/확인
→ cohort freeze
→ report 준비
→ analysis worker 처리
→ 5일 관리자 검수 대기

가 자동으로 시작되어야 합니다.

현재 실제 Render deployment 구조를 조사하여

기존 distributed lock으로 중복 실행 방지

Production에서 항상 살아 있는 실행 주체가 있어야 합니다.

9. DB Connection 안정화
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

최소한 rolling deploy 중
old + new instance가 잠시 겹쳐도
DB connection 한도를 넘지 않도록 하십시오.

가능한 해결은 실제 구조를 보고 선택하십시오.

예:

- API/worker pool max 적정화
- startup DB init 직렬화
- migration connection 별도/단일화
- startup retry/backoff
- transient connection exhaustion 시 즉시 process.exit 금지
- graceful shutdown 확실히 보장

단,
DB 오류를 무시하고 서버를 띄우는 식으로
안전성을 낮추면 안 됩니다.

필수 DB init이 실패하면
bounded retry/backoff 후 실패하도록 하십시오.
