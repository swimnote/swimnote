아직 코드 수정하지 말 것.
OTA/Render 배포 금지.

목표:
현재 SWIMNOTE APP에 존재하는
모든 "일지 작성 / 일지 목록 / 일지 상세" 진입 경로를 전수 조사하고,
중복 화면과 불필요한 navigation을 제거한
최종 단일 일지 구조 설계안을 제출한다.

0. 제품 UX 원칙 — 절대 기준
━━━━━━━━━━━━━━━━━━━━━━

사용자가 확정한 원칙:

1.
일지 관련 진입 경로는 많으면 안 된다.

2.
일지 작성 화면 상단에는
이미 날짜/요일 변경 UI가 존재한다.

따라서 다른 날짜의 일지로 이동하려면
작성 화면 안의 날짜/요일 변경 UI를 사용한다.

별도 날짜별 일지 화면을 계속 만들지 않는다.

3.
다른 반의 일지를 보고/작성하고 싶으면
일지 화면 안에서 반을 다시 선택하지 않는다.

반 변경은:

일지 화면
→ 스케줄러로 복귀
→ 시간표에서 다른 반 선택
→ 해당 반의 일지 진입

으로 고정한다.

4.
"반 선택 + 날짜 선택 + 일지 선택"을
여러 화면에서 반복시키지 않는다.

5.
가능하면:
- 일지 목록 = 1개
- 일지 작성 화면 = 1개
- 일지 상세 화면 = 1개

로 통일하고,
진입 경로마다 context/filter만 다르게 전달한다.

━━━━━━━━━━━━━━━━━━━━━━
1. 현재 존재하는 모든 일지 화면 전수 조사
━━━━━━━━━━━━━━━━━━━━━━

코드 기준으로 아래를 전부 찾는다.

A. Teacher
- 홈 → 일지 바로쓰기
- 스케줄러 → 수업 카드 → 수업일지
- 날짜 선택 → 수업 → 일지
- 기타 Teacher 일지 진입
- 일지 작성
- 일지 목록
- 일지 상세
- 수정/재열기

B. Admin
- 관리자 전체 일지
- 회원관리 → 학생 → 일지
- X Dashboard → AI 일지
- 기타 관리자 일지 진입

C. Parent
- 학부모 피드/일지 보기
- 학생별 일지 상세
- 해당 화면이 관리자/선생님 Diary와 어떤 data source를 공유하는지

각 경로마다 제출:

- 진입 화면
- route path
- component 파일
- 호출 API
- DB source
- 전달 params
- back 동작
- home 이동 여부
- 중복되는 다른 화면

━━━━━━━━━━━━━━━━━━━━━━
2. 화면별 기능 비교표
━━━━━━━━━━━━━━━━━━━━━━

현재 존재하는 각 일지 목록/작성/상세 화면의 기능을 비교.

최소 비교:

- 날짜 변경
- 요일 변경
- 반 context
- 학생 context
- AI/일반 구분
- 검색
- 날짜 필터
- 선생님 필터
- 학생 필터
- 사진
- 영상
- 공통 일지
- 학생별 일지
- AI 생성
- STT
- 저장
- 수정
- 재열기
- 상세
- 뒤로가기
- 무한스크롤
- 관리자 조회
- Teacher 조회

기능 누락 여부를 반드시 표시.

예:
SCREEN A에는 사진 있음 / SCREEN B에는 없음
SCREEN A에는 학생별 내용 있음 / SCREEN B에는 없음

이런 차이를 정확히 제출.

3. Canonical 화면 후보 선정
━━━━━━━━━━━━━━━━━━━━━━

각 용도별로 가장 기능이 완전한 화면을 하나씩 선정.

후보:

- canonical diary list
- canonical diary write
- canonical diary detail

선정 기준:

- 현재 Production에서 가장 안정적
- 기능 누락이 가장 적음
- AI/일반 모두 처리 가능
- Teacher/Admin context 재사용 가능
- 기존 API/DB와 가장 잘 연결됨

새 화면을 만들기보다
기존 가장 완전한 화면을 재사용하는 방향 우선.

━━━━━━━━━━━━━━━━━━━━━━
4. 최종 진입 구조 설계
━━━━━━━━━━━━━━━━━━━━━━

사용자 원칙에 맞게
최종 navigation을 아래처럼 단순화할 수 있는지 설계.

[Teacher]

A.
홈 → 일지 바로쓰기
→ 반 선택 또는 오늘 수업 선택
→ canonical diary write

B.
스케줄러 → 특정 수업 카드 → 수업일지
→ 해당 class/date context를 그대로 전달
→ canonical diary write 또는 canonical diary list

중요:
이미 class/date를 알고 있으면 다시 고르게 하지 말 것.

C.
다른 날짜 이동
→ diary write 상단 날짜/요일 변경 UI

D.
다른 반 이동
→ diary 화면 내부에서 반 선택 UI 추가 금지
→ 스케줄러로 복귀
→ 다른 수업 선택

[Admin]

E.
관리자 전체 일지
→ canonical diary list

F.
회원관리 → 학생 → 일지
→ canonical diary list + student filter

G.
X Dashboard → AI 일지
→ canonical diary list + ai filter

[Detail]

H.
어떤 경로에서 들어와도
→ canonical diary detail

I.
뒤로가기
→ 직전 목록/작성 화면 + 기존 context 유지

━━━━━━━━━━━━━━━━━━━━━━
5. 제거 후보 경로
━━━━━━━━━━━━━━━━━━━━━━

현재 아래와 같은 중복 경로가 있다면
삭제/비노출 후보로 표시:

- 별도 AI 일지피드 화면
- 별도 날짜별 일지 목록
- 별도 반 선택 후 또 날짜 선택하는 중간 화면
- 같은 diary data를 다른 API로 읽는 중복 관리자 화면
- 일지 카드 클릭 시 홈으로 보내는 legacy route
- 동일 기능의 Teacher/Admin 중복 목록

이번 단계에서는 삭제하지 말고
"제거 후보"로만 분류.

━━━━━━━━━━━━━━━━━━━━━━

- 저장/수정/재열기

- 관리자 조회

- AI 필터

- 기존 Parent 노출

- Local Curriculum progress 연결

━━━━━━━━━━━━━━━━━━━━━━
7. 날짜/반 UX 최종 검토
━━━━━━━━━━━━━━━━━━━━━━

반드시 사용자 원칙과 충돌하는 UI가 있는지 찾아라.

날짜:
- diary write 상단 날짜/요일 변경 UI를 canonical로 사용
- 다른 날짜 화면을 별도로 만들 필요 있는지 검토
- 불필요하면 제거 후보

반:
- diary 화면 안에서 반 변경 UI 추가 금지
- 다른 반은 scheduler를 통해 이동
- 현재 class context는 scheduler 진입 시 전달

이 원칙이 현재 코드와 충돌하는 지점 모두 제출.

━━━━━━━━━━━━━━━━━━━━━━
8. Back Navigation 설계
━━━━━━━━━━━━━━━━━━━━━━

경로별 기대값 제출.

예:

Scheduler
→ Diary Write
→ Back
= Scheduler의 기존 날짜/스크롤 위치

Admin Diary List
→ Detail
→ Back
= 기존 list + filter 유지

Member Detail
→ Diary List(student filter)
→ Detail
→ Back
= student-filtered Diary List

X Hub
→ Diary List(AI filter)
→ Detail
→ Back
= AI-filtered Diary List

Home으로 강제 이동하는 route/replace 코드가 있으면 전부 표시.
