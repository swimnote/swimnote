[SWIMNOTE — 사진 전체앨범 업로드 순서 근본 수정]

조사 결과 승인합니다.

확정 ROOT CAUSE:

photo_assets_meta.sort_order가

1. 최초 사진 업로드 시:
   전체앨범 업로드 순서 0..N-1

2. 이후 diary/student-note 등에 사진 첨부 시:
   해당 첨부 컨텍스트 내부 순서 0..K

라는 서로 다른 두 의미로 재사용되고 있습니다.

따라서 일지 첨부 후 sort_order가 덮어써지고,
GET /photos/teacher-all이:

created_at DESC,
sort_order ASC,
id ASC

로 정렬하면서 최초 업로드 순서가 파괴됩니다.

이번에는 이 의미 충돌을 근본적으로 분리하십시오.

광범위 조사 금지.

[A]

photos.tsx의 실제 ImagePicker 설정에서
한 번에 선택 가능한 최대 장수를 확인하십시오.

특히:

selectionLimit

실제 값을 보고하십시오.

만약 최대 50장 이하라면
현재 BATCH_SIZE=50이므로
picker 1회 = direct-upload session 1개가 보장됩니다.

만약 50장 초과 선택 가능하면
picker 1회가 여러 session으로 나뉠 수 있으므로
별도 upload batch 식별까지 필요합니다.

[B]

photo_assets_meta.sort_order를 UPDATE하는
현재 attachment 관련 write site만 검색하십시오.

예:

- diary attach
- student note attach

sort_order가 현재
“첨부 컨텍스트 내부 순서”로 실제 사용되고 있는지 확인.

이 의미는 유지합니다.

━━━━━━━━━━━━━━━━━━━━━━
1. 핵심 정책
━━━━━━━━━━━━━━━━━━━━━━

앞으로 필드 의미를 분리합니다.

sort_order
=
일지/학생별 추가일지 등
첨부 컨텍스트 내부 표시 순서

upload_sort_order
=
사진 전체앨범에서
사용자가 picker에서 선택한 최초 순서

upload_sort_order는
사진 최초 생성 이후 절대로 변경하지 않습니다.

diary attach / note attach가
upload_sort_order를 UPDATE해서는 안 됩니다.

━━━━━━━━━━━━━━━━━━━━━━
2. DB MIGRATION
━━━━━━━━━━━━━━━━━━━━━━

photo_assets_meta에 nullable 컬럼 추가:

upload_sort_order INTEGER

기존 데이터 전체 backfill 금지.

이유:

기존 sort_order는 이미 diary attach 등에 의해
변경된 row가 존재하므로
원래 업로드 순서를 신뢰성 있게 복원할 수 없습니다.

새 업로드부터 정확히 보존합니다.

기존 row:
upload_sort_order = NULL

허용.

━━━━━━━━━━━━━━━━━━━━━━
3. 50장 이하가 보장되는 경우
━━━━━━━━━━━━━━━━━━━━━━

PRECHECK 결과:

ImagePicker selectionLimit <= 50

이고

picker 1회가 항상 direct-upload session 1개라면

추가 batch 컬럼 만들지 마십시오.

APP에서 result.assets 전체 기준 index:

0,1,2,...N-1

를 각 파일의:

upload_sort_order

로 session API에 전달.

서버가 photo_assets_meta INSERT 시
그 값을 그대로 저장.

finalize에서는 변경 금지.

이 경우 같은 picker session의 created_at이
이미 공통이므로

teacher-all 최종 정렬:

ORDER BY
  sp.created_at DESC,
  sp.upload_sort_order ASC NULLS LAST,
  sp.sort_order ASC NULLS LAST,
  sp.id ASC

의미:

신규 사진:
upload_sort_order 사용

기존 legacy 사진:
upload_sort_order NULL이므로
기존 sort_order/id fallback

단 실제 SQL에서 NULLS LAST 때문에
신규/legacy 혼재 시 이상한 순서가 생긴다면

CASE/COALESCE를 사용해
동일 created_at 그룹에서 안정적으로 처리하십시오.

실제 데이터 의미에 맞게 최소 구현.

━━━━━━━━━━━━━━━━━━━━━━
4. 50장 초과 선택이 가능한 경우
━━━━━━━━━━━━━━━━━━━━━━

PRECHECK 결과
picker 1회가 2개 이상 session으로 분리될 수 있다면

upload_sort_order만 추가해서 끝내지 마십시오.

그 경우 picker 1회 전체를 식별하는 nullable:

upload_batch_id

도 추가하십시오.

APP에서 picker 완료 직후
batch id를 딱 1개 생성.

같은 picker selection에서 생성되는
모든 session/chunk에
동일 upload_batch_id를 전달.

그리고 upload_sort_order는
session-local index가 아니라
picker 전체 global index:

0..N-1

를 유지.

예:

51장:

session1:
upload_sort_order 0..49

session2:
upload_sort_order 50

이어야 함.

0으로 reset 금지.

batch id 생성은
기존 APP의 ID 생성 helper가 있으면 재사용.
새 dependency 추가 금지.

━━━━━━━━━━━━━━━━━━━━━━
5. MULTI-SESSION 정렬
━━━━━━━━━━━━━━━━━━━━━━

upload_batch_id가 필요한 구조라면
session마다 created_at이 다르므로:

created_at DESC를 최우선으로 두면
session chunk가 역순으로 나올 수 있습니다.

따라서 teacher-all에서는

동일 upload_batch_id 전체를
하나의 업로드 묶음으로 취급하고

묶음 최신순
→ upload_sort_order ASC

가 되도록 쿼리하십시오.

새 batch table은 만들지 마십시오.

현재 row들의 created_at을 이용하여
동일 batch의 대표 시각:

MAX(created_at)

등을 query에서 계산할 수 있으면
그 방식을 사용하십시오.

legacy upload_batch_id IS NULL row는
기존 created_at 기준 정렬 유지.
